# ADR-0012: Outbox Pattern

> **Status:** Accepted  
> **Date:** 2026-08-09  
> **Decision Type:** Data Consistency / Event Publishing  
> **Scope:** Reliable publication of domain and integration events from RideForge transactional services  
> **Owner:** RideForge Architecture / Engineering  
> **Supersedes:** None  
> **Superseded By:** None

---

# 1. Context

RideForge uses a distributed, event-driven architecture built around:

```text
Go Services
PostgreSQL
Redis
Redpanda
Domain Events
Integration Events
Asynchronous Consumers
```

Important business operations frequently require two related actions:

```text
1. Change durable transactional state
2. Publish an event
```

For example:

```text
Create Ride
      ↓
PostgreSQL Transaction
      +
RideCreated Event
      ↓
Redpanda
```

A direct implementation can create a consistency problem.

Consider:

```text
BEGIN
    Update PostgreSQL
COMMIT

Publish Event
    ↓
Failure
```

The database transaction succeeds, but the event is never published.

The opposite failure is also possible:

```text
Publish Event
    ↓
Database Transaction
    ↓
Failure
```

The event exists even though the business transaction did not complete.

RideForge therefore requires a reliable mechanism for coordinating:

```text
Transactional State
```

with:

```text
Event Publication
```

without requiring a distributed transaction across PostgreSQL and Redpanda.

---

# 2. Problem

RideForge must reliably publish events generated by successful database transactions while preventing the following conditions:

```text
Committed State Without Event
Event Without Committed State
Lost Events
Duplicate Processing
Unbounded Publisher Retry
Inconsistent Event Ordering
```

The solution must work with:

```text
PostgreSQL
Redpanda
Go Services
Microservices
Event Consumers
Retries
Dead Letter Queues
```

---

# 3. Decision

RideForge will use:

> **The Transactional Outbox Pattern for reliable publication of events originating from PostgreSQL-backed business transactions.**

The core flow is:

```text
Application
    ↓
BEGIN PostgreSQL Transaction
    │
    ├── Update Business State
    │
    └── Insert Outbox Event
    │
COMMIT
    ↓
Outbox Publisher
    ↓
Redpanda
```

The business state and outbox record are committed atomically in the same PostgreSQL transaction.

The outbox publisher is responsible for asynchronously publishing committed outbox records to Redpanda.

---

# 4. Core Principle

> **If a business transaction requires a durable event to be published, the business state change and the corresponding outbox record must be committed in the same database transaction.**

This establishes:

```text
Business State
+
Outbox Event
=
One PostgreSQL Transaction
```

---

# 5. Why the Outbox Pattern

Without an outbox:

```text
PostgreSQL
    ↓
Commit
    ↓
Redpanda
    ↓
Failure
```

the event can be lost.

With the outbox:

```text
PostgreSQL Transaction
       │
       ├── Business State
       │
       └── Outbox Record
              ↓
           COMMIT
              ↓
       Outbox Publisher
              ↓
          Redpanda
```

The event record survives application or broker failures after the transaction commits.

---

# 6. Atomicity Boundary

The atomicity boundary is:

```text
PostgreSQL
```

The following belong to the same transaction:

```text
Business State Change
Outbox Record
```

Redpanda publication happens asynchronously after the PostgreSQL transaction commits.

RideForge does not require a distributed transaction between PostgreSQL and Redpanda.

---

# 7. Example: Ride Creation

A ride creation transaction may conceptually perform:

```text
BEGIN

INSERT ride

INSERT outbox_event:
    type = RideCreated
    aggregate_id = ride_id
    payload = event payload

COMMIT
```

After commit:

```text
Outbox Publisher
      ↓
Reads RideCreated
      ↓
Publishes to Redpanda
      ↓
Marks Outbox Record Published
```

---

# 8. Example: Driver Assignment

A driver assignment may perform:

```text
BEGIN

UPDATE ride
SET driver_id = ...

INSERT outbox_event:
    type = DriverAssigned
    aggregate_id = ride_id

COMMIT
```

The event is then published asynchronously.

---

# 9. Outbox Record

An outbox record should contain sufficient information to publish and operate the event reliably.

A conceptual model is:

```text
id
event_id
aggregate_type
aggregate_id
event_type
payload
headers / metadata
created_at
published_at
attempts
available_at
last_error
```

The exact schema is implementation-specific.

---

# 10. Event Identity

Every outbox event should have a globally unique event identifier.

Conceptually:

```text
event_id
```

This identifier should remain stable across publisher retries.

For example:

```text
Attempt 1
→ event_id = E123

Attempt 2
→ event_id = E123

Attempt 3
→ event_id = E123
```

The publisher must not generate a new event identity for every retry.

---

# 11. Why Stable Event Identity Matters

Stable event identity supports:

```text
Deduplication
Tracing
Debugging
Consumer Idempotency
Operational Investigation
```

It also provides a common identifier across:

```text
PostgreSQL
Outbox
Redpanda
Consumer Logs
Consumer State
```

---

# 12. Aggregate Identity

Events should identify the domain aggregate or entity they relate to.

Examples:

```text
aggregate_type = ride
aggregate_id   = ride_id
```

or:

```text
aggregate_type = driver
aggregate_id   = driver_id
```

This supports:

```text
Partitioning
Ordering
Tracing
Debugging
Consumer Processing
```

---

# 13. Event Type

The event type should represent a domain or integration fact.

Examples:

```text
RideCreated
RideCancelled
DriverAssigned
RideStarted
RideCompleted
DriverAvailabilityChanged
```

Event names should describe something that happened rather than an imperative command.

Prefer:

```text
RideCreated
```

over:

```text
CreateRide
```

---

# 14. Event Payload

The outbox should store the event payload required by the event contract.

The payload should be:

```text
Explicit
Versionable
Serializable
Stable
Minimal
```

Avoid placing unrelated internal database fields into event payloads.

---

# 15. Event Envelope

RideForge events should use a consistent event envelope.

A conceptual envelope is:

```text
event_id
event_type
event_version
aggregate_type
aggregate_id
occurred_at
producer
correlation_id
causation_id
payload
```

The exact envelope is governed by the event and messaging development standards.

---

# 16. Event Version

Events should support explicit versioning where the contract is expected to evolve.

For example:

```text
event_type   = RideCreated
event_version = 1
```

A schema change should not silently change the meaning of an existing event version.

---

# 17. Occurred Time vs Published Time

These timestamps have different meanings.

```text
occurred_at
→ When the business event occurred

published_at
→ When the outbox publisher successfully published it
```

The two timestamps must not be conflated.

---

# 18. Correlation ID

The event should preserve correlation information where available.

Example:

```text
HTTP Request
    ↓
Ride Creation
    ↓
RideCreated Event
    ↓
Matching Service
```

A shared correlation identifier helps trace the workflow across services.

---

# 19. Causation ID

Where one event or command causes another event, RideForge may preserve causation information.

Conceptually:

```text
Command A
   ↓
Event B
   ↓
Event C
```

`causation_id` can identify the event or command that caused the current event.

---

# 20. Outbox Table Ownership

Each service should own its transactional outbox according to its database ownership model.

A service should not directly write another service's outbox table.

For example:

```text
Ride Service
    ↓
Ride Service Database
    ↓
Ride Service Outbox
```

---

# 21. Database Ownership

The outbox pattern does not change domain ownership.

The owning service remains responsible for:

```text
Business State
Outbox Record
Event Contract
Event Publication
```

where that service owns the transaction.

---

# 22. Outbox Table Design

A conceptual table may be:

```text
outbox_events
```

with fields such as:

```text
id
event_id
aggregate_type
aggregate_id
event_type
event_version
payload
occurred_at
created_at
published_at
available_at
attempts
last_error
```

Additional fields may be introduced based on operational requirements.

---

# 23. Primary Key

The outbox record should have a stable primary key.

The event identifier should also be uniquely constrained where appropriate.

Conceptually:

```text
PRIMARY KEY (id)

UNIQUE (event_id)
```

The exact schema depends on the implementation.

---

# 24. Payload Storage

The payload may be stored in a PostgreSQL-native structured representation such as JSON/JSONB when appropriate.

The choice should consider:

```text
Payload Size
Query Requirements
Serialization
Indexing
Schema Evolution
```

The outbox is primarily a delivery buffer, not an analytics store.

---

# 25. Payload Size

Outbox payloads should remain reasonably small.

Avoid storing:

```text
Large Documents
Binary Objects
Complete Historical Records
Unbounded Collections
```

If consumers require large data, prefer:

```text
Reference
+
Authoritative Storage
```

rather than embedding large payloads in every event.

---

# 26. Transactional Write

The application should write business state and the outbox event using the same database transaction.

Conceptually:

```text
tx.Begin()

businessOperation(tx)

outboxRepository.Insert(tx, event)

tx.Commit()
```

The outbox repository should participate in the caller's transaction.

---

# 27. Repository Design

The application layer should avoid independently committing the outbox record.

Prefer:

```text
Application Service
      ↓
Transaction Boundary
      ├── Domain Repository
      └── Outbox Repository
```

rather than:

```text
Business Repository
    ↓
COMMIT

Outbox Repository
    ↓
Separate COMMIT
```

---

# 28. Transaction Failure

If the business transaction fails:

```text
Business State
→ Rolled Back

Outbox Record
→ Rolled Back
```

No event should be published for the failed transaction.

---

# 29. Outbox Insert Failure

If the business operation succeeds but the outbox insert fails:

```text
Transaction
→ Rollback
```

The business state must not commit without the required outbox record.

---

# 30. Database Commit Failure

If PostgreSQL cannot commit:

```text
Business State
→ Not Committed

Outbox
→ Not Committed
```

The publisher should never see an outbox record from an uncommitted transaction.

---

# 31. Publisher Responsibility

The outbox publisher is responsible for:

```text
Finding Pending Events
Publishing Events
Retrying Failures
Recording Publication State
Handling Poison Events
Maintaining Observability
```

It should not contain business-domain transaction logic.

---

# 32. Polling Publisher

The initial implementation may use polling:

```text
Outbox Publisher
      ↓
Query Pending Records
      ↓
Claim / Process
      ↓
Publish
      ↓
Mark Published
```

Polling is intentionally simple and reliable.

---

# 33. Polling Frequency

The polling interval should balance:

```text
Event Publication Latency
Database Load
Publisher Throughput
```

Avoid aggressive polling that repeatedly scans an empty outbox table.

---

# 34. Batch Processing

The publisher should process events in bounded batches.

Conceptually:

```text
Fetch N Events
      ↓
Publish
      ↓
Mark Successful
      ↓
Fetch Next Batch
```

Batch size should be configurable.

---

# 35. Bounded Batches

Avoid loading the entire outbox table into memory.

Use:

```text
LIMIT
```

or an equivalent bounded retrieval strategy.

---

# 36. Pending Event Selection

Pending events may be selected using:

```text
published_at IS NULL
```

combined with an availability policy such as:

```text
available_at <= now()
```

The exact query depends on retry and claim semantics.

---

# 37. Outbox Indexing

Indexes should support the publisher's actual access pattern.

A typical access pattern may require an index involving:

```text
published_at
available_at
created_at
```

The exact index should be validated using PostgreSQL query plans.

---

# 38. Locking and Claiming

Multiple publisher workers may process the outbox concurrently.

The system must avoid uncontrolled duplicate claims.

PostgreSQL mechanisms such as row-level locking and:

```text
FOR UPDATE SKIP LOCKED
```

may be used where appropriate.

---

# 39. Concurrent Publishers

A service may eventually run multiple outbox publisher workers:

```text
Publisher A
Publisher B
Publisher C
       ↓
Shared Outbox
```

The claiming mechanism must allow workers to process different records safely.

---

# 40. Publication Semantics

The outbox pattern generally provides:

> **At-least-once event publication semantics.**

This means an event may be published more than once in certain failure scenarios.

Consumers must therefore be idempotent.

---

# 41. Why Duplicates Can Occur

Consider:

```text
Publisher
   ↓
Publish to Redpanda
   ↓
Redpanda accepts event
   ↓
Publisher crashes
   ↓
published_at not updated
```

After restart:

```text
Publisher
   ↓
Sees event as pending
   ↓
Publishes again
```

The same event may therefore appear more than once.

---

# 42. Exactly-Once Assumption

RideForge must not depend on an unrealistic global exactly-once assumption across:

```text
PostgreSQL
PgBouncer
Application
Redpanda
Consumers
```

Instead:

```text
Outbox
→ At-Least-Once Publication

Consumers
→ Idempotent Processing
```

---

# 43. Consumer Idempotency

Consumers should use the stable:

```text
event_id
```

to prevent duplicate business effects where required.

For example:

```text
Processed Event IDs
        ↓
event_id = E123
        ↓
Already Processed?
   ├── Yes → Ignore
   └── No  → Process
```

---

# 44. Idempotency Boundary

Consumer idempotency is a separate concern from outbox reliability.

The responsibilities are:

```text
Outbox
→ Reliable Event Publication

Consumer Idempotency
→ Safe Duplicate Handling
```

---

# 45. Publication Acknowledgement

An event should be considered published only after the Redpanda producer confirms successful acceptance according to the producer's configured acknowledgement policy.

The publisher must not mark an event as published merely because it attempted to send it.

---

# 46. Marking Published

After successful publication:

```text
UPDATE outbox_events
SET published_at = ...
```

The update should identify the exact event being marked.

---

# 47. Publication Failure

If publication fails:

```text
published_at remains NULL
```

and the event becomes eligible for retry according to the retry policy.

---

# 48. Retry Strategy

Retries should use:

```text
Bounded Attempts
Exponential Backoff
Jitter
Available-At Timestamp
```

where appropriate.

Avoid tight retry loops.

---

# 49. Retry Schedule

A conceptual schedule is:

```text
Attempt 1
   ↓
Failure
   ↓
Short Delay
   ↓
Attempt 2
   ↓
Failure
   ↓
Longer Delay
   ↓
Attempt 3
```

The exact values belong to configuration.

---

# 50. Retry Classification

Failures should be classified where possible.

### Transient Failures

Examples:

```text
Temporary Network Failure
Broker Unavailable
Connection Timeout
Temporary Resource Exhaustion
```

These should generally be retried.

### Permanent / Poison Failures

Examples:

```text
Invalid Event Payload
Unsupported Event Schema
Unrecoverable Serialization Error
```

These require controlled failure handling.

---

# 51. Dead Letter Queue

Events that cannot be successfully published after the configured retry policy may require a dead-letter or quarantine mechanism.

RideForge already defines a DLQ strategy separately.

The relationship is:

```text
Outbox
   ↓
Retry
   ↓
Failure
   ↓
DLQ / Quarantine
```

The exact DLQ design is governed by ADR-0013.

---

# 52. Outbox vs DLQ

These are not interchangeable.

```text
Outbox
→ Pending Durable Events

DLQ
→ Events That Require Exceptional Handling
```

The outbox is the normal delivery mechanism.

The DLQ is an exception path.

---

# 53. Poison Events

A poison event should not block unrelated events indefinitely.

For example:

```text
Event A → Fails Permanently
Event B → Valid
Event C → Valid
```

The system should be able to continue processing B and C according to the required ordering guarantees.

---

# 54. Ordering

Event ordering requirements must be explicit.

RideForge should distinguish:

```text
Global Ordering
Aggregate Ordering
Partition Ordering
No Ordering Requirement
```

Global ordering should not be assumed.

---

# 55. Aggregate Ordering

When ordering matters for a specific aggregate, the event stream should use an appropriate key.

For example:

```text
aggregate_id = ride_id
```

can be used as the partitioning key so events for the same ride are routed consistently.

---

# 56. Event Ordering Example

For a ride:

```text
RideCreated
    ↓
DriverAssigned
    ↓
RideStarted
    ↓
RideCompleted
```

Ordering may matter within the ride aggregate.

The event publication design should preserve the required ordering semantics.

---

# 57. Concurrent Aggregate Updates

If multiple transactions modify the same aggregate concurrently, the application must establish the required transactional ordering before events are written.

The outbox does not automatically solve business-level concurrency conflicts.

---

# 58. Outbox Ordering Field

An implementation may use fields such as:

```text
created_at
sequence
aggregate_version
```

to help preserve or diagnose ordering.

The exact mechanism depends on the domain requirements.

---

# 59. Aggregate Version

For stateful aggregates, an aggregate version can help establish:

```text
Version 1
Version 2
Version 3
```

and detect out-of-order processing.

---

# 60. Event Publication Latency

The outbox introduces asynchronous publication.

Therefore:

```text
Database Commit
```

and:

```text
Event Publication
```

are not instantaneous.

The platform should define acceptable event publication latency.

---

# 61. Eventual Consistency

Consumers may observe state changes after the originating transaction commits.

Therefore RideForge accepts eventual consistency for appropriate asynchronous workflows.

Critical transactional invariants must remain enforced within the authoritative database transaction.

---

# 62. Critical Invariants

The outbox should not be used to defer an invariant that must be enforced synchronously.

For example:

```text
Unique Ride Assignment
Payment Balance
Ride State Transition
```

should be protected by:

```text
Database Constraints
Transactions
Domain Validation
```

where required.

---

# 63. Outbox Is Not a Workflow Engine

The outbox should not become a general-purpose workflow engine.

It is responsible for:

```text
Reliable Event Publication
```

not:

```text
Long-Running Business Workflow
Scheduling
Complex Orchestration
```

Those concerns belong elsewhere.

---

# 64. Outbox Is Not an Event Store

The outbox is a delivery mechanism.

It should not automatically become the permanent source of historical events.

After successful publication, records may eventually be:

```text
Retained
Archived
Deleted
```

according to operational and audit requirements.

---

# 65. Outbox Retention

Outbox records should have an explicit retention policy.

Possible strategies include:

```text
Delete After Successful Publication
Retain For N Days
Archive Before Deletion
Partition By Time
```

The choice depends on:

```text
Audit Requirements
Debugging
Recovery
Storage Cost
Compliance
```

---

# 66. Cleanup

Outbox cleanup should not interfere with active publication.

A safe process is:

```text
Publisher
    ↓
Publish
    ↓
Mark Published
    ↓
Retention Period
    ↓
Cleanup
```

---

# 67. Cleanup Batching

Cleanup should be bounded.

Avoid deleting millions of rows in one transaction.

Prefer:

```text
Small Batch
   ↓
Commit
   ↓
Repeat
```

to reduce:

```text
Locks
WAL Pressure
Replication Lag
Vacuum Pressure
```

---

# 68. Outbox Partitioning

If event volume becomes large, the outbox may eventually require partitioning.

Potential strategies include:

```text
Time-Based Partitioning
Service-Based Partitioning
Event-Type Partitioning
```

Partitioning should be introduced only when workload evidence justifies it.

---

# 69. Outbox Table Growth

Monitor:

```text
Pending Events
Published Events
Oldest Pending Event
Table Size
Index Size
Cleanup Rate
```

An outbox that continuously grows indicates an operational problem.

---

# 70. Outbox Backlog

A critical metric is:

```text
Outbox Backlog
```

Conceptually:

```text
Created Events
      -
Published / Removed Events
      =
Backlog
```

---

# 71. Oldest Pending Event

Monitor:

```text
Now - Oldest Pending Event Created Time
```

This indicates event publication delay.

---

# 72. Publisher Throughput

Monitor:

```text
Events Published / Second
Events Failed / Second
Events Retried / Second
```

and compare with:

```text
Events Created / Second
```

---

# 73. Backlog Growth

If:

```text
Events Created Rate
>
Events Published Rate
```

the backlog will grow.

The system should alert before backlog growth becomes operationally significant.

---

# 74. Outbox Publisher Scaling

Publisher concurrency may be increased when:

```text
Backlog ↑
Database Capacity Available
Redpanda Capacity Available
```

Scaling must remain bounded.

---

# 75. Publisher Concurrency

Do not create unbounded publisher workers.

Control:

```text
Worker Count
Batch Size
Database Connections
Broker Producer Concurrency
```

---

# 76. Database Load

Outbox polling adds database workload.

The publisher should use:

```text
Indexed Queries
Bounded Batches
Efficient Claiming
Reasonable Polling
```

---

# 77. Redpanda Load

The publisher should respect Redpanda producer configuration and broker capacity.

Do not increase publisher concurrency without considering:

```text
Broker Throughput
Partition Count
Producer Batching
Network
```

---

# 78. Transactional Outbox with Redpanda

The intended flow is:

```text
PostgreSQL
    │
    ├── Business State
    │
    └── Outbox Event
          │
        COMMIT
          │
          ▼
    Outbox Publisher
          │
          ▼
       Redpanda
          │
          ▼
      Consumers
```

---

# 79. Outbox and Kafka / Redpanda Transactions

RideForge does not require a distributed transaction spanning:

```text
PostgreSQL
+
Redpanda
```

The outbox provides the reliability boundary at PostgreSQL.

Redpanda producer guarantees may still be used to improve publication reliability.

---

# 80. Publisher Crash Recovery

If the publisher crashes:

```text
Before Publish
→ Event remains pending

After Publish, Before Marking Published
→ Event may be republished

After Marking Published
→ Event is considered complete
```

This is why consumer idempotency is required.

---

# 81. Partial Failure

A partial failure may look like:

```text
PostgreSQL Commit
        ↓
Outbox Exists
        ↓
Redpanda Unavailable
        ↓
Retry
        ↓
Success
```

This is an expected operating mode.

---

# 82. Database Failure

If PostgreSQL is unavailable:

```text
Business Transaction
→ Fails

Outbox Insert
→ Fails

No Event Commit
```

The publisher should not fabricate events for transactions that did not commit.

---

# 83. Redpanda Failure

If Redpanda is unavailable:

```text
PostgreSQL Transaction
→ Can Continue

Outbox Event
→ Stored

Publisher
→ Retries Later
```

This decouples business transaction availability from temporary broker availability, subject to capacity and retention limits.

---

# 84. Outbox Capacity During Broker Outage

If Redpanda remains unavailable for an extended period:

```text
Outbox
→ Backlog Growth
→ Storage Growth
```

The platform must have operational thresholds and failure handling.

---

# 85. Extended Outage

During a prolonged broker outage:

```text
Monitor Backlog
Monitor Database Storage
Monitor Event Age
Control Event Creation If Necessary
Restore Broker
Drain Backlog
```

The system must avoid silently exhausting PostgreSQL storage.

---

# 86. Backlog Protection

If backlog exceeds a defined operational threshold, the system may need:

```text
Alerting
Traffic Controls
Degraded Features
Publisher Scaling
Broker Recovery
```

depending on business criticality.

---

# 87. Event Creation During Degradation

Not every event-producing workflow can necessarily continue indefinitely if the event infrastructure is unavailable.

Criticality should be classified per event.

Examples:

```text
Critical Domain Event
→ Must Not Be Lost

Low-Priority Operational Event
→ May Be Deferred / Sampled / Dropped Only If Explicitly Allowed
```

The default should be to preserve business-required events.

---

# 88. Event Classification

Events may be classified as:

```text
Critical
Important
Operational
Analytical
```

This can influence:

```text
Retention
Retry
Alerting
Backpressure
```

---

# 89. Event Schema Compatibility

Outbox events must conform to the event contract.

Before publishing:

```text
Serialize
Validate
Publish
```

where validation is practical.

---

# 90. Serialization Failure

If an event cannot be serialized:

```text
Retrying Forever
```

is usually incorrect.

The event should be classified as a poison event and handled according to the DLQ/quarantine strategy.

---

# 91. Schema Evolution

Event schemas must evolve compatibly.

Preferred strategies include:

```text
Additive Fields
Optional Fields
Explicit Versioning
Backward-Compatible Consumers
```

Breaking changes require coordinated versioning or migration.

---

# 92. Event Contract Ownership

The producing service owns its event contract.

Consumers should not directly depend on internal database schema.

For example:

```text
Database Table
≠
Public Event Contract
```

---

# 93. Outbox and Domain Events

A domain event may be generated from a domain operation.

The application layer can translate it into an integration event suitable for external consumers.

Conceptually:

```text
Domain Operation
      ↓
Domain Event
      ↓
Integration Event
      ↓
Outbox
      ↓
Redpanda
```

The exact layering depends on service architecture.

---

# 94. Event Publication Boundary

The outbox publisher should not make additional business decisions before publishing.

Its responsibilities should remain:

```text
Load
Validate Delivery Metadata
Publish
Retry
Record Status
Observe
```

---

# 95. Outbox Repository

The repository should provide focused operations such as:

```text
Insert
Claim
MarkPublished
MarkRetry
RecordFailure
```

The exact API should follow the service's code conventions.

---

# 96. Transaction Context

Outbox insertion should accept the transaction context rather than silently opening a separate database transaction.

Conceptually:

```text
func CreateRide(ctx, tx, command)
```

and:

```text
outbox.Insert(ctx, tx, event)
```

This ensures both writes share the same transaction.

---

# 97. Publisher Transaction

The publisher's database transaction should be short.

Avoid:

```text
BEGIN
Fetch Events
Publish to Redpanda
Wait
COMMIT
```

for a large batch.

External network calls should generally not remain inside a PostgreSQL transaction.

---

# 98. Claim-Then-Publish

A common publisher approach is:

```text
Claim Rows
   ↓
Commit Claim
   ↓
Publish to Redpanda
   ↓
Mark Published
```

This avoids holding database locks during network publication.

The exact claim mechanism must be designed to safely handle publisher crashes.

---

# 99. Claim Leases

If claims are used, a lease may include:

```text
claimed_at
claim_owner
claim_expires_at
```

If a publisher crashes, another worker can eventually reclaim the event.

---

# 100. Claiming Trade-Off

Claiming introduces additional state and complexity.

The simplest implementation should be preferred if:

```text
Low Event Volume
Single Publisher
Short Processing
```

make it sufficient.

---

# 101. Multiple Publisher Safety

When multiple publishers operate concurrently, they must avoid:

```text
Uncontrolled Duplicate Claims
Long Locks
Starvation
```

The database query and claim mechanism should be tested under concurrency.

---

# 102. Fairness

The publisher should avoid indefinitely starving old events.

A typical ordering may use:

```text
created_at
```

while allowing retries and available events to be processed appropriately.

---

# 103. Priority

Priority should not be introduced unless the business requires it.

If priority is required, it should be explicit:

```text
priority
```

and included in the scheduling logic.

---

# 104. Outbox and Event Ordering

Ordering requirements should be documented per event stream.

Do not assume that database insertion order automatically equals broker consumption order.

The broker partition key and consumer processing model matter.

---

# 105. Event Partition Key

A typical strategy is:

```text
aggregate_id
```

as the Redpanda partition key when per-aggregate ordering is required.

Example:

```text
ride_id
```

for ride lifecycle events.

---

# 106. Cross-Aggregate Ordering

If strict ordering is required across multiple aggregates:

```text
Ride A
Driver B
```

the architecture becomes more complex.

Global ordering should be avoided unless there is a strong business requirement.

---

# 107. Exactly-Once Business Effects

RideForge should focus on:

```text
Exactly-Once Business Effect
```

rather than:

```text
Exactly-Once Transport
```

This is achieved through:

```text
Outbox
+
Stable Event ID
+
Idempotent Consumers
+
Transactional Consumer State
```

where required.

---

# 108. Consumer Transaction

A consumer may process an event and update PostgreSQL in one transaction:

```text
BEGIN
    Apply Event
    Record Event ID
COMMIT
```

This can provide strong duplicate protection for database-backed consumers.

---

# 109. Inbox Pattern

For consumers that require durable idempotency, an inbox or processed-event table may be used.

Conceptually:

```text
Event
  ↓
Inbox / Processed Event
  ↓
Business Transaction
```

The exact consumer strategy is governed by the idempotency architecture.

---

# 110. Outbox + Inbox

The complete reliable event flow can be:

```text
Producer Service
    │
    ├── Business State
    └── Outbox
          │
          ▼
      Redpanda
          │
          ▼
     Consumer Service
          │
          ├── Inbox / Deduplication
          └── Business State
```

This provides robust at-least-once event processing.

---

# 129. If Redpanda Is Down

Expected behaviour:

```text

→ Continues If Capacity Allows

→ Retries
```

# 130. If PostgreSQL Is Down

Expected behaviour:

```text

→ Fails

Outbox
→ Cannot Commit

Event
→ Not Created
```

No event should be generated for a transaction that never committed.

Expected behaviour:

```text

→ Continue

→ Accumulates

Publisher
→ Restart
→ Drain Backlog
```

Investigate:

# 134. If Storage Is at Risk

If outbox storage approaches an operational limit:

```text
Alert
Identify Cause
Protect Critical Events
Recover Broker / Publisher
Scale Storage Where Appropriate
Apply Controlled Degradation
```

Never silently delete required unpublished events merely to reclaim space.

# 135. Data Retention

The retention policy should distinguish:

```text

Published Events
Failed Events
DLQ Events
```

Pending events require stronger protection.

---

# 136. Backup and Recovery

The outbox is part of the PostgreSQL transactional state.

Therefore PostgreSQL backups include outbox records.

During recovery:

```text
PostgreSQL Restore
      ↓
Outbox Records Restored
      ↓
Publisher Resumes
      ↓
Events Republished Where Required
```

Consumers must remain idempotent.

---

# 137. Disaster Recovery

After PostgreSQL restoration:

```text
Business State
+
Outbox
```

must remain consistent.

The publisher may republish events whose publication state is uncertain.

Duplicate-safe consumers are therefore essential.

# 150. Decision Summary

RideForge adopts the:

```text
Transactional Outbox Pattern
```

for reliable publication of PostgreSQL-backed business events to Redpanda.

The intended flow is:

```text
                PostgreSQL Transaction
                        │
             ┌──────────┴──────────┐
             │                     │
       Business State         Outbox Event
             │                     │
             └──────────┬──────────┘
                        │
                      COMMIT
                        │
                        ▼
                 Outbox Publisher
                        │
                        ▼
                    Redpanda
                        │
                        ▼
                    Consumers
```

The pattern provides:

```text
Atomic Business State + Event Intent
+
At-Least-Once Publication
+
Recoverability
+
No Distributed Transaction
```

Consumers must therefore support idempotent processing.

---

# 151. Final Principle

> **When a successful PostgreSQL transaction must produce an event, commit the business state and the outbox record together, then publish the outbox record asynchronously with at-least-once semantics.**

The reliability model is:

```text
PostgreSQL
    │
    ├── Durable Business State
    │
    └── Durable Outbox
             │
             ▼
       Outbox Publisher
             │
             ▼
          Redpanda
             │
             ▼
        Idempotent
          Consumers
```

This establishes the RideForge transactional boundary between durable business state and asynchronous event publication while avoiding distributed transactions between PostgreSQL and Redpanda.
