# RideForge — Retry Policy

> **Document:** `docs/01-business/5.RETRY_POLICY.md`  
> **Status:** Active  
> **Scope:** Business and dispatch-policy rules governing matching retries  
> **Related:** `1.DISPATCH_BUSINESS_RULES.md`, `2.DRIVER_LIFECYCLE.md`, `3.RIDE_LIFECYCLE.md`, `4.MATCHING_RULES.md`, `docs/02-architecture/`

---

# 1. Purpose

This document defines how RideForge decides whether a failed matching attempt should be retried and how a subsequent attempt may differ from the previous one.

Retry exists to improve the probability of successful assignment without:

- retrying indefinitely,
- repeatedly processing the same unsuccessful search,
- creating duplicate offers,
- creating excessive infrastructure load,
- violating ride or driver lifecycle rules.

---

# 2. Retry Objective

The objective of retry is:

```text
Attempt failed
    ↓
Evaluate current dispatch context
    ↓
Decide whether another attempt is useful
    ↓
Adapt dispatch policy when appropriate
    ↓
Attempt again
```

Retry is an optimization decision.

It is not a guarantee that another attempt must always occur.

---

# 3. Retry Is Part of Dispatch Policy

The matching engine should execute retry policy.

It should not independently invent retry behaviour.

Conceptually:

```text
Matching Result
      ↓
Retry Policy
      ↓
Retry?
 ├── Yes → Next Attempt
 └── No  → Stop Matching
```

---

# 4. Retry Preconditions

A retry may occur only when:

```text
Ride is still matchable
AND
Ride is not cancelled
AND
Ride is not already assigned
AND
Retry budget remains
AND
Another attempt is considered useful by policy
```

If any mandatory condition fails, matching must stop.

---

# 5. Retry Is Not Blind Repetition

A retry should not simply execute the exact same operation indefinitely.

A subsequent attempt may adapt:

```text
Search Radius
Candidate Limit
Offer Batch Size
Offer Timeout
```

according to configured policy.

---

# 6. Attempt Number

Each matching attempt has a bounded attempt number.

Conceptually:

```text
Attempt 1
Attempt 2
Attempt 3
...
```

The attempt number is dispatch context.

It is not a replacement for the ride lifecycle state.

---

# 7. Maximum Attempts

Retry must be bounded.

The system must never allow:

```text
MATCHING
   ↓
Retry
   ↓
Retry
   ↓
Retry
   ↓
...
```

without a terminal condition.

When the retry budget is exhausted:

```text
Stop Normal Matching
```

and follow the applicable ride/business outcome.

---

# 8. Retry Budget

Retry budget should be configuration/policy rather than a hidden constant inside matching logic.

Possible policy dimensions include:

```text
Maximum Attempts
Maximum Matching Duration
Maximum Search Radius
Maximum Offer Count
```

Only dimensions required by the current system should be implemented.

---

# 9. Retryable Outcomes

Typical retryable outcomes include:

```text
No Eligible Candidate
Reservation Contention
All Offers Rejected
All Offers Timed Out
Insufficient Candidate Population
```

Whether each outcome is retryable is a policy decision.

---

# 10. Non-Retryable Outcomes

Matching should stop when the ride is no longer matchable.

Examples:

```text
Ride Cancelled
Ride Already Assigned
Ride Completed
Terminal Business Restriction
Retry Budget Exhausted
```

---

# 11. Infrastructure Failures

Infrastructure failures are different from normal dispatch failures.

Examples:

```text
Redis Failure
Database Failure
Event Infrastructure Failure
Routing Provider Failure
```

The system should not automatically classify every infrastructure failure as:

```text
No Candidate
```

Retry handling should follow the appropriate application/infrastructure policy.

---

# 12. No Candidate

If candidate discovery and filtering complete successfully but produce no eligible candidate:

```text
No Candidate
```

This is a normal dispatch outcome.

The retry policy may expand the search or otherwise adapt the next attempt.

---

# 13. Reservation Contention

A candidate may be eligible when ranked but unavailable when reservation is attempted.

Example:

```text
Candidate
   ↓
Ranked
   ↓
Another ride reserves driver
   ↓
Reservation rejected
```

This is a normal concurrency outcome.

Retry may continue with remaining candidates or another attempt.

---

# 14. Offer Rejection

If all selected drivers reject their offers:

```text
Offers Rejected
      ↓
Release Reservations
      ↓
Retry Policy
```

The next attempt may use the same or adapted dispatch parameters.

---

# 15. Offer Timeout

If all selected offers expire:

```text
Offers Timed Out
      ↓
Release Reservations
      ↓
Retry Policy
```

Timeout history may become useful input to future optimization.

---

# 16. Mixed Offer Outcomes

A batch may produce mixed results:

```text
Driver A → Rejected
Driver B → Timed Out
Driver C → Reservation Failed
```

If no assignment occurs, retry policy evaluates the aggregate result.

The system should not create duplicate offers merely because different failure outcomes occurred.

---

# 17. Successful Assignment Stops Retry

Once a ride is successfully assigned:

```text
Assignment
    ↓
Stop Matching
    ↓
No Further Retry
```

Retry must not continue after successful assignment.

---

# 18. Cancellation Stops Retry

If a ride becomes cancelled:

```text
Cancellation
    ↓
Stop Matching
    ↓
Invalidate / Cleanup Active Dispatch State
```

A delayed retry trigger must not restart matching for the cancelled ride.

---

# 19. Retry and Concurrent Assignment

A retry may race with another matching operation or driver response.

Before starting another attempt, the system must verify that the ride remains matchable.

Conceptually:

```text
Retry Trigger
     ↓
Check Current Ride State
     ↓
Still Matchable?
 ├── Yes → Attempt
 └── No  → Stop
```

---

# 20. Retry State Validation

A retry must not rely solely on the state captured by the previous attempt.

The current authoritative ride state must be considered before starting another attempt.

This protects against:

```text
Delayed Retry
Concurrent Assignment
Concurrent Cancellation
Duplicate Event
```

---

# 21. Retry Parameter Adaptation

The policy may adapt parameters between attempts.

Example:

```text
Attempt 1
Radius = R1
Batch = B1

Attempt 2
Radius = R2
Batch = B2
```

The values should come from dispatch configuration/policy.

They must not be hard-coded inside unrelated services.

---

# 22. Search Radius Expansion

When supply is insufficient, a later attempt may expand geographic search.

Conceptually:

```text
Attempt 1
   ↓
Local Search
   ↓
Insufficient Supply
   ↓
Attempt 2
   ↓
Wider Search
```

This should respect the maximum configured search budget.

The discovery/ring-expansion system remains responsible for geographic search mechanics.

---

# 23. Candidate Limit Adaptation

A retry may change the candidate limit when policy requires it.

Example:

```text
Attempt 1 → small candidate population
Attempt 2 → larger candidate population
```

The purpose is to improve assignment probability without processing an unnecessarily large candidate set on every attempt.

---

# 24. Offer Batch Adaptation

The offer batch size may adapt between attempts.

Conceptually:

```text
High expected acceptance
    → smaller batch

Low expected acceptance
    → larger batch
```

The policy should remain configurable.

The matching engine should not contain separate hard-coded batch rules.

---

# 25. Offer Timeout Adaptation

Offer timeout may eventually adapt based on:

```text
ETA
Traffic
Driver Response History
```

The current implementation should only use signals that actually exist and are reliable.

Do not introduce speculative prediction infrastructure merely to support the roadmap.

---

# 26. Acceptance Probability

Future retry optimization may use:

```text
Estimated Acceptance Probability
```

to decide:

```text
Batch Size
Search Expansion
Timeout
Retry Strategy
```

This should be introduced only when a reliable acceptance-probability signal exists.

Until then, existing deterministic policy should remain the source of truth.

---

# 27. Retry Does Not Guarantee Radius Expansion

A retry does not automatically mean:

```text
Radius++
```

The policy should decide whether geographic expansion is useful.

For example:

```text
No candidates
    → Expand search

Candidates exist but all rejected
    → Consider offer/ranking adaptation

Reservation contention
    → Continue with available candidates
```

The exact behaviour belongs to policy.

---

# 28. Retry Does Not Guarantee Larger Batches

A retry does not automatically mean:

```text
Batch Size++
```

Increasing the offer batch can increase:

```text
Notification Load
Reservation Contention
Offer State
Driver Experience Cost
```

Therefore batch size should be policy-driven.

---

# 29. Retry Does Not Guarantee Longer Timeout

A longer timeout is not automatically better.

The policy must balance:

```text
Driver Response Time
Passenger Waiting Time
ETA
Traffic
Assignment Probability
```

---

# 30. Retry and Passenger Experience

Retry exists to improve assignment, but excessive retry increases passenger waiting time.

Therefore retry policy should consider the remaining practical dispatch window.

Conceptually:

```text
Retry Benefit
    vs
Passenger Waiting Cost
```

---

# 31. Retry and Driver Experience

Retries must avoid repeatedly targeting the same unsuitable drivers.

The candidate pipeline should continue to enforce:

```text
Already Offered
Availability
Reservation
Eligibility
```

---

# 32. Already-Offered Protection

A retry must not blindly rediscover and re-offer a driver who already has an active offer for the same ride.

Existing offer state must be respected.

---

# 33. Previous Rejection

A previously rejecting driver should not automatically receive another offer for the same ride unless an explicit business policy permits it.

The default behaviour should avoid redundant repeated offers.

---

# 34. Previous Timeout

A driver who previously timed out should not automatically receive another identical offer for the same ride unless retry policy explicitly permits it.

Historical outcome may later become a ranking or dispatch-policy signal.

---

# 35. Retry and Candidate Discovery

Each retry may run candidate discovery again because driver supply can change between attempts.

Example:

```text
Attempt 1
No Driver

Time Passes

Driver Becomes Available

Attempt 2
Driver Found
```

Retry should therefore not assume that the previous candidate population remains current.

---

# 36. Retry and Realtime Freshness

Realtime driver state must be refreshed or revalidated according to the current candidate pipeline.

A driver being eligible in a previous attempt does not guarantee current eligibility.

---

# 37. Retry and Ranking

Each retry may rerank candidates because:

```text
Driver Location Changed
Driver Availability Changed
ETA Changed
Quality Data Changed
Fairness Changed
Demand Changed
```

The system should use current reliable data rather than blindly reusing stale scores.

---

# 38. Retry and Reservation

Reservations from previous failed attempts must be cleaned up before they can interfere with future attempts.

The retry system must not assume that cleanup happened merely because an attempt ended.

---

# 39. Retry and Offers

Active offers from a previous attempt must be considered before creating new offers.

The system must avoid:

```text
Old Offer Active
+
New Offer For Same Driver
```

unless explicitly supported by policy.

---

# 40. Retry Idempotency

Retry triggers may be delivered more than once.

Examples:

```text
Timeout Event
Retry Event
Worker Retry
Application Restart
Duplicate Message
```

Duplicate retry processing must not create uncontrolled additional attempts.

---

# 41. Retry Attempt Identity

Where the architecture requires durable attempt tracking, each attempt should be uniquely identifiable.

The identity should allow the system to distinguish:

```text
Attempt 1
Attempt 2
```

and prevent accidental duplicate execution of the same attempt.

---

# 42. Retry and Event Processing

If retry is triggered by an event:

```text
Event
   ↓
Validate Current Ride State
   ↓
Validate Retry Eligibility
   ↓
Start Attempt
```

The event itself must not be treated as sufficient proof that retry is still valid.

---

# 43. Retry and Application Restart

After application restart, persisted dispatch state must be sufficient to determine whether a retry remains valid.

The system should not create additional attempts solely because an in-memory worker was restarted.

---

# 44. Retry Failure

If a retry attempt itself fails due to infrastructure/application failure:

```text
Retry Attempt
     ↓
Operational Failure
```

the system should follow the appropriate failure-handling policy.

It must not silently increment attempts forever.

---

# 45. Retry Exhaustion

When retry policy determines that no further attempt should occur:

```text
Retry Exhausted
      ↓
Stop Normal Matching
      ↓
Apply Ride/Business Outcome
```

The outcome should remain observable.

---

# 46. Retry Exhaustion Is Not Automatically Cancellation

Retry exhaustion does not inherently mean:

```text
CANCELLED
```

unless the applicable business policy explicitly defines that transition.

The ride lifecycle owns the final ride-state decision.

---

# 47. Retry Metrics

Retry behaviour should support measurement of:

```text
Attempts Per Ride
Retry Rate
Retry Reason
Successful Assignment By Attempt
Average Attempt Duration
Radius By Attempt
Candidate Count By Attempt
Offer Batch By Attempt
Reservation Success By Attempt
```

These metrics are useful for future optimization.

---

# 48. Retry Reason Classification

Retry reasons should remain distinguishable.

Examples:

```text
NO_CANDIDATE
RESERVATION_CONTENTION
ALL_OFFERS_REJECTED
ALL_OFFERS_TIMED_OUT
PARTIAL_DISPATCH_FAILURE
POLICY_RETRY
```

Infrastructure failures should remain separately identifiable.

---

# 49. Retry Policy Configuration

Policy values should be configuration-driven.

Examples:

```text
Maximum Attempts
Maximum Search Radius
Candidate Limits
Offer Batch Limits
Timeout Limits
```

Configuration should be validated when loaded.

Invalid configuration must not silently create unsafe retry behaviour.

---

# 50. Retry Policy Boundaries

The retry policy decides:

```text
Whether to retry
How the next attempt should differ
When to stop
```

The matching engine decides:

```text
How to execute the attempt
```

The candidate pipeline decides:

```text
How candidates are processed
```

The reservation mechanism decides:

```text
Whether a driver can be claimed
```

These responsibilities must remain separated.

---

# 51. Retry and Performance

Retry optimization must avoid unnecessary expensive work.

Preferred:

```text
Cheap policy decision
      ↓
Bounded candidate discovery
      ↓
Filtering
      ↓
Expensive ranking/ETA only where useful
```

A retry should not multiply expensive operations without a meaningful expected benefit.

---

# 52. Retry and Routing

Routing/ETA calls may be expensive.

A retry should not automatically recalculate ETA for an unnecessarily large candidate population.

Use the existing candidate narrowing and ranking pipeline.

---

# 53. Retry and Geo Expansion

Geographic expansion should reuse the existing discovery/ring-expansion policy.

Do not introduce a second radius-expansion algorithm inside retry logic.

---

# 54. Retry and Ranking Policy

Retry may alter ranking context through configured parameters, but it should not duplicate the ranking engine.

Ranking remains responsible for:

```text
Feature Extraction
Normalization
Weighted Scoring
Ordering
```

Retry remains responsible for deciding whether and how to attempt again.

---

# 55. Retry Invariants

### Invariant 1

A retry may occur only while the ride remains matchable.

### Invariant 2

Retries must be bounded.

### Invariant 3

Successful assignment stops retry.

### Invariant 4

Cancellation stops retry.

### Invariant 5

A retry must not create duplicate active offers for the same driver without explicit policy.

### Invariant 6

Previous reservations must not leak into future attempts.

### Invariant 7

No-candidate and infrastructure failure remain distinguishable.

### Invariant 8

Retry policy must not bypass candidate eligibility.

### Invariant 9

Retry must not bypass reservation safety.

### Invariant 10

Retry configuration must not be hidden inside unrelated business components.

---

# 56. AI Agent Implementation Rules

Before modifying retry behaviour, an AI coding agent must:

1. Read this document.
2. Read `1.DISPATCH_BUSINESS_RULES.md`.
3. Read `2.DRIVER_LIFECYCLE.md`.
4. Read `3.RIDE_LIFECYCLE.md`.
5. Read `4.MATCHING_RULES.md`.
6. Inspect the current matching attempt/retry implementation.
7. Inspect existing retry configuration.
8. Inspect candidate discovery and expansion policy.
9. Inspect offer timeout/response handling.
10. Inspect reservation cleanup.
11. Reuse existing retry abstractions where possible.
12. Add or update tests for retry outcomes and boundary conditions.

---

# 57. AI Agent Forbidden Patterns

An AI agent must not:

- add infinite or unbounded retry,
- increment attempts without a real retry,
- retry cancelled or assigned rides,
- create duplicate offers during retry,
- bypass already-offered filtering,
- introduce another radius-expansion algorithm,
- hard-code retry limits inside services,
- hard-code batch-size policy inside retry code,
- hard-code timeout policy inside retry code,
- treat infrastructure failure as no-candidate without justification,
- introduce acceptance prediction merely because the roadmap mentions it,
- create a second retry engine,
- change retry behaviour solely to mark a roadmap phase complete.

---

# 58. Canonical Retry Flow

```text
Matching Attempt
      ↓
Assignment?
 ├── Yes → STOP
 │
 └── No
      ↓
Current Ride Still Matchable?
 ├── No → STOP
 │
 └── Yes
      ↓
Retry Policy
      ↓
Retry Allowed?
 ├── No → STOP / Business Outcome
 │
 └── Yes
      ↓
Adapt Attempt Parameters
      ↓
New Matching Attempt
```

The core principle is:

```text
Retry only when useful
Adapt only when justified
Keep every attempt bounded
Respect current ride state
Never bypass eligibility or reservation safety
```
