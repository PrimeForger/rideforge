# RideForge — Matching Rules

> **Document:** `docs/01-business/4.MATCHING_RULES.md`  
> **Status:** Active  
> **Scope:** Business rules governing candidate matching, filtering, ranking, reservation, offers, and matching completion  
> **Related:** `1.DISPATCH_BUSINESS_RULES.md`, `2.DRIVER_LIFECYCLE.md`, `3.RIDE_LIFECYCLE.md`, `5.RETRY_POLICY.md`, `docs/02-architecture/`

# 1. Purpose

This document defines the business rules for the RideForge matching process.

Matching answers:

> **Which eligible driver should be attempted for this ride, in what order, and under what conditions?**

Matching is not the same as ride assignment.

The business sequence is:

```text
Ride
 ↓
Candidate Discovery
 ↓
Candidate Enrichment
 ↓
Candidate Filtering
 ↓
Candidate Ranking
 ↓
Offer Selection
 ↓
Driver Reservation
 ↓
Offer
 ↓
Driver Response
 ↓
Assignment or Retry
```

---

# 2. Dispatch Strategy Context

Matching operates after the effective dispatch strategy has been resolved for the ride.

The system must distinguish:

```text
Configuration Hierarchy
      ↓
Dispatch Strategy Resolution
      ↓
Candidate Discovery
      ↓
Candidate Filtering
      ↓
Strategy-Specific Prioritization
      ↓
Ranking / Selection
```

The configuration hierarchy determines **which dispatch strategy applies**. It does not by itself define a hard candidate boundary.

The effective strategy is resolved by starting at the most specific applicable configuration level and moving upward until an explicit strategy is found.

```text
Most Specific Configuration
      ↓
Explicit Strategy?
 ├── YES → Use it
 └── NO
      ↓
Parent Configuration
      ↓
...
      ↓
System Default
```

The first explicit configuration found takes precedence.

Supported configuration levels may include:

```text
State
District
City / Town
Rural Area
Auto Stand
Specific Ride Level
Other configured intermediate levels
```

The hierarchy must not be assumed to contain a configuration at every level, and implementation must not hard-code a fixed list of levels.

# 3. Matching Objective

The primary objective is:

```text
Find a suitable driver
with the highest practical probability
of successfully serving the ride.
```

The system should balance:

```text
Pickup ETA
Driver Eligibility
Driver Availability
Driver Quality
Fairness
Demand Context
Operational Cost
```

The closest driver is not automatically the best driver.

---

# 4. Matching Preconditions

A matching operation may begin only when:

```text
Ride is matchable
AND
Ride is not already assigned
AND
Ride is not cancelled
AND
Matching policy permits an attempt
```

If any mandatory precondition fails, normal matching must not proceed.

---

# 5. Matching Attempt

A matching attempt is one execution of the dispatch process for a ride.

Conceptually:

```text
Matching Attempt
    ├── Discover
    ├── Enrich
    ├── Filter
    ├── Rank
    ├── Select
    ├── Reserve
    └── Offer
```

A failed attempt may be followed by another attempt according to retry policy.

---

# 6. Candidate Discovery

Candidate discovery should narrow the driver population before expensive matching work.

Preferred flow:

```text
Pickup Location
      ↓
Geographic Discovery
      ↓
Candidate Set
```

The discovery mechanism may use H3 and other configured geographic indexes.

Discovery is not an assignment decision.

---

# 7. Candidate Deduplication

A driver must appear only once in the candidate set for a matching attempt.

If a driver is found through multiple cells or discovery paths:

```text
Driver A
 ├── Cell 1
 ├── Cell 2
 └── Cell 3
```

the matching pipeline must treat it as:

```text
Driver A
```

not three independent candidates.

---

# 8. Candidate Enrichment

Candidate information required for matching should be loaded before the decisions that depend on it.

Examples include:

```text
Driver State
Availability
Quality Metrics
Location
Operational Metadata
```

When the same data is required for multiple candidates, batch retrieval should be preferred where supported.

---

# 9. Filtering Before Ranking

Hard eligibility rules must be evaluated before ranking.

The conceptual order is:

```text
Discover
  ↓
Enrich
  ↓
Filter
  ↓
Rank
```

A driver that cannot receive the ride must not consume ranking resources.

---

# 10. Required Candidate Filters

Applicable filters include:

```text
Invalid Candidate
Duplicate Candidate
Unavailable Driver
Reserved Driver
Already Offered Driver
Blocked / Ineligible Driver
Regionally Ineligible Driver
Ride-Specific Ineligible Driver
```

Additional filters may be introduced only when required by business rules.

---

# 11. Availability Filter

A driver must be operationally available before becoming an eligible matching candidate.

The system must not consider a driver available merely because:

```text
Driver exists
Driver has a recent location
Driver has a realtime connection
Driver exists in H3
```

Availability requires the applicable driver lifecycle conditions.

---

# 12. Reservation Filter

A driver already reserved by another conflicting operation should not be treated as freely available.

The matching system should avoid unnecessary reservation attempts for candidates known to be unavailable.

The final ownership decision remains with the reservation mechanism.

---

# 13. Already-Offered Filter

A driver with an active offer for the same ride must not receive another independent offer for that ride.

This prevents:

```text
Duplicate Notifications
Duplicate Offer State
Conflicting Responses
```

---

# 14. Regional Eligibility

Geographic proximity does not guarantee business eligibility.

Before ranking, applicable regional rules must be satisfied.

```text
Nearby
  +
Eligible Region
  =
Candidate Eligible for Ranking
```

---

# 15. Candidate Collection

The candidate collection represents the current matching population.

It should support:

```text
Iteration
Lookup
Deduplication
Filtering
Ranking
```

The collection should remain bounded by the matching/search policy.

---

# 16. Candidate Iterator

Matching should process candidates without requiring unnecessary duplication of the entire candidate population.

Where the existing candidate iterator supports streaming/controlled traversal, later stages should consume it rather than introducing another collection abstraction.

The implementation should optimize memory without complicating the business model.

---

# 17. Candidate Limit

Candidate discovery and processing must respect the configured candidate limit.

The purpose is to bound:

```text
Memory
Redis Work
Enrichment Work
Ranking Work
Reservation Attempts
Dispatch Latency
```

A larger candidate population is not automatically better.

---

# 18. Ranking Preconditions

Only candidates that pass hard eligibility filters should be ranked.

Ranking signals are preferences among eligible candidates.

They must not override:

```text
Eligibility
Availability
Regional Restrictions
Ride Constraints
Reservation Safety
```

---

# 19. ETA-Based Preference

When reliable ETA information is available, ETA should be preferred over raw distance.

Example:

```text
Driver A
Distance = 2 km
ETA = 10 min

Driver B
Distance = 3 km
ETA = 6 min
```

Driver B may rank higher.

The objective is practical pickup time, not geometric proximity.

---

# 20. Distance as a Fallback Signal

Distance may remain useful when:

```text
Routing/ETA is unavailable
ETA confidence is insufficient
Policy explicitly permits distance
```

Distance should not silently replace ETA when reliable ETA is available.

---

# 21. Driver Quality

Quality may influence ranking using configured driver-performance signals.

Possible signals:

```text
Acceptance Rate
Cancellation Rate
Timeout Rate
Rating
Completed Trips
```

Quality is a ranking preference.

It is not an eligibility gate unless a separate business rule explicitly defines it as one.

---

# 22. Fairness

Fairness may influence ranking among otherwise eligible candidates.

Possible signals include:

```text
Idle Time
Time Since Last Assignment
```

Fairness should prevent repeatedly favouring the same drivers when meaningful alternatives exist.

Fairness must not override hard eligibility.

---

# 23. Demand Context

The ranking system may incorporate local demand/supply context.

Conceptually:

```text
Supply
+
Demand
+
Candidate Suitability
```

may influence ranking.

Demand-aware ranking must not select an ineligible driver.

---

# 24. Score Normalization

Ranking features should be normalized into comparable ranges before weighted combination.

Conceptually:

```text
Raw Feature
    ↓
Normalization
    ↓
0..1 Score
    ↓
Configured Weight
```

This prevents one feature from dominating merely because it uses a larger numeric scale.

---

# 25. Configurable Ranking Weights

Ranking weights are policy/configuration.

They must not be hidden as unexplained constants inside calculators.

The configuration should control the relative importance of applicable features.

Examples:

```text
ETA Weight
Quality Weight
Fairness Weight
Demand Weight
```

The exact values belong to deployment/policy configuration.

---

# 26. Ranking Output

Ranking produces an ordered candidate set.

Conceptually:

```text
Candidate A → Score 0.91
Candidate B → Score 0.84
Candidate C → Score 0.72
```

The score is a selection signal.

It does not reserve or assign a driver.

---

# 27. Ranking Failure

If required ranking data cannot be obtained or calculated:

```text
Ranking Failure
```

must remain distinguishable from:

```text
No Eligible Candidates
```

The system must not silently treat an infrastructure/application failure as an empty candidate population.

---

# 28. Offer Selection

After ranking, matching policy determines which candidates should be offered the ride.

Conceptually:

```text
Ranked Candidates
       ↓
Offer Policy
       ↓
Offer Batch
```

The batch size is policy-driven.

---

# 29. Adaptive Offer Batch

The system should support policy-driven batch size.

For example:

```text
High acceptance probability
    → smaller batch

Low acceptance probability
    → larger batch
```

The implementation should keep this decision in dispatch policy rather than scattering batch-size logic across matching components.

---

# 30. Reservation Before Offer

A driver must be successfully reserved before an offer is created.

Required sequence:

```text
Ranked Candidate
      ↓
Reserve
      ↓
Success
      ↓
Create Offer
```

Never:

```text
Create Offer
      ↓
Try to Reserve
```

---

# 31. Reservation Race

If a candidate was eligible when ranked but another dispatch operation claims the driver before reservation:

```text
Ranking
   ↓
Reservation
   ↓
Rejected
```

the candidate is no longer available to this matching operation.

The system should continue with the next suitable candidate according to policy.

---

# 32. Offer Creation

An offer represents a valid dispatch opportunity created after successful reservation.

The offer must contain sufficient information to:

```text
Identify the ride
Identify the driver
Validate the response
Enforce expiry
Resolve assignment
```

---

# 33. Offer Delivery

Realtime delivery is a transport mechanism.

Successful message delivery does not itself establish assignment.

The authoritative state remains in the application lifecycle.

---

# 34. Offer Timeout

Every offer must have a bounded validity period.

When it expires:

```text
Offer
  ↓
Timed Out
  ↓
Reservation Released
  ↓
Matching Continues
```

when the ride remains matchable.

---

# 35. Driver Rejection

When a driver rejects:

```text
Offer
  ↓
Rejected
  ↓
Reservation Released
  ↓
Matching Continues
```

when the ride remains eligible.

---

# 36. Driver Acceptance

When a driver accepts:

```text
Offer
  ↓
Validate
  ↓
Assign Ride
```

The application must verify the current ride and offer state before assignment.

---

# 37. Acceptance Race

If multiple active offers exist and multiple drivers accept:

```text
Driver A → Accept
Driver B → Accept
```

only one successful assignment may occur.

The authoritative assignment operation must resolve the race safely.

---

# 38. Assignment Stops Normal Matching

Once assignment succeeds:

```text
Ride
  ↓
Assigned
```

normal matching must stop.

Remaining:

```text
Offers
Reservations
Retry Work
```

must be cleaned up or invalidated as appropriate.

---

# 39. Failed Offer Creation

If:

```text
Reservation → Success
Offer Creation → Failure
```

the reservation must be released when appropriate.

A failed partial operation must not leak driver ownership.

---

# 40. Partial Batch Failure

When multiple candidates are being processed:

```text
Driver A → Success
Driver B → Failure
Driver C → Success
```

the system must preserve successful operations and clean up failed partial operations.

One failed candidate must not unnecessarily invalidate independent successful candidates.

---

# 41. Matching Retry

If no assignment occurs:

```text
Matching Attempt
      ↓
Retry Policy
      ↓
Next Attempt
```

when retry conditions permit.

Retry logic belongs to dispatch policy.

---

# 42. Retry Inputs

Retry decisions may consider:

```text
Attempt Number
Candidates Found
Eligible Candidates
Reservation Success
Offer Outcome
Current Supply
```

Future optimization may also incorporate acceptance probability.

---

# 43. Matching Termination

Matching terminates when:

```text
Ride Assigned
OR
Ride Cancelled
OR
Retry Policy Exhausted
OR
Terminal Business Condition
```

The matching engine must not continue indefinitely.

---

# 44. No Candidate vs Failure

These outcomes must remain distinct:

```text
No Candidate
```

means the system successfully performed matching work but found no eligible driver.

```text
Matching Failure
```

means the system could not reliably complete the matching operation.

This distinction is important for retry and observability.

---

# 45. Dispatch Search Budget

Candidate discovery must remain bounded by the applicable geographic/search budget.

The system should not expand indefinitely just because no driver has been found.

---

# 46. Expensive Work Ordering

Matching should prefer cheaper narrowing operations before expensive calculations.

Preferred:

```text
Geographic Narrowing
      ↓
Availability / Eligibility
      ↓
Enrichment
      ↓
ETA / Expensive Calculation
      ↓
Ranking
      ↓
Reservation
```

The exact order may differ where an existing stage contract requires it, but unnecessary expensive work should be avoided.

---

# 47. Batch Data Loading

When multiple candidates require the same backend data:

```text
Candidate IDs
      ↓
One Batch Load
      ↓
Candidate Enrichment
```

should be preferred over:

```text
Candidate A → Load
Candidate B → Load
Candidate C → Load
```

This is especially important for hot dispatch paths.

---

# 48. Realtime Data

Realtime data may be used for:

```text
Availability
Location
Connection
Heartbeat
Offer State
```

but stale realtime data must not be treated as current.

---

# 49. H3 Discovery

H3 is used to efficiently narrow geographic candidate discovery.

Conceptually:

```text
Pickup
  ↓
H3 Cell
  ↓
Nearby Cells
  ↓
Driver IDs
```

H3 discovery should not itself decide driver eligibility.

---

# 50. Geo Refinement

When additional geographic refinement is required:

```text
H3
 ↓
Secondary Geo Lookup
 ↓
Distance Refinement
```

may be used.

The purpose is to improve candidate precision without scanning unnecessary drivers.

---

# 51. ETA Refinement

ETA/routing should be used where the configured ranking policy requires reliable travel-time information.

Expensive routing work should be restricted to candidates that have survived cheaper filtering where practical.

---

# 52. Stand Matching

When Smart Stand Dispatch is selected, stand preference is applied according to the rider's relationship to a configured auto stand.

### Rider inside a stand radius

When the pickup location is within the configured radius of an auto stand:

```text
Ride
  ↓
Relevant Auto Stand
  ↓
Eligible drivers associated with the stand
  ↓
Stand queue / ordering preference
```

The stand is the **preferred dispatch source**, not an exclusive candidate boundary.

The matching process should first consider suitable eligible drivers from that stand according to the configured queue/order rules.

If the stand cannot provide a suitable available driver, the matching process may expand to broader eligible candidates according to the dispatch search policy.

The broader candidate set may include:

```text
Drivers from nearby stands
Drivers outside any stand
Drivers associated with nearby locations
```

### Rider outside all stand radii

If the rider is not within the configured radius of any relevant auto stand:

```text
No stand preference
      ↓
Eligible nearby drivers
      ↓
Normal matching / ranking
```

Drivers are not excluded merely because they are not at a stand.

### Important matching rule

Smart ranking signals must not silently override an applicable stand queue rule during the preferred stand phase.

At the same time, the stand preference must not be implemented as:

```text
Only stand drivers are eligible
```

The correct model is:

```text
Stand preference
      ↓
Try suitable stand candidates
      ↓
If insufficient / unsuitable
      ↓
Expand to broader eligible candidates
```

Shared rules remain:

```text
Ride Eligibility
Driver Eligibility
Regional / Legal Eligibility
Reservation
Offer Validity
Assignment Safety
```


# 53. Smart Matching

Smart Dispatch is a stand-agnostic dispatch strategy.

When Smart Dispatch is the effective strategy for the ride, matching should consider eligible nearby drivers without giving preference or restriction based on auto-stand membership.

Typical signals include:

```text
H3 Discovery
Availability
ETA
Quality
Fairness
Demand
Configured Ranking
```

Any eligible driver may be considered regardless of whether the driver is:

```text
At an auto stand
Outside an auto stand
Associated with another nearby location
```

The final selection remains subject to:

```text
Driver Eligibility
Regional / Legal Eligibility
Availability
Reservation Safety
Ride Constraints
```

Smart Dispatch must not accidentally inherit stand-only candidate restrictions from Smart Stand Dispatch.


# 54. Cross-Location Matching

Candidate discovery may expand beyond the ride's originating location when local supply cannot provide a suitable driver.

A location's dispatch strategy determines how candidates associated with that location are prioritized; it does not automatically create a hard boundary that prevents those candidates from serving nearby locations.

Example:

```text
Location A
Smart Dispatch
      ↓
No suitable local driver
      ↓
Expand search
      ↓
Location B
Smart Stand Dispatch
```

When candidates from Location B enter the matching flow, the system must respect the applicable Smart Stand Dispatch context for those candidates.

For example:

```text
Location B — Stand Driver
2 km / 5 min ETA

Location B — Non-Stand Driver
4 km / 9 min ETA
```

The stand driver may be the better candidate when the applicable strategy and eligibility rules support that outcome.

Cross-location matching must still enforce:

```text
Driver Eligibility
Availability
Distance / ETA
Regional / Legal Rules
Service Constraints
Ride Constraints
Reservation Safety
```

The system must not assume:

```text
Different Location
    =
Ineligible Driver
```

Likewise, geographic proximity alone must not bypass regional or legal restrictions.

---

# 55. Matching Strategy and Candidate Scope

The matching pipeline must keep these concepts separate:

```text
Dispatch Strategy
        ↓
How candidates are prioritized

Candidate Discovery Scope
        ↓
Where candidates may be discovered
```

Therefore:

```text
Smart Stand Dispatch
≠
Stand-only candidate pool
```

and:

```text
Location
≠
Hard dispatch boundary
```

Candidate discovery and expansion are governed by the configured search policy, while strategy-specific prioritization determines how the discovered candidates are handled.



Business policy decides:

```text
Who should be preferred?
How many should be offered?
When should retry occur?
When should matching stop?
```

Infrastructure/mechanism provides:

```text
H3
Redis
PostgreSQL
Kafka
Locks
Routing
```

The mechanism must not silently encode policy.

---

# 56. Concurrency

Matching must assume concurrent operations.

Examples:

```text
Two rides → same driver
Two workers → same ride
Retry → previous offer still active
Driver response → cancellation
```

The business result must remain consistent.

---

# 57. Idempotency

Repeated processing of the same matching event or response must not produce unintended duplicate business effects.

Examples:

```text
Duplicate acceptance
Duplicate timeout
Duplicate rejection
Duplicate retry trigger
```

must be safely handled.

---

# 58. Matching State Authority

Matching state must follow the application's authoritative lifecycle.

Realtime messages and cached state can accelerate decisions but must not independently create assignment.

---

# 59. Matching Metrics

The matching process should support measurement of:

```text
Candidates Discovered
Candidates Enriched
Candidates Filtered
Candidates Ranked
Reservations Attempted
Reservations Succeeded
Offers Created
Offers Accepted
Offers Rejected
Offers Timed Out
Matching Attempts
Time to Assignment
```

These metrics support both operations and future optimization.

---

# 60. Business Outcome Priority

Matching should optimize for:

```text
Successful Assignment
```

rather than:

```text
Maximum Candidate Count
Maximum Offers
Minimum Geometric Distance
```

---

# 61. Operational Cost

Matching should avoid unnecessary:

```text
Redis Calls
Database Queries
Routing Calls
Candidate Processing
Offer Creation
Reservation Contention
```

Performance optimization must preserve business correctness.

---

# 62. Matching Invariants

### Invariant 1

Only a matchable ride may enter normal matching.

### Invariant 2

Only eligible candidates may be ranked.

### Invariant 3

A driver must be reserved before an offer is created.

### Invariant 4

A failed reservation does not create ownership.

### Invariant 5

An expired offer cannot produce assignment.

### Invariant 6

A ride can have only one successful final assignment.

### Invariant 7

Matching stops after successful assignment.

### Invariant 8

Retries are bounded.

### Invariant 9

No-candidate and infrastructure failure remain distinct.

### Invariant 10

Ranking preferences cannot override hard eligibility.

# 63. AI Agent Implementation Rules

Before changing matching behaviour, an AI coding agent must:

1. Read this document.
2. Read `1.DISPATCH_BUSINESS_RULES.md`.
3. Read `2.DRIVER_LIFECYCLE.md`.
4. Read `3.RIDE_LIFECYCLE.md`.
5. Inspect the current candidate discovery pipeline.
6. Inspect candidate enrichment and filtering.
7. Inspect ranking configuration and implementation.
8. Inspect reservation/driver-lock behaviour.
9. Inspect offer creation and response handling.
10. Reuse existing abstractions where they already satisfy the rule.
11. Preserve lifecycle and concurrency invariants.
12. Add or update tests for changed matching behaviour.

---

# 64. AI Agent Forbidden Patterns

An AI agent must not:

- introduce a second candidate pipeline without a clear responsibility boundary,
- bypass existing reservation/locking abstractions,
- create offers before successful reservation,
- rank candidates before required eligibility filtering,
- hard-code ranking policy inside calculators,
- hard-code retry or batch policy inside unrelated components,
- treat H3 membership as eligibility,
- treat distance as automatically superior to ETA,
- add per-driver database queries when an existing batch-loading path is available,
- silently convert infrastructure failures into no-candidate results,
- change matching behaviour merely to satisfy a roadmap phase,
- duplicate existing candidate, ranking, or policy abstractions.

---
- interpret Smart Stand Dispatch as a stand-only candidate pool,
- treat an auto stand as a hard geographic dispatch boundary,
- treat a driver's originating location as an automatic eligibility boundary,
- skip dispatch strategy resolution and assume a fixed strategy,
- hard-code the configuration hierarchy as a fixed State → District → Town → Stand chain,
- let a parent configuration override an explicit child configuration,
- discard cross-location candidates solely because their location uses a different dispatch strategy,


```text
Matchable Ride
      ↓
Resolve Effective Dispatch Strategy
      ↓
Determine Candidate Discovery Scope
      ↓
Candidate Discovery
      ↓
Deduplication
      ↓
Candidate Enrichment
      ↓
Hard Eligibility Filters
      ↓
Strategy-Specific Prioritization
      ↓
ETA / Quality / Fairness / Demand Features
      ↓
Ranking / Candidate Selection
      ↓
Offer Policy
      ↓
Driver Reservation
      ↓
Offer Creation
      ↓
Driver Response
      ├── Accept → Assignment
      ├── Reject → Release → Retry
      └── Timeout → Release → Retry
```

The core principle is:

```text
Discover broadly enough
Filter aggressively
Rank intelligently
Reserve safely
Offer deliberately
Assign exactly once
Retry only when policy permits
```
