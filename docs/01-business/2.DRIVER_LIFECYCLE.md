# RideForge — Driver Lifecycle

> **Document:** `docs/01-business/2.DRIVER_LIFECYCLE.md`  
> **Status:** Active  
> **Scope:** Business lifecycle and state rules for drivers participating in RideForge dispatch  
> **Related:** `1.DISPATCH_BUSINESS_RULES.md`, `3.RIDE_LIFECYCLE.md`, `4.MATCHING_RULES.md`, `5.RETRY_POLICY.md`, `docs/00-project/5.TERMINOLOGY.md`

---

# 1. Purpose

This document defines the business lifecycle of a RideForge driver.

It describes:

- driver operational states,
- dispatch eligibility,
- realtime availability,
- reservation,
- offer participation,
- ride assignment,
- stale/offline handling,
- lifecycle invariants.

This document defines business behaviour. Redis, PostgreSQL, H3, locks, realtime connections, and event infrastructure are implementation mechanisms.

---

# 2. Lifecycle Model

Driver lifecycle has two related dimensions:

```text
Driver Account / Eligibility State
+
Realtime / Dispatch State
```

These must not be treated as one undifferentiated state machine.

A driver can have an active account while being:

```text
OFFLINE
AVAILABLE
RESERVED
ON_TRIP
```

---

# 3. Core Operational States

The dispatch lifecycle distinguishes:

```text
OFFLINE
AVAILABLE
RESERVED
OFFERED
ASSIGNED
ON_TRIP
```

Administrative states such as blocked or suspended are separate eligibility concerns.

---

# 4. Normal Lifecycle

```text
OFFLINE
   │
   │ goes online
   ▼
AVAILABLE
   │
   │ reservation succeeds
   ▼
RESERVED
   │
   ▼
OFFERED
   │
   ├── rejected ──────► AVAILABLE
   │
   ├── timeout ───────► AVAILABLE
   │
   └── accepted
          ▼
       ASSIGNED
          ▼
       ON_TRIP
          │
          │ trip completed
          ▼
       AVAILABLE
```

A driver may return to `OFFLINE` whenever the driver is no longer participating in realtime dispatch.

---

# 5. OFFLINE

A driver is `OFFLINE` when the driver is not currently participating in normal realtime dispatch.

An offline driver must not receive a new normal dispatch offer.

Typical causes:

```text
Driver explicitly goes offline
Realtime connection lost
Heartbeat expires
Operational state becomes unavailable
```

---

# 6. AVAILABLE

A driver is `AVAILABLE` when the driver is actively eligible for consideration for a new ride, subject to ride-specific rules.

Availability requires more than an active driver account.

The driver must satisfy applicable:

```text
Account eligibility
Operational availability
Realtime freshness
Reservation state
Ride-specific eligibility
Regional/business rules
```

---

# 7. RESERVED

`RESERVED` means the dispatch system has successfully claimed the driver for a specific dispatch operation.

Reservation is the concurrency boundary.

A driver must not be successfully reserved by two conflicting dispatch operations.

Reservation does not itself mean that the driver has been assigned the ride.

---

# 8. OFFERED

`OFFERED` means a valid ride offer has been created for the driver after the required reservation.

The offer is ride-specific.

It does not redefine the driver's permanent account state.

---

# 9. ASSIGNED

`ASSIGNED` means the application has successfully established the driver-rider/ride assignment.

The following do **not** independently mean assignment:

```text
Driver discovered
Driver ranked
Driver reserved
Offer created
Notification delivered
```

Assignment requires the appropriate authoritative business state transition.

---

# 10. ON_TRIP

`ON_TRIP` means the driver is actively serving an assigned ride.

An on-trip driver must not be considered normally available for another independent ride.

After the ride completes:

```text
ON_TRIP
   ↓
AVAILABLE
```

only when the driver remains otherwise eligible and online.

---

# 11. Driver Account Eligibility

Administrative eligibility is separate from realtime availability.

A driver may be:

```text
Active
Suspended
Blocked
Pending
```

while separately having:

```text
OFFLINE
AVAILABLE
```

A suspended, blocked, or otherwise prohibited driver must not receive new dispatch offers even if realtime data appears available.

---

# 12. Driver Capability

Where applicable, a driver must satisfy ride-specific capabilities before becoming an eligible candidate.

Examples:

```text
Vehicle Type
Service Type
Capacity
Operating Area
Required Qualification
```

Capability checks are eligibility rules, not ranking signals.

---

# 13. Availability Is Not Reservation

These concepts must remain separate:

```text
AVAILABLE
    =
driver appears eligible for consideration

RESERVED
    =
driver has been authoritatively claimed
```

A driver can be available when discovered and become unavailable before reservation succeeds.

---

# 14. Reservation Entry

The normal reservation flow is:

```text
Eligible Candidate
      ↓
Reserve Driver
      ↓
Reservation Success
      ↓
Reserved
```

Reservation must be concurrency-safe.

---

# 15. Reservation Rejection

If another operation has already claimed the driver:

```text
Reserve
  ↓
Rejected
```

the failed operation does not own the driver.

The matching operation should continue according to dispatch policy.

A normal reservation race is not automatically an infrastructure failure.

---

# 16. Reservation Error

A reservation error means the reservation mechanism itself failed operationally.

Examples:

```text
Redis unavailable
Network failure
Lock implementation failure
Unexpected infrastructure error
```

This must remain distinguishable from normal reservation rejection.

---

# 17. Reservation Release

A reservation should be released when the dispatch operation no longer requires it.

Typical cases:

```text
Offer rejected
Offer timed out
Offer creation failed
Ride cancelled
Dispatch attempt abandoned
Assignment completed and reservation is no longer needed
```

Cleanup must prevent leaked reservations.

---

# 18. Failed Offer Cleanup

If:

```text
Reserve → Success
Offer persistence → Failure
```

the reservation must be released when appropriate.

Partial failures are normal reliability cases and require explicit cleanup.

---

# 19. Driver Accepts Offer

A valid acceptance transitions the dispatch flow toward assignment:

```text
OFFERED
   ↓
ACCEPTED
   ↓
ASSIGNED
   ↓
ON_TRIP
```

The system must verify that:

```text
Offer exists
Offer is still active
Ride is still matchable
Response is valid
```

before applying the acceptance.

---

# 20. Driver Rejects Offer

A rejection means the driver explicitly declined an active offer.

```text
OFFERED
   ↓
REJECTED
   ↓
Release Reservation
   ↓
Continue Dispatch
```

The driver may become available again only if all other driver state permits it.

---

# 21. Offer Timeout

A timeout occurs when an offer expires without a valid acceptance.

```text
OFFERED
   ↓
TIMED_OUT
   ↓
Release Reservation
   ↓
Continue Dispatch
```

Timeout duration belongs to dispatch policy/configuration and must not be hidden as a hard-coded lifecycle rule.

---

# 22. Late Response

A response received after an offer has expired must not automatically produce assignment.

The application must validate the current authoritative state before accepting a response.

---

# 23. Realtime Connection

Realtime connection is an operational signal, not proof of availability.

A connected driver may still be:

```text
ON_TRIP
RESERVED
UNAVAILABLE
BLOCKED
```

Likewise, a disconnected driver account is not automatically disabled.

---

# 24. Heartbeat

Heartbeat freshness provides evidence that realtime driver state is current.

When heartbeat expires:

```text
Heartbeat Expired
       ↓
Realtime State Stale
       ↓
Driver must not be treated as reliably available
```

The freshness window belongs to configuration.

---

# 25. Location Freshness

Driver location is realtime operational information.

An excessively stale location must not be treated as the driver's current position.

Location freshness can affect:

```text
Candidate Discovery
ETA
Ranking
Availability
```

---

# 26. Driver Location and H3

The geographic representation is:

```text
Driver Location
      ↓
H3 Cell
      ↓
Realtime Geo Index
```

H3 membership is a derived operational index.

It is not proof of driver eligibility.

---

# 27. Same-Cell Updates

When a driver moves while remaining in the same H3 cell, the system should avoid unnecessary spatial index movement while maintaining appropriate realtime freshness.

This is an implementation optimization that must not change lifecycle semantics.

---

# 28. Driver Cache

The driver cache may contain hot realtime information such as:

```text
Location
Availability
Heartbeat
Connection
Offer-related state
```

The cache is an operational representation.

It must not automatically become the authoritative durable driver business record.

---

# 29. H3 Index

The H3 index answers:

```text
Which drivers are geographically nearby?
```

It does not answer:

```text
Is this driver legally eligible?
Is this driver administratively eligible?
Is this driver assigned?
```

Those decisions belong to the appropriate business/application state.

---

# 30. Stale Driver Cleanup

Stale realtime state may result from:

```text
Expired heartbeat
Expired connection
Expired location
Expired cache entry
```

Stale drivers must not remain indefinitely discoverable as active supply.

Existing TTL and cleanup mechanisms should be reused before introducing duplicate cleanup systems.

---

# 31. Reconnection

When a driver reconnects:

```text
Connection Restored
      ↓
Refresh Realtime State
      ↓
Refresh Heartbeat / Location
      ↓
Evaluate Availability
      ↓
Re-enter Dispatch If Eligible
```

Reconnection must not blindly restore every previous state.

---

# 32. Driver State Recovery

After infrastructure failure or restart, realtime state may need to be reconstructed.

Recovery must restore only state for which sufficient evidence exists.

The system must not fabricate availability merely because a durable driver record exists.

---

# 33. Cross-Region Eligibility

A geographically nearby driver is not automatically eligible for every ride.

Regional/business rules must be evaluated separately:

```text
Nearby
 +
Operationally Eligible
 +
Regionally Eligible
 =
Dispatch Eligible
```

---

# 34. Stand Dispatch

Under stand dispatch:

```text
Driver
   ↓
Stand / Queue
   ↓
Eligible Position
   ↓
Assignment
```

Stand-specific ordering rules may determine selection.

They must not be silently replaced by geographic ranking.

---

# 35. Smart Dispatch

Under smart dispatch:

```text
Available Drivers
      ↓
Geographic Discovery
      ↓
Eligibility
      ↓
Ranking
      ↓
Reservation
```

Possible ranking signals include:

```text
ETA
Quality
Fairness
Demand Context
```

---

# 36. Shared Lifecycle Guarantees

Both dispatch strategies must preserve:

```text
Eligibility
Availability
Reservation Safety
Offer Validity
Assignment Correctness
Trip Lifecycle
```

Strategy-specific selection must not redefine ownership semantics.

---

# 37. Driver Quality

Driver quality is a ranking signal, not an eligibility substitute.

Possible quality inputs:

```text
Acceptance Rate
Cancellation Rate
Timeout Rate
Rating
Completed Trips
```

The relationship is:

```text
Eligibility
    ↓
Candidate
    ↓
Quality / Ranking
```

not:

```text
Quality
    ↓
Eligibility
```

---

# 38. Fairness and Idle Time

Fairness may consider:

```text
Idle Time
Time Since Last Assignment
```

Fairness can influence ordering among eligible candidates.

It must not override:

```text
Availability
Eligibility
Reservation
Regional restrictions
Ride constraints
```

---

# 39. Driver Metrics

The lifecycle should support measurement of:

```text
Time Online
Time Available
Time Reserved
Time On Trip
Acceptance Rate
Rejection Rate
Timeout Rate
Cancellation Rate
Completed Trips
Idle Time
```

These metrics can support ranking, dispatch optimization, and operational monitoring.

---

# 40. Lifecycle Invariants

The following invariants must always hold:

### Invariant 1

An ineligible driver must not receive a new normal dispatch offer.

### Invariant 2

A driver must not be successfully reserved by two conflicting operations.

### Invariant 3

An expired offer must not create a successful assignment.

### Invariant 4

An assigned/on-trip driver must not be treated as normally available.

### Invariant 5

A failed reservation is not ownership.

### Invariant 6

A failed offer creation must not leave an unnecessary reservation.

### Invariant 7

Realtime freshness must be respected when determining operational availability.

### Invariant 8

H3 membership does not prove business eligibility.

### Invariant 9

A connected driver is not automatically available.

### Invariant 10

A fresh location is not automatically proof of availability.

---

# 41. Failure Handling

When a lifecycle operation fails, the system should preserve the last known valid state where safe and make the failure observable.

It must not silently transition to a more permissive state.

For example:

```text
Unable to verify availability
```

must not become:

```text
AVAILABLE
```

without sufficient evidence.

---

# 42. Conservative Availability

When realtime state becomes uncertain, the system should prefer avoiding an invalid dispatch over falsely claiming availability.

This protects:

```text
Driver Experience
Ride Assignment Correctness
Reservation Consistency
```

---

# 43. Driver Lifecycle and Events

Only meaningful lifecycle changes should generate application events where required.

Examples:

```text
Driver Became Available
Driver Became Unavailable
Driver Location Updated
Driver Reserved
Driver Offer Created
Driver Accepted
Driver Rejected
Driver Offer Timed Out
Driver Assignment Completed
```

Not every internal mutation requires an event.

---

# 44. Event Idempotency

Driver lifecycle event consumers must tolerate duplicate delivery where applicable.

Duplicate processing must not create unintended duplicate state transitions.

---

# 45. Driver State Authority

A simplified authority model is:

```text
Durable Driver Eligibility
        ↓
Realtime Operational State
        ↓
Dispatch Reservation
        ↓
Ride Assignment
```

Each layer has a distinct responsibility.

No single cache/index should silently become authoritative for every layer.

---

# 46. AI Agent Implementation Rules

Before changing driver lifecycle behaviour, an AI coding agent must:

1. Read this document.
2. Read `1.DISPATCH_BUSINESS_RULES.md`.
3. Read the ride lifecycle documentation.
4. Inspect current driver/domain state models.
5. Inspect realtime cache behaviour.
6. Inspect reservation/locker behaviour.
7. Inspect relevant event producers/consumers.
8. Reuse existing lifecycle concepts.
9. Preserve lifecycle invariants.
10. Add or update tests for new transitions and failure paths.

---

# 47. AI Agent Forbidden Patterns

An AI agent must not:

- treat Redis cache state as automatically authoritative durable driver state,
- use H3 membership as proof of eligibility,
- make connected drivers automatically available,
- make located drivers automatically available,
- bypass the reservation abstraction,
- create offers without required reservation,
- allow expired offers to become valid through late responses,
- leave reservations after failed operations,
- introduce a second driver state machine without a clear boundary,
- hard-code lifecycle policy that belongs in configuration,
- change lifecycle rules solely to satisfy a roadmap phase.

---

# 48. Canonical Lifecycle Summary

```text
OFFLINE
   ↓
AVAILABLE
   ↓
RESERVED
   ↓
OFFERED
   ├── REJECTED ──→ AVAILABLE
   ├── TIMED OUT ─→ AVAILABLE
   └── ACCEPTED
          ↓
       ASSIGNED
          ↓
       ON_TRIP
          ↓
       COMPLETED
          ↓
       AVAILABLE
```

The most important distinctions are:

```text
Available ≠ Assigned
Connected ≠ Available
Located ≠ Available
Candidate ≠ Reserved
Reserved ≠ Assigned
Offer ≠ Assignment
H3 Membership ≠ Eligibility
Quality ≠ Eligibility
```

These distinctions are mandatory architectural/business invariants.
