# 1. Purpose

This document defines how RideForge should govern data used by AI systems.

The objective is to ensure that AI data is:

```text
Necessary
+
Accurate
+
Traceable
+
Protected
+
Purpose-Bound
+
Retained Appropriately
```

AI systems must not become an uncontrolled secondary store of user, driver, ride, location, or operational data.

---

# 2. Core Principle

> **Collect and retain only the data required for an explicitly defined operational, analytical, safety, or model-development purpose.**

AI capability must not be used as a justification for indefinite data collection.

---

# 3. AI Data Lifecycle

The governed lifecycle is:

```text
Collect
  ↓
Validate
  ↓
Classify
  ↓
Use
  ↓
Store
  ↓
Monitor
  ↓
Retain
  ↓
Delete / Anonymize
```

Each stage should have an explicit owner and policy where the data is material.

```text
Vehicle Data

Operational Data
Event Data
Feature Data
Prediction Data
Outcome Data

```

Not every category should be treated identically.

---

# 5. Data Classification

A practical classification is:

```text
Public
Internal
Confidential
Sensitive
```

The actual classification should be aligned with the platform's broader security and privacy policies.

---

# 6. Public Data

Data intended for unrestricted public use.

Examples may include:

```text
Public Service Metadata
Public Geographic Information
Publicly Published Information
```

Only data genuinely intended for public use belongs here.

---

# 7. Internal Data

Operational information intended for authorized RideForge systems and personnel.

Examples:

```text
Aggregated Operational Metrics
System Configuration
Non-Sensitive Model Metrics
```

---

# 8. Confidential Data

Data whose disclosure could create meaningful operational or business risk.

Examples:

```text
Internal Model Configuration
Operational Statistics
Private Business Metrics
Model Artifacts
```

---

# 9. Sensitive Data

Data requiring stronger protection.

Potential examples include:

```text
Precise Location History
Personal Identifiers
Contact Information
Identity / KYC Information
Payment-Related Information
Sensitive User Attributes
```

Exact classification must follow the applicable legal and organizational requirements.

---

# 10. Data Minimization

Before adding a data field to an AI pipeline, ask:

```text
Why is this field required?
Which model or capability uses it?
Can a less sensitive field achieve the same purpose?
How long is it needed?
Who needs access?
```

If there is no clear answer:

```text
Do Not Collect It for AI.
```

---

# 11. Purpose Limitation

Data collected for one purpose should not automatically be reused for another unrelated purpose.

For example:

```text
Operational Location
```

does not automatically imply:

```text
Unlimited Historical ML Dataset
```

Reuse should be evaluated under applicable policy and law.

---

# 12. Data Lineage

Important AI datasets should be traceable to their sources.

Conceptually:

```text
Source Event
    ↓
Raw Data
    ↓
Transformation
    ↓
Feature
    ↓
Training Dataset
    ↓
Model
```

---

# 13. Source Traceability

For important datasets, record:

```text
Source
Collection Time
Transformation
Dataset Version
Feature Version
Model Version
```

where operationally and legally appropriate.

---

# 14. Point-in-Time Correctness

Training and evaluation features must represent information that would have been available at the prediction time.

Avoid:

```text
Future Data Leakage
```

This is both a model-quality and governance concern.

---

# 15. Training Data Governance

Before a dataset becomes a training dataset, verify:

```text
Source
Purpose
Quality
Allowed Use
Sensitivity
Retention
Lineage
```

---

# 16. Dataset Approval

Production training datasets should have an identifiable owner.

Important datasets should not become permanent simply because a pipeline can access them.

---

# 17. Dataset Versioning

Training datasets should be versioned or reproducible enough to answer:

```text
Which data produced this model?
```

---

# 18. Dataset Reproducibility

A model release should be traceable to:

```text
Dataset Version
Feature Version
Code Version
Training Configuration
Model Version
```

---

# 19. Feature Governance

Features should have:

```text
Name
Definition
Owner
Source
Type
Freshness Requirement
Sensitivity Classification
Allowed Uses
```

where appropriate.

---

# 20. Feature Purpose

A feature should have an explicit purpose.

Example:

```text
Recent Area Demand
```

may support:

```text
Demand Prediction
```

but should not automatically be reused for unrelated profiling.

---

# 21. Feature Sensitivity

Features derived from sensitive source data remain subject to appropriate controls.

Derived data is not automatically non-sensitive.

---

# 22. Derived Data

Examples:

```text
Historical Location Pattern
Driver Behaviour Score
Demand Score
Risk Indicator
```

can reveal information even when direct identifiers are removed.

Treat derived data according to its actual sensitivity.

---

# 23. Location Data

Location is particularly important for ride-hailing.

AI systems may use:

```text
Pickup Location
Drop Location
Driver Location
Historical Movement
Area-Level Demand
```

---

# 24. Precise Location Minimization

Use the lowest geographic precision required by the capability.

For example:

```text
Exact Coordinate
```

should not automatically be stored where:

```text
Area / Zone
```

is sufficient.

---

# 25. Location Retention

Precise historical location should have a defined retention policy.

Do not retain detailed movement histories indefinitely merely because they may be useful for future modelling.

---

# 26. Location Aggregation

Where possible, aggregate historical location into:

```text
Zone
Grid
Area
Time Bucket
```

when exact movement is no longer required.

---

# 27. Temporal Minimization

Use the shortest time window required for the prediction.

Examples:

```text
Recent Demand
Recent Supply
Recent Traffic
```

should not necessarily require indefinite history in online features.

---

# 28. Personal Identifiers

AI datasets should avoid unnecessary direct identifiers.

Examples:

```text
Name
Phone Number
Email
Government Identifier
```

should not be included in model features unless there is a justified and governed requirement.

---

# 29. Pseudonymization

When identity linkage is required, use controlled pseudonymous identifiers where appropriate.

Conceptually:

```text
Real Identity
      ↓
Controlled Identifier
      ↓
ML Dataset
```

The mapping should remain separately protected.

---

# 30. Anonymization

When identity linkage is no longer required, anonymization or aggregation may reduce privacy risk.

However:

```text
Removing a Name
```

does not automatically make a dataset anonymous.

---

# 31. Re-Identification Risk

Consider combinations of fields such as:

```text
Location
Time
Ride Pattern
Unique Behaviour
```

that may allow an individual to be inferred.

---

# 32. Data Aggregation

Aggregation can reduce sensitivity.

Examples:

```text
Driver-Level
→
Area-Level

Ride-Level
→
Hourly Area Statistics
```

Use aggregation where individual-level detail is not required.

---

# 33. Access Control

AI data access should follow:

```text
Least Privilege
```

Users and services should receive only the access required for their responsibilities.

---

# 34. Service-Level Access

AI services should access only the data required for their function.

For example:

```text
ETA Service
```

should not automatically have unrestricted access to:

```text
All User Records
```

---

# 35. Training Access

Training systems should receive controlled access to approved datasets.

Do not give training jobs unrestricted production database access merely for convenience.

---

# 36. Production Database Access

Prefer:

```text
Approved Data Pipeline
```

over:

```text
Direct Unrestricted Production Queries
```

for ML dataset generation.

---

# 37. Database Credentials

AI services should use dedicated credentials with scoped permissions.

Avoid sharing:

```text
Application Superuser Credentials
```

with AI workloads.

---

# 38. Secret Handling

Never store:

```text
Database Passwords
API Keys
Cloud Credentials
Tokens
```

inside:

```text
Training Data
Feature Data
Model Artifacts
Prediction Logs
```

---

# 39. Encryption

Sensitive AI data should use appropriate encryption:

```text
In Transit
At Rest
```

according to platform security requirements.

---

# 40. Network Security

AI services should communicate with data systems through controlled network paths.

Avoid exposing sensitive data stores unnecessarily.

---

# 41. Model Artifacts

Model artifacts may encode information about training data.

Therefore protect:

```text
Model Files
Checkpoints
Embeddings
Feature Statistics
Training Artifacts
```

appropriately.

---

# 42. Embeddings

Embeddings are not automatically anonymous.

An embedding may encode information derived from sensitive source data.

Apply appropriate access and retention controls.

---

# 43. Vector Stores

If RideForge uses vector storage for AI capabilities, govern:

```text
Embedding Source
Embedding Content
Access
Retention
Deletion
```

according to the source data's sensitivity.

---

# 44. Prediction Data

Predictions can themselves be sensitive.

Examples:

```text
Driver Score
Demand Forecast
Behaviour Prediction
Risk Score
```

Treat predictions according to what they reveal and how they are used.

---

# 45. Prediction Logging

Store only the metadata required for:

```text
Monitoring
Evaluation
Debugging
Audit
```

Avoid storing complete sensitive input payloads by default.

---

# 46. Experiment Data

A/B testing may create additional records containing:

```text
Experiment Assignment
Variant
Prediction
Outcome
```

These records must follow the same privacy and retention principles.

---

# 47. AI Observability Data

Logs, metrics, and traces can contain sensitive information.

Do not assume:

```text
Observability Data
```

is exempt from privacy controls.

---

# 48. Logging Restrictions

Avoid logging:

```text
Raw Personal Information
Full Contact Details
Unnecessary Precise Coordinates
Authentication Secrets
Payment Secrets
```

---

# 49. Trace Restrictions

Distributed traces should contain identifiers needed for correlation, but avoid unnecessarily embedding sensitive payloads.

---

# 50. Metric Cardinality and Privacy

Avoid using raw personal identifiers as high-cardinality metric labels.

Examples:

```text
driver_id
rider_id
phone_number
```

should not become routine metric dimensions.

---

# 51. Retention Policy

Every AI data category should have a defined retention principle.

Conceptually:

```text
Purpose Ends
   ↓
Delete
or
Aggregate
or
Anonymize
```

---

# 52. Retention Categories

Define retention separately for:

```text
Operational Data
Training Data
Feature Data
Prediction Metadata
Experiment Data
Logs
Traces
Model Artifacts
```

---

# 53. Indefinite Retention

Indefinite retention should not be the default.

If long-term retention is required:

```text
Document the Purpose
+
Protect the Data
+
Review Periodically
```

# 54. Deletion

Potential locations:

```text
Primary Database
Feature Store
Training Dataset
Prediction Store
Cache
Object Storage
Analytics Store
```

The exact deletion workflow depends on the storage architecture.

Deleting source data does not automatically delete every derived artifact.

```text

Aggregates
Embeddings

```

when defining deletion processes.

---

# 56. Aggregated Data

Aggregated data may have lower privacy risk, but aggregation does not automatically remove all risk.

Very small groups may still be re-identifiable.

---

# 57. Small-Group Protection

Where relevant, avoid exposing highly detailed statistics for very small populations.

---



# 66. Consent and Lawful Use

The AI system should not assume that data being technically accessible means it is automatically permissible to use for every purpose.

The applicable legal basis, notices, consent requirements, contractual requirements, or other governance mechanisms must be determined by the responsible legal/privacy process.

# 117. AI Agent Implementation Rules

When implementing AI data governance, an AI coding agent must:

1. Collect only data required by the defined AI use case.
2. Preserve the source and purpose of important AI data.
3. Classify sensitive data before adding it to an AI pipeline.
4. Avoid unnecessary personal identifiers in model features.
5. Treat precise location data as sensitive operational data.
6. Keep production credentials out of datasets, logs, and model artifacts.
7. Use least-privilege access for AI services and training jobs.
8. Preserve dataset and feature version traceability.
9. Prevent future-data leakage in training and evaluation.
10. Avoid copying production personal data into local development by default.
11. Apply retention and deletion rules to derived AI data where applicable.
12. Treat embeddings and predictions as potentially sensitive data.
13. Avoid logging unnecessary sensitive payloads.
14. Govern third-party AI data transfers explicitly.
15. Preserve experiment identity when experiment data becomes training or evaluation data.
16. Keep data lineage available for production model releases.
17. Update the relevant AI documentation when introducing new data assets.

---

# 118. AI Agent Prohibited Patterns

AI agents must not:

- collect personal data merely because it may be useful later,
- use production databases as unrestricted ML data sources,
- place secrets inside training datasets or model artifacts,
- log sensitive payloads for convenience,
- assume anonymization because a direct identifier was removed,
- treat embeddings as automatically anonymous,
- retain precise location histories indefinitely without a defined purpose,
- use future information in training features,
- send unnecessary sensitive data to third-party AI services,
- silently reuse data for an unrelated purpose,
- bypass access controls for model development,
- copy production personal data into local development without authorization,
- assume deleted source data disappears automatically from derived datasets,
- create new sensitive profiling features without governance review,
- treat technical accessibility as proof that data use is permissible.

# 125. Final Principle

> **RideForge AI must treat data as a governed product asset, not as unlimited fuel for machine learning.**

The desired model is:

```text
Purpose
  ↓
Minimize
  ↓
Protect
  ↓
Use
  ↓
Trace
  ↓
Retain Appropriately
  ↓
Delete / Aggregate
```

A trustworthy AI data system should provide:

```text
Clear Purpose
+
Least-Privilege Access
+
Data Minimization
+
Traceability
+
Controlled Retention
+
Privacy-Aware Observability
+
Governed Model Training
```

without creating:

```text
Uncontrolled Data Collection
+
Indefinite Retention
+
Opaque Profiling
+
Unrestricted Production Access
+
Unnecessary Sensitive Data Exposure
```
