# 1. Purpose

This document defines the architectural structure of the RideForge AI layer and how it integrates with the core ride-hailing platform.

The AI architecture must preserve a clear separation between:

```text
Core Transactional Platform
        +
AI Intelligence Layer
        +
Deterministic Decision / Enforcement Layer
```

The AI layer provides predictions, scores, forecasts, and recommendations.

The core platform remains authoritative for transactional state and business-rule enforcement.

---

# 2. Architectural Objective

The AI architecture should enable RideForge to progressively support:

```text
ETA Prediction
Demand Prediction
Supply Prediction
Candidate Ranking
Driver-Ride Matching
Dispatch Optimization
Operational Intelligence
```

without requiring the core ride-hailing platform to become dependent on a single model, algorithm, or AI provider.

---

# 3. Architectural Principles

The AI architecture follows these principles:

```text
1. AI Is an Intelligence Layer
2. Core State Remains Authoritative
3. Deterministic Rules Enforce Safety
4. AI Interfaces Are Explicit
5. Model Versions Are Traceable
6. AI Failures Have Fallbacks
7. Training and Inference Are Separated
8. Offline and Online Data Semantics Must Match
9. AI Decisions Must Be Observable
10. AI Complexity Must Be Justified
```

# 5. Core Architectural Boundary

The most important boundary is:

```text
AI Prediction
        ≠
Business Authority
```

For example:

```text
AI:
Driver A score = 0.91
```

does not mean:

```text
Driver A must receive the ride
```

The application must still verify:

```text
Driver Available?
Driver Eligible?
Region Allowed?
Ride Still Assignable?
Reservation Successful?
```

---

# 6. Core Platform Responsibilities

The core RideForge platform remains responsible for:

```text
Ride Lifecycle
Driver State
Reservation
Assignment
Authentication
Authorization
Region Validation
Business Rules
Payment State
Persistence
Transactional Consistency
```

These responsibilities should not be moved into an AI service simply because an AI model participates in the workflow.

# 7. AI Layer Responsibilities

The AI layer is responsible for intelligence-oriented workloads such as:

```text
Prediction
Scoring
Ranking
Forecasting
Classification
Optimization Signals
```

It should expose explicit contracts to the core platform.

# 8. AI Architectural Domains

The AI layer can be organized into these logical domains:

```text
AI Data
    ↓
Feature Engineering
    ↓
Model Training
    ↓
Model Registry
    ↓
Inference
    ↓
Prediction / Ranking
    ↓
Decision Integration
    ↓
Monitoring / Feedback
```

These are logical boundaries.

They do not automatically require one microservice per box.

---

# 9. Avoiding AI Microservice Overengineering

The logical architecture must not be interpreted as a requirement to immediately create:

```text
ETA Service
Demand Service
Ranking Service
Feature Service
Model Service
Training Service
Registry Service
```

as separate deployable services.

The deployment boundary should follow actual operational needs.

---

# 10. AI Service Boundary

A dedicated AI service becomes useful when one or more of the following are true:

```text
Independent Scaling
Independent Model Lifecycle
Different Runtime
Specialized ML Dependencies
Independent Deployment
GPU / Specialized Compute
Multiple Consumers
```

Until those needs exist, related AI functionality may remain within an appropriately isolated application component.

# 15. PostgreSQL in the AI Architecture

PostgreSQL remains a core system of record.

AI workloads may consume curated data from PostgreSQL, but AI-specific analytical access should not interfere with transactional workloads.

Where AI workloads become large, use appropriate separation rather than allowing analytical queries to overload the transactional database.

---

# 16. Redis in the AI Architecture

Redis can provide low-latency operational state needed by AI-assisted workflows.

Examples include:

```text
Driver Location
Availability
Spatial Candidate State
Temporary Operational Signals
```

Redis should not become the authoritative source for transactional business state merely because an AI component reads from it.

# 19. Feature Freshness

Examples:

```text

→ Near Real-Time

Demand History
→ Historical / Aggregated

Driver Performance
```

# 20. Feature Availability

If required features are unavailable:

```text
Feature Missing
        ↓
Inference Decision
        ├── Safe Default / Fallback
        └── Inference Rejected
```

Do not silently substitute arbitrary values for missing features unless the model was explicitly designed for that behaviour.

---

# 21. Offline / Online Feature Consistency

The same feature semantics must be maintained between:

```text
Training
```

and:

```text
Inference
```

For example, if:

```text
average_driver_eta
```

has a particular definition during training, the online system must use the same definition.

# 22. Model Interface

Models should be accessed through explicit interfaces.

A conceptual prediction request may contain:

```text
Model Capability
Feature Set
Request Context
Timestamp
```

A response may contain:

```text
Prediction
Model Version
Quality / Confidence Signal
Inference Timestamp
```

Only fields actually required by the consumer should be returned.

# 23. Model Output Validation

Every AI output must be validated before being used.

Examples:

```text
ETA >= 0
Score within expected range
Probability within [0, 1]
Ranking contains valid candidates
```

Invalid model output must trigger the defined fallback.

Conceptually:

```text
+
```

A model deployment should be independent from application logic where practical.

The application should depend on a stable inference contract rather than directly coupling business logic to model implementation details.


The budget includes:

```text

+

+
Inference
+

+
```

Every online AI call should have a bounded timeout.

Conceptually:

```text

 ↓
```

# 33. Candidate Eligibility

Eligibility should be resolved before AI ranking whenever possible.

Examples:

```text
Driver Online
Driver Available
Vehicle Eligible
Region Allowed
Operationally Eligible
```

AI should not spend inference capacity ranking candidates that cannot legally or operationally receive the ride.

---

# 34. Candidate Ranking

Ranking may combine:

```text
Predicted ETA
Distance
Driver State
Demand Conditions
Supply Conditions
Historical Signals
Operational Policy
```

The ranking system should remain configurable so that the platform can evolve from deterministic scoring to predictive ranking.

---

# 35. Reservation Boundary

AI ranking must end before the authoritative reservation operation.

Conceptually:

```text
AI:
"Candidate A is preferred."

Core System:
"Attempt reservation."

Database / Transaction:
"Reservation succeeded or failed."
```

This prevents AI output from becoming an unsafe state mutation.

---

# 36. Race Conditions

Two dispatch attempts may independently rank the same driver.

Therefore:

```text
Ranking
```

does not reserve the driver.

The authoritative reservation mechanism must resolve concurrent claims.

# 42. Training / Validation Separation

Training data must not accidentally leak future information into model inputs.

Time-dependent ride-hailing data requires special attention to:

```text
Temporal Leakage
Future Events
Post-Outcome Features
```

The dataset construction process must respect the prediction point.

---

# 43. Prediction Point

Every predictive model should define:

```text
What is known?
When is it known?
What is being predicted?
When does the prediction become useful?
```

For example:

```text
At Ride Request Time
→ Predict Pickup ETA
```

Features that become available only after pickup cannot be used for that prediction.

---

# 81. AI Agent Architecture Rules

An AI coding agent working on the AI architecture must:

1. Inspect existing architecture documentation first.
2. Inspect existing AI components before adding a new one.
3. Preserve the core transactional boundary.
4. Avoid creating microservices solely for conceptual separation.
5. Reuse existing event infrastructure where appropriate.
6. Reuse existing PostgreSQL and Redis infrastructure where appropriate.
7. Define explicit AI input/output contracts.
8. Validate AI output before business use.
9. Define fallback behaviour.
10. Preserve model version traceability.
11. Avoid inventing unavailable infrastructure.
12. Avoid inventing model performance.
13. Update the correct documentation file rather than creating duplicates.

# 82. AI Agent Prohibited Architecture Patterns

AI agents must not:

- make an AI model the authoritative source of ride state,
- bypass deterministic region or regulatory validation,
- directly mutate transactional state from model output without an application boundary,
- create one service per AI concept without an operational reason,
- introduce a feature store solely because it is common in ML architectures,
- introduce GPU infrastructure without a model requirement,
- introduce an LLM where a deterministic or predictive model is more appropriate,
- couple core business logic directly to model internals,
- remove fallback behaviour,
- use unbounded inference latency,
- silently change prediction semantics,
- duplicate architecture documentation already owned by another document.

# 84. Final Architecture Principle

> **RideForge AI is an intelligence layer around the core ride-hailing platform, not a replacement for the platform's transactional and business-rule authority.**

The architecture must allow:

```text
AI to Predict
AI to Rank
AI to Forecast
AI to Recommend
AI to Optimize
```

while ensuring:

```text
Core Platform
→ Validates
→ Authorizes
→ Reserves
→ Persists
→ Executes
```

The resulting system should be able to become progressively more intelligent without becoming progressively less reliable.
