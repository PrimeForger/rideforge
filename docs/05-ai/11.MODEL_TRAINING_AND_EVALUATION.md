# 1. Purpose

This document defines how RideForge AI and machine-learning models are:

```text
Defined
↓
Trained
↓
Validated
↓
Evaluated
↓
Compared
↓
Approved
↓
Promoted
```

The objective is to ensure that a model is not considered production-ready merely because it can produce predictions.

A production model must demonstrate:

```text
Predictive Value
+
Data Integrity
+
Operational Reliability
+
Acceptable Latency
+
Acceptable Cost
+
Safe Failure Behaviour
```

---

# 2. Core Principle

> **Every model must beat an appropriate baseline or provide another explicitly justified operational benefit before it is promoted to production.**

The preferred progression is:

```text
Business Objective
        ↓
Baseline
        ↓
Dataset
        ↓
Candidate Model
        ↓
Offline Evaluation
        ↓
Operational Evaluation
        ↓
Controlled Deployment
```

# 4. Model Objective

Before training, define exactly what the model is expected to predict or rank.

Examples:

```text
ETA:
Predict travel duration.

Demand:
Predict future ride requests.

Supply:
Predict future driver availability.

Ranking:
Order eligible candidates according to the defined dispatch objective.
```

A model objective must be measurable.

---

# 5. Business Objective vs Model Objective

The business objective may be:

```text
Improve Pickup Experience
```

while the model objective may be:

```text
Predict Pickup ETA
```

The two should be connected.

Do not optimize a technical metric that has no meaningful relationship to the actual product objective.

---

# 6. Baseline First

Every model evaluation should begin with a baseline.

Examples:

```text
ETA
→ Routing Estimate

Demand
→ Historical / Seasonal Baseline

Supply
→ Current / Historical Baseline

Ranking
→ Deterministic Ranking
```

The baseline establishes the minimum acceptable reference.

---

# 7. Baseline Requirements

A baseline should be:

```text
Simple
Reproducible
Relevant
Measurable
Available
```

A complicated baseline that cannot be reproduced reliably is not useful.

---

# 8. Dataset Selection

Training data must come from the approved ML data pipeline.

The training run should identify:

```text
Dataset Version
Time Range
Feature Version
Label Version
Schema Version
```

where applicable.

---

# 9. Dataset Quality Gate

Do not begin training if critical dataset checks fail.

Required checks may include:

```text
Schema Validity
Missing Data
Invalid Values
Duplicate Records
Label Availability
Point-in-Time Correctness
Leakage Checks
Distribution Checks
```

---

# 10. Training Dataset

The training dataset should contain:

```text
Features
+
Target
+
Required Metadata
```

Identifiers should only be included when needed for:

```text
Joining
Grouping
Evaluation
Traceability
```

---

# 11. Validation Dataset

The validation dataset is used for:

```text
Model Selection
Hyperparameter Tuning
Threshold Selection
Feature Decisions
```

It should not be treated as the final unbiased test.

---

# 12. Test Dataset

The test dataset should represent unseen data and be protected from repeated tuning.

It is used for:

```text
Final Evaluation
Model Comparison
Release Decision
```

---

# 13. Time-Based Splitting

For RideForge's time-dependent systems, time-aware splitting should be preferred where appropriate.

Conceptually:

```text
Older Data
→ Training

Later Data
→ Validation

Newest Data
→ Test
```

This better represents production behaviour.

---

# 14. Geographic Splitting

Where geography materially affects performance, evaluate across:

```text
Operating Region
Zone
Urban Area
Low-Density Area
```

A model should not be approved based only on a global average if important regions perform poorly.

---

# 15. Leakage Prevention

Before training, verify:

```text
No Future Events
No Future Outcomes
No Post-Decision Information
No Test Data Leakage
No Label Leakage
```

This is mandatory for production-quality evaluation.

---

# 18. Random Seeds


Record relevant environment information such as:

```text

   ↓

   ↓

   ↓

   ↓

   ↓

   ↓

   ↓
```

---

# 21. Preprocessing

Preprocessing must be consistent with the feature definitions.

Examples:

```text
Scaling
Encoding
Missing Value Handling
Feature Selection
Transformation
```

The same required preprocessing must be available during production inference.

---

# 22. Preprocessing Versioning

Material preprocessing changes should be versioned.

Do not train:

```text
Model V2
```

with a different transformation while pretending it uses the same feature definition.

---

# 23. Training Objective

The optimization objective should match the model task.

Examples:

```text
Regression
→ Travel Time Error

Classification
→ Outcome Classification

Forecasting
→ Forecast Error

Ranking
→ Ranking Objective
```

---

# 24. Hyperparameter Tuning

Hyperparameters may be tuned using:

```text
Manual Search
Grid Search
Random Search
Bayesian Optimization
```

The simplest appropriate method should be preferred.

---

# 25. Hyperparameter Search Boundaries

Search spaces should be constrained.

Avoid:

```text
Unlimited Search
```

because it increases:

```text
Training Cost
Experiment Count
Overfitting Risk
Operational Complexity
```

---

# 26. Validation During Tuning

Hyperparameter selection should use:

```text
Validation Data
```

rather than repeatedly optimizing against the final test set.

---

# 27. Test Set Protection

The test dataset should not be repeatedly used to select:

```text
Features
Hyperparameters
Thresholds
Model Architecture
```

Doing so reduces the reliability of the final evaluation.

---

# 28. Early Stopping

Where supported, early stopping may reduce:

```text
Overfitting
Training Time
Compute Cost
```

The stopping criterion must be defined using validation data.

---

# 29. Overfitting

Monitor the difference between:

```text
Training Performance
```

and:

```text
Validation Performance
```

A model that performs exceptionally on training data but poorly on validation data may be overfitting.

---

# 30. Underfitting

A model may underfit when:

```text
Training Performance
≈
Poor Validation Performance
```

Potential causes include:

```text
Insufficient Features
Insufficient Model Capacity
Incorrect Objective
Poor Data
```

---

# 31. Evaluation Metrics

Metrics must match the model objective.

Potential regression metrics:

```text
MAE
RMSE
Median Absolute Error
Percentile Error
```

Potential classification metrics:

```text
Precision
Recall
F1
ROC-AUC
PR-AUC
Calibration
```

Potential forecasting metrics:

```text
MAE
RMSE
Forecast Bias
Suitable Percentage Error
```

Potential ranking metrics:

```text
Top-K Quality
Pairwise Ranking Metrics
NDCG
Ranking Accuracy
```

Only use metrics that are appropriate for the task.

---

# 32. Primary Metric

Each model should define:

```text
Primary Metric
```

This is the main metric used for the model objective.

---

# 33. Secondary Metrics

Secondary metrics can identify trade-offs.

Examples:

```text
Accuracy
Latency
Memory
Cost
Fallback Rate
Regional Error
```

A model should not be promoted based on one metric while ignoring severe regressions in important secondary metrics.

---

# 34. Business Metrics

Where possible, evaluate downstream business outcomes.

Examples:

```text
Pickup ETA
Assignment Success
Driver Acceptance
Cancellation
Unserved Demand
Driver Utilization
```

The relevant metric depends on the model.

---

# 35. Model vs Baseline Comparison

Always compare:

```text
Candidate Model
vs
Baseline
```

at minimum.

Example:

```text
Baseline MAE
Candidate MAE
Improvement
```

---

# 36. Improvement Calculation

For error metrics:

```text
Improvement =
(Baseline Error - Model Error)
/
Baseline Error
```

The exact reporting method should be documented.

Do not report improvement without specifying:

```text
Dataset
Metric
Evaluation Window
Baseline
Model
```

---

# 37. Statistical Significance

Where an experiment is large enough, evaluate whether observed improvements are likely meaningful rather than random.

The method should match the metric and experiment design.

Do not claim statistical significance without an appropriate test.

---

# 38. Confidence Intervals

Where useful, report:

```text
Metric
+
Confidence Interval
```

This is especially valuable when comparing models with small performance differences.

---

# 39. Error Distribution

Do not rely only on the mean.

Inspect:

```text
Median
P90
P95
P99
Outliers
```

where relevant to the operational use case.


# 45. Worst-Case Segment

Do not approve a model solely because:

```text
Global Average
```


# 46. Geographic Performance

A model may perform differently by geography due to:

```text
Road Patterns

Supply Density
Data Volume
Operating Rules
```

---

# 47. Temporal Performance

Evaluate across:

```text
Peak
Off-Peak
Weekday
Weekend
Seasonal Periods
```

where relevant.

---

# 48. Data Volume Segmentation

Compare model performance across:

```text
High Data Volume
Medium Data Volume

```

---

# 49. Cold-Start Evaluation

Explicitly test:

```text
New Region
New Zone
New Driver
Sparse Area
```

where applicable.

A production model must have a defined fallback for insufficient data.

---

# 50. Backtesting

Forecasting models should be backtested over historical periods.

Conceptually:

```text
Historical Cutoff
       ↓
Generate Forecast
       ↓
Compare With Known Future
       ↓
Measure Error
```

The same information-availability rules used in production must be preserved.

---

# 51. Rolling Evaluation

For time-dependent models, evaluation can use multiple historical windows:

```text
Window 1
Window 2
Window 3
...
```

This helps determine whether performance is stable across time.

---

# 52. Stability Evaluation

A model should be evaluated for:

```text
Performance Stability
Prediction Stability
Latency Stability
```

A model with slightly better average accuracy but severe instability may be unsuitable for production.

---

# 53. Prediction Distribution

Inspect:

```text
Minimum
Maximum
Mean
Median
Percentiles
```

Unexpected prediction distributions may indicate:

```text
Feature Failure
Training Issue
Model Bug
Data Drift
```

---

# 54. Residual Analysis

For regression models, inspect:

```text
Prediction
vs
Actual
```

and:

```text
Residual
=
Prediction - Actual
```

Look for systematic patterns.

---

# 55. Bias Analysis

Check whether the model systematically:

```text
Overpredicts
Underpredicts
```

for specific:

```text
Regions
Times
Areas
Data Volumes
```

---

# 56. Outlier Analysis

Investigate extreme errors.

Do not automatically remove them.

An outlier may represent:

```text
Data Error
```

or:

```text
Real Operational Condition
```

---

# 57. Error Taxonomy

Classify important model errors:

```text
Data Problem
Feature Problem
Model Problem
Label Problem
Operational Change
External Condition
```

This helps determine the correct remediation.

---

# 58. Model Explainability

Where appropriate, use explainability methods to understand:

```text
Important Features
Unexpected Dependencies
Prediction Behaviour
```

Explainability should support engineering and operational analysis rather than become a substitute for evaluation.

---

# 59. Feature Importance Review

Before production, inspect whether the model relies heavily on:

```text
Expected Features
```

rather than:

```text
Suspicious Leakage Features
```

Unexpected feature importance should trigger investigation.

---

# 60. Model Sanity Checks

Every candidate model should pass basic sanity checks.

Examples:

```text
No Negative ETA
No Negative Demand
No Negative Supply
Valid Ranking Scores
Valid Output Shape
```

---

# 61. Monotonic Expectations

Where domain logic implies a directional relationship, test it where appropriate.

Example:

```text
Greater route distance
```

should not produce:

```text
Unreasonably lower travel time
```

without a valid contextual reason.

Do not impose artificial monotonic rules when the domain does not justify them.

---

# 62. Robustness Testing

Test model behaviour under:

```text
Missing Features
Stale Features
Extreme Values
Sparse Data
High Demand
Low Supply
```

---

# 63. Input Perturbation

Where useful, slightly vary valid inputs and observe whether predictions behave reasonably.

This can identify:

```text
Unstable Models
Unexpected Sensitivity
Implementation Errors
```

---

# 64. Model Failure Testing

Simulate:

```text
Model Timeout
Model Error
Invalid Output
Feature Failure
Dependency Failure
```

The model's production fallback must remain functional.

---

# 65. Latency Evaluation

Measure:

```text
Feature Retrieval
Preprocessing
Inference
Postprocessing
Total Prediction Time
```

The total must fit the consumer's latency budget.

---

# 66. Resource Evaluation

Measure:

```text
CPU
Memory
GPU, if applicable
Network
Storage
```

Use only the resources actually required by the selected implementation.

---

# 67. Cost Evaluation

Estimate:

```text
Training Cost
Inference Cost
Feature Cost
Storage Cost
Monitoring Cost
```

A model is not production-ready if its cost is incompatible with the product's operating constraints.

---

# 68. Model Size

Model size matters for:

```text

Startup
Memory
Deployment
Scaling
```

Prefer the smallest model that satisfies the objective.

# 106. AI Agent Implementation Rules

When implementing model training or evaluation, an AI coding agent must:

1. Identify the exact model objective.
2. Establish a deterministic baseline.
3. Use an approved dataset.
4. Verify dataset quality before training.
5. Preserve point-in-time correctness.
6. Prevent training and test leakage.
7. Define primary and secondary metrics.
8. Protect the test set from tuning.
9. Evaluate important geographic and temporal segments.
10. Measure latency and resource usage where relevant.
11. Record training configuration.
12. Record dataset and feature versions.
13. Make experiments reproducible where required.
14. Never fabricate evaluation results.
15. Preserve the deterministic production fallback.
16. Prepare rollback before controlled deployment.
17. Update the relevant AI documentation.

---

# 107. AI Agent Prohibited Patterns

AI agents must not:

- train on unvalidated data,
- use future outcomes as input features,
- repeatedly tune against the final test set,
- declare a model production-ready because training succeeded,
- fabricate metrics,
- compare models using different datasets without disclosure,
- ignore important segment regressions,
- remove the baseline,
- deploy a candidate directly to full production without the required rollout process,
- silently change preprocessing,
- omit model or dataset version information,
- make AI model output authoritative transactional state,
- remove fallback behaviour,
- optimize for technical metrics unrelated to the business objective.

---

# 108. Recommended Initial Training Strategy

For the current RideForge stage:

```text
1. Establish Baseline
2. Build Small, Reliable Dataset
3. Train Simple Candidate
4. Compare Against Baseline
5. Perform Segment Evaluation
6. Validate Latency / Cost
7. Shadow Candidate
8. Measure Production Outcomes
9. Promote Only With Evidence
```

Avoid beginning with highly complex training infrastructure.

# 112. Final Principle

> **A model becomes valuable only when measured evidence shows that it improves a real RideForge decision without creating unacceptable operational cost or risk.**

The intended lifecycle is:

```text
Measure
   ↓
Train
   ↓
Compare
   ↓
Understand
   ↓
Validate
   ↓
Control
   ↓
Deploy
   ↓
Observe
   ↓
Improve
```

The goal is not to maximize model sophistication.

The goal is to build the **simplest model that reliably improves the defined RideForge objective over a validated baseline and can be safely operated in production.**
