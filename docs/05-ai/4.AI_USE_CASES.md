# 1. Purpose

This document defines the AI use cases planned for RideForge.

It answers:

```text
Where should AI be used?
What problem does each use case solve?
What does it consume?
What does it produce?
Who consumes the result?
How important is it?
What happens when AI is unavailable?
```

This document is a **use-case catalogue**.

Detailed implementation belongs in the dedicated AI documents.

---

# 2. AI Use-Case Principle

AI should be introduced only where it can provide measurable value.

The preferred progression is:

```text
Business Problem
        ↓
Baseline
        ↓
Data Availability
        ↓
AI Candidate
        ↓
Offline Evaluation
        ↓
Controlled Production
        ↓
Measured Outcome
```

A use case should not be implemented merely because a machine-learning technique is available.

---

# 3. Use-Case Categories

RideForge AI use cases fall into the following categories:

```text
Real-Time Intelligence
    ├── ETA Prediction
    ├── Candidate Ranking
    └── Smart Dispatch

Predictive Intelligence
    ├── Demand Prediction
    ├── Supply Prediction
    └── Cancellation / Risk Prediction

Operational Intelligence
    ├── Supply Positioning
    ├── Demand-Supply Balancing
    └── Operational Forecasting

Optimization
    ├── Matching Optimization
    ├── Dispatch Optimization
    └── Adaptive Strategy Optimization
```

Not every category needs to be implemented immediately.


Better ETA can improve:

```text
Rider Experience
```

```text

Historical Travel Patterns
```

# 7. Use Case: Smart Dispatch

## 7.1 Objective

Select the best eligible driver for a ride using richer operational signals than simple proximity.

Conceptually:

```text
Ride
 ↓
Eligible Candidates
 ↓
Signals
 ↓
Ranking
 ↓
Preferred Candidate
```

---

## 7.2 Business Value

Potential improvements include:

```text
Lower Pickup Time
Better Driver Utilization
Better Matching Quality
Lower Cancellation
Better Supply Distribution
```

---

## 7.3 Inputs

Potential signals:

```text
Driver Location
ETA
Distance
Availability
Demand
Supply
Ride Characteristics
Operational Policy
Historical Signals
```

---

## 7.4 Output

The AI layer may produce:

```text
Candidate Scores
+
Ranking
+
Recommendation
```

The core platform performs the authoritative reservation.

---

## 7.5 Important Boundary

```text
AI Recommendation
        ≠
Reservation
```

A driver can become unavailable after the AI decision.

The core transactional system must therefore perform the final reservation.

---

## 7.6 Fallback

Potential fallback:

```text
AI Ranking unavailable
        ↓
Deterministic Ranking
```

or another configured dispatch strategy.

Allow dispatch behaviour to adapt to changing operating conditions.

```text
Current Conditions
        ↓
Predictions
        ↓

        ↓
```

```text

```

# 19. Use Case: Demand-Aware Ranking

Ranking may incorporate predicted future demand.

Example concept:

```text
Candidate A:
Fast Pickup
but
Located in a high-demand area

Candidate B:
Slightly slower
but
Located in a low-demand area
```

A policy may decide whether preserving Candidate A's future availability has value.

This should be evaluated experimentally rather than assumed to improve outcomes.

---

# 20. Use Case: Supply-Aware Ranking

Ranking can consider expected supply conditions.

Potential goal:

```text
Optimize Immediate Assignment
+
Avoid Creating Future Supply Imbalance
```

This is an advanced use case and should be introduced only after reliable demand and supply predictions exist.

# 34. Use Case: AI Shadow Evaluation

A candidate model can run without controlling production decisions.

```text
Production Request
       ├── Existing System → Actual Decision
       │
       └── Candidate AI → Shadow Prediction
```

Compare:

```text
Prediction
vs
Actual Outcome
```

before enabling the model.

A model may perform differently across regions.

```text
Region A
Region B
Region C
```

# 37. Use Case: Cold Start

New regions or newly launched services may have insufficient historical data.

Fallback strategies may include:

```text
Deterministic Baseline
Global Model
Regional Baseline
Transferable Features
```

Do not assume every region has enough data for a custom model.

---

# 38. Use Case: New Driver Cold Start

A new driver may have little or no historical behaviour.

Models must avoid requiring unavailable driver history.

Possible alternatives:

```text
Fleet-Level Features
Recent Operational Signals
Neutral Prior
```

The exact strategy should be capability-specific.

---

# 39. Use Case: New Ride Cold Start

A newly created ride may lack historical ride-specific information.

Use only features available at prediction time.

---

# 40. Use Case: Sparse Areas

```text
Sparse Data

Low Sample Size
```

Fallbacks may be required.

# 54. Use-Case Independence

Failure of one use case should not automatically disable unrelated capabilities.

For example:

```text
Demand Prediction Failure
```

should not inherently disable:

```text
ETA Prediction
```

unless ETA explicitly depends on the failed capability.

# 55. Use-Case Fallback Matrix

| Use Case | Primary Intelligence | Possible Fallback |
|---|---|---|
| ETA | Predictive ETA | Routing / deterministic ETA |
| Smart Dispatch | AI ranking | Deterministic ranking |
| Candidate Ranking | Predictive scoring | Rule-based scoring |
| Demand Prediction | Forecast model | Historical baseline |
| Supply Prediction | Supply model | Current / historical baseline |
| Matching | Matching intelligence | Deterministic ranking |
| Driver Positioning | Demand-supply forecast | Rule-based positioning |
| Cancellation Prediction | Risk model | No predictive intervention |
| Anomaly Detection | Detection model | Statistical thresholds |
| Adaptive Dispatch | Optimization | Fixed approved policy |

The actual fallback for each capability must be documented before production deployment.

# 56. Use-Case Evaluation Metrics

Each AI use case should define metrics.

Examples:

| Use Case | Example Metrics |
|---|---|
| ETA | MAE, RMSE, percentile error, pickup-time impact |
| Ranking | Match success, pickup ETA, ranking quality |
| Smart Dispatch | Assignment success, pickup time, cancellation |
| Demand | Forecast error |
| Supply | Forecast error, supply-gap accuracy |
| Cancellation | Precision, recall, business outcome |
| Anomaly Detection | Detection quality, false-positive rate |
| Optimization | Business outcome improvement |

Model metrics alone are insufficient for production decisions.

unless the data, scale, and business requirement justify them.

# 68. Baseline Requirement

Every important AI use case should have a baseline.

Examples:

```text
ETA
→ Routing / deterministic ETA

Ranking
→ Distance / ETA-based ranking

Demand
→ Historical average / seasonal baseline

Supply
→ Historical availability baseline
```

The AI model must demonstrate improvement over the baseline.

# 71. AI Agent Use-Case Rules

When an AI agent implements a new AI use case, it must:

1. Identify the business problem.
2. Check whether an existing use case already covers it.
3. Define the measurable objective.
4. Identify the baseline.
5. Identify the data requirements.
6. Define the prediction point.
7. Define the output contract.
8. Define consumers.
9. Define latency requirements.
10. Define fallback behaviour.
11. Define success metrics.
12. Add appropriate tests.
13. Update the correct AI documentation.
14. Avoid creating duplicate capabilities.
15. Avoid claiming model performance without measurement.

---

# 72. AI Agent Prohibited Use-Case Patterns

AI agents must not:

- add AI without a measurable purpose,
- create duplicate ETA or dispatch logic,
- bypass deterministic eligibility,
- make model output authoritative transactional state,
- invent training data,
- invent business improvements,
- use unavailable features,
- silently introduce autonomous behaviour,
- remove a fallback to make AI appear more important,
- introduce advanced ML merely for architectural sophistication.
