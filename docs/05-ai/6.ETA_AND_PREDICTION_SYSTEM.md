# 1. Purpose

This document defines the architecture and operational rules for ETA and related travel-time prediction in RideForge.

ETA is a core predictive capability because it can influence:

```text
Rider Experience
Driver Experience
Smart Dispatch
Candidate Ranking
Matching
Operational Planning
```

The system must distinguish between:

```text
Routing Estimate
```

and:

```text
Predictive ETA
```

The predictive layer may improve an existing routing estimate, but the routing system and AI prediction system do not automatically become the same component.

---

# 2. ETA Vision

The objective is:

> **Provide the most useful and sufficiently accurate travel-time estimate available for the current operating context while preserving a deterministic fallback when predictive inference is unavailable.**

The system should optimize for:

```text
Accuracy
+
Freshness
+
Low Latency
+
Reliability
+
Cost
```

not model complexity alone.

---

# 3. ETA Definitions

RideForge should explicitly distinguish the following concepts.

## 3.1 Pickup ETA

Estimated time for the assigned or candidate driver to reach the rider pickup location.

```text
Driver Location
        +
Pickup Location
        ↓
Pickup ETA
```

This is particularly important for dispatch.

---

## 3.2 Trip ETA

Estimated travel time from pickup to destination.

```text
Pickup
   +
Destination
      ↓
Trip ETA
```

This can support rider experience and operational planning.

---

## 3.3 Total Journey Estimate

Where required by the product:

```text
Pickup ETA
+
Trip ETA
=
Journey Estimate
```

The two components should remain distinguishable internally even if the client displays a combined value.

---

# 4. ETA Prediction Point

Every prediction must define exactly when it is made.

Examples:

```text
At Ride Request
→ Predict Driver Pickup ETA

After Driver Assignment
→ Predict Assigned Driver Pickup ETA

After Pickup
→ Predict Trip Duration
```

A model must only use information that was actually available at the prediction point.

---

# 5. Prediction-Time Data Rule

The most important data rule is:

> **A prediction may only use information available at the time the prediction is supposed to be made.**

For example:

```text
Prediction Time: Ride Request
```

must not use:

```text
Actual Pickup Time
Actual Trip Duration
Post-Assignment Events
```

because those values would not have been known yet.

---

# 6. ETA Architecture

The conceptual architecture is:

```text
Ride / Driver Context
        ↓
Location + Route Context
        ↓
Feature Resolution
        ↓
Routing Baseline
        ↓
ETA Prediction
        ↓
Prediction Validation
        ↓
ETA Result
        ↓
Consumers
```

Consumers may include:

```text
Smart Dispatch
Candidate Ranking
Rider Application
Driver Application
Operations
```

---

# 7. Routing Baseline

The predictive ETA system should have a baseline.

A baseline may come from:

```text
Routing Engine
Distance / Duration Estimate
Historical Average
```

depending on the available platform.

The baseline provides:

```text
Fallback
Benchmark
Evaluation Reference
```

---

# 8. Why a Baseline Is Required

A model should demonstrate improvement over an existing useful estimate.

The comparison should be:

```text
Routing / Deterministic Baseline
             vs
Predictive ETA
```

A predictive model is not automatically better because it uses more features.

---

# 9. ETA Inputs

Potential inputs include:

```text
Driver Location
Pickup Location
Destination
Route Distance
Route Duration
Time
Day
Historical Travel Time
Traffic-Related Signals
Road / Area Context
Operational Context
```

Only inputs actually available in the implementation should be used.

---

# 10. Driver Location

Driver location is one of the most important inputs for pickup ETA.

The system should consider:

```text
Current Location
Location Timestamp
Location Freshness
```

A stale location can produce a misleading ETA.

---

# 11. Location Freshness

The ETA system should define what constitutes acceptable location freshness.

Conceptually:

```text
Fresh
→ Normal Prediction

Slightly Stale
→ Prediction with Reduced Confidence / Validation

Too Stale
→ Refresh / Fallback
```

The actual thresholds should be determined by the operational requirements.

---

# 12. Pickup Location

Pickup coordinates must be validated before use.

Validation should include, where applicable:

```text
Latitude Range
Longitude Range
Presence
Expected Geographic Area
```

Invalid coordinates should not be sent to inference as if they were valid.

---

# 13. Destination

Destination is required for trip ETA.

It may not be required for pickup ETA.

Therefore:

```text
Pickup ETA
→ Driver + Pickup

Trip ETA
→ Pickup + Destination
```

Feature requirements should match the prediction objective.

---

# 14. Route Context

Routing information may provide useful baseline signals:

```text
Distance
Estimated Duration
Route Geometry / Summary
Road Context
```

The exact data depends on the routing provider and implementation.

---

# 15. Temporal Features

ETA can vary with time.

Potential temporal signals:

```text
Hour
Day of Week
Weekend
Peak Period
Season
```

Temporal features should be generated consistently between training and inference.

---

# 16. Historical Travel Signals

Historical information may capture recurring travel patterns.

Examples:

```text
Historical Travel Time
Area-Level Travel Time
Time-of-Day Travel Patterns
```

Historical signals must not leak future information into training.

---

# 17. Traffic Signals

If traffic data is available, it may improve ETA.

The architecture should treat external traffic data as:

```text
Input Signal
```

rather than an assumption.

If traffic data is unavailable, the ETA system must continue to operate through its baseline or alternative features.

---

# 18. Feature Categories

ETA features can be grouped as:

```text
Spatial
Temporal
Route
Driver
Traffic
Historical
Operational
```

Each feature should have a clear definition.

---

# 19. Feature Semantics

A feature must document:

```text
Name
Meaning
Unit
Source
Freshness
Availability
Transformation
```

For example:

```text
route_distance
Meaning:
Estimated route distance between origin and destination.

Unit:
Distance unit defined by the platform.

Source:
Routing layer.
```

The exact implementation contract should be maintained in code and relevant feature documentation.

---

# 20. Online Feature Resolution

For real-time ETA:

```text
Prediction Request
        ↓
Resolve Current Features
        ↓
Validate Features
        ↓
Inference
```

Feature retrieval must fit inside the ETA latency budget.

---

# 21. Offline Feature Generation

Training features follow:

```text
Historical Events
        ↓
Validation
        ↓
Transformation
        ↓
Feature Generation
        ↓
Training Dataset
```

The same semantic definitions should be preserved between offline and online processing.

---

# 22. Online / Offline Consistency

Avoid:

```text
Training Feature Definition
        ≠
Production Feature Definition
```

This mismatch can cause:

```text
Training / Serving Skew
```

The feature pipeline should therefore maintain consistent semantics.

---

# 23. Training Data

ETA training data may be derived from completed trips and relevant historical observations.

Potential records include:

```text
Prediction Context
Actual Travel Outcome
Route Context
Time
Location
```

Only data with a reliable target should be used for supervised training.

---

# 24. ETA Target

The target must match the prediction objective.

For pickup ETA:

```text
Prediction Point
→
Actual Driver Arrival Time
```

For trip duration:

```text
Pickup Time
→
Actual Trip Completion Time
```

Do not mix different targets without explicitly defining the model objective.

---

# 25. Label Quality

Training labels should be checked for:

```text
Missing Values
Invalid Timestamps
Negative Duration
Impossible Duration
Duplicate Records
Incorrect Event Ordering
```

Poor labels can produce poor models even when the model architecture is strong.

---

# 26. Temporal Leakage

ETA datasets are particularly vulnerable to temporal leakage.

Do not allow features generated after the prediction point to enter training.

For example:

```text
Actual Arrival Time
```

must not become an input for:

```text
Pickup ETA at Request Time
```

---

# 27. Dataset Splitting

For time-dependent ETA data, evaluation should preserve temporal ordering where appropriate.

Conceptually:

```text
Older Data
→ Training

Later Data
→ Validation

Newest Data
→ Test
```

This better represents production behaviour than random mixing of all historical observations.

---

# 28. Geographic Evaluation

ETA quality can vary by geography.

Evaluate where relevant across:

```text
Operating Region
Urban Areas
Low-Density Areas
High-Density Areas
Different Road Environments
```

A single global metric can hide regional weaknesses.

---

# 29. Time-Based Evaluation

Evaluate across relevant conditions:

```text
Peak
Off-Peak
Weekday
Weekend
High Demand
Low Demand
```

This helps identify model weaknesses that average metrics can hide.

---

# 30. Baseline Metrics

At minimum, compare the predictive model with the chosen baseline.

Possible metrics:

```text
Mean Absolute Error
Median Absolute Error
RMSE
Percentile Error
```

The exact metrics should reflect the business use case.

---

# 31. Business ETA Metrics

Technical prediction error is not enough.

Also evaluate:

```text
Pickup Experience
Dispatch Quality
Rider ETA Accuracy
Driver ETA Accuracy
Cancellation
```

where the product provides enough data to measure these outcomes.

---

# 32. ETA Accuracy

A prediction should be evaluated as:

```text
Predicted ETA
vs
Actual Outcome
```

Do not report accuracy without defining:

```text
Prediction Point
Target
Error Metric
Evaluation Window
Dataset
```

---

# 33. ETA Confidence

If the model supports a valid uncertainty or confidence measure, the system may expose internal quality information.

Possible interpretation:

```text
High Confidence
→ Normal Use

Low Confidence
→ Conservative Behaviour / Fallback
```

Do not fabricate confidence values for models that do not support them.

---

# 34. ETA Output Contract

A conceptual ETA response may contain:

```text
prediction
unit
prediction_timestamp
model_version
feature_version
quality_signal
```

Only fields required by consumers should be exposed.

---

# 35. ETA Units

The unit must be explicit.

For example:

```text
Seconds
```

or:

```text
Minutes
```

Do not allow different services to assume different units.

---

# 36. Output Validation

ETA output must be validated.

Examples:

```text
ETA Exists
ETA Is Numeric
ETA Is Non-Negative
ETA Is Within Reasonable Bounds
Model Version Is Known
```

Invalid output triggers fallback.

---

# 37. Reasonable Bounds

The system may define operational sanity limits.

For example:

```text
Negative ETA
→ Invalid

Extreme ETA
→ Suspicious / Validation Required
```

The actual bounds should be derived from the product and operating environment rather than invented arbitrarily.

---

# 38. ETA Inference

The online inference flow is:

```text
Request
  ↓
Input Validation
  ↓
Feature Resolution
  ↓
Model Selection
  ↓
Inference
  ↓
Output Validation
  ↓
ETA Result
```

---

# 39. Model Selection

The active model may depend on:

```text
Capability
Region
Model Version
Feature Version
Deployment Configuration
```

The selected model must be an approved production model.

---

# 40. Inference Timeout

ETA inference must have a bounded timeout.

```text
ETA Request
      ↓
Inference
      ├── Success
      └── Timeout
             ↓
          Fallback
```

The system must never wait indefinitely for a prediction.

---

# 41. ETA Fallback Hierarchy

A possible hierarchy is:

```text
Predictive ETA
      ↓ failure
Routing ETA
      ↓ failure
Deterministic / Available Baseline
```

The actual hierarchy depends on the available routing and operational infrastructure.

---

# 42. Fallback Metadata

When fallback occurs, the system should be able to determine:

```text
Fallback Used
Fallback Reason
Fallback Type
```

This supports operational monitoring.

---

# 43. ETA and Smart Dispatch

ETA is a key Smart Dispatch input.

Conceptually:

```text
Candidate A → ETA 3 min
Candidate B → ETA 5 min
Candidate C → ETA 7 min
```

The ranking layer can use these predictions alongside other signals.

ETA does not itself make the assignment decision.

---

# 44. ETA for Candidate Ranking

For each eligible candidate:

```text
Candidate
   ↓
ETA Prediction
   ↓
Ranking Signal
```

The ranking system may combine ETA with:

```text
Distance
Demand
Supply
Driver State
Operational Policy
```

---

# 45. Batch ETA

Not every ETA workload requires individual real-time model calls.

Where appropriate, candidate ETA calculations may be optimized through:

```text
Batch Inference
Shared Features
Cached Forecasts
```

Only use batching if it improves overall latency or resource efficiency.

---

# 46. ETA Caching

Caching may be useful for stable or repeated computations.

However, highly dynamic values such as:

```text
Driver Location
Traffic
Availability
```

require strict freshness controls.

Never use a stale cached ETA as authoritative without considering its age.

---

# 47. ETA Refresh

ETA may need to be refreshed when relevant context changes.

Examples:

```text
Driver Moves
Route Changes
Traffic Changes
Ride State Changes
```

The refresh policy should be determined by product requirements.

---

# 48. ETA Update Frequency

The platform should avoid unnecessary high-frequency inference.

Balance:

```text
Freshness
+
Accuracy
+
Latency
+
Compute Cost
```

The update frequency should be based on actual user and dispatch needs.

---

# 49. ETA Model Types

The architecture does not require a single ML technique.

Potential approaches include:

```text
Statistical Model
Gradient-Boosted Model
Neural Model
Hybrid Routing + ML Model
```

The selected approach must be justified by:

```text
Accuracy
Latency
Data
Operational Cost
Maintainability
```

---

# 50. Hybrid ETA Architecture

A practical architecture may combine routing and ML:

```text
Routing Estimate
        +
Contextual Features
        ↓
ETA Model
        ↓
Predicted ETA
```

This allows the model to learn corrections to an established routing baseline.

---

# 51. ETA Model Complexity

Do not start with a complex model without evidence that complexity is required.

A sensible progression is:

```text
Routing Baseline
        ↓
Simple Statistical Correction
        ↓
ML Model
        ↓
More Advanced Model
```

Only move forward when measured improvement justifies the complexity.

# 78. ETA and Dispatch SLA

The complete flow is:

```text
Candidate Discovery
+
Feature Retrieval
+
ETA Inference
+
Ranking
+
Reservation
```

ETA cannot consume the majority of the total dispatch budget without justification.

# 99. ETA Agent Implementation Rules

An AI coding agent implementing ETA must:

1. Identify the exact prediction target.
2. Define the prediction point.
3. Inspect existing routing functionality.
4. Preserve the routing baseline.
5. Identify available data before designing features.
6. Prevent temporal leakage.
7. Keep online and offline feature semantics consistent.
8. Define the output contract.
9. Validate model output.
10. Set a bounded inference timeout.
11. Implement a deterministic fallback.
12. Record model/version metadata where required.
13. Add unit, integration, and failure tests.
14. Measure latency.
15. Avoid inventing model accuracy.
16. Avoid introducing unnecessary ML infrastructure.
17. Update the relevant AI documentation.

---

# 100. ETA Agent Prohibited Patterns

AI agents must not:

- claim ETA accuracy without evaluation,
- use future information as a prediction feature,
- remove the routing baseline,
- make ETA inference a mandatory single point of failure,
- use stale driver location as authoritative without validation,
- return negative or invalid ETA values,
- expose internal model objects as public API contracts,
- introduce complex models without a baseline,
- silently change ETA units,
- silently change ETA semantics,
- log precise location unnecessarily,
- introduce unbounded inference latency,
- remove fallback behaviour.

# 107. Final Principle

> **ETA prediction should improve travel-time estimates without making prediction availability a prerequisite for the core ride-hailing system to operate.**

The intended behaviour is:

```text
Accurate when AI is available
+
Useful when data is imperfect
+
Fast enough for real-time workflows
+
Observable in production
+
Traceable by model version
+
Safe when prediction fails
```

The ETA system therefore follows:

```text
Baseline
   ↓
Predict
   ↓
Validate
   ↓
Serve
   ↓
Observe
   ↓
Compare
   ↓
Improve
```

The model is an intelligence component.

The routing baseline, deterministic validation, fallback, and core transactional platform remain essential parts of the overall ETA architecture.
