# 1. Purpose

This document defines how RideForge AI systems behave when:

```text
The model fails
The feature system fails
The inference service fails
A dependency fails
The prediction is invalid
The prediction is stale
The system is overloaded
A model becomes unsafe
```

The primary objective is:

```text
AI Failure
    ↓
Controlled Degradation
    ↓
Safe Fallback
    ↓
Continued Core Operation
```

The system must not allow an AI failure to automatically become a ride-hailing platform failure.

---

# 2. Core Principle

> **AI is an optimization layer, not a single point of failure for core ride operations.**

The preferred architecture is:

```text
Primary AI
    ↓
Validation
    ↓
Fallback
    ↓
Deterministic / Previously Validated Behaviour
```

---

# 3. Failure Philosophy

RideForge should distinguish:

```text
AI Failure
```

from:

```text
Core Domain Failure
```

For example:

```text
ETA Model Unavailable
```

does not necessarily mean:

```text
Ride Creation Must Fail
```

The system should use the safest appropriate degraded behaviour.

# 18. Health Checks

AI services should expose appropriate health signals for:

```text
Process Health
Model Loaded

Inference Readiness
```

---

# 19. Readiness vs Liveness

Where applicable:

```text
Liveness:
Is the service process alive?

Readiness:
Can the service safely serve AI predictions?
```

A running process is not necessarily ready to serve a valid model.

---

# 20. Model Readiness

A model should not receive production traffic until:

```text
Artifact Loaded
+
Schema Compatible
+
Smoke Test Passed
+
Required Dependencies Available
```

---

# 21. Failure Isolation

An AI failure should remain isolated from unrelated platform components.

For example:

```text
Demand Forecast Failure
```

should not automatically stop:

```text
Ride Creation
```

---

# 22. Bulkhead Principle

Separate workloads where practical:

```text
Online Inference
Offline Training
Forecasting
Evaluation
```

so that one workload cannot consume all shared resources.

---

# 23. Timeout Strategy

Every online AI dependency should have a bounded timeout.

Conceptually:

```text
Request
  ↓
AI Call
  ↓
Timeout
  ↓
Fallback
```

---

# 24. Timeout Must Be Bounded

Never allow:

```text
AI Dependency
```

to wait indefinitely.

An AI timeout must fit within the parent request's latency budget.

---

# 25. Retry Strategy

Retries should be used only for failures that are reasonably transient.

Potential retryable failures:

```text
Temporary Network Error
Transient Service Unavailability
```

Do not blindly retry:

```text
Invalid Input
Invalid Model Output
Schema Mismatch
Authorization Failure
```

---

# 26. Bounded Retries

Retries should be:

```text
Limited
Time-Bounded
Observable
Idempotency-Aware
```

---

# 27. Exponential Backoff

For suitable transient failures:

```text
Retry
  ↓
Backoff
  ↓
Retry
```

Do not create rapid retry storms.

---

# 28. Retry Storm Protection

When a dependency is unhealthy:

```text
Many Requests
    ↓
Many Retries
    ↓
More Load
    ↓
Worse Failure
```

Avoid this feedback loop with:

```text
Retry Limits
Circuit Breaker
Backoff
Fallback
```

---

# 29. Circuit Breaker

A circuit breaker can prevent repeated calls to a known-failing AI dependency.

Conceptually:

```text
Closed
  ↓
Failures
  ↓
Open
  ↓
Fallback
  ↓
Recovery Check
  ↓
Half-Open
  ↓
Healthy
  ↓
Closed
```

---

# 30. Circuit Breaker Rules

A circuit breaker should be:

```text
Observable
Bounded
Recoverable
```

Thresholds should be based on measured behaviour rather than arbitrary values.

---

# 31. Fallback Principle

A fallback must be:

```text
Known
Safe
Deterministic Where Possible
Operationally Valid
Observable
```

---

# 32. Fallback Hierarchy

A useful hierarchy is:

```text
Primary AI
   ↓
Validated Secondary AI
   ↓
Cached / Recent Valid Prediction
   ↓
Deterministic Algorithm
   ↓
Reduced Functionality
```

The appropriate level depends on the use case.

---

# 33. Fallback Must Not Introduce New Risk

A fallback should not bypass:

```text
Legal Validation
Safety Constraints
Eligibility
Domain State Validation
```

---

# 34. Fallback Selection

Select fallback based on:

```text
Decision Criticality
Freshness Requirement
Operational Risk
Latency Budget
Available Dependencies
```

---

# 35. ETA Fallback

Possible hierarchy:

```text
Primary ETA Model
      ↓
Secondary ETA Model
      ↓
Routing-Based ETA
      ↓
Configured Safe Estimate
```

The actual production hierarchy should be validated for the specific deployment.

---

# 36. Matching Fallback

Possible hierarchy:

```text
AI Ranking
      ↓
Validated Ranking Model
      ↓
Deterministic Candidate Ranking
      ↓
First Valid Candidate
```

The deterministic path must still enforce all hard constraints.

---

# 37. Smart Dispatch Fallback

If Smart Dispatch AI is unavailable:

```text
Smart Dispatch
      ↓
Stand Dispatch / Deterministic Dispatch
```

where the operating region and configuration permit the deterministic strategy.

This preserves the project's ability to support both:

```text
Smart Dispatch
```

and:

```text
Stand Dispatch
```

without making AI mandatory for all operations.

---

# 38. Demand Forecast Fallback

Possible fallback:

```text
Current Forecast
      ↓
Historical Baseline
      ↓
Recent Rolling Average
```

The selected fallback must be appropriate to the forecast horizon.

---

# 39. Supply Forecast Fallback

Possible fallback:

```text
Current Forecast
      ↓
Recent Supply Baseline
      ↓
Historical Pattern
```

---

# 40. Ranking Fallback

If ranking inference fails:

```text
AI Ranking
    ↓
Deterministic Ranking
```

Possible deterministic signals:

```text
Distance
Availability
Eligibility
Operational Priority
```

Only approved signals should be used.

---

# 41. Feature Failure

If an AI model depends on a missing feature:

```text
Missing Feature
      ↓
Feature Contract Check
      ↓
Defined Default / Alternate Feature / Fallback
```

Do not silently invent arbitrary values.

---

# 42. Stale Feature

If:

```text
Feature Age > Allowed Freshness
```

then:

```text
Do Not Treat as Fresh
```

Possible actions:

```text
Refresh
Use Defined Safe Default
Use Alternate Model
Use Fallback
```

---

# 43. Partial Feature Failure

If only some features are unavailable:

```text
Determine Whether Model Contract Supports Missing Features
```

If not:

```text
Fallback
```

---

# 44. Model Output Failure

If output is:

```text
Null
NaN
Infinity
Out of Range
Malformed
```

then:

```text
Reject Output
→
Fallback
```

---

# 45. Model Quality Failure

A model may remain technically available but become operationally unreliable.

Example:

```text
Inference Success = 100%
```

but:

```text
Prediction Quality = Poor
```

This should trigger:

```text
Degradation Handling
```

when validated thresholds are crossed.

---

# 46. Model Rollback

If a newly deployed model causes unacceptable degradation:

```text
Candidate
  ↓
Failure Detected
  ↓
Rollback
  ↓
Known Good Model
```

---

# 47. Rollback Target

Rollback should point to:

```text
Known Validated Model Version
```

rather than an arbitrary older artifact.

# 49. Configuration Rollback

AI behaviour can fail because of configuration rather than model code.

Rollback may therefore include:

```text

```

---

# 50. Feature Rollback

If a feature release causes model failures:

```text
Feature Version
```

may need to be rolled back or disabled.

---

# 51. Schema Failure

If model and feature schemas become incompatible:

```text
Do Not Force Inference
```

Instead:

```text
Stop AI Path
Fallback
Correct Compatibility
```

---

# 52. Dependency Failure

If a dependency is unavailable:

```text
Determine Whether AI Can Operate Without It
```

If not:

```text
Fallback
```

---

# 53. Redis Failure

If Redis provides:

```text
Online AI Features
```

and becomes unavailable:

```text
Use Defined Alternate Source / Fallback
```

Do not assume stale Redis state is automatically safe.

---

# 54. PostgreSQL Failure

If PostgreSQL is required for an AI decision:

```text
Respect Database Failure Handling
```

Do not create a second inconsistent source of truth merely to keep AI running.

---

# 55. Kafka / Redpanda Failure

If AI learning or feature pipelines consume events:

```text
Event Delay
```

should not automatically be interpreted as:

```text
No Demand
```

or:

```text
No Supply
```

Missing events must be handled explicitly.

---

# 56. Event Delay

For delayed events:

```text
Record Event Age
```

and determine whether the dependent feature is still valid.

---

# 57. Event Loss

If required events are lost:

```text
Mark Derived Data as Potentially Incomplete
```

rather than silently treating it as normal.

---

# 58. Partial System Failure

RideForge should support degraded operation when:

```text
One AI Component
```

fails while:

```text
Other Core Services
```

remain healthy.

---

# 59. Graceful Degradation

Examples:

```text
AI ETA unavailable
→ Routing ETA

AI Ranking unavailable
→ Deterministic Ranking

Smart Dispatch unavailable
→ Configured Deterministic Dispatch

Forecast unavailable
→ Historical Baseline
```

---

# 60. Reduced Functionality

If no reliable fallback exists, provide the safest reduced behaviour.

Examples:

```text
Disable Advanced Ranking
Limit Candidate Set
Disable Non-Critical Prediction
```

---

# 61. Last Known Value

A last known prediction may be used only when:

```text
Freshness Is Acceptable
+
Operational Context Has Not Materially Changed
```

Do not reuse stale predictions blindly.

---

# 62. Cached Prediction

Cached predictions require:

```text
TTL
Context Compatibility
Invalidation Strategy
```

---

# 63. Fallback Cache

A fallback cache should never become an accidental permanent source of stale decisions.

---

# 64. Deterministic Fallback

Deterministic fallback is preferred when it is:

```text
Simple
Reliable
Fast
Understandable
```

---

# 65. Fallback Correctness

A fallback should be tested as a production path.

Do not treat fallback code as:

```text
Code That Will Never Run
```

---

# 66. Fallback Testing

Test:

```text
Model Timeout
Model Crash
Feature Failure
Dependency Failure
Invalid Output
Stale Data
```

and verify the fallback executes correctly.

---

# 67. Fallback Observability

Record:

```text
Fallback Activated
Fallback Reason
Fallback Type
Fallback Duration
```

where appropriate.

---

# 68. Fallback Rate

Monitor:

```text
Fallbacks / Total AI Requests
```

A sudden increase should be investigated.

---

# 69. Fallback Duration

Track how long the system remains degraded.

```text
Failure Start
→
Fallback Start
→
Recovery
```

---

# 70. Recovery

Recovery should be controlled.

Conceptually:

```text
Failure
 ↓
Fallback
 ↓
Health Check
 ↓
Recovery Candidate
 ↓
Canary
 ↓
Resume
```

---

# 71. Recovery Must Be Validated

Do not immediately restore full traffic after a dependency or model incident.

Use:

```text
Health Check
+
Smoke Test
+
Limited Traffic
```

where appropriate.

---

# 72. Half-Open Recovery

Circuit breakers may test a small number of requests before fully reopening the dependency.

---

# 73. Recovery Storm

When a dependency returns, avoid sending all accumulated traffic immediately.

Use controlled recovery.

---

# 74. Backlog Handling

For asynchronous AI workloads, define what happens to backlog after recovery:

```text
Replay
Skip
Recompute
Expire
```

based on the data's business value and freshness.

---

# 75. Expired Work

Time-sensitive AI tasks may become useless after a certain age.

Do not process obsolete work merely because it is queued.

---

# 76. Idempotent Recovery

Recovery processing should be safe against:

```text
Duplicate Events
Retry
Replay
```

where applicable.

---

# 77. AI Disable Switch

Production AI components should support controlled disablement where practical.

```text
AI Enabled
    ↓
AI Disabled
    ↓
Fallback
```

---

# 78. Disable Scope

The system should support disabling:

```text
Entire AI Capability
Specific Model
Specific Region
Specific Experiment
Specific Traffic Percentage
```

where practical.

---

# 79. Regional Failure

A model may fail only in one region.

Prefer:

```text
Regional Degradation
```

over:

```text
Global AI Shutdown
```

when safe.

---

# 80. Region-Level Fallback

Example:

```text
Region A → AI Active
Region B → Deterministic Fallback
```

This supports controlled incident containment.

---

# 81. Multi-Model Failure

If both primary and secondary models fail:

```text
Deterministic Fallback
```

should be used where possible.

---

# 82. No Safe Fallback

If no safe AI fallback exists:

```text
Do Not Invent One
```

Instead:

```text
Disable the AI-Dependent Capability
```

or use the safest reduced operation available.

---

# 83. Safety-First Degradation

When uncertain:

```text
Choose the Behaviour with the Lower Safety Risk
```

while preserving core service continuity where possible.

---

# 84. Legal Failure Handling

If legal or region validation cannot be performed reliably:

```text
Do Not Allow AI to Guess
```

The system must use the authoritative deterministic validation path or reject the operation when required.

---

# 85. Domain State Failure

If the ride state cannot be reliably validated:

```text
Do Not Execute AI-Driven State Changes
```

The domain remains authoritative.

---

# 86. Concurrency Failure

If the AI decision is based on stale state:

```text
Revalidate
```

before executing the action.

---

# 87. Duplicate AI Action

Protect against:

```text
Duplicate Dispatch
Duplicate Assignment
Duplicate Event
```

using:

```text
Idempotency
Domain State Validation
```

---

# 88. AI Failure and Event Processing

AI consumers should handle:

```text

Out-of-Order Event
```

---

# 89. Poison Message

A message that repeatedly causes processing failure should be isolated rather than retried indefinitely.

---

# 90. Dead Letter Handling

Record enough metadata for investigation without exposing unnecessary sensitive payloads.

```text

    ↓

    ↓

    ↓
```

# 108. Dependency Isolation

AI services should not hold critical resources while waiting indefinitely for external dependencies.

---

# 109. Fallback Independence

A fallback should preferably use a dependency path that is independent of the failed primary path.

Example:

```text
AI Model Failure
→ Routing ETA
```

is stronger than:

```text
AI Model Failure
→ Another Service Using Same Failed Model Infrastructure
```

---

# 110. Failure and Cost

Fallbacks may increase cost.

Example:

```text
Primary AI
→ External Routing API
```

may be more expensive than the normal model.

Cost should be monitored but should not prevent safety-critical fallback.

---

# 111. Failure and Performance

Fallback latency should remain within the parent operation's budget where possible.

# 129. AI Agent Implementation Rules

When implementing AI failure and fallback handling, an AI coding agent must:

1. Define failure modes before implementing the AI path.
2. Give every critical online AI dependency a bounded timeout.
3. Use bounded retries only for appropriate transient failures.
4. Prevent retry storms.
5. Validate model outputs before use.
6. Treat stale critical features explicitly.
7. Preserve deterministic fallbacks where required.
8. Keep hard legal and safety constraints active during fallback.
9. Revalidate mutable domain state before critical actions.
10. Prevent duplicate AI-triggered actions.
11. Make fallback activation observable.
12. Keep rollback targets explicit and validated.
13. Support controlled AI disablement where practical.
14. Avoid making fallback depend on the same failed component.
15. Test fallback paths as real production paths.
16. Preserve failure and recovery metadata.
17. Update the relevant AI documentation.

---

# 130. AI Agent Prohibited Patterns

AI agents must not:

- allow AI failure to silently block unrelated core operations,
- retry indefinitely,
- use arbitrary stale predictions,
- invent missing feature values,
- accept invalid model outputs,
- bypass legal or safety validation during fallback,
- use an unvalidated model as a rollback target,
- create a fallback that depends on the same failed component,
- hide fallback activation from observability,
- automatically restore full traffic without health validation,
- treat a technically available model as healthy when quality has degraded,
- create a new fallback without defining its safety properties,
- bypass domain state validation because AI is unavailable,
- expose sensitive data during failure logging,
- use failure handling as a reason to create a second inconsistent source of truth.

# 24. Dispatch Strategy Preservation and Fallback Clarifications

AI failure and fallback behavior must preserve the dispatch strategy resolved for the ride unless an explicit business/configuration rule defines a different strategy transition.

## 24.1 Two Primary Dispatch Strategies

RideForge has two primary dispatch strategies:

```text
Smart Stand Dispatch
Smart Dispatch
```

AI-assisted dispatch is an optimization capability applied to these strategies. It is not a third primary dispatch strategy.

Therefore, AI failure must not implicitly perform:

```text
Smart Stand Dispatch
        ↓
AI failure
        ↓
Smart Dispatch
```

unless such a transition is explicitly configured as a business fallback.

---

## 24.2 Smart Stand Dispatch Fallback

Smart Stand Dispatch is **stand-preferred, not stand-exclusive**.

When a rider is inside a configured stand radius:

```text
Preferred Stand
    ↓
Eligible Stand Drivers
    ↓
Stand Queue / Ordering
```

If the preferred stand cannot provide a suitable driver, the dispatch process may expand to broader eligible candidates.

Broader candidates may include:

```text
Drivers outside the preferred stand
Drivers at nearby stands
Drivers from nearby locations
```

This expansion is a candidate-discovery/fallback behavior. It does not automatically change the effective strategy to Smart Dispatch.

The effective strategy remains:

```text
Smart Stand Dispatch
```

unless an explicit configuration says otherwise.

---

## 24.3 Smart Dispatch Fallback

Smart Dispatch is stand-agnostic.

If an AI ranking or optimization capability fails, the system should fall back to a deterministic Smart Dispatch ranking/selection path using the approved non-AI dispatch factors.

For example:

```text
AI Ranking
    ↓
Unavailable
    ↓
Deterministic Smart Dispatch Ranking
```

Stand membership must not suddenly become a preference merely because AI is unavailable.

---

## 24.4 Cross-Location Fallback

If local supply is insufficient, candidate discovery may expand to nearby locations.

Example:

```text
Location A
    ↓
No suitable local candidate
    ↓
Nearby Location B
    ↓
Evaluate eligible candidates
```

Location B may use a different dispatch strategy from Location A.

That difference must not automatically make B's drivers ineligible.

The candidate's source context should remain available:

```text
Candidate Location
Candidate Location Strategy
Stand Membership
Relevant Stand
Queue Position
Discovery Source
Expansion Level
```

The applicable strategy context is used for prioritization, while hard eligibility and legal constraints remain authoritative.

---

## 24.5 AI Failure Must Not Remove Hard Constraints

When AI is unavailable, the deterministic fallback must continue to enforce:

```text
Driver Eligibility
Driver Availability
Legal / Regional Constraints
Vehicle / Service Compatibility
Safety Constraints
Location Freshness
Ride Constraints
Other Hard Business Rules
```

AI failure must never be used as a reason to bypass these constraints.

---

## 24.6 Hierarchical Configuration Remains Authoritative

Fallback processing must not bypass the resolved configuration hierarchy.

The effective strategy is resolved using:

```text
Most Specific Applicable Configuration
        ↓
Explicit Strategy?
   ├── YES → Use it
   └── NO → Parent Configuration
        ↓
Continue upward
        ↓
System Default
```

Once resolved, the fallback path must preserve that strategy unless an explicit business rule defines a strategy transition.

---

## 24.7 Fallback Is Not Strategy Switching

The following concepts must remain separate:

```text
Candidate Expansion
AI Failure
Retry
Degradation
Strategy Switching
```

For example:

```text
Smart Stand Dispatch
    ↓
Preferred Stand unavailable
    ↓
Broader candidate discovery
    ↓
Still Smart Stand Dispatch
```

This is candidate expansion, not a strategy switch.

Likewise:

```text
Smart Stand Dispatch
    ↓
AI unavailable
    ↓
Deterministic stand-aware processing
```

This is AI degradation, not a switch to Smart Dispatch.

---

## 24.8 Stand Queue Semantics During AI Failure

If Smart Stand Dispatch requires first-eligible-in-queue behavior, AI failure must not allow a generic AI/ranking score to replace that business rule.

The deterministic fallback must preserve the configured stand ordering semantics.

```text
Stand Queue
    ↓
Eligibility
    ↓
First Eligible Driver
```

where that is the configured stand rule.

---

## 24.9 Fallback Decision Order

A strategy-preserving fallback should conceptually follow:

```text
1. Preserve Effective Dispatch Strategy
2. Enforce Hard Eligibility / Legal / Safety Constraints
3. Preserve Strategy-Specific Rules
4. Expand Candidate Discovery if configured
5. Use Deterministic Ranking / Selection when AI is unavailable
6. Apply Retry / Degradation Policy
7. Only switch strategy if explicitly configured
```

This ordering prevents accidental strategy changes during failure handling.

---

## 24.10 AI-Agent Implementation Guardrails

Implementations must not:

```text
Treat AI failure as permission to switch Smart Stand Dispatch to Smart Dispatch.

Treat lack of a suitable stand driver as permission to ignore Smart Stand Dispatch rules entirely.

Reject non-stand candidates solely because the rider is inside a stand radius.

Reject nearby-location candidates solely because their source location uses another strategy.

Bypass hierarchical configuration when executing fallback logic.

Allow AI ranking to override hard eligibility, legal, safety, or operational constraints.

Replace a configured stand queue rule with an arbitrary AI score.

Conflate candidate expansion with strategy switching.
```

The fallback implementation must preserve the effective dispatch strategy and only broaden or degrade the processing path according to explicitly defined business rules.
