# 1. Purpose

This document defines the architecture and development principles for predicting:

```text
Ride Demand
Driver Supply
Demand-Supply Gaps
```

These predictions provide operational intelligence that can support:

```text
Smart Dispatch
Driver Positioning
Supply Planning
Operations
Capacity Planning
```

The prediction layer does not directly own:

```text
Driver State
Ride State
Reservation
Dispatch Authorization
```

Those remain core platform responsibilities.

---

# 2. Core Objective

The objective is:

> **Estimate future ride demand and available driver supply for relevant operating areas and time windows so that RideForge can make better operational decisions.**

The system should optimize for:

```text
Useful Forecasts
+
Fresh Data
+
Low Operational Complexity
+
Reliable Fallbacks
```

rather than model complexity alone.

---

# 3. Demand Definition

Demand represents expected ride requests within a defined:

```text
Location
+
Time Window
```

A demand forecast must therefore explicitly define:

```text
What is being counted?
Where is it counted?
For which time period?
```

---

# 4. Supply Definition

Supply represents expected driver capacity within a defined:

```text
Location
+
Time Window
```

Supply should be based on a clearly defined operational meaning.

For example:

```text
Available Drivers
```

may differ from:

```text
Drivers Currently Online
```

and from:

```text
Drivers Expected to Become Available
```

The chosen definition must be explicit.

---

# 5. Demand-Supply Gap

A basic operational gap can be represented as:

```text
Expected Demand
-
Expected Supply
=
Expected Gap
```

Conceptually:

```text
Positive Gap
→ Potential Supply Shortage

Near-Zero Gap
→ Potential Balance

Negative Gap
→ Potential Supply Surplus
```

The exact interpretation depends on the operating model.

---

Every forecast must define its horizon.

Examples:

```text
Next 15 Minutes
Next 30 Minutes
Next Hour
Next Several Hours
Next Day
```

The appropriate horizon depends on the operational decision.

Do not build one generic forecast and assume it is equally useful for every time horizon.

The chosen resolution should match the operational decision.

# 9. Demand Forecasting

The demand forecasting component estimates future ride requests.

Conceptually:

```text
Historical Requests
        +
Current Request Pattern
        +
Time
        +
Location
        ↓
Demand Model
        ↓
Expected Requests
```

---

# 10. Demand Inputs

Potential demand features include:

```text
Historical Ride Requests
Recent Request Volume
Location
Time
Day of Week
Weekend / Weekday
Seasonality
Recent Demand Trend
Operational Context
```

---

# 11. Recent Demand

Recent request volume can provide information about short-term changes.

Conceptually:

```text
Historical Pattern
+
Recent Demand
```

may be more informative than historical averages alone.

Recent signals must respect the forecast creation time.

---

# 12. Temporal Features

Potential temporal features include:

```text
Hour of Day
Day of Week
Weekend
Month
Season
Holiday / Special Period
```

The system should only include external calendar or event signals when they are available and properly governed.

---

# 13. Spatial Features

Demand can vary significantly by location.

Potential spatial signals include:

```text
Operating Area
Grid Cell
Neighbouring Areas
Historical Area Demand
```

The spatial representation should align with the platform's actual operating model.

---

# 14. Demand Aggregation

Historical demand should be aggregated consistently.

Conceptually:

```text
Ride Requests
      ↓
Spatial Bucket
      +
Time Bucket
      ↓
Demand Count
```

The aggregation rules must remain consistent between:

```text
Training
Evaluation
Inference
```

---

# 15. Demand Labels

For supervised forecasting, the target may be:

```text
Number of Ride Requests
```

within:

```text
Area
+
Future Time Window
```

The target definition must be fixed before model evaluation.

---

# 16. Demand Data Quality

Demand data should be checked for:

```text
Missing Timestamps
Invalid Locations
Duplicate Events
Incorrect Ride States
Out-of-Order Events
Cancelled / Invalid Records
```

The system should clearly define which ride states count toward demand.

---

# 17. Demand Event Semantics

The demand pipeline must define which event represents a demand request.

For example:

```text
Ride Requested
```

may represent demand more accurately than:

```text
Ride Completed
```

because completed rides represent fulfilled demand rather than all requested demand.

The actual event must follow the platform's domain definition.

---

# 18. Demand Leakage

Forecasting must prevent future information from entering features.

For example:

```text
Forecast Time:
10:00

Feature Data:
Available only before 10:00
```

must not contain:

```text
10:05 Request Count
```

---

# 19. Demand Baseline

Every demand model should have a baseline.

Possible baselines include:

```text
Historical Average
Same Time Previous Day
Same Time Previous Week
Rolling Average
Seasonal Baseline
```

The selected baseline should be measurable and reproducible.

---

# 20. Demand Model

The architecture does not require a specific forecasting algorithm.

Potential approaches include:

```text
Statistical Forecasting
Tree-Based Models
Time-Series Models
Neural Forecasting
Hybrid Models
```

Start with the simplest model that provides measurable improvement.

# 23. Supply Forecasting

Supply forecasting estimates future driver capacity.

Conceptually:

```text
Current Driver State
        +
Historical Availability
        +
Time
        +
Location
        ↓
Supply Model
        ↓
Expected Supply
```

---

# 24. Supply Inputs

Potential supply features include:

```text
Current Available Drivers
Online Drivers
Historical Availability
Location
Time
Day
Recent Driver Activity
Expected Driver State Changes
```

Only features that can be reliably produced should be used.

---

# 25. Current Supply

Current supply should come from the authoritative driver-state system.

AI must not become the owner of:

```text
Driver Availability
```

It only predicts future availability.

---

# 26. Driver State vs Predicted Supply

The distinction is critical:

```text
Core System:
Driver is currently available.

AI System:
Driver supply is expected to be available later.
```

Prediction must never overwrite current authoritative state.

---

# 27. Supply Label

The supply target must be explicitly defined.

Possible targets include:

```text
Available Drivers
Online Drivers
Drivers Completing Trips
Drivers Expected to Become Available
```

Do not mix these definitions without an explicit model objective.

---

# 28. Supply Data Quality

Check:

```text
Driver State Events
Location Timestamps
Duplicate Events
Invalid State Transitions
Missing Transitions
Impossible Durations
```

Incorrect driver-state history can produce misleading supply forecasts.

---

# 29. Supply Baseline

Possible baselines:

```text
Current Supply
Historical Same-Time Supply
Rolling Average
Historical Availability Rate
```

The baseline should be selected according to the forecast horizon.

---

# 30. Supply Forecast Output

A conceptual result:

```text
Area
Forecast Window
Predicted Supply
Model Version
Prediction Timestamp
Quality Signal
```

---

# 31. Demand-Supply Gap

Once forecasts exist:

```text
Demand Forecast
        +
Supply Forecast
        ↓
Gap Calculation
```

Conceptually:

```text
Gap = Predicted Demand - Predicted Supply
```

The gap is a derived operational signal.

---

# 32. Gap Interpretation

The gap can support:

```text
Shortage Detection
Surplus Detection
Operational Alerts
Driver Positioning
Dispatch Context
```

It should not automatically trigger operational actions unless an approved policy exists.

---

# 33. Demand-Supply Ratio

Another useful derived signal may be:

```text
Demand / Supply
```

However, the system must handle:

```text
Supply = 0
```

explicitly.

Do not allow division-by-zero or meaningless ratios.

---

# 34. Supply-Zero Condition

When:

```text
Predicted Supply = 0
```

the system should use an explicit representation such as:

```text
No Predicted Supply
```

rather than producing an invalid ratio.

---

# 35. Demand-Supply Classification

The gap can optionally be converted into operational categories:

```text
Surplus
Balanced
Shortage
Severe Shortage
```

Thresholds must be policy-defined and validated.

---

# 36. Threshold Management

Thresholds should not be hidden inside model code.

Where appropriate, define them as:

```text
Operational Policy
```

with:

```text
Version
Owner
Configuration
```

---

# 37. Driver Positioning

Demand and supply forecasts may support driver positioning recommendations.

Conceptually:

```text
Predicted Demand
-
Predicted Supply
        ↓
Potential Shortage Area
        ↓
Positioning Recommendation
```

The recommendation does not automatically move a driver.

---

# 38. Driver Positioning Output

A recommendation could contain:

```text
Area
Time Window
Expected Demand
Expected Supply
Expected Gap
Recommendation
```

The product determines how to present or act on it.

---

# 39. Smart Dispatch Integration

Demand and supply predictions can provide contextual signals to Smart Dispatch.

Conceptually:

```text
Current Ride
+
Current Candidates
+
Demand Forecast
+
Supply Forecast
        ↓
Smart Ranking
```

The ranking policy determines whether those signals should influence candidate selection.

---

# 40. Immediate vs Future Optimization

Smart Dispatch may have two competing objectives:

```text
Immediate:
Serve the current ride well.

Future:
Preserve healthy fleet distribution.
```

Demand and supply prediction can support the second objective.

Any trade-off must be explicit.

---

# 41. Demand-Aware Ranking

A future ranking policy may consider:

```text
Pickup ETA
+
Expected Future Demand
+
Expected Future Supply
```

This should be introduced only after the forecasts demonstrate adequate quality.

---

# 42. Supply-Aware Ranking

A driver may be valuable in a particular area because supply is expected to be low there.

A ranking system can potentially incorporate this context.

The behaviour must remain:

```text
Policy-Controlled
Observable
Experimentable
Reversible
```

---

# 43. Demand-Supply Forecasting Is Decision Support

The preferred relationship is:

```text
Prediction
        ↓
Recommendation
        ↓
Policy
        ↓
Execution
```

not:

```text
Prediction
        ↓
Uncontrolled Action
```

---

# 44. Forecast Freshness

Forecasts have a validity window.

A forecast should include:

```text
Generated At
Forecast Start
Forecast End
```

Consumers should know whether the forecast is still relevant.

---

# 45. Forecast Refresh

Forecasts may be refreshed:

```text
On Schedule
```

or:

```text
When Significant New Data Arrives
```

The refresh frequency should match the forecast horizon.

---

# 46. Forecast Storage

Forecasts may be stored when they are needed for:

```text
Operational Consumption
Historical Evaluation
Auditing
Model Comparison
```

Avoid retaining forecasts indefinitely without a business or operational reason.

---

# 47. Forecast Versioning

Each production forecast should be traceable to:

```text
Model Version
Feature Version
Forecast Timestamp
Forecast Window
```

---

# 48. Forecast Comparison

A forecast should eventually be compared with actual outcomes.

Conceptually:

```text
Forecast
   ↓
Future Period
   ↓
Actual Demand / Supply
   ↓
Error
```

This creates the feedback loop.

---

# 49. Demand Evaluation Metrics

Potential metrics:

```text
MAE
RMSE
MAPE / Suitable Percentage Error
Weighted Error
Forecast Bias
```

The selected metrics must account for low-volume or zero-demand areas where percentage metrics can become misleading.

---

# 50. Supply Evaluation Metrics

Potential metrics:

```text
MAE
RMSE
Forecast Bias
Availability Classification Accuracy
```

The metric should match the supply target.

---

# 51. Gap Evaluation

The derived gap can also be evaluated:

```text
Predicted Gap
vs
Actual Gap
```

This may be more operationally useful than evaluating demand and supply independently.

---

# 52. Operational Metrics

Forecast quality should also be evaluated through:

```text
Reduced Supply Shortage
Reduced Unserved Demand
Improved Driver Utilization
Improved Pickup Time
Improved Dispatch Outcomes
```

Only use metrics that can actually be measured.

---

# 53. Geographic Evaluation

Forecast quality should be evaluated across:

```text
High-Demand Areas
Low-Demand Areas
Urban Areas
Low-Density Areas
Different Operating Regions
```

A model that performs well globally may perform poorly in a specific zone.

---

# 54. Temporal Evaluation

Evaluate across:

```text
Peak Hours
Off-Peak
Weekdays
Weekends
Seasonal Periods
Special Operational Periods
```

where relevant.

---

# 55. Cold Start — New Region

A new region may have insufficient historical data.

Possible fallback:

```text
Historical Baseline
```

or:

```text
Global / Shared Model
```

provided its assumptions are valid.

---

# 56. Cold Start — New Zone

A new operating area may have no local history.

Possible strategies:

```text
Neighbouring Area Signal
Broader Regional Signal
Global Baseline
Deterministic Baseline
```

The selected strategy must be validated.

---

# 57. Cold Start — New Driver

A new driver has little personal history.

Supply prediction should rely on:

```text
Fleet-Level Patterns
Area-Level Patterns
Current State
Temporal Features
```

rather than requiring a long individual history.

---

# 58. Sparse Demand

Low-demand areas can create:

```text
High Forecast Variance
Many Zero Values
Limited Training Data
```

The system should use methods appropriate for sparse demand.

---

# 59. Zero Demand

Zero-demand periods are valid observations.

Do not automatically treat:

```text
Demand = 0
```

as missing data.

The pipeline must distinguish:

```text
True Zero
```

from:

```text
Missing Observation
```

---

# 60. Zero Supply

Similarly:

```text
Supply = 0
```

can be a valid operational condition.

It must not be confused with:

```text
Missing Supply Data
```

---

# 61. Missing Data

Missing data should be explicitly represented.

Avoid silently converting:

```text
Missing
```

into:

```text
Zero
```

unless the feature semantics explicitly define that behaviour.

---

# 62. Event Ordering

Demand and supply forecasting rely on event history.

The pipeline should account for:

```text
Event Timestamp
Ingestion Timestamp
Processing Timestamp
```

Out-of-order events should be handled according to the event architecture.

---

# 63. Event-Driven Data Flow

A conceptual data flow:

```text
Ride Events
     ↓
Demand Aggregation
     ↓
Demand Features

Driver Events
     ↓
Supply Aggregation
     ↓
Supply Features
```

These can feed forecasting pipelines.

---

# 64. Feature Store / Feature Layer

The implementation may use a feature store or another feature-serving mechanism.

The architectural requirement is:

```text
Stable Feature Semantics
+
Fresh Data
+
Consistent Training / Serving
```

The specific technology is an implementation decision.

# 65. Online Forecast Serving

If forecasts are required in real time:

```text
Current State
      ↓
Feature Resolution
      ↓
Forecast Inference
      ↓
Forecast Result
```

The serving path must have a defined latency budget.

---

# 66. Batch Forecast Serving

For operational planning:

```text

Feature Generation
      ↓

      ↓

      ↓
```

---

# 67. Forecast Cache

Forecasts can be cached when:

```text
Forecast Window
```

is shared by many consumers.

Cache invalidation should follow forecast freshness.

---

# 68. Forecast API

A conceptual forecast request may specify:

```text
Area

Forecast Resolution
```

A response may contain:

```text
Forecast Window
Predicted Demand
Predicted Supply
Model Version

```

The exact API contract belongs to the API architecture and implementation.

---

# 69. Forecast Contract Validation

Validate:

```text
Area Exists
Forecast Window Is Valid
Prediction Is Numeric
Prediction Is Non-Negative
Timestamp Is Valid
Model Version Is Known
```

Invalid forecast results should not silently propagate.

---

# 70. Non-Negative Forecasts

Demand and supply counts generally cannot be negative.

Therefore:

```text
Predicted Demand < 0
→ Invalid / Corrective Post-Processing

Predicted Supply < 0
→ Invalid / Corrective Post-Processing
```

Any correction must be explicit and tested.

---

# 71. Forecast Granularity

Higher granularity is not automatically better.

For example:

```text
5-minute forecasts
```

may be unnecessary if the operational decision only changes:

```text
Every 30 minutes
```

Choose granularity based on actual use.

---

# 72. Forecast Cost

Consider:

```text
Inference Cost
Feature Retrieval Cost
Storage Cost
Training Cost
Refresh Frequency
```

Avoid forecasting at unnecessarily high frequency or resolution.

---

```text

        ↓
```

# 76. Training / Validation / Test

A time-aware split is generally preferred for forecasting.

Conceptually:

```text
Past
→ Training

Later Period
→ Validation

Newest Period
→ Test
```

This better reflects future prediction behaviour.

---

# 77. Backtesting

Forecasting models should be backtested against historical periods.

Conceptually:

```text
Historical Cutoff
       ↓
Generate Forecast
       ↓
Compare Against Known Future
       ↓
Measure Error
```

Backtesting should use only information that would have been available at each historical prediction point.

---

# 78. Forecast Drift

Monitor for changes in:

```text
Demand Distribution
Supply Distribution
Geographic Patterns
Temporal Patterns
```

Drift can indicate model degradation.

---

# 79. Forecast Bias

Track whether predictions systematically:

```text
Overestimate
```

or:

```text
Underestimate
```

actual demand or supply.

Persistent bias may be operationally more important than average error alone.

---

# 80. Demand Spike Detection

Forecasting systems should be able to identify when actual demand significantly exceeds expected demand.

Conceptually:

```text
Actual Demand
      >
Expected Demand
      ↓
Demand Spike
```

This can become an operational signal.

---

# 81. Supply Shock Detection

Similarly:

```text
Actual Supply
      <
Expected Supply
      ↓
Supply Shortage
```

may trigger operational attention.

---

# 82. Forecast vs Detection

Do not confuse:

```text
Forecast
```

with:

```text
Anomaly Detection
```

A forecast predicts future conditions.

Anomaly detection identifies unusual observed conditions.

They can complement each other.

---

# 83. Operational Alerting

Alerts may be generated when:

```text
Expected Demand High
+
Expected Supply Low
```

or:

```text
Forecast Error
```

becomes unusually high.

Alerts should be policy-controlled to avoid excessive noise.

---

# 84. Driver Positioning Recommendations

A positioning recommendation may rank areas by:

```text
Expected Opportunity
```

which may combine:

```text
Demand
Supply
Travel Time
Operational Constraints
```

The recommendation must remain explainable enough for operational use.

---

# 85. Driver Positioning Safety

The system must not:

```text
Automatically Relocate Drivers
```

unless the product explicitly supports such behaviour and the action is authorized.

Prediction should initially remain advisory.

---

# 86. Smart Dispatch Safety

Demand and supply forecasts must not bypass:

```text
Eligibility
Regional Rules
Reservation Integrity
Driver Availability
```

---

# 87. Supply Prediction and Driver State

The supply model can predict:

```text
Future Supply
```

but cannot directly change:

```text
Current Driver Availability
```

---

# 88. Demand Prediction and Ride Creation

The demand model can predict:

```text
Expected Requests
```

but cannot create:

```text
Ride Records
```

---

# 89. Forecast Failure

If a demand or supply forecast fails:

```text
Forecast Failure
        ↓
Historical / Deterministic Baseline
```

where an appropriate baseline exists.

The failure should be observable.

---

# 90. Forecast Timeout

Real-time forecasting must use bounded timeouts.

```text
Forecast Request
      ↓
Inference
      ├── Success
      └── Timeout
             ↓
          Fallback
```

---

# 91. Forecast Fallback Matrix

| Capability | Primary | Possible Fallback |
|---|---|---|
| Demand Forecast | Forecast Model | Historical Baseline |
| Supply Forecast | Supply Model | Current / Historical Baseline |
| Demand-Supply Gap | Forecasts | Baseline-Derived Gap |
| Positioning Signal | Forecast-Based | Rule-Based Signal |
| Dispatch Context | Predictive Signal | No Forecast Signal |

# 120. AI Agent Implementation Rules

When implementing demand or supply prediction, an AI coding agent must:

1. Define the forecast target.
2. Define the spatial resolution.
3. Define the temporal resolution.
4. Define the forecast horizon.
5. Identify the authoritative source data.
6. Define event semantics.
7. Establish a baseline.
8. Prevent temporal leakage.
9. Validate zero vs missing values.
10. Validate event ordering.
11. Define forecast output contracts.
12. Define freshness.
13. Implement fallback behaviour.
14. Add backtesting.
15. Measure geographic and temporal performance.
16. Add monitoring.
17. Preserve model/version traceability.
18. Avoid creating unnecessary infrastructure.
19. Keep predictions separate from authoritative operational state.
20. Update the relevant AI documentation.

---

# 121. AI Agent Prohibited Patterns

AI agents must not:

- treat predicted supply as authoritative driver availability,
- treat predicted demand as actual ride requests,
- silently convert missing data into zero,
- use future events as prediction features,
- skip a baseline,
- claim forecast accuracy without evaluation,
- create automatic driver movement without product authorization,
- let forecasts bypass dispatch eligibility,
- introduce advanced forecasting without measurable need,
- automatically promote newly trained models,
- remove deterministic fallbacks,
- expose unnecessary location data,
- create duplicate forecasting components,
- make predictions directly mutate transactional state.

# 125. Final Principle

> **Demand and supply prediction should provide forward-looking operational intelligence while leaving current platform state and transactional decisions authoritative and deterministic.**

The intended lifecycle is:

```text
Observe
   ↓
Aggregate
   ↓
Forecast
   ↓
Compare
   ↓
Recommend
   ↓
Execute Through Policy
   ↓
Measure
   ↓
Improve
```

The forecasting system should remain:

```text
Useful
+
Measurable
+
Fresh
+
Observable
+
Fallback-Safe
+
Operationally Simple
```

The immediate goal is not to predict everything.

The immediate goal is to predict the small number of operational signals that can materially improve RideForge's dispatch and supply decisions.
