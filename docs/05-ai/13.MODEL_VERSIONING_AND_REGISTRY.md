# 1. Purpose

This document defines how RideForge AI models are identified, versioned, stored, evaluated, promoted, deployed, rolled back, and retired.

The model lifecycle must provide:

```text
Identity
+
Traceability
+
Compatibility
+
Reproducibility
+
Controlled Promotion
+
Rollback
```

The objective is to ensure that production systems always know:

```text
Which Model
+
Which Features
+
Which Dataset
+
Which Code
+
Which Configuration
```

produced a given prediction.

---

# 2. Core Principle

> **A production model is an immutable, identifiable artifact with explicit compatibility and lifecycle state.**

A model should never be treated as:

```text
latest.bin
```

without a stable identity.

---

# 3. Registry Scope

The model registry is responsible for:

```text
Model Identity
Model Versions
Model Artifacts
Model Metadata
Training Lineage
Evaluation Results
Compatibility
Lifecycle State
Promotion
Deployment Reference
Rollback Reference
Retirement
```

It does not own:

```text
Training Data Generation
Model Inference Logic
Core Ride State
Dispatch Transaction State
```

Those remain responsibilities of their respective systems.

---

# 4. Why Model Versioning Matters

Without controlled model versioning, it becomes difficult to determine:

```text
What is running?
Why did behaviour change?
Which model produced this prediction?
Can the previous model be restored?
Which dataset trained the model?
Which feature definition was used?
```

Versioning solves these problems.

---

# 5. Model Identity

Every model should have a stable logical identity.

Conceptually:

```text
Model Name
+
Model Family
+
Model Version
```

Example:

```text
ETA Prediction
ETA Model
v1
```

The exact naming convention should remain consistent across the project.

---

# 6. Model Families

RideForge may maintain separate model families for:

```text
ETA
Demand Forecasting
Supply Forecasting
Matching
Ranking
Cancellation Prediction
Future AI Capabilities
```

Each family has its own:

```text
Objective
Features
Evaluation
Release Cadence
Fallback
```

---

# 7. Model Version

A model version identifies a specific model artifact and its associated configuration.

Conceptually:

```text
eta-model:v1
eta-model:v2
```

A version must not silently change meaning.

---

# 8. Immutable Versions

Once a model version is approved or deployed:

```text
Do Not Mutate Its Artifact
```

If the model changes:

```text
Create New Version
```

For example:

```text
v1 → Existing
v2 → Modified
```

---

# 9. Semantic Versioning

The project may use a simple model version scheme or semantic versioning.

The important requirement is:

```text
Version Meaning Must Be Consistent
```

Do not create a versioning scheme that is more complex than required.

---

# 10. Model Artifact

A model artifact may contain:

```text
Trained Parameters
Model Structure
Preprocessing
Required Runtime Metadata
```

The artifact format depends on the selected model framework.

---

# 11. Artifact Integrity

Every production artifact should have integrity protection.

Possible mechanisms:

```text
Checksum
Digest
Signature
Trusted Artifact Storage
```

A serving system must not silently load a modified artifact.

---

# 12. Artifact Storage

Artifacts should be stored in controlled storage rather than:

```text

Temporary Directory
Untracked Repository File
```

The storage system must support:

```text
Versioning
Access Control
Retention
Retrieval
```

# 19. Model Lifecycle

A model may move through:

```text
Created
   ↓
Candidate
   ↓
Validated
   ↓
Approved
   ↓
Shadow
   ↓
Canary
   ↓
Production
   ↓
Deprecated
   ↓
Retired
```

A model may also be:

```text
Rejected
```

during evaluation.

---

# 20. Candidate

A newly trained model starts as:

```text
Candidate
```

It must not receive production traffic automatically.

---

# 21. Validated

A model becomes:

```text
Validated
```

after passing required technical evaluation.

Validation may include:

```text
Data Quality
Metrics
Leakage Checks
Sanity Checks
Robustness
```

---

# 22. Approved

A validated model becomes:

```text
Approved
```

only after the required engineering and operational review.

Approval does not necessarily mean:

```text
Production
```

---

# 23. Shadow

A model may enter:

```text
Shadow
```

to observe real production inputs without controlling the production decision.

---

# 24. Canary

A model may enter:

```text
Canary
```

when a controlled portion of traffic is allowed to use it.

---

# 25. Production

A model is:

```text
Production
```

when it is the active model for its intended workload.

---

# 26. Deprecated

A model is:

```text
Deprecated
```

when it should no longer receive new production traffic but may still be retained for:

```text
Rollback
Historical Reproduction
Evaluation
Audit
```

---

# 27. Retired

A model becomes:

```text
Retired
```

when it is no longer required operationally and can be removed from active serving and normal deployment workflows.

---

# 28. Rejected

A model may be:

```text
Rejected
```

if it fails:

```text
Evaluation
Quality
Safety
Cost
Performance
Operational Requirements
```

Rejected models should not become production candidates without a new evaluation.

---

# 29. Promotion Rules

Promotion must be explicit:

```text
Candidate
→ Validated
→ Approved
→ Shadow
→ Canary
→ Production
```

Do not allow an unapproved artifact to become active simply because it exists in storage.

---

# 30. Promotion Criteria

A model should satisfy:

```text
Baseline Comparison
+
Evaluation Metrics
+
Segment Evaluation
+
Robustness
+
Latency
+
Cost
+
Fallback
```

before production promotion.

---

# 31. Model Registry States

A registry should make the current state visible.

For example:

```text
ETA Model
v1 → Deprecated
v2 → Production
v3 → Canary
v4 → Candidate
```

---

# 32. One Active Production Model

For a given model family, prefer one clearly identified production model unless the architecture intentionally supports:

```text
A/B Testing
Regional Models
Traffic Splitting
Specialized Models
```

If multiple models are active, their routing rules must be explicit.

---

# 33. Multi-Model Serving

Multiple model versions may coexist for:

```text
Shadow
Canary
A/B Testing
Regional Deployment
Rollback Readiness
```

The serving layer must know which model applies to each request.

---

# 34. Model Selection

Model selection may depend on:

```text
Model Family
Region
Environment
Experiment
Traffic Allocation
```

The selection rule must be deterministic and auditable.

---

# 35. Feature Compatibility

A model must declare its required feature version.

Example:

```text
Model V3
→ Features V2
```

Serving must reject or safely handle:

```text
Model V3
+
Incompatible Features V1
```

# 36. Dataset Compatibility

This supports:

```text
Reproducibility
```

# 37. Runtime Compatibility


# 38. Model Build Environment

```text

Dependency Lock
Build Configuration
```

---

# 44. Breaking Model Changes

A model change is breaking when it changes:

```text
Input Schema
Output Schema
Prediction Meaning
Units
Feature Requirements
```

Such changes require a new compatible version and controlled migration.

---

# 45. Non-Breaking Model Changes

An internal optimization may be non-breaking if:

```text
Input Contract Unchanged
Output Contract Unchanged
Prediction Semantics Unchanged
```

However, the artifact should still receive a distinct version if its predictions can differ materially.

---

# 46. Model Version and Feature Version

Do not assume:

```text
Model Version == Feature Version
```

They are independent lifecycles.

A model can use:

```text
Features V3
```

while another model uses:

```text
Features V2
```

---

# 47. Model Version and Dataset Version

Similarly:

```text
Model Version
```

and:

```text
Dataset Version
```

should remain separate identifiers.

# 50. Registry and Serving

The serving system should resolve:

```text

```

from a trusted configuration or registry reference.

# 51. Model Activation

# 53. Rollback

Rollback should select a previously approved version.

Conceptually:

```text
Production V4
      ↓
Problem Detected
      ↓
Production V3
```

---

# 54. Rollback Requirements

A rollback candidate should have:

```text
Valid Artifact
Compatible Features
Known Runtime
Known Configuration
Previously Approved State
```

---

# 55. Rollback Testing

Rollback should be tested before a production incident requires it.

At minimum verify:

```text
Model Loads
Feature Compatibility
Inference Works
Traffic Can Switch
Fallback Works
```

---

# 56. Model Retirement

Before retiring:

```text
Identify Consumers
Verify No Active Traffic
Verify Rollback Requirements
Archive Metadata
Remove Serving
```

---

# 57. Retention

Retain models according to:

```text
Rollback Requirements
Reproducibility
Evaluation
Audit
Storage Cost
Governance
```

Do not retain everything indefinitely without purpose.

---

# 58. Artifact Cleanup

When artifacts are eligible for cleanup:

```text
Verify No Dependency
Verify No Required Historical Reference
Verify Retention Policy
Then Delete
```

```text
Old Model
      ↓
New Model Ready
      ↓
Traffic Switch
```



# 100. AI Agent Implementation Rules

When implementing model versioning or registry functionality, an AI coding agent must:

1. Give every model artifact a stable identity.
2. Treat production model artifacts as immutable.
3. Create a new version for material model changes.
4. Record feature compatibility.
5. Record dataset and training lineage.
6. Record the code version used to build the model.
7. Preserve input and output schemas.
8. Implement explicit lifecycle states.
9. Prevent unapproved models from becoming active.
10. Keep rollback references available.
11. Validate artifact integrity.
12. Make activation auditable.
13. Protect registry access.
14. Avoid storing unnecessary sensitive data in registry metadata.
15. Keep registry failures from unnecessarily breaking already-loaded inference.
16. Prefer simple infrastructure until actual model-management scale requires more.
17. Update the relevant AI documentation.

---

# 101. AI Agent Prohibited Patterns

AI agents must not:

- overwrite a production model artifact in place,
- silently change model semantics under the same version,
- activate an unvalidated model,
- remove the previous known-good model before rollout safety is established,
- hardcode production model paths throughout application code,
- silently mix incompatible feature and model versions,
- claim a model is approved without evidence,
- delete production artifacts without retention checks,
- store unnecessary sensitive training data in registry metadata,
- make the registry a mandatory dependency for every inference request unless required,
- introduce a heavyweight model registry without demonstrated operational need.

# 107. Final Principle

> **Model versioning gives every RideForge AI decision a traceable identity, while the registry provides controlled movement from experiment to production.**

The desired model-management lifecycle is:

```text
Identify
   ↓
Version
   ↓
Record
   ↓
Evaluate
   ↓
Approve
   ↓
Deploy
   ↓
Observe
   ↓
Rollback / Improve
   ↓
Retire
```

The goal is not to build a large ML registry from day one.

The goal is to ensure that every production model is:

```text
Identifiable
+
Immutable
+
Compatible
+
Traceable
+
Deployable
+
Rollback-Ready
```

and that RideForge can always answer:

```text
Which model is running?
Which features does it use?
Which data trained it?
Which code built it?
Why was it approved?
How do we safely return to the previous model?
```
