# 1. Purpose

This document defines the Machine Learning data pipeline used by RideForge AI systems.

The pipeline converts operational platform data into reliable datasets and features for:

```text
ETA Prediction
Demand Forecasting
Supply Forecasting
Driver Matching
Candidate Ranking
Smart Dispatch
Future AI Capabilities
```

The objective is to establish a controlled path:

```text
Operational Events
        ↓
Ingestion
        ↓
Validation
        ↓
Normalization
        ↓
Historical Data
        ↓
Label Generation
        ↓
Feature Engineering
        ↓
Dataset Construction
        ↓
Training / Evaluation
```

---

# 2. Core Principle

> **AI quality depends primarily on the quality, correctness, timing, and semantics of the data used to train and evaluate the models.**

Therefore:

```text
Bad Events
    ↓
Bad Dataset
    ↓
Bad Model
```

The pipeline must prioritize:

```text
Correctness
+
Point-in-Time Integrity
+
Data Quality
+
Reproducibility
+
Traceability
+
Privacy
```

---

# 3. Pipeline Scope

The ML data pipeline owns:

```text
Data Ingestion
Event Selection
Data Validation
Data Normalization
Historical Storage
Label Generation
Feature Dataset Generation
Training Dataset Construction
Evaluation Dataset Construction
Data Quality Monitoring
Data Lineage
```

It does not own:

```text
Ride State
Driver State
Reservation
Payment
Production Assignment
```

Those remain authoritative domain responsibilities.

---

# 4. Data Sources

Potential ML data sources include:

```text
Ride Events
Driver Events
Location Events
Dispatch Events
Reservation Events
Trip Outcomes
Routing Data
Demand Data
Supply Data
Operational Configuration
```

Only approved sources should feed production ML pipelines.

---

# 5. Authoritative Source Principle

Each data element should have a known source of truth.

Examples:

```text
Ride State
→ Ride Domain

Driver State
→ Driver / Availability Domain

Reservation Result
→ Reservation / Dispatch Domain

Driver Location
→ Location System

ETA Outcome
→ Ride / Trip Events
```

The ML pipeline should consume authoritative records rather than independently reconstructing transactional truth when avoidable.

---

# 6. Event-Driven Data Flow

RideForge already uses an event-driven architecture.

The ML pipeline can consume relevant domain events without coupling the AI layer directly to transactional workflows.

Conceptually:

```text
Domain Services
      ↓
Events
      ↓
Event Infrastructure
      ↓
ML Data Ingestion
      ↓
Historical / Analytical Data
```

---

# 7. Event Selection

Not every event belongs in the ML pipeline.

Select events based on:

```text
Model Requirement
Training Requirement
Evaluation Requirement
Operational Analytics Requirement
```

Avoid collecting data simply because it is available.


# 11. Event Ordering

Events may arrive:

```text
Late
Out of Order
```

# 12. Duplicate Events

```text
Retries
Consumer Reprocessing
Network Issues
Producer Behaviour
```

The pipeline should support idempotent processing where practical.

---

# 13. Idempotency

A pipeline stage should avoid producing duplicate analytical records when the same event is processed more than once.

Possible mechanisms:

```text
Event ID
Unique Constraint
Processed Event Registry
Deterministic Upsert
```

The implementation should follow the project's infrastructure patterns.


# 21. Completeness

Measure:

```text
Required Field Present Rate
Event Coverage
Feature Availability
Label Availability
```

A missing target can make an otherwise valid training example unusable.

---

# 22. Correctness

Correctness asks:

```text
Does the value represent the real business event?
```

Examples:

```text
Actual Arrival Time
Actual Trip Duration
Actual Driver Availability
```

must reflect authoritative operational events.

---

# 23. Consistency

Check consistency across sources.

For example:

```text
Ride Service
vs
Event Stream
vs
Analytical Record
```

should not contradict each other without a known reason.

---

# 24. Timeliness

Track how long data takes to become available:

```text
Event Time
→ Ingestion Time
```

Large delays may affect:

```text
Online Features
Forecasting
Monitoring
Training Data
```

---

# 25. Uniqueness

Ensure records that should be unique remain unique.

Examples:

```text
Event ID
Prediction ID
Trip Outcome
Training Example ID
```

---

# 26. Validity

Validate values against their domain.

Examples:

```text
Coordinate Range
Non-Negative Duration
Valid Ride State
Valid Vehicle Type
Valid Timestamp
```

---

# 27. Quarantine

Invalid data should not silently enter production training datasets.

A quarantine path may be:

```text
Invalid Record
      ↓
Quarantine
      ↓
Inspection
      ↓
Correction / Rejection
```

---

# 28. Dead-Letter Data

Where the event architecture supports a dead-letter mechanism, ML ingestion can use a corresponding invalid-data path.

Conceptually:

```text
Event
 ↓
Validation
 ├── Valid → Pipeline
 └── Invalid → DLQ / Quarantine
```

---

# 33. Historical Data Model

The analytical data model should preserve enough information to reconstruct model inputs and outcomes.

Conceptually:

```text
Event History
      ↓
Historical State / Fact Records
      ↓
Feature / Label Generation
```

---

# 34. State Reconstruction

Some ML use cases require reconstructing state at a historical point.

Example:

```text
Driver Availability at 10:00
```

must represent what was actually known at:

```text
10:00
```

not the current state.

---

# 35. Point-in-Time State

Historical state reconstruction is essential for:

```text
Matching
ETA
Demand Forecasting
Supply Forecasting
```

---

# 36. Label Generation

Labels represent known outcomes.

Examples:

```text
Pickup ETA:
Actual Driver Arrival Time

Trip Duration:
Actual Trip Completion - Pickup

Demand:
Requests in Future Window

Supply:
Available Drivers in Future Window

Ranking:
Observed Assignment / Acceptance Outcome
```

The exact target must match the model objective.

---

# 37. Label Timestamp

A label must be tied to the prediction point.

Conceptually:

```text
Prediction Point
        ↓
Future Outcome
        ↓
Label
```

This makes the relationship explicit.

---

# 38. Label Leakage

A label must never become an input feature for the same prediction.

Example:

```text
Actual Arrival Time
```

is a target for pickup ETA.

It must not also appear as an input feature.

---

# 39. Label Quality

Validate labels for:

```text
Missing
Invalid
Negative
Impossible
Duplicated
Incorrectly Ordered
```

---

# 40. Label Availability

Not every historical event immediately produces a label.

For example:

```text
Ride Requested
```

may only become a complete training example after:

```text
Ride Completed
```

or another required outcome occurs.

---

# 41. Delayed Labels

The pipeline must support delayed labels.

Conceptually:

```text

Wait for Outcome
        ↓
Generate Label
        ↓
Training Example
```

---

# 42. Censored Data

Some observations may not have a complete outcome.

Examples:

```text

```

The pipeline must define whether such records are:

```text

Separate Label

```

according to the model objective.




```text

Later Period

Newest Period
→ Test
```


# 52. Leakage During Splitting




```text

Stratified Sampling
```


# 56. Imbalance Handling

Potential approaches:

```text

Sampling
```

# 145. AI Agent Implementation Rules

When implementing ML data pipelines, an AI coding agent must:

1. Identify the exact model use case.
2. Identify authoritative data sources.
3. Inspect existing event contracts before creating new data paths.
4. Preserve event semantics.
5. Distinguish event time from processing time.
6. Handle duplicate and out-of-order events.
7. Validate data before downstream use.
8. Define invalid-data handling.
9. Define labels explicitly.
10. Prevent temporal leakage.
11. Preserve point-in-time correctness.
12. Version dataset-affecting transformations.
13. Make processing idempotent where appropriate.
14. Add data-quality tests.
15. Add pipeline failure and recovery tests.
16. Make important pipeline runs traceable.
17. Avoid heavy analytical workloads on latency-sensitive transactional systems.
18. Preserve privacy and data minimization.
19. Avoid creating a separate event or storage system without a demonstrated need.
20. Update the relevant AI documentation.

---

# 146. AI Agent Prohibited Patterns

AI agents must not:

- train models directly from unvalidated production tables,
- use future events as historical features,
- silently convert invalid data into valid-looking data,
- silently drop large portions of a dataset,
- mix incompatible units,
- ignore event ordering,
- assume ingestion time is event time,
- mutate transactional state during ML replay,
- trigger ride or payment side effects during data processing,
- overwrite historical datasets without versioning,
- create duplicate data pipelines for existing event streams,
- bypass privacy requirements,
- expose raw sensitive data unnecessarily,
- treat a partially generated dataset as complete,
- claim reproducibility without recording the required versions.
