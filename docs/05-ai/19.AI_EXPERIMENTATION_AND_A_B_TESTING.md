# 1. Purpose

This document defines how RideForge experiments with AI systems safely and measurably.

The experimentation system should answer:

```text
What are we changing?
Why are we changing it?
Who receives the change?
What is the control?
What metrics determine success?
What safety conditions must hold?
When should the experiment stop?
```

The objective is:

```text
Controlled Learning
+
Statistically Meaningful Evaluation
+
Operational Safety
+
Traceability
```

---

# 2. Core Principle

> **An experiment changes a controlled variable; it does not remove system constraints.**

Experiments must remain inside:

```text
Legal Constraints
Safety Constraints
Hard Business Rules
Operational Constraints
Privacy Requirements
```

# 7. Offline Experiment

Offline experiments compare candidates using historical data.

```text
Historical Dataset
       ↓
Model A
       ↓
Model B
       ↓
Compare
```

Advantages:

```text
Low Production Risk
Low Operational Cost
Fast Iteration
```

Limitations:

```text
Historical Data Bias
No Direct Live Behaviour
Potential Distribution Difference
```

---

# 8. Replay Evaluation

Replay testing reconstructs historical decisions using recorded context.

Conceptually:

```text
Historical State
      ↓
Candidate Model
      ↓
Simulated Decision
      ↓
Compare with Historical Outcome
```

Replay must respect point-in-time data availability.

---

# 9. Shadow Experiment

A candidate receives live production inputs but does not control production decisions.

```text
Production Request
       │
       ├────→ Champion → Production
       │
       └────→ Candidate → Observation Only
```

This is useful for:

```text
Latency
Prediction Distribution
Candidate Stability
Offline-to-Online Validation
```

---

# 10. A/B Experiment

An A/B test sends controlled traffic to:

```text
Control
```

and:

```text
Treatment
```

and compares outcomes.

```text
                    Traffic
                       │
                ┌──────┴──────┐
                ▼             ▼
             Control       Treatment
                │             │
                ▼             ▼
             Outcome        Outcome
                │             │
                └──────┬──────┘
                       ▼
                    Compare
```

---

# 11. Control Group

The control should normally represent:

```text
Current Production Behaviour
```

unless another baseline is explicitly justified.

---

# 12. Treatment Group

The treatment receives:

```text
Candidate Model
```

or:

```text
Candidate Behaviour
```

being evaluated.

---

# 13. Control Stability

During an experiment, the control should remain stable.

Avoid changing:

```text
Control Model
Control Configuration
Control Traffic Definition
```

mid-experiment without explicitly handling the change.

---

# 14. Experiment Unit

The experiment must define what receives assignment.

Possible units:

```text
Ride
Driver
Rider
Region
Request
Time Window
```

The unit should match the behaviour being evaluated.

---

# 15. Assignment Consistency

If the experiment is assigned at:

```text
Driver
```

the same driver should generally remain in the same treatment group for the defined experiment period when appropriate.

This reduces contamination.

---

# 16. Avoid Random Per-Request Assignment When Inappropriate

Randomly changing models for the same entity across requests can create:

```text
Behavioural Contamination
Learning Effects
Inconsistent Experience
```

Use stable assignment where the experiment requires it.

---

# 17. Experiment Key

An experiment assignment should be traceable to:

```text
Experiment ID
Variant
Assignment Unit
Assignment Timestamp
```

---

# 18. Deterministic Assignment

Where appropriate, use deterministic assignment such as:

```text
Hash(Experiment ID + Entity ID)
```

to produce stable allocation.

The exact implementation is an engineering decision.

---

# 19. Traffic Allocation

Traffic may be split:

```text
90% Control
10% Treatment
```

or:

```text
50% Control
50% Treatment
```

depending on risk and statistical requirements.

---

# 20. Progressive Traffic

For a risky candidate:

```text
1%
 ↓
5%
 ↓
10%
 ↓
25%
 ↓
50%
```

may be safer than immediate full allocation.

---

# 21. Traffic Allocation Must Be Observable

Monitor:

```text
Expected Allocation
vs
Actual Allocation
```

A major mismatch indicates an experiment infrastructure issue.


Examples:

```text
ETA MAE
Assignment Success
```

```text

```

# 28. Guardrail Metrics

Guardrail metrics are metrics that must not degrade beyond acceptable limits.

Examples:

```text
Constraint Violations
P95 Latency
Fallback Rate
Cancellation Rate
Safety Events
```

---

# 29. Primary vs Guardrail Metrics

An experiment should not be declared successful if:

```text
Primary Metric Improves
```

while:

```text
Critical Guardrail Fails
```

---

# 30. Experiment Hypothesis

Define:

```text
If we change X,
then Y will improve,
without violating Z.
```

Example:

```text
If the new ranking model is deployed,
assignment quality should improve,
while latency and safety constraints remain within limits.
```

# 33. Do Not Stop Too Early

Very small samples may produce unstable conclusions.

Do not declare success based only on:

```text
A Few Positive Events
```

---

# 34. Do Not Run Forever

An experiment should have a stopping decision based on:


---

# 35. Statistical Evaluation

Where applicable, compare:

```text
Control
vs
Treatment
```

using an appropriate statistical method.

The exact method depends on:

```text
Metric Type
Distribution
Experiment Unit
Sample Size
```

---

# 36. Statistical Significance

Statistical significance should be considered when deciding whether an observed difference is likely to represent more than random variation.

It should not be treated as the only decision criterion.

---

# 37. Practical Significance

A statistically significant improvement may be operationally insignificant.

Evaluate:

```text
Magnitude of Improvement
```

in addition to:

```text
Statistical Evidence
```

---

# 38. Confidence Intervals

Where appropriate, report:

```text
Estimated Effect
+
Confidence Interval
```

rather than only a single point estimate.

---

# 39. Sample Size

Experiment design should consider the amount of traffic required to detect a meaningful effect.

Do not assume:

```text
More Data
```

automatically means:

```text
Better Experiment
```

if the population or assignment is biased.

---

# 40. Experiment Power

For important experiments, consider:

```text
Baseline Rate
Expected Effect
Traffic Volume
Variance
Required Confidence
```

before launch.

---

# 41. Multiple Metrics

If many metrics are examined, the probability of finding an apparently positive result by chance increases.

Therefore:

```text

```

should be defined before analysis.

# 48. Experiment Contamination

Contamination occurs when treatment behaviour affects control behaviour or vice versa.

Examples:

```text

```

# 49. Marketplace Experiments

Ride-hailing is a marketplace.

Changing one side can affect the other:

```text
Driver Behaviour
↔
Rider Behaviour
```

Therefore simple user-level A/B testing may not always be sufficient.

---

# 50. Driver-Rider Interaction

For dispatch experiments, consider effects across:


Example:

```text
Treatment
→ Changes Driver Availability
→ Changes Control Outcome
```

This can invalidate a simple comparison.

# 120. AI Agent Implementation Rules

When implementing AI experimentation, an AI coding agent must:

1. Define the experiment hypothesis.
2. Define the control and treatment.
3. Define the experiment unit.
4. Define the population.
5. Define the primary metric.
6. Define guardrail metrics.
7. Preserve hard safety and legal constraints.
8. Make experiment assignment traceable.
9. Preserve model and feature versions.
10. Monitor actual traffic allocation.
11. Distinguish assignment from actual treatment exposure.
12. Preserve experiment identity in prediction and feedback records.
13. Check for experiment contamination and collisions.
14. Support pause, stop, and rollback.
15. Evaluate both statistical and practical significance.
16. Inspect important segments.
17. Document the final decision.
18. Update the relevant AI documentation.

---

# 121. AI Agent Prohibited Patterns

AI agents must not:

- launch an experiment without a defined control,
- change hard legal or safety constraints as part of an experiment,
- silently change experiment allocation,
- assign the same entity inconsistently when stable assignment is required,
- mix control and treatment outcomes without preserving variant identity,
- declare success from a single positive metric,
- ignore guardrail failures,
- ignore marketplace spillover,
- use future outcomes during experiment assignment,
- modify the control group without recording the change,
- automatically promote a treatment solely because it has a better average,
- remove rollback capability,
- create uncontrolled production experiments,
- run experiments without monitoring,
- hide fallback events from experiment analysis.

# 126. Final Principle

> **RideForge experimentation should turn production uncertainty into controlled evidence without turning production into a laboratory.**

The desired loop is:

```text
Hypothesis
  ↓
Controlled Experiment
  ↓
Measured Outcome
  ↓
Safety Validation
  ↓
Statistical Evaluation
  ↓
Operational Decision
  ↓
Controlled Rollout
```

A good experiment should produce:

```text
Clear Evidence
+
Known Risk
+
Traceable Assignment
+
Measurable Outcome
+
Safe Rollback
```

rather than:

```text
Uncontrolled Change
+
Ambiguous Metrics
+
Unknown Exposure
+
No Rollback
```
