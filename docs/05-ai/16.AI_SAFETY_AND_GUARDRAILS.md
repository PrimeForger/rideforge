# 1. Purpose

This document defines the safety boundaries that apply to every RideForge AI capability.

The central principle is:

```text
AI may optimize decisions
but
AI must not override hard constraints.
```

RideForge AI must operate inside:

```text
Legal Constraints
+
Safety Constraints
+
Business Rules
+
Operational Constraints
+
System Integrity
```

---

# 2. Core Safety Principle

> **Machine learning is an optimization mechanism, not the source of authority for safety-critical or legally constrained decisions.**

AI may recommend:

```text
ETA
Driver Ranking
Matching Score
Demand Forecast
Supply Forecast
Dispatch Preference
```

but authoritative systems remain responsible for:

```text
Eligibility
Legal Validation
Ride State
Driver State
Payment State
Safety Rules
Hard Operational Constraints
```

---

# 3. Safety Layers

RideForge should use layered protection:

```text
Input Validation
      ↓
Feature Validation
      ↓
Model Inference
      ↓
Output Validation
      ↓
Hard Constraint Validation
      ↓
Decision Policy
      ↓
Execution
      ↓
Monitoring
      ↓
Fallback
```

No single AI model should be trusted as the only safety mechanism.

---

# 4. AI Safety Boundary

The AI layer should answer:

```text
What is likely?
What is preferable?
What is the estimated score?
What is the expected outcome?
```

The deterministic domain layer should answer:

```text
What is allowed?
What is prohibited?
What is valid?
What can actually happen?
```

---

# 5. Hard Constraints

Hard constraints are conditions that AI cannot override.

Examples:

```text
Driver Eligibility
Vehicle Eligibility
Ride Eligibility
Legal Region Rules
Service Availability
Driver Availability
Ride State
Payment State
Safety Restrictions
```

---

# 6. Soft Constraints

Soft constraints may be optimized by AI.

Examples:

```text
Estimated Pickup Time
Expected Acceptance Probability
Candidate Ranking
Predicted Demand
Predicted Supply
Expected Matching Quality
```

---

# 7. Hard vs Soft Rule

A useful distinction:

```text
Hard Rule:
Must never be violated.

Soft Objective:
Should be optimized when possible.
```

---

# 8. AI Must Not Create Authority

A model prediction does not create authorization.

For example:

```text
Model:
Driver appears suitable.
```

does not mean:

```text
Driver is legally eligible.
```

The eligibility service remains authoritative.

---

# 9. Legal Constraints

RideForge operates in environments where regional and jurisdictional rules may affect ride operations.

Therefore:

```text
AI must never infer legal permission.
```

Legal validation must remain deterministic and explicitly implemented.

---

# 10. Region Validation

A ride crossing regions may require special validation.

Conceptually:

```text
Origin Region
+
Destination Region
+
Applicable Operational Rules
        ↓
Deterministic Validation
```

Only after the ride is legally allowed should AI optimization occur.

---

# 11. AI Dispatch Boundary

The dispatch pipeline should be:

```text
Ride Request
     ↓
Eligibility / Legal Validation
     ↓
Candidate Generation
     ↓
AI Ranking / Matching
     ↓
Hard Constraint Revalidation
     ↓
Dispatch Decision
```

AI should not be the first or final authority for hard constraints.

---

# 12. Candidate Generation

Candidate generation should remove clearly invalid candidates before AI ranking.

For example:

```text
Unavailable Driver
Invalid Vehicle
Invalid Service Type
Illegal Region
```

should not be presented as valid AI candidates.

---

# 13. Candidate Ranking

The ranking model may optimize among eligible candidates.

Conceptually:

```text
Eligible Candidates
        ↓
AI Score
        ↓
Ranking
        ↓
Constraint Check
        ↓
Selection
```

---

# 14. Final Constraint Check

Even if candidate filtering occurred earlier, critical constraints should be revalidated before execution when state may have changed.

Example:

```text
Driver Available
```

at:

```text
10:00
```

may become:

```text
Driver Unavailable
```

at:

```text
10:01
```

---

# 15. Stale State

AI decisions based on stale operational state must not silently execute.

Examples:

```text
Old Driver Location
Old Availability
Old Ride State
Old Region State
```

The system should refresh or use a safe fallback.

---

# 16. Model Input Guardrails

Before inference validate:

```text
Required Features
Feature Types
Feature Ranges
Feature Freshness
Feature Version
```

Invalid input should not be passed blindly to the model.

---

# 17. Feature Range Validation

Examples:

```text
Distance >= 0
Duration >= 0
Counts >= 0
Probability ∈ [0,1]
Latitude within valid bounds
Longitude within valid bounds
```

Actual ranges must be defined by each feature contract.

---

# 18. Missing Feature Guardrail

If a required feature is unavailable:

```text
Do Not Invent a Value
```

unless the model contract explicitly defines a safe default.

Possible actions:

```text
Use Defined Default
Use Last Known Value
Use Fallback Model
Use Deterministic Algorithm
Reject AI Decision
```

---

# 19. Feature Freshness Guardrail

If:

```text
Feature Age > Maximum Allowed Age
```

the feature should be considered stale.

The model should then follow its defined fallback behaviour.

---

# 20. Model Availability Guardrail

If the model is:

```text
Unavailable
Loading
Corrupted
Incompatible
Unhealthy
```

the system should not attempt to use it.

---

# 21. Model Output Validation

Every production model should have output validation.

Validate:

```text
Type
Range
Bounds
Required Fields
NaN / Infinity
Business Meaning
```

---

# 22. Invalid Output

Examples of invalid output:

```text
Negative ETA
NaN Score
Infinite Score
Probability > 1
Probability < 0
Unexpected Class
Missing Ranking Score
```

Such outputs must not directly control production decisions.

---

# 23. ETA Safety

ETA predictions should never produce operationally impossible values.

Conceptually:

```text
Predicted Duration >= Minimum Valid Duration
```

and:

```text
Predicted Duration <= Maximum Accepted Bound
```

where bounds are defined by the model contract.

---

# 24. ETA Fallback

If the ETA model produces an invalid or unavailable prediction:

```text
AI ETA
   ↓
Invalid
   ↓
Routing / Deterministic ETA
```

The exact fallback is defined in:

```text
21.AI_FAILURE_AND_FALLBACK_STRATEGY.md
```

---

# 25. Demand Prediction Safety

Demand predictions should be validated for:

```text
Non-Negative Values
Expected Time Window
Expected Geography
Reasonable Magnitude
```

Extreme values should be flagged rather than blindly trusted.

---

# 26. Supply Prediction Safety

Supply predictions should respect:

```text
Non-Negative Values
Known Operational Capacity
Relevant Geography
Relevant Time Window
```

---

# 27. Ranking Safety

Ranking scores should not bypass:

```text
Eligibility
Availability
Legal Constraints
Vehicle Constraints
Service Constraints
```

---

# 28. Matching Safety

AI matching should only select from:

```text
Eligible
Available
Operationally Valid
```

candidates.

---

# 29. AI Score Is Not Permission

A high model score means:

```text
Preferred According to Model
```

It does not mean:

```text
Allowed
```

---

# 30. Safety Envelope

Every AI decision should operate within a defined envelope:

```text
Allowed Inputs
+
Allowed Outputs
+
Allowed Actions
```

Anything outside the envelope must be rejected or handled through fallback.

---

# 31. Decision Policy

The AI output should pass through a decision policy:

```text
Model Output
     ↓
Safety Checks
     ↓
Business Constraints
     ↓
Operational Constraints
     ↓
Decision Policy
     ↓
Action
```

---

# 32. Separation of Concerns

Keep these responsibilities separate:

```text
Model:
Prediction / Score

Policy:
Decision Rules

Domain:
State Transition

Infrastructure:
Execution
```

This makes the system easier to reason about and audit.

---

# 33. Deterministic Rules

Deterministic rules should remain deterministic.

Examples:

```text
Region Eligibility
Driver Availability
Vehicle Compatibility
Ride State Transition
Payment Authorization
```

Do not replace these with probabilistic predictions.

---

# 34. Safety-Critical Decisions

Any decision that can cause significant operational or legal impact should have:

```text
Deterministic Guardrails
+
Fallback
+
Observability
```

---

# 35. Human Override

Operational systems should provide an override mechanism where required.

Examples:

```text
Disable AI Dispatch
Disable Candidate Ranking
Force Deterministic Matching
Disable Candidate Model
```

---

# 36. Kill Switch

A production AI capability should have a controlled kill switch where practical.

Conceptually:

```text
AI Enabled
     ↓
AI Disabled
     ↓
Fallback Algorithm
```

---

# 37. Kill Switch Requirements

A kill switch should be:

```text
Fast
Auditable
Authorized
Reversible
Observable
```

---

# 38. AI Feature Flags

Feature flags may control:

```text
AI Model Enablement
Model Version
Traffic Percentage
Region
Experiment
```

They should not be used to bypass hard constraints.

---

# 39. Safe Defaults

When AI is unavailable, the system should have a defined deterministic behaviour.

Examples:

```text
Routing ETA
First Valid Candidate
Configured Ranking
Historical Baseline
```

The actual fallback must be model-specific.

---

# 40. Fallback Must Be Valid

A fallback must itself obey:

```text
Legal Rules
Safety Rules
Business Rules
Operational Constraints
```

---

# 41. Fail Closed vs Fail Open

Use:

```text
Fail Closed
```

when allowing the action could cause unacceptable harm or violation.

Use:

```text
Fail Open
```

only when the fallback behaviour is explicitly safe.

The choice is decision-specific.

---

# 42. Safety During Model Rollout

New models should progress through:

```text
Validation
 ↓
Shadow
 ↓
Canary
 ↓
Production
```

rather than immediate full rollout.

---

# 43. Shadow Safety

Shadow models must not:

```text
Change Production Decisions
```

They only generate observations.

---

# 44. Canary Safety

Canary rollout should have:

```text
Limited Traffic
Defined Success Criteria
Defined Failure Criteria
Rollback Path
```

---

# 45. Automatic Rollback

Automatic rollback may be used for clearly measurable failures.

Examples:

```text
Inference Error Spike
Invalid Output Spike
Latency Failure
Fallback Spike
Critical Metric Degradation
```

High-impact rollback conditions should be carefully validated before automation.

---

# 46. Model Health Gate

Before serving traffic:

```text
Model Loaded
+
Artifact Valid
+
Schema Compatible
+
Inference Smoke Test Passed
```

---

# 47. Runtime Safety

The serving runtime should protect against:

```text
Timeout

Crash

Dependency Failure
```

---

# 48. Inference Timeout

Every online AI request should have a bounded timeout.

Do not allow model inference to block critical ride operations indefinitely.

---

# 49. Resource Limits

Model serving should have appropriate:

```text
CPU
Memory
Concurrency
Timeout
```

limits.

---

# 50. Prediction Confidence

If a model provides confidence information, it may be used as an additional signal.

However:

```text
Confidence ≠ Safety
```

A highly confident prediction can still be wrong.

---

# 51. Confidence Threshold

Where appropriate:

```text
Confidence < Threshold
        ↓
Fallback
```

The threshold must be validated empirically.

---

# 52. Out-of-Distribution Detection

Where useful, detect inputs that are significantly different from training data.

Conceptually:

```text
Known Distribution
      ↓
Inference
```

versus:

```text
Unknown / Extreme Distribution
      ↓
Fallback / Reduced Trust
```

---

# 53. OOD Handling

Out-of-distribution detection should not be treated as perfect.

It is an additional signal for:

```text
Monitoring
Fallback
Investigation
```

---

# 54. Extreme Input Guardrail

Extreme inputs may include:

```text
Very Long Distance
Unusual Demand
Unexpected Driver Count
Invalid Coordinates
Unexpected Vehicle Configuration
```

The system should handle these explicitly.

---

# 55. Geographic Guardrails

AI decisions should remain inside configured operational geography.

Examples:

```text
Supported Region
Service Zone
Allowed Pickup Area
Allowed Drop Area
```

---

# 56. Cross-Region Guardrail

Cross-region behaviour must be governed by:

```text
Explicit Region Policy
```

not learned behaviour.

---

# 57. Driver Safety

AI must not optimize solely for:

```text
Lower ETA
Higher Acceptance
Lower Cost
```

if doing so creates unsafe operational outcomes.

---

# 58. User Safety

AI decisions should not create unacceptable:

```text
Pickup Risk
Routing Risk
Operational Risk
```

where such risks are identifiable by the system.

---

# 59. Operational Safety

The model should not create:

```text
Impossible Assignment
Overloaded Driver
Duplicate Assignment
Invalid Ride State
```

---

# 60. Duplicate Action Protection

If the same AI decision is processed more than once:

```text
Idempotency
+
Domain State Validation
```

must prevent duplicate operational actions.

---

# 61. Race Conditions

AI decisions can become stale because of concurrent events.

Example:

```text
Model selects Driver A
       ↓
Another request assigns Driver A
       ↓
Original decision executes
```

The final domain transaction must revalidate state.

---

# 62. Transaction Boundary

The AI layer should not assume that:

```text
Prediction
```

and:

```text
Domain State Change
```

are automatically atomic.

The domain layer must protect its own transaction boundary.

---

# 63. AI and Event Processing

AI consumers must respect:

```text
Event Ordering
Idempotency
Duplicate Delivery
Retry
Dead Letter Handling
```

according to the platform's event architecture.

---

# 64. AI and Kafka / Redpanda

Where AI components consume events:

```text
Event
 ↓
Validation
 ↓
Feature Update / Learning Signal
```

AI must not create an alternate undocumented event semantics.

---

# 65. AI Safety and Redis

Redis-derived online state should be treated according to its freshness guarantees.

```text
Redis Value Exists
```

means:

```text

```

---

# 66. AI Safety and PostgreSQL

# 99. AI Agent Implementation Rules

When implementing AI safety controls, an AI coding agent must:

1. Keep hard business and legal constraints outside model predictions.
2. Validate model inputs before inference.
3. Validate model outputs before use.
4. Define explicit bounds for important outputs.
5. Define timeout and failure behaviour.
6. Preserve deterministic fallback paths.
7. Revalidate mutable operational state before critical actions.
8. Protect domain transaction boundaries.
9. Prevent duplicate AI-triggered actions.
10. Preserve audit metadata for important AI decisions.
11. Support controlled model rollback.
12. Keep AI experiments inside safety boundaries.
13. Treat stale features explicitly.
14. Preserve operator override where required.
15. Never use model confidence as a substitute for hard validation.
16. Update the relevant AI documentation.

---

# 100. AI Agent Prohibited Patterns

AI agents must not:

- allow a model to override legal constraints,
- allow a model to override hard eligibility rules,
- treat a high model score as authorization,
- execute decisions using known-stale critical state,
- accept NaN, infinity, or invalid model outputs,
- silently invent missing feature values,
- remove deterministic fallbacks,
- bypass domain transaction validation,
- let AI directly mutate critical state without domain authorization,
- deploy a candidate directly to full production without the required controls,
- make safety constraints dependent on model predictions,
- disable monitoring merely to improve performance,
- silently change guardrail thresholds,
- create autonomous self-modifying production behaviour without explicit approval and safety controls.

```text
                    Continue               Fallback / Rollback
```

# 105. Final Principle

> **RideForge AI must remain subordinate to legal, safety, business, and domain constraints. AI can optimize within the allowed operating space, but it must never define the boundaries of that space.**

The desired safety model is:

```text
AI Predicts
    ↓
Validators Check
    ↓
Constraints Decide What Is Allowed
    ↓
Domain Executes
    ↓
Monitoring Watches
    ↓
Fallback Protects
```

This keeps RideForge:

```text
Intelligent
+
Constrained
+
Auditable
+
Recoverable
+
Operationally Safe
```

without turning the AI layer into an uncontrolled authority.
