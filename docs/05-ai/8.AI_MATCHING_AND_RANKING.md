# 1. Purpose

This document defines how RideForge discovers, filters, scores, and ranks driver candidates for a ride.

The matching system is intentionally separated into:

```text
Candidate Discovery
        ↓
Eligibility
        ↓
Feature Resolution
        ↓
Ranking
        ↓
Recommendation
        ↓
Reservation
```

The system must preserve the distinction between:

```text
Who can receive the ride?
```

and:

```text
Who is the best candidate among those who can receive it?
```

---

# 2. Core Principle

> **Eligibility determines who may receive a ride; ranking determines which eligible candidate is preferred.**

Therefore:

```text
Ineligible Driver
        ↓
Never Ranked
```

and:

```text
Eligible Driver
        ↓
Can Be Ranked
```

---

# 3. Matching vs Ranking

These concepts are related but not identical.

## Matching

Matching establishes whether a driver and ride are compatible.

Examples:

```text
Vehicle Type
Operating Region
Driver State
Ride Requirements
Regulatory Constraints
```

## Ranking

Ranking determines the preferred candidate among compatible drivers.

Examples:

```text
ETA
Distance
Expected Acceptance
Demand / Supply Context
Operational Policy
```

---

# 4. Matching Objective

The matching system should:

```text
Find Eligible Candidates
        ↓
Rank Candidates
        ↓
Provide Best Available Recommendation
```

The system should optimize the active dispatch objective without bypassing deterministic platform rules.

---

# 5. Authoritative Boundary

The matching and ranking layer does not own:

```text
Ride State
Driver State
Reservation
Assignment Transaction
Payment
Regulatory Authorization
```

Those remain authoritative responsibilities of the core platform.

---

# 6. End-to-End Flow

```text
Ride Created
    ↓
Candidate Discovery
    ↓
Deterministic Eligibility
    ↓
Candidate Feature Resolution
    ↓
Baseline Ranking
    ↓
AI Ranking
    ↓
Candidate Ordering
    ↓
Reservation Attempt
    ↓
Assignment
```

Failure:

```text
AI Ranking Failure
    ↓
Deterministic Ranking
    ↓
Configured Fallback
```

---

# 7. Candidate Discovery

Candidate discovery identifies drivers that are potentially relevant.

Potential discovery dimensions:

```text
Location
Availability
Operating Area
Vehicle
Ride Type
```

Candidate discovery should be optimized for low latency.

---

# 8. Discovery Is Not Eligibility

Discovery should be treated as a broad candidate-generation step.

Example:

```text
Nearby Drivers
        ↓
Potential Candidates
```

does not mean:

```text
All Nearby Drivers
        =
Eligible Drivers
```

Eligibility must be evaluated separately.

---

# 9. Deterministic Eligibility

Eligibility should evaluate authoritative rules such as:

```text
Driver Is Available
Driver Is Online
Vehicle Is Compatible
Region Is Allowed
Ride Requirements Are Satisfied
Driver Is Not Already Reserved
```

The exact rules belong to the core domain and dispatch implementation.

---

# 10. Eligibility Must Run Before AI Ranking

Preferred sequence:

```text
Candidate Discovery
        ↓
Eligibility Filtering
        ↓
AI Ranking
```

not:

```text
All Drivers
        ↓
AI Ranking
        ↓
Eligibility
```

This protects correctness and reduces unnecessary model work.

---

# 11. Regulatory Boundary

AI cannot make an otherwise prohibited assignment valid.

For example:

```text
Driver
 ↓
AI Score = Excellent
 ↓
Regional Rule = Not Allowed
 ↓
Candidate Rejected
```

Hard regulatory and business constraints always win.

---

# 12. Candidate Set

After filtering:

```text
Candidate Set =
All Discovered Drivers
minus
All Ineligible Drivers
```

The ranking system operates only on this set.

---

# 13. Empty Candidate Set

If:

```text
Eligible Candidates = 0
```

the system must follow the configured no-candidate policy.

Possible outcomes:

```text
Retry Discovery
Wait
Continue Dispatch Strategy
Notify Operational Layer
Fail According to Business Rules
```

Do not invent a candidate.

---

# 14. Feature Resolution

For each eligible candidate, resolve ranking features.

Potential groups:

```text
Driver Features
Ride Features
ETA Features
Spatial Features
Temporal Features
Demand Features
Supply Features
Historical Features
Policy Features
```

---

# 15. Driver Features

Potential driver signals:

```text
Current Location
Availability
Vehicle Type
Operating Region
Relevant Historical Behaviour
```

Only features necessary for the ranking objective should be used.

---

# 16. Ride Features

Potential ride signals:

```text
Pickup
Destination
Ride Type
Requested Vehicle
Trip Characteristics
Operational Requirements
```

---

# 17. ETA Features

ETA can be a major ranking signal.

Conceptually:

```text
Candidate A → 3 min
Candidate B → 5 min
Candidate C → 8 min
```

ETA may be produced by the ETA system defined in:

```text
6.ETA_AND_PREDICTION_SYSTEM.md
```

---

# 18. Spatial Features

Potential spatial signals:

```text
Driver-to-Pickup Distance
Pickup Area
Destination Area
Area Relationships
```

Spatial features must use consistent geographic definitions.

---

# 19. Temporal Features

Potential signals:

```text
Time of Day
Day of Week
Peak / Off-Peak
```

Temporal context may influence:

```text
Demand
Supply
Travel Time
Driver Availability
```

---

# 20. Demand Features

Demand forecasts may provide:

```text
Expected Demand
```

for relevant areas and future time windows.

These features should only influence ranking when explicitly included in dispatch policy.

---

# 21. Supply Features

Supply forecasts may provide:

```text
Expected Future Supply
```

which can support fleet-level optimization.

The current driver state remains authoritative.

---

# 22. Historical Features

Historical features may include:

```text
Acceptance Behaviour
Completion Behaviour
Cancellation Behaviour
Other Validated Operational Signals
```

Historical signals must be carefully governed.

---

# 23. Feature Freshness

Different features have different freshness requirements.

Example:

```text
Driver Location
→ Very Fresh

Availability
→ Very Fresh

ETA
→ Recent

Historical Performance
→ Periodic

Forecasts
→ Forecast-Window Specific
```

---

# 24. Feature Availability

The ranking system should explicitly handle:

```text
Feature Available
Feature Missing
Feature Stale
Feature Invalid
```

It should not silently treat all missing values as valid zero values.

---

# 25. Candidate Feature Validation

Before scoring:

```text
Validate Features
        ↓
Valid?
 ├── Yes → Rank
 └── No  → Fallback / Exclude According to Policy
```

The behaviour must be explicit.

---

# 26. Deterministic Baseline

RideForge should maintain a deterministic ranking baseline.

A practical baseline can use:

```text
ETA
Distance
Availability
Operational Rules
```

This provides:

```text
Fallback
Benchmark
Evaluation Reference
```

---

# 27. Why the Baseline Matters

AI ranking should prove improvement against:

```text
Existing Deterministic Ranking
```

rather than against an arbitrary or weak comparison.

---

# 28. Deterministic Score

An intermediate ranking system may calculate:

```text
Score =
    w1 * ETA Score
  + w2 * Distance Score
  + w3 * Operational Preference
```

Weights should be explicit and version-controlled where appropriate.

---

# 29. AI Ranking

AI ranking may learn relationships between candidate features and assignment outcomes.

Conceptually:

```text
Eligible Candidates
        ↓
Feature Vector
        ↓
Ranking Model
        ↓
Candidate Scores
        ↓
Ordered Candidates
```

---

# 30. Ranking Target

The ranking target must be explicitly defined.

Possible objectives:

```text
Lower Pickup ETA
Higher Acceptance Probability
Higher Completion Probability
Lower Cancellation Risk
Higher Overall Assignment Quality
```

Do not combine targets without defining the intended objective.

---

# 31. Ranking Score

A conceptual score:

```text
Candidate Score =
    f(
        ETA,
        Distance,
        Driver Context,
        Ride Context,
        Demand,
        Supply,
        Historical Signals
    )
```

The exact function is implementation-specific.

---

# 32. Score Meaning

A score must have a documented meaning.

For example:

```text
Higher Score
=
Preferred Candidate
```

or:

```text
Lower Score
=
Preferred Candidate
```

Do not allow different services to interpret the same score differently.

---

# 33. Score Comparability

Scores should only be directly compared when the model and scoring semantics support that comparison.

Do not assume:

```text
Model A Score = Model B Score
```

without a defined contract.

---

# 34. Candidate Ordering

The ranking layer should return:

```text
Rank 1
Rank 2
Rank 3
...
```

The ordering must be deterministic when scores are equal or effectively equivalent.

---

# 35. Tie Breaking

A tie-breaking policy may use:

```text
Lower ETA
Lower Distance
Stable Candidate Identifier
Queue Position
```

The actual order should be explicitly defined.

---

# 36. Ranking Stability

Monitor for excessive:

```text
Rank Flapping
Score Oscillation
Candidate Reordering
```

especially when input values change only slightly.

---

# 37. Ranking Confidence

If the model provides a valid confidence or uncertainty measure, it may influence whether AI ranking is used.

Conceptually:

```text
High Confidence
→ AI Ranking

Low Confidence
→ Conservative / Deterministic Ranking
```

Only use confidence if the model supports a validated interpretation.

---

# 38. Multi-Objective Ranking

Advanced ranking may consider:

```text
Immediate Pickup
+
Acceptance
+
Cancellation
+
Fleet Balance
```

The weighting must be governed by dispatch policy.

---

# 39. Immediate Objective

The immediate objective is typically:

```text
Serve the Current Ride
```

Potential metrics:

```text
Pickup ETA
Assignment Success
Acceptance
```

---

# 40. Fleet Objective

An advanced objective may also consider:

```text
Future Supply
Future Demand
Driver Distribution
```

This should only be introduced after the supporting forecasts are reliable.

---

# 41. Immediate vs Fleet-Level Trade-Off

Example:

```text
Candidate A
→ Faster pickup
→ Located in high-demand area

Candidate B
→ Slightly slower pickup
→ Located in lower-demand area
```

The system must explicitly determine whether preserving Candidate A's future supply is worth the immediate difference.

This should be policy-controlled and experimentally validated.

---

# 42. Demand-Aware Ranking

Demand forecasts can provide:

```text
Expected Future Demand
```

for the driver's current area.

This may influence ranking where approved.

---

# 43. Supply-Aware Ranking

Supply forecasts can provide:

```text
Expected Future Supply
```

and help identify areas where a driver is operationally valuable.

---

# 44. Demand-Supply Signal

A derived signal may be:

```text
Expected Demand
-
Expected Supply
=
Expected Gap
```

A high gap may indicate that retaining nearby supply has greater value.

---

# 45. Ranking Policy

The ranking system should be controlled by an explicit policy containing:

```text
Hard Constraints
Soft Preferences
Objectives
Fallback
Tie Breaking
```

---

# 46. Hard Constraints

Hard constraints include:

```text
Eligibility
Regional Rules
Vehicle Compatibility
Driver State
Ride Requirements
```

They must be applied before ranking.

---

# 47. Soft Preferences

Soft preferences may include:

```text
Lower ETA
Lower Distance
Higher Acceptance Probability
Lower Cancellation Risk
Supply Balance
```

These can be optimized by ranking.

---

# 48. Policy Versioning

Where ranking policy changes materially, retain:

```text
Policy Version
```

This helps explain why a candidate was ranked differently after a deployment.

---

# 49. Model Versioning

Every AI ranking result should be traceable to:

```text
Model Version
Feature Version
Policy Version
```

where applicable.

---

# 50. Ranking Output Contract

A conceptual output:

```text
Candidate ID
Rank
Score
Model Version
Policy Version
Prediction Timestamp
```

Additional metadata may be included when required.

---

# 51. Output Validation

Validate:

```text
Candidate ID Exists
Candidate Is Eligible
Candidate Belongs to Candidate Set
Score Is Valid
Rank Is Valid
Model Version Is Known
```

Invalid output triggers fallback.

---

# 52. Candidate Eligibility Recheck

Because driver state can change between:

```text
Ranking
```

and:

```text
Reservation
```

the core system must revalidate the candidate at reservation time.

---

# 53. Reservation Boundary

The final flow is:

```text
Rank Candidate
        ↓
Reservation Attempt
        ↓
Success?
 ├── Yes → Assignment
 └── No  → Next Candidate / Fallback
```

---

# 54. Reservation Race

Two ride requests may rank the same driver.

Example:

```text
Ride A → Driver X
Ride B → Driver X
```

Both may receive Driver X as the top recommendation.

Only the core reservation transaction determines who successfully acquires the driver.

---

# 55. Ranking Does Not Lock Drivers

The ranking system should not be treated as a lock.

```text
Ranking
=
Recommendation
```

not:

```text
Ranking
=
Reservation
```

---

# 56. Candidate Progression

If the top-ranked driver cannot be reserved:

```text
Candidate 1
   ↓
Reservation Failure
   ↓
Candidate 2
   ↓
Reservation Attempt
```

Continue only within the configured retry and dispatch limits.

---

# 57. Retry Limits

Retries must be bounded.

Avoid:

```text
Infinite Candidate Loop
```

Use:

```text
Maximum Attempts
+
Maximum Dispatch Duration
```

---

# 58. Dispatch Timeout

The complete ranking workflow must operate within the dispatch latency budget.

Budget components may include:

```text
Candidate Discovery
Feature Resolution
Model Inference
Ranking
Reservation
```

---

# 59. AI Inference Timeout

AI inference must have a bounded timeout.

```text
Inference
 ├── Success
 └── Timeout
       ↓
    Fallback
```

---

# 60. Ranking Fallback

Recommended hierarchy:

```text
AI Ranking
    ↓ failure
Deterministic Ranking
    ↓ failure
Configured Dispatch Strategy
```

The exact fallback depends on the active operating strategy.

---

# 61. Dispatch Strategy Integration

RideForge has two primary dispatch strategies:

```text
Smart Stand Dispatch
+
Smart Dispatch
```

**AI-Assisted Dispatch is not a third primary dispatch strategy.**

AI matching and ranking operate within the effective strategy selected for the ride.

The high-level flow is:

```text
Dispatch Configuration Hierarchy
        ↓
Effective Dispatch Strategy
        ↓
Candidate Discovery
        ↓
Eligibility
        ↓
Strategy-Specific Prioritization
        ↓
Deterministic / AI Ranking
        ↓
Reservation
```

AI must preserve the semantics of the effective dispatch strategy.

---

# 62. Hierarchical Dispatch Strategy Resolution

The effective dispatch strategy must be resolved from the applicable configuration hierarchy before AI ranking.

Possible configuration levels include:

```text
State
District
City / Town
Rural Area
Auto Stand
Specific Ride Level
Other configured intermediate levels
```

Not every level requires an explicit configuration.

The resolution rule is:

```text
Most Specific Applicable Level
        ↓
Explicit Dispatch Strategy?
   ├── YES → Use it
   └── NO
        ↓
Move to Parent Level
        ↓
Continue Until Explicit Strategy Is Found
        ↓
System Default if None Exists
```

Therefore:

> **Specific configuration overrides inherited configuration.**

Example:

```text
District → Smart Dispatch
Town A   → Smart Stand Dispatch
Town B   → No explicit configuration
```

Results:

```text
Ride from Town A → Smart Stand Dispatch
Ride from Town B → Smart Dispatch
```

AI ranking must consume the resolved strategy and must not independently invent or override this inheritance process.

---

# 63. Smart Stand Dispatch

**Smart Stand Dispatch is stand-preferred, not stand-exclusive.**

When the rider is within the configured radius of an auto stand:

```text
Ride Pickup
    ↓
Preferred Auto Stand
    ↓
Eligible Drivers at Preferred Stand
    ↓
Stand Queue / Ordering Preference
```

The preferred stand is the initial preferred source.

If suitable stand drivers are unavailable or unsuitable, the candidate flow may expand to:

```text
Drivers outside the preferred stand
Drivers from nearby stands
Drivers from nearby locations
```

These candidates may then be evaluated using the applicable dispatch and ranking factors.

The important distinction is:

```text
Stand Preference
≠
Stand-Only Candidate Pool
```

A candidate must not be excluded merely because the candidate is not physically at the preferred stand.

If the rider is outside the radius of all configured stands:

```text
Smart Stand Dispatch
        ↓
No Preferred Stand
        ↓
Eligible Nearby Drivers
```

There is no stand-only restriction.

---

# 64. Smart Dispatch

**Smart Dispatch is stand-agnostic.**

When Smart Dispatch is the effective strategy, candidate ranking does not depend on auto-stand membership.

Eligible candidates may include:

```text
Drivers at auto stands
Drivers outside auto stands
Drivers from nearby locations
```

subject to normal eligibility, geographic, legal, operational, and service constraints.

Typical ranking signals include:

```text
Driver Eligibility
Availability
Distance
ETA
Acceptance / Cancellation Predictions
Operational Factors
Other Approved Ranking Features
```

---

# 65. Candidate Eligibility vs Preference

AI matching must preserve the distinction between eligibility and preference.

```text
Ineligible
    ↓
Never Ranked
```

but:

```text
Eligible but Not Preferred
    ↓
May Still Be Ranked
```

For example, under Smart Stand Dispatch:

```text
Non-stand Driver
    = potentially eligible
    ≠ automatically excluded
```

The same principle applies to drivers from nearby locations.

Therefore:

```text
Not Preferred ≠ Ineligible
```

AI ranking must never convert a strategy preference into a hard eligibility rule unless an explicit business rule defines it as such.

---

# 66. Cross-Location Dispatch

Dispatch candidate discovery may expand beyond the ride's originating location when local supply cannot provide a suitable driver.

Example:

```text
Location A
Smart Dispatch
    ↓
No suitable local driver
    ↓
Expand to Location B
    ↓
Location B uses Smart Stand Dispatch
```

Drivers from Location B may be considered if they satisfy the applicable eligibility and geographic constraints.

Because Location B uses Smart Stand Dispatch, its stand context may influence prioritization:

```text
Location B
    ↓
Stand Context
    ↓
Stand Driver / Non-Stand Driver
    ↓
Eligibility + ETA + Distance + Other Factors
```

The source location's dispatch strategy does not automatically make its drivers ineligible for a ride originating in another nearby location.

The candidate context should preserve:

```text
Candidate Location
Candidate Location Strategy
Stand Membership
Relevant Stand
Queue Position
Discovery Source
Expansion Level
Distance
ETA
```

The final decision must compare eligible candidates according to the applicable dispatch and ranking rules.

---

# 67. Strategy Does Not Define a Hard Candidate Boundary

The AI matching layer must not assume:

```text
Dispatch Strategy
=
Candidate Pool Boundary
```

Instead:

```text
Dispatch Strategy
        ↓
Strategy-Specific Preference / Prioritization

Candidate Discovery
        ↓
Geographic / Operational Candidate Scope
```

For example:

```text
Smart Stand Dispatch
+
Rider inside Stand Radius
```

does **not** mean:

```text
Only Stand Drivers Can Be Ranked
```

It means:

```text
Prefer the relevant stand first
        ↓
Expand when suitable stand supply is unavailable
        ↓
Evaluate broader eligible candidates
```

---

# 68. Strategy-Specific Ranking

The ranking layer must preserve the semantics of the resolved strategy.

For Smart Stand Dispatch:

```text
Preferred Stand Context
        ↓
Stand Queue / Ordering Rules
        ↓
Eligibility
        ↓
Distance / ETA / Other Factors
        ↓
Broader Candidate Evaluation when required
```

For Smart Dispatch:

```text
Eligibility
        ↓
Distance / ETA
        ↓
Other Ranking Features
        ↓
Final Candidate Ordering
```

The exact weighting or ordering must follow the approved business and ranking configuration.

AI must not silently replace a deterministic stand-queue rule with an arbitrary numerical score.

---

# 69. AI Ranking and Strategy Preservation

AI ranking may optimize candidate ordering, but it must not silently change the effective dispatch strategy.

For example:

```text
Effective Strategy:
Smart Stand Dispatch

AI Ranking
    ↓
May improve candidate ordering
```

It must not become:

```text
Smart Dispatch
```

merely because the AI model considers a non-stand driver to be a better candidate.

If a broader candidate is allowed under Smart Stand Dispatch, that is still an execution of Smart Stand Dispatch.

---

# 70. AI Strategy Switching

AI should not silently switch:

```text
Smart Stand Dispatch
```

to:

```text
Smart Dispatch
```

because:

```text
Preferred Stand Unavailable
```

or:

```text
AI Predicts Another Driver Is Better
```

Expansion from the preferred stand to broader eligible candidates is part of the Smart Stand Dispatch behavior.

A true strategy change requires an explicit configuration or business rule.

Any explicit automatic strategy switching must have:

```text
Conditions
Observability
Authorization
Rollback
Auditability
```

---

# 71. AI Failure and Deterministic Fallback

AI ranking failure must preserve the active dispatch strategy.

Example:

```text
Smart Stand Dispatch
        ↓
AI Ranking Failure
        ↓
Deterministic Strategy-Compatible Ranking
        ↓
Reservation
```

and:

```text
Smart Dispatch
        ↓
AI Ranking Failure
        ↓
Deterministic Smart Ranking
        ↓
Reservation
```

AI failure must not cause an implicit:

```text
Smart Stand Dispatch
        ↓
Smart Dispatch
```

strategy change.

---

# 72. AI Feature Context for Dispatch Strategy

AI ranking features may include strategy context such as:

```text
Effective Dispatch Strategy

Applicable Auto Stand
Stand Membership
Queue Position
Candidate Location
Candidate Location Strategy
Discovery Source
Expansion Level
Distance
ETA
Availability
Historical Signals
Demand / Supply Signals
```

These features provide context to the model but do not replace authoritative eligibility or business rules.

---

# 73. Hard Constraints Remain Authoritative

AI ranking cannot override:

```text
Legal / Regional Restrictions
Driver Eligibility
Driver Availability
Vehicle / Service Compatibility
Safety Constraints
Ride Constraints
Reservation State
Platform Rules
```

Therefore:

```text
Hard Constraints
        ↓
Eligible Candidates
        ↓
AI / Deterministic Ranking
```

not:

```text
AI Ranking
        ↓
Override Hard Constraints
```

---

# 64. Regional Constraints

Matching may differ by operating region.

The system should support:

```text
Regional Eligibility Rules
Regional Policies
Regional Models
Regional Features
```

where justified.

---

# 65. Cross-Region Rides

Regional and legal validation must happen before AI ranking can recommend a driver.

The model cannot override:

```text
Ride Legality
```

---

# 66. Candidate Ranking by Region

Where regional models exist:

```text
Region
 ↓
Approved Model
 ↓
Ranking
```

The model selection must be traceable.

---

# 67. Cold Start

New regions, drivers, or ride types may have limited historical data.

The ranking system should support:

```text
Deterministic Baseline
```

as a reliable cold-start mechanism.

---

# 68. New Driver

A new driver may have no meaningful personal historical signals.

The ranking system should avoid penalizing the driver merely because:

```text
Historical Data = Insufficient
```

Use appropriate neutral or fleet-level features.

---

# 69. Sparse Candidate Areas

In low-density areas:

```text
Candidate Count
```

may be small.

The system should not assume that a complex ranking model adds value when only one or two eligible drivers exist.

---

# 70. Single Candidate

If only one candidate is eligible:

```text
Candidate Count = 1
```

ranking complexity may be unnecessary.

The system can proceed directly to reservation subject to normal validation.

---

# 71. Empty Candidate Handling

If:

```text
Candidate Count = 0
```

follow the configured dispatch policy.

Do not invoke ranking with an empty candidate set unless the interface explicitly supports it.

---

# 72. Candidate Count Optimization

The system should avoid unnecessarily large candidate sets.

Benefits:

```text
Lower Inference Cost
Lower Latency
Less Feature Retrieval
Simpler Ranking
```

Candidate limits must not exclude viable candidates arbitrarily.

---

# 73. Candidate Ordering Before AI

An optional deterministic pre-ranking stage can reduce the candidate set:

```text
All Eligible
      ↓
Cheap Baseline Filter
      ↓
Top K
      ↓
AI Ranking
```

Only use this if it is validated not to harm matching quality.

---

# 74. Top-K Ranking

A top-K model may rank only a subset of candidates.

The K value should be based on:

```text
Candidate Density
Latency
Model Cost
Match Quality
```

---

# 75. Ranking Cost

AI ranking cost includes:

```text
Feature Retrieval
Inference
Network Calls
Serialization
```

The system should optimize the complete path rather than inference alone.

---

# 76. Batch Ranking

Where supported, multiple candidates may be scored in a single inference call.

Conceptually:

```text
Candidate 1
Candidate 2
Candidate 3
        ↓
Batch Model
        ↓
Scores
```

Batching is useful only when it reduces latency or resource consumption.

---

# 77. Ranking Cache

Caching rankings is generally sensitive because:

```text
Driver State
Location
Availability
Ride Context
```

change quickly.

Caching should therefore be used cautiously.

---

# 78. Feature Cache

# 127. AI Agent Implementation Rules

When implementing AI matching or ranking, an AI coding agent must:

1. Inspect the existing matching and dispatch implementation.
2. Preserve Stand Dispatch.
3. Preserve deterministic eligibility.
4. Define the ranking objective before coding the model.
5. Establish a deterministic baseline.
6. Reuse the existing ETA capability where appropriate.
7. Reuse demand/supply predictions where appropriate.
8. Keep model output separate from reservation.
9. Validate every model output.
10. Add bounded inference timeouts.
11. Implement deterministic fallback.
12. Preserve reservation concurrency guarantees.
13. Add model and policy version traceability.
14. Add business and technical metrics.
15. Test no-candidate and single-candidate cases.
16. Test reservation races.
17. Avoid unnecessary model complexity.
18. Update the relevant AI documentation.

---

# 128. AI Agent Prohibited Patterns

AI agents must not:

- let AI decide eligibility,
- bypass regional or regulatory validation,
- let AI directly reserve a driver,
- mutate transactional state from model output,
- remove Stand Dispatch,
- remove deterministic ranking,
- create duplicate matching services,
- invent ranking accuracy,
- use future information as ranking features,
- treat stale availability as authoritative,
- retry indefinitely,
- use unvalidated confidence scores,
- introduce complex ML without a baseline,
- silently change ranking policy,
- expose unnecessary sensitive data,
- make AI a single point of failure.

# 131. Final Principle

> **RideForge matching should use AI to improve candidate ordering, not to replace deterministic eligibility or transactional reservation.**

The target architecture is:

```text
Discover
   ↓
Filter
   ↓
Understand
   ↓
Rank
   ↓
Validate
   ↓
Reserve
   ↓
Assign
   ↓
Measure
   ↓
Improve
```

The matching system should remain:

```text
Fast
+
Correct
+
Observable
+
Experimentable
+
Fallback-Safe
+
Policy-Controlled
```

The long-term goal is not to make every assignment dependent on AI.

The goal is to consistently select better candidates while preserving a reliable deterministic operating path.
