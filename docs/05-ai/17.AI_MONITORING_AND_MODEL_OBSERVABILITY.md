# 1. Purpose

This document defines how RideForge observes AI systems in production.

AI observability must answer:

```text
Is the AI service available?
Is inference healthy?
Are features healthy?
Are predictions valid?
Is model quality degrading?
Is data changing?
Are fallbacks increasing?
Are important segments degrading?
Is the AI system still safe?
```

The objective is to detect problems early and provide enough evidence to investigate them.

---

# 2. Core Principle

> **AI observability must cover the entire prediction lifecycle, not only model latency.**

The minimum observable path is:

```text
Input
  ↓
Feature Retrieval
  ↓
Feature Validation
  ↓
Inference
  ↓
Output Validation
  ↓
Decision
  ↓
Execution
  ↓
Outcome
  ↓
Model Evaluation
```

# 37. Feature Drift

```text

vs

```

```text

vs
```

---

# 38. Drift Is Not Automatically Failure

A distribution change can represent a real operational change.

Therefore:

```text
Drift
→ Investigation
```

rather than:

```text
Drift
→ Automatic Retraining
```

# 114. AI Agent Implementation Rules

When implementing AI observability, an AI coding agent must:

1. Monitor service availability and inference errors.
2. Measure latency using meaningful percentiles.
3. Make model versions observable.
4. Monitor feature freshness and availability.
5. Monitor invalid model outputs.
6. Monitor fallback behaviour.
7. Monitor prediction distributions.
8. Connect predictions to authoritative outcomes where applicable.
9. Monitor model quality after outcomes become available.
10. Monitor important geographic and operational segments.
11. Track safety and constraint violations.
12. Make critical failures actionable through alerts.
13. Avoid logging unnecessary sensitive data.
14. Preserve correlation and prediction identifiers where appropriate.
15. Support investigation of model, feature, and infrastructure failures.
16. Keep monitoring aligned with existing platform observability.
17. Update the relevant AI documentation.

AI agents must not:

- treat model latency as the only AI health metric,
- assume no alert means the model is correct,
- monitor only aggregate performance while ignoring critical segments,
- hide invalid outputs inside successful request counts,
- silently ignore feature freshness failures,
- log sensitive raw data unnecessarily,
- create alerts without actionable thresholds,
- automatically retrain solely because drift was detected,
- automatically roll back based on an unvalidated noisy metric,
- mix champion and candidate metrics without identifying model versions,
- remove telemetry to reduce cost without assessing operational impact,
- treat missing telemetry as healthy system behaviour.

# 119. Final Principle

> **RideForge AI observability must make model behaviour visible from input to outcome, including infrastructure health, feature health, prediction quality, safety, and operational impact.**

The desired loop is:

```text
Observe
  ↓
Understand
  ↓
Detect
  ↓
Contain
  ↓
Investigate
  ↓
Improve
```

A production AI system should never be considered healthy merely because:

```text
Requests Are Succeeding
```

It should be considered healthy only when:

```text
Infrastructure Is Healthy
+
Features Are Healthy
+
Predictions Are Valid
+
Model Quality Is Acceptable
+
Safety Constraints Hold
+
Operational Outcomes Remain Acceptable
```

That is the standard RideForge should use for production AI observability.
