# 1. Purpose

This document defines how RideForge manages features used by AI systems across:

```text
Offline Training
Offline Evaluation
Online Inference
Forecasting
Matching
Ranking
ETA Prediction
```

The primary objective is to maintain:

```text
Feature Correctness
+
Training / Serving Consistency
+
Point-in-Time Correctness
+
Freshness
+
Low Latency
+
Operational Reliability
```

---

# 2. Core Principle

> **An ML model is only as reliable as the feature values it receives at prediction time and the feature values it received during training.**

Therefore:

```text
Training Feature
        ≈
Production Feature
```

must be true semantically, even when the physical computation paths differ.

---

# 3. Feature Categories

RideForge features can broadly be divided into:

```text
Offline Features
Online Features
Hybrid Features
```

---

# 4. Offline Features

Offline features are primarily used for:

```text
Training
Evaluation
Backtesting
Historical Analysis
Dataset Generation
```

They can be computed from historical data without strict real-time latency requirements.

---

# 5. Online Features

Online features are required during production inference.

Examples:

```text
Current Driver Availability
Current Driver Location
Current Candidate Distance
Current Area Demand
Current Supply
Recent Ride Activity
```

---

# 6. Hybrid Features

Some features have both:

```text
Offline Computation
+
Online Serving
```

The definition should remain consistent even when the storage and computation path differs.

---

# 7. Feature Definition vs Feature Storage

A feature has two separate concerns:

```text
Feature Definition
```

and:

```text
Feature Storage / Serving
```

The definition describes what the value means.

The serving system determines how the value is obtained.

---

# 8. Feature Contract

Every important feature should define:

```text
Feature Name
Definition
Type
Unit
Entity
Timestamp Semantics
Freshness Requirement
Allowed Range
Offline Availability
Online Availability
```

---

# 9. Feature Entity

A feature must identify what it belongs to.

Examples:

```text
Driver
Ride
Candidate Driver
Area
Region
Time Window
```

---

# 10. Feature Timestamp

A feature must define what its timestamp represents.

Possible meanings:

```text
Event Time
Observation Time
Aggregation End Time
Last Updated Time
```

Do not leave temporal semantics ambiguous.

---

# 11. Point-in-Time Correctness

For historical training:

```text
Feature Value at T
```

must represent information available at:

```text
T
```

and must not use information learned after:

```text
T
```

---

# 12. Future Leakage

The following is invalid:

```text
Prediction Time = 10:00

Feature:
Actual Ride Completion Time = 10:35
```

because the feature uses future information.

---

# 13. Online / Offline Parity

The same logical feature should mean the same thing in:

```text
Training
```

and:

```text
Production Inference
```

Example:

```text
driver_completed_rides_last_30d
```

must represent the same business definition in both paths.

---

# 14. Feature Transformation Parity

If training applies:

```text
Normalization
Encoding
Bucketing
Aggregation
```

production inference must apply compatible transformations.

---

# 15. Offline Feature Pipeline

A typical offline path:

```text
Historical Events
      ↓
Validated Data
      ↓
Feature Computation
      ↓
Feature Dataset
      ↓
Training / Evaluation
```

---

# 16. Online Feature Pipeline

A typical online path:

```text
Current Events / State
      ↓
Feature Computation
      ↓
Online Feature Store / Cache
      ↓
Inference
```

---

# 17. Hybrid Architecture

A practical architecture can be:

```text
                     Domain Events
                          │
              ┌───────────┴───────────┐
              │                       │
              ▼                       ▼
        Offline Pipeline        Online Pipeline
              │                       │
              ▼                       ▼
        Historical Data        Current Features
              │                       │
              └───────────┬───────────┘
                          ▼
                     ML Models
```

# 18. Feature Freshness

Each online feature should have a defined freshness requirement.

Conceptually:

```text
Feature
+
Maximum Acceptable Age
```

Features may be classified as:

```text
Real-Time
Near Real-Time
Periodic

```

---

# 20. Real-Time Features

Real-time features may require updates within:

```text
Seconds
```

Examples:

```text
Current Driver Location
Current Availability
```

The exact requirement depends on the model.

---

# 21. Near Real-Time Features

Near real-time features may tolerate:

```text
Seconds to Minutes
```

Examples:

```text
Recent Demand
Recent Supply
Recent Acceptance Rate
```

---

# 22. Periodic Features

Periodic features may update:

```text
Minutes
Hours
Daily
```

depending on their use.

---

# 23. Historical Features

Historical features may be relatively stable:

```text
Driver Historical Acceptance Rate
Historical Area Demand
Historical Trip Statistics
```

---

# 24. Static Features

Static or slowly changing features may include:

```text
Vehicle Type
Service Type
Region Configuration
```

These still require versioning when their semantics change.

---

# 25. Feature Freshness Contract

A feature contract should define:

```text
Expected Freshness
Maximum Staleness
Update Frequency
Fallback
```

---

# 26. Stale Feature Handling

When a feature is stale:

```text
Do Not Silently Treat It as Current
```

Possible strategies:

```text
Refresh
Use Last Known Value
Use Default
Use Fallback Model
Reject Prediction
```

The strategy must be defined per feature.

---

# 27. Feature Availability

A model may require:

```text
10 Features
```

but only:

```text
8 Features
```

may be available at runtime.

The serving layer must have a defined response rather than silently producing an invalid prediction.

Online feature values should be validated for:

```text
Type
```

# 31. Feature Range

Examples:

```text
Distance >= 0
Duration >= 0
Count >= 0
Probability ∈ [0,1]
Latitude / Longitude within valid bounds
```

---

# 32. Feature Units

Units must remain consistent.

For example:

```text
Distance → meters
Duration → seconds
```

or another explicitly defined project convention.

Do not mix units between training and serving.

---

# 33. Feature Storage

Possible storage mechanisms include:

```text
Redis
PostgreSQL
Dedicated Feature Store
Object Storage
Analytical Storage
```

The storage technology should be selected based on:

```text
Latency
Freshness
Scale
Cost
Operational Complexity
```

---

# 34. Redis for Online Features

Redis may be appropriate for:

```text
Low-Latency Reads
Short-Lived State
Frequently Updated Features
```

It should not automatically become the authoritative historical source.

---

# 35. PostgreSQL for Features

PostgreSQL may be appropriate for:

```text
Moderate-Scale Historical Features
Reference Data
Curated Aggregations
Feature Metadata
```

Avoid placing heavy analytical workloads on latency-sensitive transactional tables without an appropriate architecture.

---

# 36. Dedicated Feature Store

A dedicated feature store may become useful when RideForge has:

```text
Many Models
Many Shared Features
Large Feature Volume
Complex Online / Offline Synchronization
Strong Feature Governance Requirements
```

Do not introduce one merely because it is common in ML architectures.

---

# 37. Initial Feature Strategy

For the current RideForge stage, prefer:

```text
Simple Feature Definitions
+
Existing Infrastructure
+
Explicit Contracts
+
Controlled Online Storage
```

and evolve only when actual workload requires a dedicated feature platform.

---

# 38. Feature Computation

Features can be computed:

```text
At Write Time
At Read Time
Periodically
From Events
During Dataset Generation
```

The choice depends on:

```text
Freshness
Latency
Cost
Complexity
```

---

# 39. Write-Time Computation

A feature can be updated when an event occurs:

```text
Ride Completed
      ↓
Update Historical Driver Statistics
```

This can reduce read-time computation.

---

# 40. Read-Time Computation

A feature can be calculated when inference occurs:

```text
Current Context
      ↓
Compute Feature
      ↓
Inference
```

This can be useful for simple features.

---

# 41. Periodic Computation

Features can be precomputed:

```text
Every Minute
Every Hour
Every Day
```

depending on freshness requirements.

---

# 42. Event-Driven Computation

Events can trigger feature updates:

```text
Event
 ↓
Feature Processor
 ↓
Updated Feature
```

This is useful for incremental aggregates.

---

# 43. Aggregated Features

Common ML features may be aggregations:

```text
Count
Average
Median
Rate
Percentile
Recent Activity
Rolling Window
```

---

# 44. Rolling Window Features

Examples:

```text
driver_acceptance_rate_7d
ride_requests_last_15m
area_demand_last_1h
```

The window definition must specify:

```text
Start
End
Inclusion Rule
Timezone
```

---

# 45. Window Boundary

Define whether the current event belongs to:

```text
[Start, End)
```

or another explicit interval.

Ambiguous window boundaries can produce inconsistent training and serving values.

---

# 46. Event-Time Windows

For historical data, prefer event-time semantics where appropriate.

This reduces errors caused by:

```text
Late Ingestion
Delayed Processing
```

---

# 47. Late Events

Late events may require feature correction.

The pipeline should define:

```text
Allowed Lateness
Reprocessing
Correction
```

---

# 48. Online Aggregations

Online rolling aggregates should use a reliable update mechanism.

Examples:

```text
Recent Ride Count
Recent Acceptance Count
Recent Cancellation Count
```

---

# 49. Offline Aggregations

Offline aggregation should reconstruct the same logical feature from historical data.

Example:

```text
Online:
Count accepted rides in previous 30 days

Offline:
Count accepted rides in previous 30 days
```

The definition must match.

---

# 50. Training / Serving Skew

Training-serving skew occurs when:

```text
Training Feature
≠
Production Feature
```

This can happen because of:

```text
Different Logic
Different Units
Different Time Windows
Different Missing-Value Rules
Different Data Sources
```

---

# 51. Preventing Skew

Use:

```text
Shared Feature Definitions
+
Explicit Contracts
+
Parity Tests
+
Versioning
```

where practical.

---

# 52. Feature Definition Registry

As feature count grows, maintain a registry or equivalent metadata source containing:


# 53. Feature Ownership

Each important feature should have an identifiable owner:

```text
Domain Team
```

# 55. Feature Versioning

Create a new feature version when the meaning materially changes.

```text
acceptance_rate:v1
```

# 56. Feature Deprecation

A feature may be deprecated when:

```text

```

```text

```

---

# 57. Feature Retirement

Before removing a feature:

```text
Check Model Dependencies
Check Training Pipelines
Check Serving Pipelines
Check Historical Reproducibility
```

---

# 58. Shared Features

Features used by multiple models should have especially clear contracts.

Example:

```text
driver_acceptance_rate_30d
```

may be used by:

```text
Matching
Ranking
Demand / Supply Analysis
```

---

# 59. Feature Reuse

Reuse feature definitions when semantics are identical.

Do not create:

```text
driver_acceptance_rate_a
driver_acceptance_rate_b
```

with identical meaning simply because two models use them.

---

# 60. Feature Duplication

Avoid duplicated computation when:

```text
Same Input
+
Same Definition
+
Same Freshness
```

can be shared.

---

# 61. Feature Isolation

Do not share a feature merely because the names look similar.

For example:

```text
driver_recent_acceptance_rate
```

and:

```text
driver_historical_acceptance_rate
```

may have different:

```text
Window
Freshness
Semantics
```

---

# 62. Feature Dependencies

Complex features may depend on:

```text
Raw Events
Other Features
Aggregations
Reference Data
```

The dependency graph should be known for important features.

---

# 63. Feature Dependency Graph

Conceptually:

```text
Ride Events
    ↓
Completed Ride Count
    ↓
Driver Activity
    ↓
Driver Ranking Feature
```

---

# 64. Feature Computation Failure

If feature computation fails:

```text
Do Not Produce Invalid Values
```

Use:

```text
Fallback
Last Known Value
Default
Prediction Failure
```

according to the feature contract.

---

# 65. Last Known Value

A last-known value can be acceptable for some features.

It is not automatically safe for:

```text
Rapidly Changing Features
```

such as current driver location.

---

# 66. Default Values

Defaults must be semantically meaningful.

Do not use:

```text
0
```

as a universal missing-value replacement.

---

# 67. Missingness as a Feature

In some models, missingness itself may be informative.

If used:

```text
Feature Missing Indicator
```

must be defined consistently across training and serving.

---

# 68. Feature Freshness Monitoring

Monitor:

```text
Age of Feature
```

against:

```text
Maximum Allowed Age
```

---

# 69. Feature Latency

Online feature systems should measure:

```text
P50
P95
P99
```

where appropriate.

Feature latency is part of total inference latency.

---

# 70. Feature Cache Hit Rate

Where caching is used, monitor:

```text
Cache Hit Rate
Cache Miss Rate
Stale Hit Rate
```

---

# 71. Feature Store Availability

If a feature store or cache is unavailable:

```text
AI Consumer
```

must follow the defined fallback path.

---

# 72. Feature Store as a Dependency

Avoid making every AI decision depend on a large number of independent feature services.

Prefer:

```text
Small Number
+
High Reliability
+
Clear Contracts
```

---

# 73. Batch Feature Retrieval

For ranking:

```text
Ride
+
Candidate 1
+
Candidate 2
+
Candidate 3
```

retrieve required features efficiently.

Avoid:

```text
N Candidates
×
N Network Calls
```

when batching is possible.

---

# 74. Feature Materialization

Materialization means:

```text
Compute Feature
      ↓
Store Result
      ↓
Serve Quickly
```

It can reduce online latency at the cost of:

```text
Storage
Freshness Management
Update Complexity
```

---

# 75. Read-Time vs Materialized Trade-Off

Prefer read-time computation when:

```text
Feature Is Cheap
Feature Is Simple
Freshness Is Critical
```

Prefer materialization when:

```text
Feature Is Expensive
Feature Is Frequently Reused
Latency Is Critical
```

---

# 76. Feature Storage TTL

For temporary features, TTL may be used.

TTL should be based on:

```text
Freshness Requirement
```

not simply:

```text
Convenience
```

---

# 77. Feature Invalidation

Invalidate or refresh features when:

```text
Underlying State Changes
Feature Definition Changes
Model Requirements Change
TTL Expires
```

---

# 78. Feature Backfill

When a new feature is introduced:

```text
Historical Data
      ↓
Feature Backfill
      ↓
Training Dataset
```

# 79. Feature Reprocessing

Reprocess historical features when:


---

# 80. Feature Snapshot

Training datasets may use:

```text
Feature Snapshot
```

---

# 81. Offline Feature Snapshot


---

# 82. Online Feature Snapshot

Online systems may not use static snapshots because current features change continuously.

Instead, preserve:

```text
Current Value
Timestamp
Version
```

where necessary.

---

# 83. Feature Time Travel

Historical training may require retrieving:

```text
Feature Value As Of T
```

rather than:

```text
Feature Value Now
```

This is essential for point-in-time correctness.

---

# 84. Point-in-Time Join

A point-in-time join conceptually performs:

```text
Prediction Context at T
+
Feature Value Known at T
```

not:

```text
Prediction Context at T
+
Latest Feature Value
```

# 106. Feature Rollback

If a new feature causes production problems:

```text
Rollback Model
```

to a model compatible with the previous feature set where possible.

# 107. Feature and Model Deployment Ordering

For a new feature/model pair:

```text
1. Introduce Compatible Feature Support
2. Validate Feature
3. Deploy Model
4. Shadow
5. Canary
6. Promote
```

Do not remove old feature support before old models are no longer active.

# 115. Online Feature Failure Matrix

| Failure | Preferred Behaviour |
|---|---|
| Feature Missing | Defined default / fallback |
| Feature Stale | Refresh / controlled fallback |
| Feature Store Timeout | Fallback |
| Invalid Feature | Reject / fallback |
| Version Mismatch | Reject activation / fallback |

| Source Unavailable | Deterministic fallback |

The exact action is feature-specific.

# 126. AI Agent Implementation Rules

When implementing online/offline features, an AI coding agent must:

1. Define the feature semantics before implementing storage.
2. Define entity, type, unit, and timestamp semantics.
3. Preserve point-in-time correctness.
4. Keep training and serving definitions semantically aligned.
5. Define freshness requirements for online features.
6. Validate feature values before inference.
7. Handle missing and stale features explicitly.
8. Version material feature-definition changes.
9. Test online/offline parity.
10. Avoid unnecessary feature-store infrastructure.
11. Reuse existing Redis, PostgreSQL, and event infrastructure where appropriate.
12. Keep domain systems authoritative for operational state.
13. Add feature observability.
14. Protect sensitive feature data.
15. Test feature failure and fallback behaviour.
16. Update the relevant AI documentation.

---

# 127. AI Agent Prohibited Patterns

AI agents must not:

- use future data in historical features,
- calculate different meanings for the same feature online and offline,
- silently mix units,
- use current values when historical point-in-time values are required,
- treat stale data as fresh without an explicit contract,
- use `0` as a universal missing-value replacement,
- make Redis the historical source merely because it is fast,
- introduce a dedicated feature store without demonstrated need,
- duplicate existing domain logic unnecessarily,
- silently change a feature definition under the same version,
- remove old feature support while dependent models are still active,
- expose unnecessary sensitive feature data,
- allow feature failure to become an uncontrolled production failure.

# 133. Final Principle

> **RideForge should maintain one semantic definition for each important feature while allowing different physical paths for historical training and low-latency production inference.**

The desired feature lifecycle is:

```text
Correct Definition
      ↓
Historical Correctness
      ↓
Online Freshness
      ↓
Serving Consistency
      ↓
Monitoring
      ↓
Controlled Evolution
```

The goal is not to build a feature platform prematurely.

The goal is to ensure that every production model receives **the right feature, at the right time, with the right meaning, at the right freshness, and with a safe fallback when the feature is unavailable.**
