# 1. Purpose

This document defines how RideForge AI systems should be made:

```text
Fast
Reliable
Scalable
Cost-Efficient
Predictable
```

without sacrificing:

```text
Correctness
Safety
Observability
Maintainability
```

The objective is not to make every AI component as fast or cheap as possible.

The objective is:

> **Achieve the required business and operational outcome at the lowest sustainable system cost while preserving required quality and safety.**

---

# 2. Core Principle

> **Optimize the complete AI path, not only model inference.**

The actual online path may be:

```text
Request
 ↓
Feature Retrieval
 ↓
Preprocessing
 ↓
Model Inference
 ↓
Output Validation
 ↓
Decision Logic
 ↓
Domain Execution
```

A faster model does not help if:

```text
Feature Retrieval
```

is the dominant latency.

---

# 3. Optimization Priorities

Optimization should normally follow:

```text
1. Correctness
2. Safety
3. Reliability
4. Required Latency
5. Throughput
6. Resource Efficiency
7. Cost
```

Do not trade a critical safety or correctness requirement for a small cost reduction.

```text
+
```

rather than only model inference.

# 14. Feature Retrieval Optimization

Feature retrieval can become the largest component of online latency.

Optimize:

```text
Number of Reads
Read Size
Network Round Trips
Serialization
Cache Hit Rate
Feature Computation
```

---

# 15. Minimize Network Round Trips

Prefer:

```text
One Efficient Retrieval
```

over:

```text
Many Sequential Requests
```

when the feature access pattern permits it.

---

# 16. Parallel Feature Retrieval

Independent feature sources may be retrieved concurrently.

Conceptually:

```text
                Request
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
     Feature A  Feature B  Feature C
        │          │          │
        └──────────┼──────────┘
                   ▼
               Inference
```

Use concurrency carefully to avoid overwhelming dependencies.

---

# 17. Feature Caching

Cache frequently accessed features when:

```text
Freshness Requirements
```

allow it.

Potential candidates:

```text
Driver State
Area Statistics
Recent Demand
Recent Supply
Static Geographic Data
```

---

# 18. Cache Trade-Off

Caching improves:

```text
Latency
Database Load
Network Load
```

but introduces:

```text
Staleness
Memory Cost
Invalidation Complexity
```

Use only where the trade-off is justified.

---

# 19. Redis Optimization

Where Redis is used for online AI state:

```text
Minimize Round Trips
Use Efficient Keys
Avoid Excessive Payloads
Set Appropriate TTLs
Use Batching Where Useful
```

Do not use Redis as a replacement for authoritative domain storage.

---

# 20. PostgreSQL Optimization

AI workloads that depend on PostgreSQL should consider:

```text
Indexes
Query Plans
Connection Pooling
Batch Reads
Projection of Required Columns
```

Avoid loading entire domain records when only a few fields are needed.

---

# 21. Avoid N+1 Feature Retrieval

Do not perform:

```text
Candidate 1 → Database
Candidate 2 → Database
Candidate 3 → Database
...
```

when the same data can be retrieved efficiently in a batch.

---

```text
        ↓
Retrieve Features
        ↓
```

# 32. Precomputation

Precompute expensive values when:

```text
Input Changes Slowly
```

or:

```text
The Same Calculation Is Reused Frequently
```

Examples:

```text
Area-Level Statistics
Historical Features
Geographic Features
Forecast Inputs
```

---

# 33. Avoid Recomputing Stable Features

If a feature is expensive and changes infrequently:

```text
Compute Once
Store
Reuse
```

subject to freshness requirements.


# 35. Model Loading

Prefer:


when the serving runtime supports it safely.

# 114. AI Agent Implementation Rules

When implementing AI performance and cost optimization, an AI coding agent must:

1. Measure a baseline before significant optimization.
2. Optimize end-to-end latency rather than only model execution.
3. Preserve correctness and safety constraints.
4. Avoid unnecessary feature retrieval.
5. Prefer efficient batch retrieval where appropriate.
6. Use caching only when freshness requirements permit it.
7. Bound concurrency and queues.
8. Use explicit timeouts for online inference.
9. Prevent uncontrolled retries.
10. Evaluate model accuracy together with latency and cost.
11. Keep deterministic fallbacks available.
12. Avoid unnecessary telemetry payloads.
13. Monitor resource utilization.
14. Validate optimization with benchmarks.
15. Document important performance trade-offs.
16. Update the relevant AI documentation.

---

# 115. AI Agent Prohibited Patterns

AI agents must not:

- optimize latency by removing required safety checks,
- remove validation to reduce compute,
- increase model complexity without measurable value,
- cache predictions across incompatible operational states,
- introduce unbounded queues,
- introduce unbounded retries,
- store large raw payloads without justification,
- increase telemetry cardinality unnecessarily,
- choose a model solely because it has higher accuracy,
- choose infrastructure solely because it is cheaper,
- remove fallback paths to reduce resource usage,
- perform large optimization changes without benchmarking,
- use production traffic as an uncontrolled performance experiment.

# 121. Final Principle

> **RideForge should optimize AI systems around the complete quality–latency–reliability–cost trade-off, not around a single benchmark.**

The desired loop is:

```text
Measure
  ↓
Understand
  ↓
Optimize
  ↓
Validate
  ↓
Deploy
  ↓
Observe
  ↓
Optimize Again
```

A successful optimization should produce:

```text
Required Quality
+
Required Safety
+
Required Reliability
+
Acceptable Latency
+
Sustainable Cost
```

without turning performance optimization into:

```text
Premature Complexity
Unsafe Shortcuts
Unbounded Infrastructure
Uncontrolled Cost
```
