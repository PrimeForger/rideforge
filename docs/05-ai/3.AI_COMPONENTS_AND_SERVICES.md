# 1. Purpose

This document defines the logical AI components and services that make up the RideForge intelligence layer.

It answers:

```text
What AI components exist?
What does each component own?
What does each component consume?
What does each component produce?
How do components communicate?
Which components should remain logical boundaries?
Which components may become deployable services later?
```

The document does not require every logical component to become an independent microservice.

---

# 2. Component Design Principle

The AI layer should follow:

```text
Clear Responsibility
+
Explicit Interfaces
+
Minimal Coupling
+
Independent Evolution
+
Safe Fallback
```

The architecture should avoid creating services merely because a capability has a different name.

---

# 3. Logical vs Deployable Components

A logical AI component represents a responsibility.

A deployable service represents an operational boundary.

These are not the same thing.

For example:

```text
ETA Prediction
Demand Prediction
Ranking
```

may initially exist inside one AI runtime while remaining logically separated.

Later they may become independently deployable if scaling, ownership, runtime, or operational requirements justify it.

# 6. AI Integration Boundary

The AI Integration Boundary is the controlled interface between core RideForge services and AI capabilities.

It is responsible for:

```text
Request Translation
Input Validation
Feature Resolution
AI Invocation
Output Validation
Fallback Selection
Correlation Propagation
```

It should prevent core business logic from depending directly on model implementation details.

---

# 7. Integration Boundary Responsibilities

The integration boundary should answer:

```text
Which AI capability is being requested?
What inputs are required?
Which model/version should be used?
How long may inference take?
What happens when inference fails?
How is the result returned?
```

---

# 8. Integration Boundary Does Not Own

It should not own:

```text
Ride State
Driver State
Reservation State
Payment State
Regulatory Rules
Core Business Transactions
```

Those remain owned by the core application domains.

---

# 9. Feature and Signal Layer

The Feature / Signal Layer converts operational state and events into inputs usable by AI capabilities.

Conceptually:

```text
Operational State
+
Events
+
Historical Data
        ↓
Feature / Signal Processing
        ↓
AI Features
```

---

# 10. Feature Layer Responsibilities

The feature layer may provide:

```text
Temporal Features
Spatial Features
Driver Features
Ride Features
Demand Features
Supply Features
Historical Features
Operational Features
```

It should expose stable feature semantics to prediction components.

---

# 11. Feature Layer Does Not Own

The feature layer does not own:

```text
Model Training
Model Deployment
Ride Assignment
Reservation
Business Authorization
```

Its responsibility ends at producing valid model inputs.

---

# 12. Feature Freshness

Features should have explicit freshness expectations.

Example:

```text
Driver Location
→ Near Real-Time

Current Availability
→ Near Real-Time

Historical Completion Rate
→ Periodic / Rolling

Demand Statistics
→ Aggregated / Time-Based
```

The consuming model must know whether stale data is acceptable.

# 22. Matching Intelligence Component

The Matching Intelligence Component provides intelligence for evaluating potential driver-ride assignments.

Its role is:

```text
Candidate Information
        ↓
Matching Signals
        ↓
Candidate Evaluation
        ↓
Matching Score / Recommendation
```

---

# 23. Matching Does Not Own Reservation

Matching intelligence must not be confused with reservation.

```text
Matching:
"Driver A is the preferred candidate."

Reservation:
"Driver A has been successfully reserved."
```

Reservation remains authoritative core application behaviour.


```text

      ↓
```


# 29. Stand Dispatch Relationship

Stand Dispatch remains an independent dispatch strategy.

AI components should not make Stand Dispatch dependent on AI.

The platform can therefore support:

```text
Stand Dispatch
```

and:

```text
Smart Dispatch
```

as separate strategies.

---

# 30. Hybrid Strategy Component

A strategy-selection layer may determine which dispatch approach applies.

Conceptually:

```text
Ride Request
      ↓
Operating Context
      ↓
Strategy Selection
      ├── Stand Dispatch
      └── Smart Dispatch
```

The selection policy remains a core application decision.

AI can provide signals to Smart Dispatch without owning the overall policy.

# 32. Inference Runtime Boundary



# 33. Inference Isolation

# 52. Component Communication

AI components should communicate through explicit contracts.

Communication may use:

```text
Synchronous Request / Response
Asynchronous Events
Batch Data
```

The choice depends on latency and consistency requirements.

---

# 53. Synchronous AI Communication

Use synchronous communication when the prediction is required immediately.

Examples:

```text
ETA Request
Ranking Request
Real-Time Dispatch Score
```

Such calls require:

```text
Timeout
Fallback
Output Validation
```

---

# 54. Asynchronous AI Communication

Use asynchronous communication for workflows that do not require immediate inference.

Examples:

```text
Dataset Processing
Feedback Collection
Model Evaluation
Training
Forecast Generation
```

Kafka / Redpanda can support relevant event-driven workflows.

---

# 55. Batch AI Components

Batch processing is appropriate for:

```text
Historical Feature Generation
Demand Forecasting
Dataset Preparation
Model Training
Periodic Evaluation
```

Batch components should not block real-time ride workflows.

---

Model-specific preprocessing and postprocessing should remain close to the model capability rather than leaking into core business logic.

```text

Ranking Model
→ Ranking-specific feature transformation
```

---

# 61. AI and Core Domain Models

AI-specific representations should not unnecessarily replace core domain entities.

For example:

```text
Ride Domain Model
```

remains the core representation of a ride.

An AI model may consume a:

```text
Ride Feature Vector
```

derived from the domain state.

---

# 62. AI and Driver State

The core platform owns driver state.

AI may consume:

```text
Availability
Location
Historical Signals
```

but must not independently declare:

```text
Driver Available
```

as authoritative platform state.

---

# 63. AI and Ride State

The core platform owns ride lifecycle state.

AI may predict:

```text
ETA
Cancellation Probability
Match Quality
```

but should not directly transition:

```text
REQUESTED → MATCHED
```

without the appropriate core application workflow.

---

# 64. AI and Reservation

Reservation is an authoritative transactional operation.

The AI architecture must preserve:

```text
Candidate Recommendation
        ≠
Reservation Success
```

A recommendation can become invalid between inference and reservation.

---

AI components consuming RideForge events should depend on stable event contracts.

# 87. AI Agent Component Rules

An AI coding agent must:

1. Determine whether an existing AI component already owns the requested capability.
2. Reuse existing component boundaries.
3. Avoid introducing duplicate services.
4. Keep model-specific logic inside the appropriate AI boundary.
5. Keep transactional logic inside core application domains.
6. Preserve explicit input/output contracts.
7. Validate model outputs.
8. Implement defined fallback behaviour.
9. Add appropriate tests.
10. Update the appropriate AI documentation.
11. Avoid turning every logical component into a microservice.
12. Verify the final architecture remains understandable.

---

# 88. AI Agent Prohibited Patterns

AI agents must not:

- create duplicate ETA, ranking, matching, or dispatch components,
- move reservation ownership into AI,
- allow models to bypass eligibility,
- create a microservice for every model,
- introduce infrastructure without an operational need,
- expose internal model objects as public business contracts,
- silently change existing AI contracts,
- remove fallback paths,
- invent model capabilities,
- claim an AI component is production-ready without the required validation.

---

Before approving a new AI component:

```text

[ ] Fallback is defined
```

# 91. Final Principle

> **RideForge AI components should be separated by responsibility, not by fashion.**

The architecture should remain:

```text
Simple Enough to Operate
+
Explicit Enough to Understand
+
Independent Enough to Evolve
+
Safe Enough to Trust
```

The immediate goal is not to create a large AI platform.

The immediate goal is to establish clean AI boundaries that allow RideForge to progressively introduce:

```text
Prediction
Ranking
Matching
Forecasting
Optimization
```

while keeping the core ride-hailing platform:

```text
Transactional
Deterministic
Observable
Resilient
```

and fully capable of operating safely when AI is unavailable.
