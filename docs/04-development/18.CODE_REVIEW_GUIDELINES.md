# 1. Purpose

Code review is a quality and engineering-control mechanism.

A review should verify that a change is:

```text
Correct
+
Understandable
+
Tested
+
Architecturally Consistent
+
Operationally Safe
+
Secure
+
Maintainable
```

Code review is not merely a style inspection.

---

# 2. Review Principle

Review the change in this order:

```text
Intent
 ↓
Correctness
 ↓
Architecture
 ↓
Data / State
 ↓
Failure Behaviour
 ↓
Testing
 ↓
Security
 ↓
Performance
 ↓
Observability
 ↓
Maintainability
 ↓
Style
```

Do not spend most of the review discussing formatting while a correctness problem remains unresolved.

---

# 3. Reviewer Responsibility

A reviewer is responsible for identifying problems that could materially affect:

```text
Users
Business Rules
Data Integrity
Availability
Security
Performance
Operations
Maintainability
```

The reviewer is not expected to redesign unrelated parts of the system during every review.

---

# 4. Author Responsibility

The author should provide a change that is:

```text
Focused
Tested
Documented where required
Reviewable
```

The author should not rely on reviewers to discover basic:

```text
Compilation Errors
Formatting Problems
Obvious Test Failures
Missing Required Files
```

---

# 5. Pull Request Scope

A pull request should have a clear purpose.

Prefer:

```text
One Feature
One Fix
One Refactor
One Operational Change
```

or a small set of tightly coupled changes.

---

# 6. Pull Request Description

The PR description should explain, where applicable:

```text
What Changed?
Why?
How Was It Tested?
Database Changes?
API Changes?
Event Changes?
Configuration Changes?
Operational Impact?
```

---

# 7. Review the Diff, Not Just the Description

The reviewer must inspect the actual code diff.

Do not approve a change solely because:

```text
Description Looks Correct
Tests Are Green
```

The implementation itself must be understood.

---

# 8. Start With the Change Boundary

Before reviewing individual lines, determine:

```text
Which Components Changed?
Which Dependencies Changed?
Which Data Changed?
Which Contracts Changed?
Which Runtime Behaviour Changed?
```

This establishes the review scope.

---

# 9. Understand the Existing Architecture

Reviewers should use the architecture documentation to understand intended boundaries.

Important questions:

```text
Does the change belong in this component?
Does it preserve service boundaries?
Does it bypass an established abstraction?
Does it introduce a new dependency?
Does it duplicate existing functionality?
```

---

# 10. Architecture Consistency

A change should fit the existing architecture.

Avoid unnecessary introduction of:

```text
New Communication Pattern
New Infrastructure
New Persistence Mechanism
New Abstraction Layer
New Framework
```

when an existing architectural mechanism already solves the problem.

---

# 11. Domain Boundaries

Business rules should remain in appropriate domain/application boundaries.

A reviewer should question business logic placed arbitrarily inside:

```text
HTTP Handler
Repository
Infrastructure Adapter
Serialization Layer
```

when it belongs in the application/domain layer.

---

# 12. Dependency Direction

Review dependencies for unwanted coupling.

A component should not bypass established boundaries merely because direct access is convenient.

For example:

```text
Handler
 ↓
Repository
```

may be questionable if the architecture requires:

```text
Handler
 ↓
Application Service
 ↓
Repository
```

---

# 13. Application Services

Application services should coordinate use cases rather than becoming uncontrolled containers for unrelated logic.

Review for:

```text
Clear Responsibility
Transaction Boundaries
Dependency Usage
Error Mapping
Business Rule Placement
```

---

# 14. Repository Review

Repositories should focus on persistence concerns.

Review:

```text
Query Correctness
Transaction Behaviour
Error Handling
Resource Cleanup
Performance
```

Do not allow repositories to silently implement unrelated business policies.

---

# 15. Go Code Correctness

For Go changes, verify:

```text
Types
Error Handling
Context Usage
Goroutine Lifecycle
Channel Behaviour
Resource Cleanup
Nil Handling
Concurrency
```

---

# 16. Context Propagation

Long-running or dependency-bound operations should use context appropriately.

Review whether:

```text
Request Cancellation
Timeouts
Shutdown
```

are propagated through relevant operations.

---

# 17. Error Handling

Errors should be:

```text
Classified
Wrapped with Useful Context
Mapped Appropriately
```

Review for:

```text
Ignored Errors
Incorrect Error Translation
Lost Context
Incorrect HTTP Mapping
Incorrect Retry Behaviour
```

Follow:

```text
11.ERROR_HANDLING_AND_VALIDATION.md
```

for detailed rules.

---

# 18. Error Ownership

Avoid duplicate logging and handling of the same error at every layer.

Review:

```text
Who Creates the Error?
Who Adds Context?
Who Decides Operational Severity?
Who Maps It to an External Response?
```

---

# 19. Validation

Validate inputs at the correct boundary.

Review:

```text
Required Fields
Value Ranges
State Rules
Business Constraints
Authorization
```

Do not rely solely on client-side validation.

---

# 20. Business Invariants

The reviewer should explicitly ask:

```text
What invariant does this operation need to preserve?
```

For RideForge examples:

```text
Ride State Validity
Driver Availability
Reservation Exclusivity
Region Restrictions
Event Idempotency
```

A change that can violate an invariant should not be approved without a deliberate design.

---

# 21. Concurrency Review

Concurrency-sensitive code requires additional scrutiny.

Review:

```text
Shared State
Locks
Atomic Operations
Channels
Goroutines
Database Transactions
Redis Operations
Race Conditions
```

---

# 22. Goroutine Lifecycle

Every background goroutine should have:

```text
Owner
Purpose
Cancellation
Shutdown Behaviour
Error Handling
```

Question code that starts goroutines without a clear lifecycle.

---

# 23. Channel Safety

Review:

```text
Who Writes?
Who Reads?
Who Closes?
Can It Block?
Can It Leak?
```

Do not close channels from a component that does not own their lifecycle.

---

# 24. Race Conditions

Concurrency changes should be tested appropriately.

Where relevant:

```bash
go test -race ./...
```

A reviewer should request race testing when the change materially affects shared concurrent state.

---

# 25. Database Review

Database changes should be reviewed for:

```text
Correctness
Transactions
Indexes
Constraints
Locks
Query Performance
Migration Safety
```

---

# 26. Query Review

Review database queries for:

```text
Correct Filters
Correct Joins
Correct Ordering
Pagination
N+1 Patterns
Unnecessary Columns
Index Compatibility
```

---

# 27. Transaction Review

Ask:

```text
What must be atomic?
What is inside the transaction?
What is intentionally outside it?
How long can the transaction remain open?
```

Do not hold transactions across slow external operations unless explicitly required.

---

# 28. Migration Review

Every migration should be reviewed independently from the application code.

Check:

```text
Existing Data
Compatibility
Locking
Performance
Rollback / Recovery
Deployment Order
```

Follow:

```text
16.MIGRATIONS_AND_SCHEMA_CHANGES.md
```

---

# 29. Destructive Schema Changes

Changes involving:

```text
DROP
DELETE
Rename
Required Constraints
Type Conversion
```

require additional review.

Ask:

```text
Can old application versions coexist?
Can existing data survive?
How is recovery handled?
```

---

# 30. Index Review

For new indexes, review:

```text
Query Being Optimized
Selectivity
Write Cost
Storage
Existing Indexes
```

Do not approve indexes based only on column popularity.

---

# 31. Redis Review

Redis changes should be reviewed for:

```text
Key Design
TTL
Atomicity
Round Trips
Memory Usage
Failure Behaviour
Concurrency
```

---

# 32. Redis as Operational State

When Redis represents operational state, verify that the change does not accidentally make Redis the authoritative source for data that should remain authoritative elsewhere.

---

# 33. Driver Location Review

For driver-location changes, review:

```text
H3 Calculation
Cell Membership
Stale State
TTL
Availability
Candidate Discovery
```

Avoid unnecessary exact-coordinate storage or logging.

---

# 34. Redis Atomicity

If multiple Redis operations must behave atomically, the implementation should use an appropriate atomic mechanism.

Review whether:

```text
Separate Commands
```

can introduce a race.

---

# 35. Messaging Review

Event-driven changes require review of both producer and consumer behaviour.

Check:

```text
Event Contract
Serialization
Event Version
Idempotency
Retries
DLQ
Ordering
Correlation
```

---

# 36. Producer Changes

When changing an event producer, determine:

```text
Which Consumers Read This Event?
Is the New Payload Compatible?
Does Event Versioning Apply?
Can Old Consumers Continue?
```

---

# 37. Consumer Changes

When changing a consumer, review:

```text
Failure Handling
Retry Behaviour
Idempotency
Acknowledgement
Transaction Boundaries
DLQ Behaviour
```

---

# 38. Event Compatibility

Do not silently introduce incompatible event changes.

If compatibility is required:

```text
Old Consumer
+
New Consumer
+
New Event
```

must coexist safely during the transition.

---

# 39. Outbox Review

Changes to the outbox workflow should verify:

```text
Database Transaction
Outbox Record Creation
Publication
Retry
Duplicate Handling
```

The review should ensure the change does not create an event/data consistency gap.

---

# 40. DLQ Review

DLQ behaviour should remain intentional.

Review:

```text
What Causes DLQ?
How Many Retries?
What Metadata Is Preserved?
How Is Recovery Performed?
```

---

# 41. API Review

API changes should be reviewed for:

```text
Contract
Validation
Authorization
Error Responses
Status Codes
Pagination
Performance
Compatibility
```

---

# 42. HTTP Handler Review

Handlers should generally:

```text
Parse
Validate Boundary Input
Call Application Service
Map Result
Return Response
```

Avoid placing large business workflows directly in handlers.

---

# 43. API Error Review

Ensure internal errors are not accidentally exposed.

External responses should contain safe:

```text
Error Code
Message
Request / Trace Correlation
```

where supported.

Do not expose:

```text
Stack Traces
SQL Errors
Credentials
Internal Paths
Sensitive Dependency Details
```

---

# 44. API Compatibility

Before changing an existing API, determine:

```text
Existing Clients
Response Consumers
Required Fields
Optional Fields
Status Codes
```

Breaking changes require explicit planning.

---

# 45. Configuration Review

Configuration changes should be checked for:

```text
Required Variables
Defaults
Validation
Environment Separation
Secret Handling
Backward Compatibility
```

---

# 46. Secrets

Reviewers must actively check that a PR does not introduce:

```text
Passwords
Tokens
API Keys
Private Keys
Connection Secrets
Production Credentials
```

into:

```text
Source Code
Tests
Logs
Configuration
Documentation
```

---

# 47. Logging Review

Review logs for:

```text
Useful Context
Correct Level
No Sensitive Data
No Duplicate Errors
Bounded Volume
Correlation
```

Follow:

```text
12.LOGGING_AND_DEBUGGING.md
```

---

# 48. Observability Review

When telemetry changes, check:

```text
Metric Type
Label Cardinality
Trace Propagation
Sensitive Attributes
Performance Overhead
Alert Impact
```

Avoid:

```text
Metric Per Ride
Metric Per Driver
Metric Per Request
```

as unbounded labels.

---

# 49. Performance Review

Every significant performance-sensitive change should answer:

```text
What Was Slow?
What Changed?
How Was It Measured?
What Is the New Result?
```

Do not accept complexity justified only by:

```text
"It should be faster."
```

---

# 50. Hot Path Review

Pay extra attention to:

```text
Driver Location Updates
Candidate Discovery
Ranking
Reservation
High-Volume APIs
Event Consumers
```

Avoid unnecessary:

```text
Allocations
Logs
Network Calls
Database Queries
Serialization
```

---

# 51. Retry Review

Retries can amplify failures.

Check:

```text
Maximum Attempts
Backoff
Timeout Budget
Idempotency
Dependency Capacity
```

A retry should not cause a larger outage than the original failure.

---

# 52. Caching Review

A cache change must explain:

```text
What Is Cached?
Why?
TTL?
Invalidation?
Stale Data Behaviour?
Failure Behaviour?
Memory Bound?
```

Do not approve a cache without a clear consistency model.

---

# 53. Security Review

Security review should cover:

```text
Authentication
Authorization
Input Validation
Secret Handling
Data Exposure
Dependency Security
Injection Risks
```

---

# 54. Authorization Review

For every protected operation ask:

```text
Who Can Perform It?
Which Resource Are They Allowed to Access?
Is Authorization Enforced Server-Side?
```

Do not rely on client-side restrictions.

---

# 55. Data Exposure

Review:

```text
API Responses
Logs
Events
Database Queries
Telemetry
```

for unnecessary sensitive data.

---

# 56. Dependency Review

New dependencies should have a clear reason.

Review:

```text
Functionality
Maintenance
License
Security
Size
Performance
Operational Impact
```

Do not add a dependency for a small utility that can safely be implemented with the standard library or existing project dependencies.

---

# 57. Testing Review

A PR should include appropriate tests for the change.

Review:

```text
Happy Path
Failure Path
Boundary Conditions
Regression Case
Integration Behaviour
```

as applicable.

---

# 58. Test Quality

Tests should verify behaviour rather than implementation details whenever practical.

Prefer:

```text
Expected Outcome
```

over:

```text
Exact Internal Call Sequence
```

unless the interaction itself is the contract.

---

# 59. Missing Tests

Ask:

```text
What can break if this code changes?
```

If the answer identifies a meaningful regression risk and no test protects it, request appropriate coverage.

---

# 60. Integration Tests

Use integration tests when correctness depends on:

```text
PostgreSQL
Redis
Kafka / Redpanda
Transactions
Concurrency
Serialization
```

Do not replace all integration tests with mocks.

---

# 61. Migration Tests

Schema changes should test:

```text
Fresh Database
Existing Representative Data
Application Compatibility
```

where applicable.

---

# 62. Event Tests

Event changes should test:

```text
Serialization
Deserialization
Consumer Behaviour
Failure Handling
Idempotency
```

where relevant.

---

# 63. Dispatch Tests

Dispatch changes should cover meaningful scenarios such as:

```text
No Candidate
One Candidate
Multiple Candidates
Ineligible Candidate
Reservation Conflict
Unavailable Driver
```

according to the implemented strategy.

---

# 64. Region Rule Tests

Changes affecting ride-region validation should include explicit tests for:

```text
Allowed Region
Disallowed Region
Boundary / Edge Cases
```

where applicable.

---

# 65. Code Readability

A reviewer should be able to understand the change without reconstructing the author's intent from every line.

Prefer:

```text
Clear Names
Small Focused Functions
Explicit Control Flow
Simple Abstractions
```

---

# 66. Complexity

Question code that introduces unnecessary:

```text
Abstractions
Interfaces
Generics
Reflection
Concurrency
Caching
Distributed Coordination
```

Complexity must solve a real problem.

---

# 67. Abstraction Review

Before accepting a new interface or abstraction, ask:

```text
What variation does it support?
Who needs the abstraction?
Does it improve testing or architecture?
Is the abstraction stable?
```

Avoid speculative abstraction.

---

# 68. Duplication

Not every repeated line requires immediate abstraction.

Review duplication in context:

```text
Accidental Duplication
→ Consider Refactor

Intentional Similarity
→ May Be Acceptable
```

Do not create a complicated abstraction merely to remove a few repeated lines.

---

# 69. Comments

Comments should explain:

```text
Why
```

rather than merely repeating:

```text
What
```

Good comments explain:

```text
Non-Obvious Constraint
Concurrency Requirement
External Limitation
Business Reason
Performance Trade-Off
```

---

# 70. TODOs

A TODO should have a clear reason and, where practical:

```text
Owner
Issue / Tracking Reference
Expected Follow-Up
```

Do not introduce vague TODOs that permanently remain in the codebase.

---

# 71. Generated Code

Review generated code according to its source.

The important question is:

```text
Is the generator input correct?
```

Do not manually patch generated output unless the repository explicitly requires it.

---

# 72. Documentation Review

If behaviour changes, verify that relevant documentation remains accurate.

Potential documentation includes:

```text
Architecture
API
Configuration
Development
Migration
ADR
Operations
```

Do not add duplicate documentation when an existing document already owns the topic.

---

# 73. Review Comments

Review comments should be:

```text
Specific
Actionable
Respectful
Relevant
```

Prefer:

```text
"This can race with reservation. Can we make the state transition atomic here?"
```

over:

```text
"This is wrong."
```

---

# 74. Blocking vs Non-Blocking Comments

Distinguish between:

```text
Blocking
```

and:

```text
Suggestion
```

A blocking comment should identify a real issue that must be resolved before integration.

---

# 75. Review Priority

Prioritize findings roughly as:

```text
Critical
High
Medium
Low
Suggestion
```

The repository may use different labels, but severity should be clear.

---

# 76. Critical Findings

Examples:

```text
Data Loss
Security Vulnerability
Broken Production Invariant
Corruption Risk
Unrecoverable Failure
```

These should block approval.

---

# 77. High-Severity Findings

Examples:

```text
Incorrect Business Logic
Race Condition
Broken Event Contract
Unsafe Migration
Major Production Failure
```

These normally block approval.

---

# 78. Medium-Severity Findings

Examples:

```text
Missing Important Test
Significant Maintainability Problem
Unbounded Resource Usage
Incorrect Error Mapping
```

Address before integration unless explicitly accepted.

---

# 79. Low-Severity Findings

Examples:

```text
Minor Readability Issue
Naming Improvement
Small Documentation Gap
```

These should not distract from important correctness issues.

---

# 80. Suggestions

Suggestions can improve:

```text
Clarity
Simplicity
Maintainability
Developer Experience
```

They should not be presented as blocking requirements unless they actually are.

# 89. Approval Criteria

A reviewer should approve when:

```text
Correctness Is Established
+
Risks Are Acceptable
+
Tests Are Adequate
+
Architecture Is Consistent
+
Operational Impact Is Understood
```

Approval does not mean the code is perfect.

It means the change meets the project's required engineering standard.

---

# 90. Request Changes Criteria

Request changes when the PR contains a meaningful unresolved problem involving:

```text
Correctness
Security
Data Integrity
Architecture
Compatibility
Testing
Operational Safety
```

Do not block a PR for personal preference alone.

---

# 91. Re-Review

After requested changes:

```text
Review Updated Diff
+
Review New Behaviour
```

Do not assume a small change cannot affect another part of the PR.

---

# 92. Review After Conflict Resolution

When a branch resolves merge conflicts, review the resulting diff again.

Conflict resolution can accidentally:

```text
Delete Logic
Duplicate Logic
Change Ordering
Break Tests
Alter Migrations
```

---

# 93. Review Generated Diffs Carefully

Generated files can create large diffs.

Review:

```text
Source Change
+
Generated Result
```

rather than approving a large generated diff blindly.

---

# 94. Review Dependencies Carefully

A dependency update may change more than one package.

Review the complete dependency diff when available.

Check for:

```text
Breaking Changes
Security Changes
Transitive Updates
Build Changes
```

---

# 95. Review Configuration Changes Carefully

Configuration changes can affect production even when source code changes are small.

Review:

```text
Default Values
Environment Variables
Timeouts
Pool Sizes
Feature Flags
Broker Settings
```

---

# 96. Review Feature Flags

A feature flag should have:

```text
Defined Meaning
Safe Default
Controlled Scope
Removal Plan
```

Avoid permanent feature flags without ownership.

---

# 97. Review Operational Changes

Changes to:

```text
Docker
Deployment
Health Checks
Telemetry
Migrations
Broker Configuration
```

should be reviewed for production impact, not only code correctness.

---

# 98. AI-Assisted Code Review

AI-generated code must receive the same review standard as manually written code.

The reviewer should not assume:

```text
AI Generated
=
Correct
```

or:

```text
AI Generated
=
Incorrect
```

Review the actual implementation.

---

# 99. AI Agent Review Rules

Before asking for or performing review, an AI agent should:

1. Inspect the complete diff.
2. Understand the intended change.
3. Identify affected architecture boundaries.
4. Inspect related existing code.
5. Check correctness first.
6. Check business invariants.
7. Check database and transaction behaviour.
8. Check Redis behaviour.
9. Check messaging compatibility.
10. Check API compatibility.
11. Check error handling.
12. Check tests.
13. Check security.
14. Check observability.
15. Check performance.
16. Check documentation.
17. Report only findings supported by the code.

---

# 100. AI Agent Review Prohibitions

AI agents must not:

- approve code without inspecting the actual diff,
- invent bugs unsupported by the implementation,
- invent tests that were not run,
- claim CI passed without evidence,
- treat style preferences as correctness failures,
- ignore existing architecture,
- recommend replacing established components without justification,
- overlook migrations when schema changes exist,
- overlook consumers when event contracts change,
- overlook authorization when protected operations change,
- overlook concurrency in stateful workflows,
- approve secrets in code or configuration,
- rewrite unrelated code merely to make the review cleaner.

# 102. Final Code Review Principle

> **A good RideForge code review protects correctness and production safety while keeping the codebase simple, understandable, and consistent with its architecture.**

The intended review flow is:

```text
Understand Intent
        ↓
Inspect Diff
        ↓
Check Correctness
        ↓
Check Architecture
        ↓
Check Data / State
        ↓
Check Failure Behaviour
        ↓
Check Tests
        ↓
Check Security
        ↓
Check Performance
        ↓
Check Observability
        ↓
Check Maintainability
        ↓
Approve / Request Changes
```

The reviewer should continuously ask:

```text
Does this change do what it claims?

Does it preserve RideForge's business invariants?

Does it fit the existing architecture?

What happens when dependencies fail?

What happens under concurrency?

What happens during deployment?

What happens to existing data?

What happens to old consumers or clients?

Can operators diagnose a failure?

Can another developer maintain this code?
```

Approval should be based on those engineering questions rather than personal coding style.
