# 1. Purpose

Logging and debugging must make RideForge failures and behaviour understandable without creating excessive noise, leaking sensitive information, or turning logs into an unofficial database.

The logging strategy must provide:

```text
Useful Context
+
Consistent Structure
+
Safe Diagnostic Information
+
Request Correlation
+
Distributed Traceability
+
Controlled Volume
```

---

# 2. Logging Principle

Logs should answer:

```text
What happened?
Where did it happen?
Which operation was involved?
What was the outcome?
Why did it fail?
Can the event be correlated with another component?
```

Do not log information merely because it is available.

---

# 3. Structured Logging

Production logs should be structured rather than relying primarily on free-form text.

Conceptually:

```text
Timestamp
Level
Message
Component
Operation
Trace / Request Context
Outcome
Error Classification
```

Use the project's established Go logging implementation and conventions.

---

# 4. Log Ownership

Each component should log meaningful events within its own responsibility.

Examples:

```text
API
→ Request outcome

Application Service
→ Business operation outcome

Repository
→ Important dependency failure

Messaging
→ Publication / consumption outcome

Infrastructure
→ Dependency lifecycle / failure
```

Do not log the same error repeatedly at every layer.

---

# 5. Log Levels

Use log levels intentionally.

Typical levels:

```text
DEBUG
INFO
WARN
ERROR
```

The exact logger and level configuration should follow the existing project implementation.

---

# 6. DEBUG

Use DEBUG for detailed information useful during development or controlled troubleshooting.

Examples:

```text
Candidate Discovery Details
Configuration Decisions
Internal State Transitions
Detailed Dependency Timing
```

Do not rely on DEBUG logs for mandatory production audit information.

---

# 7. INFO

INFO should represent meaningful normal operational events.

Examples:

```text
Service Started
Service Shutdown
Consumer Started
Consumer Stopped
Configuration Loaded
Recovery Completed
```

Avoid logging every trivial internal function call at INFO.

---

# 8. WARN

WARN indicates an unusual condition that does not necessarily mean the operation failed.

Examples:

```text
Retry Started
Stale Operational Data
Fallback Activated
Approaching Capacity
Unexpected but Recoverable Condition
```

Do not use WARN for ordinary expected client validation errors.

---

# 9. ERROR

ERROR should represent a failure that requires attention or caused an operation to fail.

Examples:

```text
Database Operation Failed
Redis Unavailable
Event Publication Failed
Unhandled Application Failure
Consumer Permanently Failed
```

Do not log an error simply because an expected business rejection occurred.

---

# 10. Expected Business Errors

Expected outcomes such as:

```text
Ride Not Found
Driver Unavailable
Invalid State
Region Not Allowed
Validation Failure
```

should normally not produce noisy ERROR logs for every occurrence.

They may be represented through:

```text
API Response
Metrics
Structured Debug / Info Context
```

according to severity and operational importance.

---

# 11. Error Logging Ownership

A lower layer should add diagnostic context.

The boundary that can decide the final operational significance should generally own the ERROR-level log.

Avoid:

```text
Repository logs ERROR
Service logs ERROR
Handler logs ERROR
```

for the same failure.

This creates duplicate noise.

---

# 12. Log Context

Useful contextual fields may include:

```text
component
operation
event_type
error_code
dependency
trace_id
request_id
```

Resource identifiers may be included where safe and useful.

---

# 13. Request Correlation

Requests should be traceable across the application.

Conceptually:

```text
HTTP Request
    ↓
Request ID / Trace ID
    ↓
Application Service
    ↓
Database / Redis
    ↓
Event
    ↓
Consumer
```

This is essential for distributed debugging.

---

# 14. Trace ID

Where distributed tracing is enabled, the trace ID should be propagated through supported boundaries.

Use the established observability implementation.

Do not invent a second tracing mechanism inside individual components.

---

# 15. Request ID

A request identifier can help correlate HTTP activity when tracing is unavailable or when a stable request-level identifier is required.

It should not replace distributed tracing when tracing is the appropriate mechanism.

---

# 16. Event Correlation

When an operation produces an event, preserve correlation information where supported.

Conceptually:

```text
API Request
    ↓
Ride Creation
    ↓
Ride Event
    ↓
Consumer
    ↓
Matching
```

should be traceable during investigation.

---

# 17. Aggregate Identifiers

Business identifiers such as:

```text
ride_id
driver_id
user_id
```

can be useful in logs when safe.

Do not automatically include every identifier in every log line.

---

# 18. Sensitive Data

Never log:

```text
Passwords
Access Tokens
Refresh Tokens
API Keys
Private Keys
Database Passwords
Redis Credentials
Broker Credentials
Payment Secrets
```

---

# 19. Location Data

RideForge handles driver and ride location information.

Exact coordinates should not be logged routinely.

Prefer a safer representation such as:

```text
H3 Cell
Operation
Outcome
```

when that is sufficient for diagnosis.

---

# 20. Request Bodies

Do not log complete request bodies by default.

Request bodies may contain:

```text
Identity Information
Location
Authentication Data
Payment Information
Other Sensitive Data
```

Log only the fields required for diagnosis.

---

# 21. Response Bodies

Do not log complete response bodies by default.

Large or sensitive responses create:

```text
Security Risk
Log Volume
Storage Cost
Performance Overhead
```

---

# 22. Event Payloads

Do not log complete event payloads by default.

Prefer:

```text
event_id
event_type
version
aggregate_id where safe
consumer
outcome
error_class
```

---

# 23. Database Queries

Do not log every SQL query in normal production operation.

Query logging can create:

```text
Huge Log Volume
Sensitive Data Exposure
Performance Overhead
```

Use targeted query logging during controlled debugging.

---

# 24. Database Errors

Database failures should contain enough context to identify:

```text
Operation
Repository
Table / Resource where safe
Failure Classification
```

Do not expose:

```text
Credentials
Full Connection Strings
Sensitive Query Parameters
```

---

# 25. Redis Debugging

Redis-related logs should identify:

```text
Operation
Component
Failure Type
Latency where useful
```

Do not log every Redis command.

For driver-location debugging, prefer:

```text
H3 Cell
Driver Operation
Lookup Result Summary
```

over exact coordinates.

---

# 26. Messaging Debugging

Messaging logs should help trace:

```text
Event Publication
Event Consumption
Retry
DLQ
```

Useful fields include:

```text
event_id
event_type
version
topic
partition where useful
consumer_group
attempt
outcome
```

Do not expose complete sensitive payloads.

---

# 27. Producer Logging

Producer logs should distinguish:

```text
Publication Started where useful
Publication Succeeded where operationally meaningful
Publication Failed
```

Avoid logging every successful event at INFO in a high-throughput stream.

Use metrics for aggregate volume.

---

# 28. Consumer Logging

Consumer logs should identify:

```text
Event Type
Event ID
Consumer
Outcome
Failure Classification
Attempt
```

Avoid logging complete payloads.

---

# 29. Retry Logging

A retry should be observable without producing excessive noise.

A useful retry record includes:

```text
Operation
Attempt
Maximum Attempts
Failure Classification
Backoff
```

Repeated retries may be better represented through metrics plus a final error log.

---

# 30. DLQ Logging

DLQ routing should be clearly observable.

Include:

```text
Event ID
Event Type
Failure Classification
Attempt Count
DLQ Destination
```

Do not dump the entire message payload into logs.

---

# 31. Startup Logging

Startup should provide enough information to determine:

```text
Service Started
Environment
Application Version
Enabled Safe Features
Dependency Initialization
```

Never log secrets during startup.

---

# 32. Shutdown Logging

Shutdown should make lifecycle behaviour clear:

```text
Shutdown Requested
Consumers Stopped
HTTP Server Stopped
Dependencies Closed
Shutdown Completed
```

Unexpected shutdown failures should be distinguished from normal cancellation.

---

# 33. Configuration Logging

It is useful to log non-sensitive configuration summary.

For example:

```text
Environment=development
HTTP Port=...
Messaging Enabled=true
```

Do not log:

```text
Database Password
API Key
Broker Credential
Signing Secret
```

---

# 34. Panic Logging

Unexpected panics should contain enough information to identify:

```text
Component
Operation
Stack Trace
Trace / Request Context
```

but the response to an external caller must remain safe.

---

# 35. Stack Traces

Stack traces are useful for unexpected programming failures.

Do not include stack traces in normal API responses.

Avoid generating stack traces for every expected business error.

---

# 36. Contextual Error Wrapping

Errors should carry useful context through the call chain.

For example:

```text
PostgreSQL Failure
    ↓
Repository Operation
    ↓
Application Operation
```

The final log should explain the operation without requiring developers to reconstruct the entire call chain manually.

---

# 37. Avoid Duplicate Context

Do not repeatedly add the same information at every layer.

Avoid log messages such as:

```text
ride creation failed
ride service ride creation failed
handler ride creation failed
```

when one final structured error log can provide the necessary context.

---

# 38. Logging and Error Classification

Logging should follow the error-handling taxonomy.

For example:

```text
Validation Failure
→ Not necessarily ERROR

Business Conflict
→ Not necessarily ERROR

Infrastructure Failure
→ ERROR where operation failed

Unexpected Programming Failure
→ ERROR
```

---

# 39. Logging and Retries

A transient dependency failure that will be retried should not necessarily produce an ERROR log on every attempt.

Consider:

```text
First / Significant Retry
→ WARN or structured diagnostic event

Final Failure
→ ERROR
```

according to operational importance.

---

# 40. Logging and Health Checks

Health-check traffic should not flood logs.

Do not emit an INFO log for every:

```text
/health
/ready
```

request.

Use metrics and targeted failure logs.

---

# 41. Logging and High Traffic

High-frequency paths require special care.

Avoid logging every:

```text
Location Update
Candidate Lookup
Heartbeat
Health Check
Successful API Request
```

at INFO.

Use:

```text
Metrics
Sampling
DEBUG
Aggregated Logs
```

where appropriate.

---

# 42. Logging and Performance

Logging is application work.

Excessive logging can increase:

```text
CPU
Memory
I/O
Network
Storage
Latency
```

Do not add detailed logs to a hot path without considering the performance cost.

---

# 43. Structured Fields vs Message Text

Prefer structured fields for values that need to be searched or aggregated.

Instead of:

```text
"ride 123 failed after 4 retries"
```

prefer a structured event containing:

```text
ride_id=123
attempt=4
error_code=...
```

where the logging framework supports it.

---

# 44. Stable Field Names

Use consistent field names.

Prefer one convention for:

```text
trace_id
request_id
ride_id
driver_id
event_id
event_type
```

Do not create aliases such as:

```text
traceId
traceID
trace
```

in different components.

---

# 45. Log Schema

The application's structured log schema should remain stable enough for:

```text
Search
Dashboards
Alerts
Debugging
```

Avoid unnecessary changes to common field names.

---

# 46. Local Debugging

Local logs may be more verbose than production logs.

Development may enable:

```text
DEBUG
Detailed Dependency Errors
Selected SQL Diagnostics
Detailed Messaging Diagnostics
```

provided sensitive information is still protected.

---

# 47. Local Debugging Configuration

Debug verbosity should be controlled through configuration.

Do not permanently hard-code debug logging into application code.

---

# 48. Production Debugging

Production debugging should follow:

```text
Observe
 ↓
Identify Scope
 ↓
Correlate Request / Trace
 ↓
Inspect Component
 ↓
Inspect Dependency
 ↓
Reproduce Safely
 ↓
Apply Fix
 ↓
Verify Recovery
```

Avoid making arbitrary production data changes merely to investigate a problem.

---

# 49. Debugging Order

When diagnosing a failure, start at the boundary:

```text
Client / Request
 ↓
API
 ↓
Application
 ↓
Dependency
 ↓
Infrastructure
```

Use correlation IDs to follow the operation.

---

# 50. Dependency Debugging

When a component reports failure, determine whether the problem is:

```text
Application Logic
Database
Redis
Kafka / Redpanda
External Provider
Network
Configuration
Capacity
```

Do not assume the first visible error is the root cause.

---

# 51. Root Cause vs Symptom

Logs should distinguish symptoms from causes where possible.

Example:

```text
Ride Matching Failed
```

is a symptom.

A useful underlying cause may be:

```text
Redis Candidate Lookup Timed Out
```

or:

```text
Reservation Conflict
```

The final diagnostic record should preserve the meaningful cause.

---

# 52. Debugging Distributed Workflows

For a distributed ride workflow:

```text
API Request
    ↓
Ride Creation
    ↓
Outbox
    ↓
Kafka / Redpanda
    ↓
Matching Consumer
    ↓
Redis Discovery
    ↓
Reservation
    ↓
Match Event
```

use:

```text
Trace ID
Request ID
Event ID
Ride ID
```

as appropriate to reconstruct the workflow.

---

# 53. Debugging Driver Location

For location-related issues inspect:

```text
Latest Location Update
Current H3 Cell
Redis Membership
Freshness / TTL
Availability State
Candidate Lookup
```

Do not treat Redis membership alone as authoritative driver state.

---

# 54. Debugging Dispatch

When a ride fails to match, distinguish:

```text
No Eligible Driver
```

from:

```text
Redis Discovery Failure
```

from:

```text
Reservation Conflict
```

from:

```text
Messaging Failure
```

This distinction should be visible through structured diagnostics.

---

# 55. Debugging API Failures

For an API failure inspect:

```text
Request
 ↓
Authentication
 ↓
Authorization
 ↓
Validation
 ↓
Application Operation
 ↓
Dependencies
 ↓
Response Mapping
```

Use the API error code and trace/request ID as starting points.

---

# 56. Debugging Database Failures

Inspect:

```text
Query / Operation
Connection Pool
Latency
Timeout
Transaction State
Constraint Errors
Database Availability
```

Do not immediately increase connection pool sizes without evidence.

---

# 57. Debugging Redis Failures

Inspect:

```text
Redis Availability
Connection Pool
Command Latency
Timeouts
Memory
Key Behaviour
TTL
```

Distinguish:

```text
Missing Key
```

from:

```text
Redis Failure
```

---

# 58. Debugging Messaging Failures

Inspect:

```text
Producer Errors
Broker Availability
Consumer State
Consumer Lag
Event ID
Event Type
Retry Count
DLQ
```

Check whether the failure is:

```text
Publication
Transport
Deserialization
Business Handling
Acknowledgement
```

---

# 59. Debugging Configuration

When behaviour differs between environments, compare non-sensitive configuration:

```text
Environment
Feature State
Timeouts
Pool Sizes
Broker Addresses
Dependency Modes
```

Do not compare secrets by printing them.

---

# 60. Debugging Configuration Drift

Configuration drift can cause:

```text
Works Locally
Fails in Staging
Fails in Production
```

The deployment process should make important configuration differences visible and traceable.

---

# 61. Debugging Timeouts

When an operation times out, determine:

```text
Caller Timeout
Application Timeout
Database Timeout
Redis Timeout
Broker Timeout
External Provider Timeout
```

A timeout without knowing which layer timed out is difficult to diagnose.

---

# 62. Debugging Retries

When latency increases unexpectedly, inspect:

```text
Retry Count
Backoff
Dependency Failure Rate
Consumer Lag
Request Volume
```

Retries can amplify load and create cascading failures.

---

# 63. Debugging Cascading Failures

A dependency failure can propagate:

```text
Redis Failure
 ↓
Candidate Discovery Failure
 ↓
Matching Failure
 ↓
API Error
 ↓
Client Retry
 ↓
Higher Load
```

Logs and metrics should make this chain visible.

---

# 64. Debugging With Metrics

Logs explain individual events.

Metrics explain system-wide behaviour.

Use both:

```text
Metrics
→ Detect / quantify problem

Logs
→ Explain individual failures

Traces
→ Connect distributed operation
```

Detailed observability practices belong in:

```text
13.OBSERVABILITY_DEVELOPMENT.md
```

---

# 65. Debugging With Traces

Use traces for workflows that cross:

```text
API
Database
Redis
Messaging
External Services
```

Avoid manually recreating distributed tracing through ad-hoc log fields when the observability system already provides tracing.

---

# 66. Debugging With Events

For event-driven failures, the event ID should allow developers to locate:

```text
Producer
Broker
Consumer
Retry
DLQ
```

where the infrastructure supports those records.

---

# 67. Debugging DLQ Messages

A DLQ investigation should follow:

```text
Event ID
 ↓
Event Type / Version
 ↓
Original Producer
 ↓
Consumer
 ↓
Failure
 ↓
Retry Attempts
 ↓
Root Cause
```

Only replay after the underlying issue is understood.

---

# 68. Debugging Database State

Use read-only inspection where possible.

Do not modify production records merely to test a hypothesis.

If a repair is required, it should follow an explicit operational process.

---

# 69. Debugging Redis State

Inspect targeted keys only.

Avoid broad commands or operations that can create production load or alter state.

Never use destructive commands such as:

```text
FLUSHDB
FLUSHALL
```

as a debugging shortcut in production.

---

# 70. Debugging Production Safely

Production debugging must preserve:

```text
Availability
Data Integrity
Security
Privacy
Auditability
```

Prefer:

```text
Read-Only Inspection
Metrics
Logs
Traces
Reconciliation
Controlled Diagnostic Tools
```

over ad-hoc mutations.

---

# 71. Debugging Reproduction

When possible, reproduce the failure in:

```text
Local
Test
Staging
```

before changing production behaviour.

Use sanitized data and representative configuration.

---

# 72. Debugging After a Fix

After applying a fix:

```text
Verify Error Rate
Verify Latency
Verify Dependency Health
Verify Queue / Consumer Lag
Verify Business Outcome
```

Do not conclude that a problem is solved merely because one error log disappeared.

---

# 73. Log Retention

Log retention should follow operational and security requirements.

Consider:

```text
Debugging Need
Storage Cost
Privacy
Compliance
Incident Investigation
```

Do not retain sensitive logs indefinitely.

---

# 74. Log Rotation

Local and self-managed logging must prevent unbounded disk growth.

Production log infrastructure should use the established centralized logging/collection mechanism.

---

# 75. Log Sampling

High-volume logs may require sampling.

Sampling must not hide:

```text
Critical Errors
Security Events
Important State Transitions
```

unless the observability architecture explicitly supports another source of truth.

---

# 76. Logging and Compliance

If a field is sensitive or regulated, logging should be treated as data handling.

Prefer:

```text
Redaction
Hashing where appropriate
Omission
Aggregation
```

over storing raw sensitive values.

---

# 77. Redaction

Sensitive fields should be removed or masked before logging.

Do not depend on a downstream log system to clean up unsafe application logs.

---

# 78. Logging Tests

Logging code should be tested when:

```text
Security Redaction
Critical Error Context
Structured Field Contract
```

is important.

Do not write tests for every ordinary log message.

---

# 79. Debugging Test Failures

When tests fail:

```text
Identify Failing Layer
 ↓
Read Error Classification
 ↓
Inspect Relevant Logs
 ↓
Inspect Dependency State
 ↓
Reproduce
 ↓
Fix Root Cause
```

Do not weaken the test merely to make the suite pass.

---

# 80. Race and Concurrency Debugging

For concurrency issues, use:

```bash
go test -race ./...
```

where applicable.

Also inspect:

```text
Goroutine Ownership
Context Cancellation
Shared State
Locks
Channels
Database Transactions
Redis Atomicity
```

---

# 81. Deadlocks

When investigating deadlocks, inspect:

```text
Lock Ordering
Channel Blocking
Database Transactions
Connection Pools
Goroutine Waits
```

Avoid adding arbitrary timeouts as a substitute for fixing the underlying synchronization problem.

---

# 82. Goroutine Leaks

When investigating goroutine growth, check:

```text
Missing Cancellation
Blocked Channels
Unclosed Consumers
Long-Lived Background Work
Retry Loops
```

Every long-lived goroutine should have an explicit ownership and shutdown strategy.

---

# 83. Memory Debugging

When investigating memory growth, consider:

```text
Unbounded Caches
Redis Payloads
Large API Responses
Goroutine Growth
Unbounded Queues
```

Use profiling tools where necessary rather than guessing.

---

# 84. CPU Debugging

When investigating CPU usage, inspect:

```text
Hot Loops
Serialization
Logging
JSON Processing
Candidate Ranking
Database Query Volume
Retry Storms
```

Measure before optimizing.

---

# 85. Latency Debugging

Break request latency into components:

```text
HTTP
 ↓
Application
 ↓
PostgreSQL
 ↓
Redis
 ↓
Messaging
 ↓
External Provider
```

Use traces and metrics to determine the actual bottleneck.

---

# 86. AI Agent Logging Rules

Before adding or changing logs, an AI agent must:

1. Identify the operational event being diagnosed.
2. Determine the correct log level.
3. Reuse the existing structured logger.
4. Reuse established field names.
5. Add correlation context where available.
6. Check for sensitive information.
7. Avoid logging complete payloads.
8. Consider hot-path performance.
9. Avoid duplicate logging at multiple layers.
10. Prefer metrics for high-frequency aggregate behaviour.
11. Update tests when redaction or log contracts matter.
12. Review the final diff.

---

# 87. AI Agent Debugging Rules

When debugging a failure, an AI agent must:

1. Identify the failing architectural layer.
2. Trace the operation across boundaries.
3. Distinguish symptom from root cause.
4. Inspect existing logs, metrics, and traces where available.
5. Check configuration before changing code.
6. Check dependency failures before assuming business-logic failure.
7. Preserve existing error semantics.
8. Reproduce the issue where practical.
9. Make the smallest justified correction.
10. Add a regression test when appropriate.
11. Run relevant validation.
12. Review the final diff.

---

# 88. AI Agent Forbidden Logging Patterns

AI agents must not:

- log passwords, tokens, API keys, or private keys,
- log complete request or response bodies by default,
- log complete event payloads by default,
- log exact driver coordinates unnecessarily,
- log every Redis or SQL command in normal production operation,
- use ERROR for every expected business rejection,
- duplicate the same error at every architectural layer,
- create inconsistent field names,
- introduce a second tracing/correlation mechanism without justification,
- add verbose logging to hot paths without considering performance,
- use logs as a substitute for metrics,
- use logs as a substitute for traces,
- modify production data as a debugging shortcut,
- use destructive Redis operations to diagnose problems,
- claim an issue is fixed without verifying the relevant system behaviour.

# 91. Final Logging and Debugging Principle

> **Log enough to explain system behaviour, not enough to recreate sensitive state; use logs for contextual evidence, metrics for system-wide signals, and traces for distributed execution.**

The intended debugging flow is:

```text
Failure / Anomaly
        ↓
Metrics
        ↓
Logs
        ↓
Trace
        ↓
Component
        ↓
Dependency
        ↓
Root Cause
        ↓
Controlled Fix
        ↓
Verification
```

RideForge debugging should make distributed failures understandable without compromising:

```text
Security
Privacy
Performance
Data Integrity
System Availability
```
