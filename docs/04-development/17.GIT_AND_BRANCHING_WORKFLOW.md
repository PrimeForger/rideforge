# 1. Purpose

Git is the source-control foundation for RideForge development.

The Git workflow must provide:

```text
Traceability
+
Controlled Integration
+
Reviewability
+
Safe Collaboration
+
Reproducible Releases
```

The workflow should remain simple enough for daily development while supporting the project's long-term production lifecycle.

---

# 2. Git Principle

Every change should be:

```text
Intentional
        ↓
Isolated
        ↓
Reviewable
        ↓
Tested
        ↓
Integrated
        ↓
Traceable
```

Avoid unnecessary Git complexity.

---

# 3. Repository Source of Truth

The Git repository is the source of truth for:

```text
Application Code
Infrastructure Definitions
Migrations
Configuration Templates
Tests
Documentation
Build / Development Scripts
```

Secrets and environment-specific private configuration must not be committed.

---

# 4. Branching Strategy

RideForge should use a lightweight branch-based workflow.

The recommended structure is:

```text
main
 │
 ├── feature/*
 ├── fix/*
 ├── refactor/*
 ├── docs/*
 ├── chore/*
 └── hotfix/*
```

Use additional long-lived branches only when the release/deployment architecture genuinely requires them.

---

# 5. Main Branch

`main` represents the integrated, stable codebase.

It should contain code that has:

```text
Passed Required Validation
Been Reviewed
Satisfied Integration Requirements
```

Do not use `main` as an experimental workspace.

---

# 6. Feature Branches

Feature branches isolate new functionality.

Naming convention:

```text
feature/<short-description>
```

Examples:

```text
feature/smart-dispatch
feature/driver-location-index
feature/ride-cancellation
```

Keep feature branches focused.

---

# 7. Fix Branches

Use fix branches for ordinary defect corrections.

Naming convention:

```text
fix/<short-description>
```

Examples:

```text
fix/reservation-conflict
fix/redis-timeout
fix/ride-validation
```

---

# 8. Refactor Branches

Use refactor branches when restructuring code without intentionally changing externally observable behaviour.

Naming:

```text
refactor/<short-description>
```

Examples:

```text
refactor/matching-service
refactor/repository-layer
```

If behaviour also changes materially, use a feature/fix branch instead.

---

# 9. Documentation Branches

Documentation-only work may use:

```text
docs/<short-description>
```

Examples:

```text
docs/development-guide
docs/architecture-update
```

---

# 10. Chore Branches

Use `chore/*` for maintenance that does not represent a user-facing feature or defect fix.

Examples:

```text
chore/update-dependencies
chore/ci-maintenance
chore/dev-tooling
```

---

# 11. Hotfix Branches

Urgent production fixes may use:

```text
hotfix/<short-description>
```

A hotfix should remain narrowly scoped.

After the fix is integrated, ensure the correction is also present in the normal development line.

---

# 12. Branch Lifetime

Prefer short-lived branches.

A branch should generally represent:

```text
One Change
One Intent
One Review
```

Long-lived branches increase:

```text
Merge Conflicts
Drift
Integration Risk
Review Complexity
```

---

# 13. Branch Creation

Before creating a branch:

```bash
git status
git fetch origin
```

Ensure the working tree is understood and the branch starts from the intended base.

---

# 14. Starting From Updated Main

When beginning normal work:

```text
Update Local Main
        ↓
Create Branch
        ↓
Implement Change
```

Do not routinely branch from an outdated local base.

---

# 15. Branch Naming Rules

Branch names should be:

```text
Short
Descriptive
Lowercase
Consistent
```

Avoid:

```text
test
new
final
changes
temp
branch2
```

unless there is a very specific temporary purpose.

---

# 16. One Branch, One Intent

Avoid combining unrelated work:

```text
Feature
+
Dependency Upgrade
+
Large Refactor
+
Documentation Rewrite
```

in one branch unless the changes are genuinely coupled.

Smaller changes are easier to:

```text
Review
Test
Revert
Deploy
```

---

# 17. Working Tree

Before starting work:

```bash
git status
```

Understand:

```text
Current Branch
Modified Files
Untracked Files
Staged Files
```

Never overwrite unrelated local work without understanding what it is.

---

# 18. Untracked Files

Before committing, review untracked files carefully.

Do not commit:

```text
.env
Secrets
Private Keys
Local Database Files
Build Artifacts
Large Logs
IDE State
Temporary Debug Files
```

---

# 19. Staging

Stage only the intended changes.

Prefer reviewing:

```bash
git diff
git status
```

before:

```bash
git commit
```

---

# 20. Partial Staging

When a file contains unrelated changes, use selective staging where appropriate.

The goal is:

```text
One Commit
=
One Coherent Change
```

---

# 21. Commit Principle

A commit should represent a meaningful, coherent unit of work.

Good examples:

```text
Add ride cancellation validation
Add Redis driver-cell repository
Add reservation conflict handling
Add migration for ride status
```

Avoid vague messages such as:

```text
changes
fix
update
done
work
final
```

---

# 22. Commit Message Structure

Use a consistent commit style.

A recommended structure is:

```text
<type>: <short description>
```

Examples:

```text
feat: add smart dispatch strategy
fix: handle reservation conflicts
docs: add migration workflow
refactor: simplify matching service
test: add dispatch integration coverage
chore: update development tooling
```

Follow the repository's existing convention if one is already established.

---

# 23. Commit Message Quality

A good commit message describes the change, not the coding activity.

Prefer:

```text
fix: prevent duplicate ride reservation
```

over:

```text
fix code
```

---

# 24. Commit Scope

Avoid giant commits containing unrelated work.

A useful commit should allow a reviewer to understand:

```text
What Changed?
Why?
What Should Be Tested?
```

---

# 25. Commit Frequency

Commit at meaningful milestones.

Do not wait until an entire feature contains dozens of unrelated modifications.

Good milestones may include:

```text
Domain Change
Repository Change
Service Change
API Change
Tests
Migration
```

when they form independently understandable units.

---

# 26. Do Not Commit Broken Intermediate States

A commit intended for integration should normally build and pass the relevant validation.

Avoid committing code that is knowingly:

```text
Uncompilable
Broken
Missing Required Migration
Missing Required Tests
```

unless the repository explicitly uses a workflow where such commits are expected and hidden from integration.

---

# 27. Before Committing

Run:

```text
Format
Lint / Static Checks
Relevant Tests
```

according to the project's validation requirements.

For Go, typical checks may include:

```bash
gofmt
go test ./...
go vet ./...
```

Use the repository's actual commands when available.

---

# 28. Before Pushing

Review:

```bash
git status
git diff
git log
```

Confirm:

```text
Correct Branch
Correct Files
No Secrets
No Debug Artifacts
Correct Commit Messages
```

---

# 29. Remote

The primary remote should normally be named:

```text
origin
```

Verify remote configuration with:

```bash
git remote -v
```

Do not assume a remote name if the repository has a custom configuration.

---

# 30. Push Workflow

Push the feature branch to the remote:

```bash
git push -u origin <branch-name>
```

After the upstream is configured:

```bash
git push
```

can normally be used.

---

# 31. Pull Requests

Changes intended for integration should normally go through a pull request.

A pull request should provide:

```text
Purpose
Scope
Important Design Decisions
Testing Performed
Migration Impact
Operational Impact
```

when applicable.

---

# 32. Pull Request Size

Keep pull requests reasonably focused.

Large changes should be split when possible.

Do not artificially split tightly coupled changes merely to reduce line count.

---

# 33. Pull Request Description

A useful PR description should answer:

```text
What changed?
Why was it needed?
How was it tested?
Are there migration changes?
Are there API/event contract changes?
Are there operational risks?
```

---

# 34. Review Before PR

Before opening a PR:

```text
[ ] Branch is correct
[ ] Diff reviewed
[ ] Unrelated changes removed
[ ] Tests pass
[ ] Formatting applied
[ ] Documentation updated if required
[ ] Migration reviewed if applicable
[ ] Configuration reviewed if applicable
[ ] Secrets absent
```

---

# 35. Updating a Feature Branch

If `main` has advanced while work is in progress, update the branch using the repository's preferred integration strategy.

Possible strategies include:

```text
Rebase
Merge
```

The project should use one consistent team convention rather than mixing strategies unpredictably.

---

# 36. Rebase

Rebase creates a linear history by replaying commits on top of a newer base.

Conceptually:

```text
Old Base
   ↓
Feature Commits

becomes:

New Base
   ↓
Feature Commits
```

Use rebase only when rewriting the branch history is safe.

---

# 37. Do Not Rebase Shared Branches

Avoid rebasing branches that other developers are actively building on unless the team explicitly coordinates the rewrite.

Rewriting shared history creates unnecessary disruption.

---

# 38. Force Push

Avoid force pushing shared branches.

When force push is genuinely required for a private feature branch, prefer:

```bash
git push --force-with-lease
```

over:

```bash
git push --force
```

`--force-with-lease` provides a safer check against overwriting unexpected remote changes.

---

# 39. Merge

Merge may be used when preserving branch history is preferred or when the team workflow requires it.

Do not mix merge/rebase policies randomly within the same repository.

---

# 40. Conflict Resolution

When a conflict occurs:

```text
Stop
 ↓
Understand Both Changes
 ↓
Resolve Intentionally
 ↓
Run Tests
 ↓
Review Diff
 ↓
Continue
```

Do not choose one side blindly.

---

# 41. Conflict Resolution Principle

The correct result is not always:

```text
ours
```

or:

```text
theirs
```

The correct result is:

```text
Desired Combined Behaviour
```

---

# 42. Migration Conflicts

Migration files deserve special care.

If two branches create migrations:

```text
Branch A → Migration A
Branch B → Migration B
```

resolve them according to the migration framework's ordering requirements.

Do not silently delete one migration merely to resolve a Git conflict.

---

# 43. Generated Files

Generated files should follow repository policy.

If a file is generated from source configuration:

```text
Source
→ Generator
→ Generated Artifact
```

do not manually edit the generated output unless the project explicitly requires committed manual changes.

---

# 44. Lock Files

Dependency lock files should follow the project's established policy.

When dependency versions change, review:

```text
Direct Dependencies
Indirect Dependencies
Security Impact
Compatibility
```

Do not manually edit generated dependency metadata without understanding the package manager.

---

# 45. Documentation Changes

Documentation should be committed alongside the implementation when the implementation changes documented behaviour.

Examples:

```text
API Contract
Migration Workflow
Configuration
Development Setup
Architecture Decision
```

---

# 46. Database Migration Commits

A schema change should keep migration and application changes synchronized where practical.

A reviewer should be able to understand:

```text
Schema Change
+
Application Change
+
Tests
```

as one coherent feature.

---

# 47. API Contract Changes

When an API changes:

```text
Implementation
+
Tests
+
Documentation
```

should be reviewed together.

---

# 48. Event Contract Changes

When an event contract changes:

```text
Producer
+
Consumer
+
Event Schema
+
Compatibility
+
Tests
```

must be considered.

Do not merge producer-only changes that silently break consumers.

---

# 49. Configuration Changes

Configuration changes should include:

```text
Code
+
Environment Template
+
Documentation
```

when required.

Never commit real secret values.

---

# 50. Release Tags

Production releases should be traceable to a specific Git commit.

Use repository-approved tags.

A tag should allow operators to determine:

```text
Which Code Version?
Which Commit?
Which Release?
```

---

# 51. Tagging

Use a consistent versioning convention.

If semantic versioning is adopted, use:

```text
vMAJOR.MINOR.PATCH
```

Examples:

```text
v1.0.0
v1.1.0
v1.1.1
```

Follow the project's actual release policy.

---

# 52. Release Branches

Do not create release branches by default.

Introduce a release branch only when the deployment process requires:

```text
Release Stabilization
Parallel Development
Long-Lived Release Maintenance
```

Otherwise, keep the workflow simple.

---

# 53. Hotfix Workflow

A production hotfix should be:

```text
Identify Production Commit
        ↓
Create Hotfix Branch
        ↓
Implement Minimal Fix
        ↓
Test
        ↓
Review
        ↓
Merge
        ↓
Tag / Deploy
        ↓
Ensure Fix Exists in Main Development Line
```

---

# 54. Hotfix Scope

Avoid combining:

```text
Emergency Fix
+
Refactor
+
Feature
```

in one hotfix.

Keep emergency changes minimal.

---

# 55. Revert

Use `git revert` when a committed change needs to be undone while preserving history.

Prefer:

```bash
git revert <commit>
```

over rewriting shared history.

---

# 56. Reset

`git reset` changes local history/state and must be used carefully.

It is appropriate for local work when the developer understands the consequences.

Do not reset shared history as a normal collaboration technique.

---

# 57. Cherry-Pick

Cherry-pick may be useful for:

```text
Backport
Hotfix
Selective Release Change
```

Use it intentionally because it duplicates a commit into another history.

---

# 58. Backports

A production fix may need to be applied to multiple supported release lines.

Verify:

```text
Behaviour
Dependencies
Migration Compatibility
Tests
```

before backporting.

---

# 59. Git History

Preserve useful history.

History should help developers understand:

```text
Why a Change Happened
When It Happened
Which Commit Introduced It
```

Do not rewrite shared history merely to make it look cleaner.

---

# 60. Blame

`git blame` can help identify when a line changed and which commit introduced it.

Use it as an investigation tool, not as a mechanism for assigning personal fault.

---

# 61. Bisect

`git bisect` is useful for locating regressions across commit history.

Conceptually:

```text
Known Good
    ↓
Unknown Commit Range
    ↓
Known Bad
    ↓
Binary Search
    ↓
Regression Commit
```

Use it for difficult regressions when ordinary inspection is insufficient.

---

# 62. Git Tags and Database Migrations

Release tags must correspond to a compatible database state.

A deployment version should make it possible to determine:

```text
Application Version
+
Required Migration State
```

---

# 63. Git and Migration Safety

Never assume a Git rollback automatically means:

```text
Database Rollback
```

Application history and database history are related but independently managed.

Follow:

```text
16.MIGRATIONS_AND_SCHEMA_CHANGES.md
```

for schema rollback and recovery rules.

---

# 64. Git and Configuration

Git should contain:

```text
Configuration Schema
Configuration Templates
Safe Defaults
```

but not:

```text
Production Secrets
Private Credentials
```

---

# 65. Git and Environment Files

If `.env` contains secrets, it should normally remain untracked.

A safe repository pattern is:

```text
.env.example
```

containing placeholders or safe development values.

---

# 66. Secret Detection

Before pushing:

```text
Review Diff
Review Staged Files
```

If automated secret scanning is available, use it.

If a secret is accidentally committed:

```text
Revoke / Rotate Secret
```

first.

Removing the file from the latest commit does not necessarily remove it from Git history.

---

# 67. Large Files

Do not commit:

```text
Large Database Dumps
Build Artifacts
Local Logs
Generated Temporary Data
```

unless explicitly required.

Use appropriate artifact or object-storage mechanisms when large files genuinely belong outside normal Git history.

---

# 68. Binary Files

Avoid storing unnecessary binaries in the repository.

If a binary is a required project artifact, follow the repository's established storage policy.

---

# 69. Dependency Updates

Dependency updates should be isolated when possible.

Review:

```text
Version Change
Breaking Changes
Security Advisories
Transitive Changes
Tests
```

---

# 70. Git Hooks

Hooks may be used for local developer convenience.

Do not rely exclusively on local hooks for repository correctness because developers can bypass them.

Critical validation should also exist in CI or another shared mechanism.

---

# 71. CI as the Integration Gate

The shared integration process should verify appropriate checks such as:

```text
Build
Tests
Static Analysis
Formatting
Security Checks
Migration Validation
```

according to the project's CI configuration.

---

# 72. Protected Branches

Production integration branches should use appropriate branch protections.

Potential protections include:

```text
Required Pull Request
Required Review
Required CI
No Direct Push
```

The exact repository settings are an operational concern and should match the project's collaboration model.

---

# 73. Direct Commits to Main

Direct commits to `main` should be restricted unless the repository intentionally permits them.

Normal development should use:

```text
Branch
 ↓
Review
 ↓
CI
 ↓
Merge
```

---

# 74. Merge Commit Policy

If the repository uses squash merging:

```text
Feature Branch
    ↓
Pull Request
    ↓
Squashed Main Commit
```

If it uses merge commits, preserve the configured workflow.

The important requirement is consistency.

---

# 75. Squash Merging

Squashing is useful when a feature branch contains many noisy development commits.

The resulting commit should have a clear description of the integrated change.

---

# 76. Commit History Quality

A clean history is valuable, but history readability must not come at the expense of safe collaboration.

Prefer:

```text
Useful History
```

over:

```text
Perfectly Linear History at Any Cost
```

---

# 77. Working on Existing Changes

If the working tree contains changes from another task:

```text
Do Not Overwrite Them
```

Instead:

```text
Inspect
Separate
Stash if appropriate
Commit if appropriate
```

according to the actual ownership of the changes.

---

# 78. Git Stash

`git stash` can temporarily save local work.

Use it carefully.

Before restoring a stash, understand whether the target branch has changed in ways that may create conflicts.

---

# 79. Detached HEAD

Avoid performing normal development work in detached HEAD state.

If encountered:

```text
Identify Commit
Create / Switch to Intended Branch
Continue Safely
```

before making substantial changes.

---

# 80. Remote Synchronization

Before integrating major changes:

```bash
git fetch origin
```

Fetch updates without automatically changing the working tree.

Then determine how the current branch should be updated.

---

# 81. Pull Behaviour

Do not rely on an implicit pull strategy if the repository has not defined one.

Understand whether the team expects:

```text
Pull + Merge
```

or:

```text
Pull + Rebase
```

and configure Git accordingly if appropriate.

---

# 82. Branch Deletion

After a branch has been successfully integrated and is no longer needed:

```text
Delete Local Branch
Delete Remote Branch
```

when appropriate.

Do not delete branches that are still needed for:

```text
Release
Backport
Investigation
Recovery
```

---

# 83. Repository Hygiene

Periodically remove:

```text
Merged Feature Branches
Stale Local Branches
Unused Remotes
Temporary Files
```

Keep the repository navigable.

---

# 88. Git Workflow for Refactoring

A refactor should:

```text
Preserve Behaviour
        ↓
Keep Tests Passing
        ↓
Change Internal Structure
        ↓
Review Diff Carefully
```

Avoid mixing unrelated feature changes into a refactor unless necessary.

---

# 89. Git Workflow for AI-Assisted Development

AI-generated changes must follow the same Git standards as human-written changes.

The use of an AI agent does not justify:

```text
Huge Unreviewed Commits
Unclear History
Skipped Tests
Unreviewed Generated Code
```

---

# 90. AI Agent Branch Rules

Before modifying code, an AI agent must:

1. Inspect the current Git status.
2. Identify the current branch.
3. Avoid overwriting unrelated local changes.
4. Understand the intended change scope.
5. Keep modifications focused.
6. Avoid creating unnecessary branches.
7. Follow repository branch naming conventions.
8. Preserve existing Git workflow.

---

# 91. AI Agent Commit Rules

An AI agent preparing a commit must:

1. Review `git status`.
2. Review the full diff.
3. Check for unrelated changes.
4. Check for secrets.
5. Check generated files.
6. Run relevant validation.
7. Use a meaningful commit message.
8. Avoid committing known broken states.
9. Confirm migration/configuration changes are intentional.
10. Never claim a commit was created unless it actually was.

---

# 92. AI Agent Forbidden Git Patterns

AI agents must not:

- delete unrelated local changes,
- run destructive Git commands without explicit justification,
- force push shared branches,
- rewrite shared history,
- reset the working tree blindly,
- commit secrets,
- commit generated artifacts unnecessarily,
- create arbitrary branch names,
- combine unrelated changes into one commit,
- skip required tests merely to produce a clean commit,
- modify migration history to resolve Git conflicts without understanding the schema implications,
- claim a branch, commit, push, or merge happened when it did not.

---

# 93. Git Safety Rules

Before any potentially destructive Git command, verify:

```text
Current Branch
Current Commit
Working Tree
Remote
Target
```

Commands requiring special care include:

```bash
git reset --hard
git clean
git push --force
git branch -D
git rebase
```

---

# 94. Recovery

If Git state becomes confusing:

```text
Stop
 ↓
Inspect status
 ↓
Inspect log
 ↓
Inspect reflog if necessary
 ↓
Determine intended state
 ↓
Recover deliberately
```

Do not issue multiple destructive commands while the repository state is unknown.

---

# 95. Reflog

`git reflog` can help recover commits or branch states that are no longer referenced by normal branch names.

Use it when local history appears to have been lost.

---

# 96. Git and Production Releases

A production deployment should be traceable to:

```text
Git Commit
+
Release / Tag
+
Migration State
+
Configuration Version
```

This allows an incident to be correlated with the exact source version.

---

Before opening a pull request:

```text
[ ] Formatting completed
[ ] Relevant tests pass

```

# 98. Final Git Principle

> **Git should make every RideForge change understandable, reviewable, reproducible, and recoverable without introducing unnecessary workflow complexity.**

The standard development path is:

```text
main
  ↓
Focused Branch
  ↓
Focused Commits
  ↓
Validation
  ↓
Pull Request
  ↓
Review + CI
  ↓
Integration
  ↓
Release
```

The repository history must remain trustworthy enough to answer:

```text
What changed?
Why did it change?
Who integrated it?
Which tests validated it?
Which release contains it?
Which database migration accompanies it?
```

Git is not merely a place to store code.

For RideForge, it is part of the engineering control system connecting:

```text
Code
+
Schema
+
Configuration
+
Documentation
+
Tests
+
Releases
```
