# 1. Purpose

The RideForge API is an external application boundary.

Its responsibility is to provide:

```text
Stable Contracts
Clear Request Semantics
Validated Input
Authenticated Access
Authorized Operations
Predictable Errors
Bounded Work
Observable Behaviour
```

The API layer must translate transport concerns into application commands/queries without becoming the location of core business logic.

---

# 2. API Architecture

The preferred flow is:

```text
HTTP Request
    ↓
Router
    ↓
Handler / Transport Adapter
    ↓
Request Validation
    ↓
Authentication Context
    ↓
Application Service
    ↓
Domain / Repository / Infrastructure
    ↓
Application Result
    ↓
Response Mapping
    ↓
HTTP Response
```

The handler should remain thin.

---

# 3. API Boundary

The API is responsible for:

```text
HTTP
Headers
Path Parameters
Query Parameters
Request Body
Authentication Context
Response Serialization
HTTP Status Codes
```

The API is not responsible for implementing:

```text
Core Business Rules
Database Transactions
Redis Algorithms
Dispatch Ranking
Event Processing
```

Those belong to their appropriate layers.

---

# 4. Resource-Oriented Design

Where appropriate, API resources should represent business concepts.

Examples:

```text
Rides
Drivers
Users
Offers
Assignments
Locations
```

Use consistent resource naming throughout the API.

---

# 5. HTTP Methods

Use HTTP methods according to operation semantics.

Typical usage:

```text
GET
    Read

POST
    Create / Execute Action

PUT
    Full Replacement where applicable

PATCH
    Partial Update where applicable

DELETE
    Delete / Deactivate where applicable
```

Do not use HTTP methods merely because they are convenient.

---

# 6. Path Naming

Paths should be:

```text
Predictable
Consistent
Resource-Oriented
Versionable
```

Avoid paths that expose internal implementation details.

Prefer:

```text
/api/v1/rides
```

over paths such as:

```text
/api/v1/runRideService
/api/v1/postgres/rides
```

---

# 7. API Versioning

The API should use an explicit versioning strategy.

The established API structure should be followed consistently, for example:

```text
/api/v1/...
```

Do not introduce a second versioning convention for a new endpoint.

---

# 8. Version Compatibility

A new API version should not silently change the meaning of existing contracts.

Breaking changes should be:

```text
Explicit
Documented
Versioned
Tested
```

---

# 9. Request Contract

Every endpoint should define:

```text
Path Parameters
Query Parameters
Headers
Request Body
Required Fields
Optional Fields
Validation Rules
Authentication
Authorization
```

Do not rely on undocumented behaviour.

---

# 10. Response Contract

Every endpoint should define:

```text
Success Status
Success Body
Error Statuses
Error Body
Relevant Headers
```

Responses should remain stable enough for clients to depend on them.

---

# 11. JSON Conventions

JSON fields should follow the project's established naming convention.

Do not introduce inconsistent naming such as:

```text
driver_id
driverId
DriverID
```

within the same API style.

Choose the established convention and use it consistently.

---

# 12. Request DTOs

Transport request structures should represent the API contract.

Do not directly expose database models as request contracts.

Prefer:

```text
HTTP Request DTO
    ↓
Application Input
```

rather than coupling API contracts directly to persistence models.

---

# 13. Response DTOs

Responses should also be explicit.

Do not automatically serialize internal domain or database objects when that would expose:

```text
Internal Fields
Sensitive Fields
Implementation Details
Unstable Structures
```

---

# 14. Input Validation

All client input is untrusted.

Validate:

```text
Required Fields
Types
Formats
Ranges
Lengths
Enumerations
Relationships
```

before passing input into business operations.

---

# 15. Validation Boundary

Basic transport validation belongs at the API boundary.

Business validation belongs in the application/domain layer.

For example:

```text
API
→ Is latitude syntactically valid?

Application / Domain
→ Is this ride allowed between these regions?
```

Do not move business rules into HTTP validation merely because they are triggered by an API request.

---

# 16. Path Parameter Validation

Validate identifiers before using them.

Examples:

```text
UUID
Integer ID
ULID
Driver ID
Ride ID
```

Invalid identifiers should produce a predictable client error.

---

# 17. Query Parameter Validation

Validate:

```text
Limit
Offset / Cursor
Sort
Filter
Search
Date Range
Enum Values
```

Do not allow arbitrary query expressions to reach repositories.

---

# 18. Request Size Limits

API requests must be bounded.

Prevent unbounded:

```text
JSON Bodies
Query Strings
Headers
Bulk Operations
Uploads
```

where the transport stack supports configurable limits.

---

# 19. Pagination

Collection endpoints should not return unbounded data.

Use a defined pagination strategy:

```text
Limit + Offset
```

or:

```text
Cursor Pagination
```

according to the endpoint's requirements.

---

# 20. Pagination Limits

Clients must not be able to request arbitrary enormous pages.

Define:

```text
Default Limit
Maximum Limit
```

and enforce them at the API boundary.

---

# 21. Cursor Pagination

Cursor pagination is preferred for large or frequently changing datasets when stable traversal is required.

A cursor should be:

```text
Opaque
Validated
Bounded
```

Do not expose internal database implementation unnecessarily through cursor values.

---

# 22. Stable Ordering

Paginated results require stable ordering.

Without stable ordering:

```text
Page 1
+
Page 2
```

can produce duplicates or missing records when data changes between requests.

---

# 23. Filtering

Filters should be explicit and documented.

For example:

```text
status=available
vehicle_type=car
```

should map to known application/repository operations.

Do not accept raw SQL-like filters.

---

# 24. Sorting

Sorting fields must be allowlisted.

Conceptually:

```text
Client Sort Field
    ↓
Allowed Field Mapping
    ↓
Known Query Expression
```

Never interpolate arbitrary client-provided column names into SQL.

---

# 25. Search

Search endpoints should define:

```text
Supported Fields
Minimum Query Length where appropriate
Maximum Query Length
Result Limit
Ordering
```

Do not expose unrestricted database search functionality.

---

# 26. Authentication

Authentication establishes the caller's identity.

The API layer should obtain authentication information through the established security mechanism and pass the resulting identity/context to application services.

Do not duplicate authentication implementation across handlers.

---

# 27. Authorization

Authentication does not imply permission.

Before protected operations:

```text
Authenticate
    ↓
Identify Actor
    ↓
Authorize
    ↓
Execute
```

---

# 28. Resource Authorization

For resource-specific operations, verify that the caller has permission to access or modify the resource.

Do not assume:

```text
Valid Ride ID
```

means:

```text
Caller Can Access Ride
```

---

# 29. Role Authorization

Where roles exist, authorization should be explicit.

Potential actors include:

```text
Passenger
Driver
Operator
Administrator
Internal Service
```

The exact role model belongs to the business/security architecture.

---

# 30. Authentication Data Handling

Do not pass raw authentication tokens through application/domain layers unless an infrastructure operation explicitly requires them.

Prefer passing:

```text
Authenticated Actor
Actor ID
Roles / Permissions
Request Context
```

according to the established architecture.

---

# 31. API Idempotency

State-changing endpoints that can safely be retried should support idempotency where the business operation requires it.

Examples may include:

```text
Ride Creation
Payment Initiation
Offer Acceptance
Assignment
```

The requirement depends on the business operation.

---

# 32. Idempotency Key

For idempotent operations, an idempotency key should be:

```text
Client-Generated or Contract-Generated
Stable Across Retries
Scoped Appropriately
Stored Durably Where Required
```

Do not implement distributed idempotency using only process-local memory.

---

# 33. Concurrent Requests

Two identical requests may arrive concurrently.

The idempotency mechanism must protect against:

```text
Request A
Request B
```

both creating the same business effect.

Use the authoritative persistence/concurrency boundary.

---

# 34. API Timeouts

Every API request must have bounded execution.

Do not allow handlers to wait indefinitely for:

```text
Database
Redis
Broker
External Provider
Dispatch
```

---

# 35. Context Propagation

Request context should flow into application operations and dependencies.

Conceptually:

```text
HTTP Context
    ↓
Application Service
    ↓
Repository / Redis / Provider
```

Do not replace request-scoped context with `context.Background()` inside the request workflow.

---

# 36. Cancellation

If the client disconnects or the request deadline expires, request-scoped work should stop when safe.

Do not continue expensive work indefinitely after the caller has gone away unless the operation intentionally becomes background work.

---

# 37. Long-Running Operations

Do not keep HTTP requests open for work that should be asynchronous.

Prefer:

```text
Request
 ↓
Accept / Create Operation
 ↓
Event / Job
 ↓
Background Processing
```

when the operation is inherently asynchronous.

---

# 38. HTTP Status Codes

Use status codes consistently.

Typical categories include:

```text
2xx
Success

4xx
Client / Request / Authorization Problem

5xx
Server / Infrastructure Problem
```

The exact status should reflect the actual outcome.

---

# 39. Common Success Codes

Examples:

```text
200 OK
201 Created
202 Accepted
204 No Content
```

Use the code whose semantics match the endpoint.

Do not return `200` for every successful operation merely for convenience.

---

# 40. Common Client Errors

Examples:

```text
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content
429 Too Many Requests
```

Use the established project convention consistently.

---

# 41. Conflict Responses

Use a conflict response when the request is valid but cannot be completed because current state conflicts with the requested operation.

Examples:

```text
Driver Already Reserved
Ride Already Assigned
Idempotency Conflict
State Transition Conflict
```

---

# 42. Error Response Contract

API errors should have a consistent structure.

A conceptual shape is:

```json
{
  "error": {
    "code": "DRIVER_UNAVAILABLE",
    "message": "The requested driver is no longer available",
    "request_id": "..."
  }
}
```

The exact schema must follow the project's established error model.

---

# 43. Error Codes

Use stable machine-readable error codes.

Clients should not need to parse human-readable messages to determine the error type.

Prefer:

```text
DRIVER_UNAVAILABLE
RIDE_NOT_FOUND
INVALID_RIDE_STATE
REGION_NOT_ALLOWED
```

over relying only on:

```text
"Something went wrong"
```

---

# 44. Human-Readable Error Messages

Messages should be useful to clients/users but must not expose:

```text
SQL
Stack Traces
Internal Paths
Credentials
Infrastructure Details
```

---

# 45. Internal Errors

Map internal errors to stable API errors.

Conceptually:

```text
Repository Error
    ↓
Application Error
    ↓
HTTP Error
```

Do not expose raw infrastructure errors directly.

---

# 46. Error Classification

Application errors should distinguish:

```text
Validation
Not Found
Unauthorized
Forbidden
Conflict
Dependency Failure
Internal Failure
```

according to the established error architecture.

---

# 47. Sensitive Errors

Do not reveal whether protected resources exist when the authorization model requires hiding that information.

Be careful with differences such as:

```text
User Does Not Exist
```

versus:

```text
User Exists but Access Is Forbidden
```

---

# 48. API Security

API development must follow:

```text
Authentication
Authorization
Validation
Rate Limiting where required
Request Size Limits
Secure Transport
Sensitive Data Protection
```

Do not rely only on network-level security.

---

# 49. CORS

CORS should explicitly define permitted origins according to the deployment architecture.

Avoid unrestricted production configuration without a deliberate requirement.

---

# 50. CSRF

If the API uses browser cookies for authenticated state-changing requests, apply the appropriate CSRF protection.

If the authentication architecture does not use cookie-based authentication, follow the corresponding security model instead.

Do not add or remove CSRF protection without considering the authentication mechanism.

---

# 51. Rate Limiting

Rate limiting should protect endpoints susceptible to:

```text
Brute Force
Abuse
Resource Exhaustion
High-Cost Operations
```

Rate limits should be appropriate to:

```text
Actor
Endpoint
Operation
Infrastructure Capacity
```

---

# 52. Dispatch Endpoint Protection

Dispatch operations can be expensive.

Protect endpoints that trigger:

```text
Candidate Discovery
Routing
Ranking
Reservation
External Provider Calls
```

from uncontrolled request amplification.

---

# 53. API and Redis

API handlers should not directly manipulate Redis for dispatch logic.

Prefer:

```text
Handler
 ↓
Application Service
 ↓
Discovery / Redis Component
```

This keeps transport concerns separate from operational data logic.

---

# 54. API and PostgreSQL

API handlers should not directly execute database queries.

Prefer:

```text
Handler
 ↓
Application Service
 ↓
Repository
 ↓
PostgreSQL
```

---

# 55. API and Messaging

API handlers should not directly publish arbitrary broker messages.

When a business operation needs an event:

```text
API
 ↓
Application Service
 ↓
Business State Change
 ↓
Outbox / Event Boundary
 ↓
Broker
```

---

# 56. API and Dispatch

A dispatch request should use the established application workflow.

Conceptually:

```text
HTTP
 ↓
Ride Application Service
 ↓
Dispatch / Discovery
 ↓
Candidate Pipeline
 ↓
Reservation
 ↓
Event
```

Do not duplicate dispatch logic inside an HTTP handler.

---

# 57. API Performance

Handlers should remain lightweight.

Avoid:

```text
Repeated Queries
Large In-Memory Transformations
Unbounded Loops
Unbounded Serialization
Blocking External Calls Without Timeout
```

---

# 58. Response Size

Return only information needed by the client.

Large response bodies increase:

```text
CPU
Memory
Network
Serialization Cost
```

---

# 59. N+1 API Calls

API design should avoid forcing clients to make excessive dependent requests when the server can safely provide the required representation.

However, do not create giant aggregate endpoints merely to avoid a few requests.

Balance:

```text
Network Cost
Payload Size
Coupling
Caching
Client Needs
```

---

# 60. API Caching

Caching should be introduced only where semantics allow it.

For cacheable responses define:

```text
Freshness
TTL
Invalidation
Authorization Interaction
Failure Behaviour
```

Do not cache personalized or authorization-sensitive responses without a clear cache-key strategy.

---

# 61. Conditional Requests

Where appropriate, APIs may use mechanisms such as:

```text
ETag
If-None-Match
Last-Modified
```

to reduce unnecessary data transfer.

Use only when the endpoint benefits from them.

---

# 62. Health Endpoints

Operational health endpoints should distinguish between:

```text
Liveness
Readiness
```

where the deployment architecture requires the distinction.

---

# 63. Liveness

Liveness should answer whether the process is alive enough to remain running.

Do not make liveness depend on every external dependency if that could cause restart loops.

---

# 64. Readiness

Readiness should indicate whether the instance can safely receive traffic.

It may depend on required infrastructure being available according to the deployment architecture.

---

# 65. API Documentation

Every externally consumed endpoint should be documented.

Documentation should include:

```text
Purpose
Method
Path
Authentication
Authorization
Request
Validation
Response
Errors
```

---

# 66. OpenAPI

If the project uses OpenAPI, endpoint contracts should remain synchronized with the implementation.

Do not maintain a separate API description that has already diverged from the code.

---

# 67. API Compatibility

When changing an endpoint:

```text
Identify Consumers
 ↓
Review Contract
 ↓
Assess Breaking Change
 ↓
Update Tests
 ↓
Deploy Safely
```

---

# 68. Adding Fields

Adding optional response fields is generally safer than changing or removing existing fields.

Still consider:

```text
Client Deserializers
Strict Schemas
Contract Tests
```

before assuming the change is harmless.

---

# 69. Removing Fields

Do not remove response/request fields without a compatibility plan.

Potential strategies include:

```text
Deprecation
New API Version
Migration Period
```

according to the client ecosystem.

---

# 70. Renaming Fields

Treat field renaming as a contract change.

Do not silently rename:

```text
driver_id
```

to:

```text
driverId
```

without considering existing clients.

---

# 71. API Deprecation

Deprecated endpoints should have:

```text
Reason
Replacement
Deprecation Timeline
Owner
```

where the API lifecycle requires formal deprecation.

---

# 72. API Logging

Do not log complete request/response bodies by default.

Avoid logging:

```text
Passwords
Tokens
Payment Data
Private Location Data
Sensitive Identity Data
```

Log enough metadata to diagnose the operation safely.

# 87. AI Agent API Rules

Before implementing an API change, an AI agent must:

1. Identify the endpoint and business capability.
2. Read the relevant API contract.
3. Inspect existing routing/handler conventions.
4. Identify authentication requirements.
5. Identify authorization requirements.
6. Identify request validation.
7. Identify application service ownership.
8. Identify response/error contracts.
9. Identify idempotency requirements.
10. Identify database/Redis/messaging side effects.
11. Identify timeout and cancellation behaviour.
12. Review compatibility with existing clients.
13. Add or update appropriate tests.
14. Review logging and observability.
15. Review sensitive-data exposure.
16. Run relevant validation.
17. Review the final diff.

---

# 88. AI Agent Forbidden API Patterns

AI agents must not:

- put core business logic directly in handlers,
- expose database models as API contracts without justification,
- execute SQL directly from handlers,
- manipulate Redis directly from handlers,
- publish arbitrary broker events from handlers,
- trust client-provided identity,
- skip authorization because an endpoint is internal-looking,
- accept arbitrary SQL filters or sort fields,
- return unbounded collections,
- expose raw stack traces or infrastructure errors,
- log tokens or sensitive request bodies,
- create inconsistent API versioning,
- change existing contracts without checking consumers,
- create long-running HTTP requests for asynchronous work without justification,
- claim API tests passed without running them.

# 90. Final API Principle

> **Keep the API thin, explicit, secure, versioned, validated, observable, and stable; let application and domain components own business behaviour.**

The intended RideForge API flow remains:

```text
HTTP Request
      ↓
Transport Validation
      ↓
Authentication
      ↓
Authorization
      ↓
Application Service
      ↓
Domain / Infrastructure
      ↓
Stable Application Result
      ↓
HTTP Response
```

The API is a boundary around the system.

It should expose the capabilities RideForge needs while protecting the internal architecture from transport-specific coupling.
