# 1. Purpose

Observability allows RideForge developers and operators to understand what the system is doing without modifying the running system to discover basic facts.

The observability strategy must provide:

```text
Metrics
+
Logs
+
Traces
+
Health Signals
+
Operational Context
```

These signals should work together rather than becoming independent telemetry systems.

---

# 2. Observability Principle

Observability should answer three questions:

```text
Is the system healthy?
        ↓
What is happening?
        ↓
Why is it happening?
```

Use:

```text
Metrics
→ System-wide behaviour

Logs
→ Detailed contextual events

Traces
→ Distributed request/event flow
```

---

# 3. Observability Architecture

The conceptual flow is:

```text
RideForge Components
        ↓
Instrumentation
        ↓
Telemetry
 ┌──────┼──────┐
 ↓      ↓      ↓
Metrics Logs  Traces
 └──────┼──────┘
        ↓
Collection / Backend
        ↓
Dashboards / Alerts / Investigation
```

The exact telemetry backend should follow the deployment architecture.

---

# 4. Observability Ownership

Each component should expose telemetry about its own meaningful behaviour.

Examples:

```text
API
→ Request rate, latency, errors

PostgreSQL
→ Query/operation latency, pool health, failures

Redis
→ Lookup latency, failures, pool health

Messaging
→ Publish failures, consumer lag, processing latency

Dispatch
→ Discovery, candidate counts, ranking, reservation outcomes
```

---

# 5. Three Primary Signals

RideForge observability is based on:

```text
Metrics
Logs
Traces
```

Do not use one signal as a complete replacement for the others.

---

# 6. Metrics

Metrics are numerical measurements aggregated over time.

Use metrics for:

```text
Rates
Counts
Latency
Capacity
Saturation
Errors
Queue / Consumer Lag
```

---

# 7. Metric Types

Use the metric type appropriate to the measurement.

Common types include:

```text
Counter
Gauge
Histogram
```

Follow the project's telemetry library and conventions.

---

# 8. Counters

Use counters for values that monotonically increase during process lifetime.

Examples:

```text
HTTP Requests
Event Publications
Event Processing Failures
Retries
DLQ Messages
Reservation Conflicts
```

Counters are interpreted as rates or changes over time.

---

# 9. Gauges

Use gauges for values that can increase and decrease.

Examples:

```text
Active Drivers
Connection Pool Usage
Queue Depth
Consumer Lag
In-Flight Requests
```

Do not use a counter when the value represents current state.

---

# 10. Histograms

Use histograms for distributions such as:

```text
Request Latency
Database Latency
Redis Latency
Candidate Discovery Latency
Event Processing Latency
```

Histograms are preferable to logging individual durations when aggregate latency analysis is required.

---

# 11. Latency Percentiles

Important latency signals may include:

```text
p50
p95
p99
```

Do not rely only on averages.

Averages can hide slow requests that materially affect users.

---

# 12. API Metrics

The API should expose meaningful metrics such as:

```text
Request Count
Request Latency
Error Count
Status Code Distribution
```

Useful dimensions include:

```text
HTTP Method
Route
Status Class
```

Avoid raw URLs as metric labels when they contain identifiers.

---

# 13. Route Cardinality

Do not create metric labels from raw paths such as:

```text
/rides/123
/rides/124
/rides/125
```

Use normalized routes such as:

```text
/api/v1/rides/{id}
```

This keeps cardinality bounded.

---

# 14. Dispatch Metrics

Dispatch is a critical operational workflow.

Useful metrics include:

```text
Dispatch Requests
Discovery Attempts
Candidates Found
Candidates Rejected
Ranking Duration
Reservation Attempts
Reservation Success
Reservation Conflict
Dispatch Success
Dispatch Failure
```

---

# 15. Candidate Metrics

Candidate pipeline metrics should remain aggregate.

Examples:

```text
Candidates Discovered
Candidates After Filtering
Candidates Ranked
Candidates Selected
```

Avoid putting:

```text
Driver ID
Ride ID
```

into metric labels.

Use logs/traces for individual investigations.

---

# 16. Discovery Metrics

Discovery should expose useful measurements such as:

```text
Lookup Count
Lookup Latency
Cells Examined
Candidates Returned
Empty Searches
Redis Failures
```

These help determine whether dispatch failures originate in discovery or later stages.

---

# 17. Ranking Metrics

Ranking telemetry may include:

```text
Ranking Duration
Candidates Ranked
Scoring Duration
Feature Extraction Duration
```

Do not create a metric for every individual candidate.

---

# 18. Reservation Metrics

Reservation is a critical correctness boundary.

Useful metrics include:

```text
Reservation Attempts
Reservation Success
Reservation Conflict
Reservation Failure
Reservation Latency
```

A rising conflict rate can indicate contention or stale candidate data.

---

# 19. Driver Location Metrics

For the Redis/H3 location index, useful aggregate metrics include:

```text
Location Updates
Same-Cell Updates
Cell Changes
Membership Additions
Membership Removals
Lookup Latency
Stale Driver Count
```

Do not expose exact coordinates through metrics.

---

# 20. Database Metrics

Database observability should include enough information to identify:

```text
Latency
Connection Pool Pressure
Connection Errors
Timeouts
Transaction Failures
Query Load
```

Use the established database monitoring architecture where available.

---

# 21. Database Pool Metrics

Important signals include:

```text
Open Connections
Idle Connections
Wait Count
Wait Duration
Pool Exhaustion
```

A high application latency with a healthy PostgreSQL server may still be caused by pool starvation.

---

# 22. Redis Metrics

Redis-backed components should expose:

```text
Command / Operation Count
Latency
Failures
Timeouts
Pool Wait
Memory-related Signals where available
```

The application should not expose every Redis command as a separate metric.

---

# 23. Redis Driver Index Metrics

The driver-location index should make it possible to understand:

```text
How many location updates occur?
How often do drivers change cells?
How large are candidate lookups?
How often does discovery return nothing?
How often does Redis fail?
```

These signals help distinguish dispatch demand from infrastructure failure.

---

# 24. Messaging Metrics

Messaging telemetry should include:

```text
Events Produced
Publication Failures
Events Consumed
Processing Failures
Retries
DLQ Messages
Consumer Lag
Processing Latency
```

---

# 25. Consumer Lag

Consumer lag is a critical event-driven health signal.

A growing lag indicates:

```text
Incoming Rate
>
Processing Capacity
```

or a blocked/stalled consumer.

Lag should be monitored by consumer group and topic at an appropriate bounded cardinality.

---

# 26. Consumer Processing Latency

Measure the time required to process messages.

Useful dimensions may include:

```text
Topic
Consumer Group
Event Type
```

Only use event type when its cardinality remains controlled.

---

# 27. Outbox Metrics

The outbox mechanism should expose signals such as:

```text
Pending Outbox Records
Publication Success
Publication Failure
Publication Retry
Oldest Pending Record Age
```

The age of the oldest pending record is especially useful for detecting publication stalls.

---

# 28. DLQ Metrics

Monitor:

```text
DLQ Messages
DLQ Rate
DLQ Growth
```

A continuously growing DLQ is an operational problem even if the main service remains available.

---

# 29. External Dependency Metrics

External providers should be measured through:

```text
Request Count
Latency
Error Rate
Timeouts
Rate Limits
```

Do not expose sensitive provider data through metric labels.

---

# 30. Business Metrics

Some business-level metrics are useful for operational understanding.

Examples:

```text
Rides Created
Rides Matched
Rides Cancelled
Dispatch Success Rate
No-Candidate Rate
```

Business metrics should be intentionally defined and owned.

---

# 31. Business vs Technical Metrics

Keep the distinction clear:

```text
Technical
→ Redis latency

Business
→ Dispatch success rate
```

Both are useful, but they answer different questions.

---

# 32. Tracing

Distributed tracing should connect operations across component boundaries.

Conceptually:

```text
HTTP Request
    ↓
Ride Service
    ↓
PostgreSQL
    ↓
Outbox
    ↓
Kafka / Redpanda
    ↓
Matching Consumer
    ↓
Redis Discovery
    ↓
Reservation
```

---

# 33. Trace Context

Trace context should be propagated through supported boundaries.

For synchronous operations:

```text
HTTP
 ↓
Application
 ↓
Database / Redis
```

For asynchronous operations:

```text
Producer
 ↓
Event
 ↓
Consumer
```

The event/messaging architecture should define the exact propagation mechanism.

---

# 34. Span Design

Create spans around meaningful operations.

Good candidates include:

```text
HTTP Request
Database Operation
Redis Discovery
Candidate Pipeline
Event Publication
Event Consumption
Reservation
External Provider Call
```

Do not create a span for every trivial function.

---

# 35. Span Attributes

Useful attributes may include:

```text
component
operation
event_type
topic
dependency
outcome
```

Avoid sensitive data and high-cardinality identifiers unless the tracing policy explicitly permits them.

---

# 36. Trace IDs vs Business IDs

Business identifiers and trace identifiers serve different purposes.

```text
Trace ID
→ Distributed execution

Ride ID
→ Business entity
```

Use both where safe, but do not replace one with the other.

---

# 37. Trace Sampling

Tracing can be expensive.

Use an intentional sampling strategy.

Important failures and high-value workflows should remain observable even when normal traffic is sampled.

---

# 38. Error Sampling

If the tracing system supports it, error traces should receive higher retention priority than ordinary successful traces.

Do not allow sampling to hide systemic failures.

---

# 39. Debug Sampling

Detailed tracing may be enabled temporarily for controlled investigation.

Do not leave expensive debug tracing permanently enabled on high-throughput production paths without justification.

---

# 40. Health Signals

Health should be represented through appropriate:

```text
Liveness
Readiness
Dependency Health
Operational Metrics
```

---

# 41. Liveness

Liveness answers:

```text
Is this process alive?
```

It should not normally fail simply because one external dependency is temporarily unavailable.

Otherwise a dependency outage can cause unnecessary restart loops.

---

# 42. Readiness

Readiness answers:

```text
Can this instance safely receive work?
```

Readiness may consider required dependencies according to the deployment architecture.

---

# 43. Dependency Health

Dependency health should distinguish:

```text
Healthy
Degraded
Unavailable
```

Do not collapse all dependency states into a generic boolean when more useful information is available internally.

---

# 44. Startup Health

Startup telemetry should make it possible to determine:

```text
Application Started
Dependencies Initialized
Consumers Started
HTTP Server Started
```

without exposing secrets.

---

# 45. Shutdown Health

Shutdown should be observable.

Useful lifecycle events include:

```text
Shutdown Requested
Workers Stopped
Consumers Stopped
HTTP Server Stopped
Dependencies Closed
```

---

# 50. Alerting Principle

Alerts should indicate conditions requiring action.

Avoid alerting on every:

```text
Validation Error
404
Expected Conflict
Transient Single Request Failure
```

---

# 51. Alert Categories

Important alert categories may include:

```text
Availability
Latency
Error Rate
Dependency Failure
Consumer Lag
DLQ Growth
Resource Saturation
Data Freshness
```

---

# 52. API Error Alert

Alert on sustained server-side error rates rather than individual failures.

For example:

```text
5xx Rate
```

is generally more useful than:

```text
One 500 Response
```

---

# 53. Latency Alert

Alert when latency remains above the defined service objective for a sustained period.

Use percentile-based measurements where appropriate.

---

# 54. Dispatch Alert

Potential dispatch alerts include:

```text
Sustained Drop in Match Success
Unusual No-Candidate Rate
Reservation Conflict Spike
Discovery Failure Spike
```

These should be evaluated against normal traffic patterns.

---

# 55. Redis Alert

Potential Redis alerts include:

```text
Sustained Command Latency
Connection Pool Exhaustion
High Error Rate
Unavailable Redis
Unexpected Memory Pressure
```

---

# 56. PostgreSQL Alert

Potential database alerts include:

```text
Connection Pool Exhaustion
High Query Latency
Connection Failures
Sustained Transaction Failures
Database Unavailability
```

---

# 57. Messaging Alert

Potential messaging alerts include:

```text
Consumer Lag Growth
Publication Failure
DLQ Growth
Consumer Stopped
Outbox Backlog
```

---

# 58. Alert Quality

Every production alert should have:

```text
Meaning
Severity
Owner
Diagnostic Path
Expected Response
```

An alert without an operational response is often noise.

---

# 59. Cardinality

Metric cardinality must be controlled.

Avoid metric labels containing unbounded values such as:

```text
ride_id
driver_id
user_id
request_id
event_id
raw_url
coordinates
```

These belong in logs/traces when necessary.

---

# 60. Label Selection

Prefer bounded labels:

```text
route
method
status_class
component
operation
event_type
dependency
```

only where their possible values remain controlled.

---

# 61. Cardinality Review

Before adding a metric label ask:

```text
How many unique values can this field have?
```

If the answer grows with business traffic, it probably should not be a metric label.

---

# 62. Observability Cost

Telemetry consumes:

```text
CPU
Memory
Network
Storage
```

Do not instrument every function simply because instrumentation is technically possible.

---

# 63. Hot Path Instrumentation

Hot paths such as:

```text
Driver Location Updates
Candidate Discovery
Ranking
High-Volume API Requests
```

require especially careful instrumentation.

Prefer aggregate metrics and targeted traces.

---

# 64. Logging vs Metrics

Use logs for:

```text
Individual Failure
Specific Operation
Detailed Context
```

Use metrics for:

```text
Rate
Count
Trend
Capacity
```

Do not repeatedly log aggregate statistics that metrics already provide.

---

# 65. Logging vs Tracing

Use logs for detailed contextual records.

Use traces for:

```text
Cross-Service Flow
Latency Breakdown
Dependency Relationships
```

A trace should not be replaced by manually copying trace context into dozens of log messages when the tracing system already correlates them.

---

# 66. Observability and Privacy

Telemetry is data.

Apply the same discipline as application data:

```text
Minimize
Protect
Redact
Retain Appropriately
Control Access
```

---

# 67. Location Privacy

RideForge's location data requires special care.

Do not put exact coordinates into:

```text
Metrics
Routine Logs
Long-Lived Trace Attributes
```

unless there is a documented and justified operational requirement.

Prefer spatial abstractions such as H3 where appropriate.

---

# 68. Authentication Data

Never place authentication material into telemetry:

```text
Authorization Headers
Tokens
Cookies
Session Secrets
Signing Keys
```

---

# 69. Payment Data

Payment-sensitive information must not be logged or traced unless the security architecture explicitly permits a safe non-sensitive identifier.

---

# 70. Observability for Errors

Errors should connect:

```text
Error Code
Trace
Log
Metric
```

where practical.

This allows an operator to move from:

```text
High Error Rate
```

to:

```text
Specific Failure
```

to:

```text
Distributed Trace
```

---

# 71. Observability for Retries

Retries should be measurable.

Useful metrics:

```text
Retry Count
Retries by Component
Final Retry Failures
```

Do not use a unique request ID as a metric label.

---

# 72. Observability for Idempotency

Where duplicate operations matter, measure aggregate outcomes such as:

```text
Duplicate Event Count
Idempotency Conflict Count
Already-Processed Count
```

rather than logging every duplicate as an ERROR.

---

# 73. Observability for Outbox

The outbox should be operationally visible.

At minimum, operators should be able to determine:

```text
Are records accumulating?
Are they being published?
How old is the oldest pending record?
Are failures increasing?
```

---

# 74. Observability for DLQ

Operators should be able to determine:

```text
Is the DLQ growing?
Which event types are failing?
Are failures transient or permanent?
Has the failure been resolved?
```

Detailed individual investigation belongs in logs/traces.

---

# 75. Observability for Configuration

The system should expose non-sensitive runtime configuration state where useful.

For example:

```text
Environment
Application Version
Enabled Feature State
Operational Mode
```

Never expose secrets through health or metrics endpoints.

---

# 76. Version Information

Telemetry should allow operators to correlate behaviour with application version.

Useful information includes:

```text
Application Version
Build Version
Deployment Version
```

Use low-cardinality values.

---

# 77. Deployment Correlation

When an incident begins after a deployment, observability should make it possible to compare:

```text
Before Deployment
After Deployment
```

for:

```text
Error Rate
Latency
Dispatch Success
Consumer Lag
Dependency Health
```

---

# 78. SLO-Oriented Observability

Where service objectives are defined, observability should measure them directly.

Examples:

```text
API Availability
API p95 Latency
Dispatch Success
Event Processing Delay
```

Do not create SLOs merely because a metric is available.

---

# 79. Observability Testing

Instrumentation should be tested where incorrect telemetry would materially harm operations.

Test:

```text
Metric Registration
Metric Labels
Trace Propagation
Error Attributes
Redaction
Health Behaviour
```

---

# 80. Test Metric Cardinality

Metric tests should ensure that dynamic business identifiers do not accidentally become labels.

For example, a metric should not produce a new time series for every:

```text
Ride ID
Driver ID
Request ID
```

---

# 81. Test Trace Propagation

Distributed workflows should verify that trace context survives the relevant boundaries:

```text
HTTP
 ↓
Application
 ↓
Event
 ↓
Consumer
```

where the messaging architecture supports propagation.

---

# 82. Test Redaction

Security-sensitive telemetry should have explicit tests when redaction is implemented.

Verify that:

```text
Token
Password
Secret
Sensitive Payload
```

does not appear in emitted telemetry.

# 83. Local Observability

Local development should provide enough telemetry to debug the application without requiring the full production observability platform.

At minimum, developers should have access to:

```text
Structured Logs
Useful Error Context
Basic Health Signals
```

Additional local metrics/tracing can be enabled when needed.

---

# 84. Development vs Production Telemetry

Development may use:

```text
More Verbose Logs

```

```text
Signal Quality
Low Overhead
```

# 85. Observability During Incident Response

Incident investigation should follow:

```text
Alert
 ↓
Dashboard
 ↓
Metric
 ↓
Log
 ↓
Trace
 ↓
Dependency
 ↓
Root Cause
```

Do not start by changing application code simply because an alert fired.

---

# 86. Observability Anti-Patterns

Avoid:

```text
Metric Per Entity
Log Every Request Body
Log Every Redis Command
Log Every SQL Query
Trace Every Function
Alert on Every Error
Duplicate Telemetry Systems
Unbounded Labels
```

# 87. AI Agent Observability Rules

Before implementing telemetry, an AI agent must:

1. Identify the operational question the telemetry should answer.
2. Determine whether the signal belongs in metrics, logs, traces, or health checks.
3. Reuse existing instrumentation libraries and conventions.
4. Check metric cardinality.
5. Check sensitive-data exposure.
6. Check hot-path performance impact.
7. Reuse existing field and label names.
8. Avoid duplicate telemetry.
9. Add tests where telemetry correctness matters.
10. Review dashboards/alerts when the change affects an operational signal.
11. Verify the instrumentation.
12. Review the final diff.

---

# 88. AI Agent Forbidden Observability Patterns

AI agents must not:

- create metrics with unbounded business identifiers as labels,
- expose exact driver coordinates in routine telemetry,
- log secrets,
- put tokens into traces,
- create a new tracing system without architectural justification,
- create a metric for every function,
- create an alert for every error,
- use logs as a replacement for metrics,
- use metrics as a replacement for detailed logs,
- trace every trivial operation,
- add expensive instrumentation to hot paths without justification,
- duplicate existing telemetry,
- claim observability is implemented without validating emitted signals.

---

# 90. Final Observability Principle

> **Observability is not about collecting everything; it is about collecting the right signals so that RideForge can be understood, diagnosed, and operated safely under normal load and failure.**

The intended model is:

```text
                RideForge
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
      Metrics      Logs       Traces
        │           │           │
        └───────────┼───────────┘
                    ↓
             Operational View
                    ↓
          Detect → Diagnose → Recover
```

For RideForge, the most important observability path is:

```text
API
 ↓
Ride Application
 ↓
Dispatch
 ↓
Discovery
 ↓
Ranking
 ↓
Reservation
 ↓
Event
 ↓
Consumer
```

with infrastructure visibility across:

```text
PostgreSQL
Redis
Kafka / Redpanda
External Providers
```

The observability system must help answer not only:

```text
"Is RideForge up?"
```

but also:

```text
"Are rides being matched?"
"Why are candidates unavailable?"
"Is Redis slowing discovery?"
"Is PostgreSQL saturated?"
"Are consumers falling behind?"
"Are events reaching the right consumers?"
"Are reservation conflicts increasing?"
"Did the latest deployment change system behaviour?"
```

That is the standard required for operating RideForge as a production system.
