# 1. Purpose

Redis is used in RideForge for latency-sensitive operational workloads.

The Redis implementation must provide:

```text
Fast Access
Predictable Latency
Controlled Memory Usage
Correct Concurrent Behaviour
Safe Failure Handling
Recoverable Derived State
```

Redis must not become an accidental replacement for PostgreSQL when PostgreSQL is the authoritative source of durable business state.

---

# 2. Redis Role in RideForge

Redis should be used according to the responsibility defined by the architecture.

Primary use cases include:

```text
Driver Location Index
H3 Cell Membership
Fast Candidate Discovery
Short-Lived Operational State
Caching where explicitly defined
```

The exact responsibility of each Redis structure must remain documented.

---

# 3. Redis Is Not Automatically the Source of Truth

Before implementing a Redis-backed feature, explicitly determine:

```text
Is Redis Authoritative?
Is Redis Derived?
Is Redis a Cache?
Is Redis Ephemeral Operational State?
```

Do not assume every value stored in Redis has the same consistency requirements.

---

# 4. Authoritative vs Derived State

A common RideForge pattern is:

```text
PostgreSQL
    ↓
Authoritative Durable State

Redis
    ↓
Fast Operational / Derived State
```

If Redis contains derived state, the system must have a way to:

```text
Rebuild
Reconcile
Recover
```

from authoritative data.

---

# 5. Driver Location Index

The driver-location index is a latency-sensitive Redis component.

Conceptually:

```text
Driver Location
      ↓
H3 Cell
      ↓
Redis Cell Membership
      ↓
Candidate Discovery
```

The index should optimize spatial lookup rather than become a second complete driver database.

---

# 6. H3 Cell as the Spatial Index

The H3 cell is the primary spatial lookup unit for the driver-location index.

The design should support:

```text
Driver → Current Cell
Cell → Drivers
```

This allows discovery to expand through neighbouring H3 cells.

---

# 7. Driver-to-Cell State

The system should maintain enough state to determine the driver's current cell.

Conceptually:

```text
Driver ID
    ↓
Current H3 Cell
```

This enables the system to detect:

```text
Same-Cell Update
Different-Cell Update
```

without reconstructing state from an expensive spatial search.

---

# 8. Cell-to-Driver Membership

The inverse index should support:

```text
H3 Cell
    ↓
Available Driver IDs
```

Candidate discovery can then inspect relevant cells rather than scanning every driver.

---

# 9. Location Update Flow

A location update should conceptually follow:

```text
Receive Driver Location
        ↓
Validate Location
        ↓
Calculate H3 Cell
        ↓
Read Previous Cell
        ↓
Same Cell?
   ┌────┴────┐
  Yes        No
   ↓          ↓
Refresh     Remove Old
Required    Membership
State           ↓
            Add New
            Membership
```

The exact stored fields and command sequence must follow the implementation already established by the repository.

---

# 10. Same-Cell Updates

If a driver remains in the same H3 cell:

```text
Do Not Move Membership
```

Only state that genuinely requires refreshing should be updated.

This avoids unnecessary Redis writes.

---

# 11. Cell Changes

When a driver moves to a different H3 cell:

```text
Old Cell
   ↓
Remove Driver

New Cell
   ↓
Add Driver

Driver State
   ↓
Update Current Cell
```

The implementation must consider failure between these operations and provide appropriate recovery/reconciliation behaviour.

---

# 12. Availability State

The cell index should contain only drivers eligible for the discovery strategy that owns the index.

Do not assume:

```text
Driver Exists
```

means:

```text
Driver Is Available for Matching
```

Availability is a business/application state.

---

# 13. Redis Key Naming

Redis keys must use a stable namespace.

A conceptual structure may look like:

```text
rideforge:{environment}:{component}:{resource}:{id}
```

The exact naming convention should follow the existing repository implementation.

Do not introduce multiple naming styles.

---

# 14. Key Names Must Be Predictable

A key should make its ownership and purpose understandable.

Prefer:

```text
Component
+
Resource
+
Identifier
```

over opaque keys whose meaning can only be discovered by reading implementation code.

---

# 15. Key Collisions

Different components must not accidentally share the same key namespace.

Use explicit prefixes for:

```text
Driver State
H3 Membership
Cache
Locks
Temporary State
```

where those structures exist.

---

# 16. Environment Isolation

Development, staging, and production Redis data must not accidentally share the same namespace.

Environment separation should be enforced by the deployment architecture.

---

# 17. TTL

Every Redis value that represents temporary state should have a clearly defined lifetime.

For each TTL-backed structure, document:

```text
Why TTL Exists
TTL Duration
Refresh Behaviour
Expiration Consequence
Recovery Behaviour
```

---

# 18. Location Freshness

Driver location data becomes stale.

The location index should therefore have an explicit freshness model.

Conceptually:

```text
Fresh Update
    ↓
Refresh Freshness

No Update for Too Long
    ↓
Driver Becomes Stale / Ineligible
```

The exact stale threshold belongs to the dispatch/business configuration.

Do not invent a new threshold inside a Redis adapter.

---

# 19. TTL Refresh

TTL refresh must correspond to actual business freshness semantics.

Do not blindly refresh TTL on unrelated operations.

A driver should not remain apparently active merely because another process happens to access its Redis key.

---

# 20. Expiration Semantics

Expiration must not silently create incorrect business state.

If Redis expiration causes a driver to disappear from discovery:

```text
Expected Behaviour
```

must be defined.

If the state is recoverable:

```text
Reconciliation / Fresh Location Update
```

should restore it.

---

# 21. Redis Commands

Use the Redis client abstraction already established in the repository.

Do not spread raw Redis client details through application/domain code.

Preferred:

```text
Application
    ↓
Redis Component / Repository
    ↓
Redis Client
```

---

# 22. Redis Repository Boundary

Redis-specific operations should remain inside the appropriate repository/component.

The application layer should reason about:

```text
Driver Location
Cell Membership
Candidate Lookup
```

rather than:

```text
ZADD
SADD
SMEMBERS
GET
SET
```

unless the architecture explicitly exposes those primitives.

---

# 23. Atomicity

A single Redis command may be atomic, but a sequence of commands is not automatically atomic as a whole.

Do not assume:

```text
GET
+
SET
```

is one atomic business operation.

---

# 24. Multi-Step State Changes

If correctness requires multiple Redis operations to behave atomically, use an appropriate mechanism:

```text
Atomic Redis Command
Transaction
Lua Script
Database Authority
```

according to the actual invariant.

Do not introduce Lua merely because it is available.

---

# 25. Lua Scripts

Lua is appropriate when a small Redis-side operation requires atomic read/modify/write behaviour.

Good candidates include:

```text
Conditional State Transition
Atomic Membership Update
Atomic Deduplication
```

Keep scripts:

```text
Small
Deterministic
Well-Tested
Documented
```

---

# 26. Lua Boundaries

Do not move large business workflows into Redis Lua.

Avoid putting:

```text
Ranking
Dispatch Policy
Complex Business Rules
External API Calls
```

inside Redis scripts.

Redis should remain an operational data component, not the business-logic runtime.

---

# 27. Pipelines

Use Redis pipelines when multiple independent commands can safely be sent together.

Benefits include:

```text
Fewer Network Round Trips
Lower Latency
Higher Throughput
```

---

# 28. Pipeline Correctness

A pipeline is not automatically a transaction.

Before batching operations, verify:

```text
Ordering Requirement
Atomicity Requirement
Failure Semantics
Result Dependency
```

If operation B depends on the result of operation A, a simple pipeline may not be sufficient.

---

# 29. Driver Cell Lookup

Candidate discovery may need to inspect multiple H3 cells.

Avoid:

```text
Network Round Trip
 ↓
Next Cell
 ↓
Network Round Trip
 ↓
Next Cell
```

when independent lookups can safely be batched.

Use the existing discovery/pipeline architecture.

---

# 30. Candidate Lookup Bounds

Redis lookups must remain bounded.

Discovery should define limits for:

```text
Maximum Cells
Maximum Candidates
Maximum Search Radius / Rings
Maximum Processing Time
```

according to the dispatch architecture.

Do not allow one request to trigger unbounded Redis work.

---

# 31. Empty Cells

Empty H3 cells are normal.

The discovery pipeline should handle:

```text
Cell Exists
Cell Empty
Cell Missing
```

without treating every empty cell as an error.

---

# 32. Missing Keys

A missing Redis key must have explicit semantics.

For example:

```text
No Drivers in Cell
```

may be normal.

Whereas:

```text
Required Configuration Key Missing
```

may be an error.

Do not treat all missing keys identically.

---

# 33. Redis Errors

Distinguish:

```text
Key Does Not Exist
```

from:

```text
Redis Unavailable
```

and:

```text
Redis Command Failed
```

A missing operational value is often different from a Redis infrastructure failure.

---

# 34. Redis Failure Behaviour

Every Redis-backed feature must define what happens when Redis is unavailable.

Possible policies include:

```text
Fail Request
Degrade
Use Fallback
Retry
Rebuild / Reconcile Later
```

The correct policy depends on whether Redis is:

```text
Authoritative
Derived
Cache
Operational Accelerator
```

---

# 35. Driver Discovery and Redis Failure

If Redis is the primary fast driver-location index, a Redis failure may prevent normal candidate discovery.

Do not silently return:

```text
No Drivers
```

if the real reason is:

```text
Redis Unavailable
```

The application must preserve the distinction between:

```text
No Candidate
```

and:

```text
Discovery Infrastructure Failed
```

---

# 36. Retry Policy

Redis operations should not retry indefinitely.

Retries must be:

```text
Bounded
Context-Aware
Backoff-Aware
Safe for the Operation
```

---

# 37. Retry Safety

Before retrying a Redis operation, determine whether it is:

```text
Read
Idempotent Write
Non-Idempotent Write
Atomic State Transition
```

Do not blindly retry a potentially non-idempotent operation.

---

# 38. Timeouts

Redis operations should respect the request or operation deadline.

Do not allow a Redis call to block indefinitely.

---

# 39. Context Propagation

Pass the appropriate `context.Context` through Redis operations.

Do not replace request-scoped context with an unrelated background context.

---

# 40. Connection Pooling

The Redis client should use controlled connection pooling according to the application's workload.

Do not create a new Redis connection for every request.

---

# 41. Pool Sizing

More Redis connections do not automatically produce more throughput.

Tune pool size based on:

```text
Concurrency
Redis Capacity
Network
Command Latency
Application Load
```

---

# 42. Connection Exhaustion

Observe:

```text
Pool Usage
Wait Time
Connection Errors
Command Latency
```

A Redis pool that is too small can cause application latency even when Redis itself is healthy.

---

# 43. Memory Management

Redis is memory-oriented infrastructure.

Avoid:

```text
Unbounded Sets
Large Payloads
Unnecessary Duplicate Data
Long-Lived Temporary Keys
Unbounded History
```

---

# 44. Cardinality

Monitor the number of:

```text
Drivers
Cells
Keys
Membership Entries
Cached Objects
```

where those quantities can grow significantly.

---

# 45. Driver Membership Cleanup

Driver membership must not accumulate indefinitely.

When a driver:

```text
Leaves Availability
Disconnects
Becomes Stale
Moves Cell
```

the relevant membership should be cleaned or expire according to the component design.

---

# 46. Duplicate Membership

The Redis data structure should prevent or tolerate duplicate driver membership appropriately.

Do not rely on application code alone if the Redis structure itself can provide uniqueness.

---

# 47. Stale Membership

A stale cell membership can create false candidates.

The discovery pipeline must therefore combine:

```text
Fast Redis Candidate
+
Current Application Eligibility
```

where required.

Do not assume Redis membership is always perfectly current.

---

# 48. Candidate Eligibility

Redis discovery should find possible candidates.

Final eligibility may still depend on:

```text
Driver State
Availability
Region
Vehicle Type
Ride Requirements
Reservation State
Business Rules
```

These belong to the appropriate application/domain components.

---

# 49. Redis Does Not Own Ranking

Redis should not become the place where complex candidate ranking rules are implemented unless explicitly designed for a specific optimization.

The existing candidate architecture should continue to own:

```text
Filtering
Enrichment
Feature Extraction
Scoring
Ranking
```

---

# 50. Redis Does Not Own Reservation

Redis location state should help identify candidates.

Reservation correctness must be enforced by the authoritative concurrency boundary.

Do not treat:

```text
Driver Appears in Redis
```

as:

```text
Driver Successfully Reserved
```

---

# 51. Race Between Discovery and Reservation

The expected sequence is:

```text
Redis Discovery
    ↓
Candidate
    ↓
Application Validation
    ↓
Authoritative Reservation
```

The driver can change state between discovery and reservation.

The reservation operation must therefore revalidate the authoritative state.

---

# 52. Redis and PostgreSQL Consistency

Redis and PostgreSQL may temporarily disagree when Redis is derived state.

The architecture should define which system wins.

A common pattern is:

```text
PostgreSQL
→ Source of Truth

Redis
→ Rebuildable Operational Index
```

Do not create ad-hoc conflict resolution in individual features.

---

# 53. Reconciliation

A Redis index that represents derived state should have a reconciliation strategy.

Conceptually:

```text
Authoritative State
      ↓
Compare
      ↓
Redis Index
      ↓
Repair Differences
```

Reconciliation should be bounded and observable.

---

# 54. Rebuild

For recoverable Redis structures, the system should be able to rebuild the index from authoritative data.

A rebuild process should define:

```text
Source
Batch Size
Concurrency
Failure Handling
Progress
Completion
Verification
```

---

# 55. Rebuild Safety

Do not rebuild a production index using an uncontrolled script that:

```text
Consumes Unlimited Memory
Overloads PostgreSQL
Overloads Redis
Blocks Dispatch
```

Use bounded processing.

---

# 56. Cache Development

When Redis is used as a cache:

```text
Cache Miss
 ↓
Authoritative Lookup
 ↓
Populate Cache
```

The application must remain correct if the cache is empty.

---

# 57. Cache Invalidation

Every cache should define how stale values are removed.

Possible strategies:

```text
TTL
Explicit Invalidation
Versioned Keys
Write-Through
Write-Behind
```

Use the simplest strategy that satisfies correctness.

---

# 58. Cache Consistency

A cached value may be stale.

The application must know whether stale data is:

```text
Acceptable
Temporarily Acceptable
Unacceptable
```

Do not silently use stale cache data for a business decision that requires current authoritative state.

---

# 59. Cache Stampede

If many requests miss the same key simultaneously, they may overload the source system.

Where measured as a real risk, use:

```text
Request Coalescing
Short Lock
Stale-While-Revalidate
Precomputation
```

according to the cache architecture.

---

# 60. Cache Failure

A cache failure should not automatically become a system-wide outage when the cache is non-authoritative.

Where safe:

```text
Redis Failure
    ↓
Fallback to Source
```

But only when the source can handle the resulting load.

---

# 61. Cache Warming

Cache warming should be used only when cold-cache performance is unacceptable.

Do not add a startup process that loads the entire database into Redis without a demonstrated requirement.

---

# 62. Serialization

Redis values should use the project's established serialization approach.

Avoid storing large opaque blobs when the application only needs a small number of fields.

---

# 63. Serialization Compatibility

If serialized values persist across deployments, schema evolution must be considered.

Do not change the format in a way that makes existing Redis data unreadable without a migration/rebuild strategy.

---

# 64. TTL and Deployment

When changing TTL semantics:

```text
Existing Keys
+
New Keys
+
Old Application
+
New Application
```

must be considered.

Do not assume all Redis state disappears immediately after deployment.

---

# 65. Key Migration

When Redis key structure changes, use a deliberate migration strategy:

```text
Dual Read / Write
Rebuild
Versioned Namespace
Controlled Flush
```

according to the data's role.

Do not casually flush production Redis to solve a schema change.

---

# 66. Redis Flush Operations

Commands equivalent to:

```text
FLUSHDB
FLUSHALL
```

must never be used casually in production.

A flush can destroy unrelated operational state.

---

# 67. Production Debugging

Avoid manually changing production Redis state unless the operation is:

```text
Authorized
Documented
Targeted
Recoverable
```

Prefer application-level repair/reconciliation mechanisms.

---

# 68. Redis Security

Production Redis should use the deployment's:

```text
Authentication
TLS where required
Network Isolation
Access Control
```

Do not expose Redis directly to untrusted clients.

---

# 69. Redis Credentials

Redis credentials must never appear in:

```text
Source Code
Logs
Metrics
Traces
API Responses
Git
```

---

# 70. Redis Observability

Redis-backed components should expose enough telemetry to understand:

```text
Operation Count
Latency
Errors
Pool Wait
Memory
Key Growth
Lookup Size
```

The exact instrumentation should follow:

```text
9.OBSERVABILITY_DEVELOPMENT_GUIDELINES.md
```

and the repository's observability architecture.

---

# 71. H3 Index Metrics

The driver-location component should retain meaningful measurements such as:

```text
Cell Changes
Same-Cell Updates
Drivers Added
Drivers Removed
Lookup Latency
Drivers Per Cell
```

These metrics should remain bounded in cardinality.

---

# 72. Redis Logging

Do not log every Redis command.

Prefer meaningful operational events such as:

```text
Redis Unavailable
Reconciliation Started
Reconciliation Completed
Rebuild Failed
Unexpected State
```

---

# 73. Sensitive Location Logging

Do not log exact driver coordinates merely to diagnose ordinary Redis operations.

Prefer:

```text
Driver Identifier where safe
H3 Cell
Operation
Outcome
```

when sufficient.

---

# 74. Redis Testing

Redis-backed functionality should be tested at multiple levels:

```text
Unit
Component
Integration
Concurrency
Failure
Recovery
```

according to the behaviour being verified.

---

# 75. Unit Testing Redis Components

Unit tests should cover application behaviour independent of a real Redis server where practical.

Examples:

```text
Same-Cell Decision
Cell Change Decision
Error Classification
Key Construction
Input Validation
```

---

# 76. Redis Integration Tests

Use a real Redis instance when correctness depends on:

```text
Redis Commands
Pipelines
Lua
TTL
Atomicity
Data Structures
```

Mocks cannot fully prove Redis semantics.

---

# 77. Location Index Integration Tests

Important scenarios include:

```text
Add Driver
Update Same Cell
Move Cell
Remove Driver
Lookup Cell
Lookup Empty Cell
Stale Driver
Redis Failure
```

---

# 78. Atomicity Tests

If an operation depends on Redis atomicity, test concurrent execution.

Example:

```text
N Concurrent Operations
        ↓
Atomic Redis Boundary
        ↓
Expected Single / Consistent Result
```

---

# 79. TTL Tests

TTL-related tests should verify:

```text
Key Created
TTL Applied
TTL Refreshed when Required
Expired State Behaves Correctly
```

Avoid tests that depend on unnecessarily long real-time sleeps.

Use controlled/test-friendly timing where practical.

---

# 80. Failure Tests

Redis failure tests should distinguish:

```text
Redis Unavailable
Command Error
Timeout
Missing Key
```

and verify that each produces the expected application outcome.

---

# 81. Reconciliation Tests

Reconciliation tests should verify:

```text
Missing Membership
Stale Membership
Unexpected Membership
Correct Membership
```

are detected and repaired according to policy.

---

# 82. Performance Testing

Redis performance testing should measure:

```text
Lookup Latency
Write Latency
Pipeline Throughput
Candidate Retrieval
Concurrent Location Updates
```

under realistic workloads.

---

# 83. Avoid Premature Redis Optimization

Do not introduce:

```text
Lua
Complex Pipelines
Distributed Locks
Multiple Redis Clusters
Custom Serialization
```

without a measured requirement.

Simple Redis operations are preferable when they satisfy correctness and performance requirements.

---

# 84. Redis Change Compatibility

Before changing a Redis structure, determine:

```text
Who Writes It?
Who Reads It?
Is It Durable?
Is It Derived?
Is It Cached?
Can It Be Rebuilt?
What Happens During Rolling Deployment?
```

---

# 85. AI Agent Redis Rules

An AI agent implementing Redis-related changes must:

1. Read the Redis architecture documentation.
2. Inspect existing Redis key conventions.
3. Identify whether the data is authoritative, derived, or cached.
4. Reuse the existing Redis abstraction.
5. Preserve H3 index semantics.
6. Preserve driver availability semantics.
7. Define TTL behaviour.
8. Consider atomicity.
9. Consider concurrent updates.
10. Consider Redis failure.
11. Consider PostgreSQL/Redis consistency.
12. Add integration tests when Redis semantics matter.
13. Add concurrency tests when atomicity matters.
14. Review observability and sensitive-data exposure.
15. Review the final diff.

---

# 86. AI Agent Forbidden Redis Patterns

AI agents must not:

- introduce a second Redis abstraction without architectural justification,
- expose raw Redis commands throughout application code,
- assume Redis is the source of truth without documentation,
- use Redis presence as proof of driver availability,
- use unbounded keys or collections,
- create indefinite TTLs for temporary state without justification,
- use `FLUSHDB`/`FLUSHALL` as a migration strategy,
- introduce distributed locks without evaluating simpler alternatives,
- move business ranking/reservation logic into Redis,
- ignore Redis failure semantics,
- log precise location data unnecessarily,
- hard-code Redis credentials,
- claim Redis integration/concurrency tests passed without running them.

---

---

# 88. Final Redis Principle

> **Use Redis as a deliberately bounded operational data component: optimize for fast access and predictable latency while keeping ownership, freshness, atomicity, recovery, and failure semantics explicit.**

For RideForge, the critical Redis path is:

```text
Driver Location
      ↓
H3 Cell
      ↓
Redis Membership
      ↓
Candidate Discovery
      ↓
Application Filtering
      ↓
Ranking
      ↓
Authoritative Reservation
```

Redis accelerates dispatch.

It must not silently become the owner of business truth merely because it is fast.
