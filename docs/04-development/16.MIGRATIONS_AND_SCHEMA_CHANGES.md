# 1. Purpose

Database schema changes are production changes.

A migration must preserve:

```text
Data Integrity
+
Application Compatibility
+
Deployment Safety
+
Rollback / Recovery
+
Performance
```

Schema evolution must be deliberate because application instances, workers, migrations, and database versions can temporarily coexist during deployment.

---

# 2. Migration Principle

The database schema should evolve through versioned migrations.

Prefer:

```text
Migration
    ↓
Review
    ↓
Test
    ↓
Deploy
```

over:

```text
Manual Production SQL
```

Manual SQL may be used for controlled operational recovery when explicitly required, but it must not replace normal schema evolution.

---

# 3. Source of Truth

Migration files are the source of truth for schema evolution.

Application code should not assume that a database change exists merely because a model or repository was changed.

The required flow is:

```text
Schema Requirement
        ↓
Migration
        ↓
Application Code
        ↓
Tests
```

---

# 4. Migration Tooling

Use the migration mechanism already established by the RideForge repository.

Do not introduce a second migration framework merely for convenience.

The selected tooling must provide:

```text
Versioning
Ordering
Migration Tracking
Forward Application
Controlled Rollback where supported
```

---

# 5. Migration Naming

Migration files should follow the existing repository convention.

A migration name should communicate:

```text
Order / Version
+
Purpose
```

Examples conceptually:

```text
001_create_rides
002_add_driver_status
003_add_ride_indexes
```

Use the actual naming convention already present in the repository.

---

# 6. Migration Atomicity

Where PostgreSQL and the migration operation support transactional execution, prefer transactional migrations.

A migration should avoid leaving the database in a partially modified state when an operation fails.

Not every PostgreSQL operation is safely transactional, so migration authors must understand the behaviour of the statements they introduce.

---

# 7. Migration Ordering

Migrations are ordered and should be applied sequentially.

Do not:

```text
Create Migration 10
```

while assuming:

```text
Migration 9
```

will not exist in another environment.

Never rewrite migration history that may already have been applied to shared environments.

---

# 8. Immutable Migration History

Once a migration has been applied to a shared environment, treat it as immutable.

Do not edit an already-applied migration to change its meaning.

Instead:

```text
Existing Migration
        ↓
New Migration
        ↓
Corrective Change
```

---

# 9. Migration Dependencies

A migration may depend on objects created by previous migrations.

Make dependencies explicit through ordering.

For example:

```text
Create Table
    ↓
Add Constraint
    ↓
Add Index
    ↓
Add Data Transformation
```

Do not assume a database already contains objects that are not created by the migration history.

---

# 10. Schema Changes

Schema changes include:

```text
Create Table
Alter Table
Add Column
Remove Column
Rename Column
Add Constraint
Remove Constraint
Create Index
Drop Index
Create / Alter Type
Create Function
Create Trigger
```

Treat all of these as production-impacting changes.

---

# 11. Adding a Column

Adding a nullable column is usually easier to roll out than immediately adding a required column.

A safer evolution may be:

```text
1. Add Nullable Column
2. Deploy Application Supporting Both States
3. Backfill Data
4. Validate Data
5. Enforce Required Constraint
6. Deploy Application Assuming Required Value
```

The exact sequence depends on the data and deployment strategy.

---

# 12. Adding a Non-Nullable Column

Avoid directly adding a required column to a large populated table when doing so requires an expensive table rewrite or immediate data population.

Prefer a staged migration:

```text
Add Column
    ↓
Backfill
    ↓
Validate
    ↓
Add Constraint
```

Measure the expected impact before production execution.

---

# 13. Column Defaults

A database default and an application default are different concepts.

Define intentionally:

```text
Database Default
→ Protects database-level inserts

Application Default
→ Controls application behaviour
```

Do not add both automatically.

---

# 14. Backfilling Data

A data backfill transforms existing records.

Before performing one, determine:

```text
Rows Affected
Execution Time
Lock Behaviour
Write Load
Failure Recovery
Restart Behaviour
```

---

# 15. Large Backfills

Large tables should generally be backfilled in bounded batches where practical.

Conceptually:

```text
Read Batch
 ↓
Transform
 ↓
Write Batch
 ↓
Commit
 ↓
Next Batch
```

Avoid one massive transaction when it creates unacceptable:

```text
Lock Duration
WAL Growth
Memory Usage
Replication Pressure
```

---

# 16. Idempotent Backfills

A backfill should ideally be safe to resume.

Prefer logic that can determine:

```text
Already Processed
```

versus:

```text
Still Needs Processing
```

This reduces recovery complexity.

---

# 17. Backfill Validation

After a backfill, verify:

```text
Expected Row Count
Unexpected NULLs
Invalid Values
Constraint Compatibility
Application Behaviour
```

Do not assume successful SQL execution means the transformed data is correct.

---

# 18. Zero-Downtime Schema Evolution

When rolling deployments are possible, schema changes should generally follow:

```text
Expand
    ↓
Deploy Compatible Code
    ↓
Migrate / Backfill
    ↓
Validate
    ↓
Contract
```

This reduces incompatibility between old and new application versions.

---

# 19. Expand Phase

Expand means adding new database structures without breaking the currently deployed application.

Examples:

```text
Add Nullable Column
Add New Table
Add New Index
Add Compatible Constraint
```

---

# 20. Compatible Application

During the expand phase, the application should support:

```text
Old Schema State
+
New Schema State
```

where rolling deployment requires it.

---

# 21. Contract Phase

Contract removes structures no longer required.

Examples:

```text
Drop Old Column
Drop Old Index
Remove Deprecated Constraint
Remove Temporary Compatibility Structure
```

Contract should happen only after the application no longer depends on the old structure.

---

# 22. Column Rename

A direct rename can break older application instances.

For rolling deployments, prefer:

```text
Add New Column
        ↓
Write Both if Necessary
        ↓
Backfill
        ↓
Read New Column
        ↓
Stop Writing Old Column
        ↓
Remove Old Column
```

Use a direct rename only when deployment compatibility is guaranteed.

---

# 23. Column Removal

Before removing a column:

```text
Search Application Code
Search Queries
Search Repositories
Search Reports / Jobs
Search Operational Tools
```

Confirm that no active component depends on it.

---

# 24. Table Removal

Before dropping a table, verify:

```text
Application References
Foreign Keys
Jobs
Consumers
Scripts
Operational Tools
```

Table removal should normally be a deliberate final contract step.

---

# 25. Index Creation

Indexes can improve read performance but add:

```text
Write Cost
Storage
Maintenance
Build Time
```

Before adding an index, verify the query pattern.

Follow:

```text
14.PERFORMANCE_AND_OPTIMIZATION.md
```

for performance analysis.

---

# 26. Large Indexes

Large production indexes require operational planning.

Consider:

```text
Build Duration
Lock Behaviour
Disk Space
Write Load
Replication Impact
```

Use the PostgreSQL index creation strategy appropriate for the deployment environment.

---

# 27. Concurrent Index Creation

When an index must be created without blocking normal writes, PostgreSQL's concurrent index creation may be appropriate.

However, it has different transactional and failure semantics.

Do not use it automatically.

Understand the migration framework's support for such operations before adding them.

---

# 28. Dropping Indexes

Before removing an index:

```text
Check Query Plans
Check Application Workload
Check Existing Indexes
Check Production Usage
```

An index that appears redundant may support an important workload.

---

# 29. Unique Constraints

Unique constraints are correctness mechanisms.

They should be used when the invariant must hold regardless of application path.

Examples may include:

```text
Unique Business Identifier
Unique Event Identifier
Unique Idempotency Key
```

Use the actual domain invariants defined by RideForge.

---

# 30. Adding a Unique Constraint

Before adding uniqueness:

```text
Find Duplicate Rows
Resolve Duplicates
Verify Clean State
Add Constraint
```

Do not assume existing data satisfies a newly introduced invariant.

---

# 31. Foreign Keys

Foreign keys protect relational integrity.

Before adding one:

```text
Find Orphan Rows
Clean Invalid References
Add Constraint
```

Consider the impact of the constraint on existing application workflows.

---

# 32. Constraint Changes

Constraints should reflect domain/data invariants.

Do not add constraints simply to make invalid application states impossible without understanding:

```text
Existing Data
Legacy Behaviour
Deployment Compatibility
```

---

# 33. Check Constraints

Check constraints are useful for invariants that belong at the database level.

Examples may include:

```text
Non-Negative Amount
Valid State Representation
Valid Range
```

Use them when the invariant is stable and database-enforceable.

---

# 34. Enum / State Changes

RideForge contains stateful workflows such as:

```text
Ride
Driver
Matching
Reservation
```

When changing state values:

```text
Add New State
        ↓
Deploy Compatible Code
        ↓
Migrate / Transition Data
        ↓
Remove Deprecated State
```

Do not immediately remove an old state if older application instances can still produce it.

---

# 35. State Transition Safety

Schema changes must not allow invalid business state transitions merely because a new database representation exists.

Database schema and domain rules must evolve together.

---

# 36. Database Types

Changes to PostgreSQL types require compatibility analysis.

Consider:

```text
Existing Rows
Application Driver Behaviour
Serialization
Queries
Indexes
Constraints
```

Do not modify a type used by production code without testing both old and new representations.

---

# 37. JSON / JSONB Schema Changes

When JSON/JSONB data is used, application-level schema evolution must be considered even when the PostgreSQL table schema does not change.

A change to:

```text
JSON Field
```

can still be a compatibility change.

---

# 38. Event Schema vs Database Schema

Database schema and event schema are related but distinct.

A database migration must not silently break event consumers.

When both change:

```text
Database Compatibility
+
Event Compatibility
```

must be reviewed together.

---

# 39. Outbox Schema Changes

The outbox is part of the event-driven architecture.

Changes to outbox structures must consider:

```text
Producer
Publisher
Retry Logic
Consumers
Operational Inspection
```

Do not modify outbox columns without checking the publication workflow.

---

# 40. Event and Messaging Migration

When a schema change affects event payload generation:

```text
Database Migration
+
Application Compatibility
+
Event Contract Compatibility
```

must be deployed in a safe order.

Follow:

```text
8.EVENT_AND_MESSAGING_DEVELOPMENT.md
```

for event-specific rules.

---

# 41. Migration and Application Deployment

A deployment involving schema changes should have an explicit order.

A common pattern is:

```text
1. Apply Expand Migration
2. Deploy Compatible Application
3. Backfill / Transition Data
4. Verify
5. Deploy Final Application
6. Apply Contract Migration
```

Use a different sequence when the architecture requires it.

---

# 42. Migration Before Application

A migration may be safely applied before application deployment when it is backward compatible.

Example:

```text
Add Nullable Column
```

is generally easier to pre-deploy than:

```text
Drop Column
```

---

# 43. Application Before Migration

An application may need to be deployed before a schema change when the application can safely prepare data or dual-write to a new structure.

This must be deliberate.

Do not assume:

```text
Application First
```

or:

```text
Migration First
```

is universally correct.

---

# 44. Rolling Deployments

When multiple application versions coexist:

```text
Old Version
+
New Version
+
Current Database
```

must all remain compatible during the transition.

This is one of the primary reasons for expand/contract migrations.

---

# 45. Rollback Reality

Application rollback and database rollback are not always symmetric.

For example:

```text
Application v2
+
Migration v2
```

may not safely support:

```text
Rollback Application to v1
```

if v2 introduced irreversible data transformations.

Migration planning must consider this explicitly.

---

# 46. Prefer Forward Recovery

When a schema change has already been deployed, a corrective forward migration is often safer than trying to reverse a complex production data transformation.

Conceptually:

```text
Bad Migration
    ↓
Understand Damage
    ↓
Corrective Migration
```

rather than:

```text
Blind Rollback
```

---

# 47. Migration Rollback

Rollback scripts should be provided when they are:

```text
Safe
Meaningful
Supported by the migration tooling
```

Do not create a rollback merely to satisfy a template if the operation cannot safely reverse existing data.

---

# 48. Destructive Migrations

Destructive changes include:

```text
DROP TABLE
DROP COLUMN
DELETE Data
Irreversible Transformation
```

These require explicit review.

---

# 49. Destructive Migration Procedure

Before a destructive migration:

```text
Confirm Dependency Removal
        ↓
Backup / Recovery Strategy
        ↓
Validate Target Data
        ↓
Review Rollout
        ↓
Execute
        ↓
Verify
```

---

# 50. Production Backup

Production schema changes must be compatible with the established backup and recovery strategy.

A backup should not be treated as permission to make unsafe migrations.

---

# 51. Migration Testing

Every migration should be tested before production.

At minimum:

```text
Fresh Database
Existing Representative Database
Application Compatibility
```

where applicable.

---

# 52. Fresh Database Test

A fresh database should be able to apply all migrations sequentially:

```text
Migration 1
 ↓
Migration 2
 ↓
...
 ↓
Current Schema
```

This detects broken migration history.

---

# 53. Existing Database Test

Test migrations against representative pre-migration data.

This is especially important for:

```text
Backfills
Constraints
Unique Indexes
Type Changes
Large Tables
```

---

# 54. Migration Idempotency

Migration files themselves are normally versioned and executed once.

Do not add unnecessary:

```text
IF EXISTS
IF NOT EXISTS
```

everywhere merely to hide ordering or deployment errors.

Use such guards when they provide intentional compatibility or safe operational behaviour.

---

# 55. Migration Failure Testing

Test failure scenarios where practical:

```text
Invalid Existing Data
Duplicate Rows
Constraint Violation
Insufficient Resources
Interrupted Migration
```

Determine whether the migration leaves a recoverable state.

---

# 56. Migration Performance

Estimate:

```text
Execution Time
Rows Affected
Locks
I/O
WAL
Replication Impact
```

for large production migrations.

A migration that takes milliseconds locally may take hours on production data.

---

# 57. Large Table Changes

Large tables require special care.

Before modifying one, determine:

```text
Table Size
Row Count
Write Rate
Read Rate
Indexes
Traffic
Replication
```

---

# 58. Locking

Schema changes can acquire locks.

Before production execution, understand:

```text
Lock Type
Lock Duration
Blocked Queries
```

Do not assume every `ALTER TABLE` is harmless.

---

# 59. Long Transactions

Avoid long-running migration transactions when they create unacceptable operational pressure.

Long transactions can affect:

```text
Vacuum
WAL
Replication
Locks
Storage
```

---

# 60. Migration Observability

Migration execution should be observable.

Useful information includes:

```text
Migration Version
Start Time
End Time
Success / Failure
Environment
```

Do not expose credentials or sensitive data.

---

# 61. Migration Logs

Migration logs should make failures diagnosable.

A useful failure should identify:

```text
Migration Version
Operation
Database
Failure Classification
```

without exposing connection secrets.

---

# 62. Migration Metrics

Where deployment tooling supports it, track:

```text
Migration Duration
Migration Failures
Migration Count
```

Avoid excessive application-level metrics for one-time migration details.

---

# 63. Local Migration Workflow

Local development should follow:

```text
Change Schema Requirement
        ↓
Create Migration
        ↓
Run Migration
        ↓
Run Tests
        ↓
Inspect Schema
        ↓
Run Application
```

---

# 64. Local Database Reset After Migration Changes

If a migration sequence becomes difficult to test locally:

```text
Reset Disposable Database
        ↓
Run Full Migration History
        ↓
Run Tests
```

Do not edit old applied migrations merely to simplify a local reset.

---

# 65. Migration and Seed Data

Seed data must remain compatible with the current schema.

When schema changes:

```text
Migration
+
Seed Data
+
Tests
```

must be reviewed together.

---

# 66. Migration and Fixtures

Test fixtures may depend on schema details.

When changing:

```text
Column
Constraint
Relationship
State
```

search and update affected fixtures.

---

# 67. Migration and Repositories

Repository queries must be updated consistently with schema changes.

The change should be reviewed across:

```text
Migration
 ↓
Repository
 ↓
Application Service
 ↓
API / Event
 ↓
Tests
```

# 68. Migration and API Compatibility

A database migration can indirectly change API behaviour.

For example:

```text
Nullable → Required
```

may change:

```text
API Validation
Response Shape
Error Behaviour
```

Review the API contract when schema semantics change.

---

# 69. Migration and Performance

A schema change can affect query performance even when application code does not change.

After important migrations, verify:

```text
Query Plans
Latency
Index Usage
Connection Load
```

---

# 70. Migration and Data Integrity

After a migration, verify important invariants.

Examples:

```text
No Orphan Records
No Unexpected NULLs
No Duplicate Business Keys
Valid State Values
Valid Foreign Keys
```

---

# 71. Migration Review

A schema migration review should cover:

```text
Purpose

Performance
Compatibility
```

---

# 72. Migration Documentation

A migration should have enough context in its name and associated change description to explain:

```text
Why It Exists
What It Changes
What Depends On It
```

Do not put long architecture explanations inside SQL migration files when repository documentation is the better location.

# 74. Schema Review Questions

Before approving a migration, ask:

```text
What data changes?
What code depends on it?
Can old and new application versions coexist?
Will it lock a large table?
How long can it run?
Can it be interrupted safely?
How is failure recovered?
What happens to existing rows?
Does it affect events?
Does it affect API behaviour?
```

# 75. AI Agent Migration Rules

Before implementing a migration, an AI agent must:

1. Inspect the existing migration framework.
2. Inspect the current schema.
3. Inspect relevant repositories and queries.
4. Determine the exact schema invariant being introduced.
5. Check existing data compatibility.
6. Determine whether the change is additive or destructive.
7. Check rolling-deployment compatibility.
8. Determine migration ordering.
9. Evaluate locks and performance.
10. Determine whether a backfill is required.
11. Define validation after migration.
12. Update application code consistently.
13. Add or update tests.
14. Verify the complete migration history.
15. Review the final diff.

---

# 76. AI Agent Forbidden Migration Patterns

AI agents must not:

- edit an already-applied migration to change its meaning,
- create duplicate migration frameworks,
- drop columns without dependency analysis,
- add non-null constraints without checking existing data,
- add unique constraints without checking duplicates,
- run destructive database operations against non-local environments,
- use manual schema changes as the normal development workflow,
- perform huge unbounded backfills without planning,
- ignore lock behaviour,
- assume local migration timing represents production timing,
- bypass database constraints to simplify application code,
- claim a migration is safe without compatibility analysis,
- remove rollback/recovery considerations for destructive changes,
- modify schema and repository code independently without testing them together.

# 80. Final Migration Principle

> **Database schema evolution must be treated as a compatibility and production-safety problem, not merely as a SQL change.**

The intended RideForge flow is:

```text
Schema Requirement
        ↓
Compatibility Analysis
        ↓
Expand
        ↓
Compatible Application
        ↓
Backfill / Transition
        ↓
Validate
        ↓
Contract
        ↓
Verify
```

Every schema change must preserve:

```text
Data Integrity
Application Compatibility
Operational Stability
Performance
Recoverability
```

The database is an authoritative part of RideForge's correctness model. Migration design must therefore evolve the schema without silently weakening the invariants enforced by:

```text
PostgreSQL
+
Application Services
+
Repositories
+
Redis Operational State
+
Event / Messaging Workflows
```
