# 1. Purpose

RideForge is a latency-sensitive distributed system.

Performance engineering must optimize for:

```text
Low Latency
+
Predictable Tail Latency
+
Sufficient Throughput
+
Controlled Resource Usage
+
Stable Behaviour Under Load
```

Performance work must preserve correctness.

The fastest implementation is not useful if it:

```text
Loses Data
Breaks Ordering
Violates Business Rules
Creates Duplicate Effects
Exhausts Dependencies
```

---

# 2. Performance Principle

The engineering process is:

```text
Measure
    ↓
Identify Bottleneck
    ↓
Understand Cause
    ↓
Change
    ↓
Benchmark / Test
    ↓
Compare
    ↓
Verify Correctness
    ↓
Keep Only Measured Improvements
```

Do not optimize based only on intuition.

---

# 3. Performance Goals

Performance targets should be defined for the workloads that matter.

Important dimensions include:

```text
Request Latency
Dispatch Latency
Candidate Discovery Latency
Reservation Latency
Event Processing Latency
Throughput
Error Rate
Resource Utilization
```

The exact service objectives belong to the operational architecture.

---

# 4. Latency

Latency is the time required to complete an operation.

For user-facing RideForge operations, distinguish:

```text
End-to-End Latency
API Latency
Application Latency
Database Latency
Redis Latency
Messaging Latency
External Provider Latency
```

Do not assume the slowest visible component is automatically the root cause.

---

# 5. Tail Latency

Average latency can hide slow requests.

Important measurements include:

```text
p50
p95
p99
```

Tail latency is especially important for dispatch and high-concurrency workflows.

---

# 6. Throughput

Throughput measures how much work the system can process over time.

Examples:

```text
HTTP Requests / Second
Location Updates / Second
Dispatch Requests / Second
Events / Second
Database Operations / Second
```

Increasing throughput at the cost of unacceptable latency is not automatically an improvement.

---

# 7. Capacity

Capacity depends on:

```text
CPU
Memory
Network
PostgreSQL
Redis
Kafka / Redpanda
External Providers
```

A component should not be optimized independently from its dependencies.

---

# 8. Performance Budget

Critical operations should have explicit performance expectations.

For example:

```text
API
→ Request Latency Budget

Dispatch
→ Discovery + Ranking + Reservation Budget

Messaging
→ Processing Delay Budget
```

When a component consumes most of the budget, investigate it before adding more downstream work.

---

# 9. Performance Hierarchy

When optimizing a request, consider:

```text
Algorithm
 ↓
Data Access
 ↓
Network Calls
 ↓
Serialization
 ↓
Concurrency
 ↓
Memory
 ↓
Logging / Telemetry
```

The largest architectural bottleneck should be addressed before micro-optimizations.

---

# 10. Measure Before Optimizing

Before changing performance-sensitive code, establish a baseline.

Record:

```text
Current Latency
Current Throughput
Resource Usage
Error Rate
Relevant Dependency Metrics
```

Without a baseline, an optimization cannot be confidently evaluated.

---

# 11. Correctness Before Performance

Performance improvements must not weaken:

```text
Business Invariants
Data Integrity
Authorization
Idempotency
Ordering
Concurrency Safety
Recovery
```

A faster incorrect system is a regression.

---

# 12. Benchmarking

Benchmarks should represent realistic workloads.

Consider:

```text
Small Load
Typical Load
High Load
Peak Load
Failure Conditions
```

Do not optimize only for a trivial benchmark dataset.

---

# 13. Go Benchmarks

Use Go benchmarks for isolated performance-sensitive code.

Examples:

```text
Candidate Ranking
Serialization
Parsing
Data Transformation
Geospatial Calculations
```

Benchmark only where the result is meaningful.

---

# 14. Benchmark Reproducibility

A useful benchmark should document:

```text
Input Size
Environment
Concurrency
Dataset Characteristics
Implementation Version
Measurement
```

Avoid comparing benchmarks taken under materially different conditions.

---

# 15. Microbenchmark Limitations

Microbenchmarks do not prove system-level performance.

A function that is faster in isolation may not improve:

```text
API Latency
Dispatch Latency
Throughput
```

if the real bottleneck is PostgreSQL, Redis, network, or another dependency.

---

# 16. Profiling

Use profiling to identify actual CPU and memory bottlenecks.

Useful profiling areas include:

```text
CPU
Memory / Heap
Goroutines
Blocking
Mutex Contention
```

Use Go's profiling tooling where appropriate.

---

# 17. CPU Profiling

CPU profiling should identify:

```text
Hot Functions
Expensive Algorithms
Serialization Cost
JSON Processing
Ranking Cost
Excessive Logging
```

Do not optimize a function simply because it appears frequently without understanding why.

---

# 18. Memory Profiling

Memory profiling should identify:

```text
Large Allocations
Allocation Rate
Retained Objects
Large Payloads
Unbounded Collections
Goroutine-Related Growth
```

---

# 19. Allocation Reduction

Reduce allocations when measurements show allocation pressure.

Possible techniques include:

```text
Reuse Appropriate Buffers
Avoid Unnecessary Conversions
Reduce Temporary Objects
Stream Large Data
```

Do not introduce unsafe or overly complex pooling merely to reduce allocations.

---

# 20. Object Pooling

Pooling can reduce allocation pressure but adds complexity.

Before introducing a pool, establish:

```text
Measured Allocation Problem
Safe Ownership
Pool Lifecycle
Concurrency Behaviour
Memory Retention Impact
```

Do not pool everything.

---

# 21. Goroutine Management

Goroutines are lightweight but not free.

Avoid:

```text
Unbounded Goroutine Creation
One Goroutine per Unbounded Item
Goroutines Without Cancellation
Goroutines Without Error Ownership
```

Use bounded worker pools when workload requires controlled concurrency.

---

# 22. Concurrency

Concurrency should increase useful throughput without overwhelming dependencies.

Consider:

```text
CPU
Database Connections
Redis Connections
Broker Partitions
External Rate Limits
Memory
```

More concurrency is not automatically faster.

---

# 23. Backpressure

When incoming work exceeds processing capacity:

```text
Incoming Work
    ↓
Bounded Queue
    ↓
Controlled Workers
    ↓
Dependency
```

Do not allow unlimited in-memory queues.

---

# 24. Request Concurrency

API concurrency should be bounded by:

```text
Server Capacity
Database Capacity
Redis Capacity
External Dependencies
```

Protect downstream systems from request amplification.

---

# 25. Database Performance

Database performance is often a major system bottleneck.

Optimize:

```text
Query Design
Indexes
Connection Pooling
Transaction Scope
Batching
Pagination
Data Access Patterns
```

before applying application-level micro-optimizations.

---

# 26. Avoid N+1 Queries

Do not perform:

```text
1 Query
+
N Queries
```

when the required data can be obtained efficiently through:

```text
Join
Batch Query
Preload
Aggregation
```

according to the repository architecture.

---

# 27. Query Selectivity

Queries should retrieve only the data required by the operation.

Avoid:

```text
SELECT *
```

when a smaller projection is sufficient and meaningful.

---

# 28. Database Indexes

Indexes should be introduced based on actual query patterns.

Before adding an index, consider:

```text
Query Frequency
Selectivity
Write Cost
Storage Cost
Existing Indexes
```

Do not create indexes merely because a column is frequently mentioned in code.

---

# 29. Index Verification

After adding an important index, verify the query plan.

Use appropriate PostgreSQL tooling to determine whether the database actually uses the index.

---

# 30. Connection Pooling

Database pool configuration must balance:

```text
Application Concurrency
PostgreSQL Capacity
Number of Application Instances
Query Latency
```

If every application instance creates a large pool, total database connections can grow beyond PostgreSQL capacity.

---

# 31. Pool Exhaustion

Symptoms may include:

```text
Request Latency Increase
Connection Wait Time
Timeouts
```

Investigate pool pressure before simply increasing the pool size.

---

# 32. Transaction Scope

Keep database transactions as short as practical.

Do not hold a transaction open while waiting for:

```text
Redis
Kafka
External APIs
Long Computation
Client Input
```

unless the architecture explicitly requires it.

---

# 33. Database Batching

Batch database operations when it materially reduces:

```text
Network Round Trips
Transaction Overhead
Query Overhead
```

Do not create extremely large batches that increase:

```text
Memory
Lock Duration
Transaction Size
Failure Cost
```

---

# 34. Pagination Performance

Large offsets can become increasingly expensive.

For large datasets or high-volume traversal, consider cursor/keyset pagination according to the API and repository architecture.

---

# 35. PostgreSQL and Dispatch

Dispatch-related database operations should be latency-sensitive.

Avoid unnecessary database work in the critical path:

```text
Request
 ↓
Candidate Discovery
 ↓
Ranking
 ↓
Reservation
```

Use Redis for its intended fast operational role while keeping PostgreSQL as the authoritative boundary where required.

---

# 36. Reservation Performance

Reservation must remain:

```text
Correct
Atomic where required
Bounded
Fast
```

Do not remove authoritative validation merely to reduce latency.

---

# 37. Redis Performance

Redis is used for latency-sensitive operational workloads.

Optimize:

```text
Round Trips
Key Access
Pipelines
Payload Size
Connection Pool
Command Count
```

---

# 38. Redis Round Trips

Multiple sequential network calls can dominate latency.

Prefer safe batching or pipelining when operations are independent.

Avoid batching operations when their semantics require strict intermediate results.

---

# 39. Redis Payload Size

Do not store large objects when only a small set of fields is required.

Large Redis values increase:

```text
Memory
Network
Serialization
Latency
```

---

# 40. Redis Driver Location Performance

The driver-location path should remain efficient:

```text
Location Update
 ↓
H3 Calculation
 ↓
Membership Update
```

and:

```text
Ride Request
 ↓
H3 Cell Discovery
 ↓
Candidate Retrieval
```

Avoid unnecessary database round trips in this fast path.

---

# 41. H3 Discovery Expansion

Spatial search should remain bounded.

Define limits for:

```text
Cells Examined
Search Rings
Candidates Retrieved
Processing Time
```

according to dispatch configuration.

Never allow a request to trigger unbounded spatial expansion.

---

# 42. Candidate Set Size

Candidate discovery should avoid producing unnecessarily large candidate sets.

Too many candidates increase:

```text
Memory
Ranking CPU
Database Lookups
Network
Latency
```

Use appropriate filtering before expensive ranking.

---

# 43. Candidate Filtering Order

Where business semantics permit, apply cheaper filters before expensive operations.

Conceptually:

```text
Cheap Eligibility
 ↓
Spatial Candidate
 ↓
Availability
 ↓
Vehicle / Ride Constraints
 ↓
Expensive Ranking
```

The exact order must preserve business correctness.

---

# 44. Ranking Performance

Ranking should be measured independently.

Track:

```text
Candidate Count
Ranking Duration
Feature Extraction Duration
Scoring Duration
```

Avoid optimizing ranking until discovery and data access costs are understood.

---

# 45. Dispatch Critical Path

The dispatch critical path should remain explicit:

```text
Ride Request
    ↓
Validation
    ↓
Candidate Discovery
    ↓
Filtering
    ↓
Ranking
    ↓
Reservation
    ↓
Result
```

Each stage should have a measurable latency contribution.

---

# 46. Stand Dispatch Performance

For stand dispatch, optimize for:

```text
Fast Queue / Stand Lookup
Correct Driver Ordering
Low Reservation Latency
Bounded Candidate Processing
```

Do not add smart-dispatch work to the stand-dispatch path unless required by the selected strategy.

---

# 47. Smart Dispatch Performance

For smart dispatch, optimize:

```text
Spatial Discovery
Candidate Filtering
Scoring
Ranking
Reservation
```

Keep the strategy behind the established dispatch abstraction.

---

# 48. Strategy Selection Cost

Selecting a dispatch strategy should be inexpensive.

Do not repeatedly construct expensive infrastructure or load large datasets merely to determine:

```text
Stand Dispatch
```

vs:

```text
Smart Dispatch
```

---

# 49. Messaging Performance

Messaging performance depends on:

```text
Producer Throughput
Broker Capacity
Partition Count
Consumer Concurrency
Handler Latency
Database / Redis Capacity
```

Optimize the bottleneck rather than increasing producer speed when consumers are already saturated.

---

# 50. Producer Batching

Batching can improve producer throughput by reducing network overhead.

Consider:

```text
Latency Trade-Off
Batch Size
Flush Interval
Message Size
Broker Capacity
```

Do not introduce batching that violates latency requirements.

---

# 51. Consumer Concurrency

Consumer concurrency should respect:

```text
Partition Count
Ordering
Database Pool
Redis Pool
Business Invariants
```

Do not create more workers than the partitioning and dependency architecture can use effectively.

---

# 52. Consumer Backlog

If consumer lag grows:

```text
Measure Producer Rate
Measure Consumer Rate
Measure Handler Latency
Check Dependency Capacity
```

Do not immediately add unlimited consumers.

---

# 53. Event Processing Optimization

Optimize event processing by reducing:

```text
Unnecessary Queries
Repeated Deserialization
Unnecessary Redis Calls
Large Payloads
Unbounded Retries
```

Preserve idempotency and ordering.

---

# 54. API Performance

API handlers should avoid:

```text
Repeated Queries
Blocking Work
Large Serialization
Unbounded Collection Responses
Unnecessary Dependency Calls
```

---

# 55. Response Size

Large API responses increase:

```text
Serialization CPU
Memory
Network
Client Latency
```

Return the required representation rather than the entire internal object graph.

---

# 56. Serialization

Serialization performance matters on high-throughput endpoints.

Optimize only after measuring.

Potential areas include:

```text
Payload Size
Repeated Conversion
Reflection Overhead
Nested Structures
```

---

# 57. HTTP Connection Reuse

HTTP clients used for external providers should reuse connections where the client architecture supports it.

Do not create a new HTTP client for every request.

---

# 58. External API Performance

External providers should have:

```text
Timeouts
Connection Reuse
Bounded Retries
Rate Limit Handling
Observability
```

Do not allow provider latency to become an unbounded API latency source.

---

# 59. Timeout Budgets

Timeouts should form a hierarchy.

Conceptually:

```text
Overall Request Timeout
    ↓
Application Operation Timeout
    ↓
Dependency Timeout
```

A dependency should not routinely outlive the request that needs its result.

---

# 60. Retry Budget

Retries consume latency and dependency capacity.

A retry policy should fit within the operation's overall timeout budget.

Avoid:

```text
Request Timeout = 2s
Dependency Retry = 3 × 2s
```

because the retry strategy can exceed the caller's useful deadline.

---

# 61. Logging Performance

Logging can become a hot-path bottleneck.

Avoid:

```text
Large Payload Serialization
Repeated String Formatting
Excessive INFO Logs
```

in high-frequency operations.

---

# 62. Observability Overhead

Metrics and traces have runtime cost.

Keep instrumentation:

```text
Useful
Bounded
Low Overhead
```

Follow:

```text
13.OBSERVABILITY_DEVELOPMENT.md
```

for telemetry design.

---

# 63. Memory Bounds

Every queue, cache, collection, and candidate list should have an intentional bound where unbounded growth is possible.

Consider:

```text
Maximum Candidates
Maximum Queue Size
Cache Size
Payload Size
Worker Count
```

---

# 64. Cache Performance

A cache is useful only when:

```text
Cache Hit Benefit
>
Cache Maintenance Cost
```

Measure:

```text
Hit Rate
Miss Rate
Latency
Memory
Invalidation Cost
```

Do not add a cache merely because Redis exists.

---

# 65. Cache Stampede

High concurrency can turn a cache miss into a source-system overload.

Where measured as a real problem, consider:

```text
Request Coalescing
Stale-While-Revalidate
Short Lock
Precomputation
```

Do not add distributed locking without a demonstrated requirement.

---

# 66. Lock Performance

Locks can protect correctness but reduce concurrency.

Before adding a lock, determine whether the invariant can instead be enforced through:

```text
Database Constraint
Conditional Update
Atomic Redis Operation
Partition Ordering
```

Use the simplest correct mechanism.

---

# 67. Contention

Measure contention before optimizing synchronization.

Potential sources include:

```text
Mutex
Database Row Lock
Database Pool
Redis Pool
Broker Partition
Application Queue
```

---

# 68. Hot Keys

Redis hot keys can create uneven load.

Monitor workloads where many requests repeatedly access the same key.

Do not redesign key structures solely on speculation.

---

# 69. Hot Partitions

Kafka/Redpanda partitioning can create hot partitions when too many events use the same key.

Review:

```text
Key Distribution
Ordering Requirements
Partition Count
Consumer Concurrency
```

before changing partitioning.

---

# 70. Network Performance

Distributed systems pay network costs.

Reduce unnecessary:

```text
Round Trips
Payload Size
Cross-Service Calls
Serialization Cycles
```

but do not merge components merely to eliminate every network request.

Architectural boundaries still matter.

---

# 71. Service-to-Service Calls

A synchronous service call adds:

```text
Latency
Failure Dependency
Connection Usage
```

Use asynchronous events when the workflow does not require an immediate response.

---

# 72. Avoid Distributed Chatty Workflows

Avoid:

```text
Service A
 → Service B
 → Service C
 → Service D
 → Service E
```

for every request when the workflow can be designed more efficiently.

Keep critical paths bounded.

---

# 73. Performance and Resilience

Performance optimization must consider failure.

For example:

```text
Increase Concurrency
```

may improve throughput until:

```text
PostgreSQL Saturates
```

which can then increase latency for every request.

Performance and resilience must be optimized together.

---

---

# 78. Optimization Acceptance Criteria

An optimization should define success before implementation.

For example:

```text
Reduce p95 discovery latency
without increasing

```

---

# 79. Avoid Premature Optimization

Do not optimize:

```text
Unmeasured Code
Rarely Used Paths
Already Fast Operations
```

while a major architectural bottleneck remains unresolved.

---

# 84. AI Agent Performance Rules

Before implementing a performance optimization, an AI agent must:

1. Identify the workload being optimized.
2. Establish or inspect a baseline.
3. Identify the actual bottleneck.
4. Confirm the relevant architecture boundary.
5. Check correctness implications.
6. Check concurrency implications.
7. Check dependency capacity.
8. Check memory impact.
9. Check observability impact.
10. Define measurable acceptance criteria.
11. Benchmark or profile where appropriate.
12. Add regression tests where useful.
13. Compare before/after results.
14. Verify the optimization does not merely move the bottleneck.
15. Review the final diff.

---

# 85. AI Agent Forbidden Performance Patterns

AI agents must not:

- optimize without evidence,
- increase worker counts blindly,
- increase database pools blindly,
- add caches without an invalidation strategy,
- add distributed locks without justification,
- create unbounded goroutines,
- create unbounded queues,
- remove validation to improve latency,
- bypass authoritative state for speed,
- weaken idempotency or ordering,
- add complex Lua/pipeline logic without measurement,
- optimize only microbenchmarks while ignoring system-level bottlenecks,
- introduce premature abstractions solely for speculative performance,
- claim a performance improvement without measurement.

# 87. Final Performance Principle

> **Optimize RideForge from measured bottlenecks, preserve correctness and bounded resource usage, and prefer simple improvements that produce measurable gains over speculative complexity.**

The intended performance engineering loop is:

```text
Observe
   ↓
Measure
   ↓
Profile
   ↓
Identify Bottleneck
   ↓
Optimize
   ↓
Benchmark
   ↓
Load Test
   ↓
Verify Correctness
   ↓
Monitor in Production
```

The most important RideForge performance path remains:

```text
Ride Request
      ↓
Validation
      ↓
Candidate Discovery
      ↓
Filtering
      ↓
Ranking
      ↓
Reservation
      ↓
Event Publication
```

with critical infrastructure dependencies:

```text
PostgreSQL
Redis
Kafka / Redpanda
External Providers
```

Performance work must make this path faster and more predictable without turning the architecture into an unnecessarily complex system.
