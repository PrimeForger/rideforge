# 1. Purpose

Configuration controls how RideForge operates in different environments without changing application source code.

The configuration system must provide:

```text
Explicit Configuration
+
Environment Isolation
+
Startup Validation
+
Secure Secret Handling
+
Predictable Defaults
+
Operational Flexibility
```

The same application code should be deployable across environments while receiving environment-specific configuration externally.

---

# 2. Configuration Principle

Prefer:

```text
One Application
+
Environment-Specific Configuration
```

over:

```text
Different Application Code
for Each Environment
```

Environment differences should be expressed through configuration wherever the difference is operational rather than business logic.

---

Feature configuration must not become an alternative mechanism for arbitrary business logic.

# 9. Business Rules vs Configuration

Not every business rule should be an environment variable.

Avoid turning core rules into values such as:

```text
RIDE_RULE_1=true
RIDE_RULE_2=37
RIDE_RULE_3=abc
```

If a value represents a stable domain rule, it belongs in the appropriate business/domain architecture.

Configuration should primarily control deployment/runtime variation.


# 22. Secret Validation

Required secrets should be validated during startup.

If a production-required secret is absent:

```text
Fail Fast
```

# 23. Development Defaults

Safe development defaults may be provided where they improve local setup.

Do not provide defaults for sensitive production settings that could accidentally allow an insecure production startup.

---

# 24. Required vs Optional Configuration

Every configuration value should have an intentional classification:

```text
Required
Optional with Safe Default
Optional Feature
Environment-Specific
```

Avoid making everything optional merely to simplify startup.

# 26. Fail-Fast Startup

Invalid critical configuration should prevent startup.

Example:

```text

        ↓
Startup Failure
```

```text

```

Configuration errors should clearly identify:

```text
Configuration Field
Problem
Expected Form
```

Do not include the secret value itself in the error.

For example:

```text

```

is acceptable.

Printing the actual password is not.


# 45. Dispatch Strategy Configuration

RideForge supports multiple primary dispatch strategies, including:

```text
Smart Stand Dispatch
Smart Dispatch
```

The strategy used for a ride must be resolved through the established **hierarchical dispatch configuration** before dispatch execution begins.

The configuration system determines **which strategy applies**. It does not implement the dispatch algorithm itself.

The conceptual flow is:

```text
Ride
 ↓
Identify Applicable Configuration Hierarchy
 ↓
Resolve Effective Dispatch Strategy
 ↓
Execute Resolved Strategy
```

---

## 45.1 Hierarchical Dispatch Configuration

Dispatch strategy may be explicitly configured at different levels of the applicable configuration hierarchy.

Possible levels include:

```text
State
District
City / Town
Rural Area
Auto Stand
Specific Ride Level
Other configured intermediate levels
```

Not every level requires an explicit configuration.

The hierarchy must be represented as a parent-child configuration structure rather than as a hard-coded list of geographic levels.

The system should resolve the strategy from the most specific applicable level upward:

```text
Most Specific Applicable Level
        ↓
Explicit Dispatch Strategy?
   ├── YES → Use it
   └── NO
        ↓
Parent Level
        ↓
Explicit Dispatch Strategy?
   ├── YES → Use it
   └── NO
        ↓
Continue Upward
        ↓
System Default
```

The canonical rule is:

> **The closest / lowest-level explicit configuration takes precedence over inherited configuration.**

Example:

```text
District → Smart Dispatch
Town A   → Smart Stand Dispatch
Town B   → No explicit configuration
```

The effective strategy is:

```text
Town A ride → Smart Stand Dispatch
Town B ride → Smart Dispatch
```

The District configuration acts as the inherited default for Town B.

---

## 45.2 Explicit Configuration vs Inherited Configuration

An explicit configuration is a strategy directly configured at the current applicable level.

An inherited configuration is a strategy obtained from the nearest configured ancestor.

These must remain distinguishable:

```text
Explicit Configuration
        >
Inherited Configuration
```

A lower-level explicit configuration must never be overwritten by a higher-level inherited configuration.

If no explicit configuration exists anywhere in the applicable hierarchy, the system uses the configured system default.

---

## 45.3 Configuration Resolution Is Separate from Strategy Execution

The configuration hierarchy determines:

```text
Which dispatch strategy applies to this ride?
```

It does not determine:

```text
Which driver wins?
How the candidate pool is ranked?
How stand preference is executed?
How geographic expansion works?
```

Those responsibilities belong to the dispatch, discovery, candidate-pipeline, ranking, and geo components.

Therefore:

```text
Configuration Resolution
        ↓
Effective Dispatch Strategy
        ↓
Strategy Execution
```

must remain separate responsibilities.

---

## 45.4 Smart Stand Dispatch Configuration

When the effective strategy is **Smart Stand Dispatch**, the configured strategy must be interpreted as:

> **Stand-preferred, not stand-exclusive.**

If the rider is within the radius of a configured auto stand:

```text
Preferred Auto Stand
        ↓
Prefer eligible drivers from that stand
        ↓
Apply stand queue / ordering rules
```

If suitable drivers are unavailable or unsuitable at the preferred stand, the dispatch flow may consider broader eligible candidates, including:

```text
Drivers outside the stand
Drivers at nearby stands
Drivers from nearby locations
```

If the rider is outside the radius of all configured stands, Smart Stand Dispatch must not create a stand-only candidate pool.

It should allow the normal eligible-driver discovery flow according to the established dispatch rules.

The configuration of Smart Stand Dispatch therefore controls the **dispatch strategy**, not an exclusive geographic boundary.

---

## 45.5 Smart Dispatch Configuration

When the effective strategy is **Smart Dispatch**, auto-stand membership does not create a dispatch preference.

Eligible drivers may be considered regardless of whether they are:

```text
At an auto stand
Outside an auto stand
Associated with another nearby location
```

subject to the normal eligibility, geographic, legal, service, availability, and matching constraints.

---

## 45.6 Cross-Location Dispatch Configuration

Dispatch strategy configuration must not be treated as a hard location boundary.

For example:

```text
Location A → Smart Dispatch
Location B → Smart Stand Dispatch
```

If a ride from Location A cannot be served by suitable local drivers, geographic discovery may expand to Location B.

Drivers from Location B may then be considered while preserving the applicable strategy context of their source location.

For example:

```text
Location B
 ├── Stand driver → 2 km / 5 min ETA
 └── Non-stand driver → 4 km / 9 min ETA
```

The stand driver may be the better candidate under the established dispatch and ranking rules.

Therefore:

```text
Dispatch Strategy
≠
Hard Candidate Location Boundary
```

The source location's strategy determines how candidates from that location are prioritized/contextualized; it does not automatically make those candidates unavailable to nearby rides.

Legal and regional constraints remain authoritative.

---

## 45.7 Strategy Resolution vs Configuration Source

The hierarchical dispatch configuration described above is a **business/operational configuration model**.

It should not be confused with the technical sources from which runtime configuration is loaded, such as:

```text
Environment Variables
Configuration Files
Secret Stores
Deployment Configuration
```

Those technical sources provide configuration values to the application.

The dispatch configuration hierarchy determines the effective business configuration for a ride.

Do not implement the location hierarchy by scattering environment-variable reads throughout dispatch logic.

---

## 45.8 Configuration Must Not Duplicate Dispatch Logic

Configuration should contain declarative values such as:

```text
Effective Strategy Selection
Hierarchy Relationships
Strategy Parameters
Stand Radius
Operational Thresholds
Candidate / Discovery Limits
```

Configuration must not contain a second implementation of:

```text
Candidate Discovery
Queue Processing
Ranking
Driver Assignment
Retry Algorithms
```

The dispatch engine and related components remain responsible for executing the configured strategy.

---

## 45.9 Configuration Precedence

Dispatch strategy precedence is:

```text
Ride-level Explicit Configuration
        ↓
Stand-level Explicit Configuration
        ↓
Rural Area Explicit Configuration
        ↓
Town / City Explicit Configuration
        ↓
District Explicit Configuration
        ↓
State Explicit Configuration
        ↓
System Default
```

The actual hierarchy may contain additional intermediate levels.

The implementation must traverse the configured parent relationship rather than assuming that every deployment has exactly these levels.

---

## 45.10 Configuration Resolution Output

Strategy resolution should produce an explicit runtime context containing, as applicable:

```text
Effective Dispatch Strategy
Configuration Level
Configuration Source / Node
Inheritance Status
Applicable Location
Applicable Stand
Strategy Parameters
```

Downstream dispatch components should consume this resolved context rather than independently repeating configuration lookup.

---

## 45.11 Strategy Configuration Changes

Changing a dispatch strategy configuration can change production ride-assignment behaviour without changing application source code.

Therefore, changes to:

```text
Smart Dispatch
Smart Stand Dispatch
Configuration Hierarchy
Stand Preference
Dispatch Strategy Parameters
```

should be reviewed and traceable like other production-impacting changes.

Where practical, configuration changes should support:

```text
Validation
Auditability
Controlled Rollout
Observability
Rollback
```

---

## 45.12 AI-Assisted Dispatch Configuration

AI-assisted dispatch is not a third primary dispatch strategy.

The effective strategy remains one of the configured primary strategies:

```text
Smart Stand Dispatch
OR
Smart Dispatch
```

AI may assist with:

```text
Ranking
ETA Prediction
Acceptance Prediction
Demand / Supply Prediction
Other Optimization Signals
```

but AI must not silently replace the configured strategy.

For example:

```text
Smart Stand Dispatch
        ↓
AI-assisted ranking
```

does not become:

```text
Smart Dispatch
```

unless an explicit business/configuration rule defines such a strategy change.

# 75. AI Agent Configuration Rules

Before implementing configuration-related changes, an AI agent must:

1. Read the existing configuration architecture.
2. Inspect current configuration structures and loaders.
3. Reuse existing naming conventions.
4. Determine whether the value is configuration or business logic.
5. Identify whether the value is secret.
6. Define required/optional semantics.
7. Define validation.
8. Define safe defaults where appropriate.
9. Review environment compatibility.
10. Review startup/shutdown impact.
11. Review database/Redis/messaging capacity impact.
12. Update relevant documentation.
13. Add configuration tests.
14. Review the final diff for hard-coded environment assumptions.
15. If changing dispatch configuration, verify the hierarchical inheritance and precedence rules.
16. Verify that the most-specific explicit dispatch configuration overrides inherited configuration.
17. Verify that dispatch strategy configuration is not implemented as scattered environment-variable reads.
18. Verify that Smart Stand Dispatch is treated as stand-preferred, not stand-exclusive.
19. Verify that cross-location candidate consideration is not blocked by strategy configuration alone.

---

# 76. AI Agent Forbidden Configuration Patterns

AI agents must not:

- hard-code production endpoints,
- commit secrets,
- log complete configuration objects containing secrets,
- introduce duplicate configuration systems,
- read environment variables throughout business logic,
- use `context.Context` as a configuration container,
- create arbitrary environment variables for domain rules,
- implement hierarchical dispatch inheritance through unrelated environment variables,
- hard-code State → District → Town → Stand as the only possible dispatch hierarchy,
- treat Smart Stand Dispatch as a stand-only candidate boundary,
- reject cross-location candidates solely because their source location uses another dispatch strategy,
- silently switch Smart Stand Dispatch to Smart Dispatch during candidate expansion,
- introduce unbounded worker/pool configuration,
- silently change existing configuration semantics,
- remove configuration compatibility without reviewing deployment order,
- use insecure defaults for production secrets,
- claim configuration validation without testing invalid cases.

# 78. Final Configuration Principle

> **Configuration should control intentional runtime and environment differences without becoming a hidden second implementation of the business domain.**

The RideForge configuration flow should remain:

```text
Environment / Secret Source
        ↓
Configuration Loader
        ↓
Validation
        ↓
Immutable Runtime Configuration
        ↓
Application Bootstrap
        ↓
Components
```

The application should be able to answer:

```text
What environment am I running in?
What dependencies am I using?
What operational limits apply?
What features are enabled?
```

without exposing secrets or relying on hidden global state.

Configuration should make deployment flexible while keeping application behaviour explicit, testable, and predictable.
