# RideForge — Go Development Standards

> **Document:** `docs/04-development/3.GO_DEVELOPMENT_STANDARDS.md`  
> **Status:** Active  
> **Scope:** Go-specific coding standards for RideForge production development  
> **Related:** `docs/04-development/1.DEVELOPMENT_GUIDELINES.md`, `docs/04-development/2.CODE_STRUCTURE_AND_CONVENTIONS.md`, `docs/03-components/`, `docs/02-architecture/`

---

# 1. Purpose

This document defines Go-specific engineering standards for RideForge.

It supplements the general development guidelines with rules for:

```text
Go packages
Types
Interfaces
Errors
Context
Concurrency
Goroutines
Channels
I/O
Memory
Testing
Formatting
Tooling
```

The goal is idiomatic, maintainable, production-grade Go.

---

# 2. General Go Principle

Prefer:

```text
Simple Code
Explicit Dependencies
Small Interfaces
Clear Ownership
Idiomatic Go
Standard Library First
Measured Optimization
```

Avoid unnecessary abstraction and cleverness.

---

# 3. Go Version

Use the Go version declared by the repository's `go.mod` as the authoritative version.

Do not use language or standard-library features newer than the declared project version without intentionally updating the project's Go version.

---

# 4. Formatting

All Go code must be formatted with the standard Go formatter.

Use the repository's established formatting command/tooling.

Do not manually format code in ways that fight `gofmt`.

---

# 5. Imports

Keep imports clean and formatted.

Prefer direct imports over unnecessary aliases.

Use an alias only when:

```text
Name Collision
Clarity
Required Package Convention
```

makes it justified.

---

# 6. Package Names

Package names should be:

```text
Lowercase
Short
Meaningful
Stable
```

Avoid:

```text
camelCase
snake_case
package1
common
misc
utils
```

unless the responsibility genuinely justifies such a package.

---

# 7. Exported Identifiers

Export only what forms part of a package contract.

Avoid exporting implementation details merely for tests or convenience.

Prefer:

```go
type ranker struct {}
```

when the concrete type does not need to be public.

---

# 8. Naming

Use idiomatic Go naming.

Prefer:

```text
ID
URL
HTTP
JSON
API
ETA
H3
```

for established initialisms.

Avoid inconsistent forms such as:

```text
Id
Url
Http
Json
Api
```

when those names are exported or part of the established codebase convention.

---

# 9. Receiver Names

Use short, consistent receiver names.

Example:

```go
func (r *Repository) Get(...) {}
func (s *Service) Execute(...) {}
func (c *Client) Close(...) {}
```

Avoid unnecessarily verbose receiver names.

---

# 10. Avoid `Get` Prefixes When Unnecessary

Go method names can often be concise.

Prefer:

```go
Driver(ctx, id)
```

over:

```go
GetDriver(ctx, id)
```

when the surrounding package already makes the operation obvious.

Follow existing public API conventions when they are already established.

---

# 11. Constructors

Use `New...` for constructors.

Examples:

```go
NewRanker(...)
NewDriverRepository(...)
NewMatchingEngine(...)
```

Constructors should explicitly receive required dependencies.

---

# 12. Constructor Responsibilities

Constructors should generally:

```text
Validate Required Dependencies
Initialize Internal State
Store Configuration
Return the Component
```

They should not normally:

```text
Start Background Loops
Publish Events
Perform Network Calls
Execute Business Workflows
```

---

# 13. Zero Values

Prefer useful zero values where practical.

A type should not require unnecessary initialization merely to avoid panics.

However, do not force a useful zero value when the component requires mandatory dependencies.

For dependency-heavy components, constructors remain the preferred construction path.

---

# 14. Pointer Receivers

Use pointer receivers when:

```text
The method mutates receiver state
The type is large
The type contains synchronization primitives
Identity matters
```

Use value receivers for small immutable value-like types when appropriate.

Keep receiver choice consistent within a type.

---

# 15. Avoid Accidental Copies

Be careful when copying structs containing:

```text
Mutex
RWMutex
WaitGroup
Atomic State
Other Synchronization Primitives
```

Such types should generally be used through pointers.

---

# 16. Context

For operations involving I/O or cancellation:

```go
context.Context
```

should normally be the first argument.

Example:

```go
func (r *Repository) Find(
    ctx context.Context,
    id DriverID,
) (*Driver, error)
```

---

# 17. Never Store Request Context in Structs

Do not store request-scoped `context.Context` inside long-lived service structs.

Pass it through the call chain.

Bad:

```go
type Service struct {
    ctx context.Context
}
```

Prefer:

```go
func (s *Service) Execute(ctx context.Context, ...) error
```

---

# 18. Do Not Use Context for Configuration

Do not store:

```text
Configuration
Dependencies
Business State
Optional Parameters
```

inside context values.

Context is for:

```text
Cancellation
Deadlines
Request-scoped Metadata
```

where appropriate.

---

# 19. Context Cancellation

Respect cancellation in blocking operations.

Examples:

```text
Database
Redis
HTTP
Kafka
External Routing
Worker Loops
```

Long-running loops should periodically observe cancellation.

---

# 20. `context.Background()`

Use `context.Background()` only at a genuine application root or when starting intentionally independent work.

Do not replace a caller-provided context with:

```go
context.Background()
```

inside business operations.

---

# 21. `context.TODO()`

Do not leave `context.TODO()` in production code as a permanent substitute for understanding context ownership.

Use it only temporarily during migration and remove it before completion.

---

# 22. Error Handling

Errors are part of the API of a function.

Every returned error should communicate enough information for the caller to make the correct decision.

---

# 23. Always Handle Errors

Do not silently ignore meaningful errors.

Avoid:

```go
result, _ := operation()
```

unless the ignored error is explicitly irrelevant and the reason is obvious.

---

# 24. Error Wrapping

Use `%w` when adding context while preserving the underlying error.

Example:

```go
return fmt.Errorf("reserve driver: %w", err)
```

This enables callers to use:

```go
errors.Is
errors.As
```

where appropriate.

---

# 25. Sentinel Errors

Use sentinel errors when callers need stable category checks.

Example:

```go
var ErrNotFound = errors.New("not found")
```

Use them deliberately.

Do not create dozens of sentinel errors for conditions that callers never need to distinguish.

---

# 26. Typed Errors

Use typed errors when structured information is useful.

For example:

```text
Conflict
Validation Failure
Provider Failure
State Transition Failure
```

The type should exist because callers need the structured information.

---

# 27. Error Strings

Error messages should:

```text
Be lowercase where idiomatic
Describe the operation
Provide useful context
Avoid secrets
```

Prefer:

```text
"reserve driver: driver already reserved"
```

over:

```text
"ERROR!!!"
```

---

# 28. Error Classification

Keep distinctions between:

```text
Expected Business Outcome
Validation Failure
Conflict
Not Found
Timeout
Unavailable Dependency
Internal Failure
```

This is especially important in dispatch.

---

# 29. Do Not Log and Return the Same Error Everywhere

Avoid:

```text
Repository logs error
Service logs same error
Handler logs same error
```

creating three identical log entries.

Log at the boundary that has enough context to make the log useful.

---

# 30. `defer`

Use `defer` for cleanup when it improves correctness and readability.

Examples:

```text
Close Resource
Unlock Mutex
Rollback on Failure
```

Be aware of the lifetime of deferred operations inside loops.

---

# 31. Mutexes

Use mutexes only for state that is owned by the current process.

A mutex does not protect state shared across:

```text
Multiple Processes
Multiple Containers
Multiple Dispatch Nodes
```

For distributed state use the appropriate:

```text
Database
Redis Atomic Operation
Distributed Reservation
```

mechanism.

---

# 32. Mutex Scope

Keep critical sections short.

Bad:

```text
Lock
 ↓
Network Call
 ↓
Database Query
 ↓
External API
 ↓
Unlock
```

Prefer:

```text
Lock
 ↓
Small State Mutation
 ↓
Unlock
```

then perform external work outside the lock when safe.

---

# 33. `sync.RWMutex`

Use `RWMutex` only when its read/write characteristics actually benefit the workload.

Do not use it automatically instead of `Mutex`.

Measure when the decision matters.

---

# 34. Atomic Operations

Use atomic operations for small independent state transitions where they provide a simpler and correct solution.

Do not replace a multi-field invariant with multiple unrelated atomics.

If several values must change together, use a stronger synchronization mechanism.

---

# 35. Goroutines

Every goroutine must have:

```text
Owner
Purpose
Termination Condition
Cancellation Path
Resource Bound
```

Before adding a goroutine, answer:

```text
Who stops it?
```

---

# 36. Goroutine Leaks

Avoid goroutines that can remain blocked forever.

Common causes:

```text
Channel Receive Without Cancellation
Channel Send Without Consumer
Network Call Without Timeout
Worker Without Shutdown
Ticker Without Stop
```

---

# 37. Worker Lifecycle

Background workers should normally follow:

```text
Create
 ↓
Start
 ↓
Run
 ↓
Cancel
 ↓
Stop
 ↓
Close Resources
```

The composition root should own application-level lifecycle coordination.

---

# 38. WaitGroups

Use `sync.WaitGroup` to coordinate goroutine completion.

Do not use arbitrary sleeps to wait for goroutines.

Bad:

```go
time.Sleep(time.Second)
```

as a synchronization mechanism.

---

# 39. Channels

Use channels when they represent a meaningful communication or ownership boundary.

Do not introduce channels merely because Go provides them.

---

# 40. Channel Ownership

The component that creates a channel should clearly define who:

```text
Sends
Receives
Closes
```

Only the appropriate owner should close a channel.

---

# 41. Channel Closing

Do not close a channel from the receiver unless the receiver owns the channel lifecycle.

A common rule:

```text
Sender owns closing
```

when there is a single clear producer.

---

# 42. Buffered Channels

Buffer channels only when the buffer has a clear semantic or performance purpose.

Do not use a large buffer to hide backpressure.

A growing workload should eventually expose:

```text
Queue Saturation
Slow Consumer
Dependency Failure
```

rather than silently consuming unlimited memory.

---

# 43. Select

Use `select` to coordinate:

```text
Channel
Cancellation
Timeout
Ticker
```

where appropriate.

Long-running worker loops should generally provide a cancellation path.

---

# 44. Timers

Use:

```go
time.NewTimer
```

when a timer needs explicit lifecycle control.

Use:

```go
time.After
```

for simple one-shot cases where the allocation/lifecycle characteristics are acceptable.

For repeated operations, prefer a ticker with proper cleanup.

---

# 45. Tickers

Always stop tickers when their lifecycle ends.

Example:

```go
ticker := time.NewTicker(interval)
defer ticker.Stop()
```

Do not create permanent tickers without an explicit worker lifecycle.

---

# 46. Timeouts

Every potentially blocking external operation should have a bounded timeout where appropriate.

Examples:

```text
Database
Redis
HTTP
Routing
Messaging
Realtime
```

Do not allow a network dependency to block dispatch indefinitely.

---

# 47. `time.Sleep`

Do not use `time.Sleep` as:

```text
Retry synchronization
Concurrency synchronization
Worker synchronization
Test synchronization
```

Use explicit mechanisms.

Sleep may be appropriate as part of an intentionally designed backoff strategy.

---

# 48. Retry Backoff

Retries should normally use bounded backoff.

Consider:

```text
Initial Delay
Maximum Delay
Attempt Limit
Jitter
Context Cancellation
```

Do not retry indefinitely.

---

# 49. Idempotency and Retry

Before adding a retry, determine whether the operation is idempotent.

Safe retry candidates generally have semantics such as:

```text
Read
Idempotent Update
Idempotent Publish Mechanism
```

A non-idempotent operation requires an explicit correctness strategy.

---

# 50. Database Code

Database operations should:

```text
Accept Context
Use Parameterized Queries
Handle Errors
Respect Transactions
Avoid N+1 Access
Use Appropriate Pooling
```

Do not construct database connections inside individual repository methods.

---

# 51. SQL Parameters

Never build SQL by concatenating untrusted values.

Prefer parameterized queries.

This is both a security and correctness requirement.

---

# 52. Database Transactions

Transactions should be explicit and bounded.

Do not hide long transaction lifetimes behind helpers that make ownership unclear.

The component owning the use-case transaction should make the boundary understandable.

---

# 53. Database Rows

Close row iterators correctly.

Check iteration errors after consuming rows.

Do not assume:

```text
rows.Next()
```

means all errors have been handled.

---

# 54. Connection Pooling

Use the application's shared database pool.

Do not create:

```text
One Pool Per Request
One Pool Per Repository
```

unless an explicitly documented architecture requires it.

---

# 55. Redis Code

Redis operations should:

```text
Accept Context
Use Shared Client
Respect Atomicity
Respect TTL
Handle Errors
Avoid Unnecessary Round Trips
```

---

# 56. Redis Pipelines

Use pipelines when multiple independent Redis operations can be grouped safely.

Do not pipeline operations that require intermediate results unless the chosen Redis mechanism supports the required atomicity/semantics.

---

# 57. Redis Lua

Use Lua scripts when a multi-step Redis operation must be atomic.

Document the invariant the script protects.

Do not use Lua merely because it can reduce lines of Go code.

---

# 58. Kafka / Redpanda Code

Messaging code should separate:

```text
Transport
Serialization
Application Event
Business Handling
```

A Kafka client message should not become the application's domain model.

---

# 59. Consumer Loops

Consumer loops should handle:

```text
Cancellation
Broker Failure
Deserialization Failure
Handler Failure
Acknowledgement
Retry / DLQ Policy
```

according to the messaging architecture.

---

# 60. Consumer Idempotency

Consumers must assume duplicate delivery unless the architecture explicitly guarantees otherwise.

Business handlers should protect durable side effects accordingly.

---

# 61. Serialization

Serialization failures should not be silently ignored.

A malformed event should follow the project's explicit failure/DLQ strategy.

---

# 62. JSON

Use JSON when it is the established contract.

Do not introduce custom serialization formats for convenience without an architectural reason.

---

# 63. HTTP Clients

Use shared HTTP clients for repeated external communication where appropriate.

Configure:

```text
Timeout
Transport
Connection Reuse
```

according to application requirements.

---

# 64. HTTP Response Handling

Always check:

```text
Network Error
HTTP Status
Response Body
Decoding Error
```

Do not treat a successful TCP response as a successful business operation.

---

# 65. Response Body Cleanup

Close response bodies appropriately after HTTP calls.

Do not leak connections by leaving response bodies open.

---

# 66. External Provider Errors

Provider-specific errors should be translated into application-relevant categories at the appropriate boundary.

Do not leak vendor SDK types across the whole application.

---

# 67. Memory Allocation

Avoid unnecessary allocations in hot paths.

Pay particular attention to:

```text
Candidate Discovery
Candidate Ranking
Serialization
High-Frequency Driver Location
```

Optimize only when evidence justifies it.

---

# 68. Slice Reuse

Reuse slices where it improves a measured hot path and ownership remains clear.

Do not prematurely optimize every slice allocation.

---

# 69. Map Allocation

Preallocate maps/slices when the expected size is known and the optimization is meaningful.

Avoid speculative micro-optimizations.

---

# 70. Escape Awareness

Be aware that returning pointers, closures, and interface values can affect allocations.

Do not contort code purely to avoid theoretical allocations.

Use benchmarks when allocation behaviour matters.

---

# 71. Interfaces and Performance

Interfaces are useful architectural boundaries.

Do not remove interfaces solely because of hypothetical performance concerns.

If performance is critical:

```text
Benchmark
Measure
Then Decide
```

---

# 72. Reflection

Avoid reflection in latency-sensitive application paths unless it solves a genuine requirement.

Prefer:

```text
Static Types
Interfaces
Generics where appropriate
Explicit Mapping
```

---

# 73. Generics

Use generics when they make reusable code:

```text
Clearer
Safer
Less Duplicated
```

Do not introduce generics merely to demonstrate language features.

Business abstractions should remain easy to understand.

---

# 74. `any`

Use `any` only when the value genuinely has no useful static type.

Avoid using `any` as a shortcut around designing an appropriate contract.

---

# 75. Type Assertions

Type assertions should be justified and checked.

Prefer:

```go
value, ok := x.(Type)
```

when the assertion can legitimately fail.

Avoid unchecked assertions at untrusted boundaries.

---

# 76. Defer in Hot Paths

`defer` is generally acceptable, but in extremely hot code paths its cost may matter.

Do not remove it speculatively.

Benchmark before replacing clear cleanup code with manual cleanup.

---

# 77. Panics

Do not use panic for expected runtime conditions.

Expected conditions include:

```text
Invalid Input
Not Found
Conflict
Dependency Failure
Timeout
```

Return errors.

---

# 78. Panic Usage

Panic may be appropriate for:

```text
Impossible Internal Invariant
Startup Misconfiguration
Programmer Error
```

depending on the component and lifecycle.

Do not use panic as ordinary error handling.

---

# 79. Recovery

Do not add broad panic recovery everywhere.

Recovery should exist at deliberate process/goroutine boundaries where it prevents one unexpected panic from taking down unrelated work.

Recovered panics must remain observable.

---

# 80. Logging in Go

Use the project's established structured logger.

Do not introduce multiple unrelated logging libraries.

Avoid `fmt.Println` or ad-hoc printing in production code.

---

# 81. Formatting and Static Checks

Before committing Go changes, run the repository's configured:

```text
Formatter
Compiler
Tests
Linter / Static Analysis
```

Use the actual project tooling rather than inventing new commands.

---

# 82. Race Detection

Concurrency-sensitive changes should be verified with Go's race detector where practical.

Particularly important for:

```text
Shared Maps
Caches
Workers
Realtime Connections
Dispatch State
Reservation Logic
```

---

# 83. Tests

Use table-driven tests where they improve clarity.

A table is especially useful for:

```text
Many Input Variants
State Transitions
Validation Cases
Ranking Cases
Error Cases
```

Do not force every test into a table when a simple test is clearer.

---

# 84. Test Parallelism

Use `t.Parallel()` only when the test is genuinely isolated.

Do not introduce parallel tests that mutate:

```text
Global State
Shared Database
Shared Redis Keys
Environment
```

without proper isolation.

---

# 85. Test Cleanup

Use test cleanup mechanisms to release:

```text
Resources
Temporary Files
Database State
Redis Keys
Goroutines
```

Tests should not leave state behind.

---

# 86. Avoid Flaky Tests

Do not depend on:

```text
Arbitrary Sleeps
Real Clock Timing
Network Availability
Random External State
Execution Ordering
```

unless the test explicitly targets those behaviours.

---

# 87. Benchmarks

Benchmarks should represent realistic workloads.

For dispatch benchmarks consider:

```text
Candidate Count
Feature Count
Ranking Complexity
Distance Calculation
Heap Size
```

Record benchmark changes when optimization decisions depend on them.

---

# 88. Fuzz Testing

Use fuzzing where input space is large and correctness can be expressed through invariants.

Potential candidates include:

```text
Parsers
Decoders
Validation
Serialization
Geospatial Input
Event Envelopes
```

Do not fuzz arbitrary business workflows without a useful invariant.

---

# 89. Documentation in Go Code

Comments should explain non-obvious behaviour.

Especially document:

```text
Concurrency Invariants
Atomicity Requirements
External Constraints
Why a Fallback Exists
Why a Retry Is Safe
```

---

# 90. Avoid Clever Go

Prefer readable code over compressed code.

Bad:

```go
if x != nil && x.Active && !x.Busy && ...
```

when extracting named decisions makes the rule clearer.

The dispatch system contains complex business behaviour; readability is a production feature.

---

# 91. Avoid Premature Helper Functions

Do not create helpers for trivial one-line expressions unless they improve:

```text
Readability
Reuse
Testability
Domain Meaning
```

---

# 92. Avoid Giant Functions

If a function simultaneously performs:

```text
Validation
Persistence
Ranking
Messaging
Realtime
Retry
```

it likely needs decomposition by responsibility.

Decompose around meaningful boundaries, not arbitrary line counts.

---

# 93. Avoid Giant Structs

A struct with dozens of unrelated fields often indicates missing component boundaries.

Prefer focused state.

---

# 94. Avoid Boolean Parameter Ambiguity

Avoid APIs such as:

```go
Execute(ctx, true, false, true)
```

when the booleans have non-obvious meanings.

Prefer named options/types where the complexity warrants it.

---

# 95. Options Pattern

Use functional/options patterns only when they genuinely improve construction of complex optional configuration.

Do not introduce an options framework for simple constructors.

---

# 96. Dependency Ownership

The package that uses a dependency should not automatically own the dependency's lifecycle.

For shared infrastructure:

```text
Composition Root
    ↓
Creates Resource
    ↓
Injects Resource
    ↓
Owns Shutdown
```

---

# 97. Resource Cleanup

Any resource opened by a component should have a clear cleanup path.

Examples:

```text
DB Rows
HTTP Body
File
Ticker
Timer
Connection
Worker
```

---

# 98. File I/O

File operations should:

```text
Use Context where supported
Check Errors
Close Handles
Avoid Unbounded Reads
```

Do not load arbitrarily large files into memory without a reason.

---

# 99. Security-Sensitive Code

For authentication, authorization, tokens, and secrets:

```text
Minimize Exposure
Avoid Logging
Validate Inputs
Use Standard Cryptographic Libraries
```

Do not implement cryptographic primitives yourself.

---

# 100. Dependency Security

When adding or updating a dependency, consider:

```text
Maintenance
Known Vulnerabilities
License
Transitive Dependencies
Operational Complexity
```

Use the project's dependency-management process.

---

# 101. Go Code Review Checklist

Reviewers should verify:

```text
[ ] Idiomatic Go
[ ] Clear package ownership
[ ] Small interfaces
[ ] Explicit dependencies
[ ] Context propagated correctly
[ ] Errors handled
[ ] No accidental panic
[ ] Goroutines have lifecycle
[ ] No resource leaks
[ ] Concurrency is safe
[ ] Timeouts are bounded
[ ] Tests cover behaviour
[ ] Formatting is clean
[ ] No unnecessary abstraction
[ ] No unrelated refactor
```

---

# 102. AI Agent Go Rules

An AI coding agent must:

1. Follow the Go version in `go.mod`.
2. Follow existing package conventions.
3. Search before creating new types/interfaces.
4. Use idiomatic Go.
5. Preserve context propagation.
6. Handle errors explicitly.
7. Avoid panic for expected failures.
8. Give every goroutine a lifecycle.
9. Avoid unbounded concurrency.
10. Respect distributed-state boundaries.
11. Use parameterized database operations.
12. Respect Redis atomicity.
13. Preserve messaging idempotency.
14. Run formatting.
15. Run relevant tests.
16. Run race detection when concurrency changes warrant it.
17. Inspect the final diff.

---

# 103. AI Agent Forbidden Patterns

AI agents must not:

- use `context.Background()` to discard a caller context,
- store request contexts in long-lived structs,
- silently ignore errors,
- use `panic` for ordinary failures,
- use `time.Sleep` as synchronization,
- start unmanaged goroutines,
- create unbounded worker pools,
- create a database/Redis pool per request,
- concatenate untrusted SQL,
- bypass existing repository abstractions,
- use distributed state protected only by local mutexes,
- introduce reflection without a real requirement,
- add generics without a concrete benefit,
- create giant interfaces,
- add generic `utils` packages,
- introduce a new logging framework,
- claim tests passed without running them.

---

# 104. Preferred Implementation Flow

For a normal Go change:

```text
Read Architecture
      ↓
Read Component Contract
      ↓
Inspect Existing Code
      ↓
Design Smallest Correct Change
      ↓
Implement Idiomatic Go
      ↓
Add / Update Tests
      ↓
Format
      ↓
Static Checks
      ↓
Run Tests
      ↓
Race Test if Relevant
      ↓
Review Diff
```

---

# 105. Final Rule

> **Write Go that is boring in the best possible way: explicit dependencies, clear ownership, predictable errors, bounded concurrency, straightforward control flow, idiomatic types, and tests that prove the behaviour that matters.**

RideForge is a distributed, concurrency-heavy system. Go code should therefore optimize first for **correctness and clarity**, then for **measured performance**, while preserving the architectural boundaries documented by the project.
