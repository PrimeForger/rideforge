# RideForge — Code Structure and Conventions

> **Document:** `docs/04-development/2.CODE_STRUCTURE_AND_CONVENTIONS.md`  
> **Status:** Active  
> **Scope:** Source-code organization, package boundaries, naming, dependency direction, file placement, interfaces, constructors, and implementation conventions  
> **Related:** `docs/00-project/1.PROJECT_VISION.md`, `docs/02-architecture/`, `docs/03-components/`, `docs/04-development/1.DEVELOPMENT_GUIDELINES.md`, `docs/04-development/3.GO_DEVELOPMENT_STANDARDS.md`

---

# 1. Purpose

This document defines how RideForge source code should be organized and how developers should decide:

```text
Where code belongs
How packages are structured
How dependencies flow
How types are named
How interfaces are defined
How constructors are designed
How new files and packages are introduced
```

The goal is to make the repository understandable without requiring knowledge of the original developer's intent.

---

# 2. Core Principle

Code placement must follow responsibility.

The primary question when creating or modifying code is:

> **Which component owns this behaviour?**

Do not place code based only on:

```text
Convenience
Shortest Import Path
Existing Large Package
Personal Preference
```

---

# 3. Repository Structure

The repository should retain clear separation between executable entry points, internal application logic, infrastructure, configuration, and documentation.

Conceptually:

```text
rideforge/
├── cmd/
├── internal/
├── docs/
├── docker-compose.yml
├── go.mod
├── go.sum
└── environment / tooling files
```

The current repository structure is authoritative.

Do not reorganize top-level directories without an architectural reason.

---

# 4. `cmd/`

`cmd/` contains executable application entry points.

Its responsibility is primarily:

```text
Process Entry
Configuration Bootstrap
Application Startup
Application Shutdown
```

It should not contain core business logic.

Prefer:

```text
cmd
  ↓
bootstrap / composition
  ↓
application components
```

Avoid implementing dispatch algorithms directly inside `cmd`.

---

# 5. `internal/`

`internal/` contains RideForge application implementation that should not be imported by external Go modules.

It contains the primary system implementation.

The exact current package tree is authoritative.

Do not create arbitrary top-level packages when the functionality belongs inside the internal application.

---

# 6. Application Packages

Application packages should represent business capabilities and application workflows.

Examples from the current architecture include areas such as:

```text
dispatch
candidate
discovery
ranking
reservation
offer
messaging
persistence
```

The package names already present in the repository should be preferred over introducing competing structures.

---

# 7. Package by Responsibility

Prefer:

```text
candidate/
ranking/
discovery/
reservation/
```

when the responsibility is meaningful and independently understandable.

Avoid organizing the entire application around technical object types such as:

```text
controllers/
services/
models/
helpers/
utils/
```

when doing so hides business ownership.

---

# 8. Avoid Generic Packages

Avoid creating packages named:

```text
utils
helpers
common
misc
shared
general
```

unless the package has a clearly defined and documented responsibility.

Generic packages tend to become dependency dumping grounds.

---

# 9. Package Cohesion

A package should contain types that change for related reasons.

A package becomes suspicious when it contains unrelated responsibilities such as:

```text
Redis Client
Ranking Algorithm
HTTP Handler
Database Query
Kafka Consumer
```

in the same package.

---

# 10. Package Boundaries

Package boundaries should support the architecture.

Conceptually:

```text
Application
    ↓
Capability / Component
    ↓
Infrastructure Implementation
```

A package should not bypass another package's ownership merely because an internal field or concrete implementation is accessible.

---

# 11. Dependency Direction

The intended dependency direction is:

```text
Transport
    ↓
Application
    ↓
Domain / Contracts
    ↑
Infrastructure
```

The composition root connects concrete implementations.

Avoid dependency inversion through accidental import cycles.

---

# 12. Import Cycles

Go import cycles indicate an architectural dependency problem.

Do not solve an import cycle by:

```text
Moving random files
Adding globals
Creating an arbitrary `common` package
Duplicating types
```

Instead identify:

```text
Which responsibility is misplaced?
Which dependency should be an interface?
Which boundary is missing?
```

---

# 13. Interfaces

Interfaces should represent capabilities required by consumers.

Prefer:

```go
type CandidateSearcher interface {
    Search(ctx context.Context, request Request) (...) 
}
```

over interfaces that expose every method of a large implementation.

---

# 14. Consumer-Owned Interfaces

When practical, define interfaces near the component that consumes the behaviour.

Conceptually:

```text
Consumer
   ↓
Required Interface
   ↑
Implementation
```

This keeps the contract focused on what the consumer actually needs.

Follow existing repository conventions when an interface is already intentionally shared.

---

# 15. Do Not Create Interfaces Automatically

A concrete type does not need an interface merely because it exists.

Introduce an interface when it provides a meaningful benefit:

```text
Multiple Implementations
Testing Isolation
Technology Boundary
Application Contract
Dependency Inversion
```

---

# 16. Interface Size

Prefer narrow interfaces.

Bad:

```go
type DriverService interface {
    Create(...)
    Update(...)
    Delete(...)
    Search(...)
    Lock(...)
    Unlock(...)
    Publish(...)
    Notify(...)
}
```

when consumers need only one capability.

Prefer focused contracts:

```text
DriverRepository
DriverLocker
DriverNotifier
```

when those are genuinely separate responsibilities.

---

# 17. Concrete Implementations

Implementation names should make their role obvious.

Examples:

```text
DefaultRanker
RedisDriverLocker
PostgresDriverRepository
RedisGeoRefiner
KafkaProducer
```

Avoid vague implementation names such as:

```text
Manager
Helper
Thing
ServiceImpl
```

unless an established project convention requires them.

---

# 18. Constructors

Constructors should make dependencies explicit.

Preferred:

```go
func NewMatchingEngine(
    repository DriverRepository,
    locker DriverLocker,
    ...
) *MatchingEngine
```

Avoid hidden dependency acquisition inside constructors.

---

# 19. Constructor Validation

Constructors may reject invalid required dependencies.

For example:

```text
nil required dependency
invalid required configuration
missing mandatory provider
```

The exact error strategy should follow the existing codebase convention.

---

# 20. Constructors Should Not Perform Work

Avoid constructors that:

```text
Start goroutines
Publish events
Run database queries
Call external APIs
Perform dispatch
```

Construction should establish an object.

Lifecycle operations should be explicit.

---

# 21. Lifecycle Methods

Long-lived components may expose explicit lifecycle operations such as:

```text
Start
Run
Close
Shutdown
```

Use the existing project convention.

Lifecycle ownership must remain visible from the composition root.

---

# 22. Dependency Injection

Dependencies should be passed explicitly.

Preferred:

```text
Builder
    ↓
Constructor
    ↓
Component
```

Avoid:

```text
Component
    ↓
Global Registry
    ↓
Dependency Lookup
```

---

# 23. Builders

Builders belong near the composition boundary when they construct application components.

A builder should primarily:

```text
Read Configuration
Construct Dependencies
Wire Components
Return Component
```

It should not become a second application service.

---

# 24. Builder Placement

Keep builders in the project's established builder/composition area.

Do not create:

```text
builders/
builders2/
factory/
factory2/
```

for the same responsibility.

Search existing builders before creating a new one.

---

# 25. Factory vs Builder

Use the existing project convention.

As a general rule:

```text
Factory
    → Select/create an implementation

Builder
    → Assemble a component and its dependencies
```

Do not introduce both patterns for the same construction path without a clear need.

---

# 26. Configuration Types

Configuration types should represent meaningful configuration boundaries.

Prefer:

```text
RankingConfig
DiscoveryConfig
RedisConfig
DatabaseConfig
```

when those boundaries exist in the current project.

Avoid passing a large application configuration object into every package.

---

# 27. Configuration Access

Application components should receive configuration explicitly.

Avoid reading environment variables directly from:

```text
Ranker
Repository
Matching Engine
Candidate Filter
Domain Logic
```

Configuration loading belongs at the application boundary.

---

# 28. File Naming

File names should describe the primary implementation or responsibility.

Examples:

```text
default_ranker.go
quality_calculator.go
redis_geo_refiner.go
driver_repository.go
```

Use the existing repository naming convention consistently.

---

# 29. One Primary Responsibility Per File

A file may contain closely related declarations, but avoid unrelated implementations in one file.

Prefer:

```text
ranker.go
scorer.go
feature_extractor.go
```

over one enormous:

```text
ranking_everything.go
```

---

# 30. Interfaces and Implementations

Keep interfaces and implementations separated when the package size and complexity justify it.

For example:

```text
ranker.go
default_ranker.go
```

The current package organization is authoritative; do not split files solely for aesthetics.

---

# 31. Small Types

Small related types may remain together.

For example:

```text
Features
QualityFeatures
TravelFeatures
FairnessFeatures
```

may be grouped when they form a coherent feature model.

Do not create one file per tiny type without a meaningful reason.

---

# 32. Go Package Names

Go package names should be:

```text
Short
Lowercase
Clear
Stable
```

Avoid underscores and unnecessary abbreviations.

Prefer:

```go
package ranking
```

over:

```go
package candidate_ranking_engine
```

---

# 33. Exported Names

Export identifiers only when they are part of a meaningful package contract.

Prefer unexported helpers for implementation details.

Avoid exporting everything "just in case."

---

# 34. Naming Interfaces

Interface names should describe capability.

Good:

```text
Ranker
CandidateSearcher
DriverLocker
OutboxRepository
```

Avoid:

```text
IRanker
IRankerService
IRankerInterface
```

The `I` prefix is not idiomatic Go.

---

# 35. Naming Methods

Methods should describe the operation clearly.

Examples:

```text
Search
Rank
Reserve
Release
Publish
CreateRide
AcceptOffer
```

Avoid vague methods:

```text
Process
Handle
Do
Execute
Run
```

unless the context makes the meaning unambiguous.

---

# 36. Context Parameters

For operations that may block or perform I/O, propagate:

```go
context.Context
```

as appropriate.

The context should normally be the first parameter.

Example:

```go
func (r *Repository) Get(
    ctx context.Context,
    id ID,
) (...)
```

---

# 37. Context Ownership

Do not create arbitrary background contexts deep inside application logic when the caller already provides a context.

Avoid:

```go
context.Background()
```

inside request-scoped operations unless the component intentionally starts independent work.

---

# 38. Cancellation

Long-running operations should respect cancellation.

Examples:

```text
Database Query
Redis Operation
HTTP Request
Broker Operation
External Routing Call
Background Worker
```

Cancellation should propagate through the dependency chain where supported.

---

# 39. Error Values

Use errors as structured program information.

Prefer sentinel or typed errors when callers need to distinguish categories.

Examples:

```text
ErrNotFound
ErrConflict
ErrUnavailable
ErrInvalidState
```

Follow the existing project error conventions before adding new types.

---

# 40. Error Wrapping

When adding context, preserve the original error where possible.

Conceptually:

```go
fmt.Errorf("reserve driver %s: %w", driverID, err)
```

This allows callers and observability code to inspect the underlying cause.

---

# 41. Error Ownership

The layer that understands an error's business meaning should classify it.

For example:

```text
Redis timeout
    ↓
Infrastructure error

Reservation conflict
    ↓
Application/business outcome
```

Do not force repositories to decide dispatch policy.

---

# 42. Domain Types

Use domain-specific types where they improve correctness.

Examples may include:

```text
RideID
DriverID
Region
Coordinates
RideState
OfferState
```

Follow the existing domain model.

Do not introduce wrappers around primitive values without a meaningful invariant or boundary.

---

# 43. Primitive Obsession

Avoid passing long lists of related primitive parameters when they represent one meaningful concept.

Instead of:

```text
latitude
longitude
radius
maxCandidates
```

consider an existing request/value type when the architecture already defines one.

Do not introduce new structs if an existing type already represents the concept.

---

# 44. Struct Design

Keep structs focused.

Avoid one giant struct containing:

```text
Database
Redis
Kafka
Ranking
Discovery
HTTP
Metrics
```

when those are separate dependencies.

---

# 45. Pointer vs Value

Use pointers where:

```text
Mutability
Large Object Size
Optionality
Identity
```

make them appropriate.

Use values for small immutable data where practical.

Follow existing package conventions.

---

# 46. Nil Handling

Required dependencies should not silently accept nil values.

Optional dependencies should have an explicit contract.

Avoid scattered defensive nil checks that hide invalid construction.

Prefer catching invalid construction at the composition boundary.

---

# 47. Collections

Prefer the simplest collection appropriate to the operation.

Consider:

```text
Slice
Map
Heap
Channel
```

according to semantics and performance.

Do not choose a complex structure without a concrete requirement.

---

# 48. Candidate Collections

Candidate handling is performance-sensitive.

Use the existing:

```text
CandidateCollection
Iterator
Heap
Pipeline
```

abstractions rather than introducing parallel candidate containers.

---

# 49. Iterators

When the architecture provides an iterator abstraction, preserve streaming semantics.

Avoid changing:

```text
Iterator
```

into:

```text
Load Everything Into Memory
```

without a measured reason.

---

# 50. Concurrency Primitives

Use concurrency primitives according to ownership.

Examples:

```text
Mutex
RWMutex
Channel
Atomic
Redis Atomic Operation
Database Constraint
```

Do not use an in-process mutex to protect distributed state that can be modified by another process.

---

# 51. Goroutines

Every goroutine should have a clear owner and termination path.

Before starting a goroutine ask:

```text
Who owns it?
When does it stop?
What cancels it?
What happens on panic?
What resources does it hold?
```

---

# 52. Channels

Channels should represent a meaningful concurrency boundary.

Avoid channels merely to make synchronous code look asynchronous.

---

# 53. Time

Do not use arbitrary timeouts directly inside business code.

Prefer:

```text
Configuration
    ↓
Component
```

when the timeout represents operational policy.

Use fixed durations in code only when they are true implementation invariants.

---

# 54. Time Injection for Tests

Time-sensitive logic should be testable.

Where the behaviour requires control over time, use an appropriate clock abstraction or existing project mechanism.

Avoid tests that depend on fragile real-time sleeps.

---

# 55. Randomness

If randomness affects business behaviour and must be tested, make the source controllable.

Do not make production randomness impossible to reproduce in tests when deterministic testing is required.

---

# 56. Logging Placement

Log at meaningful boundaries.

Prefer:

```text
Application Operation
Infrastructure Failure
Lifecycle Event
Important State Transition
```

Avoid logging the same error at every layer.

---

# 57. Metrics Placement

Metrics should be owned by the component that understands the metric.

Examples:

```text
Discovery → search metrics
Ranking → ranking metrics
Reservation → reservation metrics
Messaging → broker metrics
```

Avoid multiple components incrementing the same semantic metric.

---

# 58. Tracing Placement

Create spans around meaningful operations.

Avoid:

```text
Span per helper
Span per trivial function
```

unless profiling/debugging requirements justify it.

---

# 59. Serialization

Serialization formats should remain at boundaries.

Examples:

```text
HTTP JSON
Kafka Event Envelope
Realtime Message
Database Representation
```

Do not leak transport serialization models throughout the domain.

---

# 60. DTOs and Domain Models

Transport DTOs and domain/application models should not automatically be the same type.

Map between them where the boundary requires different concerns.

Avoid exposing database models directly as public API contracts.

---

# 61. Database Models

Database-specific representations belong to persistence boundaries.

Application services should work with application/domain concepts rather than SQL-row structures.

---

# 62. Event Models

Event contracts should be stable and explicit.

Do not reuse arbitrary internal structs as events merely because their fields happen to match.

Events are integration contracts.

---

# 63. Redis Models

Redis-specific representations should remain inside the Redis-backed component.

Application code should not need to know:

```text
Redis Hash
Redis Set
Sorted Set
Key Prefix
TTL Command
```

unless the architecture explicitly exposes such a capability.

---

# 64. Dependency Injection in Tests

Tests should be able to replace external dependencies without changing production code.

Use:

```text
Fake
Stub
In-memory implementation
Test repository
```

where appropriate.

Do not introduce a mocking framework solely because it is available.

---

# 65. Test Package Placement

Tests should remain close to the code they verify unless an external-package test is intentionally required.

Use external package tests when verifying only public behaviour is desirable.

---

# 66. Test Naming

Tests should communicate behaviour.

Prefer:

```text
TestReserveDriver_RejectsAlreadyReservedDriver
TestRanker_PrefersLowerETA
TestConsumer_IsIdempotent
```

over:

```text
Test1
TestBasic
TestFunction
```

---

# 67. Benchmark Placement

Benchmarks should live near the implementation they measure.

Use benchmarks for:

```text
Ranking
Candidate Processing
H3 Lookup
Serialization
Hot Path Algorithms
```

when performance matters.

---

# 68. Generated and Tooling Files

Generated code, local tooling, and temporary files should follow repository conventions.

Do not commit:

```text
IDE State
Local Secrets
Temporary Logs
Debug Dumps
Build Artifacts
```

unless explicitly required.

---

# 69. Imports

Keep imports formatted using standard Go tooling.

Prefer clear import grouping and remove unused dependencies.

Do not use import aliases unless they resolve an actual naming conflict or improve clarity.

---

# 70. Formatting

Run the project's Go formatting tooling before committing.

Do not manually fight formatter output.

Formatting should remain consistent across the repository.

---

# 71. Static Analysis

Use the repository's configured static analysis and linting tools where available.

Static analysis should be part of development verification rather than an afterthought.

---

# 72. Dead Code

Remove unused code when it is confirmed to be obsolete.

Do not retain old implementations merely because they might be useful someday.

If compatibility requires retaining old code, document why.

---

# 73. Compatibility Wrappers

When an API must remain temporarily compatible:

```text
Old API
   ↓
Compatibility Wrapper
   ↓
New Implementation
```

Document the migration/removal plan.

Do not create permanent duplicate paths accidentally.

---

# 74. Refactoring Package Boundaries

Before moving a package:

```text
Find Consumers
Find Imports
Find Tests
Find Builders
Find Documentation References
Find Configuration References
```

Then move the responsibility coherently.

---

# 75. Package API Surface

Keep package APIs small.

Every exported type or function increases the coupling surface.

Prefer:

```text
Small Public Contract
Large Private Implementation
```

where practical.

---

# 76. Avoid Circular Business Dependencies

For example, avoid:

```text
Ranking → Discovery
Discovery → Ranking
```

when both responsibilities are intended to remain independent.

Use composition to connect them.

---

# 77. Dispatch Dependency Shape

The dispatch system should conceptually remain:

```text
Discovery
   ↓
Candidate Pipeline
   ↓
Ranking
   ↓
Reservation
   ↓
Offer
```

Do not create shortcuts such as:

```text
Ranking → Redis
Ranking → Discovery
Offer → Ranking
```

unless the architecture explicitly requires them.

---

# 78. Infrastructure Dependency Shape

Infrastructure implementations should remain behind their contracts.

Conceptually:

```text
Application
    ↓
Contract
    ↑
Implementation
    ↓
External Technology
```

This keeps provider details replaceable.

---

# 79. Composition Dependency Shape

Construction should remain centralized:

```text
Configuration
      ↓
Builders / Bootstrap
      ↓
Concrete Implementations
      ↓
Application Components
```

Do not move construction into leaf components.

---

# 80. Documentation References

When a code change materially changes:

```text
Architecture
Component Responsibility
Business Rule
Configuration
Operational Behaviour
Event Contract
```

update the appropriate documentation.

Do not duplicate the same explanation across multiple documents unless each document needs a different perspective.

---

# 81. Avoid Documentation Drift

Documentation should describe the actual system.

After a structural change:

```text
Code
Architecture Docs
Component Docs
Development Docs
ADR
```

should be reviewed for consistency.

Do not invent implementation details that are not present in the repository.

---

# 82. New Component Checklist

Before introducing a new component:

```text
[ ] Existing responsibility searched
[ ] Existing package searched
[ ] Ownership defined
[ ] Interface requirement justified
[ ] Configuration requirement identified
[ ] Lifecycle defined
[ ] Error behaviour defined
[ ] Concurrency considered
[ ] Tests planned
[ ] Observability considered
[ ] Documentation impact identified
```

---

# 83. New Package Checklist

Before creating a package:

```text
[ ] Responsibility is cohesive
[ ] Existing package cannot reasonably own it
[ ] Dependency direction remains valid
[ ] No import cycle introduced
[ ] Public API is intentionally small
[ ] Package name clearly communicates responsibility
[ ] Tests have a natural location
```

---

# 84. New Interface Checklist

Before creating an interface:

```text
[ ] Consumer has a real capability dependency
[ ] Existing interface does not already provide it
[ ] Interface is narrow
[ ] Implementation(s) exist or are justified
[ ] Testing/provider replacement benefits are real
```

---

# 85. New Configuration Checklist

Before adding configuration:

```text
[ ] Value represents runtime/deployment policy
[ ] Hard-coding is undesirable
[ ] Owner is identified
[ ] Validation exists
[ ] Default behaviour is intentional
[ ] Configuration is documented
```

---

# 86. AI Agent Rules

Before modifying code, an AI agent must:

1. Read `1.DEVELOPMENT_GUIDELINES.md`.
2. Read the relevant architecture document.
3. Read the relevant component document.
4. Search the repository for existing implementations.
5. Search for existing interfaces.
6. Search for existing configuration.
7. Identify the dependency owner.
8. Identify the correct package.
9. Implement within the existing structure.
10. Add/update tests.
11. Run formatting and relevant verification.
12. Inspect the final diff.

---

# 87. AI Agent Forbidden Patterns

AI agents must not:

- create duplicate abstractions,
- create generic `utils` packages to avoid architectural decisions,
- introduce globals,
- bypass existing interfaces,
- move business logic into infrastructure,
- move infrastructure details into application/domain code,
- add configuration for every constant,
- hard-code operational policy,
- create hidden dependency lookups,
- introduce import cycles,
- create orphan goroutines,
- expose provider-specific models through application APIs,
- perform unrelated refactors during feature work,
- claim verification that was not actually performed.

---

# 88. Decision Rule for Code Placement

When unsure where code belongs, use this sequence:

```text
Does it define a business rule?
        │
        ├── Yes → Domain / Application ownership
        │
        └── No
             ↓
Does it orchestrate a use case?
        │
        ├── Yes → Application Service
        │
        └── No
             ↓
Does it persist/retrieve state?
        │
        ├── Yes → Persistence
        │
        └── No
             ↓
Does it communicate with an external system?
        │
        ├── Yes → Infrastructure
        │
        └── No
             ↓
Is it a transport concern?
        │
        ├── Yes → Transport
        │
        └── No
             ↓
Does an existing component already own it?
        │
        ├── Yes → Extend existing component
        │
        └── No → Define a new responsibility deliberately
```

```text
Dispatch
Candidate Management
Discovery
Ranking
Reservation
Refinement
Messaging
Persistence
Bootstrap / Composition
```

Future development should extend these existing boundaries before introducing new parallel structures.

---

# 90. Final Rule

The most important code-structure rule is:

> **Place code according to responsibility and architectural ownership, not according to convenience. Reuse existing contracts and components, keep dependency direction explicit, keep package APIs narrow, and make new abstractions only when they represent a real boundary.**

The codebase should remain understandable to a developer or AI agent who has never worked on RideForge before but has read the project documentation.
