# 1. Purpose

The local development environment should allow a developer to:

```text
Clone the Repository
        ↓
Configure the Environment
        ↓
Start Required Infrastructure
        ↓
Run the Application
        ↓
Run Tests
        ↓
Inspect Logs / Telemetry
        ↓
Develop Safely
```

The environment should be:

```text
Reproducible
Simple
Isolated
Close to Production Architecture
Easy to Reset
```

---

# 2. Local Development Principle

Local development should reproduce the application's important architectural dependencies without requiring production infrastructure.

The goal is:

```text
Production Architecture
        ↓
Local Equivalent
```

not:

```text
Production Architecture
        ↓
Completely Different Local Implementation
```

---

# 3. Supported Local Stack

The local environment should support the core RideForge components:

```text
Go Application
PostgreSQL
Redis
Kafka / Redpanda
```

Additional services should be started only when required by the current development workflow.

---

# 4. Development Machine Requirements

A developer should have the tools required by the repository and its infrastructure.

Core requirements include:

```text
Git
Go
Docker
Docker Compose
```

Additional tools may be required for:

```text
Database Inspection
Redis Inspection
Kafka / Redpanda Inspection
API Testing
Profiling
```

Use the versions documented by the repository where version pinning exists.

---

# 5. Go Version

The local Go version should match the version declared by the project.

Use the repository's:

```text
go.mod
```

as the authoritative source for the required Go toolchain unless project documentation explicitly specifies otherwise.

Do not upgrade the Go version merely because a newer version is available.

---

# 6. Docker

Docker should be used for local infrastructure where the project provides containerized dependencies.

Typical infrastructure:

```text
PostgreSQL
Redis
Kafka / Redpanda
```

Containerization keeps developer environments more consistent.

---

# 7. Docker Compose

Docker Compose should be the preferred mechanism for bringing up multiple local infrastructure dependencies together when the repository provides a Compose configuration.

Conceptually:

```text
docker compose up -d
```

should start the required infrastructure.

Use the repository's actual Compose files and commands.

---

# 8. Repository Setup

A new developer should begin with:

```bash
git clone <repository>
cd <repository>
```

Then inspect:

```text
README
go.mod
Docker / Compose files
.env.example or equivalent
docs/
```

Do not assume local infrastructure or configuration before inspecting the repository.

# 13. Infrastructure Startup

Start infrastructure before starting application components that require it.

Conceptually:

```text
PostgreSQL
Redis
Kafka / Redpanda
        ↓

```

---

# 14. Infrastructure Health

After starting containers, verify that required dependencies are actually ready.

Do not assume:

```text
Container Running
```

means:

```text
Service Ready
```

Use the health checks provided by the repository or inspect the dependency directly.

---

# 15. PostgreSQL

PostgreSQL provides the authoritative relational data store.

Local PostgreSQL should be isolated from:

```text
Staging
Production
```

---

# 16. PostgreSQL Initialization

Database initialization should follow the repository's migration workflow.

Do not manually create tables unless the project explicitly requires it.

Use:

```text
Migration Files
```

as the source of schema evolution.

---

# 17. PostgreSQL Reset

When local database state becomes invalid, use the documented reset procedure.

A reset may conceptually be:

```text
Stop Application
    ↓
Remove Local Database
    ↓
Recreate Database
    ↓
Run Migrations
    ↓
Seed Development Data if Required
```

Do not use destructive reset commands against non-local databases.

---

# 18. PostgreSQL Inspection

Developers should be able to inspect local database state using a PostgreSQL client or database tool.

Inspection should normally be:

```text
Read
```

rather than modifying data manually.

---

# 19. Redis

Redis supports latency-sensitive operational workloads.

Local Redis should be isolated from all non-local environments.

---

# 20. Redis Initialization

Redis generally does not require schema migrations like PostgreSQL.

Application-owned key structures should nevertheless be documented and reproducible.

Follow:

```text
7.REDIS_DEVELOPMENT.md
```

for Redis-specific development practices.

---

# 21. Redis Reset

When local Redis state becomes invalid, a local reset may be performed.

A reset should affect only the local Redis instance.

Never run destructive Redis reset operations against production.

---

Local development should support the driver-location workflow:

```text
Driver Location Update
        ↓

        ↓

        ↓
```

Use controlled test data rather than uncontrolled real-world location streams.

# 23. Kafka / Redpanda

The local messaging environment should reproduce the project's production-compatible event architecture as closely as practical.

The repository's selected broker implementation is authoritative for local development.

```text
Production Consumer Group
```

# 58. Local Network

Containers may communicate using Compose service names rather than:

```text
localhost
```

Be aware of the distinction:

```text
Host → localhost
Container → Service Name
```

Use the repository's network configuration.

---

# 59. Local Database Hostname

When the application runs:

```text
On Host
```

the PostgreSQL connection may use a host-mapped port.

When the application runs:

```text
Inside Docker
```

it may use the Compose service name.

Do not hard-code one topology into the application.

---

# 60. Local Redis Hostname

Apply the same distinction to Redis:

```text
Host Application
→ Host / mapped port

Container Application
→ Redis service name / container network
```

Use configuration.

---

# 61. Local Broker Connectivity

Kafka / Redpanda can require different advertised listener configuration depending on whether clients run:

```text
On Host
```

or:

```text
Inside Docker Network
```

The local broker configuration must support the intended development topology.

---

# 62. Time and Clock

Distributed development workflows can be affected by clock differences.

Avoid relying on local wall-clock assumptions for correctness.

Use the application's time abstraction where one exists.

---

# 63. Timezone

Local development should use an explicitly understood timezone configuration.

Business dates and timestamps must follow the application's documented time semantics.

Do not silently use a developer's machine timezone for domain decisions.

---

# 64. Environment Isolation

```text
Test
```

# 92. AI Agent Local Setup Rules

Before changing local development infrastructure, an AI agent must:

1. Inspect the repository's existing startup and infrastructure files.
2. Reuse existing Docker / Compose definitions.
3. Reuse existing environment variable names.
4. Determine which dependencies the requested change actually needs.
5. Avoid creating duplicate local infrastructure definitions.
6. Keep local configuration isolated from non-local environments.
7. Check migration requirements.
8. Check messaging topic and consumer-group requirements.
9. Preserve existing developer workflows where possible.
10. Update documentation only when the workflow actually changes.
11. Validate the local setup.
12. Review the final diff.

---

# 93. AI Agent Forbidden Local Setup Patterns

AI agents must not:

- invent startup commands when repository commands already exist,
- hard-code local infrastructure addresses into application code,
- point local configuration to production infrastructure,
- commit secrets,
- reuse production credentials,
- run destructive commands against non-local infrastructure,
- create duplicate Docker Compose definitions without justification,
- manually modify database schemas instead of using migrations,
- reset Redis or broker state without confirming the target environment,
- add unnecessary dependencies to the local stack,
- claim local setup works without validating the relevant workflow.

# 95. Final Local Development Principle

> **A local RideForge environment should be easy to create, safe to destroy, representative of the production architecture, and deterministic enough that developers can focus on application behaviour rather than machine-specific infrastructure problems.**

The intended local workflow is:

```text
Clone
  ↓
Configure
  ↓
Start Infrastructure
  ↓
Migrate
  ↓
Seed
  ↓
Start Application
  ↓
Verify
  ↓
Develop
  ↓
Test
  ↓
Debug
  ↓
Review
```

The local environment must remain isolated from:

```text
Production Data
Production Credentials
Production Infrastructure
```

while still preserving the important architectural behaviour of:

```text
Go
+
PostgreSQL
+
Redis
+
Kafka / Redpanda
+
Event-Driven Workflows
+
Dispatch
+
Reservation
```

The goal is not to reproduce production scale locally.

The goal is to reproduce the important **behaviour, boundaries, dependencies, and development workflow** locally in a safe and repeatable way.
