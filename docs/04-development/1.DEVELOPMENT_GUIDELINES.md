# RideForge — Development Guidelines

> **Document:** `docs/04-development/1.DEVELOPMENT_GUIDELINES.md`  
> **Status:** Active  
> **Scope:** General development rules for building, modifying, testing, reviewing, and maintaining the RideForge codebase  
> **Related:** `docs/00-project/1.PROJECT_VISION.md`, `docs/02-architecture/`, `docs/03-components/`, `docs/04-development/2.CODE_STRUCTURE_AND_CONVENTIONS.md`, `docs/04-development/3.GO_DEVELOPMENT_STANDARDS.md`, `docs/04-development/20.DEVELOPMENT_CHECKLIST.md`

---

# 1. Purpose

This document defines the general engineering rules for developing RideForge.

It is the first development document an engineer or AI coding agent should read before modifying the codebase.

The objective is to ensure that development remains:

```text
Consistent
Predictable
Testable
Maintainable
Production-Grade
Architecture-Aligned
```

---

# 2. Development Philosophy

RideForge should be developed as a production system rather than as a collection of features that happen to work.

Every implementation should consider:

```text
Correctness
Concurrency
Failure
Performance
Observability
Testability
Maintainability
Operational Safety
```

A feature is not complete merely because the happy path works.

---

# 3. Read Before Coding

Before implementing a non-trivial change, developers and AI agents must understand the relevant documentation.

At minimum:

```text
Project Vision
      ↓
Relevant Architecture
      ↓
Relevant Component
      ↓
Development Guidelines
      ↓
Existing Implementation
```

Do not begin implementation by guessing how the system is structured.

---

# 4. Existing Code Is Part of the Contract

Before creating a new implementation:

```text
Search Existing Code
      ↓
Search Existing Interfaces
      ↓
Search Existing Components
      ↓
Search Existing Configuration
      ↓
Reuse Where Appropriate
```

Do not create a second implementation simply because the existing one was not immediately obvious.

---

# 5. Architecture Before Code

When a requested change crosses architectural boundaries:

```text
Understand Boundary
      ↓
Identify Owning Component
      ↓
Identify Application Contract
      ↓
Implement
```

Do not solve architectural problems by adding code wherever it is easiest.

---

# 6. Component Ownership

Every piece of behaviour should have a clear owner.

Examples:

```text
Geographic Discovery
    → Discovery

Candidate Filtering
    → Candidate Pipeline

Candidate Ranking
    → Ranking

Temporary Driver Ownership
    → Reservation

Offer Lifecycle
    → Offer Component

Durable State
    → Persistence

Event Transport
    → Messaging

External Technology
    → Infrastructure
```

If a change has no obvious owner, stop and determine the correct boundary before implementing it.

---

# 7. Single Responsibility

A component should have one primary responsibility.

Avoid components that simultaneously own:

```text
Discovery
Ranking
Persistence
Messaging
Realtime
Configuration
```

when these responsibilities already have dedicated components.

---

# 8. Prefer Composition

Prefer:

```text
Small Component
      ↓
Focused Interface
      ↓
Composition
```

over:

```text
Large Component
      ↓
Many Internal Responsibilities
```

The composition root should connect the focused components.

---

# 9. Explicit Dependencies

Dependencies should be visible through constructors or explicit composition.

Prefer:

```text
NewService(
    repository,
    locker,
    searcher,
    ranker,
)
```

Avoid hidden dependencies through:

```text
Global Variables
Service Locators
Implicit Singletons
Environment Reads Inside Business Logic
```

---

# 10. No Global Business State

Do not introduce mutable global state for:

```text
Current Ride
Current Driver
Dispatch State
Ranking Configuration
Reservations
Request State
```

Runtime state should belong to an explicit component.

---

# 11. Configuration-Driven Policy

Operational policy should be configurable where appropriate.

Examples:

```text
Search Limits
Ranking Weights
Reservation TTL
Offer Timeout
Retry Limits
Connection Pool Limits
```

Do not hard-code deployable operational policy inside business components.

---

# 12. Do Not Over-Configure

Not every constant needs configuration.

Keep implementation-level invariants in code when they are genuinely fixed.

Good configuration:

```text
Offer Timeout
Retry Limit
Pool Size
Ranking Weight
```

Potentially unnecessary configuration:

```text
Internal Collection Initial Capacity
Simple Mathematical Constant
Private Implementation Detail
```

Configuration should represent meaningful runtime policy.

---

# 13. Business Logic Must Be Explicit

Business rules should be visible in the appropriate application/domain component.

Do not hide business behaviour inside:

```text
Repository
Redis Adapter
Kafka Producer
HTTP Handler
Configuration Loader
```

Infrastructure provides capabilities.

Application/domain components decide what those capabilities mean.

---

# 14. Preserve Layer Boundaries

The general dependency direction is:

```text
Transport
    ↓
Application
    ↓
Domain / Contracts
    ↑
Infrastructure
```

Infrastructure implements application-facing contracts.

Application code should not become dependent on:

```text
Redis Command APIs
SQL Driver Types
Kafka Message Types
Provider SDK Models
```

unless an explicitly documented boundary requires it.

---

# 15. No Shortcut Through Infrastructure

Do not bypass an existing abstraction merely because direct access is convenient.

Bad:

```text
MatchingEngine
    ↓
Redis Client
```

when the architecture already provides:

```text
MatchingEngine
    ↓
DriverLocker / Cache Interface
    ↓
Redis
```

Shortcuts create coupling that becomes expensive later.

---

# 16. Reuse Before Creating

Before adding:

```text
Interface
Service
Repository
Builder
Helper
Utility
Configuration Section
```

search the codebase for an existing equivalent.

Ask:

```text
Does this already exist?
Can the existing abstraction support this?
Would extending it preserve its responsibility?
```

Only create a new abstraction when there is a genuine boundary.

---

# 17. Avoid Premature Abstraction

Do not create generic abstractions merely because they look architecturally elegant.

An abstraction should solve a real problem such as:

```text
Technology Isolation
Provider Replacement
Testing
Multiple Implementations
Clear Application Boundary
```

---

# 18. Avoid Premature Optimization

Optimize based on:

```text
Measured Latency
Measured Throughput
Resource Usage
Production Failure
```

rather than assumptions.

However, established hot-path requirements should be respected.

RideForge dispatch is latency-sensitive, so avoid obviously expensive patterns such as:

```text
N+1 Database Queries
Unbounded Candidate Collection
Sequential Network Calls Where Batching Exists
Repeated Redis Round Trips
```

---

# 19. Performance Is a Design Concern

Performance should be considered before implementation reaches production.

For dispatch-related code consider:

```text
Network Round Trips
Database Queries
Redis Commands
Allocations
Candidate Count
Serialization
Lock Duration
External API Latency
```

---

# 20. Correctness Before Optimization

The preferred order is:

```text
Correct
    ↓
Tested
    ↓
Measured
    ↓
Optimized
```

Do not sacrifice correctness for an unmeasured performance improvement.

---

# 21. Concurrency Is Normal

RideForge is a concurrent distributed system.

Assume that operations can happen simultaneously.

Examples:

```text
Two Dispatch Nodes
Two Offer Responses
Ride Cancellation + Offer Acceptance
Offer Timeout + Driver Acceptance
Driver Location Updates
Duplicate Events
Redis Expiration
```

Code must not assume that a state observed a moment ago is still unchanged.

---

# 22. Protect State Transitions

Concurrency-sensitive state changes should use appropriate mechanisms:

```text
Database Transaction
Conditional Update
Unique Constraint
Redis Atomic Operation
Lua Script
Reservation
Idempotency
```

Choose the mechanism according to the state owner.

---

# 23. Check-Then-Act Warning

Be careful with:

```text
READ
 ↓
CHECK
 ↓
WRITE
```

when another process can modify the same state between the operations.

Prefer atomic or conditional operations when the state transition requires them.

---

# 24. Idempotency

Important operations should tolerate duplicate execution where practical.

Examples:

```text
Event Consumption
Offer Acceptance
Assignment Creation
Outbox Publication
Retry
Background Jobs
```

The system should aim for:

```text
Duplicate Delivery
      ↓
One Business Effect
```

---

# 25. Failure Is Part of the Design

Every non-trivial implementation should consider:

```text
Timeout
Unavailable Dependency
Duplicate Request
Partial Failure
Concurrent Update
Process Restart
Message Redelivery
Stale Data
```

Do not implement only the successful path.

---

# 26. Distinguish Empty From Failure

A critical rule:

```text
No Result
```

is not automatically:

```text
Dependency Failure
```

Examples:

```text
No nearby drivers
```

is different from:

```text
Redis unavailable
```

and:

```text
No database record
```

is different from:

```text
PostgreSQL unavailable
```

Preserve these distinctions.

---

# 27. Error Handling

Errors should preserve enough context for the caller to make the correct decision.

Prefer meaningful categories such as:

```text
Not Found
Conflict
Invalid State
Timeout
Unavailable
Validation Failure
Internal Failure
```

Do not turn every error into a generic string.

---

# 28. Do Not Swallow Errors

Avoid:

```text
if err != nil {
    return nil
}
```

when the failure affects correctness.

Every ignored error should be intentional and justified.

---

# 29. Do Not Leak Infrastructure Errors

Application-facing APIs should not unnecessarily expose:

```text
RedisError
KafkaError
SQLDriverError
ProviderSDKError
```

Map infrastructure failures into application-level error semantics at the appropriate boundary.

Preserve the underlying cause for diagnostics.

---

# 30. Transactions

Use transactions when multiple durable operations must be atomic.

For example:

```text
Business State
+
Outbox Event
```

should be committed together when the event represents that durable state change.

---

# 31. Keep Transactions Short

Do not hold database transactions while performing:

```text
HTTP Requests
Redis Calls
Kafka Publication
WebSocket Delivery
Long Computation
Driver Waiting
```

Preferred:

```text
Transaction
   ↓
Commit
   ↓
External Work / Event Processing
```

Use the outbox pattern where asynchronous delivery must be reliable.

---

# 32. Database Access

Database access should remain behind repositories or the appropriate persistence abstraction.

Avoid:

```text
SQL in Handler
SQL in Ranker
SQL in Redis Adapter
SQL scattered across Application Services
```

---

# 33. Avoid N+1 Access

Before writing a loop that accesses persistence:

```text
for candidate:
    fetch(...)
```

ask whether the operation can use:

```text
Batch Fetch
Pipeline
Join
Projection
Bulk Operation
```

This is especially important in dispatch.

---

# 34. Redis Development

Redis should be treated as an operational store, not an accidental second source of durable business truth.

Respect:

```text
TTL
Atomicity
Key Ownership
Concurrency
Failure Semantics
```

Use the existing Redis abstractions.

---

# 35. Event Development

Events should represent facts that have already occurred.

Preferred:

```text
State Change
    ↓
Outbox
    ↓
Event
```

Avoid publishing an event that claims a business operation succeeded before the required durable state exists.

---

# 36. At-Least-Once Assumption

Consumers must assume messages can be delivered more than once.

Therefore:

```text
Consumer
    ↓
Idempotent Business Effect
```

Do not design consumers around exactly-once assumptions unless an explicit mechanism guarantees the required semantics.

---

# 37. Event Contract Stability

Events are APIs between asynchronous components.

Before changing an event:

```text
Search Consumers
      ↓
Check Compatibility
      ↓
Plan Migration
      ↓
Change
```

Do not casually rename/remove event fields.

---

# 38. API Development

Transport handlers should remain thin.

Typical flow:

```text
Decode
 ↓
Validate Transport Input
 ↓
Call Application Service
 ↓
Map Result
```

Do not duplicate application business logic in HTTP or realtime handlers.

---

# 39. Realtime Development

Realtime handlers should treat incoming messages as external input.

Validate:

```text
Message Type
Required Fields
Entity Ownership
State
```

before invoking application operations.

---

# 40. Testing Is Part of Implementation

A change is not complete when code compiles.

The implementation should include appropriate tests.

At minimum consider:

```text
Happy Path
Invalid Input
Failure Path
Concurrency
Duplicate Execution
Boundary Conditions
```

---

# 41. Test at the Right Level

Use:

```text
Unit Tests
    → Pure logic / orchestration

Integration Tests
    → PostgreSQL / Redis / Messaging semantics

End-to-End Tests
    → Critical complete workflows
```

Do not force every test into one category.

---

# 42. Test Behaviour, Not Implementation

Prefer tests that verify:

```text
Given
When
Then
```

rather than tests tightly coupled to internal helper structure.

A refactor should not require rewriting tests when externally observable behaviour remains unchanged.

---

# 43. Integration Tests for Infrastructure Semantics

Use real infrastructure in tests when correctness depends on actual behaviour.

Examples:

```text
Redis Lua Atomicity
PostgreSQL Transactions
Database Constraints
Kafka Redelivery
Redis TTL
```

Mocks cannot fully prove technology-specific semantics.

---

# 44. Concurrency Testing

For concurrency-sensitive code, add tests that actually exercise concurrent execution.

Examples:

```text
Concurrent Reservation
Concurrent Acceptance
Concurrent Cancellation
Duplicate Event Processing
```

Use race detection where appropriate.

---

# 45. Observability During Development

New non-trivial workflows should provide enough:

```text
Metrics
Logs
Tracing
```

to diagnose failures.

Do not add telemetry blindly.

Use existing instrumentation conventions.

---

# 46. Logging Rules

Logs should be:

```text
Structured
Useful
Low-Noise
Safe
Correlatable
```

Do not log:

```text
Secrets
Passwords
Tokens
Sensitive Payloads
```

or every high-frequency candidate operation.

---

# 47. Metric Rules

Metrics should be:

```text
Aggregated
Low Cardinality
Stable
Actionable
```

Avoid labels containing unbounded values such as:

```text
ride_id
driver_id
request_id
trace_id
```

Use logs/traces for per-entity diagnostics.

---

# 48. Tracing Rules

Use tracing for cross-component flows such as:

```text
Dispatch
Reservation
Offer
Database
Redis
Messaging
External Routing
```

Avoid creating spans for every trivial helper function.

---

# 49. Security

Every development change should consider:

```text
Authentication
Authorization
Input Validation
Secrets
Sensitive Data
Injection
Transport Security
```

Never commit credentials or secrets.

---

# 50. Input Validation

Validate external input at the application boundary.

Examples:

```text
IDs
Coordinates
Enums
State
Pagination
Timeout Values
Payload Size
```

Do not assume client input is trustworthy.

---

# 51. Authorization

Do not assume that reaching an application operation means the caller is authorized.

Where authorization is required:

```text
Authenticate
   ↓
Authorize
   ↓
Execute Use Case
```

The exact authorization architecture is defined by the project security model.

---

# 52. Dependency Updates

Before updating a dependency:

```text
Check Current Version
      ↓
Review Breaking Changes
      ↓
Check Usage
      ↓
Update
      ↓
Run Tests
```

Do not upgrade dependencies merely to obtain a newer version without understanding impact.

---

# 53. Library Selection

Prefer existing project dependencies when they already satisfy the requirement.

Before adding a library consider:

```text
Do We Already Have This Capability?
Is the Dependency Maintained?
Does It Increase Operational Complexity?
Does It Fit the Architecture?
Is the Problem Large Enough to Justify It?
```

Avoid dependency proliferation.

---

# 54. File and Package Placement

Put code where its responsibility belongs.

Before creating a file ask:

```text
Which layer owns this?
Which component owns this?
Does a package already exist?
```

Do not create miscellaneous:

```text
utils/
helpers/
common/
misc/
```

packages merely to avoid deciding ownership.

---

# 55. Utility Functions

A utility should be:

```text
Small
Generic Within Its Real Scope
Stateless Where Possible
Clearly Owned
```

Avoid utility packages becoming a dumping ground for unrelated logic.

---

# 56. Naming

Names should describe responsibility.

Prefer:

```text
CandidateSearcher
DriverLocker
QualityCalculator
OutboxPublisher
```

over vague names such as:

```text
Manager
Helper
Processor
Handler
Utility
```

when a more precise name exists.

---

# 57. Comments

Comments should explain:

```text
Why
Invariant
Concurrency Requirement
Non-Obvious Decision
External Constraint
```

Do not write comments that merely restate obvious code.

Bad:

```go
// Increment counter
counter++
```

Good:

```go
// Keep the reservation owner token stable so a stale cleanup
// cannot release a newer reservation.
```

---

# 58. Documentation Comments

Public exported Go types/functions should have appropriate documentation where required by project standards.

Comments should remain accurate as code changes.

Outdated comments are worse than missing comments.

---

# 59. TODOs

A TODO should explain:

```text
What remains
Why it remains
Relevant context
```

Avoid vague TODOs:

```text
TODO: fix this
```

Prefer:

```text
TODO: Replace fallback ETA calculation with routing-provider ETA
      once the routing adapter is enabled in production.
```

---

# 60. Temporary Code

Temporary code must be clearly identifiable.

Do not leave:

```text
Debug Prints
Hard-Coded Test Values
Dead Feature Flags
Temporary Bypasses
Commented-Out Implementations
```

in production code without an explicit reason.

---

# 61. Feature Flags

If a feature requires staged rollout:

```text
Configuration / Feature Flag
      ↓
Controlled Selection
```

Feature flags should have:

```text
Owner
Purpose
Default
Removal Plan
```

Do not allow permanent feature-flag accumulation.

---

# 62. Commit Discipline

Commits should represent coherent changes.

Prefer:

```text
One Logical Change
      ↓
One Clear Commit
```

Avoid mixing:

```text
Refactor
Feature
Formatting
Dependency Upgrade
Unrelated Bug Fix
```

into one commit unless there is a real reason.

---

# 63. Commit Messages

Commit messages should explain the change.

Prefer:

```text
feat(dispatch): add reservation-aware candidate selection
fix(reservation): prevent stale release
refactor(ranking): isolate quality scoring
test(dispatch): add concurrent reservation coverage
```

The repository's actual Git convention is authoritative if already defined.

---

# 64. Pull Requests

A pull request should explain:

```text
What Changed
Why
Architecture Impact
Tests
Operational Impact
Migration Requirements
```

Keep unrelated changes out.

---

# 65. Code Review

Reviewers should evaluate:

```text
Correctness
Architecture
Concurrency
Failure Handling
Performance
Security
Testing
Observability
Maintainability
```

Compilation alone is not sufficient review.

---

# 66. Before Modifying Existing Architecture

If a requested change appears to contradict the documented architecture:

```text
Stop
 ↓
Identify Conflict
 ↓
Review Architecture / ADR
 ↓
Determine Whether Architecture Should Change
 ↓
Document Decision
 ↓
Implement
```

Do not silently change architectural direction through code.

---

# 67. Architecture Changes

A change is architectural when it affects:

```text
Component Ownership
Storage Strategy
Messaging Model
Consistency Model
Concurrency Model
Service Boundaries
External Provider Strategy
Runtime Topology
```

Architectural changes should be documented through the project's ADR process.

---

# 68. Avoid Phase Fragmentation

Development should not artificially split a coherent implementation into many tiny changes merely to create phases.

Prefer:

```text
Complete Coherent Capability
```

over:

```text
Ten Tiny Changes
```

when the work can safely be implemented and reviewed together.

---

# 69. AI-Assisted Development

AI agents may be used extensively, but generated code must follow the same engineering standards as manually written code.

The agent should:

```text
Read Documentation
Inspect Existing Code
Understand Ownership
Implement
Test
Review
Report Changes
```

AI-generated code is not exempt from architecture or testing requirements.

---

# 70. AI Agent Context

When assigning work to an AI agent, provide:

```text
Relevant Documentation
Current Objective
Constraints
Expected Files
Existing Implementation
Tests
Acceptance Criteria
```

The agent should not infer missing architecture from a single file.

---

# 71. AI Agent Change Scope

Agents should avoid unrelated changes.

If the requested task is:

```text
Fix Reservation Atomicity
```

do not simultaneously:

```text
Rewrite Ranking
Rename Packages
Upgrade Dependencies
Refactor Logging
```

unless required by the task.

---

# 72. AI Agent Verification

An AI agent should report:

```text
Files Changed
Behaviour Added/Changed
Tests Added
Tests Run
Known Limitations
Potential Follow-Up
```

Do not claim tests passed if they were not actually run.

---

# 73. Build Verification

Before considering implementation complete:

```text
Format
 ↓
Compile
 ↓
Unit Tests
 ↓
Relevant Integration Tests
 ↓
Race Detection where applicable
 ↓
Review Diff
```

Use the project's actual commands and tooling.

---

# 74. Diff Review

Always inspect the final diff.

Look for:

```text
Unexpected Files
Debug Code
Secrets
Unrelated Changes
Accidental API Changes
Generated Files
Incorrect Imports
Dead Code
```

A successful test suite does not guarantee a clean change.

---

# 75. Generated Code

Generated files should follow the project's generation workflow.

Do not manually edit generated code unless the repository explicitly requires it.

Document generation commands where appropriate.

---

# 76. Dependency Graph Awareness

Before changing a shared interface:

```text
Find Implementations
      ↓
Find Consumers
      ↓
Find Builders
      ↓
Find Tests
      ↓
Change Contract
      ↓
Update All Required Implementations
```

Do not update only the first compilation error and stop.

---

# 77. Refactoring

A refactor should preserve behaviour unless the purpose is explicitly to change behaviour.

Preferred sequence:

```text
Existing Tests
      ↓
Small Refactor
      ↓
Tests
      ↓
Next Refactor
```

Avoid combining large behavioural changes with unrelated refactors.

---

# 78. Performance-Sensitive Code

For dispatch hot paths, pay special attention to:

```text
Allocations
Redis Round Trips
Database Queries
Candidate Count
Sorting
Heap Operations
External Calls
Lock Duration
Serialization
```

Use benchmarks/profiling when optimizing.

---

# 79. Resource Limits

Every external or concurrent resource should have bounded usage.

Consider:

```text
Connections
Goroutines
Workers
Queue Size
Retries
Timeouts
Payload Size
Candidate Count
```

Unbounded behaviour is a production risk.

---

# 80. Graceful Shutdown

New background components must integrate with the application's lifecycle.

A new worker must define:

```text
Start
Stop
Cancellation
Resource Cleanup
Shutdown Timeout
```

Do not create orphan goroutines.

---

# 81. Backward Compatibility

When changing public contracts, consider:

```text
Existing Consumers
Existing Events
Existing Database Data
Existing Configuration
Rolling Deployments
```

Do not assume the entire system changes simultaneously.

---

# 82. Data Compatibility

Database changes should consider existing rows and old application versions.

Prefer safe migration sequences such as:

```text
Add Compatible Field
      ↓
Deploy Code
      ↓
Backfill
      ↓
Switch Reads/Writes
      ↓
Remove Old Field Later
```

when required by deployment strategy.

---

# 83. Operational Readiness

A feature should be operationally understandable.

Before completion ask:

```text
How will we know it failed?
How will we know it is slow?
How will we debug it?
What dependency can fail?
What happens during restart?
What happens during duplicate execution?
```

---

# 84. Definition of Done

A development change is complete when:

```text
Implementation
    +
Tests
    +
Architecture Alignment
    +
Error Handling
    +
Observability
    +
Documentation where required
    +
Clean Diff
```

are satisfied.

---

# 85. Change Checklist

Before submitting a change:

```text
[ ] Correct component identified
[ ] Existing implementation searched
[ ] Existing interfaces reused where appropriate
[ ] Dependencies explicit
[ ] No business logic in infrastructure
[ ] No infrastructure logic in domain
[ ] Configuration is appropriate
[ ] Concurrency considered
[ ] Failure paths considered
[ ] Idempotency considered
[ ] Transactions reviewed
[ ] Performance considered
[ ] Tests added/updated
[ ] Observability considered
[ ] Security considered
[ ] No secrets/debug code
[ ] Final diff reviewed
```

---

# 86. AI Agent Final Checklist

An AI agent should finish a task only after answering:

```text
1. What component owns this behaviour?
2. Which existing interfaces/components were reused?
3. What architectural boundary was preserved?
4. What happens on failure?
5. What happens concurrently?
6. What happens if the operation is duplicated?
7. What is the transaction boundary?
8. What is configurable?
9. What tests prove correctness?
10. What observability exists?
11. What files changed?
12. Were the relevant tests actually run?
```

---

# 87. Current Development Principle

The RideForge development process should consistently follow:

```text
Understand
   ↓
Locate Ownership
   ↓
Reuse Existing Architecture
   ↓
Design
   ↓
Implement
   ↓
Test
   ↓
Observe
   ↓
Review
   ↓
Document
```

not:

```text
Start Coding
   ↓
Fix Compilation Errors
   ↓
Patch Tests
   ↓
Discover Architecture Later
```

---

# 88. Final Rule

The most important development rule is:

> **Do not add code merely because it solves the immediate problem. Add the smallest production-grade change that solves the problem while preserving the architecture, ownership boundaries, concurrency guarantees, operational behaviour, and future maintainability of RideForge.**

This guideline is the baseline for all subsequent development documentation and should be followed by both human developers and AI coding agents.
