# PART 1 — TESTING STRATEGY & PHILOSOPHY
# 1. Purpose

This document defines how RideForge should establish confidence that the system is:

```text
Correct
Reliable
Concurrent-Safe
Performant
Observable
Maintainable
Operationally Safe
```

Testing is treated as part of implementation, not as a final activity after coding.

---

# 2. Testing Philosophy

The preferred testing flow is:

```text
Fast Tests
    ↓
Component Tests
    ↓
Integration Tests
    ↓
Concurrency Tests
    ↓
End-to-End Tests
    ↓
Performance / Load Tests
```

Not every change requires every level.

The appropriate level is determined by the behaviour being changed.

---

# 3. Testing Pyramid

RideForge should generally follow:

```text
                    E2E
                   /   \
              Integration
             /           \
        Component Tests
       /                 \
             Unit Tests
```

The majority of tests should be fast and deterministic.

Infrastructure-dependent tests should exist where real infrastructure semantics matter.

---

# 4. Test Categories

RideForge tests should be considered across these categories:

```text
Unit
Component
Integration
Concurrency
Contract
End-to-End
Benchmark
Load
Failure / Recovery
```

Each category answers a different question.

---

# 5. Unit Tests

Unit tests verify isolated logic without requiring external infrastructure.

Good candidates:

```text
Ranking Calculations
Quality Calculations
Feature Extraction
State Validation
Retry Decisions
Candidate Filtering Rules
Domain Rules
Value Transformations
```

They should be:

```text
Fast
Deterministic
Isolated
Repeatable
```

---

# 6. Component Tests

Component tests verify a complete application component using controlled dependencies.

Examples:

```text
Candidate Pipeline
Ranking Component
Discovery Policy
Reservation Component
Application Service
```

A component test should verify the component's public behaviour rather than its private implementation details.

---

# 7. Integration Tests

Integration tests verify interactions with real infrastructure.

Examples:

```text
PostgreSQL
Redis
Kafka / Redpanda
Database Transactions
Redis Lua Scripts
Redis TTL
Outbox
Message Consumption
```

Use integration tests when a mock cannot prove the required infrastructure semantics.

---

# 8. Concurrency Tests

Concurrency is a first-class testing concern because RideForge is a distributed dispatch system.

Test scenarios such as:

```text
Concurrent Reservation
Concurrent Offer Acceptance
Concurrent Cancellation
Reservation + Timeout
Acceptance + Timeout
Duplicate Event Delivery
Concurrent Driver Updates
```

---

# 9. Contract Tests

Contract tests verify that independently developed components agree on their interfaces.

Potential contracts include:

```text
Application Interfaces
Event Schemas
Messaging Contracts
External Provider Adapters
API Contracts
```

Contract testing should be introduced where independent evolution creates compatibility risk.

---

# 10. End-to-End Tests

End-to-end tests verify critical business workflows across multiple components.

Examples:

```text
Create Ride
    ↓
Discover Drivers
    ↓
Rank Candidates
    ↓
Reserve Driver
    ↓
Create Offer
    ↓
Driver Accepts
    ↓
Assignment Created
```

E2E tests should focus on critical workflows rather than attempting to test every internal branch.

---

# 11. Test Ownership

Tests should live close to the behaviour they verify.

Conceptually:

```text
Component
   ↓
Component Tests

Repository
   ↓
Persistence Integration Tests

Consumer
   ↓
Messaging / Integration Tests

Application Service
   ↓
Orchestration Tests
```

---

# 12. Behaviour Over Implementation

Tests should verify externally meaningful behaviour.

Prefer:

```text
Given candidate with lower ETA
When ranking occurs
Then candidate receives higher travel score
```

over asserting a particular private helper was called.

This allows implementation refactoring without unnecessarily rewriting tests.

---

# 13. Determinism

Tests should produce the same result repeatedly.

Avoid unnecessary dependence on:

```text
Current Time
Randomness
Network
Execution Order
External Services
Arbitrary Sleeps
```

When time or randomness is part of the behaviour, provide controlled mechanisms.

---

# 14. Test Isolation

Tests should not unintentionally share mutable state.

Avoid shared:

```text
Global Variables
Redis Keys
Database Rows
Environment Variables
Goroutines
```

without explicit isolation.

---

# 15. Test Data

Test data should be:

```text
Minimal
Relevant
Readable
Deterministic
```

Do not construct huge datasets for tests that verify a simple rule.

For performance tests, use intentionally larger datasets.

---

# 16. Test Naming

Test names should communicate behaviour.

Preferred:

```text
TestRanker_PrefersLowerETA
TestReservation_RejectsAlreadyReservedDriver
TestConsumer_DoesNotDuplicateAssignment
```

Names should help identify failures without opening the test immediately.

---

# 17. Table-Driven Tests

Use table-driven tests when multiple cases exercise the same behaviour.

Typical candidates:

```text
Validation
State Transitions
Ranking
Filtering
Error Classification
Configuration Validation
```

Do not force unrelated behaviours into one table merely to use the pattern.

---

# 18. Error Tests

Test both:

```text
Expected Success
Expected Failure
```

For important errors, verify the error category rather than only the exact error string.

Use:

```text
errors.Is
errors.As
```

where appropriate.

---

# 19. Boundary Tests

Important boundaries should have explicit tests.

Examples:

```text
Zero Candidates
One Candidate
Maximum Candidates
Empty Collection
Invalid Coordinates
Expired Reservation
Expired Offer
Maximum Retry
```

---

# 20. State Transition Tests

Stateful components should verify valid and invalid transitions.

Example:

```text
Available
   ↓
Reserved
   ↓
Offered
   ↓
Assigned
```

and invalid transitions such as:

```text
Assigned
   ↓
Reserve
```

should be rejected when the business model requires it.

---

# 21. Idempotency Tests

Whenever an operation can be delivered more than once, test duplicate execution.

Example:

```text
Execute
Execute Again
```

Expected:

```text
One Durable Business Effect
```

Important targets include:

```text
Event Consumers
Offer Acceptance
Assignment Creation
Outbox Processing
Retries
```

---

# 22. Concurrency Test Pattern

A concurrency test should generally establish:

```text
Initial State
      ↓
Start Concurrent Operations
      ↓
Wait for Completion
      ↓
Inspect Durable State
      ↓
Verify Invariant
```

The invariant is more important than the order in which goroutines happened to execute.

---

# 23. Reservation Concurrency

Reservation is a critical concurrency boundary.

Test:

```text
Driver Available
      ↓
Dispatcher A reserves
Dispatcher B reserves
      ↓
Exactly one succeeds
```

The test should verify the durable/authoritative ownership result.

---

# 24. Acceptance Concurrency

Test:

```text
Offer Active
      ↓
Multiple Acceptance Attempts
      ↓
Exactly one valid assignment
```

depending on the business rule.

A duplicate acceptance must not produce duplicate assignment state.

---

# 25. Timeout Concurrency

Test races such as:

```text
Driver Accept
       ↕
Offer Timeout
```

The result must follow the defined offer lifecycle invariant.

Do not rely on sleep timing to prove correctness.

---

# 26. Cancellation Concurrency

Test:

```text
Ride Cancellation
       ↕
Driver Acceptance
```

and other cancellation races where the final state must remain valid.

---

# 27. Database Testing

Database integration tests should verify:

```text
Constraints
Transactions
Conditional Updates
Indexes
Unique Rules
Rollback
Isolation-Sensitive Behaviour
```

These properties cannot always be proven with repository mocks.

---

# 28. Transaction Rollback Tests

For operations involving multiple durable writes:

```text
Operation A
+
Operation B
```

force:

```text
Operation B → Failure
```

and verify:

```text
Operation A → Rolled Back
```

when atomicity is required.

---

# 29. Outbox Testing

The outbox pattern requires tests proving:

```text
Business State
+
Outbox Event
```

are persisted atomically where required.

Also test:

```text
Publisher Retry
Duplicate Publication
Consumer Redelivery
Failed Publication
```

according to the messaging semantics.

---

# 30. Redis Testing

Redis integration tests should verify behaviour that depends on Redis semantics.

Important examples:

```text
Atomic Lua Movement
TTL Refresh
Expired Keys
Pipeline Results
Reservation
Distributed Locking / Ownership
H3 Index Updates
```

Do not replace these tests entirely with mocks.

---

# 31. Redis Atomicity Test

For an atomic operation:

```text
Read
Modify
Write
```

test concurrent execution and verify that the final state satisfies the intended invariant.

The purpose is to prove atomicity, not merely that the script returns the expected value once.

---

# 32. Messaging Tests

Messaging integration tests should verify:

```text
Publish
Consume
Deserialize
Handle
Acknowledge
Retry
Dead-Letter
```

according to the current event architecture.

---

# 33. Consumer Failure Tests

A consumer should be tested when:

```text
Payload Invalid
Handler Fails
Database Unavailable
Dependency Times Out
Message Duplicated
```

The test should verify the expected acknowledgement/retry/DLQ behaviour.

---

# 34. Event Contract Tests

When event schemas are shared between producers and consumers, test:

```text
Required Fields
Field Types
Event Version
Envelope
Backward Compatibility
```

before changing event contracts.

---

# 35. Candidate Discovery Tests

Discovery tests should verify:

```text
Ring Expansion
Search Budget
Density Policy
Candidate Limits
Empty Cells
Multiple Cells
Geographic Refinement
```

without coupling tests to Redis command implementation when a component-level test is sufficient.

---

# 36. Ranking Tests

Ranking tests should verify:

```text
Feature Extraction
Normalization
Weight Application
ETA Preference
Quality Preference
Fairness Behaviour
Demand Influence
```

when those behaviours exist in the current implementation.

Do not hard-code implementation assumptions in tests that are not part of the configured contract.

---

# 37. Configuration-Aware Tests

Where behaviour is configuration-driven:

```text
Test Input
+
Configuration
→
Expected Result
```

Do not duplicate production configuration values as unexplained constants inside tests.

Test the actual configured policy or inject an intentionally defined test configuration.

---

# 38. Dispatch Workflow Tests

The dispatch workflow should verify:

```text
Ride
 ↓
Candidate Search
 ↓
Filtering
 ↓
Ranking
 ↓
Reservation
 ↓
Offer
```

including relevant failure branches.

---

# 39. No Candidate Tests

Test:

```text
No Candidates
```

as a valid application outcome where appropriate.

Verify that the system does not incorrectly classify an empty candidate set as an infrastructure failure.

---

# 40. Candidate Exhaustion

Test when:

```text
Candidates Exist
```

but all are rejected because of:

```text
Busy
Reserved
Blocked
Invalid
Unavailable
```

The expected dispatch outcome should be verified.

---

# 41. Failure Injection

Important distributed workflows should have failure-injection tests where practical.

Examples:

```text
Redis Failure
PostgreSQL Failure
Broker Failure
Reservation Conflict
External Routing Timeout
```

The goal is to verify controlled failure rather than ideal conditions only.

---

# 42. Recovery Tests

When a component has recovery behaviour, test:

```text
Failure
 ↓
Recovery
 ↓
Normal Operation
```

Examples:

```text
Redis Rebuild
Consumer Restart
Outbox Retry
Worker Restart
Connection Recovery
```

---

# 43. Restart Tests

Critical state should remain correct across process restarts.

Test where applicable:

```text
Pending Outbox
Active Reservation
Unprocessed Event
Driver Index Rebuild
Worker Shutdown
```

---

# 44. Stale State Tests

Distributed systems accumulate stale state.

Test:

```text
Expired Driver
Expired Reservation
Expired Offer
Stale Cache
Delayed Event
```

and verify cleanup or rejection behaviour.

---

# 45. Time-Based Testing

Time-dependent workflows should use controlled time where practical.

Important examples:

```text
Reservation TTL
Offer Timeout
Retry Backoff
Stale Driver Detection
```

Avoid tests that wait for real production-duration timeouts.

---

# 46. Property and Invariant Testing

Some behaviours are better expressed as invariants.

Examples:

```text
One Driver Cannot Have Two Active Exclusive Reservations
One Offer Cannot Produce Two Assignments
Expired Reservation Cannot Be Accepted
Candidate Score Remains Within Expected Bounds
```

Use property-style testing or repeated randomized tests where valuable.

---

# 47. Fuzz Testing

Fuzzing is useful for:

```text
Event Decoding
Input Validation
Geospatial Inputs
Configuration Parsing
Serialization
```

when there is a clear invariant or crash-safety expectation.

---

# 48. Performance Testing

Performance tests should answer measurable questions.

Examples:

```text
How many candidates can ranking process?
How does discovery latency scale with candidate count?
How many location updates can the service process?
How does Redis lookup latency behave?
```

Do not create benchmarks without a useful question.

---

# 49. Benchmark Tests

Use Go benchmarks for isolated performance-sensitive code.

Potential areas:

```text
Candidate Ranking
Feature Extraction
H3 Operations
Candidate Heap
Serialization
Filtering
```

Benchmark representative input sizes.

---

# 50. Load Testing

Load testing should represent realistic system traffic.

For RideForge, workloads may include:

```text
Ride Creation
Driver Location Updates
Candidate Discovery
Dispatch Attempts
Offer Responses
Event Consumption
```

The workload should be based on explicit assumptions rather than arbitrary request rates.

---

# 51. Performance Baselines

Important performance-sensitive components should maintain measurable baselines where practical.

Track:

```text
Latency
Throughput
CPU
Memory
Allocations
Redis Operations
Database Queries
```

A performance regression should be detectable.

---

# 52. Test Environment

Integration tests should use isolated infrastructure.

Potential services include:

```text
PostgreSQL
Redis
Kafka / Redpanda
```

The exact local/test infrastructure configuration is defined by the repository.

---

# 53. Test Database Isolation

Tests should avoid depending on developer-local production-like data.

Use:

```text
Dedicated Test Database
Transactions where safe
Fixture Cleanup
Unique Test Data
```

according to the test type.

---

# 54. Redis Test Isolation

Use isolated key namespaces or databases according to the project's Redis setup.

Tests must not accidentally delete or mutate unrelated developer data.

---

# 55. Messaging Test Isolation

Integration tests should use isolated:

```text
Topics
Consumer Groups
Test Identifiers
```

where required.

Avoid consuming unrelated developer messages.

---

# 56. Test Fixtures

Fixtures should be explicit and minimal.

Avoid enormous global fixtures that make individual tests difficult to understand.

Prefer helper constructors such as:

```text
NewTestDriver
NewTestRide
NewTestOffer
```

when they genuinely reduce repetition.

---

# 57. Test Builders

Test builders can simplify complex setup.

They should not hide the behaviour being tested.

A test should remain understandable from its setup.

---

# 58. Mocks

Mocks are appropriate when verifying interaction with a dependency is itself part of the contract.

Do not mock everything.

For infrastructure semantics, prefer real integration tests.

---

# 59. Fakes

Fakes are useful when a lightweight implementation can provide realistic behaviour.

Examples:

```text
In-Memory Repository
Fake Candidate Searcher
Fake Locker
Fake Event Publisher
```

Fakes should not silently behave differently from the production contract.

---

# 60. Testing Application Services

Application service tests should verify:

```text
Correct Dependency Coordination
Correct Ordering
Correct Error Propagation
Correct Transaction Intent
Correct Event Creation
Correct Retry Decision
```

They should not re-test implementation details of every dependency.

---

# 61. Testing Repositories

Repository unit tests should remain lightweight.

Repository integration tests should verify actual:

```text
SQL
Constraints
Transactions
Indexes
Database Behaviour
```

---

# 62. Testing Infrastructure Adapters

Infrastructure adapters should be tested against the technology they wrap when behaviour depends on provider semantics.

Examples:

```text
Redis Adapter → Redis
PostgreSQL Adapter → PostgreSQL
Kafka Adapter → Kafka / Redpanda
```

---

# 63. Testing External Providers

External provider adapters should have:

```text
Contract Tests
Failure Tests
Timeout Tests
Mapping Tests
```

and use mocks/fakes for provider calls where external integration is impractical.

---

# 64. Test Coverage

Coverage is a signal, not the definition of correctness.

High line coverage can still miss:

```text
Concurrency Bugs
State Races
Transaction Failures
Message Duplication
Infrastructure Semantics
```

Prioritize meaningful behaviour.

---

# 65. Coverage Priorities

Highest priority should generally be:

```text
Business-Critical State Transitions
Concurrency Boundaries
Persistence Transactions
Reservation
Assignment
Messaging Reliability
Dispatch Workflow
```

Lower priority:

```text
Trivial Getters
Generated Code
Simple Wiring
```

---

# 66. Mutation Thinking

When writing a test, ask:

> If this implementation were accidentally changed, would this test fail?

If not, the test may not be proving meaningful behaviour.

---

# 67. Regression Tests

Every confirmed production bug should result in a regression test when practical.

Preferred flow:

```text
Bug
 ↓
Reproduce
 ↓
Write Failing Test
 ↓
Fix
 ↓
Test Passes
```

This prevents the same class of bug from returning.

---

# 68. Test Before Refactoring

For significant refactors:

```text
Establish Behaviour Tests
      ↓
Refactor
      ↓
Run Tests
      ↓
Verify Behaviour Preserved
```

Do not refactor critical workflows without sufficient behavioural coverage.

---

# 69. Test Before Optimization

For performance changes:

```text
Correctness Tests
      ↓
Baseline Benchmark
      ↓
Optimization
      ↓
Correctness Tests
      ↓
Benchmark
      ↓
Compare
```

Do not accept a performance optimization that changes correctness.

---

# 70. Race Detector

Run the race detector for changes involving shared in-process state or concurrency.

Particularly:

```text
Caches
Workers
Maps
Channels
Reservation Logic
Realtime State
Background Processing
```

---

# 71. Deadlock Testing

Concurrency-sensitive tests should avoid relying on arbitrary timeouts alone.

Use:

```text
Context Cancellation
Bounded Test Timeout
WaitGroups
Explicit Synchronization
```

to identify deadlocks.

---

# 72. Test Timeouts

Tests should have bounded execution time.

A test that hangs indefinitely is an operational problem for CI.

Use appropriate test-level deadlines where necessary.

---

# 73. CI Testing

The CI pipeline should progressively verify:

```text
Formatting
Build
Unit Tests
Static Analysis
Integration Tests
Race / Specialized Tests
```

The exact CI commands should follow the repository configuration.

---

# 74. Fast Feedback

Developers should run the smallest relevant test set while iterating.

Example:

```text
Changed Ranking
    ↓
Run Ranking Tests
```

then broader verification:

```text
Package
 ↓
Application
 ↓
Integration
```

before submission.

---

# 75. Full Verification

Before merging a significant change, run the repository's full applicable verification suite.

Do not rely only on the narrow test for the changed file when shared contracts were modified.

---

# 76. Test Failure Investigation

When a test fails:

```text
Understand Failure
      ↓
Determine Root Cause
      ↓
Fix Code or Test
      ↓
Re-run
```

Do not weaken a test merely to make CI green.

---

# 77. Flaky Tests

A flaky test is a defect in the development system.

Do not simply rerun until it passes.

Investigate:

```text
Race
Timing
Shared State
External Dependency
Randomness
Cleanup
```

---

# 78. Test Documentation

Tests should be self-explanatory where possible.

Document unusual setup when the reason is not obvious.

Avoid comments that merely narrate every line.

---

For important workflows, maintain a mental or documented matrix:

| Scenario | Unit | Component | Integration | Concurrency | E2E |
|---|---:|---:|---:|---:|---:|
| Normal dispatch | ✓ | ✓ | ✓ |  | ✓ |
| No candidate | ✓ | ✓ |  |  | ✓ |

| Duplicate acceptance | ✓ | ✓ | ✓ | ✓ | ✓ |
| Offer timeout | ✓ | ✓ | ✓ | ✓ | ✓ |
| Redis failure |  | ✓ | ✓ |  |  |
| Database rollback |  |  | ✓ |  |  |
| Event redelivery | ✓ | ✓ | ✓ | ✓ |  |

---

# 80. Definition of Testable

A component is sufficiently testable when:

```text
Dependencies Are Explicit
Behaviour Has Clear Inputs/Outputs
External Effects Have Boundaries
Time Can Be Controlled Where Needed
Concurrency Has Observable Invariants
Failures Can Be Simulated
```

---

# 81. AI Agent Testing Rules

Before completing a coding task, an AI agent must:

1. Identify the behaviour being changed.
2. Identify the correct test level.
3. Inspect existing tests.
4. Reuse existing test helpers where appropriate.
5. Add regression coverage for changed behaviour.
6. Test important failure paths.
7. Test concurrency when the change is concurrency-sensitive.
8. Use integration tests for real infrastructure semantics.
9. Avoid arbitrary sleeps.
10. Run the relevant tests.
11. Run broader tests when shared contracts change.
12. Report exactly which tests were run.

---

# 82. AI Agent Forbidden Testing Patterns

AI agents must not:

- delete failing tests merely to make the suite pass,
- weaken assertions without justification,
- replace integration tests with mocks solely to simplify execution,
- use sleeps as synchronization,
- claim tests passed without running them,
- create tests that assert private implementation details unnecessarily,
- duplicate large fixture setups when existing helpers exist,
- ignore race-sensitive behaviour,
- skip regression tests for confirmed bugs,
- introduce flaky timing assumptions.

---

# 83. Testing Decision Tree

When changing code, ask:

```text
Is this pure logic?
    ↓
Unit Test

Is this a complete component?
    ↓
Component Test

Does correctness depend on PostgreSQL / Redis / Broker?
    ↓
Integration Test

Does correctness depend on concurrency?
    ↓
Concurrency Test

Does it cross independent contracts?
    ↓
Contract Test

Does it represent a critical user workflow?
    ↓
E2E Test

Is performance the question?
    ↓
Benchmark / Load Test
```

Multiple levels may be appropriate.

# 85. Release Confidence

Before releasing a significant change, confidence should come from multiple signals:

```text
Tests Pass
+
Static Checks Pass
+
No Known Regression
+
Concurrency Verified
+
Infrastructure Semantics Verified
+
Observability Available
+
Diff Reviewed
```

No single metric is sufficient.

---

# 86. Final Testing Principle

> **Test the behaviour that must remain correct, test real infrastructure where infrastructure semantics matter, and explicitly test concurrency and failure where distributed execution can violate correctness.**

RideForge testing should provide confidence not only that the happy path works, but that the system remains correct when:

```text
Drivers Compete
Messages Duplicate
Dependencies Fail
Timeouts Race
Processes Restart
State Becomes Stale
Traffic Increases
```

That is the standard required for a production-grade dispatch platform.

# PART 2 — PRACTICAL GO TESTING GUIDELINES & IMPLEMENTATION
# 1. Purpose

This document explains how developers and AI agents should actually write tests in RideForge.

`4.TESTING_STRATEGY.md` defines **what kinds of testing the system needs**.

This document defines **how those tests should be implemented**.

The objective is to make tests:

```text
Readable
Deterministic
Isolated
Fast
Meaningful
Concurrency-Safe
Architecture-Aware
Easy to Maintain
```

---

# 2. Core Testing Rule

A test should answer one clear question:

> **What behaviour must remain correct?**

A useful test should make it obvious:

```text
Given
When
Then
```

---

# 3. Test Naming

Use behaviour-oriented names.

Prefer:

```go
func TestRanker_PrefersLowerETA(t *testing.T)
```

```go
func TestReservation_RejectsAlreadyReservedDriver(t *testing.T)
```

```go
func TestConsumer_DoesNotDuplicateAssignment(t *testing.T)
```

Avoid:

```go
TestRanker1
TestBasic
TestFunction
TestSomething
```

---

# 4. Arrange — Act — Assert

The preferred test structure is:

```text
Arrange
   ↓
Act
   ↓
Assert
```

Example:

```go
// Arrange
driver := newTestDriver()
request := newTestRequest()

// Act
result, err := service.Execute(ctx, request)

// Assert
require.NoError(t, err)
assert.Equal(t, expected, result)
```

Keep the three phases visually clear.

---

# 5. One Behaviour Per Test

A test may have multiple assertions when they collectively verify one behaviour.

Avoid tests that verify many unrelated behaviours:

```text
Create Ride
Ranking
Reservation
Messaging
Cancellation
```

in one giant test.

Prefer focused tests.

---

# 6. Multiple Assertions

Multiple assertions are appropriate when they describe one expected outcome.

For example:

```text
Reservation succeeded
Reservation owner is correct
Reservation expiry is correct
```

These belong to one reservation behaviour.

---

# 7. Table-Driven Tests

Use table-driven tests when several inputs exercise the same rule.

Example structure:

```go
tests := []struct {
    name    string
    input   Input
    want    Output
    wantErr error
}{
    {
        name: "valid request",
    },
    {
        name: "invalid request",
    },
}
```

Each case should remain understandable without excessive abstraction.

---

# 8. Test Case Names

Case names should explain the scenario.

Prefer:

```text
"rejects invalid coordinates"
"returns no candidates when search is empty"
"rejects already reserved driver"
```

Avoid:

```text
"case1"
"case2"
"error"
```

---

# 9. Assertions

Use the project's existing assertion style.

Assertions should clearly communicate the failure.

Prefer assertions that identify:

```text
Expected
Actual
Relevant Context
```

Do not create complicated assertion helpers for trivial checks.

---

# 10. `require` vs `assert`

When a failed condition makes the rest of the test invalid:

```text
require
```

is appropriate.

For independent checks:

```text
assert
```

may be preferable.

The repository's existing testing library and conventions are authoritative.

---

# 11. Error Assertions

Prefer checking error semantics.

For categorized errors:

```go
require.ErrorIs(t, err, ErrConflict)
```

or the project's equivalent.

Avoid relying only on exact error strings when callers are not required to preserve the exact string.

---

# 12. Testing Success and Failure

For important behaviour, test both:

```text
Expected Success
Expected Failure
```

Examples:

```text
Reservation succeeds
Reservation conflicts

Offer accepted
Offer expired

Ride created
Invalid ride rejected
```

---

# 13. Boundary Cases

Always consider boundary inputs.

Examples:

```text
Zero
One
Maximum
Empty
Nil
Expired
Duplicate
Invalid
```

For numeric policies:

```text
Minimum
Below Minimum
Normal
Maximum
Above Maximum
```

where those boundaries exist.

---

# 14. Nil Inputs

Only test nil inputs when the API can legitimately receive them or when nil is a meaningful defensive boundary.

Do not add dozens of nil tests for impossible states that constructors already prevent.

---

# 15. Empty Collections

Important collection operations should explicitly test:

```text
Empty Input
One Item
Multiple Items
```

Examples:

```text
No Candidates
One Candidate
Many Candidates
```

---

# 16. Candidate Tests

Candidate-related tests should preserve the candidate pipeline's semantics.

Examples:

```text
Candidate Creation
Candidate Filtering
Candidate Iteration
Candidate Collection
Candidate Ranking
```

Avoid rebuilding candidate logic in test code.

---

# 17. Ranking Tests

Ranking tests should provide controlled features.

For example:

```text
Travel Features
Quality Features
Fairness Features
```

Then verify the resulting ranking behaviour.

Do not duplicate production scoring formulas inside tests merely to calculate expected values.

---

# 18. Configuration in Tests

When behaviour depends on configuration:

```text
Test Configuration
      ↓
Component
      ↓
Expected Behaviour
```

Use an explicit test configuration.

Avoid unexplained literals such as:

```go
0.45
0.25
15
40
```

when those values represent configurable production policy.

---

# 19. Testing Configuration Boundaries

Configuration tests should verify:

```text
Valid Configuration
Invalid Configuration
Default Behaviour
Boundary Values
```

when those behaviours exist.

Do not test every field merely for the sake of coverage.

---

# 20. Avoid Duplicating Production Configuration

Do not copy the entire production configuration into test code.

Instead define the minimum configuration required for the test.

This keeps tests focused and reduces maintenance.

---

# 21. Test Fixtures

Use small test fixtures.

Example:

```go
driver := newTestDriver()
```

should create only the fields required by the test.

Avoid giant fixtures with dozens of unrelated defaults.

---

# 22. Test Builders

A test builder is appropriate when constructing a complex object repeatedly.

Example:

```text
TestDriverBuilder
TestRideBuilder
TestOfferBuilder
```

Use builders to reduce setup noise.

Do not hide important test conditions inside builder defaults.

---

# 23. Explicit Test Conditions

A reader should be able to identify the important condition from the test itself.

If the test is about:

```text
Expired Reservation
```

the expiration should be visible.

Do not hide the key condition five helper functions deep.

---

# 24. Shared Test Helpers

Create shared helpers when setup is genuinely repetitive.

Good candidates:

```text
Database Setup
Redis Setup
Test Driver
Test Ride
Event Envelope
```

Avoid helpers for simple one-line setup.

---

# 25. Helper Naming

Test helpers should make their purpose obvious.

Prefer:

```text
newTestDriver
newTestRide
setupTestDatabase
seedDriver
```

Avoid:

```text
helper1
setup
doThing
```

---

# 26. Helper Assertions

A helper that performs assertions should clearly communicate that it does so.

Do not create helpers that unexpectedly fail the test when their name implies only object construction.

---

# 27. Test Cleanup

Every test must clean up resources it creates.

Examples:

```text
Database Rows
Redis Keys
Temporary Files
Goroutines
Timers
Connections
Containers
```

Use Go test cleanup facilities where appropriate.

---

# 28. `t.Cleanup`

Prefer:

```go
t.Cleanup(func() {
    // cleanup
})
```

for cleanup tied to the test lifecycle.

This makes cleanup reliable even when the test fails.

---

# 29. Temporary Files

Use testing utilities for temporary directories/files.

Do not create fixed paths such as:

```text
/tmp/test
```

that can collide between tests.

---

# 30. Database Test Isolation

Tests using PostgreSQL should have deliberate isolation.

Possible approaches include:

```text
Transaction Rollback
Dedicated Test Database
Unique Test Data
Schema Reset
```

Choose according to the test type and repository setup.

---

# 31. Transaction-Based Tests

A transaction wrapper can be useful for isolated repository tests when the code under test can participate in the same transaction.

Do not use transaction rollback as a universal solution when the behaviour being tested includes:

```text
Commit
Outbox Publication
Separate Connection
Asynchronous Worker
```

Those require appropriate integration testing.

---

# 32. Database Cleanup

If a test writes durable state outside a rollback boundary:

```text
Clean It Explicitly
```

Do not rely on test order.

---

# 33. Redis Test Isolation

Redis tests should use unique or isolated keys.

Avoid broad cleanup such as deleting an entire shared Redis namespace unless the test environment is guaranteed to be dedicated.

---

# 34. Redis Cleanup

Track created keys and remove them during test cleanup.

Prefer deterministic cleanup rather than deleting unrelated keys.

---

# 35. Redis TTL Tests

Do not wait for long production TTLs.

Use test configuration with a short duration.

Then verify:

```text
Key Exists
      ↓
TTL Active
      ↓
Expiration
      ↓
Key Removed
```

without slowing the suite unnecessarily.

---

# 36. Redis Atomicity Tests

For Lua or atomic Redis operations, test the invariant.

Example:

```text
Initial Driver → Cell A

Concurrent Movement
      ↓

Final Driver Membership
      ↓
Exactly One Correct Cell
```

The goal is not merely to verify the script's return value.

---

# 37. Redis Pipeline Tests

Pipeline tests should verify:

```text
All Expected Operations
Correct Results
Error Handling
Partial/Failure Semantics
```

where applicable.

---

# 38. Messaging Test Isolation

Use isolated test topics/streams and consumer groups when testing messaging.

Tests should not depend on messages generated by another test.

---

# 39. Event Test Data

Use explicit event fixtures.

A test event should clearly identify:

```text
Event Type
Event ID
Aggregate / Entity ID
Timestamp
Payload
Version
```

according to the current event contract.

---

# 40. Duplicate Event Tests

A duplicate event test should actually deliver the same logical event more than once.

Verify:

```text
First Delivery → Business Effect
Second Delivery → No Duplicate Business Effect
```

---

# 41. Consumer Failure Tests

Force the application handler to fail and verify the expected:

```text
Retry
Nack
DLQ
Acknowledgement
```

behaviour.

Do not merely verify that an error was returned.

---

# 42. Outbox Tests

Test the important outbox invariants:

```text
Business State + Outbox
```

should have the intended atomic relationship.

Also test:

```text
Unpublished Event
Retry
Successful Publication
Duplicate Publication
```

where applicable.

---

# 43. Application Service Tests

Application service tests should use focused dependency doubles.

For example:

```text
Fake Repository
Fake Searcher
Fake Locker
Fake Ranker
Fake Outbox
```

Verify orchestration rather than implementation details.

---

# 44. Dependency Call Verification

Verify interactions only when they matter to the behaviour.

Example:

```text
Reservation succeeds
    ↓
Offer must be created
```

This interaction is meaningful.

Do not assert every internal helper call.

---

# 45. Application Transaction Tests

If a service requires multiple operations to be atomic, test:

```text
Success
Failure During Intermediate Step
Rollback
```

The test should prove the state invariant, not merely that an error was returned.

---

# 46. Concurrency Tests

Use actual concurrent execution.

Example structure:

```go
var wg sync.WaitGroup

for ... {
    wg.Add(1)
    go func() {
        defer wg.Done()
        // operation
    }()
}

wg.Wait()
```

Then verify the final invariant.

---

# 47. Avoid Timing-Based Concurrency Tests

Avoid:

```go
go operation()

time.Sleep(100 * time.Millisecond)

assert(...)
```

This creates flaky tests.

Prefer explicit synchronization.

---

# 48. Barriers

When multiple goroutines must start at approximately the same logical point, use an explicit synchronization mechanism.

The test should control execution rather than hoping the scheduler creates the desired race.

---

# 49. Concurrent Reservation Test

A strong reservation test should:

```text
Create One Available Driver
      ↓
Start Multiple Reservation Attempts
      ↓
Wait for All Attempts
      ↓
Count Successful Reservations
      ↓
Assert Exactly One
```

---

# 50. Race Detector

Run:

```text
go test -race
```

or the repository's equivalent race-enabled command for concurrency-sensitive changes.

Do not assume passing normal tests proves race safety.

---

# 51. Deadlock Protection

Concurrency tests should have bounded execution.

If goroutines fail to finish, the test should fail rather than hang CI indefinitely.

Use test-level deadlines or controlled cancellation where appropriate.

---

# 52. Testing Time

Time-sensitive code should use a controllable time source where practical.

Avoid:

```go
time.Sleep(15 * time.Second)
```

to test a 15-second production timeout.

Use a test-specific timeout or controllable clock mechanism.

---

# 53. Testing Retry Logic

Retry tests should verify:

```text
Attempt Count
Backoff Policy
Stop Condition
Context Cancellation
Final Error / Success
```

Do not make retry tests wait through real production backoff durations.

---

# 54. Testing Randomness

If production logic uses randomness:

```text
Inject Controllable Source
```

when deterministic tests are required.

Test both:

```text
Normal Random Behaviour
Boundary / Controlled Behaviour
```

where appropriate.

---

# 55. Testing External APIs

External provider calls should normally be isolated behind an adapter.

Unit/component tests can use:

```text
Fake Provider
Stub HTTP Server
Mock Transport
```

Integration tests should be used when the real provider contract itself needs verification.

---

# 56. HTTP Stub Servers

When testing HTTP provider adapters, prefer a local test server over hard-coded external endpoints.

Verify:

```text
Request
Headers
Payload
Status
Response
Timeout
Malformed Response
```

as appropriate.

---

# 57. Provider Timeout Tests

A timeout test should simulate a real timeout condition.

Do not merely return a generic error if the production behaviour depends on:

```text
context deadline exceeded
```

or transport timeout semantics.

---

# 58. API Tests

API tests should verify:

```text
Request Validation
Authentication / Authorization where applicable
Application Service Invocation
Response Mapping
Error Mapping
```

They should not duplicate all application-service tests.

---

# 59. HTTP Status Mapping

If an application error maps to an HTTP response, test the mapping.

Examples:

```text
Not Found → 404
Conflict → 409
Validation → 400
Unavailable → appropriate failure response
```

Use the project's actual API contract.

---

# 60. Event Handler Tests

Event handlers should test:

```text
Valid Event
Invalid Event
Duplicate Event
Application Failure
Successful Processing
```

Keep transport decoding separate from application workflow tests where practical.

---

# 61. Discovery Tests

Discovery tests should cover the policies currently implemented.

Potential cases:

```text
Ring 0 Sufficient
Ring Expansion Required
Search Budget Exhausted
Sparse Density
Dense Density
Empty Cells
Candidate Limit
```

Do not test future policies that are not implemented yet.

---

# 62. Refinement Tests

For geographic refinement:

```text
Candidate Inside Threshold
Candidate Outside Threshold
Boundary Distance
Missing Location
Provider Failure
```

when supported by the current component.

---

# 63. Ranking Test Structure

A ranking test should make feature inputs explicit.

Example:

```text
Travel:
    ETA
    Distance

Quality:
    Acceptance
    Cancellation
    Rating
    Experience

Fairness:
    Idle Time
```

Then verify the expected ordering or score behaviour.

---

# 64. Quality Calculator Tests

When quality scoring is configuration-driven:

```text
Create Test Ranking Config
      ↓
Create Quality Features
      ↓
Calculate
      ↓
Verify Result
```

Do not hard-code production weights into the test formula.

The test should validate the configured behaviour.

---

# 65. Score Normalization Tests

If a feature is expected to be normalized:

```text
Minimum Input
→ Expected Lower Bound

Maximum Input
→ Expected Upper Bound
```

Test boundaries explicitly.

---

# 66. Candidate Pipeline Tests

Test pipeline stages independently where contracts permit:

```text
Filtering
Enrichment
Ranking
Iteration
```

Then add component-level tests for the composed pipeline.

---

# 67. Iterator Tests

For iterator-based components test:

```text
Empty Iterator
One Candidate
Multiple Candidates
Exhaustion
Repeated Next After Exhaustion
Error Propagation
```

according to the iterator contract.

---

# 68. Heap Tests

If the candidate heap is part of the dispatch hot path, test:

```text
Push
Pop
Ordering
Empty Heap
Duplicate Scores
Capacity Behaviour
```

and any tie-breaking rules that are part of the contract.

---

# 69. Reservation Tests

Reservation tests should cover:

```text
Reserve Available Driver
Reject Already Reserved
Release Reservation
Expired Reservation
Wrong Owner Cannot Release
Concurrent Reservation
```

where these behaviours exist.

---

# 70. Offer Tests

Offer lifecycle tests should cover:

```text
Create Offer
Accept
Reject
Expire
Invalid State
Duplicate Response
```

according to the implemented lifecycle.

---

# 71. Ride Lifecycle Tests

Ride lifecycle tests should cover valid transitions and invalid transitions.

Do not test every state combination if the state machine is already covered through focused transition tests.

---

# 72. Driver State Tests

Driver state changes should verify:

```text
Valid Transition
Invalid Transition
Availability
Reservation Interaction
Assignment Interaction
```

where relevant.

---

# 73. Location Tests

High-frequency location processing should test:

```text
Valid Update
Invalid Coordinates
Same Cell
Cell Movement
Stale Update
Infrastructure Failure
```

where supported by the current implementation.

---

# 74. Testing H3 Behaviour

H3 tests should distinguish:

```text
H3 Calculation Correctness
```

from:

```text
Redis Index Persistence
```

Use unit tests for deterministic H3 calculation and integration tests for Redis-backed index behaviour.

---

# 75. Testing Distance

Test distance calculations using known points.

Include:

```text
Same Point
Nearby Points
Different Points
Boundary Threshold
```

Avoid relying on approximate values without a defined tolerance.

---

# 76. Floating-Point Assertions

For floating-point calculations, use an appropriate tolerance when exact equality is not guaranteed.

Do not use arbitrary large tolerances that hide real errors.

---

# 77. Testing Precision-Sensitive Logic

If a business rule depends on a threshold:

```text
Below Threshold
Exactly At Threshold
Above Threshold
```

should be tested.

---

# 78. Integration Test Naming

Integration tests should make infrastructure dependence obvious when useful.

For example:

```text
TestRedisReservation_ConcurrentRequests
TestPostgresOutbox_RollsBackWithRide
TestConsumer_RedeliversFailedMessage
```

---

# 79. Build Tags

Use build tags only when they solve a real test-environment requirement.

Do not hide important tests behind tags that developers forget to run.

---

# 80. Test Execution Order

Tests must not depend on execution order.

Every test should establish its own required state.

---

# 81. Parallel Tests

Use `t.Parallel()` only after confirming:

```text
No Shared Mutable State
No Shared Database Conflicts
No Shared Redis Keys
No Shared Consumer Group
No Global Configuration Mutation
```

---

# 82. Environment Variables in Tests

Avoid mutating process-wide environment variables concurrently.

If environment mutation is necessary:

```text
Set
Run
Restore
```

and keep the test isolated.

---

# 83. Configuration Tests and Global State

Prefer passing configuration explicitly rather than changing global configuration between tests.

This is one reason RideForge components should use dependency injection.

---

# 84. Test Logging

Tests should remain reasonably quiet.

Only log additional diagnostic information when it helps investigate a failure.

Avoid printing every candidate or every message in normal test execution.

---

# 85. Test Data Privacy

Do not put real:

```text
Tokens
Credentials
Customer Data
Driver Personal Data
Production Identifiers
```

into fixtures.

Use synthetic values.

---

# 86. Regression Tests

Every important bug should produce a regression test.

Preferred sequence:

```text
Bug Reproduction
      ↓
Failing Test
      ↓
Fix
      ↓
Passing Test
```

The regression test should target the invariant that was broken.

---

# 87. Refactoring Tests

Tests should be refactored when they become:

```text
Duplicated
Opaque
Slow
Flaky
Over-Coupled
```

Do not leave bad test architecture merely because the tests technically pass.

---

# 88. Avoid Over-Mocking

Over-mocking can produce tests that prove only that mocks were called.

Use real component behaviour when practical.

For example:

```text
Application Service
    +
Fake Repository
    +
Fake Reservation
```

may be appropriate.

But:

```text
Entire Dispatch System
    +
Mock Everything
```

does not provide meaningful confidence.

---

# 89. Integration Test Boundary

Use integration tests when correctness depends on:

```text
Database Transactions
Redis Atomicity
Broker Semantics
TTL
Indexes
Constraints
Connection Behaviour
```

These cannot be fully replaced by mocks.

---

# 90. E2E Test Boundary

Use E2E tests for critical workflows.

Do not attempt to cover every branch through E2E tests.

They are slower and more operationally expensive.

---

# 91. Test Pyramid Discipline

Prefer:

```text
Many Unit Tests
      +
Focused Component Tests
      +
Important Integration Tests
      +
Small Critical E2E Suite
```

rather than:

```text
Huge E2E Suite
```

---

# 92. Performance Test Discipline

Performance tests should:

```text
Use Stable Inputs
Warm Up Where Appropriate
Measure Multiple Iterations
Avoid Unrelated External Noise
Record Relevant Metrics
```

Do not compare a single noisy run as a definitive performance result.

---

# 93. Load Test Discipline

Load tests should define:

```text
Workload
Concurrency
Duration
Success Criteria
Latency Target
Resource Target
```

before execution.

---

# 94. Performance Regression

When an optimization is merged, retain enough benchmark information to understand why the optimization exists.

Do not preserve arbitrary benchmark numbers as permanent guarantees unless they are formally defined targets.

---

# 95. CI Failure Handling

When CI fails:

```text
Read Full Failure
      ↓
Identify Root Cause
      ↓
Reproduce Locally
      ↓
Fix
      ↓
Re-run Relevant Tests
```

Do not simply rerun indefinitely.

---

# 96. Test Flakiness

A flaky test must be treated as a defect.

Investigate:

```text
Race
Timing
Shared State
External Dependency
Resource Leak
Randomness
Ordering
```

---

# 97. AI Agent Test Workflow

An AI agent implementing a change should follow:

```text
1. Read existing tests
2. Identify the behaviour changed
3. Identify test level
4. Reuse existing fixtures
5. Add focused tests
6. Add failure tests
7. Add concurrency tests if required
8. Run tests
9. Inspect failures
10. Run broader tests if contracts changed
11. Review test diff
```

---

# 98. AI Agent Test Restrictions

AI agents must not:

```text
Delete tests to make failures disappear
Weaken assertions without reason
Use sleeps as synchronization
Invent nonexistent test commands
Claim tests passed without execution
Mock infrastructure semantics that require real integration tests
Create huge fixtures unnecessarily
Test future behaviour as if already implemented
```

---

# 99. Test Review Checklist

Before merging tests:

```text
[ ] Test name describes behaviour
[ ] Arrange / Act / Assert is clear
[ ] Test is deterministic
[ ] Test has appropriate isolation
[ ] Failure path is covered where needed
[ ] Boundary cases are covered
[ ] No unnecessary sleeps
[ ] No unnecessary mocks
[ ] Infrastructure semantics use integration tests
[ ] Concurrency invariants are tested
[ ] Cleanup is reliable
[ ] Assertions are meaningful
[ ] Test does not depend on execution order
```

# 101. Definition of a Good Test

A good RideForge test is:

```text
Small enough to understand
Strong enough to catch a regression
Fast enough to run frequently
Deterministic enough for CI
Close enough to the real contract
```

---

# 102. Final Rule

> **Write tests around invariants and observable behaviour, not around implementation details. Use unit tests for logic, integration tests for infrastructure semantics, concurrency tests for races, and end-to-end tests for critical workflows.**

A test suite should make it safer to evolve RideForge, not become another system developers are afraid to touch.
