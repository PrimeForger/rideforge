# 1. Purpose

This document defines how PostgreSQL should be used and modified within RideForge.

The database is a critical part of the system's durable state and must be developed with explicit attention to:

```text
Correctness
Transactions
Concurrency
Query Performance
Connection Management
Schema Evolution
Consistency
Testing
Operational Safety
```

---

# 2. Database Role

PostgreSQL is a durable system of record for state that must survive:

```text
Process Restart
Service Restart
Redis Failure
Dispatch Node Failure
Message Redelivery
```

Do not treat PostgreSQL as merely a cache.

---

# 3. Source of Truth

Before modifying state, determine which component owns the authoritative state.

Conceptually:

```text
Durable Business State
        ↓
PostgreSQL

Ephemeral / Operational State
        ↓
Redis / Other Runtime Infrastructure
```

Do not introduce duplicate sources of truth without an explicit architectural reason.

---

# 4. Repository Boundary

Application and domain components should interact with PostgreSQL through the existing persistence abstractions.

Preferred:

```text
Application
    ↓
Repository / Persistence Contract
    ↓
PostgreSQL Implementation
```

Avoid:

```text
Application
    ↓
Raw SQL
```

unless the architecture explicitly defines that package as the persistence owner.

---

# 5. Repository Responsibilities

A repository should own:

```text
Persistence Queries
Persistence Mapping
Database Error Handling
Transaction Participation
Database-Specific Details
```

A repository should not own:

```text
Dispatch Policy
Ranking
Retry Policy
Offer Lifecycle
Transport Behaviour
```

---

# 6. Application Service Responsibilities

Application services should own use-case orchestration.

They may coordinate:

```text
Repository
Domain Rules
Reservation
Outbox
Other Application Components
```

but should not contain scattered SQL statements.

---

# 7. Database Models vs Domain Models

Do not automatically expose database representations as domain/application models.

Database models may contain:

```text
Nullable Columns
Database Metadata
Storage-Specific Types
Internal Keys
```

Application/domain models should represent the concepts required by the application.

Map between representations when the boundaries require it.

---

# 8. Query Design

Queries should retrieve only the data required by the operation.

Avoid:

```sql
SELECT *
```

when a narrower projection is sufficient.

Prefer explicit columns.

Benefits include:

```text
Reduced Data Transfer
Clearer Contracts
Lower Memory Usage
Safer Schema Evolution
```

---

# 9. Parameterized Queries

Always use parameterized queries.

Never construct SQL using string concatenation with external input.

Bad:

```text
"SELECT ... WHERE id = '" + id + "'"
```

Preferred:

```text
Parameterized Query
```

This is a security and correctness requirement.

---

# 10. Query Ownership

A query should live with the repository/component that owns the corresponding data.

Do not scatter queries across unrelated packages.

---

# 11. Query Naming

Repository methods should describe the business/persistence operation.

Prefer:

```text
FindDriver
FindAvailableDrivers
CreateReservation
UpdateRideState
ListPendingOutboxEvents
```

over:

```text
Query1
Execute
GetData
RunSQL
```

---

# 12. Read Methods

Read methods should clearly communicate whether they return:

```text
One Record
Many Records
Optional Record
Required Record
```

Their not-found behaviour should be consistent with the repository contract.

---

# 13. Not Found

Distinguish:

```text
Record Does Not Exist
```

from:

```text
Database Failure
```

For example:

```text
No Driver Found
```

is different from:

```text
PostgreSQL Connection Failed
```

The application layer may make different decisions based on that distinction.

---

# 14. Write Methods

Write methods should make their persistence semantics clear.

Examples:

```text
Create
Update
Delete
Reserve
Release
Transition
```

If a method performs a conditional write, the contract should make the condition meaningful.

---

# 15. Conditional Updates

For concurrency-sensitive state, prefer atomic database operations.

Instead of:

```text
SELECT state
↓
Check state in Go
↓
UPDATE
```

consider:

```text
UPDATE ... WHERE state = expected_state
```

when the state transition can be expressed safely that way.

---

# 16. Check-Then-Act

Avoid race-prone:

```text
Read
 ↓
Check
 ↓
Write
```

when another process can modify the same row between operations.

Use:

```text
Transaction
Conditional Update
Lock
Unique Constraint
```

as appropriate.

---

# 17. Database Transactions

Use a transaction when multiple database operations must succeed or fail together.

Example:

```text
Ride State Change
        +
Outbox Event
```

should be committed atomically when the event represents the durable state transition.

---

# 18. Transaction Ownership

The application/use-case layer should make the transaction boundary clear.

Repositories should participate in the transaction rather than secretly creating unrelated transactions inside every method.

---

# 19. Transaction Scope

Keep transactions:

```text
Short
Focused
Bounded
```

Do not hold a transaction while waiting for:

```text
Driver Response
Kafka
External HTTP
WebSocket
Long Retry
```

---

# 20. Transaction Flow

Preferred:

```text
Begin
  ↓
Read Required State
  ↓
Validate / Transition
  ↓
Write State
  ↓
Write Outbox
  ↓
Commit
```

External asynchronous work occurs after the durable commit.

---

# 21. Rollback

Every transactional operation must have a clear rollback path.

Do not leave transactions open after:

```text
Error
Context Cancellation
Panic
```

Use the project's established transaction helpers/patterns consistently.

---

# 22. Commit Failures

Treat commit failure as a real operation failure.

Do not return success merely because all individual statements succeeded before `Commit`.

---

# 23. Transaction Context

Database operations within a transaction must use the transaction-aware database handle/context according to the repository's persistence abstraction.

Do not accidentally execute one statement outside the transaction.

---

# 24. Outbox Transactions

The outbox pattern depends on atomicity.

Preferred:

```text
BEGIN
  ↓
Business State
  ↓
Outbox Event
  ↓
COMMIT
```

If either durable operation fails:

```text
ROLLBACK
```

---

# 25. Outbox Publishing

Do not require a successful broker publish before committing the business transaction when the architecture uses the outbox pattern.

Preferred:

```text
Database Commit
      ↓
Outbox Publisher
      ↓
Broker
```

---

# 26. Database Connection Pool

RideForge should use the application's shared database pool.

Do not create a new connection pool per request or per repository instance.

---

# 27. Pool Configuration

Connection pool settings should be configuration-driven.

Relevant settings may include:

```text
Maximum Connections
Minimum Connections
Connection Lifetime
Idle Timeout
Health Checks
```

Use the project's existing configuration model.

---

# 28. Connection Limits

Database connection count must remain bounded.

Consider:

```text
Application Instances
Pool Size Per Instance
PostgreSQL max_connections
PgBouncer if used
Background Workers
Migration Processes
```

Increasing the application pool without considering total database capacity can make the system less reliable.

---

# 29. Connection Exhaustion

When PostgreSQL reports connection exhaustion:

```text
Do Not Simply Increase Pool Size
```

First investigate:

```text
Pool Configuration
Long Queries
Long Transactions
Connection Leaks
Unbounded Concurrency
PgBouncer Configuration
Application Instance Count
```

---

# 30. Connection Lifetime

Use connection lifetime settings when appropriate to prevent unhealthy long-lived connections.

Follow the project's database configuration rather than adding per-query connection management.

---

# 31. Query Timeout

Database operations should respect the caller's context.

Long-running queries should have bounded execution according to application policy.

Do not allow a blocked database operation to hold application resources indefinitely.

---

# 32. Indexing

Indexes should support actual query patterns.

Before adding an index, identify:

```text
Query
WHERE Conditions
JOIN Conditions
ORDER BY
Expected Cardinality
Write Cost
```

Do not add indexes merely because a column exists.

---

# 33. Index Trade-Off

Indexes improve reads but add cost to:

```text
INSERT
UPDATE
DELETE
Storage
Vacuum
```

Every index should have a reason.

---

# 34. Composite Indexes

Composite indexes should reflect actual query patterns.

The order of columns matters.

Design them from real access patterns rather than arbitrary column ordering.

---

# 35. Partial Indexes

Partial indexes may be appropriate for highly selective operational states.

Example concept:

```text
Only Active / Available Rows
```

Use them when the query pattern and data distribution justify the complexity.

---

# 36. Unique Constraints

Use database constraints for invariants that must hold regardless of application behaviour.

Examples:

```text
Unique Identifier
Unique Event ID
Unique Reservation Ownership
```

The database should protect critical invariants that cannot safely rely only on application checks.

---

# 37. Foreign Keys

Use foreign keys when referential integrity is part of the durable data model.

Do not remove constraints merely to simplify application code.

If eventual consistency requires a different approach, document it.

---

# 38. Check Constraints

Use database-level checks when an invariant is simple, stable, and belongs naturally in the database.

Examples may include:

```text
Non-Negative Value
Valid State Representation
Required Relationship
```

Avoid duplicating complex application business rules into SQL constraints unless the rule is genuinely database-owned.

---

# 39. Nullability

Nullability should represent a meaningful domain/storage state.

Do not make every column nullable for convenience.

Prefer:

```text
NOT NULL
```

when a value is required.

---

# 40. Timestamps

Use consistent timestamp handling across the database.

Application code should follow the project's established timezone policy.

Avoid mixing:

```text
Local Time
UTC
Implicit Timezone
```

without an explicit contract.

---

# 41. IDs

Use the repository's established identifier strategy.

Do not introduce a new ID format for one table without a clear architectural reason.

---

# 42. State Columns

State fields should use a controlled representation.

Examples:

```text
Ride State
Offer State
Driver State
Reservation State
```

The application/domain layer should define valid transitions.

The database should provide supporting constraints where appropriate.

---

# 43. State Transitions

A state transition should be atomic where concurrency matters.

Prefer:

```text
UPDATE ... WHERE current_state = expected_state
```

or an appropriate transaction/locking strategy.

---

# 44. Optimistic Concurrency

Use optimistic concurrency when multiple writers may update the same record and conflict detection is sufficient.

Possible mechanisms include:

```text
Version Column
Updated-at Condition
Conditional Update
```

Use the approach already established by the component.

---

# 45. Pessimistic Locking

Use database locks when the operation genuinely requires serialized access to database state.

Do not add row locks by default.

Locks increase contention and can contribute to deadlocks.

---

# 46. Lock Ordering

If an operation acquires multiple locks, establish a consistent ordering.

Inconsistent lock order can create:

```text
Transaction A → Lock X → Wait Y
Transaction B → Lock Y → Wait X
```

and produce a deadlock.

---

# 47. Deadlocks

Database deadlocks are possible in concurrent systems.

When they occur:

```text
Identify Lock Order
Identify Query Order
Reduce Transaction Scope
Use Consistent Ordering
Retry Only When Safe
```

Do not blindly retry every database error.

---

# 48. Retryable Database Errors

Only retry errors known to be safe to retry.

Before retrying:

```text
Is the operation idempotent?
Was the transaction rolled back?
Can the operation be repeated safely?
```

---

# 49. N+1 Queries

Avoid patterns such as:

```text
Fetch 100 Candidates
      ↓
100 Individual DB Queries
```

Prefer:

```text
Batch Query
Join
IN Query
Bulk Fetch
```

when appropriate.

---

# 50. Batch Operations

Batch database operations when:

```text
Many Independent Records
Same Query Shape
Large Candidate Set
```

are processed together.

Do not create enormous batches that exceed practical memory or parameter limits.

---

# 51. Pagination

For large datasets, use an explicit pagination strategy.

Prefer cursor/keyset pagination when offset pagination becomes inefficient at scale.

The correct strategy depends on the query and access pattern.

---

# 52. Ordering

Do not assume database row order without an explicit `ORDER BY`.

If application behaviour depends on ordering:

```text
ORDER BY
```

must define it.

---

# 53. `LIMIT`

Use limits for bounded operational queries where unbounded results are unnecessary.

Examples:

```text
Pending Outbox
Candidate Support Queries
Administrative Listings
```

---

# 54. Query Plans

For slow queries, inspect the query plan.

Use tools such as:

```text
EXPLAIN
EXPLAIN ANALYZE
```

in controlled environments.

Do not optimize SQL based solely on intuition.

---

# 55. Slow Query Investigation

When a query is slow, inspect:

```text
Query Plan
Indexes
Row Estimates
Actual Rows
Join Strategy
Sorting
Filtering
Lock Waits
Connection Pool
```

---

# 56. Avoid `SELECT *`

Explicit projections make database contracts clearer and reduce unnecessary data transfer.

Use `SELECT *` only when there is a deliberate reason and the repository contract is stable.

---

# 57. Large Payloads

Do not retrieve large payloads when only a small subset is required.

Examples:

```text
Large JSON
Event Payload
Driver Metadata
Historical Data
```

Project only required fields.

---

# 58. Historical Data

Large historical tables should not automatically participate in hot operational queries.

Consider:

```text
Indexes
Partitioning
Retention
Archival
Separate Read Models
```

only when actual scale requires them.

---

# 59. PostgreSQL as Operational Store

Hot dispatch queries should remain predictable.

Avoid repeatedly querying large historical datasets during latency-sensitive dispatch operations.

Prefer dedicated operational representations when the architecture requires them.

---

# 60. Redis vs PostgreSQL

When deciding where data belongs, ask:

```text
Must it survive restart?
Must it be durable?
Is it authoritative?
Is it high-frequency ephemeral state?
Does it require relational consistency?
```

Use the existing architecture rather than duplicating data arbitrarily.

---

# 61. Cache Consistency

If PostgreSQL is authoritative and Redis is a derived cache/index:

```text
PostgreSQL
    ↓
Authoritative State

Redis
    ↓
Operational Projection
```

The application must define what happens when they diverge.

Do not silently treat stale Redis state as authoritative business truth.

---

# 62. Database + Redis Changes

When an operation changes both PostgreSQL and Redis, do not assume a normal database transaction can make Redis atomic with PostgreSQL.

Use the architecture's explicit consistency mechanism.

Potential patterns include:

```text
Database Commit
      ↓
Event / Outbox
      ↓
Redis Update

or

Application-Level Reconciliation
```

according to the component.

---

# 63. Reconciliation

When PostgreSQL and operational indexes can diverge, the system should have a documented reconciliation strategy.

Examples:

```text
Rebuild
Background Reconciliation
Repair Job
Startup Recovery
```

The appropriate strategy is defined by the architecture.

---

# 64. Schema Changes

Database schema changes must be backward-aware when rolling deployments are possible.

Prefer:

```text
Expand
   ↓
Deploy Compatible Code
   ↓
Migrate / Backfill
   ↓
Switch Usage
   ↓
Contract
```

for changes that cannot be performed atomically.

---

# 65. Destructive Migrations

Avoid destructive migrations in the same deployment that introduces incompatible application code.

Examples:

```text
Drop Column
Rename Required Column
Change Type Incompatibly
Remove Constraint Used by Old Code
```

Plan compatibility first.

---

# 66. Migration Review

Every schema migration should consider:

```text
Existing Rows
Existing Application Version
Indexes
Locks
Migration Duration
Rollback / Recovery
Production Traffic
```

---

# 67. Large Migrations

Large data migrations should avoid holding long blocking transactions where practical.

Consider:

```text
Batching
Backfill Jobs
Online Indexing Strategy
Operational Window
```

depending on the database change.

---

# 68. Migration Testing

Before applying a significant migration:

```text
Apply to Clean Database
Apply to Representative Existing Data
Run Application Tests
Check Query Plans
Verify Constraints
```

---

# 69. Seed Data

Seed data should be used only for intentionally required development/test data.

Do not insert realistic production secrets or sensitive data.

---

# 70. Database Testing

Database-related changes should use integration tests when correctness depends on PostgreSQL behaviour.

Important targets:

```text
Constraints
Transactions
Locks
Conditional Updates
Indexes
Migrations
Outbox
```

---

# 71. Repository Unit Tests

Repository unit tests may verify:

```text
Mapping
Input Construction
Error Mapping
```

but they cannot fully prove actual PostgreSQL semantics.

---

# 72. Repository Integration Tests

Repository integration tests should verify actual:

```text
SQL Execution
Rows
Transactions
Constraints
Not Found
Failures
```

against PostgreSQL.

---

# 73. Test Isolation

Database integration tests must not depend on another test's execution order.

Use:

```text
Unique Test Data
Transactional Isolation
Dedicated Test Database
Explicit Cleanup
```

as appropriate.

---

# 74. Database Error Mapping Tests

Test meaningful categories such as:

```text
Not Found
Unique Constraint Conflict
Foreign Key Conflict
Connection Failure
Timeout
Transaction Failure
```

where application behaviour depends on them.

---

# 75. Query Regression Tests

When fixing a slow or incorrect query, add a regression test where practical.

For performance issues, also capture a benchmark or query-plan expectation when it is stable enough to be useful.

---

# 76. Connection Pool Testing

Pool configuration should be validated operationally rather than through excessive unit tests.

Important checks include:

```text
Connection Limit
Timeout Behaviour
Pool Exhaustion
Recovery
```

when the system's risk profile warrants them.

---

# 77. Graceful Shutdown

Database pools must close during application shutdown according to the lifecycle architecture.

Do not terminate the process while active resources are still expected to flush or close.

---

# 78. Health Checks

Database health checks should distinguish:

```text
Application Is Running
```

from:

```text
Database Is Reachable
```

Use the project's readiness/liveness semantics.

---

# 79. Logging Database Failures

Database errors should contain enough context to diagnose:

```text
Operation
Entity / Safe Identifier
Failure Category
```

Do not log:

```text
Credentials
Connection Strings
Sensitive Payloads
```

---

# 80. Metrics

Useful database metrics include:

```text
Query Latency
Connection Pool Usage
Connection Wait Time
Transaction Duration
Error Rate
```

Use existing observability conventions.

Avoid creating high-cardinality metrics with raw SQL or entity IDs as labels.

---

# 81. Tracing

Database spans should make important persistence latency visible within application workflows.

Useful context includes:

```text
Operation
Repository
Latency
Error
```

Do not include sensitive SQL parameters in traces.

---

# 82. Performance Priorities

For RideForge, prioritize database performance for:

```text
Dispatch
Driver State
Reservation
Assignment
Outbox
Operational Queries
```

before optimizing low-frequency administrative operations.

---

# 83. Database Performance Checklist

When optimizing a query:

```text
[ ] Identify actual slow query
[ ] Measure baseline
[ ] Inspect EXPLAIN
[ ] Check indexes
[ ] Check row count
[ ] Check lock waits
[ ] Check connection pool
[ ] Reduce unnecessary columns
[ ] Avoid N+1
[ ] Re-measure
```

---

# 84. AI Agent Database Rules

Before changing database code, an AI agent must:

1. Identify the authoritative state.
2. Identify the owning repository/component.
3. Read the relevant architecture documentation.
4. Search existing queries and repository methods.
5. Reuse existing database abstractions.
6. Determine whether a transaction is required.
7. Consider concurrent writers.
8. Check indexes and query patterns.
9. Consider connection pool impact.
10. Add appropriate integration tests.
11. Consider migration compatibility if schema changes.
12. Run relevant tests.
13. Review the final SQL/code diff.

---

# 85. AI Agent Forbidden Patterns

AI agents must not:

- put raw SQL into unrelated application components,
- create a new database pool inside a request,
- concatenate external input into SQL,
- add indexes without understanding query usage,
- increase connection limits as the first response to pool exhaustion,
- hold database transactions during external network calls,
- assume `SELECT` followed by `UPDATE` is automatically concurrency-safe,
- silently ignore commit failures,
- treat Redis and PostgreSQL as atomically consistent without a defined mechanism,
- make destructive schema changes without compatibility analysis,
- use `SELECT *` by default in hot queries,
- introduce N+1 queries,
- claim migration/test verification without actually running it.

---

# 86. Database Change Checklist

Before merging a database change:

```text
[ ] State ownership identified
[ ] Repository boundary preserved
[ ] Query parameterized
[ ] Required columns explicitly selected
[ ] Not-found semantics defined
[ ] Error semantics defined
[ ] Transaction boundary reviewed
[ ] Concurrency considered
[ ] Index impact reviewed
[ ] Connection pool impact reviewed
[ ] Migration compatibility reviewed
[ ] Integration tests added/updated
[ ] Performance impact considered
[ ] Observability considered
[ ] Final diff reviewed
```

---

# 87. Final Database Principle

> **PostgreSQL must remain a deliberate durable-state boundary: use explicit repository contracts, short transactions, concurrency-safe state transitions, measured queries, bounded connection usage, and integration tests for real database semantics.**

The database should protect critical invariants while application/domain components remain responsible for the meaning of those invariants.
