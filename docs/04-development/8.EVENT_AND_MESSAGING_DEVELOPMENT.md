# 1. Purpose

RideForge uses event-driven communication for decoupling operational workflows and preparing the system for independent service evolution.

Messaging development must preserve:

```text
Reliable Event Publication
+
Predictable Consumption
+
Explicit Event Contracts
+
Idempotent Business Effects
+
Controlled Failure Handling
+
Observable Processing
```

Messaging is a system boundary. It must not become an uncontrolled transport for arbitrary application data.

---

# 2. Messaging Architecture

The development model is:

```text
Application
    ↓
Domain / Application Event
    ↓
Event Publication Boundary
    ↓
Kafka / Redpanda
    ↓
Consumer
    ↓
Application Handler
```

The broker transports events.

Business behaviour remains in application/domain components.

---

# 3. Broker

RideForge uses Kafka-compatible event streaming infrastructure.

The current implementation may use:

```text
Redpanda
```

while retaining Kafka-compatible interfaces and concepts.

Application code should depend on the project's messaging abstraction rather than spreading broker-specific implementation details through business logic.

---

# 4. Event vs Command

Events communicate that something happened:

```text
RideCreated
RideMatched
RideCancelled
DriverAssigned
```

Commands request an action:

```text
CreateRide
AssignDriver
CancelRide
```

Do not represent every internal method call as an event.

Use events when the system benefits from decoupled notification and processing.

---

# 5. Event Ownership

Every event should have a clear producer/owner.

The producer is responsible for publishing a valid event according to the event contract.

Consumers are responsible for interpreting the contract and applying their own business behaviour.

---

# 6. Event Naming

Event names should describe facts that have occurred.

Prefer:

```text
RideCreated
RideMatched
MatchFailed
DriverAssigned
```

over implementation-oriented names such as:

```text
ExecuteRideService
RunMatchingFunction
CallRepository
```

---

# 7. Event Contract

An event contract should define:

```text
Event Type
Event Version
Event ID
Aggregate / Entity Identifier
Timestamp
Producer
Payload
```

The exact envelope must follow the existing RideForge event model.

---

# 8. Event Envelope

RideForge uses an event-envelope approach so consumers can obtain common metadata without depending on every event payload structure.

Conceptually:

```text
Event Envelope
├── Event ID
├── Event Type
├── Version
├── Timestamp
├── Aggregate / Entity ID
└── Payload
```

Do not duplicate envelope metadata unnecessarily inside every payload.

---

# 9. Event ID

Every event should have a unique event identifier.

The event ID is useful for:

```text
Deduplication
Tracing
Debugging
DLQ Investigation
Audit Correlation
```

Do not generate a new logical event ID when retrying the same event.

---

# 10. Event Timestamp

Events should carry a timestamp representing the relevant event occurrence/publication semantics defined by the contract.

Consumers must not assume that event arrival time is always the same as event occurrence time.

---

# 11. Event Version

Events should be versioned when their schema or semantics may evolve.

Example:

```text
ride.created.v1
ride.created.v2
```

The exact naming strategy should remain consistent with the existing event contract.

---

# 12. Schema Evolution

Event contracts must evolve compatibly.

Before changing an event, determine:

```text
Current Producers
Current Consumers
Historical Messages
DLQ Messages
Replay Requirements
```

Do not change a shared event payload without checking existing consumers.

---

# 13. Backward Compatibility

Prefer changes that allow old and new consumers to coexist.

Generally safer changes include:

```text
Adding Optional Fields
```

rather than:

```text
Removing Required Fields
Changing Meaning
Changing Type
Renaming Existing Fields
```

---

# 14. Event Payloads

Event payloads should contain the information consumers genuinely need.

Avoid putting:

```text
Entire Database Rows
Secrets
Credentials
Large Internal Objects
Unrelated Data
```

into events.

---

# 15. Event Payload Stability

Do not expose internal implementation details as event contracts unless those details are intentionally part of the public/internal integration contract.

Events should represent stable business facts rather than temporary implementation structures.

---

# 16. Sensitive Data

Events may remain in broker retention and can also appear in:

```text
Consumer Logs
DLQ
Tracing
Replay Systems
Monitoring
```

Therefore sensitive data must be minimized.

Never put secrets into events.

---

# 17. Producer Boundary

Application code should publish through the established producer abstraction.

Conceptually:

```text
Application Service
    ↓
Event
    ↓
Producer
    ↓
Broker
```

Do not create broker clients directly inside business logic.

---

# 18. Producer Responsibilities

A producer is responsible for:

```text
Event Serialization
Event Metadata
Topic Selection
Partition Key
Publication
Error Propagation
```

It should not own unrelated business decisions.

---

# 19. Topic Selection

Topics should represent a meaningful event stream boundary.

Use the existing topic conventions.

The current architecture includes event streams such as:

```text
ride.events
match.events
```

and a dead-letter stream such as:

```text
ride.events.dlq
```

Do not create a new topic for every individual event unless the architecture requires it.

---

# 20. Topic Naming

Topic names should be:

```text
Stable
Predictable
Domain-Oriented
Documented
```

Avoid names based on temporary implementation details.

---

# 21. Partition Keys

Partition keys must be chosen according to ordering and distribution requirements.

For aggregate-specific ordering, a common strategy is:

```text
Aggregate ID
    ↓
Partition Key
```

This can preserve ordering for events belonging to the same aggregate while allowing different aggregates to process concurrently.

Do not choose a partition key without considering:

```text
Ordering
Load Distribution
Hot Partitions
Consumer Parallelism
```

---

# 22. Ordering

Kafka/Redpanda ordering is scoped rather than global.

Do not assume that all events across a topic are globally ordered.

If ordering matters for a ride:

```text
Ride ID
    ↓
Consistent Partition Key
    ↓
Ordered Processing for That Ride
```

The exact ordering scope must be documented by the event contract.

---

# 23. Ordering vs Concurrency

Ordering requirements constrain concurrency.

If events for one ride must remain ordered:

```text
Ride A → Event 1 → Event 2 → Event 3
```

must not be processed concurrently in a way that can apply:

```text
Event 3
before
Event 2
```

---

# 24. Independent Aggregates

Events belonging to different rides/drivers may often be processed concurrently when there is no shared business invariant.

For example:

```text
Ride A
+
Ride B
+
Ride C
```

can potentially be processed independently.

The consumer architecture must still respect partition and ordering guarantees.

---

# 25. Delivery Semantics

Distributed messaging should be designed around explicit delivery semantics.

The application should generally assume that an event may be delivered more than once.

Therefore:

```text
At-Least-Once Delivery
+
Idempotent Business Effect
```

is preferred over assuming exactly-once application execution.

---

# 26. Duplicate Events

Consumers must tolerate duplicate delivery where the business operation requires it.

Duplicate delivery can occur because of:

```text
Consumer Restart
Retry
Offset Handling
Network Failure
Crash After Processing
Before Acknowledgement
```

---

# 27. Idempotency

Idempotency means processing the same logical event more than once does not produce an incorrect repeated business effect.

Possible mechanisms include:

```text
Processed Event Record
Unique Constraint
Idempotency Key
Conditional State Transition
```

Use the mechanism appropriate to the operation.

---

# 28. Do Not Use Process-Local Idempotency

Do not implement distributed event idempotency using only:

```text
map[eventID]bool
```

or another process-local structure.

It disappears on restart and does not coordinate multiple instances.

---

# 29. Database Idempotency

When the business effect is persisted in PostgreSQL, database constraints or conditional operations can provide durable idempotency.

For example:

```text
Unique Event ID
```

can prevent duplicate application of the same logical event.

The exact strategy belongs to the consuming component.

---

# 30. State-Transition Idempotency

A state transition can also provide idempotency.

Conceptually:

```text
Expected State
    ↓
Conditional Transition
```

If the state has already moved forward, a repeated event can become a safe no-op.

---

# 31. Consumer Boundary

Consumers should separate:

```text
Message Transport
        ↓
Envelope Validation
        ↓
Deserialization
        ↓
Application Handler
        ↓
Business Effect
        ↓
Acknowledgement / Offset Progress
```

Do not put all business logic inside the broker consumer loop.

---

# 32. Consumer Responsibilities

A consumer should handle:

```text
Message Retrieval
Validation
Deserialization
Handler Invocation
Failure Classification
Retry / DLQ Decision
Acknowledgement / Offset Handling
```

It should delegate business behaviour to application components.

---

# 33. Message Validation

Consumers must validate:

```text
Event Type
Version
Required Metadata
Payload Structure
Required Identifiers
```

before applying the business effect.

Malformed events should not reach business logic as if they were valid.

---

# 34. Unknown Event Types

An unknown event type must have explicit behaviour.

Possible strategies include:

```text
Ignore Safely
Route to DLQ
Alert
Reject
```

The choice depends on the consumer's contract.

Do not silently interpret an unknown event as a known event.

---

# 35. Unknown Versions

Consumers should explicitly handle unsupported event versions.

Do not deserialize an incompatible version and hope the missing/changed fields will behave correctly.

---

# 36. Consumer Errors

Consumer failures should be classified.

Typical categories:

```text
Transient Infrastructure Failure
Permanent Invalid Message
Business Conflict
Dependency Failure
Programming Error
```

The retry/DLQ strategy should depend on the classification.

---

# 37. Retryable Errors

Retry when the error is likely temporary.

Examples:

```text
Temporary Database Failure
Temporary Redis Failure
Broker/Network Interruption
External Provider Timeout
```

Retries must remain bounded.

---

# 38. Non-Retryable Errors

Do not repeatedly retry an event that can never succeed.

Examples:

```text
Malformed Payload
Unsupported Schema
Missing Required Field
Invalid Event Type
```

Such events should normally move to the appropriate failure path.

---

# 39. Retry Policy

Retries should define:

```text
Maximum Attempts
Backoff
Jitter where appropriate
Timeout
Failure Classification
Final Destination
```

Never implement an infinite retry loop.

---

# 40. Retry and Duplicate Effects

A retry can execute business logic more than once.

Therefore:

```text
Retry
+
Idempotency
```

must be designed together.

A retry mechanism without idempotent handling can create duplicate business effects.

---

# 41. Dead Letter Queue

RideForge includes a DLQ path for events that cannot be processed successfully.

Conceptually:

```text
Event
 ↓
Consumer
 ↓
Retry
 ↓
Still Failing
 ↓
DLQ
```

The DLQ is a recovery mechanism, not a place to hide application bugs permanently.

---

# 42. DLQ Requirements

A DLQ record should retain enough information to investigate:

```text
Original Event
Event ID
Event Type
Failure Reason
Failure Context
Attempt Information
Timestamp
```

Avoid exposing secrets in the DLQ payload.

---

# 43. DLQ Replay

DLQ replay must be deliberate.

Before replaying:

```text
Identify Root Cause
 ↓
Fix Consumer / Dependency
 ↓
Verify Fix
 ↓
Replay
 ↓
Observe
```

Do not blindly replay a large DLQ.

---

# 44. DLQ Replay Idempotency

Replay must remain safe if the event was partially processed before entering the DLQ.

Consumers must preserve idempotent business behaviour.

---

# 45. Poison Messages

A poison message repeatedly fails because of the message itself or a deterministic incompatibility.

Do not allow a poison message to block healthy events indefinitely.

Use:

```text
Retry Limit
+
DLQ
```

according to the messaging policy.

---

# 46. Offset / Acknowledgement Semantics

A consumer should only advance/acknowledge processing according to the broker client's semantics after the required processing outcome is known.

Do not acknowledge a message before its required business effect is safely completed.

---

# 47. Crash Window

Consider:

```text
Business Effect Succeeds
        ↓
Process Crashes
        ↓
Message Not Acknowledged
        ↓
Message Delivered Again
```

This is a normal distributed-systems scenario.

The consumer must therefore be idempotent.

---

# 48. Outbox Pattern

When a business transaction must reliably produce an event, use the established outbox architecture.

Conceptually:

```text
Business State Change
        +
Outbox Record
        ↓
Same Database Transaction
        ↓
Outbox Publisher
        ↓
Kafka / Redpanda
```

This prevents the application from depending on an unsafe dual-write sequence.

---

# 49. Dual-Write Problem

Avoid:

```text
Commit Database
    ↓
Publish Event
```

as an assumed atomic operation.

The database and broker are separate systems.

A failure between the two operations can create:

```text
Database Updated
+
Event Missing
```

The outbox pattern exists to address this class of failure.

---

# 50. Outbox Publisher

The outbox publisher should:

```text
Read Pending Outbox
 ↓
Publish Event
 ↓
Record Successful Publication
```

according to the existing outbox implementation.

It must tolerate retries and restarts.

---

# 51. Outbox Idempotency

An outbox record may be published more than once if the publisher crashes after broker publication but before marking the outbox record complete.

Consumers must therefore remain idempotent.

---

# 52. Outbox Ordering

If event order matters, the outbox implementation must preserve the required ordering scope.

Do not assume database row order alone guarantees broker processing order.

Use the event's aggregate/partition strategy.

---

# 53. Event Publication Failure

If publication fails:

```text
Do Not Lose Event
```

when the event represents a required durable business fact.

The outbox should remain available for retry according to its retry policy.

---

# 54. Event Consumer and Database Transaction

If a consumer updates PostgreSQL and needs durable processing semantics, carefully define:

```text
Database Transaction
+
Event Deduplication
+
Offset / Acknowledgement
```

Do not assume the database transaction and broker offset are automatically atomic.

---

# 55. Transaction Boundary

Keep business transactions bounded.

Do not hold a PostgreSQL transaction open while waiting for:

```text
Broker
Redis
External API
```

unless the architecture explicitly requires it.

---

# 56. Eventual Consistency

Event-driven flows can introduce eventual consistency.

Developers must understand that:

```text
Event Published
```

does not necessarily mean:

```text
Every Consumer Has Already Processed It
```

Business APIs should communicate state accurately.

---

# 57. Read-After-Write Expectations

If a user expects an immediate result after a command:

```text
Command
 ↓
Authoritative State
```

should determine the immediate response where appropriate.

Do not make a synchronous API depend on an asynchronous consumer completing instantly unless the contract explicitly requires it.

---

# 58. Event Replay

Events may need replay for:

```text
Recovery
Rebuilding Derived State
Testing
Backfill
New Consumer
```

Event schemas should therefore remain sufficiently stable and documented for their intended retention period.

---

# 59. Replay Safety

Replay should not accidentally:

```text
Send Duplicate Notification
Create Duplicate Assignment
Charge Twice
Repeat Irreversible Action
```

Consumers must distinguish between:

```text
Rebuildable Projection
```

and:

```text
Irreversible Side Effect
```

before supporting replay.

---

# 60. Event Retention

Retention should match the intended use of the event stream.

Consider:

```text
Recovery
Replay
Debugging
Storage Cost
Privacy
```

Do not retain sensitive data indefinitely without a requirement.

---

# 61. Topic Ownership

Every production topic should have a documented owner.

Document:

```text
Purpose
Producer
Consumers
Partition Key
Ordering
Retention
DLQ
Schema
```

---

# 62. Consumer Group Ownership

Consumer groups should have clear ownership and purpose.

Do not create arbitrary consumer groups merely to read the same event stream for debugging.

---

# 63. Consumer Scaling

Consumer concurrency must respect:

```text
Partition Count
Ordering
Database Capacity
Redis Capacity
External Provider Capacity
```

More workers do not automatically produce more throughput.

---

# 64. Consumer Backpressure

If processing is slower than event arrival:

```text
Lag Increases
```

Do not solve the problem by creating unlimited goroutines.

Identify the actual bottleneck and apply bounded concurrency.

---

# 65. Consumer Shutdown

Consumers must support graceful shutdown:

```text
Stop Fetching New Work
 ↓
Finish / Cancel In-Flight Work
 ↓
Commit / Acknowledge Safely
 ↓
Close Consumer
```

The exact sequence depends on the broker client.

---

# 66. Producer Shutdown

Producers should flush or close according to the messaging client's guarantees.

Do not exit while required buffered events are at risk of being lost.

---

# 67. Broker Failure

The application must define behaviour when Kafka/Redpanda is unavailable.

Possible strategies:

```text
Retry
Buffer Through Outbox
Fail Operation
Degrade
```

The correct behaviour depends on whether the event is required for business correctness.

---

# 68. Eventual Recovery

After broker recovery:

```text
Pending Outbox / Retry
        ↓
Publication Resumes
        ↓
Consumer Processing Resumes
        ↓
Lag Returns to Normal
```

Recovery should be observable.

---

# 69. Event Observability

Messaging components should expose meaningful telemetry:

```text
Produced Events
Consumed Events
Processing Latency
Consumer Lag
Retry Count
DLQ Count
Publication Failures
Deserialization Failures
```

Follow:

```text
9.OBSERVABILITY_DEVELOPMENT.md
```

for detailed observability practices.

---

# 70. Event Correlation

Events should carry or propagate correlation/trace context where supported.

This allows:

```text
API Request
 ↓
Application
 ↓
Event
 ↓
Consumer
 ↓
Application Effect
```

to be investigated as one distributed workflow.

---

# 71. Logging Events

Do not log complete event payloads by default.

Prefer:

```text
Event ID
Event Type
Aggregate ID where safe
Outcome
Failure Category
Trace ID
```

This reduces sensitive-data exposure and log volume.

---

# 72. Event Metrics Cardinality

Do not create high-cardinality metrics using:

```text
Event ID
Ride ID
Driver ID
```

as metric labels.

Use identifiers in logs/traces instead.

---

# 73. Event Testing

Messaging functionality requires more than unit tests.

Use:

```text
Unit Tests
Integration Tests
Contract Tests where appropriate
Failure Tests
Concurrency Tests
```

according to the component.

---

# 74. Producer Unit Tests

Producer tests should verify:

```text
Correct Event Type
Correct Version
Correct Metadata
Correct Topic
Correct Partition Key
Correct Serialization
Error Propagation
```

---

# 75. Consumer Unit Tests

Consumer tests should verify:

```text
Valid Event
Invalid Event
Unknown Type
Unsupported Version
Business Handler Success
Retryable Failure
Permanent Failure
DLQ Decision
```

---

# 76. Integration Tests

Use a real Kafka-compatible broker for tests where correctness depends on:

```text
Serialization
Partitioning
Ordering
Consumer Groups
Offset Behaviour
Retry
DLQ
```

Mocks cannot fully prove broker semantics.

---

# 77. Event Contract Tests

Where multiple components depend on the same event contract, tests should verify that producers and consumers agree on:

```text
Envelope
Event Type
Version
Required Fields
Field Types
```

---

# 78. Ordering Tests

Where ordering matters, test:

```text
Event 1
Event 2
Event 3
```

for the same ordering key and verify that the consumer applies them in the expected order.

Also test independent keys to ensure concurrency remains possible.

---

# 79. Duplicate Event Tests

A consumer should be tested with:

```text
Event A
Event A Again
```

and the expected business state should remain correct.

---

# 80. Retry Tests

Verify:

```text
Transient Failure
 ↓
Retry
 ↓
Success
```

and:

```text
Permanent Failure
 ↓
Retry Limit
 ↓
DLQ
```

according to the configured policy.

---

# 81. DLQ Tests

Test that:

```text
Poison Event
 ↓
Expected Attempts
 ↓
DLQ
```

and verify the DLQ retains enough diagnostic information.

---

# 82. Outbox Integration Tests

Test:

```text
Business Transaction
+
Outbox Record
```

together.

Important scenarios include:

```text
Transaction Success
Transaction Failure
Publisher Retry
Publisher Crash Window
Duplicate Publication
```

---

# 83. Concurrency Tests

Messaging concurrency tests should cover:

```text
Concurrent Consumers
Duplicate Delivery
Concurrent Event Handling
Shared Aggregate Updates
```

where applicable.

Run the race detector for relevant Go components.

---

# 84. Performance Testing

Measure messaging performance when required:

```text
Producer Throughput
Consumer Throughput
Processing Latency
Batching Impact
Concurrency Impact
Broker Lag
```

Do not optimize batching or worker counts without measurements.

---

# 85. Event Security

Messaging must follow the security rules defined in the security development documentation.

In particular:

```text
No Secrets in Events
No Unnecessary Sensitive Data
Controlled Broker Access
Validated Payloads
Controlled Replay
```

# 86. Event Contract Change Process

Before changing an event:

```text
Identify Producer
Identify Consumers
Inspect Existing Messages
Review Version Compatibility
Update Contract Documentation
Update Tests
Implement Compatible Change
Deploy Safely
```

---

# 87. Breaking Event Changes

If a breaking change is unavoidable:

```text
Create New Version
 ↓
Update Consumers
 ↓
Deploy Compatible Consumers
 ↓
Switch Producer
 ↓
Retire Old Version
```

Do not silently mutate a contract used by existing consumers.

---

# 88. AI Agent Messaging Rules

Before implementing messaging-related code, an AI agent must:

1. Read the event/messaging architecture documentation.
2. Identify the producer and consumer.
3. Identify the event contract.
4. Identify topic and partitioning requirements.
5. Identify ordering requirements.
6. Identify delivery semantics.
7. Identify idempotency requirements.
8. Identify retry behaviour.
9. Identify DLQ behaviour.
10. Identify outbox requirements.
11. Inspect existing producer/consumer abstractions.
12. Reuse existing event envelope conventions.
13. Add/update appropriate tests.
14. Review observability.
15. Review sensitive-data exposure.
16. Run relevant validation.
17. Review the final diff for contract and compatibility problems.

---

# 89. AI Agent Forbidden Messaging Patterns

AI agents must not:

- create arbitrary topics without architectural justification,
- publish directly from domain logic using a raw broker client,
- assume exactly-once execution,
- assume global event ordering,
- ignore partition-key requirements,
- acknowledge messages before required processing is complete,
- implement distributed idempotency with process-local memory,
- retry indefinitely,
- send poison messages through infinite retry loops,
- bypass the DLQ policy,
- put secrets into event payloads,
- log complete sensitive event payloads,
- change event schemas without checking consumers,
- create a dual-write database/broker flow where an outbox is required,
- claim event delivery/order/retry behaviour is verified without integration testing.

# 91. Final Messaging Principle

> **Treat events as durable contracts, assume delivery can repeat, make business effects idempotent, preserve ordering only where required, and keep broker mechanics separate from business logic.**

The RideForge messaging flow should remain:

```text
Business State Change
        ↓
Outbox / Event Boundary
        ↓
Kafka / Redpanda
        ↓
Consumer
        ↓
Validation
        ↓
Application Handler
        ↓
Idempotent Business Effect
        ↓
Observable Result
```

The broker provides asynchronous communication and decoupling.

It must not become a substitute for:

```text
Business Logic
Database Transactions
Authorization
State Ownership
```

Messaging should make RideForge more resilient and scalable while keeping correctness explicit.
