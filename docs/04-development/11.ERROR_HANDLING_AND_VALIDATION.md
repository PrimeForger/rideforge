# 1. Purpose

Error handling in RideForge must preserve:

```text
Correctness
+
Clear Failure Semantics
+
Safe Recovery
+
Useful Diagnostics
+
Stable API Contracts
+
Controlled Retries
```

Errors are part of the system's behaviour and must be designed as deliberately as successful outcomes.

---

# 2. Error Handling Principle

An error should answer:

```text
What failed?
Why did it fail?
Can it be retried?
Who should handle it?
What should the caller see?
What should be logged?
```

Do not treat all failures as generic internal errors.

---

# 3. Error Layers

Errors should be understood according to their layer:

```text
Transport
    ↓
Application
    ↓
Domain
    ↓
Infrastructure
```

Each layer should translate errors only when the translation adds meaningful semantics.

---

# 4. Domain Errors

Domain errors represent invalid business state or business rules.

Examples:

```text
Ride Not Allowed
Invalid Ride State
Driver Not Eligible
Invalid State Transition
Region Restriction
```

Domain errors should not depend on HTTP, Redis, PostgreSQL, or Kafka types.

---

# 5. Application Errors

Application errors represent failures at the use-case boundary.

Examples:

```text
Ride Creation Failed
Driver Reservation Conflict
Matching Failed
Dependency Unavailable
Operation Not Permitted
```

They may wrap lower-level errors while preserving the semantic meaning needed by callers.

---

# 6. Infrastructure Errors

Infrastructure errors originate from dependencies such as:

```text
PostgreSQL
Redis
Kafka / Redpanda
External APIs
Network
Filesystem
```

Infrastructure errors should not automatically become public API messages.

---

# 7. Transport Errors

The HTTP/API layer maps application outcomes to transport semantics.

Conceptually:

```text
Application Error
    ↓
HTTP Status
+
Stable API Error Code
+
Safe Message
```

Do not expose raw infrastructure errors to API clients.

---

# 8. Validation Categories

Validation should be separated into:

```text
Transport Validation
Application Validation
Domain Validation
Infrastructure Validation
```

Each belongs at the appropriate boundary.

---

# 9. Transport Validation

Transport validation checks whether the request can be understood.

Examples:

```text
Missing Required Field
Malformed UUID
Invalid JSON
Invalid Query Parameter
Invalid Enum
Invalid Format
```

These failures should normally be rejected before entering the business workflow.

---

# 10. Application Validation

Application validation checks whether the requested use case can execute.

Examples:

```text
Required Resource Missing
Invalid Operation Combination
Unsupported Workflow
Missing Required Dependency
```

---

# 11. Domain Validation

Domain validation enforces business invariants.

Examples:

```text
Ride Cannot Be Assigned Twice
Cross-Region Ride Not Allowed
Driver Cannot Accept Ineligible Ride
Cancelled Ride Cannot Be Matched
```

These rules must remain independent of transport concerns.

---

# 12. Infrastructure Validation

Infrastructure configuration and dependency assumptions should be validated at their respective boundaries.

Examples:

```text
Invalid Database Configuration
Missing Redis Configuration
Unsupported Broker Configuration
Invalid External Provider URL
```

Configuration failures should generally be detected during startup rather than during normal request processing.

---

# 13. Validate at the Boundary

Validate data as early as possible without duplicating business logic.

Preferred:

```text
HTTP
 ↓
Transport Validation
 ↓
Application
 ↓
Domain Validation
```

Do not rely on the database to produce every validation error.

---

# 14. Do Not Over-Validate in Every Layer

Validation should not become duplicated logic across:

```text
Handler
Service
Domain
Repository
```

Each layer should validate what it owns.

---

# 15. Trust Boundaries

Treat these as untrusted inputs:

```text
HTTP Requests
External APIs
Broker Messages
Redis Data
Database Data from Legacy/Unknown Sources
Configuration
```

Validation requirements should reflect the trust boundary.

---

# 16. Error Identity

Errors that callers need to reason about should have stable identity.

Examples:

```text
ErrNotFound
ErrUnauthorized
ErrForbidden
ErrConflict
ErrInvalidState
ErrValidation
```

Use the project's established error conventions.

---

# 17. Sentinel Errors

Sentinel errors can be useful when callers need to classify a known condition.

Example:

```go
var ErrNotFound = errors.New("not found")
```

Use them deliberately.

Do not create dozens of meaningless sentinel errors for every line of code.

---

# 18. Typed Errors

Typed errors are appropriate when callers need structured information.

Examples:

```text
Validation Field
Conflict Resource
Retry Classification
Domain State
```

Keep error structures focused.

---

# 19. Error Wrapping

When adding context, preserve the underlying error where callers may need to classify it.

Use Go error wrapping consistently.

Conceptually:

```text
Repository Error
    ↓
Wrap with Context
    ↓
Application Error Handling
```

Do not destroy error identity by converting every error to a plain string.

---

# 20. Error Context

Useful error context may include:

```text
Operation
Resource Type
Safe Identifier
Dependency
Failure Category
```

Do not include secrets or sensitive payloads.

---

# 21. Error Messages

Error messages should be:

```text
Clear
Concise
Actionable where appropriate
Safe
```

Avoid:

```text
Something went wrong
```

when a more useful classification is available.

---

# 22. Error Codes

Public APIs should expose stable machine-readable error codes.

Examples:

```text
RIDE_NOT_FOUND
RIDE_INVALID_STATE
DRIVER_UNAVAILABLE
DRIVER_NOT_ELIGIBLE
REGION_NOT_ALLOWED
RESERVATION_CONFLICT
```

Error codes should remain stable even if internal implementation changes.

---

# 23. Error Code Naming

Use a consistent naming convention.

Prefer:

```text
RESOURCE_REASON
```

where appropriate.

Avoid exposing implementation details:

```text
POSTGRES_UNIQUE_VIOLATION_23505
REDIS_COMMAND_FAILED
KAFKA_TIMEOUT
```

unless those are intentionally internal diagnostic classifications.

---

# 24. HTTP Error Mapping

Application errors should be mapped consistently.

Typical mapping:

```text
Validation
→ 400 / 422

Unauthenticated
→ 401

Forbidden
→ 403

Not Found
→ 404

Conflict
→ 409

Rate Limited
→ 429

Unexpected Internal Failure
→ 500

Dependency Failure
→ 502 / 503 / 504
```

The exact mapping should follow the established API contract.

---

# 25. Do Not Leak Infrastructure Errors

Never return raw errors such as:

```text
pq: duplicate key value violates unique constraint ...
dial tcp ...
redis: connection refused
```

to external clients.

Map them to safe application/API semantics.

---

# 26. Not Found

A not-found condition should be distinguishable from an infrastructure failure.

For example:

```text
Driver Does Not Exist
```

is not the same as:

```text
PostgreSQL Unavailable
```

The API and application layers must preserve this distinction.

---

# 27. Unauthorized vs Forbidden

Use:

```text
401
```

when the caller has not been successfully authenticated.

Use:

```text
403
```

when the caller is authenticated but lacks permission.

Follow the project's authentication architecture where information-hiding requirements alter this behaviour.

---

# 28. Conflict

Use a conflict outcome when a request is valid but current state prevents the requested transition.

Examples:

```text
Driver Already Reserved
Ride Already Assigned
Ride Already Cancelled
Idempotency Conflict
```

---

# 29. Validation Errors

Validation errors should identify the invalid field or input when doing so is safe and useful.

A structured response may conceptually contain:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "fields": {
      "pickup": "is required"
    }
  }
}
```

The exact response contract belongs to the API documentation.

---

# 30. Multiple Validation Errors

Where useful, return multiple independent validation failures in one response.

Do not expose validation details that could reveal sensitive information.

---

# 31. Error Aggregation

Do not aggregate unrelated failures merely to avoid returning an error.

For example, a failed required dependency should not be hidden because another optional operation succeeded.

---

# 32. Partial Success

If an operation can legitimately produce partial results, the application contract should explicitly define:

```text
Successful Work
Failed Work
Retryable Work
```

Do not accidentally turn partial failure into false success.

---

# 33. Dispatch Errors

Dispatch-related errors should preserve business meaning.

Examples:

```text
No Eligible Candidate
No Candidate Found
Reservation Conflict
Discovery Failure
Ranking Failure
Region Restriction
```

Do not collapse all of these into:

```text
MATCHING_FAILED
```

when the caller or system needs to distinguish them.

---

# 34. No Candidate vs Discovery Failure

These are fundamentally different:

```text
No Candidate
```

means the system successfully searched and found nobody eligible.

```text
Discovery Failure
```

means the search operation could not be completed reliably.

The application must preserve this distinction.

---

# 35. Reservation Errors

Reservation is a concurrency boundary.

A failed reservation should indicate whether:

```text
Driver Already Reserved
Driver No Longer Eligible
State Conflict
Infrastructure Failure
```

according to the actual outcome.

---

# 36. State Transition Errors

Invalid transitions should be explicit.

For example:

```text
Cancelled
    ↓
Assign Driver
```

should produce a domain/application error rather than an unexpected database error.

---

# 37. Database Constraint Errors

Database constraints are valuable correctness boundaries.

When a constraint is intentionally part of the business invariant:

```text
Database Error
    ↓
Recognize Constraint
    ↓
Map to Application Conflict
```

Do not expose raw constraint details.

---

# 38. Transaction Errors

If a database transaction fails:

```text
Rollback
 ↓
Classify Error
 ↓
Return / Retry Appropriate Outcome
```

Do not continue using application state that assumes the transaction succeeded.

---

# 39. Transaction Commit Failure

A failed commit is a serious operation outcome.

Do not assume that because individual statements succeeded, the business operation succeeded.

Treat commit failure according to the database driver's semantics and application contract.

---

# 40. Redis Errors

Redis failures must distinguish:

```text
Missing Key
```

from:

```text
Redis Unavailable
```

and:

```text
Timeout
```

A missing candidate cell may be normal.

A Redis outage may be a system failure.

---

# 41. Messaging Errors

Messaging failures should be classified into:

```text
Publication Failure
Deserialization Failure
Validation Failure
Retryable Handler Failure
Permanent Handler Failure
DLQ Failure
```

Follow the messaging development document for detailed behaviour.

---

# 42. External Provider Errors

External provider errors should be translated into controlled application outcomes.

Examples:

```text
Timeout
Rate Limit
Authentication Failure
Invalid Request
Provider Unavailable
```

Do not expose provider-specific internal details to clients unless the API contract intentionally does so.

---

# 43. Retry Classification

Every retryable operation should have an explicit classification.

Conceptually:

```text
Error
 ↓
Retryable?
 ├─ Yes → Bounded Retry
 └─ No  → Final Failure
```

Do not infer retryability merely because an operation failed.

---

# 44. Retryable Errors

Typical retryable failures include:

```text
Transient Network Failure
Temporary Database Failure
Temporary Redis Failure
Broker Unavailability
External Timeout
```

Only retry when repeating the operation is safe.

---

# 45. Non-Retryable Errors

Typical non-retryable failures include:

```text
Malformed Request
Invalid Event
Unsupported Version
Invalid Business State
Authorization Failure
Invalid Configuration
```

Do not waste resources retrying deterministic failures.

---

# 46. Retry Limits

Retries must be bounded.

Define:

```text
Maximum Attempts
Backoff
Timeout
Final Failure Path
```

Never create infinite retry loops.

---

# 47. Exponential Backoff

For transient dependency failures, exponential backoff can reduce load amplification.

Where appropriate:

```text
Attempt 1
 ↓
Short Delay

Attempt 2
 ↓
Longer Delay

Attempt 3
 ↓
Longer Delay
```

Add jitter when coordinated retries could otherwise create a thundering herd.

---

# 48. Retry and Idempotency

Retries and idempotency are coupled.

Before retrying:

```text
Can this operation safely execute again?
```

If not, use an appropriate idempotent/concurrency mechanism first.

---

# 49. API Retry Behaviour

Do not automatically retry every failed API request internally.

A retry can create duplicate side effects.

For state-changing operations, use explicit idempotency semantics where retries are expected.

---

# 50. Event Retry Behaviour

Event consumers should follow:

```text
Retryable Failure
    ↓
Bounded Retry
    ↓
DLQ if Still Failing
```

according to the messaging contract.

---

# 51. Error Propagation

Errors should propagate with enough context to diagnose the failure while preserving classification.

Conceptually:

```text
Infrastructure
    ↓
Repository
    ↓
Application
    ↓
Transport
```

Each layer may add context.

---

# 52. Error Translation

Translate an error when crossing an architectural boundary.

For example:

```text
sql.ErrNoRows
    ↓
Repository Not Found
```

and later:

```text
Application Not Found
    ↓
HTTP 404
```

Do not expose SQL-specific details throughout the application.

---

# 53. Preserve Cause

When an error's underlying cause is useful for:

```text
Classification
Logging
Debugging
Recovery
```

preserve it through Go's error wrapping mechanisms.

---

# 54. Avoid String Matching

Do not classify errors by parsing error strings such as:

```text
if strings.Contains(err.Error(), "timeout")
```

Prefer:

```text
Sentinel Errors
Typed Errors
Structured Error Classification
```

where available.

---

# 55. Panic vs Error

Expected operational failures should be returned as errors.

Do not use panic for:

```text
Validation Failure
Not Found
Conflict
Dependency Failure
Normal Business Rejection
```

---

# 56. Panic Handling

Unexpected programming failures may panic, but recovery should only be introduced where the process boundary requires it.

Do not blindly recover panics and continue with potentially corrupted state.

---

# 57. Error Handling in Goroutines

A goroutine must have an explicit error-handling strategy.

Avoid:

```go
go func() {
    doWork()
}()
```

when `doWork()` can fail and the failure matters.

The owner must define whether the error is:

```text
Reported
Collected
Retried
Logged
Fatal
```

---

# 58. Worker Errors

Worker pools should classify worker errors and prevent silent failure.

A worker error must not disappear merely because the work was executed asynchronously.

---

# 59. Background Errors

Background operations should have a defined reporting mechanism.

Examples:

```text
Metrics
Structured Logs
Error Channel
DLQ
Alert
Persistent Failure Record
```

according to severity and architecture.

---

# 60. Error Handling During Shutdown

Shutdown cancellation should not automatically be reported as an application failure.

Distinguish:

```text
Expected Context Cancellation
```

from:

```text
Unexpected Operation Failure
```

---

# 61. Context Cancellation

Context cancellation is often a control-flow outcome rather than a system error.

Handle:

```text
context.Canceled
context.DeadlineExceeded
```

according to the operation's semantics.

Do not generate noisy error logs for expected shutdown cancellation.

---

# 62. Timeout Errors

Timeouts should identify the affected operation.

Conceptually:

```text
Redis Lookup Timeout
Database Query Timeout
External Routing Timeout
```

rather than one generic:

```text
TIMEOUT
```

Internally, preserve enough context to determine which dependency was slow.

---

# 63. Validation vs Authorization

Do not reveal sensitive authorization information through overly detailed validation.

For example, avoid validating resource details before authorization when doing so would allow unauthorized callers to infer protected information.

---

# 64. Error Security

Errors must not expose:

```text
Passwords
Tokens
Private Keys
SQL
Database Credentials
Internal Network Addresses
Stack Traces
Sensitive Coordinates
Internal Infrastructure Topology
```

---

# 65. Logging Error Details

Detailed error causes belong in controlled logs/traces rather than public API responses.

The logging system must follow:

```text
12.LOGGING_AND_DEBUGGING.md
```

---

# 66. Observability Error Details

Errors should provide enough structured information for:

```text
Metrics
Logs
Traces
Alerts
```

without creating high-cardinality metrics.

---

# 67. Error Correlation

Error logs should be correlated with the operation that produced them.

Useful metadata may include:

```text
Request ID
Trace ID
Operation
Component
Error Code
Dependency
```

Avoid putting sensitive resource identifiers into metrics labels.

---

# 68. Error Metrics

Useful metrics may include:

```text
Request Errors
Dependency Errors
Retry Count
DLQ Count
Validation Failures
Conflict Count
Timeout Count
```

Keep labels low-cardinality.

---

# 69. Error Alerts

Not every error requires an alert.

Alert on meaningful operational signals such as:

```text
Sustained Error Rate
Dependency Failure
Consumer Failure
DLQ Growth
Repeated Startup Failure
```

Avoid alerting on every individual expected validation error.

---

# 70. API Error Contract

The API must expose a stable error contract.

At minimum, clients should be able to determine:

```text
Error Code
Human-Readable Message
Request / Correlation Identifier where appropriate
Validation Details where applicable
```

---

# 71. Error Contract Evolution

Do not change existing error codes casually.

If a client depends on:

```text
DRIVER_UNAVAILABLE
```

renaming it silently can break client logic.

---

# 72. Event Error Contract

Messaging failure metadata should remain distinguishable from business event payloads.

A DLQ record should retain enough context to diagnose:

```text
Event
Failure
Attempts
Time
```

without changing the original event semantics unnecessarily.

---

# 73. Validation of Broker Messages

Broker messages are not automatically trusted merely because they came from an internal broker.

Validate:

```text
Envelope
Version
Required Fields
Identifiers
Allowed Values
```

before applying business effects.

---

# 74. Database Validation

Database constraints should complement application validation.

Use database constraints for invariants that must hold regardless of application path.

Examples:

```text
Unique Values
Not Null
Foreign Keys
State Constraints where appropriate
```

Do not rely only on application validation for concurrency-sensitive invariants.

---

# 75. Race-Safe Validation

Avoid:

```text
Check
 ↓
Later Act
```

when another concurrent operation can invalidate the check.

Prefer:

```text
Authoritative Conditional Operation
```

for concurrency-sensitive business rules.

---

# 76. Reservation Validation

Reservation should validate authoritative state at the point of state transition.

Do not trust an earlier Redis discovery result as proof that the driver is still available.

---

# 77. Region Validation

Region/legal restrictions should remain part of the appropriate domain/application validation.

A transport-level validation error should not replace a domain rule such as:

```text
Ride Not Allowed Between Regions
```

---

# 78. Error Testing

Every meaningful error classification should have tests.

Test:

```text
Expected Error
Expected Classification
Expected Mapping
Expected Side Effect
```

---

# 79. Validation Tests

Validation tests should cover:

```text
Missing
Malformed
Out of Range
Unsupported
Conflicting
Unauthorized
```

inputs as appropriate.

---

# 80. Error Mapping Tests

API tests should verify:

```text
Application Error
 ↓
Correct HTTP Status
 ↓
Correct Error Code
 ↓
Safe Message
```

---

# 81. Retry Tests

Test both:

```text
Transient Failure
 ↓
Retry
 ↓
Success
```

and:

```text
Permanent Failure
 ↓
No Infinite Retry
 ↓
Final Failure / DLQ
```

---

# 82. Error Concurrency Tests

For concurrency-sensitive operations, test concurrent failures.

Example:

```text
N Concurrent Reservation Attempts
        ↓
One Success
+
Expected Conflicts
```

---

# 83. Error Recovery Tests

Where recovery is supported, test:

```text
Dependency Failure
 ↓
Recovery
 ↓
Normal Processing
```

Examples include:

```text
Redis Recovery
Broker Recovery
Database Recovery
Consumer Retry
Outbox Retry
```

---

# 84. Error Testing With the Race Detector

Concurrency-sensitive error handling should be tested with:

```bash
go test -race ./...
```

where practical.

---

# 85. AI Agent Error Handling Rules

Before implementing error handling or validation, an AI agent must:

1. Identify the architectural layer owning the error.
2. Determine whether the failure is expected or unexpected.
3. Determine whether it is retryable.
4. Determine whether it is a business conflict.
5. Preserve error identity where required.
6. Avoid string-based error classification.
7. Define the public/API mapping if applicable.
8. Define logging/observability behaviour.
9. Check security and sensitive-data exposure.
10. Check concurrency and idempotency implications.
11. Add tests for success and failure paths.
12. Reuse existing error conventions.
13. Avoid duplicating validation already owned by another layer.
14. Run relevant validation.
15. Review the final diff.

---

# 86. AI Agent Forbidden Error Patterns

AI agents must not:

- return raw infrastructure errors to API clients,
- use string matching as the primary error classification mechanism,
- use panic for expected business failures,
- silently swallow errors,
- launch goroutines whose errors have no owner,
- retry indefinitely,
- retry non-idempotent operations blindly,
- treat all errors as HTTP 500,
- expose stack traces or secrets,
- duplicate domain validation in transport code without reason,
- convert every error into a generic string and lose its identity,
- ignore context cancellation,
- log sensitive payloads for debugging,
- claim failure handling is complete without testing failure paths.

---

# 87. Error Handling Change Checklist

Before merging an error-handling or validation change:

```text
[ ] Error owner identified
[ ] Error category defined
[ ] Validation boundary reviewed
[ ] Domain rules preserved
[ ] Error identity preserved
[ ] Error wrapping reviewed
[ ] Retryability defined
[ ] Idempotency reviewed
[ ] HTTP mapping reviewed where applicable
[ ] Event/DLQ mapping reviewed where applicable
[ ] Security reviewed
[ ] Logging reviewed
[ ] Observability reviewed
[ ] Concurrency reviewed
[ ] Failure tests added
[ ] Recovery tests added where required
[ ] Final diff reviewed
```

---

# 88. Final Error Handling Principle

> **Errors must carry useful meaning across architectural boundaries without leaking internal details; expected failures should be classified, recoverable failures should be bounded and retried safely, and business invariants must never be hidden behind generic error handling.**

The intended RideForge flow is:

```text
Failure Occurs
      ↓
Classify
      ↓
Preserve Cause
      ↓
Determine Recovery
      ↓
Apply Appropriate Boundary Mapping
      ↓
Observe
      ↓
Return Safe Outcome
```

Good error handling does not mean preventing every failure.

It means ensuring that when failure occurs, RideForge:

```text
Fails Correctly
Recovers Safely
Communicates Clearly
Remains Observable
Preserves Business State
```
