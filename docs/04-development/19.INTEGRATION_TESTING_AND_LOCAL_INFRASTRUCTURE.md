# 1. Purpose

Integration tests verify that RideForge components work correctly when connected to their real infrastructure dependencies.

They validate boundaries such as:

```text
Application
    ↓
PostgreSQL
```

```text
Application
    ↓
Redis
```

```text
Application
    ↓
Kafka / Redpanda
```

and complete workflows such as:

```text
API
 ↓
Application Service
 ↓
Database
 ↓
Outbox
 ↓
Broker
 ↓
Consumer
 ↓
Matching / Reservation
```

---

# 2. Integration Testing Principle

Integration tests should validate:

```text
Real Boundaries
+
Real Infrastructure Behaviour
+
Real Serialization
+
Real Transactions
+
Real Failure Modes
```

Use mocks for isolated unit behaviour.

Use real infrastructure when the infrastructure itself is part of what must be verified.

---

# 3. What Integration Tests Are For

Integration tests should detect problems that unit tests may miss:

```text
SQL Errors
Schema Mismatch
Migration Errors
Transaction Behaviour
Redis Command Behaviour
Broker Configuration
Serialization Mismatch
Consumer Behaviour
Connection Problems
Concurrency Issues
```

---

# 4. What Integration Tests Are Not

Integration tests should not become a replacement for all unit tests.

Avoid using integration infrastructure to test simple:

```text
Pure Functions
Domain Calculations
Simple Validation
Deterministic Transformations
```

when those behaviours can be tested quickly without external dependencies.

---

# 5. Integration Test Boundary

A test should make its integration boundary explicit.

Examples:

```text
Repository Integration Test
→ PostgreSQL

Redis Repository Test
→ Redis

Event Publisher Test
→ Kafka / Redpanda

Consumer Integration Test
→ Broker + Handler Dependencies

API Integration Test
→ HTTP + Application + Required Infrastructure
```

---

# 6. Local Infrastructure

The local integration environment should provide the infrastructure required by the tests.

Core dependencies are:

```text
PostgreSQL
Redis
Kafka / Redpanda
```

Use the repository's existing local infrastructure definitions.

Do not create a second infrastructure stack merely for tests unless the architecture requires isolation.

---

# 7. Infrastructure Isolation

Integration tests must not accidentally connect to:

```text
Production
Staging
Shared Developer Database
Shared Redis
Shared Broker
```

Tests should use explicitly controlled local or test infrastructure.

---

# 8. Environment Detection

Test configuration should make the target environment unambiguous.

Before destructive setup or cleanup, verify:

```text
Database Host
Database Name
Redis Endpoint
Broker Endpoint
Environment
```

---

# 9. Test Configuration

Integration tests should use test-specific configuration.

Examples:

```text
Test Database
Test Redis Namespace / Instance
Test Broker Topics
Test Consumer Groups
```

Do not reuse production configuration.

---

# 10. Infrastructure Lifecycle

A typical integration test environment follows:

```text
Start Infrastructure
        ↓
Wait Until Ready
        ↓
Prepare Schema
        ↓
Prepare Test State
        ↓
Run Tests
        ↓
Collect Diagnostics
        ↓
Clean Up
```

---

# 11. Infrastructure Readiness

Do not start tests immediately after a container starts.

Verify service readiness for:

```text
PostgreSQL
Redis
Kafka / Redpanda
```

A running container does not necessarily mean the service is ready to accept requests.

---

# 12. PostgreSQL Integration Tests

PostgreSQL integration tests should use the actual PostgreSQL engine.

They are appropriate for validating:

```text
Queries
Repositories
Transactions
Constraints
Indexes
Migrations
Concurrency
```

---

# 13. PostgreSQL Schema Setup

The test database should be created using the project's migration mechanism.

Prefer:

```text
Migration History
```

over manually creating test tables.

This ensures tests exercise the actual schema.

---

# 14. Migration Verification

A useful integration environment should verify that:

```text
Fresh Database
        ↓
All Migrations
        ↓
Current Schema
```

can be created successfully.

This protects against broken migration history.

---

# 15. Database Test Isolation

Tests must not depend on the execution order of unrelated test cases.

Isolation can be achieved through mechanisms such as:

```text
Transaction Rollback
Dedicated Schema
Dedicated Database
Explicit Cleanup
```

Choose the mechanism appropriate to the test.

---

# 16. Transaction-Based Isolation

Transaction rollback can be efficient for tests where all operations remain within one database connection/transaction.

It may not be sufficient when the operation under test:

```text
Commits Independently
Uses Multiple Connections
Runs Background Workers
Publishes Through Separate Transactions
```

---

# 17. Database Cleanup

When transaction isolation is not sufficient, clean up created data explicitly.

Cleanup should be:

```text
Deterministic
Bounded
Safe
```

---

# 18. Test Database Reset

For larger integration suites, a disposable database may be recreated between test runs.

Conceptually:

```text
Drop Test DB
 ↓
Create Test DB
 ↓
Run Migrations
 ↓
Run Tests
```

Use this only against disposable test infrastructure.

---

# 19. Test Data

Integration test data should be:

```text
Synthetic
Minimal
Deterministic
Purposeful
```

Avoid unnecessarily large datasets.

---

# 20. Test Data Builders

Where test entities have many fields, use builders or fixtures to create valid default entities.

Tests should override only the fields relevant to the scenario.

---

# 21. Test Data Ownership

Each test should make it clear which data it creates.

Avoid hidden global fixtures that make one test depend on state created by another.

---

# 22. Deterministic Identifiers

Where practical, tests should use predictable identifiers.

This makes failures easier to:

```text
Debug
Inspect
Reproduce
```

---

# 23. PostgreSQL Repository Tests

Repository integration tests should verify:

```text
Create
Read
Update
Delete
Filtering
Ordering
Pagination
Constraints
Transactions
```

only where the repository supports those operations.

---

# 24. Query Correctness

A repository test should validate returned business data, not merely:

```text
No Error
```

For example, verify:

```text
Correct Ride
Correct Driver
Correct State
Correct Ordering
```

---

# 25. Constraint Tests

When database constraints represent important invariants, integration tests should verify them.

Examples:

```text
Unique Constraint
Foreign Key
Check Constraint
Non-Null Requirement
```

---

# 26. Transaction Tests

Test transactions when correctness depends on atomicity.

Examples:

```text
Ride Creation + Outbox Record
Reservation + Driver State
Multiple Related Writes
```

The test should verify the complete atomic outcome.

---

# 27. Transaction Failure Tests

Where practical, intentionally cause a failure within a transaction and verify:

```text
Expected Rollback
No Partial State
No Invalid Outbox Record
```

---

# 28. PostgreSQL Concurrency

Concurrency-sensitive database behaviour should be tested against real PostgreSQL.

Examples:

```text
Two Reservation Attempts
Concurrent Driver Updates
Duplicate Requests
Competing State Transitions
```

---

# 29. Reservation Race Test

A critical concurrency test may model:

```text
Request A → Driver Available
Request B → Driver Available
```

Both attempt reservation.

The expected result should preserve the reservation invariant:

```text
At Most One Successful Reservation
```

according to the domain rules.

---

# 30. Redis Integration Tests

Redis integration tests should use a real Redis instance.

Test:

```text
Key Creation
Key Retrieval
TTL
Expiration
Atomic Operations
Set Membership
Geospatial / H3-related State
```

where applicable to the implementation.

---

# 31. Redis Key Isolation

Tests must not collide with unrelated Redis state.

Use:

```text
Dedicated Redis Instance
```

or:

```text
Test-specific key namespace
```

where appropriate.

---

# 32. Redis Cleanup

Every test that creates Redis state should have a deterministic cleanup strategy.

Do not rely on Redis eventually expiring unless expiration itself is the behaviour under test.

---

# 33. TTL Testing

TTL tests should account for timing.

Avoid overly strict assertions such as:

```text
TTL == exact number
```

when timing and scheduling can naturally vary.

Test the intended invariant:

```text
Key expires within expected bounds
```

---

# 34. Redis Expiration

Expiration behaviour should be tested when application correctness depends on stale state disappearing.

Examples:

```text
Driver Location
Availability
Temporary Reservation State
```

Use controlled, short TTLs in tests where appropriate.

---

# 35. Redis Atomicity Tests

If a workflow depends on atomic Redis operations, integration tests should verify that concurrent operations do not produce invalid state.

---

# 36. Redis Failure Tests

Where resilience requires it, test behaviour when Redis is:

```text
Unavailable
Slow
Restarted
Temporarily Disconnected
```

The expected result should follow the application's failure policy.

---

# 37. Driver Location Integration Tests

Driver-location integration tests should verify:

```text
Location Update
 ↓
H3 Cell Assignment
 ↓
Redis Membership
 ↓
Candidate Discovery
```

where the current implementation supports this flow.

---

# 38. Location Update Idempotency

If repeated location updates are expected, verify that repeated updates do not leave inconsistent membership state.

---

# 39. Stale Location Tests

If stale location handling exists, verify:

```text
Fresh Location
→ Candidate Eligible

Expired / Stale Location
→ Candidate Excluded
```

according to the actual business rules.

---

# 40. Kafka / Redpanda Integration Tests

Messaging integration tests should use the actual local broker.

Test:

```text
Publish
Consume
Serialization
Consumer Groups
Retries
DLQ
Ordering
```

where applicable.

---

# 41. Topic Isolation

Integration tests should not consume production or shared development topics.

Use:

```text
Test-specific Topics
```

or a disposable broker.

---

# 42. Consumer Group Isolation

Each test suite or controlled test environment should use consumer groups that cannot interfere with normal development consumers.

---

# 43. Event Serialization

Integration tests should verify:

```text
Producer Serialization
        ↓
Broker
        ↓
Consumer Deserialization
```

This catches incompatibilities that unit tests using in-memory objects may miss.

---

# 44. Event Envelope Tests

If RideForge uses a common event envelope, integration tests should verify important envelope fields such as:

```text
Event ID
Event Type
Timestamp
Correlation ID
Payload
```

according to the actual event contract.

---

# 45. Event Delivery

A successful publish should be distinguished from successful processing.

Test separately:

```text
Published
```

and:

```text
Consumed / Processed
```

---

# 46. Consumer Processing

Consumer integration tests should verify:

```text
Receive Event
 ↓
Deserialize
 ↓
Validate
 ↓
Execute Handler
 ↓
Commit / Acknowledge
```

according to the actual consumer implementation.

---

# 47. Consumer Failure

When processing fails, test the configured behaviour:

```text
Retry
 ↓
Retry Exhaustion
 ↓
DLQ
```

where implemented.

---

# 48. Duplicate Event Testing

At-least-once event delivery can result in duplicates.

Where idempotency is required, test:

```text
Event
Event Again
```

and verify that the resulting state remains correct.

---

# 49. Ordering Tests

If ordering is a business requirement, integration tests should verify the relevant ordering boundary.

Examples:

```text
Ride Created
 ↓
Ride Matched
 ↓
Ride Accepted
```

Do not assume broker delivery order is sufficient for every workflow.

---

# 50. Outbox Integration Tests

The outbox workflow should be tested with PostgreSQL and the broker where appropriate.

A representative test should verify:

```text
Business Transaction
        ↓
Database State
+
Outbox Record
        ↓
Publisher
        ↓
Broker Event
```

---

# 51. Outbox Atomicity

A critical property is:

```text
Business State Committed
+
Outbox Record Committed
```

as one database transaction where the architecture requires it.

Test failure scenarios to verify that the event is not silently lost.

---

# 52. Outbox Retry Tests

Where retries exist, verify:

```text
Publish Failure
 ↓
Outbox Remains Available
 ↓
Retry
 ↓
Successful Publication
```

---

# 53. DLQ Integration Tests

When a message cannot be processed after the configured retries, verify that:

```text
Original Event
+
Failure Metadata
```

is available in the configured DLQ mechanism.

---

# 54. API Integration Tests

API integration tests should exercise:

```text
HTTP Request
 ↓
Routing
 ↓
Validation
 ↓
Application Service
 ↓
Infrastructure
 ↓
HTTP Response
```

---

# 55. API Request Validation

Test:

```text
Valid Request
Missing Field
Invalid Field
Invalid State
Unauthorized Request
```

according to the endpoint contract.

---

# 56. API Response Validation

Verify:

```text
Status Code
Response Body
Error Shape
Headers
```

---

# 57. API and Database Integration

For endpoints that modify persistent state, verify both:

```text
HTTP Response
```

and:

```text
Database Result
```

Do not test only the response.

---

# 58. API and Event Integration

For endpoints that publish events, verify:

```text
API Request
 ↓
Database State
 ↓
Outbox
 ↓
Broker
```

where that workflow is part of the endpoint's behaviour.

---

# 59. Dispatch Integration Testing

Dispatch integration tests should use the actual persistence and operational state dependencies.

A representative workflow is:

```text
Create Ride
 ↓
Discover Candidates
 ↓
Filter
 ↓
Rank
 ↓
Reserve
 ↓
Publish Match Event
```

according to the selected dispatch strategy.

---

# 60. Stand Dispatch Integration

Stand dispatch tests should verify the stand-based ordering and selection rules implemented by the system.

Do not accidentally invoke smart-dispatch logic in tests intended to validate stand dispatch.

---

# 61. Smart Dispatch Integration

Smart dispatch tests should verify:

```text
Spatial Candidate Discovery
 ↓
Eligibility
 ↓
Scoring / Ranking
 ↓
Reservation
```

according to the configured algorithm.

---

# 62. Hybrid Dispatch Integration

Where the system supports strategy selection, integration tests should verify:

```text
Operating Context
 ↓
Strategy Selection
 ↓
Selected Dispatch Implementation
```

The test should verify that the correct strategy is selected without duplicating the strategy's entire internal test suite.

---

# 63. Region Validation Integration

Region-sensitive ride creation should be tested using explicit synthetic region scenarios.

Verify:

```text
Allowed Ride
→ Accepted

Disallowed Ride
→ Rejected
```

according to the actual domain rules.

---

# 64. End-to-End Local Workflow

A high-value local integration test should cover the complete supported path:

```text
Client
 ↓
Ride API
 ↓
Ride Service
 ↓
PostgreSQL
 ↓
Outbox
 ↓
Kafka / Redpanda
 ↓
Matching
 ↓
Redis / PostgreSQL
 ↓
Reservation
 ↓
Match Event
```

Only include components actually implemented in the current system.

---

# 65. End-to-End Test Scope

Do not make every test a full end-to-end test.

Use:

```text
Unit Tests
→ Fast logic validation

Integration Tests
→ Infrastructure boundary validation

End-to-End Tests
→ Critical workflow validation
```

---

# 66. Test Timing

Integration tests are slower than unit tests.

Keep them:

```text
Focused
Deterministic
Parallelizable where safe
```

---

# 67. Test Parallelism

Tests may run in parallel only when their infrastructure state is isolated.

Avoid parallel tests that mutate shared:

```text
Database Rows
Redis Keys
Topics
Consumer Groups
```

without explicit isolation.

---

# 68. Race Testing

For concurrency-sensitive integration tests, use race detection where practical.

Example:

```bash
go test -race ./...
```

The race detector does not replace database or distributed concurrency testing.

---

# 69. Timeouts

Every integration test involving external infrastructure should have a bounded timeout.

Avoid tests that can hang indefinitely because:

```text
Broker Not Ready
Consumer Not Running
Database Connection Stuck
Event Never Arrives
```

---

# 70. Eventual Consistency

Event-driven tests may need to wait for asynchronous state transitions.

Prefer bounded polling with a deadline over arbitrary long sleeps.

Avoid:

```text
time.Sleep(10 * time.Second)
```

when the condition can be observed directly.

---

# 71. Polling Assertions

For asynchronous workflows:

```text
Wait
 ↓
Check Condition
 ↓
Retry Until Deadline
```

The test should fail with enough diagnostic information to identify what did not happen.

---

# 72. Avoid Flaky Timing

Do not rely on:

```text
Fixed Sleep
Exact Timestamp
Exact Scheduling Order
```

unless timing itself is the behaviour being tested.

---

# 73. Test Diagnostics

When an integration test fails, diagnostics should help identify:

```text
Application Logs
Database State
Redis State
Broker State
Consumer State
```

where practical.

---

# 74. Database Diagnostics

For database-related failures, useful diagnostics may include:

```text
Query Error
Transaction State
Relevant Record IDs
Migration Version
```

Do not dump entire databases into test output.

---

# 75. Redis Diagnostics

For Redis failures, diagnostics may include:

```text
Key
Operation
TTL
Expected State
Actual State
```

Avoid dumping sensitive or excessive Redis data.

---

# 76. Messaging Diagnostics

For broker failures, include useful context such as:

```text
Topic
Partition where known
Event ID
Consumer Group
Processing Stage
```

---

# 77. Test Failure Messages

A good integration assertion should explain:

```text
Expected
Actual
Relevant Entity
Relevant State
```

This reduces debugging time.

---

# 78. Test Cleanup on Failure

Cleanup should run even when assertions fail.

Use appropriate test lifecycle mechanisms so that:

```text
Database
Redis
Broker
```

do not accumulate uncontrolled state.

---

# 79. Container Cleanup

If tests create temporary containers or infrastructure, ensure cleanup occurs after the suite.

Use the repository's existing container lifecycle mechanism.

---

# 80. Disposable Infrastructure

Disposable infrastructure is preferred when:

```text
Isolation
Reproducibility
Parallel Execution
```

are more important than startup speed.

---

# 81. Shared Local Infrastructure

Shared local infrastructure may be acceptable for developer convenience, but tests must isolate their state.

For example:

```text
Test Redis Key Prefix
Test Topic
Test Consumer Group
```

---

# 82. CI Integration Infrastructure

CI should provide reproducible integration dependencies.

The CI environment should not rely on:

```text
Developer Machine
Developer's Local Database
Developer's Redis
Developer's Broker
```

---

# 83. CI Database

CI should create a clean test database for the integration suite.

The schema should come from migrations.

---

# 84. CI Redis

CI Redis should be isolated from every other environment.

Tests should not depend on persistent Redis state from previous CI runs.

---

# 85. CI Broker

CI Kafka / Redpanda should use isolated topics and consumer groups.

Avoid hard-coded shared topic names when parallel CI jobs can conflict.

---

# 86. Integration Test Ordering

Do not require tests to execute in a specific order unless the test is explicitly testing an ordered workflow.

A suite that passes only because:

```text
Test A
```

runs before:

```text
Test B
```

has hidden state coupling.

---

Test names should describe behaviour.


# 88. Test Organization

Organize tests according to the project's existing Go package structure.

Keep integration tests discoverable without creating duplicate package architecture.

---

# 89. Integration Test Markers

If the repository distinguishes:

```text
Unit
Integration
End-to-End
```

# 91. Focused Integration Test Runs

During development, run only the affected integration tests first.

Examples:

```text

Redis Tests
Messaging Tests

```

---

# 92. Full Validation

Before merging a significant infrastructure-dependent change:

```text
Unit Tests
+
Integration Tests
+
```

# 93. Integration Test Data Volume

Use the smallest dataset that proves the behaviour.

Large datasets belong in:

```text
Load Tests
Performance Tests
Benchmark Suites
```

rather than ordinary integration tests unless the large dataset itself is required to reproduce a correctness issue.

# 94. Integration and Performance

Integration tests are not automatically performance tests.

Avoid asserting strict latency thresholds in ordinary integration tests unless the threshold is stable and intentional.

Use:


# 101. AI Agent Integration Testing Rules

Before adding or modifying an integration test, an AI agent must:

1. Identify the exact integration boundary.
2. Inspect existing integration-test infrastructure.
3. Reuse existing local infrastructure definitions.
4. Determine required dependencies.
5. Ensure the test cannot target production or shared infrastructure.
6. Use migrations for database schema setup.
7. Isolate Redis state.
8. Isolate broker topics and consumer groups.
9. Create deterministic test data.
10. Define cleanup behaviour.
11. Bound asynchronous waits.
12. Avoid arbitrary sleeps where observable conditions exist.
13. Test failure behaviour when it is part of the requirement.
14. Run the relevant integration tests.
15. Inspect failures rather than masking them with longer timeouts.
16. Review the final diff.

---

# 102. AI Agent Forbidden Integration Testing Patterns

AI agents must not:

- connect tests to production infrastructure,
- reuse production credentials,
- use shared state without isolation,
- manually create database schema instead of using migrations,
- depend on test execution order,
- use arbitrary long sleeps to hide race conditions,
- create unbounded polling loops,
- ignore cleanup,
- swallow infrastructure failures,
- replace required integration tests with mocks,
- create duplicate infrastructure definitions unnecessarily,
- claim an integration workflow passed without actually running it,
- increase timeouts indefinitely instead of investigating the underlying failure.

---


# 104. Final Integration Testing Principle

> **Integration tests should prove that RideForge's real components work together correctly under realistic infrastructure conditions without turning the test suite into an uncontrollable or fragile environment.**

The intended testing structure is:

```text
Unit Tests
    ↓
Component Behaviour
    ↓
Integration Tests
    ↓
Infrastructure Boundaries
    ↓
Critical End-to-End Workflows
```

The core RideForge integration path is:

```text
API
 ↓
Application Service
 ↓
PostgreSQL
 ↓
Outbox
 ↓
Kafka / Redpanda
 ↓
Consumer
 ↓
Matching
 ↓
Redis / PostgreSQL
 ↓
Reservation
 ↓
Event
```

Integration testing must preserve the same architectural boundaries used by the application while providing:

```text
Isolation
Reproducibility
Deterministic Data
Bounded Execution
Useful Diagnostics
Safe Cleanup
```

A successful integration suite should provide confidence that the application is not merely correct in isolation, but also correct when connected to the infrastructure on which RideForge depends.
