# 1. Purpose

This document defines the engineering roadmap for RideForge.

The roadmap describes:

- what has already been implemented,
- what the current architecture provides,
- what should be implemented next,
- which capabilities are intentionally deferred,
- how roadmap items should be evaluated against the actual codebase.

The roadmap is a direction, not a requirement to introduce code for every named item.

---

# 2. Roadmap Principle

The roadmap follows:

```text
Business Requirement
        ↓
Architecture
        ↓
Implementation
        ↓
Verification
        ↓
Observability
        ↓
Documentation
```

A roadmap item is considered complete when the existing implementation already satisfies its intended responsibility.

Do not introduce additional abstractions merely to represent a phase or commit.

The current dispatch architecture follows:

```text
Ride Request
     ↓
Candidate Discovery
     ↓
Candidate Enrichment
     ↓
Candidate Filtering
     ↓
Candidate Ranking
     ↓
Dispatch Optimization
     ↓

     ↓
```

The geographic path is:

```text
H3
 ↓
Adaptive Ring Expansion
 ↓
Driver Index
 ↓
Optional Geo Refinement
 ↓
```

The long-term intelligence path is:

```text

       ↓
Data-Driven Dispatch
       ↓
ML-Assisted Dispatch
```

# 4. Completed Foundation

The following major foundations have already been implemented across the project.

## 4.1 Production H3 Driver Index

The H3 index foundation includes:

- driver-to-cell tracking,
- cell-to-driver indexing,
- atomic movement,
- same-cell update optimization,
- empty-cell cleanup,
- multi-cell lookup optimization,
- H3-related metrics/tracing.

The H3 index is the primary geographic driver lookup mechanism.

---

# 5. Intelligent Ring Expansion

The candidate discovery architecture includes:

```text
Density
   ↓
Expansion Profile
   ↓
Adaptive Ring Expansion
   ↓
Bounded Search
```

The discovery system can adapt search behaviour based on local supply conditions rather than always searching a fixed maximum ring.

---

# 6. Candidate Retrieval Pipeline

The candidate pipeline has been implemented as an isolated processing flow.

The current conceptual sequence is:

```text
Discovery
   ↓
Enrichment
   ↓
Validation
   ↓
Duplicate Filtering
   ↓
Availability
   ↓
Already Offered
   ↓
Ranking
   ↓
Heap / Ordered Candidates
```

The pipeline is designed so that each stage owns one primary responsibility.

---

# 7. Candidate Enrichment

Candidate enrichment provides required driver information before downstream filtering and ranking.

The architecture includes batch data loading rather than performing one backend request for every candidate where the existing data source supports batch access.

This reduces:

- Redis round trips,
- latency,
- connection pressure,
- repeated data access.

---

# 8. Candidate Filtering

Candidate filtering includes explicit stages for invalid or unsuitable candidates.

The current architecture includes filtering responsibilities such as:

```text
Validation
Duplicate Detection
Availability
Already Offered
```

Additional filters should be added only when there is a real business or operational requirement.

---

# 9. Candidate Ranking

The ranking engine has been implemented as a separate subsystem.

The current architecture includes:

```text
Feature Extraction
      ↓
Travel Features
      +
Quality Features
      +
Fairness Features
      ↓
Scoring
      ↓
Candidate Score
```

Ranking policy is configuration-driven.

---

# 10. Dispatch Orchestration

The matching/dispatch engine currently coordinates:

```text
Attempt Counting
      ↓
Retry Policy
      ↓
Candidate Discovery
      ↓
Candidate Pipeline
      ↓
Adaptive Offer Decision
      ↓
Driver Reservation
      ↓
Offer Attempt
      ↓
Outbox Event
```

Reservation remains the authoritative concurrency boundary.

---

# 11. Dispatch Optimization Foundation

The dispatch optimizer foundation includes configurable policy for:

- candidate search radius,
- candidate limit,
- offer batch size,
- offer timeout,
- retry behaviour.

The policy is kept separate from the matching loop.

---

# 12. Geo Engine Foundation

The Geo Engine currently provides the foundation for:

```text
H3 Discovery
      ↓
Adaptive Search
      ↓
Candidate IDs
      ↓
Geo Refinement
```

The architecture contains boundaries for:

- candidate search,
- H3 strategy,
- alternate geo strategy,
- refinement,
- Redis GEO refinement,
- no-op refinement,

# 13. Event-Driven Foundation

The platform uses an event-driven architecture for asynchronous application operations.

The architecture includes:

```text
Application State
      ↓
Transactional Outbox
      ↓
Event Broker
      ↓
Consumers
```

The event architecture includes reliability mechanisms such as:

- event envelopes,
- processed-event handling,
- dead-letter handling,
- asynchronous event consumers.

---

# 14. Reliability Foundation

The platform includes reliability mechanisms around:

- transactional persistence,
- outbox processing,
- idempotent event handling,
- reservation cleanup,
- realtime TTLs,
- timeout scheduling,
- recovery-oriented infrastructure.

Further reliability work should be driven by actual failure modes.

# 16. Stage 1 — Production H3 Driver Index

## Goal

Make the H3 driver index reliable and efficient under realtime driver movement.

## Target Capabilities

```text
Atomic cell movement
Same-cell update optimization
Empty-cell cleanup
Batch/multi-cell lookup
Metrics
Tracing
```

## Status

**Completed / substantially implemented.**

Existing functionality should be reused.

No duplicate H3 indexing subsystem should be introduced.

---

# 17. Stage 2 — Intelligent Ring Expansion

## Goal

Avoid fixed maximum-radius searches and expand only as needed.

## Target Capabilities

```text
Progressive search
Density-aware expansion
Search budget
Candidate limit
```

## Status

**Completed / substantially implemented.**

The current discovery architecture already contains density classification, expansion profiles, adaptive expansion policy, ring expansion, and search budgets.

---

# 18. Stage 3 — Candidate Retrieval Pipeline

## Goal

Build an isolated, efficient candidate processing pipeline.

## Target Capabilities

```text
Candidate collection
Candidate iterator
Candidate enrichment
Batch loading
Independent filters
Ranking integration
Heap ordering
Candidate context
Bootstrap composition
```

## Status

**Completed.**

The candidate pipeline is already a core production architecture component.

Do not recreate these stages under different names.

---

# 19. Stage 4 — Ranking Engine

## Goal

Move from simplistic distance-oriented selection toward feature-based ranking.

## Target Capabilities

```text
Travel / ETA
Driver quality
Fairness
Demand-aware signals
Feature normalization
Configurable weighted scoring
```

## Status

**Completed / current deterministic ranking foundation implemented.**

The architecture already contains:

```text
Ranker
Feature Extractor
Travel Features
Quality Features
Fairness Features
Quality Calculator
Scorer
Ranking Configuration
```

Future ranking improvements should extend these components.

---

# 20. Stage 4 Deferred Enhancements

The following capabilities may evolve further:

```text
Production routing-backed ETA
Improved normalization
Demand/supply ranking signals
Better fairness modelling
ETA caching/batching
```

These are enhancements, not reasons to create another ranking subsystem.

---

# 21. Stage 5 — Dispatch Optimizer

## Goal

Make dispatch policy adaptive rather than relying on fixed batch size, timeout, and retry behaviour.

## Target Capabilities

```text
Adaptive batch size
Dynamic offer timeout
Retry optimization
Acceptance-probability-aware decisions
```

## Status

**Foundation substantially implemented.**

The existing retry/dispatch policy is the correct extension point.

Future work should improve policy inputs and decision quality without moving policy formulas into the matching engine.

---

# 22. Stage 5 — Next Evolution

The preferred evolution is:

```text
Current Driver / Ride Data
        ↓
Historical Response Signals
        ↓
Dispatch Policy
        ↓
Adaptive Batch
        ↓
Adaptive Timeout
        ↓
Adaptive Retry
```

Potential inputs include:

```text
Acceptance Rate
Response Time
Cancellation Rate
ETA
Driver Availability
Current Candidate Count
```

The implementation should remain deterministic until reliable data justifies prediction-based decisions.

---

# 23. Stage 6 — Geo Engine

## Goal

Make geographic candidate discovery and refinement production-ready.

## Target Capabilities

```text
H3 primary discovery
Redis GEO secondary refinement
Haversine refinement
Future routing provider
```

## Status

**Foundation implemented / substantially complete.**

The current codebase already contains:

- H3 discovery,
- adaptive expansion,
- Geo strategy,
- refinement abstractions,
- Redis GEO refiner,
- no-op refiner,
- travel calculator boundary.

Further work should focus on completing only the missing production capability required by the actual workload.

---

# 24. Stage 6 — Routing / ETA Evolution

The next meaningful Geo Engine evolution is:

```text
H3
 ↓
Candidate narrowing
 ↓
Geo refinement
 ↓
Routing ETA
 ↓
Ranking
```

Routing should not be introduced for every discovered driver.

The candidate population must first be reduced.

Possible routing providers include:

```text
Google
Mapbox
OSRM
Valhalla
```

The provider must remain behind the travel/routing abstraction.

---

# 25. Stage 7 — Hot Region Scaling

## Goal

Understand local supply and demand conditions at the H3-cell level.

## Target Capabilities

```text
Cell occupancy
Driver supply
Ride demand
Supply/demand ratio
Hot-cell detection
Surge-related signals
```

Conceptually:

```text
H3 Cell
  │
  ├── Drivers
  ├── Requests
  ├── Supply
  └── Demand
       │
       ▼
   Cell State
```

## Status

**Not yet a primary implementation priority.**

Implement when demand-aware dispatch or regional scaling requires it.

---

# 26. Stage 7 — Recommended Implementation Order

When Stage 7 becomes necessary:

```text
Cell Occupancy
      ↓
Demand / Supply Counters
      ↓
Hot Cell Detection
      ↓
Cell-Level Metrics
      ↓
Demand-Aware Ranking
      ↓
Surge Policy
```

Do not implement surge computation before the underlying demand/supply data is reliable.

---

# 27. Stage 8 — Multi-Node Scaling

## Goal

Scale dispatch horizontally across geographic regions.

Target architecture:

```text
Region
  ↓
H3 Cells
  ↓
Cell Ownership
  ↓
Dispatch Node
  ↓
Local Matching
```

Capabilities:

```text
Regional partitioning
Cell ownership
Local dispatch
```

## Status

**Deferred.**

Do not implement distributed cell ownership until single-node/regional performance and operational requirements justify it.

---

# 28. Stage 8 — Scaling Principle

Do not distribute the system simply because it is theoretically scalable.

The preferred sequence is:

```text
Measure
  ↓
Identify bottleneck
  ↓
Determine ownership boundary
  ↓
Partition
  ↓
Operate locally
```

Distributed coordination introduces significant complexity and should have a measurable justification.

---

# 29. Stage 9 — Reliability

## Goal

Make realtime indexes and asynchronous processing recoverable and self-healing.

Target capabilities:

```text
Redis recovery
Background reconciliation
Stale driver cleanup
```

## Status

**Foundation exists; additional hardening remains workload-driven.**

# 30. Stage 9 — Recovery Architecture

The intended direction is:

```text
Durable State
      ↓
Recovery Process
      ↓
Realtime Cache
      ↓
Geo Index
```

and periodically:

```text
Cache
 ↓
Geo Index
 ↓
Database
```

---

# 31. Stage 9 — Stale Driver Cleanup

The system should remove stale driver state caused by:

```text
Expired heartbeat
Offline connection
Expired location
Expired reservation
```

Existing TTL-based mechanisms should be reused before introducing a new cleanup subsystem.

---

Target capabilities:

```text
H3 metrics
Dispatch latency
Heatmap metrics
```

The system should eventually answer:

```text
Where is demand?
How much supply exists?
How long does matching take?
Where are failures occurring?
```

# 45. Roadmap Completion Rule

A roadmap phase is complete when its intended architectural capability exists.

For example:

```text
Phase says "Batch Data Loading"
```

and the code already provides correct batch loading.

Then:

```text
Phase = Complete
```

Do not add another wrapper or abstraction solely to create a visible phase implementation.

---

# 46. Implementation Rule

When implementing a roadmap item:

1. Inspect the current code.
2. Identify existing functionality.
3. Reuse existing contracts.
4. Identify only the missing capability.
5. Implement the smallest production-grade change.
6. Add or update tests.
7. Add required observability.
8. Remove obsolete code.
9. Update documentation.
10. Verify integration.


# 52. Final Rule

The most important roadmap rule is:

```text
Do not implement a roadmap item because
the roadmap says it exists.

Implement it because the system needs it.
```

If the capability already exists:

```text
Reuse it.
Document it.
Mark it complete.
Move forward.
```

If it is partially implemented:

```text
Complete only the missing responsibility.
```

If it is not currently required:

```text
Defer it.
```

This keeps RideForge production-focused, maintainable, and free from phase-driven overengineering.
