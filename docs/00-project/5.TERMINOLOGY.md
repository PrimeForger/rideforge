# 1. Purpose

This document defines the canonical terminology used throughout RideForge.

The purpose is to ensure that:

- developers use consistent names,
- architecture documents use the same vocabulary as the codebase,
- business rules are not confused with implementation details,
- AI coding agents interpret project terminology consistently,
- similar concepts are not represented by multiple competing names.

When a term in this document conflicts with an informal synonym, this document should be treated as the canonical project vocabulary.

---

# 2. Naming Principles

RideForge terminology should follow these rules:

1. Prefer the existing codebase term over introducing a synonym.
2. Use domain terminology for business concepts.
3. Use technical terminology for implementation concepts.
4. Do not use infrastructure names as substitutes for domain concepts.
5. Keep state names explicit.
6. Avoid ambiguous words such as `data`, `item`, `object`, or `thing` when a domain-specific term exists.
7. AI agents must preserve established terminology when modifying code or documentation.

# 3. Core Domain Terms

## 3.1 Ride

A **Ride** represents the customer's requested transportation operation.

A ride contains the business context required to perform and track the trip.

Conceptually:

```text
Ride
 ├── Rider / Customer
 ├── Pickup
 ├── Destination
 ├── State
 └── Matching / Dispatch lifecycle
```

A ride is a durable business concept.

---

## 3.2 Driver

A **Driver** is the supply-side participant who can be considered for a ride.

Driver information may exist in multiple forms:

```text
Durable Driver State
Realtime Driver State
Candidate Driver Data
```

These forms must not be treated as interchangeable.

---

## 3.3 Rider

A **Rider** is the customer requesting or participating in a ride.

The rider is part of the ride domain but is not equivalent to the ride itself.

---

## 3.4 Pickup

The **Pickup** is the geographic origin associated with a ride request.

It is used by candidate discovery and travel estimation.

Typical inputs include:

```text
Latitude
Longitude
Region
H3 Cell
```

---

## 3.5 Destination

The **Destination** is the geographic endpoint of the ride.

It is primarily relevant to trip execution, pricing, routing, ETA, and ride lifecycle operations.

---

# 4. Matching Terminology

## 4.1 Matching

**Matching** is the process of finding and selecting an eligible driver for a ride.

The high-level flow is:

```text
Ride
 ↓
Candidate Discovery
 ↓
Candidate Pipeline
 ↓
Ranking
 ↓
Reservation
 ↓
Offer
```

---

## 4.2 Dispatch

**Dispatch** is the broader operational process responsible for deciding how a ride should be offered to drivers and executing that decision.

Matching is a core part of dispatch.

In RideForge:

```text
Dispatch
 ├── Discovery
 ├── Candidate Processing
 ├── Ranking
 ├── Dispatch Policy
 ├── Reservation
 └── Offer
```

---

## 4.3 Matching Engine

The **Matching Engine** is the application orchestration component that executes the matching flow.

It coordinates:

```text
Retry Policy
Candidate Searcher
Candidate Pipeline
Driver Reservation
Offer Persistence
Outbox Event Creation
```

It should not own the internal implementation of these subsystems.

---

## 4.4 Matching Attempt

A **Matching Attempt** is one dispatch cycle performed while trying to match a ride.

Conceptually:

```text
Ride
 ├── Attempt 1
 ├── Attempt 2
 └── Attempt 3
```

The attempt number may influence search and dispatch policy.

---

## 4.5 Candidate

A **Candidate** represents a driver being considered for a particular ride.

A candidate is not necessarily:

```text
available,
reserved,
offered,
or selected.
```

It is a driver that has entered the candidate processing flow.

---

## 4.6 Candidate ID

A **Candidate ID** identifies the driver represented by a candidate.

In the current architecture this corresponds to the driver's UUID.

The candidate identifier should not be confused with:

```text
Ride ID
Offer ID
Event ID
Reservation ID
```

---

## 4.7 Candidate Discovery

**Candidate Discovery** identifies drivers that are geographically relevant to the ride.

Conceptually:

```text
Pickup
 ↓
Spatial Search
 ↓
Candidate Driver IDs
```

Discovery should not determine final dispatch eligibility by itself.

---

## 4.8 Candidate Searcher

A **Candidate Searcher** is the application-facing abstraction responsible for finding geographically relevant candidate drivers.

The matching engine depends on the searcher rather than directly depending on H3 or Redis GEO.

---

## 4.9 Candidate Pipeline

The **Candidate Pipeline** processes discovered candidates before they reach dispatch.

Conceptually:

```text
Candidates
 ↓
Enrichment
 ↓
Validation
 ↓
Duplicate Filtering
 ↓
Availability
 ↓
Already Offered
 ↓
Ranking
 ↓
Ordered Candidates
```

Each pipeline stage should have a clear responsibility.

---

## 4.10 Candidate Enrichment

**Candidate Enrichment** loads the additional driver information required for downstream filtering and ranking.

The preferred access pattern is batch loading where supported.

---

## 4.11 Candidate Filter

A **Candidate Filter** removes candidates that should not continue through the pipeline.

Examples include:

```text
Validation
Duplicate
Availability
Already Offered
```

A filter should not perform unrelated ranking or dispatch operations.

---

## 4.12 Eligible Candidate

An **Eligible Candidate** is a candidate that has passed the applicable candidate filters and can proceed toward ranking or dispatch.

Eligibility is not the same as reservation.

---

## 4.13 Ranked Candidate

A **Ranked Candidate** is an eligible candidate for which the ranking system has calculated a score and ordering.

---

# 5. Candidate State Terminology

The following concepts must remain distinct:

```text
Discovered
    ↓
Enriched
    ↓
Eligible
    ↓
Ranked
    ↓
Reserved
    ↓
Offered
    ↓
Accepted / Rejected / Timed Out
```

A candidate may stop progressing at any stage.

---

# 6. Ranking Terminology

## 6.1 Ranking

**Ranking** is the process of ordering eligible candidates according to dispatch relevance.

The ranking system combines features into a score.

---

## 6.2 Ranker

A **Ranker** is the component responsible for turning candidate information into a ranked result.

It coordinates feature extraction and scoring.

---

## 6.3 Feature

A **Feature** is a normalized or otherwise prepared input used by the ranking system.

Examples:

```text
Travel Feature
Quality Feature
Fairness Feature
```

---

## 6.4 Feature Extractor

A **Feature Extractor** converts candidate/context data into ranking features.

It should not own the final weighted scoring policy.

---

## 6.5 Scorer

A **Scorer** combines ranking features according to configured ranking policy and produces a candidate score.

---

## 6.6 Score

A **Score** is the numeric ranking value assigned to a candidate.

Higher or lower score semantics must remain consistent with the configured ranking implementation.

The score itself is not a business state.

---

## 6.7 Travel Feature

A **Travel Feature** represents travel-related information used by ranking.

Potential values include:

```text
Distance
ETA
Travel Duration
```

The architecture is designed to evolve toward ETA-based ranking.

---

## 6.8 Quality Feature

A **Quality Feature** represents driver-performance information used by ranking.

Examples include:

```text
Acceptance Rate
Cancellation Rate
Timeout Rate
Rating
Completed Trips
```

---

## 6.9 Quality Score

A **Quality Score** is the calculated representation of driver quality used by the ranking system.

The calculation should use configuration rather than hidden hard-coded business weights.

---

## 6.10 Fairness Feature

A **Fairness Feature** represents dispatch fairness signals.

A current example is:

```text
Idle Time
```

or a value derived from the driver's last assignment.

Fairness should influence ranking without overriding fundamental eligibility or reservation rules.

---

# 7. Dispatch Policy Terminology

## 7.1 Retry Policy

The **Retry Policy** determines adaptive dispatch parameters for the current matching attempt.

Possible outputs include:

```text
Search Radius
Candidate Limit
Offer Batch Size
Offer Timeout
```

The policy decides.

The matching engine executes.

---

## 7.2 Dispatch Decision

A **Dispatch Decision** is the policy output used by the matching engine for the current dispatch operation.

It may contain values such as:

```text
Radius
Candidate Limit
Batch Size
Timeout
```

---

## 7.3 Offer Batch

An **Offer Batch** is the group of candidates selected for simultaneous or near-simultaneous driver offers during a dispatch operation.

Example:

```text
Batch Size = 3

Driver A
Driver B
Driver C
```

---

## 7.4 Adaptive Batch Size

**Adaptive Batch Size** means the number of drivers offered at once can change according to dispatch policy.

The value should not be hard-coded inside the matching loop when the policy is expected to vary.

---

## 7.5 Offer Timeout

An **Offer Timeout** is the maximum configured period during which a driver offer remains actionable before timeout handling occurs.

Timeout handling is asynchronous.

---

## 7.6 Retry

A **Retry** is another dispatch attempt performed after the current matching operation does not produce the required successful outcome.

Retry behaviour is controlled by policy and ride state.

---

# 8. Reservation Terminology

## 8.1 Reservation

A **Reservation** is the concurrency operation that claims a driver for a dispatch operation.

Conceptually:

```text
Candidate
 ↓
Reserve
 ↓
Success / Failure
```

Reservation is the authoritative concurrency boundary.

---

## 8.2 Driver Locker

The **Driver Locker** is the application-facing abstraction used to reserve and release drivers.

The current implementation uses Redis-backed locking.

Application code should depend on the locker abstraction rather than directly issuing Redis lock commands.

---

## 8.3 Reservation Success

Reservation succeeds when the system obtains ownership of the driver for the relevant dispatch operation.

---

## 8.4 Reservation Rejection

Reservation rejection means the driver could not be claimed.

This may occur because another concurrent operation already claimed the driver.

A reservation rejection is not automatically an infrastructure failure.

---

## 8.5 Reservation Error

A reservation error indicates an operational or infrastructure failure while attempting to perform the reservation.

Examples:

```text
Redis unavailable
Network failure
Lock implementation failure
```

This must remain distinguishable from a normal reservation rejection.

---

## 8.6 Reservation Release

**Reservation Release** removes the driver's dispatch reservation when the reservation is no longer required.

Typical reasons include:

```text
Acceptance
Rejection
Timeout
Ride Cancellation
Offer Creation Failure
```

---

# 9. Offer Terminology

## 9.1 Driver Offer

A **Driver Offer** represents an active opportunity presented to a driver for a ride.

The lifecycle is:

```text
Reserved
 ↓
Offered
 ↓
Accepted / Rejected / Timed Out
```

---

## 9.2 Offer Attempt

An **Offer Attempt** is the persistent record connecting a ride, driver, and dispatch attempt when the system creates an offer.

It provides durable dispatch history.

---

## 9.3 Driver Offered Event

The **Driver Offered Event** is the asynchronous event representing that an offer has been created for a driver.

It is persisted through the outbox before event publication.

---

## 9.4 Offer Delivery

**Offer Delivery** is the transport-level process of communicating the offer to the driver.

Possible delivery mechanisms include:

```text
Realtime
Push Notification
```

The matching engine should not own the transport implementation.

---

# 10. Driver Response Terminology

## 10.1 Driver Response

A **Driver Response** is the driver's response to an active offer.

The principal outcomes are:

```text
Accept
Reject
Timeout
```

---

## 10.2 Acceptance

**Acceptance** occurs when a driver accepts an offer within the valid offer lifecycle.

Acceptance transitions the dispatch flow toward the ride assignment state.

---

## 10.3 Rejection

**Rejection** occurs when a driver declines an active offer.

The system can then release the reservation and continue according to dispatch policy.

---

## 10.4 Timeout

**Timeout** occurs when an offer reaches its configured expiration without a valid acceptance.

Timeout processing must be idempotent.

---

# 11. Geographic Terminology

## 11.1 H3

**H3** is the hierarchical hexagonal spatial indexing system used as a primary geographic indexing mechanism.

RideForge uses H3 to reduce the geographic search space before expensive refinement.

---

## 11.2 H3 Cell

An **H3 Cell** is the geographic index unit used to group nearby locations and drivers.

Conceptually:

```text
Driver
 ↓
H3 Cell
```

---

## 11.3 H3 Index

The **H3 Index** is the realtime mapping between H3 cells and active driver identifiers.

It is used for efficient candidate discovery.

---

## 11.4 H3 Resolution

**H3 Resolution** determines the spatial granularity of the H3 grid.

Higher resolution generally means smaller cells.

The configured resolution is an operational/geographic policy.

---

## 11.5 Ring

A **Ring** is a level of geographic expansion around the pickup H3 cell.

Conceptually:

```text
Ring 0
Ring 1
Ring 2
Ring 3
```

---

## 11.6 Ring Expansion

**Ring Expansion** is the process of progressively searching additional H3 cells when the current search does not produce sufficient candidates.

---

## 11.7 Search Ring

A **Search Ring** refers to the ring boundary used by the discovery strategy.

The search should remain bounded by configured policy.

---

## 11.8 Density

**Density** represents the relative driver availability around the search location.

RideForge can use density to influence expansion behaviour.

---

## 11.9 Density Classifier

The **Density Classifier** categorizes local supply according to configured thresholds.

Conceptually:

```text
Sparse
Dense
```

The exact classification model belongs to the discovery policy.

---

## 11.10 Expansion Profile

An **Expansion Profile** describes how geographic search should progress under a particular supply condition.

It is selected by the discovery policy.

---

# 12. Geo Refinement Terminology

## 12.1 Geo Refinement

**Geo Refinement** is the process of reducing or reordering candidates using more precise geographic information after initial H3 discovery.

---

## 12.2 Redis GEO

**Redis GEO** refers to Redis's geographic indexing/query capability used as a secondary geographic refinement mechanism.

It is not the primary H3 index.

---

## 12.3 Haversine Refinement

**Haversine Refinement** calculates great-circle distance between geographic coordinates.

It is suitable for distance refinement but does not account for road networks or traffic.

---

## 12.4 Routing ETA

**Routing ETA** is an estimated travel time produced by a road-routing system.

It may account for:

```text
Road Network
Traffic
Travel Restrictions
Route Geometry
```

The architecture should keep routing behind a travel/routing abstraction.

---

# 13. Travel Terminology

## 13.1 ETA

**ETA** means **Estimated Time of Arrival**.

In dispatch ranking, ETA represents the estimated time required for the driver to reach the pickup location.

The long-term ranking goal is:

```text
ETA
```

rather than relying only on:

```text
Straight-line Distance
```

---

## 13.2 Distance

**Distance** is a geographic measurement between two coordinates.

Distance and ETA are not interchangeable.

---

## 13.3 Travel Calculator

A **Travel Calculator** is the abstraction responsible for producing travel-related values used by the ranking system.

The implementation may evolve from simple geographic calculations toward routing-provider-backed ETA.

---

# 14. Driver State Terminology

## 14.1 Driver Availability

**Driver Availability** describes whether the driver is currently eligible to receive a new dispatch offer.

Availability is realtime operational state.

---

## 14.2 Driver Location

**Driver Location** is the driver's current geographic position.

It is high-frequency realtime information.

---

## 14.3 Heartbeat

A **Heartbeat** is a realtime signal indicating that a driver/device connection is still active.

Heartbeat expiration can be used to identify stale realtime state.

---

## 14.4 Connection State

**Connection State** represents the driver's current realtime communication status.

It should not automatically be treated as equivalent to business availability.

---

## 14.5 Driver Cache

The **Driver Cache** stores hot/realtime driver information required by the dispatch path.

It is not automatically the authoritative durable driver record.

---

# 15. Event Terminology

## 15.1 Domain Event

A **Domain Event** represents a meaningful state transition or business occurrence.

---

## 15.2 Application Event

An **Application Event** is an event used by the application/event-processing architecture to communicate a completed or requested operation.

---

## 15.3 Event Envelope

An **Event Envelope** is the common wrapper containing event metadata and payload.

Typical metadata includes:

```text
Event ID
Event Type
Aggregate ID
Occurred At
Payload
```

---

## 15.4 Event Broker

The **Event Broker** transports events between producers and consumers.

RideForge uses an event-broker architecture with Kafka-compatible infrastructure.

---

## 15.5 Producer

A **Producer** publishes events to the event broker.

---

## 15.6 Consumer

A **Consumer** receives and processes events from the event broker.

Consumers must account for duplicate delivery.

---

## 15.7 Outbox

The **Outbox** is a durable database-backed mechanism for storing event publication intent together with the business transaction.

---

## 15.8 Transactional Outbox

A **Transactional Outbox** means:

```text
Business State Change
+
Outbox Event
```

are committed atomically in the same transaction.

---

## 15.9 Processed Event

A **Processed Event** is an event for which consumption has already been recorded.

This supports idempotent event processing.

---

## 15.10 Dead-Letter Queue

A **Dead-Letter Queue (DLQ)** stores events that cannot be successfully processed through the normal retry path.

A DLQ is a recovery/diagnostic mechanism, not a normal event-processing path.

---

# 16. Data and Persistence Terminology

## 16.1 Durable State

**Durable State** is business state that must survive process or infrastructure restarts.

PostgreSQL is the primary durable datastore for the platform's business data.

---

## 16.2 Realtime State

**Realtime State** is rapidly changing operational information used by the dispatch path.

Redis is used for appropriate realtime/hot state.

---

## 16.3 Repository

A **Repository** is an application-facing abstraction for accessing durable domain/application data.

SQL and database-specific implementation details belong behind the repository boundary.

---

## 16.4 Cache

A **Cache** is a fast-access copy or representation of data used to reduce latency or backend load.

A cache is not automatically the authoritative source.

---

# 17. Pipeline Terminology

## 17.1 Stage

A **Stage** is one isolated operation within a candidate pipeline.

A stage generally receives:

```text
Pipeline Context
+
Candidate Collection
```

and performs one primary transformation, enrichment, filtering, or ordering responsibility.

---

## 17.2 Pipeline Context

The **Pipeline Context** contains shared execution information required by pipeline stages.

It should not become a general-purpose global state container.

Only relevant pipeline execution state belongs in it.

---

## 17.3 Candidate Collection

A **Candidate Collection** stores candidates being processed by the pipeline.

It provides the collection/iteration abstraction used by pipeline stages.

---

## 17.4 Iterator

An **Iterator** provides sequential candidate consumption without requiring callers to know the underlying collection representation.

---

## 17.5 Heap

A **Heap** is the data structure used by the candidate ordering stage to efficiently maintain ranked candidates.

The heap is an implementation detail of candidate ordering.

The dispatch engine should not depend on heap internals.

---

# 18. Bootstrap Terminology

## 18.1 Bootstrap

**Bootstrap** is the runtime composition layer responsible for constructing the application's dependencies.

It includes:

```text
Configuration
Infrastructure
Repositories
Caches
Strategies
Policies
Application Services
Handlers
Workers
```

---

## 18.2 Composition Root

The **Composition Root** is the place where concrete implementations are assembled and injected.

For RideForge this responsibility belongs to the bootstrap/container layer.

---

## 18.3 Builder

A **Builder** is a small composition helper used to construct a known component graph.

A builder should not contain business rules.

---

```text
H3 settings
```

## 19.2 Policy

A **Policy** represents a rule or decision mechanism that determines system behaviour.

Examples:

```text
Retry Policy

Dispatch Policy
```

# 20. Reliability Terminology

## 20.1 Idempotency

**Idempotency** means processing the same operation more than once does not produce unintended duplicate business effects.

---

## 20.2 Recovery

**Recovery** is the process of restoring operational state after failure.

---

## 20.3 Reconciliation

**Reconciliation** compares related state representations and repairs known inconsistencies.

---

## 20.4 Stale State

**Stale State** is realtime or derived state that is no longer valid because its freshness window has expired or its source state has changed.

---

## 20.5 TTL

**TTL** means **Time To Live**.

It defines how long a temporary/realtime record remains valid before expiration.

TTL is a safety mechanism and should not replace explicit lifecycle cleanup where explicit cleanup is required.

---

---

## 21.2 Trace

A **Trace** represents an end-to-end request or operation flow across system components.

---

## 21.3 Span

A **Span** represents one measurable operation within a trace.

Examples:


---

## 21.4 Structured Log

---

## 21.5 Cardinality

**Cardinality** describes the number of distinct values associated with a metric label or dimension.

# 22. Scaling Terminology

## 22.1 Hot Region

A **Hot Region** is a geographic area experiencing unusually high dispatch demand relative to available driver supply.

---

## 22.2 Hot Cell

A **Hot Cell** is an H3 cell classified as experiencing high demand or insufficient supply.

---

## 22.3 Supply

**Supply** represents available driver capacity.

---

## 22.4 Demand

**Demand** represents ride requests requiring service.

---

## 22.5 Supply/Demand Ratio

The **Supply/Demand Ratio** represents the relationship between available driver supply and ride demand for a geographic area.

It can become an input to future demand-aware dispatch and pricing policies.

---

## 22.6 Regional Partition

A **Regional Partition** divides the operating geography into bounded areas for scaling.

---

## 22.7 Cell Ownership

**Cell Ownership** means assigning responsibility for a subset of H3 cells to a dispatch node.

# 24. Business Strategy Terminology

## 24.1 Dispatch Strategy

A **Dispatch Strategy** determines how a ride is dispatched and how eligible driver candidates are prioritized for assignment.

RideForge currently supports two primary dispatch strategies:

```text
Smart Stand Dispatch
Smart Dispatch
```

The selected strategy is resolved from the applicable hierarchical configuration before dispatch execution begins.

A dispatch strategy is **not automatically a geographic boundary**. Candidate discovery may expand beyond the ride's originating location when the configured dispatch flow requires it.

---

## 24.2 Smart Stand Dispatch

**Smart Stand Dispatch** is a stand-preferred dispatch strategy.

When the rider is within the configured radius of an auto stand, the system gives preference to eligible drivers associated with that stand and applies the stand's queue/order rules.

The stand is a **preferred dispatch source, not an exclusive candidate boundary**.

Conceptually:

```text
Ride
 ↓
Rider inside configured stand radius?
 ├── YES
 │    ↓
 │  Prefer eligible drivers at that stand
 │    ↓
 │  Apply stand queue / ordering rules
 │    ↓
 │  Suitable driver available?
 │      ├── YES → dispatch through stand preference
 │      └── NO  → expand to broader eligible drivers
 │
 └── NO
      ↓
   Consider eligible nearby drivers normally
```

If the rider is outside the radius of all configured auto stands, Smart Stand Dispatch does not restrict the candidate pool to stand drivers.

Eligible nearby drivers may include:

```text
Drivers at auto stands
Drivers outside auto stands
Drivers from nearby locations
```

subject to candidate eligibility, geographic reachability, legal restrictions, and the applicable dispatch rules.

---

## 24.3 Smart Dispatch

**Smart Dispatch** is the stand-agnostic dispatch strategy that evaluates eligible available drivers near the rider without using auto-stand membership as a dispatch preference.

Typical dispatch factors include:

```text
Driver Eligibility
Driver Availability
Distance
ETA
Matching / Ranking Factors
Operational Constraints
```

Any eligible driver may be considered regardless of whether the driver is:

```text
At an auto stand
Outside an auto stand
Associated with another nearby location
```

---

## 24.4 AI-Assisted Dispatch

**AI-Assisted Dispatch** is an optimization capability applied to an existing dispatch strategy rather than a third primary dispatch strategy.

AI may assist with:

```text
Candidate Ranking
ETA Prediction
Acceptance Prediction
Demand / Supply Signals
Other Prediction or Optimization Signals
```

The relationship is:

```text
Resolve Dispatch Strategy
        ↓
Execute Strategy
        ↓
AI-assisted ranking / optimization where applicable
        ↓
Final Dispatch Decision
```

AI must not override hard eligibility, legal restrictions, safety constraints, or authoritative domain state.

---

## 24.5 Dispatch Strategy Resolution

**Dispatch Strategy Resolution** is the process of determining which dispatch strategy applies to a ride before dispatch execution.

The system evaluates the applicable configuration hierarchy from the most specific configuration level upward.

Conceptually:

```text
Most Specific Configuration
        ↓
Explicit Strategy?
   ├── YES → use it
   └── NO
        ↓
Parent Configuration
        ↓
Explicit Strategy?
   ├── YES → use it
   └── NO
        ↓
Continue upward
        ↓
System Default
```

The first explicit dispatch strategy found is the effective strategy for the ride.

---

## 24.6 Dispatch Configuration

A **Dispatch Configuration** is an explicitly configured dispatch strategy and its associated dispatch settings at a particular configuration level.

A configuration may exist at levels such as:

```text
State
District
City / Town
Rural Area
Auto Stand
Specific Ride Level
Other configured intermediate levels
```

Not every level needs an explicit configuration.

---

## 24.7 Configuration Hierarchy

The **Configuration Hierarchy** is the parent-child structure used to inherit dispatch configuration.

The hierarchy may contain geographic or operational levels such as:

```text
State
 ↓
District
 ↓
Town / City
 ↓
Rural Area
 ↓
Auto Stand
 ↓
Ride-level configuration
```

The exact hierarchy is configurable and must not be hard-coded to a fixed list of levels.

---

## 24.8 Configuration Inheritance

**Configuration Inheritance** means that a lower-level configuration uses the nearest explicitly configured parent strategy when no explicit strategy exists at the lower level.

The canonical rule is:

```text
Specific configuration overrides inherited configuration.
```

Example:

```text
District      → Smart Dispatch
Town A        → Smart Stand Dispatch
Town B        → No explicit configuration
```

Therefore:

```text
Ride in Town A → Smart Stand Dispatch
Ride in Town B → Smart Dispatch
```

The District configuration acts as the inherited default for Town B.

---

## 24.9 Explicit Configuration

An **Explicit Configuration** is a dispatch configuration directly defined at the current applicable configuration level.

An explicit configuration always takes precedence over a strategy inherited from a parent level.

---

## 24.10 Effective Dispatch Strategy

The **Effective Dispatch Strategy** is the strategy obtained after resolving the configuration hierarchy for a specific ride.

Example:

```text
Town A
 ↓
Explicitly configured:
Smart Stand Dispatch

Effective Strategy:
Smart Stand Dispatch
```

The effective strategy is what the dispatch engine executes.

---

## 24.11 Auto Stand

An **Auto Stand** is a configured physical or logical stand associated with a geographic area and potentially a driver queue/order.

An auto stand may provide a preferred driver source when the rider is within its configured stand radius under Smart Stand Dispatch.

An auto stand is not necessarily an exclusive boundary for driver eligibility.

---

## 24.12 Stand Radius

A **Stand Radius** is the configured geographic boundary used to determine whether a ride pickup is considered to be within an auto stand's service area.

It is distinct from:

```text
Driver Search Radius
Location Expansion Radius
```

These values may be configured independently.

---

## 24.13 Stand Preference

**Stand Preference** is the prioritization applied by Smart Stand Dispatch when the rider is within the radius of a configured auto stand.

Stand preference means:

```text
Prefer eligible drivers from the relevant stand first.
```

It does not mean:

```text
Reject all drivers outside the stand.
```

If suitable stand drivers are unavailable, the dispatch flow may expand to other eligible drivers according to the configured rules.

---

## 24.14 Candidate Discovery Scope

**Candidate Discovery Scope** defines the geographic and operational area from which driver candidates may be discovered.

Candidate discovery scope is separate from dispatch strategy.

For example:

```text
Dispatch Strategy
    = Smart Stand Dispatch

Candidate Discovery
    = Stand-preferred local search
      followed by broader search when required
```

or:

```text
Dispatch Strategy
    = Smart Dispatch

Candidate Discovery
    = Normal eligible nearby-driver search
```

---

## 24.15 Cross-Location Dispatch

**Cross-Location Dispatch** occurs when a ride originating in one configured location considers eligible drivers associated with another nearby location because the originating location cannot provide a suitable driver.

Example:

```text
Location A
Smart Dispatch
    ↓
No suitable local driver
    ↓
Expand search
    ↓
Location B
Smart Stand Dispatch
    ↓
Evaluate eligible drivers from B
```

The strategy configured for Location B determines how its local driver context is prioritized, but Location B is not automatically excluded from serving the ride.

Cross-location candidate consideration must still respect:

```text
Driver Eligibility
Availability
Distance / ETA
Legal / Regional Rules
Service Constraints
Other Dispatch Constraints
```

---

## 24.16 Strategy Execution

**Strategy Execution** is the process of applying the already-resolved dispatch strategy to the discovered and eligible candidates.

The architectural separation is:

```text
Configuration Hierarchy
        ↓
Dispatch Strategy Resolution
        ↓
Strategy Execution
        ↓
Candidate Discovery / Processing
        ↓
Prioritization / Ranking
        ↓
Assignment
```

The configuration hierarchy determines **which strategy applies**.

The strategy determines **how candidates are prioritized and dispatched**.

Candidate discovery determines **which drivers can enter the candidate flow**.

These responsibilities must not be conflated.

---

## 24.17 Dispatch Strategy Is Not a Candidate Boundary

A dispatch strategy should not automatically be interpreted as a hard geographic or organizational boundary.

For example:

```text
Location A
Smart Dispatch
```

may eventually consider:

```text
Eligible Driver from Location B
```

if the configured candidate discovery process expands to Location B.

Similarly:

```text
Location A
Smart Stand Dispatch
```

may consider non-stand drivers when the preferred stand cannot provide a suitable driver.

Therefore:

```text
Dispatch Strategy
≠
Candidate Pool Boundary
```

---

## 24.18 Strategy-Specific Prioritization

**Strategy-Specific Prioritization** defines how candidates are preferred after the applicable strategy has been resolved.

For Smart Stand Dispatch, this may include:

```text
Relevant Auto Stand
Stand Queue / Ordering
Driver Eligibility
Availability
Distance / ETA
Other configured factors
```

For Smart Dispatch, this may include:

```text
Driver Eligibility
Availability
Distance
ETA
Ranking Factors
Other configured factors
```

The exact ordering and weighting are defined by the applicable business and ranking rules.

# 25. Region Terminology

## 25.1 Operating Region

An **Operating Region** is a geographic/business area in which RideForge operates under a defined set of operational and legal rules.

---

## 25.2 Cross-Region Ride

A **Cross-Region Ride** is a ride where pickup and/or destination crosses an operating-region boundary.

Whether such a ride is permitted is a business/legal rule and must not be inferred solely from geographic proximity.

---

# 26. State vs Event

These concepts must not be confused.

A:

```text
State
```

describes the current condition of an entity.

An:

```text
Event
```

describes something that happened or was requested.

Example:

```text
Driver State:
AVAILABLE

Event:
DriverBecameAvailable
```

The event may cause a state transition, but it is not the state itself.

---

# 27. Policy vs Mechanism

A **Policy** decides what should happen.

A **Mechanism** performs it.

Example:

```text
Retry Policy
    ↓ decides
Offer Batch = 3

Matching Engine
    ↓ executes
Reserve up to 3 candidates
```

Do not put policy formulas into mechanisms when the policy already has an explicit owner.

---

# 28. Candidate vs Driver

A **Driver** is a domain entity.

A **Candidate** is a dispatch-context representation of a driver being considered for a specific ride.

Therefore:

```text
Driver ≠ Candidate
```

A candidate can contain:

```text
Driver reference/data
Ride-specific context
Score
Pipeline state
```

---

# 29. Availability vs Reservation

These terms must remain separate.

```text
Availability
    = candidate appears eligible

Reservation
    = driver is authoritatively claimed
```

Availability is a snapshot.

Reservation is a concurrency operation.

---

# 30. Distance vs ETA

These terms must remain separate.

```text
Distance
    = geographic measurement

ETA
    = estimated travel time
```

A closer driver is not necessarily the fastest driver to the pickup point.

---

# 31. Search Radius vs Ring

These are related but different concepts.

```text
Search Radius
    = distance/policy boundary

Ring
    = H3 expansion level
```

A discovery strategy may translate between them.

They should not be used as synonyms in architecture documentation.

---

# 32. Discovery vs Ranking

These responsibilities are different.

```text
Discovery
    = find geographically relevant candidates

Ranking
    = order eligible candidates by dispatch preference
```

Discovery should not contain ranking formulas.

Ranking should not perform global geographic discovery.

---

# 33. Filtering vs Ranking

Filtering answers:

```text
Should this candidate continue?
```

Ranking answers:

```text
Among candidates that continue, which is preferable?
```

A filter should generally produce inclusion/exclusion, while a ranker produces ordering/score.

---

# 34. Reservation vs Offer

These are different lifecycle operations.

```text
Reservation
    = claim driver concurrency slot

Offer
    = communicate opportunity to driver
```

A driver should normally be reserved before the offer is created.

---

# 35. Outbox vs Event Broker

These are not the same.

```text
Outbox
    = durable publication intent

Event Broker
    = event transport
```

The outbox protects transactional consistency.

The broker transports events.

---

# 36. Cache vs Index

A **Cache** primarily provides fast access to data.

An **Index** organizes data to support efficient lookup.

In RideForge:

```text
Driver Cache
    = realtime driver data

H3 Index
    = spatial driver lookup
```

The same infrastructure technology may technically support both, but their responsibilities remain different.

---

# 37. Canonical Vocabulary for AI Agents

AI coding agents must use these terms consistently.

When the codebase already contains a canonical term:

```text
Use the canonical term.
```

Do not rename it to a more generic or personally preferred synonym without an explicit architectural reason.

---

# 38. AI Agent Terminology Rules

Before changing names, an AI agent must determine:

1. Is the existing name already part of the canonical vocabulary?
2. Is it referenced by architecture documentation?
3. Is it part of a public/internal interface?
4. Would changing it create terminology drift?
5. Is the proposed name actually clearer?

If the answer indicates that the existing name is intentional, preserve it.

---

# 39. Terminology Change Process

A terminology change should be treated as an architectural/documentation change when it affects established concepts.

Process:

```text
Identify ambiguity
      ↓
Choose canonical term
      ↓
Update code
      ↓
Update architecture docs
      ↓
Update business docs
      ↓
Update AI instructions
      ↓
Search for obsolete terminology
```

Do not leave two competing names for the same concept.
