# RideForge — Architecture Principles

> **Document:** `docs/00-project/3.ARCHITECTURE_PRINCIPLES.md`  
> **Status:** Active  
> **Scope:** Architectural principles governing the RideForge platform  
> **Related:** `1.PROJECT_VISION.md`, `2.SYSTEM_GOALS.md`, `4.ROADMAP.md`, `5.TERMINOLOGY.md`

---

# 1. Purpose

This document defines the principles that govern how RideForge is designed, extended, reviewed, and maintained.

These principles are intended to prevent architectural drift as the system grows and as additional developers and AI coding agents contribute to the codebase.

The principles describe:

- how responsibilities are separated,
- how dependencies should flow,
- how infrastructure is isolated,
- how business rules are represented,
- how performance is approached,
- how the system should evolve.

---

# 2. Correctness Before Optimization

The first architectural priority is correctness.

The system must preserve:

```text
Ride correctness
Driver correctness
Reservation correctness
Transaction correctness
Event correctness
```

before optimizing for latency or infrastructure cost.

Preferred order:

```text
Correctness
    ↓
Observability
    ↓
Measured bottleneck
    ↓
Targeted optimization
```

An optimization that creates race conditions, inconsistent state, or unreliable events is not considered an improvement.

---

# 3. Clear Responsibility Boundaries

Every major responsibility should have a clear owner.

Examples:

```text
Geo Discovery
    → CandidateSearcher / discovery subsystem

Candidate Processing
    → Candidate Pipeline

Ranking
    → Ranker

Retry Policy
    → RetryPolicy

Reservation
    → DriverLocker

Durable State
    → Repositories / PostgreSQL

Event Publication Intent
    → Outbox

Event Transport
    → Event infrastructure
```

A component should not absorb unrelated responsibilities merely because it is convenient.

---

# 4. Single Responsibility at the Module Level

Modules should have one primary reason to change.

For example:

```text
Ranking
```

should change when ranking policy changes.

It should not change because:

```text
Redis commands changed
Kafka configuration changed
Driver reservation changed
```

Likewise:

```text
Geo discovery
```

should not contain:

```text
Offer creation
Ranking formulas
Ride state transitions
```

---

# 5. Explicit Dependency Direction

Dependencies should flow toward abstractions and domain/application contracts.

Preferred:

```text
Bootstrap
   ↓
Application
   ↓
Domain / Contracts
   ↑
Infrastructure implementations
```

Infrastructure details should not leak into business logic.

---

# 6. Dependency Injection

Runtime dependencies should be assembled explicitly.

The bootstrap layer is responsible for composition.

Conceptually:

```text
Infrastructure
     ↓
Adapters
     ↓
Application Services
     ↓
Handlers / Workers
```

Components should receive dependencies through constructors or explicit contracts rather than creating infrastructure internally.

---

# 7. Infrastructure Isolation

Application logic should not directly depend on:

```text
Redis commands
PostgreSQL SQL
Kafka producer internals
H3 library calls
HTTP routing-provider SDKs
```

when an application-facing abstraction already exists.

Preferred:

```text
Application
    ↓
Interface
    ↓
Infrastructure Adapter
```

This keeps the core architecture replaceable and testable.

---

# 8. Small Interfaces

Interfaces should describe the smallest capability required by a consumer.

For example:

```text
LoadDrivers(...)
```

should not require a consumer to depend on an entire Redis cache implementation.

Small interfaces improve:

- testability,
- clarity,
- replacement,
- dependency ownership.

Do not create interfaces merely for every concrete type.

An interface should exist where it provides a meaningful boundary.

---

# 9. Reuse Existing Contracts

Before creating a new abstraction, inspect the current codebase.

If an existing contract already represents the required responsibility:

```text
Reuse it.
```

Do not create parallel interfaces such as:

```text
NewCandidateSearcher
AlternativeCandidateSearcher
AdvancedCandidateSearcher
```

when the existing `CandidateSearcher` already provides the required boundary.

---

# 10. No Duplicate Architecture

A roadmap item does not automatically require a new implementation.

Before adding a component:

```text
Does this capability already exist?
```

If yes:

```text
Extend or complete the existing implementation.
```

Do not create duplicate subsystems just to represent a roadmap phase.

---

# 11. Domain Rules Must Be Explicit

Important business rules should not be hidden inside infrastructure code.

Rules such as:

```text
Ride eligibility
Driver eligibility
Regional restrictions
Matching limits
Retry policy
```

should have explicit application/domain ownership.

Infrastructure should execute the rule's required data operations, not silently define the business policy.

---

# 12. Business Rules Before Infrastructure

The architecture should distinguish:

```text
What is allowed?
```

from:

```text
How is it stored?
```

For example:

```text
Ride is allowed between regions
```

is a business rule.

```text
Region stored in PostgreSQL
```

is an infrastructure/data concern.

The two must not become tightly coupled.

---

# 13. Transaction Boundaries Must Be Explicit

Operations that require atomicity must have clear transaction ownership.

For example:

```text
Offer Record
+
Outbox Event
```

should be committed consistently.

Transactions should not be hidden inside unrelated lower-level helpers when the application operation needs to coordinate multiple writes.

---

# 14. Transactional Outbox

Important asynchronous state transitions should use the outbox pattern where transactional consistency is required.

Preferred:

```text
Application Operation
      │
      ▼
Database Transaction
 ├── State Change
 └── Outbox Record
      │
      ▼
Commit
      │
      ▼
Event Publisher
```

The application should not depend on:

```text
Database commit
     then
Kafka publish
```

as two unrelated operations when both represent one logical state transition.

---

# 15. Event-Driven Communication

Events should be used where asynchronous decoupling is beneficial.

Events are appropriate for:

- ride lifecycle transitions,
- driver offer delivery,
- driver responses,
- asynchronous processing,
- integration between independently evolving components.

Events should not be introduced merely to make simple synchronous logic appear distributed.

---

# 16. Event Contracts Are Stable Boundaries

Events should have explicit contracts.

An event should clearly define:

```text
Event Type
Event ID
Aggregate
Payload
Occurred Time
```

Consumers should not depend on undocumented internal implementation details.

Changes to event contracts must be treated as compatibility-sensitive changes.

---

# 17. Idempotency

Distributed consumers must assume events may be delivered more than once.

Therefore:

```text
At-least-once delivery
```

must not cause:

```text
Duplicate business effects
```

where the operation is intended to be idempotent.

Existing processed-event and state-based safeguards should be reused.

---

# 18. Concurrency Ownership

Every concurrency-sensitive resource must have a clear owner.

For driver dispatch:

```text
Candidate discovery
     ↓
Availability snapshot
     ↓
Reservation
```

Reservation is the authoritative ownership boundary.

Discovery must not attempt to provide ownership guarantees that only reservation can provide.

---

# 19. Snapshot vs Authority

A system component that reads state should not automatically be treated as the authority over that state.

Examples:

```text
Candidate availability
    → snapshot

Driver reservation
    → authority

Redis driver cache
    → realtime state

PostgreSQL durable ride state
    → durable business authority
```

This distinction is important for concurrency and recovery.

---

# 20. Bounded Work

Critical-path operations should be bounded.

Examples:

```text
Maximum candidate count
Maximum search radius
Maximum search rings
Maximum retry attempts
Offer batch size
Lock TTL
```

The system should avoid unbounded loops and unbounded candidate populations.

---

# 21. Progressive Search

Geographic discovery should search progressively.

Preferred:

```text
Ring 0
  ↓
Enough?
  ├── Yes → stop
  └── No
       ↓
Ring 1
       ↓
...
```

This principle minimizes unnecessary geographic and infrastructure work.

---

# 22. Batch Data Access

When multiple records are required, prefer batch operations.

Avoid:

```text
candidate 1 → Redis
candidate 2 → Redis
candidate 3 → Redis
```

when the required data can be loaded through:

```text
one batch operation
```

Batching reduces:

- network round trips,
- latency,
- connection pressure,
- infrastructure overhead.

---

# 23. Local Computation After Enrichment

After required candidate data has been loaded, feature extraction and scoring should prefer local computation.

Preferred:

```text
Batch Load
   ↓
In-memory Features
   ↓
Normalization
   ↓
Scoring
```

Avoid repeated network calls inside ranking calculations.

---

# 24. Avoid Premature Routing Calls

Routing and ETA calculations can be expensive.

The system should narrow the candidate population before performing expensive travel calculations.

Preferred:

```text
H3
 ↓
Filtering
 ↓
Small candidate set
 ↓
ETA
 ↓
Ranking
```

rather than:

```text
All drivers
 ↓
Routing
```

---

# 25. Performance Through Elimination

The primary performance strategy should be to eliminate unnecessary work.

Examples:

```text
H3 eliminates distant drivers
Candidate filters eliminate invalid drivers
Batch loading eliminates repeated cache access
Ranking only processes eligible candidates
Reservation only processes selected candidates
```

This is preferred over prematurely adding infrastructure solely to handle work that should not have been performed.

---

# 26. Hot Path Awareness

The ride-matching path is latency-sensitive.

Critical-path code should avoid:

- unnecessary allocations,
- blocking sleeps,
- repeated database queries,
- repeated Redis calls,
- unbounded loops,
- expensive logging,
- unnecessary serialization.

Non-critical work should be moved to asynchronous processing where appropriate.

---

# 27. Asynchronous Timeout Handling

Offer timeouts should not block matching workers.

Avoid:

```text
Matching Worker
    ↓
Sleep 15 seconds
```

Preferred:

```text
Offer
  ↓
Timeout Scheduler
  ↓
Timeout Event
```

This keeps workers available for other operations.

---

# 28. Realtime State vs Durable State

Realtime operational state and durable business state have different requirements.

Conceptually:

```text
Redis
  → fast-changing operational state

PostgreSQL
  → durable business state
```

The system should not force every high-frequency update into the durable database.

Likewise, Redis should not silently become the only source of durable business truth.

---

# 29. Cache Is Not Automatically Authority

A cache may contain the latest operational information without being the durable source of truth.

If cache state is lost, the system should have a defined recovery or reconciliation path.

Important state should have a clear authoritative source.

---

# 30. Recovery Must Be Designed

Every important derived/realtime index should have a recovery strategy.

For example:

```text
Database / durable state
       ↓
Recovery
       ↓
Redis / H3 index
```

Recovery should be deterministic and observable.

---

# 31. Reconciliation

Long-running systems accumulate inconsistencies.

Where appropriate, background reconciliation should compare:

```text
Realtime State
+
Indexes
+
Durable State
```

and repair known inconsistencies.

Reconciliation must be bounded and observable.

---

# 32. Stale State Cleanup

Realtime systems must remove stale state.

Examples:

```text
Offline driver
Expired heartbeat
Expired connection
Expired reservation
Expired location
```

TTL and cleanup workers should complement one another.

---

# 33. Configuration as Policy

Configuration should hold values that are expected to vary by:

- environment,
- deployment,
- operational policy,
- business configuration.

Examples:

```text
Ranking weights
Retry limits
H3 settings
Lock TTL
Realtime TTL
Density thresholds
```

Configuration should not be used to hide structural design problems.

---

# 34. No Hard-Coded Business Policy

If a value represents a real business or operational policy, it should not be silently hard-coded inside a calculator or service.

For example:

```text
Quality weight
Retry threshold
Offer timeout
Density threshold
```

should come from the appropriate configuration/policy boundary.

---

# 35. Configuration Does Not Replace Validation

Passing configuration into a component does not remove the need to validate it.

Invalid policy should be detected as early as practical.

Prefer:

```text
Load Configuration
     ↓
Validate
     ↓
Build Components
     ↓
Run Application
```

rather than discovering invalid values deep inside a request.

---

# 36. Composition Root

Bootstrap is responsible for assembling the application.

The composition root should answer:

```text
Which implementation is used?
What dependencies does it receive?
Which configuration applies?
```

Business logic should not answer these questions.

---

# 37. Bootstrap Should Not Become Business Logic

The container/bootstrap layer may construct:

```text
Repositories
Caches
Strategies
Policies
Pipelines
Services
Handlers
```

but it should not implement:

```text
Ride matching rules
Ranking formulas
Driver eligibility
Retry algorithms
```

Those belong to their respective modules.

---

# 38. Builder Usage

Builders may be used to keep the composition root readable when dependency graphs become large.

A builder should:

```text
Construct a known component graph
```

not:

```text
Hide business logic
```

Builders should remain small and explicit.

---

# 39. Package Ownership

Packages should follow responsibility boundaries rather than arbitrary technical layers.

For example:

```text
dispatch/
  candidate/
  discovery/
  ranking/
```

groups related dispatch capabilities.

Avoid scattering one feature across unrelated packages without a strong reason.

---

# 40. Candidate Pipeline Isolation

Candidate processing should remain independently composable.

The intended flow is:

```text
Discovery
   ↓
Enrichment
   ↓
Validation
   ↓
Duplicate Filtering
   ↓
Availability
   ↓
Already Offered
   ↓
Ranking
   ↓
Heap / Ordered Source
```

Each stage should have one primary responsibility.

---

# 41. Ranking Isolation

Ranking should be independent of:

```text
Redis commands
reservation
Kafka
ride state transitions
```

It should consume prepared features and produce a score.

This keeps ranking replaceable and testable.

---

# 42. Geo Isolation

Geographic discovery should be independent of:

```text
offer creation
reservation
ranking policy
ride lifecycle
```

Its job is to identify geographically relevant candidates.

---

# 43. Reservation Isolation

Reservation should be treated as its own concurrency boundary.

The reservation implementation may use Redis today, but the application should depend on a locker abstraction.

This allows the implementation to evolve without changing dispatch orchestration.

---

# 44. Repository Isolation

Application services should depend on repository contracts.

SQL should remain inside repository/infrastructure implementations.

Do not embed SQL statements inside application services.

---

# 45. Observability as a First-Class Concern

Metrics, tracing, and structured logs should be part of important production paths.

However, observability code should not become the owner of business logic.

Preferred:

```text
Business Operation
      │
      ├── Metric
      ├── Trace
      └── Structured Log
```

rather than embedding operational decisions inside metrics code.

---

# 46. Low-Cardinality Metrics

Metrics labels must remain bounded.

Avoid labels such as:

```text
ride_id
driver_id
request_id
```

unless there is a deliberate and justified observability design for them.

High-cardinality identifiers belong primarily in logs/traces.

---

# 47. Tracing Boundaries

Tracing should follow meaningful operations.

Examples:

```text
Matching
Candidate Discovery
Candidate Pipeline
Ranking
Reservation
Event Handling
```

Spans should provide enough context to understand latency and failures.

---

# 48. Structured Logging

Logs should contain structured fields instead of concatenated strings.

Useful fields include:

```text
ride_id
driver_id
attempt
radius
candidate_count
result
```

Logs should describe meaningful transitions and failures.

---

# 49. Error Semantics

Errors should preserve meaning.

Different states should remain distinguishable:

```text
No Candidate
Candidate Rejected
Reservation Lost Race
Infrastructure Failure
Transaction Failure
Event Publication Failure
```

Do not collapse all failures into generic errors.

---

# 50. Failure Cleanup

When an operation partially succeeds, cleanup must be explicit.

Example:

```text
Reserve Driver
      ↓
Offer Persistence Fails
      ↓
Release Reservation
```

Partial failure paths are part of the normal architecture and should not be treated as rare afterthoughts.

---

# 51. Testing as an Architectural Contract

Tests should verify important contracts, not merely implementation details.

Priority should be given to:

```text
Business rules
Concurrency boundaries
Pipeline behaviour
Ranking behaviour
Transaction behaviour
Event contracts
Failure cleanup
```

Tests should remain resilient to internal refactoring.

---

# 52. Unit vs Integration Tests

Use unit tests for:

```text
Pure calculations
Policies
Filters
Ranking
Small transformations
```

Use integration tests for:

```text
Redis behaviour
PostgreSQL transactions
Outbox
Event processing
H3 index
Cross-component flows
```

Do not replace all integration tests with mocks.

---

# 53. Performance Testing

Performance claims should be supported by measurement.

Do not optimize based solely on assumptions such as:

```text
This Redis operation must be slow.
This abstraction must be expensive.
This data structure must allocate too much.
```

Measure first when the optimization is material.

---

# 54. Evolution Over Rewriting

The architecture should evolve incrementally.

Preferred:

```text
Existing Component
       ↓
Measured Limitation
       ↓
Targeted Extension
       ↓
Compatibility
       ↓
Migration
```

Avoid rewriting a working subsystem merely because a newer design appears cleaner.

---

# 55. Backward Compatibility Within the Codebase

When replacing an implementation:

1. define the new contract,
2. migrate consumers,
3. remove obsolete code,
4. update tests,
5. update documentation.

Do not leave large amounts of dead commented-out code.

Version control already preserves history.

---

# 56. Dead Code Policy

Commented-out legacy implementations should not remain indefinitely.

If the code is no longer active:

```text
Delete it.
```

If something from it is still needed:

```text
Extract the required behaviour
        ↓
Implement it in the current design
        ↓
Delete the obsolete code
```

Do not use commented code as a second implementation.

---

# 57. Documentation Is Part of Architecture

Architectural changes must be documented.

Documentation should explain:

```text
Goal
Responsibility
Design
Dependencies
Current state
Constraints
Future direction
```

Documentation should be updated as the architecture changes.

---

# 58. Architecture Decision Records

Important architectural decisions should be captured as ADRs.

Examples:

```text
Why H3?
Why Redis for realtime state?
Why transactional outbox?
Why the selected event broker?
Why a particular reservation mechanism?
```

ADRs record the reasoning, not just the final implementation.

---

# 59. AI Agent Compatibility

AI agents are treated as development contributors.

They must be able to determine:

```text
What exists
What owns it
Why it exists
What must not change
What is planned
```

AI-specific instructions should reference canonical architecture and business documents.

---

# 60. AI Agent Must Inspect Before Modifying

Before creating or modifying an architectural component, an AI agent should inspect:

```text
Relevant interface
Existing implementation
Bootstrap composition
Tests
Configuration
Related documentation
```

The agent must not assume that a roadmap item is unimplemented.

---

# 61. AI Agent Must Reuse Before Creating

Before adding a new file or abstraction, the agent should ask:

```text
Does an existing component already provide this capability?
```

If yes, extend or reuse it.

Only create a new abstraction when there is a genuine responsibility boundary.

---

# 62. No Phase-Driven Overengineering

Project phases are planning tools.

They are not a reason to add artificial code.

If:

```text
Phase item already exists
```

then:

```text
Mark it complete.
```

Do not create a new interface, wrapper, metric, or service solely to claim completion.

---

# 63. Production Grade Does Not Mean Maximum Complexity

Production-grade architecture means:

```text
Correct
Observable
Reliable
Maintainable
Performant
Understandable
```

It does not mean:

```text
Maximum number of services
Maximum number of interfaces
Maximum abstraction depth
Maximum infrastructure
```

The simplest design that satisfies the production requirement is preferred.

---

# 64. Security and Data Boundaries

Sensitive operational or user data should not be unnecessarily propagated across components.

Logs, traces, metrics, and events should contain only the data required for their purpose.

Infrastructure credentials and secrets must remain outside source code.

---

# 65. Regional Constraints

Regional business/legal rules must remain explicit.

A geographic location does not automatically determine whether a ride is legally or operationally permitted.

The architecture should therefore distinguish:

```text
Geographic Discovery
```

from:

```text
Ride Eligibility / Business Rules
```

---

# 66. Strategy Flexibility

Where business operations may require multiple dispatch models, the architecture should expose an explicit strategy boundary.

For example:

```text
Stand Dispatch
       +
Smart Dispatch
```

Both may coexist while sharing common ride, driver, reservation, and event infrastructure.

The selected strategy should not force unrelated modules to know the details of every strategy.

---

# 67. Cost-Aware Architecture

Infrastructure decisions should consider both:

```text
Performance
+
Operating Cost
```

A more expensive technology is not automatically better.

The chosen implementation should satisfy the required scale and reliability while avoiding unnecessary operational cost.

---

# 68. Avoid Distributed Systems Complexity Without Need

Distributed coordination should be introduced only when the scale or reliability requirement justifies it.

Prefer:

```text
Simple local ownership
```

until there is a measured need for:

```text
Distributed ownership
Regional coordination
Cross-node consensus
```

---

# 69. Clear Ownership of Future Scaling

Future scaling responsibilities should be introduced at explicit boundaries.

For example:

```text
Regional Partition
       ↓
H3 Cell Ownership
       ↓
Local Dispatch
```

should evolve from the existing discovery/dispatch architecture rather than bypassing it.

---

# 70. Principle for New Components

A new component should normally be justified by at least one of:

- a distinct business responsibility,
- a distinct infrastructure boundary,
- a distinct concurrency boundary,
- a distinct replacement/evolution boundary,
- a meaningful testability boundary.

If none apply, the new component may be unnecessary.

---

# 71. Architecture Review Checklist

Before merging a significant architectural change, verify:

```text
[ ] Responsibility is clear
[ ] Existing components were inspected
[ ] Existing contracts are reused where appropriate
[ ] Dependency direction remains correct
[ ] Business rules remain explicit
[ ] Infrastructure remains isolated
[ ] Transaction boundaries remain correct
[ ] Concurrency boundaries remain correct
[ ] Failure cleanup is handled
[ ] Observability is sufficient
[ ] Tests cover the important contract
[ ] Documentation is updated
[ ] No obsolete commented code remains
[ ] No roadmap-driven overengineering was introduced
```

---

# 72. Final Principles

The RideForge architecture follows these core principles:

1. **Correctness before optimization.**
2. **Clear ownership before abstraction.**
3. **Small, meaningful interfaces.**
4. **Explicit dependency direction.**
5. **Infrastructure stays behind contracts.**
6. **Business rules remain explicit.**
7. **Reservation is the concurrency authority.**
8. **Transactions protect atomic business operations.**
9. **Outbox protects database-to-event consistency.**
10. **Candidate work remains bounded.**
11. **Batch expensive operations where possible.**
12. **Use H3 before expensive geographic refinement.**
13. **Use ETA for travel-aware ranking rather than relying only on distance.**
14. **Configuration owns variable policy.**
15. **Observability is part of production design.**
16. **Recovery and reconciliation are deliberate capabilities.**
17. **Existing components are reused before new ones are created.**
18. **Roadmap phases do not justify artificial complexity.**
19. **Dead code is removed rather than commented out.**
20. **Documentation and ADRs preserve architectural intent.**
21. **AI agents must follow the established architecture.**
22. **Production grade means appropriate complexity, not maximum complexity.**
