# RideForge — System Goals

> **Document:** `docs/00-project/2.SYSTEM_GOALS.md`  
> **Status:** Active  
> **Scope:** System-level goals and engineering outcomes for RideForge  
> **Related:** `1.PROJECT_VISION.md`, `3.ARCHITECTURE_PRINCIPLES.md`, `4.ROADMAP.md`, `5.TERMINOLOGY.md`

---

## 1. Purpose

This document defines the system-level goals that guide the design and implementation of RideForge.

The goals describe **what the system must achieve**. They do not prescribe the implementation of individual components.

Implementation decisions should be evaluated against these goals.

---

# 2. Primary System Goal

RideForge should provide a production-grade ride-hailing dispatch platform capable of efficiently discovering, evaluating, matching, reserving, and offering rides to drivers while remaining:

- scalable,
- reliable,
- observable,
- geographically efficient,
- concurrency-safe,
- maintainable,
- cost-conscious,
- adaptable to different dispatch strategies.

The system should be capable of evolving from the current deterministic dispatch implementation toward more intelligent, data-driven dispatch without requiring a fundamental rewrite.

---

# 3. Dispatch Efficiency

The dispatch system should identify suitable drivers with low latency.

The target flow is:

```text
Ride Request
    ↓
Candidate Discovery
    ↓
Candidate Enrichment
    ↓
Candidate Filtering
    ↓
Candidate Ranking
    ↓
Driver Reservation
    ↓
Driver Offer
```

The system should avoid unnecessary work at every stage.

In particular:

- do not inspect the entire driver population,
- do not repeatedly fetch the same driver data,
- do not perform expensive routing calculations before narrowing candidates,
- do not rank drivers that are already known to be ineligible,
- do not perform unnecessary Redis operations.

---

# 4. Geographic Efficiency

Geographic discovery should be significantly more efficient than a global driver scan.

The system should use a spatial indexing strategy based on H3.

The intended direction is:

```text
Pickup
  ↓
H3 Cell
  ↓
Adaptive Ring Expansion
  ↓
Driver Index
  ↓
Candidate IDs
  ↓
Optional Geographic Refinement
```

The search should expand only as much as necessary to obtain a useful candidate population.

---

# 5. Adaptive Candidate Discovery

Candidate discovery should adapt to local supply conditions.

The system should distinguish between situations such as:

```text
Dense driver area
        ↓
Small search

Sparse driver area
        ↓
Broader search
```

The goal is to reduce unnecessary geographic search in high-supply areas while still providing useful coverage in low-supply areas.

Search behaviour must remain bounded.

---

# 6. Candidate Quality

Geographic proximity alone should not determine the best driver.

The system should progressively evaluate candidates using multiple signals.

The intended direction is:

```text
Geographic relevance
        ↓
Availability
        ↓
Driver quality
        ↓
Travel / ETA
        ↓
Fairness
        ↓
Final ranking
```

The ranking system should favour the candidate most likely to provide a successful dispatch outcome rather than simply the candidate with the smallest geographic distance.

---

# 7. ETA-Oriented Dispatch

The long-term primary travel signal should be estimated arrival time rather than straight-line distance.

The system should be capable of evolving from:

```text
Distance
```

toward:

```text
Road distance
+
Traffic
+
Routing
=
ETA
```

The architecture should therefore isolate travel calculations from the rest of ranking so that routing providers can be introduced without redesigning dispatch orchestration.

---

# 8. Driver Quality

The dispatch system should account for meaningful driver performance information.

The quality model should be capable of incorporating signals such as:

```text
Acceptance Rate
Cancellation Rate
Timeout Rate
Rating
Completed Trips
```

Additional quality signals may be introduced when reliable data and a clear product requirement exist.

Quality calculations should be configuration-driven where business policy is configurable.

---

# 9. Fair Dispatch

The system should avoid repeatedly selecting the same drivers when other eligible drivers are available.

Fairness may consider:

```text
Idle Time
Last Assigned Time
```

Fairness must remain a controlled ranking influence.

It must not override fundamental dispatch requirements such as:

- driver eligibility,
- availability,
- reservation correctness,
- reasonable travel time.

---

# 10. Demand-Aware Dispatch

The architecture should support demand-aware ranking and dispatch.

The system should eventually be able to consider relationships between:

```text
Demand
+
Driver Supply
+
Geographic Cell
```

to improve driver selection and dispatch outcomes.

The architecture should support this evolution without requiring demand logic to be embedded into unrelated components.

---

# 11. Concurrency Safety

The system must remain correct when multiple rides compete for the same drivers.

The key rule is:

```text
Candidate Discovery
        ↓
Eligibility Snapshot
        ↓
Reservation
```

Discovery and filtering do not guarantee ownership.

Reservation is the authoritative concurrency boundary.

A driver that appears available may become unavailable before reservation. The system must handle this safely and continue with another candidate where appropriate.

---

# 12. Reservation Correctness

Driver reservation should prevent conflicting dispatch operations from simultaneously claiming the same driver.

The reservation mechanism should provide:

- concurrency protection,
- bounded lock lifetime,
- explicit release,
- failure cleanup,
- safe behaviour under concurrent matching.

TTL-based protection should complement explicit lifecycle management rather than replace it.

---

# 13. Reliable Event Processing

Ride-hailing operations involve asynchronous events.

The system should support reliable event-driven communication for important state transitions.

The architecture should provide:

```text
Application State
      ↓
Transactional Outbox
      ↓
Event Broker
      ↓
Consumers
```

Events must not depend on an unreliable sequence where database state commits successfully but event publication is lost.

---

# 14. Transactional Consistency

Operations that require database consistency should be performed within appropriate transaction boundaries.

For dispatch offers, the intended relationship is:

```text
Transaction
 ├── Persist Offer Attempt
 └── Persist Outbox Event
        ↓
      Commit
        ↓
 Event Publication
```

This reduces the risk of inconsistent application state.

---

# 15. Idempotent Event Handling

Distributed event processing must tolerate duplicate delivery.

The system should therefore support idempotent handling through appropriate mechanisms such as:

```text
Processed Event Tracking
+
Persistent State Checks
+
Transactional Updates
```

Exactly-once delivery should not be assumed at the application level.

---

# 16. Failure Isolation

Failures in one subsystem should not unnecessarily compromise unrelated subsystems.

Important boundaries include:

```text
Geo Discovery
Candidate Pipeline
Ranking
Reservation
Offer Delivery
Event Processing
Persistence
```

Each subsystem should expose clear contracts and failure semantics.

---

# 17. Distinguish Failure From Empty Results

The system must distinguish:

```text
No drivers found
```

from:

```text
Driver discovery failed
```

Likewise:

```text
No driver could be reserved
```

is different from:

```text
Reservation infrastructure failed
```

This distinction is required for correct retries, observability, and operational diagnosis.

---

# 18. Performance

Performance should be achieved primarily by reducing unnecessary work rather than adding premature infrastructure.

The preferred strategy is:

```text
Bound the candidate population
        ↓
Batch data access
        ↓
Perform local computation
        ↓
Reserve only required candidates
        ↓
Publish asynchronously
```

The system should minimize:

- Redis round trips,
- database round trips,
- repeated feature calculation,
- unnecessary allocations,
- repeated candidate processing,
- blocking operations.

---

# 19. Memory Efficiency

Candidate processing should remain bounded.

The system should avoid unnecessarily materializing large candidate populations.

The intended direction is:

```text
Discover
   ↓
Process
   ↓
Consume
   ↓
Continue
```

rather than:

```text
Discover everything
   ↓
Copy everything
   ↓
Process everything
```

The existing candidate collection/iterator/pipeline architecture should be reused where it already satisfies this requirement.

---

# 20. Scalability

The system should scale across increasing:

```text
Rides
Drivers
Geographic areas
Dispatch operations
Event volume
```

without requiring the core dispatch model to be redesigned.

Scaling should be introduced at the appropriate boundaries:

```text
Geo Index
Candidate Pipeline
Event Infrastructure
Regional Dispatch
```

rather than prematurely distributing every component.

---

# 21. Regional Scalability

The architecture should support future regional partitioning.

The intended direction is:

```text
Region
  ↓
H3 Cells
  ↓
Dispatch Ownership
  ↓
Local Candidate Discovery
```

A dispatch node should eventually be able to operate on a bounded geographic responsibility instead of broadcasting work across the entire system.

This is a future scaling capability and should not be implemented before the current single-region architecture requires it.

---

# 22. Cost Efficiency

The system should remain conscious of infrastructure cost.

The architecture should favour efficient use of:

- PostgreSQL,
- Redis,
- event infrastructure,
- routing providers,
- compute resources.

Expensive operations should be protected by bounded candidate populations and explicit budgets.

---

# 23. Operational Observability

The system should make important dispatch behaviour measurable.

Observability should cover:

```text
Candidate Discovery
Candidate Filtering
Ranking
Reservation
Offer Creation
Offer Delivery
Driver Response
```

The system should provide enough information to answer:

- Why did matching take longer?
- How many candidates were discovered?
- How many were filtered?
- Why were candidates rejected?
- How many reservations failed?
- How many drivers were offered?
- Where is dispatch latency being spent?

---

# 24. Geographic Observability

Geographic search should expose useful measurements such as:

```text
Average / distribution of rings searched
Cells visited
Drivers examined
Candidates returned
Discovery latency
```

These measurements should help identify poor search policies and geographic supply problems.

---

# 25. Dispatch Latency Observability

Dispatch latency should be decomposable into meaningful stages.

The target model is:

```text
Lookup
  ↓
Enrichment
  ↓
Filtering
  ↓
Ranking
  ↓
Reservation
  ↓
Offer
  ↓
Acceptance
```

This allows performance problems to be isolated rather than represented by one aggregate matching latency value.

---

# 26. Reliability

The system should continue operating correctly under common infrastructure failures.

Important reliability goals include:

- Redis recovery,
- stale driver cleanup,
- background reconciliation,
- event retry,
- dead-letter handling,
- idempotent processing,
- reservation cleanup,
- transactional persistence.

Recovery mechanisms should repair state rather than silently hiding corruption.

---

# 27. Realtime Driver State

Driver location and realtime availability are high-frequency operational data.

The system should keep realtime state separate from durable business state where appropriate.

Conceptually:

```text
Realtime Driver State
        │
        ├── Location
        ├── Heartbeat
        ├── Connection
        └── Offer State
```

while durable business state remains in the appropriate persistent store.

---

# 28. Data Ownership

Each subsystem should have clear ownership of its data.

Examples:

```text
PostgreSQL
    Durable business state

Redis
    Realtime / hot operational state

H3 Index
    Spatial driver lookup

Event Broker
    Asynchronous event transport

Outbox
    Durable event publication intent
```

A cache should not silently become the authoritative source of durable business state.

---

# 29. Extensibility

The system should support future evolution without forcing large rewrites.

Important extension boundaries include:

```text
CandidateSearcher
Ranker
Travel Calculator
Driver Locker
Outbox
Event Consumer
Refiner
Retry Policy
```

New implementations should normally plug into these existing contracts rather than bypassing them.

---

# 30. Configurability

Operational and business policy that is expected to change should be configurable.

Examples include:

```text
Search limits
Retry limits
Ranking weights
Lock TTL
Realtime TTLs
H3 settings
Offer timeout policy
Density thresholds
```

Configuration must not become a substitute for architecture.

Only genuinely variable policy should be configurable.

---

# 31. Maintainability

The system should remain understandable to developers who did not build the original implementation.

Maintainability goals include:

- explicit module boundaries,
- small interfaces,
- clear dependency direction,
- meaningful naming,
- documented business rules,
- documented architectural decisions,
- tests around important contracts.

---

# 32. AI-Assisted Development

RideForge is intended to be maintainable by both human developers and AI coding agents.

The repository should therefore provide enough documentation for an agent to understand:

```text
What the system does
Why the architecture exists
Which component owns which responsibility
Which rules must not be violated
What is already implemented
What is planned
```

AI agents must follow the existing architecture rather than creating parallel implementations for responsibilities that already exist.

---

# 33. Production-Grade Evolution

The project should evolve incrementally.

The preferred pattern is:

```text
Current Working System
        ↓
Measured Requirement
        ↓
Small Architectural Extension
        ↓
Tests
        ↓
Observability
        ↓
Documentation
```

Roadmap items should not be implemented merely to mark a phase complete.

If a capability is already effectively implemented, it should be recognized as complete and reused.

---

# 34. Future Intelligence

The architecture should be ready for more intelligent dispatch without prematurely introducing machine learning.

Potential future capabilities include:

```text
Acceptance Prediction
ETA Prediction
Demand Prediction
Adaptive Batch Size
Dynamic Offer Timeout
Learned Retry Policy
Dispatch Policy Learning
```

These should be introduced only when the required data and operational foundations are available.

---

# 35. Safety of Evolution

Future improvements must preserve existing correctness guarantees.

Any optimization must not compromise:

```text
Reservation correctness
Transaction consistency
Event reliability
Driver lifecycle correctness
Ride lifecycle correctness
Idempotency
Observability
```

Performance improvements are valid only when system correctness remains intact.

---

# 36. Business Flexibility

RideForge should support different dispatch strategies where operating conditions require them.

The dispatch architecture should be capable of supporting:

```text
Stand / Queue-based Dispatch
+
Smart / Algorithmic Dispatch
```

without forcing the entire platform to use one dispatch model.

The appropriate strategy can depend on the operating location and business rules.

---

# 37. Regional and Legal Constraints

Dispatch behaviour may depend on the operating region.

The system must keep regional/business rules explicit rather than assuming that every market can operate under identical ride-hailing rules.

This includes considerations such as:

```text
Operating Region
Cross-Region Ride Rules
Driver Eligibility
Dispatch Eligibility
```

Regional rules should be represented through explicit business/application boundaries rather than hidden inside geographic search code.

---

# 38. Domain Correctness Over Optimization

The system should prioritize:

```text
Correct ride state
Correct driver state
Correct reservation
Correct event processing
```

before micro-optimizations.

The preferred optimization order is:

```text
Correctness
   ↓
Observability
   ↓
Measured Bottleneck
   ↓
Targeted Optimization
```

---

# 39. No Premature Complexity

The project should avoid introducing infrastructure or abstractions without a current requirement.

Examples of changes that should not be introduced prematurely:

```text
Machine-learning infrastructure
Multi-region deployment
Complex distributed coordination
Multiple routing providers
Advanced demand prediction
Overly generic plugin systems
```

The architecture should remain extensible, but implementation should remain proportional to current needs.

---

# 40. Long-Term System Direction

The intended evolution is:

```text
Production Dispatch Foundation
          ↓
Efficient Candidate Discovery
          ↓
Quality / ETA Ranking
          ↓
Adaptive Dispatch
          ↓
Geo-aware Scaling
          ↓
Regional Scaling
          ↓
Data-driven Optimization
          ↓
ML-assisted Dispatch
```

Each step should build on the previous one.

---

# 41. Goal Hierarchy

The system goals can be summarized as:

```text
1. Correctness
       ↓
2. Reliability
       ↓
3. Low-latency Dispatch
       ↓
4. Efficient Resource Usage
       ↓
5. Scalability
       ↓
6. Intelligent Optimization
```

A lower-level goal must not undermine a higher-level goal.

For example:

```text
Lower latency
```

must not be achieved by compromising:

```text
Reservation correctness
```

---

# 42. Success Criteria

RideForge should be considered successful at the system level when it can:

- discover geographically relevant drivers efficiently,
- avoid unnecessary candidate processing,
- identify eligible candidates,
- rank candidates using meaningful signals,
- safely reserve drivers under concurrency,
- create reliable driver offers,
- handle asynchronous responses,
- recover from expected failures,
- expose actionable operational metrics,
- scale the dispatch path without redesigning its core contracts,
- evolve toward data-driven dispatch without replacing the foundational architecture.

# 44. AI Agent Requirements

Before implementing a feature, an AI coding agent should determine:

1. Which system goal does the change support?
2. Which existing component owns the responsibility?
3. Whether the capability already exists.
4. Whether an existing interface can be reused.
5. Whether the change introduces unnecessary complexity.
6. What correctness guarantees must remain unchanged.
7. Which tests and documentation must be updated.

An agent must not create a new component merely because a roadmap item has a separate name.

---

# 45. Final System Goal

The ultimate system goal is:

```text
Build a reliable, scalable, low-latency and
geographically intelligent ride-hailing dispatch platform
that can evolve from deterministic rules into adaptive,
data-driven dispatch while preserving clear architecture,
business correctness and operational reliability.
```
