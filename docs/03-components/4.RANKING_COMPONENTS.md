# RideForge — Ranking Components

> **Document:** `docs/03-components/4.RANKING_COMPONENTS.md`  
> **Status:** Active  
> **Scope:** Component-level documentation for candidate feature extraction, enrichment, normalization, scoring, and ranking  
> **Related:** `docs/01-business/4.MATCHING_RULES.md`, `docs/02-architecture/5.RANKING_ENGINE.md`, `docs/03-components/3.CANDIDATE_PIPELINE_COMPONENTS.md`

---

# 1. Purpose

The Ranking Components convert eligible driver candidates into an ordered preference for dispatch.

The ranking layer answers:

> **Among the currently eligible candidates, which drivers should be preferred first?**

It does not decide whether a driver is operationally eligible, reserved, offered, or assigned.

The core flow is:

```text
Eligible Candidates
       ↓
Feature Extraction
       ↓
Feature Enrichment
       ↓
Feature Normalization
       ↓
Score Calculation
       ↓
Ranking
       ↓
Ordered Candidates
```

---

# 2. Ranking Boundary

The ranking layer owns:

```text
Feature Extraction
Feature Enrichment
Feature Calculation
Feature Normalization
Quality Calculation
Travel Calculation
Fairness Calculation
Score Calculation
Candidate Ordering
```

It does not own:

```text
Geographic Discovery
Availability Filtering
Driver Reservation
Offer Creation
Assignment
Retry Orchestration
Ride Lifecycle
```

---

# 3. Current Component Structure

The current ranking package contains the following conceptual components:

```text
Ranker
FeatureExtractor
Enricher
DefaultFeatureExtractor
TravelCalculator
QualityCalculator
DefaultScorer
DefaultRanker
TravelFeatures
QualityFeatures
FairnessFeatures
Features
```

The exact implementation may evolve, but these responsibilities should remain separated.

---

# 4. Ranker

The `Ranker` is the application-facing abstraction used by the candidate pipeline.

Conceptually:

```text
Candidate Collection
       ↓
Ranker
       ↓
Scored / Ordered Candidates
```

The Candidate Pipeline should depend on this abstraction rather than the concrete scoring implementation.

---

# 5. Ranker Responsibility

The ranker coordinates the ranking operation.

It should:

- obtain the required features,
- invoke scoring,
- attach or return ranking results,
- order candidates according to score.

It should not:

```text
Reserve Drivers
Send Offers
Discover Drivers
Change Ride State
```

---

# 6. Feature Model

The ranking feature model groups information required to evaluate a candidate.

Conceptually:

```text
Features
 ├── Travel
 ├── Quality
 └── Fairness
```

Additional feature groups may be introduced later when there is a concrete requirement.

---

# 7. Feature Extraction

The feature extractor converts candidate state into the ranking feature model.

Conceptually:

```text
Candidate
   ↓
FeatureExtractor
   ↓
Features
```

The extractor should coordinate feature creation rather than duplicate individual feature calculations.

---

# 8. Feature Extractor Configuration

The feature extractor receives the configured ranking dependencies/policy required by the current implementation.

Configuration must not be hidden inside individual feature calculations.

The construction boundary should remain explicit:

```text
Bootstrap / Builder
       ↓
Ranking Configuration
       ↓
Feature Extractor
```

---

# 9. Enrichers

An `Enricher` supplies additional information needed to calculate ranking features.

Conceptually:

```text
Candidate
   ↓
Enricher
   ↓
Additional Ranking Data
```

Enrichers should have narrow responsibilities.

Examples may include:

```text
Travel information
Driver quality information
Fairness information
```

Only enrichers required by the current ranking implementation should be introduced.

---

# 10. Enricher Boundary

An enricher should not become a general-purpose driver service.

Its responsibility is to provide information required for ranking.

It should not:

```text
Reserve Drivers
Change Driver Availability
Create Offers
Persist unrelated business state
```

---

# 11. Travel Features

Travel features represent geographic/travel-related information used by ranking.

The current model includes distance-based travel information.

The architecture is prepared to support richer ETA information.

Conceptually:

```text
Candidate
   ↓
Travel Calculator / Enricher
   ↓
Travel Features
   ├── Distance
   └── ETA-related data when available
```

---

# 12. ETA Ranking Direction

Production dispatch should prefer estimated arrival time over raw geographic distance when reliable ETA information is available.

The desired progression is:

```text
Current:
Distance-based travel feature

Target:
Routing / ETA-based travel feature
```

This must be implemented through the existing travel-feature boundary rather than by rewriting the complete ranking engine.

---

# 13. Travel Calculator

The travel calculator owns travel-feature calculation.

It should not own:

```text
Final candidate ranking
Driver reservation
Offer lifecycle
```

The calculator should return travel information that the feature extractor/scorer can consume.

---

# 14. Quality Features

Quality features represent driver performance characteristics relevant to ranking.

The current model includes concepts such as:

```text
Acceptance Rate
Cancellation Rate
Timeout Rate
Rating
Completed Trips
```

These are inputs to the quality calculation.

---

# 15. Quality Calculator

The quality calculator converts quality-related driver metrics into a ranking-quality score.

Conceptually:

```text
Quality Metrics
      ↓
Quality Calculator
      ↓
Normalized Quality Score
```

The calculator should not own ranking weights that belong to configuration.

---

# 16. Quality Configuration

Quality weights must be provided through the ranking configuration.

The implementation must not hide business weights inside the calculator.

For example, the calculator should not contain hard-coded policy such as:

```text
Acceptance = 0.30
Rating = 0.20
```

Instead:

```text
RankingConfig
      ↓
Quality Calculator
      ↓
Weighted Quality Score
```

This keeps policy configurable and testable.

---

# 17. Quality Normalization

Raw quality metrics may have different ranges.

Examples:

```text
Acceptance Rate → 0..1
Cancellation Rate → 0..1
Timeout Rate → 0..1
Rating → rating scale
Completed Trips → unbounded count
```

The quality calculator must normalize these inputs before combining them.

---

# 18. Cancellation and Timeout

Negative quality metrics should be converted into a positive ranking contribution through the configured normalization approach.

Conceptually:

```text
Lower Cancellation
       ↓
Higher Quality Contribution

Lower Timeout
       ↓
Higher Quality Contribution
```

The exact formula belongs to the quality calculator and its configuration contract.

---

# 19. Experience

Completed trips provide an experience signal.

Because trip count can grow substantially, the experience feature should use the existing bounded/normalized calculation rather than allowing raw trip count to dominate the final score.

The current implementation uses a logarithmic transformation before scoring.

Any change to this behaviour should be deliberate and tested.

---

# 20. Rating

Driver rating must be normalized from its source scale before being combined with other quality features.

For the current implementation, the ranking code treats the driver's five-point rating scale as the source range.

This assumption must remain explicit if the underlying rating scale changes.

---

# 21. Quality Score Boundary

The quality score is a feature of ranking.

It does not determine:

```text
Driver Eligibility
```

A low-quality score should not automatically remove a driver unless a separate business rule explicitly defines such an eligibility condition.

---

# 22. Fairness Features

Fairness features represent dispatch-balancing signals.

The current implementation includes idle-time information based on the driver's last assignment.

Conceptually:

```text
Last Assigned
      ↓
Idle Duration
      ↓
Fairness Feature
```

The purpose is to avoid repeatedly preferring only the same drivers when other eligible candidates are also available.

---

# 23. Fairness Boundary

Fairness is a ranking signal.

It should not override hard operational constraints such as:

```text
Offline
Unavailable
Reserved
Blocked
Already Offered
```

Hard eligibility rules remain higher priority.

---

# 24. Fairness Normalization

Idle duration is not naturally bounded.

The ranking system should normalize or cap the fairness contribution so that a driver who has been idle for a very long period cannot dominate the entire ranking solely because of idle time.

The exact normalization should come from ranking policy/configuration rather than hidden constants.

---

# 25. Demand-Aware Ranking

Demand-aware ranking is part of the planned ranking direction.

The intended principle is:

```text
Demand Context
      ↓
Supply Context
      ↓
Ranking Adjustment
```

The implementation should only introduce demand features when the corresponding demand/supply data is actually available.

The ranking layer must not invent demand values.

---

# 26. Score Normalization

Ranking features should be normalized to comparable ranges before weighted combination.

The intended model is:

```text
Feature A → 0..1
Feature B → 0..1
Feature C → 0..1
       ↓
Weighted Combination
       ↓
Final Score
```

This prevents a raw high-magnitude feature from dominating the score.

---

# 27. Weighted Scoring

The scorer combines normalized ranking signals according to configured weights.

Conceptually:

```text
Travel Score
      × Travel Weight
+
Quality Score
      × Quality Weight
+
Fairness Score
      × Fairness Weight
+
Future Signals
      × Configured Weights
      ↓
Final Score
```

The exact weights are configuration, not code constants.

---

# 28. Default Scorer

`DefaultScorer` is the current concrete scorer.

Its responsibility is to calculate the final candidate score from the prepared feature set and configured ranking policy.

It should not independently fetch unrelated driver data.

---

# 29. Scorer Configuration

The scorer receives `RankingConfig`.

The configuration should contain ranking policy values such as:

```text
Travel Weight
Acceptance Weight
Cancellation Weight
Timeout Weight
Rating Weight
Experience Weight
Fairness Weight
```

The exact active fields are defined by the current configuration package.

---

# 30. Configuration Injection

The ranking graph should be constructed with the same validated ranking configuration.

Conceptually:

```text
RankingConfig
      │
      ├── Feature Extractor
      ├── Quality Calculator
      └── Scorer
```

This prevents inconsistent ranking policy between components.

---

# 31. No Hidden Ranking Constants

The ranking implementation must not introduce hidden business weights such as:

```text
0.45
0.25
0.15
```

directly into calculators or scorers unless the value is explicitly a mathematical normalization constant required by the feature definition.

Business weighting belongs in configuration.

---

# 32. Mathematical Constants vs Policy

Not every numeric constant is forbidden.

There is an important distinction:

```text
Policy:
    "Quality contributes 25%"
    → configuration

Mathematical normalization:
    "Rating source scale is 5"
    → feature/domain contract
```

Even mathematical assumptions should remain explicit and documented where they materially affect ranking.

---

# 33. Default Ranker

The `DefaultRanker` coordinates:

```text
Feature Extraction
      ↓
Scoring
      ↓
Candidate Ordering
```

It should remain independent of candidate discovery and reservation.

---

# 34. Ranking Order

Candidates should be ordered by their final ranking score according to the ranking contract.

The highest-priority candidate should be available to the downstream dispatch selection mechanism first.

Tie behaviour should remain deterministic where practical.

---

# 35. Deterministic Ranking

When candidates have equal scores, the system should use a deterministic secondary ordering where the current implementation supports it.

A deterministic result helps:

```text
Testing
Debugging
Reproducibility
Operational Analysis
```

A secondary ordering must not violate business constraints.

---

# 36. Ranking and Heap

The Candidate Pipeline may use a heap after ranking.

The ranking engine's responsibility ends at producing the ranking information/order required by the pipeline.

The heap builder remains a pipeline concern.

```text
Ranker
   ↓
Ranked Candidates
   ↓
Heap Builder
```

---

# 37. Ranking and Availability

The ranking layer should assume that candidates reaching it have already passed the applicable hard availability filter.

It should not reimplement availability checks.

This avoids duplicated state reads and inconsistent eligibility definitions.

---

# 38. Ranking and Reservation

Ranking is advisory.

A highly ranked driver can still fail reservation:

```text
Rank #1
   ↓
Reservation
   ↓
Rejected due to concurrent assignment
```

The Dispatch Engine handles this outcome.

Ranking should not attempt to reserve drivers to "protect" its result.

---

# 39. Ranking and Offers

Ranking does not create offers.

The ranking result is consumed by dispatch orchestration.

```text
Ranking
   ↓
Candidate Selection
   ↓
Reservation
   ↓
Offer
```

---

# 40. Ranking and Retry

Ranking does not decide whether another dispatch attempt should occur.

Retry policy belongs to the Dispatch Engine and retry components.

A failed ranking attempt should be classified by the caller according to the error contract.

---

# 41. Ranking Failure

Ranking errors should remain distinguishable from a valid low score.

Examples:

```text
Feature Extraction Error
Travel Data Failure
Required Enrichment Failure
Scoring Error
```

must not silently become:

```text
Score = 0
```

unless the feature contract explicitly defines a safe fallback.

---

# 42. Missing Feature Data

Missing ranking data must have an explicit policy.

Possible approaches include:

```text
Use defined neutral value
Use configured fallback
Reject candidate
Return ranking error
```

The correct choice depends on the feature contract.

An AI agent must not invent fallback behaviour during a small ranking change.

---

# 43. Travel Provider Integration

When a routing provider is introduced, the preferred architecture is:

```text
Ranking / Travel Component
        ↓
Travel Provider Interface
        ↓
Google / Mapbox / OSRM / Valhalla
```

The scorer should not directly call a specific external routing provider.

---

# 44. Routing Cost Control

Routing is potentially expensive.

The ranking architecture should avoid performing expensive ETA calls for candidates that have already failed hard filters.

Preferred:

```text
Discovery
   ↓
Cheap Filters
   ↓
Ranking Candidate Set
   ↓
ETA / Travel Enrichment
```

where the current feature contract supports this sequence.

---

# 45. Quality Data Source

Quality information should come from an explicit source/enricher.

The ranking layer should not query arbitrary repositories from inside the scorer.

Preferred:

```text
Quality Enricher
      ↓
Quality Features
      ↓
Quality Calculator
```

This keeps scoring deterministic and easier to test.

---

# 46. Fairness Data Source

Fairness information should similarly be provided through an explicit feature/enrichment boundary.

The scorer should consume:

```text
FairnessFeatures
```

rather than querying the driver cache or database directly.

---

# 47. Ranking Hot Path

Ranking is executed for eligible candidates during dispatch.

The implementation should therefore:

- avoid repeated data fetching,
- avoid unnecessary allocations,
- avoid repeated normalization work,
- reuse already available candidate data,
- avoid network calls from pure scoring functions.

---

# 48. Pure Calculation Preference

Calculators such as quality and travel feature calculators should be as deterministic as their input contracts permit.

Preferred:

```text
Input Features
      ↓
Calculation
      ↓
Output Feature
```

rather than hidden external side effects.

---

# 49. Ranking Configuration Ownership

Ranking configuration is application configuration.

The ranking components consume it.

They should not:

```text
Read environment variables directly
Create independent configuration defaults
Override configured weights silently
```

---

# 50. Builder Boundary

The ranking graph should be composed by the builder/bootstrap layer.

Conceptually:

```text
RankingConfig
      ↓
Feature Extractor
      ↓
Scorer
      ↓
Ranker
```

The application currently uses a builder pattern for this composition.

This keeps dependency wiring out of ranking implementation code.

---

# 51. Builder Example

The intended composition is conceptually:

```text
BuildRanker(&cfg.Ranking)
```

The builder is responsible for constructing the configured ranking graph.

If feature enrichers are required, they should be provided through the builder rather than silently instantiated inside the ranker.

---

# 52. Enricher Composition

The ranking builder should explicitly compose the required enrichers.

Conceptually:

```text
Travel Enricher
Quality Enricher
Fairness Enricher
       ↓
Feature Extractor
       ↓
Ranker
```

Do not create hidden global enrichers.

---

# 53. Component Dependency Direction

The desired dependency direction is:

```text
Ranker
  ↓
FeatureExtractor / Scorer
  ↓
Feature Calculators / Enrichers
  ↓
Explicit Data Providers
```

Infrastructure remains below these abstractions.

At minimum test:

```text
Perfect quality
Poor quality
Zero completed trips
Large completed-trip count
Zero rating
Maximum rating
Full cancellation
No cancellation
Full timeout
No timeout
Configured weight changes
```

The tests should verify behaviour rather than implementation structure.

---

# 56. Scorer Tests

The scorer should be tested with controlled feature inputs.

Examples:

```text
Better ETA → Higher Score
Better Quality → Higher Score
Better Fairness → Higher Score
Weight Changes → Expected Ranking Changes
```

This verifies that configuration actually controls ranking.

---

# 57. Ranker Tests

Test that:

```text
Features are extracted
Scores are calculated
Candidates are ordered correctly
Errors are propagated
```

The ranker should not require Redis or PostgreSQL for pure ranking tests.

---

# 58. Configuration Tests

Configuration propagation is particularly important because ranking policy must not silently diverge between components.

Test that:

```text
RankingConfig
      ↓
Feature Extractor
      ↓
Quality Calculator
      ↓
Scorer
```

uses the intended configured values.

---

# 59. Ranking Observability

Useful ranking metrics include:

```text
Candidates Ranked
Ranking Latency
Feature Extraction Latency
Scoring Latency
Average Candidate Count
Ranking Errors
```

Avoid high-cardinality metrics based directly on driver or ride IDs.

---

# 60. Ranking Tracing

Where tracing is enabled, ranking spans should make the operation diagnosable.

Useful attributes include:

```text
Candidate Count
Feature Extraction Duration
Scoring Duration
Ranking Duration
```

Do not attach full driver records to traces.

7. Inspect all current enrichers.

10. Inspect `DefaultScorer`.
11. Inspect `DefaultRanker`.

# 62. AI Agent Forbidden Patterns

An AI agent must not:

- hard-code business ranking weights,
- create a second ranking engine,
- calculate ranking inside candidate filters,
- query Redis/PostgreSQL directly from the scorer,
- make the scorer responsible for reservation,
- make ranking determine ride assignment,
- silently convert missing feature data into arbitrary values,
- add an external routing dependency directly to the scorer,
- duplicate quality calculations in multiple components,
- duplicate travel calculations,
- bypass `RankingConfig`,
- instantiate hidden enrichers inside unrelated components,
- reorder pipeline stages merely to accommodate a ranking implementation,
- introduce ML ranking before the corresponding architecture and data contract exist.

```text

    │       → Feature / Enricher
    │
    ├── Feature calculation?
    │       → Calculator
    │
    ├── Feature normalization?
```

# 70. Dispatch Strategy Context

The Ranking Components operate after the effective dispatch strategy has been resolved and candidates have been discovered and passed through the applicable eligibility pipeline.

The ranking layer may receive strategy context such as:

```text
Effective Dispatch Strategy
Candidate Location
Candidate Location Strategy
Stand Membership
Relevant Auto Stand
Queue Position
Discovery Source
Expansion Level
Distance
ETA
```

This context must be preserved where it is required to apply strategy-specific prioritization correctly.

The Ranking Components must not resolve the configuration hierarchy themselves.

---

# 71. Smart Stand Dispatch Ranking

Smart Stand Dispatch is **stand-preferred, not stand-exclusive**.

When the rider is within the configured radius of an auto stand, eligible candidates associated with that preferred stand should receive the stand-specific preference defined by the dispatch strategy.

The conceptual flow is:

```text
Rider inside Stand Radius
        ↓
Preferred Stand Candidates
        ↓
Eligibility
        ↓
Stand Queue / Ordering Preference
        ↓
Suitable Stand Candidate?
        ├── YES → preferred dispatch path
        └── NO  → broader eligible candidates
```

The ranking layer must not interpret:

```text
Candidate not at preferred stand
```

as:

```text
Candidate is ineligible
```

A broader candidate may still be ranked and selected when the preferred stand cannot provide a suitable driver.

---

# 72. Stand Queue Is Not Automatically a Generic Score

The stand queue is a strategy-specific prioritization mechanism.

The implementation must not automatically convert queue position into an arbitrary numerical weight such as:

```text
Queue Position × Stand Weight
```

unless the approved business/ranking contract explicitly defines such a scoring model.

Where the stand strategy requires first-eligible-in-queue semantics, the ranking/dispatch flow should preserve that ordering directly.

For example:

```text
Queue:
Driver A
Driver B
Driver C

A unavailable
B eligible
C eligible

→ Driver B is the first eligible queue candidate
```

This is different from allowing a distant driver with a better generic score to automatically overtake the queue.

If the business rules later define a combined queue + ranking model, that model must be explicitly documented and configured.

---

# 73. Broader Candidates Under Smart Stand Dispatch

When the preferred stand cannot provide a suitable driver, broader candidates may include:

```text
Non-stand drivers
Drivers at nearby stands
Drivers from nearby locations
```

These candidates should be evaluated using the applicable normal dispatch factors, such as:

```text
Eligibility
Availability
Distance
ETA
Quality
Fairness
Other configured factors
```

The transition is:

```text
Preferred Stand Supply
        ↓
No Suitable Driver
        ↓
Broader Candidate Pool
        ↓
Normal Candidate Evaluation / Ranking
```

This expansion does not mean the resolved strategy has changed.

```text
Smart Stand Dispatch
        ≠
Smart Dispatch fallback
```

unless an explicit business configuration defines a strategy transition.

---

# 74. Smart Dispatch Ranking

Smart Dispatch is stand-agnostic.

The ranking layer must not provide an automatic ranking advantage merely because a driver is:

```text
At an auto stand
```

or:

```text
Outside an auto stand
```

unless a separate configured ranking feature explicitly requires it.

Normal ranking signals may include:

```text
Distance
ETA
Quality
Fairness
Acceptance Behaviour
Other configured signals
```

---

# 75. Cross-Location Ranking

Candidates from nearby locations may enter the ranking pipeline when local supply is insufficient.

A candidate from another location is not automatically invalid because:

```text
Candidate Location ≠ Ride Origin Location
```

The ranking context should preserve:

```text
Origin Location
Candidate Location
Candidate Location's Effective Strategy Context
Stand Membership
Relevant Stand
Queue Position
Distance
ETA
Discovery Source
Expansion Level
```

Cross-location candidates must still satisfy all hard eligibility, legal, geographic, service, and operational constraints before ranking.

---

# 76. Different Strategies Across Locations

Nearby locations may use different dispatch strategies.

Example:

```text
Location A
→ Smart Dispatch

Location B
→ Smart Stand Dispatch
```

A ride originating in Location A may eventually consider a candidate from Location B if candidate discovery expands to Location B.

The Ranking Components must not reject the Location B candidate solely because:

```text
Location B uses Smart Stand Dispatch
```

Instead, the candidate's strategy context should be preserved so the dispatch flow can apply the correct strategy-specific preference.

For example:

```text
Location B Stand Driver
2 km / 5 min ETA

Location B Non-Stand Driver
4 km / 9 min ETA
```

If both are eligible and the applicable strategy gives the stand driver preference, the stand driver can be selected.

The exact comparison remains governed by the approved dispatch/ranking policy.

---

# 77. Strategy Resolution Is Outside Ranking

The Ranking Components must not perform:

```text
State → District → Town → Rural Area → Stand → Ride
```

configuration traversal.

The effective strategy must already be resolved upstream.

The separation is:

```text
Configuration Hierarchy
        ↓
Effective Dispatch Strategy
        ↓
Candidate Discovery
        ↓
Candidate Pipeline
        ↓
Ranking Components
        ↓
Reservation / Assignment
```

The Ranking Components consume the result of strategy resolution; they do not own configuration inheritance.

---

# 78. Candidate Preference vs Candidate Eligibility

The Ranking Components must preserve the distinction:

```text
Eligible but lower preference
```

versus:

```text
Ineligible
```

Examples:

```text
Non-stand driver during Smart Stand Dispatch
    → potentially eligible, lower/preferred-context dependent

Driver from nearby location
    → potentially eligible

Driver outside preferred stand
    → potentially eligible

Unavailable driver
    → ineligible before ranking
```

Ranking should not turn a preference rule into an eligibility filter unless the business rules explicitly require that behavior.

---

# 79. Ranking and Candidate Expansion

Candidate expansion is owned by discovery/dispatch orchestration.

Ranking should not decide:

```text
When to expand geographic search
Which location to search next
When to retry discovery
Whether to switch dispatch strategy
```

Instead:

```text
Discovery / Dispatch
        ↓
Provides candidate set
        ↓
Ranking
        ↓
Orders candidates according to applicable ranking policy
```

If a ranking attempt produces no usable candidate, the Dispatch Engine determines the next action according to the retry and fallback policy.

---

# 80. AI-Assisted Ranking

AI-assisted dispatch may provide additional ranking signals, but it does not become a third primary dispatch strategy.

The relationship is:

```text
Effective Dispatch Strategy
        ↓
Candidate Discovery
        ↓
Candidate Pipeline
        ↓
Deterministic / AI-Assisted Ranking
        ↓
Final Dispatch Decision
```

AI may provide signals such as:

```text
Acceptance Probability
Predicted ETA
Cancellation Probability
Demand/Supply Signals
Dynamic Ranking Score
```

AI must not override:

```text
Hard Eligibility
Legal Restrictions
Safety Constraints
Availability
Authoritative Reservation State
```

AI failure must not silently convert Smart Stand Dispatch into Smart Dispatch.

---

# 81. Ranking Context Must Be Explainable

For dispatch decisions, the ranking result should be explainable enough to identify why a candidate was preferred.

Useful ranking context may include:

```text
Effective Strategy
Preferred Stand
Queue Position
Distance
ETA
Quality Score
Fairness Score
Final Score
Discovery Source
Candidate Location
```

This is particularly important when comparing:

```text
Preferred stand candidates
```

against:

```text
Broader fallback candidates
```

and when diagnosing cross-location dispatch.

---

# 82. Ranking Contract with the Candidate Pipeline

The Candidate Pipeline should provide candidates in a form that contains all information required by the ranking strategy.

Conceptually:

```text
Candidate
  ├── Driver State
  ├── Location Context
  ├── Strategy Context
  ├── Stand Context
  ├── Queue Context
  ├── Discovery Context
  └── Travel Context
        ↓
Ranker
        ↓
Ranked Candidate Results
```

The Ranking Components should not reconstruct missing strategy or location context by independently querying unrelated infrastructure.

# 84. Updated Ranking Flow

The complete flow is:

```text
Ride Request
      ↓
Resolve Effective Dispatch Strategy
      ↓
Discover Candidates
      ↓
Apply Hard Eligibility
      ↓
Prepare Candidate Context
      ↓
Strategy-Specific Preference
      ↓
Feature Extraction / Enrichment
      ↓
Score Calculation
      ↓
Candidate Ordering
      ↓
Reservation
      ↓
Offer / Assignment
```

For Smart Stand Dispatch:

```text
Preferred Stand Context
        ↓
Queue / Stand Preference
        ↓
Broader Candidates if Required
        ↓
Ranking
```

For Smart Dispatch:

```text
Eligible Nearby Candidates
        ↓
Normal Ranking
```

# 85. AI Agent Guardrails for Dispatch Strategy

When modifying ranking components, an AI coding agent must not:

```text
Implement Smart Stand Dispatch as stand-only.

Reject a candidate solely because the candidate is outside the preferred stand.

Reject a candidate solely because the candidate belongs to another location.

Treat stand membership as an automatic Smart Dispatch ranking advantage.

Resolve dispatch configuration hierarchy inside ranking components.

Hard-code State → District → Town → Stand as the only hierarchy.

Convert queue position into a hidden arbitrary score.

Silently switch Smart Stand Dispatch to Smart Dispatch when stand supply is unavailable.

Use AI ranking to override hard eligibility or legal constraints.

Make the scorer responsible for candidate discovery or geographic expansion.
```

---

# 86. Updated Ranking Modification Checklist

Before changing ranking behaviour, determine:

```text
□ What is the effective dispatch strategy?
□ Is this a Smart Dispatch or Smart Stand Dispatch path?
□ Is the candidate from the preferred stand?
□ Is stand preference required for this candidate set?
□ Is queue ordering deterministic or score-based according to the current policy?
□ Is the candidate from another location?
□ Is the candidate merely less preferred, or actually ineligible?
□ Are distance and ETA available?
□ Is the change a feature, calculator, configuration, scorer, or ordering change?
□ Does the change affect AI-assisted ranking?
□ Does the change preserve hard eligibility and legal constraints?
□ Does the change preserve the resolved dispatch strategy?
```

---

# 87. Updated Final Component Rule

When an AI agent is asked to modify ranking behaviour, determine first:

```text
Is the change about:
    │
    ├── Dispatch configuration resolution?
    │       → Configuration / Dispatch Engine
    │
    ├── Candidate discovery or geographic expansion?
    │       → Discovery Engine
    │
    ├── Candidate eligibility?
    │       → Candidate Pipeline / Business Rules
    │
    ├── Strategy-specific preference?
    │       → Dispatch / Ranking policy
    │
    ├── New ranking input data?
    │       → Feature / Enricher
    │
    ├── Feature calculation?
    │       → Calculator
    │
    ├── Feature normalization?
    │       → Feature / Calculator
    │
    ├── Business weight?
    │       → RankingConfig
    │
    ├── Score combination?
    │       → Scorer
    │
    ├── Candidate ordering?
    │       → Ranker
    │
    └── Driver reservation / assignment?
            → Dispatch Engine
```

The Ranking Components should remain responsible for **turning already-eligible candidates into a configurable, explainable, strategy-aware, and efficient preference order for dispatch without becoming the owner of configuration resolution, candidate discovery, eligibility, reservation, or assignment**.
