# 1. Purpose

The Persistence Components provide the storage boundaries used by RideForge application services.

The architecture separates:

```text
Durable Business State
        ↓
PostgreSQL
```

from:

```text
Operational / Ephemeral State
        ↓
Redis
```

and:

```text
Asynchronous Event Durability
        ↓
PostgreSQL Outbox
```

The persistence layer provides storage access without moving business rules into repositories.

---

# 2. Persistence Boundary

Persistence components own:

```text
Database Access
Repository Implementations
SQL Queries
Transaction Integration
Cache Storage
Operational State Storage
Outbox Storage
Persistence Mapping
```

They do not own:

```text
Business Decisions
Matching Policy
Ranking Policy
Retry Policy
Reservation Policy
Offer Policy
Domain State Transitions
```

Application services decide what should happen.

Repositories provide the mechanism to persist or retrieve the required state.

---

# 3. Storage Model

RideForge uses different storage systems for different workload characteristics.

Conceptually:

```text
                         RideForge
                            │
             ┌──────────────┼──────────────┐
             │              │              │
             ▼              ▼              ▼
        PostgreSQL        Redis         Message Broker
             │              │
             │              ├── Realtime State
             │              ├── Driver Cache
             │              ├── H3 Index
             │              ├── Reservation
             │              └── Operational State
             │
             ├── Durable Business State
             ├── Ride State
             ├── Driver State
             ├── Assignment State
             └── Outbox
```

Each store has a defined responsibility.

---

# 4. PostgreSQL as Durable Store

PostgreSQL is the durable business-data store.

It is responsible for data that must survive:

```text
Process Restart
Redis Restart
Application Deployment
Node Failure
```

Examples include:

```text
Rides
Drivers
Users
Assignments
Offers where durable persistence is required
Outbox Events
```

The exact schema is authoritative in the current repository.

---

# 5. Redis as Operational Store

Redis is used for low-latency operational state.

Examples include:

```text
Driver Realtime State
Driver Cache
H3 Driver Index
Redis GEO
Driver Reservation
Offer Timeout State
```

Redis data may be short-lived or reconstructable.

Redis should not silently become the durable source of business truth.

---

# 6. Repository Abstraction

Application services should depend on repository interfaces rather than database-specific implementations.

Conceptually:

```text
Application Service
      ↓
Repository Interface
      ↓
PostgreSQL Repository
```

This keeps:

```text
Business Logic
```

separate from:

```text
SQL / Driver Implementation
```

---

# 7. Repository Responsibilities

A repository should:

- execute persistence operations,
- map persistence data to application/domain structures,
- return meaningful persistence errors,
- participate in application transactions where required.

A repository should not:

```text
Decide Which Driver To Rank
Choose Retry Radius
Create Offers
Apply Dispatch Policy
```

---

# 8. Driver Repository

The Driver Repository provides durable driver data access.

Typical responsibilities include:

```text
Find Driver
Load Driver
Persist Driver State where required
Query Driver Records
```

The exact interface is defined by the current codebase.

---

# 9. Ride Repository

The Ride Repository provides durable ride state access.

It should support the application services that own ride lifecycle transitions.

The repository should not independently decide:

```text
Whether a ride may transition
Which driver should be selected
Whether a ride should retry
```

Those are application/domain responsibilities.

---

# 10. Assignment Persistence

Assignment state is durable business state.

The persistence layer stores the result of the assignment process.

Conceptually:

```text
Reservation
      ↓
Driver Acceptance
      ↓
Assignment Application Service
      ↓
PostgreSQL
```

The temporary reservation itself should not be mistaken for durable assignment.

---

# 11. Outbox Repository

The Outbox Repository persists events that must be published reliably.

Conceptually:

```text
Business Transaction
      ├── State Change
      └── Outbox Insert
```

The repository participates in the same database transaction where the business event must be atomic with the state change.

---

# 12. Transaction Boundary

Transactions belong at the application-service/use-case boundary when multiple persistence operations must succeed or fail together.

Conceptually:

```text
Application Service
      ↓
Transaction
   ┌──┴──────────┐
   ▼             ▼
Repository A   Repository B
   │             │
   └──────┬──────┘
          ▼
        Commit
```

Repositories should not independently start hidden transactions for every operation when the caller needs to coordinate multiple writes.

---

# 13. Transaction Ownership

The component that understands the business operation should own the transaction boundary.

For example:

```text
Accept Offer
    ↓
Application Service
    ↓
Transaction
    ├── Update Offer
    ├── Update Ride / Assignment State
    └── Insert Outbox Event
```

The repository executes the persistence operations.

---

# 14. Avoid Hidden Transactions

Repositories should not unexpectedly wrap individual methods in independent transactions if doing so can break the caller's atomicity.

Bad:

```text
Service
 ├── Repository A → Commit
 └── Repository B → Commit
```

when both operations must be atomic.

Preferred:

```text
Service
 ↓
One Transaction
 ├── Repository A
 └── Repository B
 ↓
Commit
```

---

# 15. Database Transactions and External Systems

Database transactions should not remain open while waiting for:

```text
Redis
Kafka / Redpanda
WebSocket
Push Notification
Routing Provider
External API
```

Preferred:

```text
Database Transaction
   ↓
Commit
   ↓
External / Asynchronous Work
```

The outbox pattern should bridge durable state changes to asynchronous publication.

---

# 16. PostgreSQL Connection Management

The application should use a bounded PostgreSQL connection pool.

The pool protects the database from unbounded application concurrency.

Conceptually:

```text
Requests
   ↓
Application
   ↓
Connection Pool
   ↓
PostgreSQL
```

Pool configuration belongs to infrastructure/configuration rather than individual repositories.

---

# 17. Connection Pooling

Repository implementations must avoid creating a new database connection per operation.

The shared application database client/pool should be injected through the composition root.

This provides:

```text
Connection Reuse
Bounded Concurrency
Predictable Database Load
```

---

# 18. Query Efficiency

Persistence queries are part of the application's latency path.

Repositories should prefer:

```text
Targeted SELECT
Indexed Predicates
Batch Queries
Bounded Result Sets
Explicit Columns
```

Avoid:

```text
SELECT *
```

when a smaller projection is sufficient.

---

# 19. Batch Data Access

The dispatch path already uses batch-oriented abstractions where appropriate.

Conceptually:

```text
Candidate Driver IDs
       ↓
Batch Repository / Cache Read
       ↓
Driver Records
```

This prevents:

```text
Driver 1 → DB
Driver 2 → DB
Driver 3 → DB
...
```

N+1 access patterns.

---

# 20. Repository and Candidate Pipeline

Candidate retrieval should not cause one database request per candidate.

Preferred:

```text
Spatial Discovery
      ↓
Driver IDs
      ↓
Batch Driver Cache / Repository
      ↓
Candidate Pipeline
```

The database should not become the default per-candidate source on the dispatch hot path.

---

# 21. Read vs Write Paths

Persistence design should distinguish:

```text
Read Path
```

from:

```text
Write Path
```

Dispatch reads prioritize:

```text
Low Latency
Batching
Bounded Queries
```

Business writes prioritize:

```text
Correctness
Transactions
Consistency
Durability
```

The architecture should not optimize one by weakening the other.

---

# 22. Redis Driver Cache

The Driver Cache provides fast operational access to driver state.

Conceptually:

```text
Driver ID
    ↓
Redis Driver Cache
    ↓
Driver Operational State
```

The cache is consumed by dispatch components through narrow interfaces.

---

# 23. Cache Interface Separation

The same Redis-backed implementation may satisfy multiple focused interfaces.

For example:

```text
BatchDataSource
OfferedDriverProvider
```

This is preferable to exposing one large interface containing unrelated Redis operations.

---

# 24. Cache Miss Semantics

A cache miss should have an explicit meaning.

Possible interpretations include:

```text
State Expired
Driver Offline
Driver Not Initialized
Operational State Unavailable
```

The consuming component must follow its contract.

Do not automatically perform a PostgreSQL fallback for every cache miss.

---

# 25. Cache vs Database

The intended flow is:

```text
Dispatch Hot Path
      ↓
Redis
```

rather than:

```text
Dispatch Hot Path
      ↓
PostgreSQL
```

for high-frequency operational state.

PostgreSQL remains the durable source for business state.

---

# 26. Cache Invalidation

Cache invalidation should be tied to explicit state transitions.

Avoid scattered invalidation logic across unrelated services.

Conceptually:

```text
Business State Change
      ↓
Application Service
      ↓
Cache Update / Invalidation
```

where the cache represents the changed state.

---

# 27. TTL Ownership

The component that owns a Redis key owns its TTL semantics.

For example:

```text
Driver Realtime State
    → Realtime Component

H3 Membership
    → H3 Driver Index

Reservation
    → Reservation Component

Offer Timeout State
    → Offer / Timeout Component
```

Other components should not silently modify these TTLs.

---

# 28. Redis Key Ownership

Redis key construction should remain inside the component responsible for that data.

Avoid:

```text
Dispatch Engine
    ↓
Build Redis Driver Key Manually
```

when a Driver Cache abstraction already exists.

This prevents key-format coupling.

---

# 29. H3 Index Persistence

The H3 Driver Index is operational spatial state.

It is not a PostgreSQL repository.

Conceptually:

```text
Driver Location
      ↓
H3 Index
      ↓
Redis
```

The index should maintain:

```text
Driver → Current Cell
Cell → Driver IDs
```

according to the geographic architecture.

---

# 30. Redis GEO Persistence

Redis GEO is also operational geographic state.

It should remain behind the Geo Service abstraction.

Application components should not directly issue Redis GEO commands.

---

# 31. Reservation Persistence

Driver reservation is temporary operational ownership.

The Redis-backed Driver Locker provides the reservation mechanism.

It should not be implemented as an ordinary PostgreSQL row update unless the architecture explicitly changes the reservation model.

---

# 32. Persistence and Reservation

The distinction is:

```text
Reservation
    =
Temporary concurrency protection

Assignment
    =
Durable business ownership
```

Both may reference the same driver and ride but have different lifecycles.

---

# 33. Persistence and Events

The outbox connects durable persistence to asynchronous messaging.

Correct:

```text
PostgreSQL Transaction
   ├── Business State
   └── Outbox
          ↓
      Publisher
          ↓
      Kafka/Redpanda
```

This avoids distributed transactions between PostgreSQL and the message broker.

---

# 34. Error Mapping

Repository implementations should return errors that preserve enough information for application services to make correct decisions.

Examples include:

```text
Not Found
Conflict
Constraint Violation
Connection Failure
Timeout
Transaction Failure
```

Do not turn every database error into:

```text
Generic Error
```

if the caller needs to distinguish the failure.

---

# 35. Not Found vs Failure

These must remain distinct:

```text
Driver Not Found
```

is different from:

```text
PostgreSQL Unavailable
```

Similarly:

```text
No Candidate
```

is different from:

```text
Candidate Query Failed
```

This distinction is important for dispatch correctness and observability.

---

# 36. Constraint Errors

Database constraints provide a final persistence-level safety boundary.

Application services should validate expected business conditions before writes, but database constraints should still protect:

```text
Uniqueness
Foreign Keys
Required Values
State Integrity
```

Do not remove useful database constraints merely because application validation exists.

---

# 37. Optimistic Concurrency

Where durable state can be modified concurrently, the application may use:

```text
Version
Updated At
Conditional UPDATE
State Predicate
```

to prevent stale writes.

The appropriate mechanism depends on the aggregate and current repository contract.

Do not introduce optimistic concurrency everywhere without a demonstrated race.

---

# 38. Conditional Updates

For state transitions, prefer persistence operations that encode the required precondition when appropriate.

Conceptually:

```sql
UPDATE offers
SET state = 'accepted'
WHERE id = ?
  AND state = 'pending';
```

The affected-row result can indicate whether the transition was still valid.

This can be safer than:

```text
SELECT
   ↓
Check
   ↓
UPDATE
```

when concurrent updates are possible.

---

# 39. Durable State Transition

A durable state transition should be treated as one application-level operation.

Conceptually:

```text
Validate Preconditions
       ↓
Transaction
       ↓
Conditional State Change
       ↓
Outbox Event where required
       ↓
Commit
```

This is particularly important for offer acceptance, assignment, and cancellation flows.

---

# 40. Soft Deletes

Soft deletion should only be used where the business model requires historical retention or recovery.

Do not add:

```text
deleted_at
```

to every table merely as a generic pattern.

The persistence model should reflect actual business requirements.

---

# 41. Time Handling

Persist timestamps consistently.

The application should use explicit time semantics and avoid mixing:

```text
Local Time
UTC
Database Session Time
```

without a defined contract.

Time-based dispatch/realtime policies should be derived from consistent timestamps.

---

# 42. Pagination

Repository queries returning potentially large datasets should use bounded access.

Where pagination is required, prefer stable pagination semantics appropriate to the query.

Do not load unbounded historical data into memory.

---

# 43. Historical Queries

Historical/reporting queries should not be placed on latency-sensitive dispatch repositories merely because they access the same database.

Keep:

```text
Dispatch Hot Path
```

focused and predictable.

Reporting/analytics workloads may require separate read paths later.

---

# 44. Database Indexing

Indexes should support actual query patterns.

Examples:

```text
Ride ID
Driver ID
Offer State
Reservation-related durable identifiers
Outbox Pending State
Created At
```

The exact indexes should be driven by measured queries and current schema.

Do not create indexes speculatively for every field.

---

# 45. Migration Ownership

Schema changes should be managed through the project's migration mechanism.

Repositories should not attempt to create or alter schema at runtime.

Conceptually:

```text
Migration
    ↓
Schema
    ↓
Repository
```

---

# 46. Migration Safety

Production migrations should consider:

```text
Existing Data
Existing Readers
Existing Writers
Lock Duration
Rollback Strategy
Deployment Order
```

A schema change should not silently break older application instances during rolling deployments.

---

# 47. Repository Testing

Repository tests should verify:

```text
Successful Read
Successful Write
Not Found
Constraint Error
Transaction Behaviour
Concurrent State Change where applicable
```

Integration tests should use the actual persistence technology where SQL semantics matter.

---

# 48. Cache Testing

Redis-backed components should test:

```text
Set
Get
Delete
TTL
Expiration
Batch Read
Atomic Update
Concurrency
```

Use the actual Redis semantics for integration tests where correctness depends on commands/scripts.

---

# 49. Transaction Testing

Transaction tests should verify rollback behaviour.

Example:

```text
Operation A succeeds
Operation B fails
       ↓
Transaction Rollback
       ↓
Neither durable change remains
```

This is especially important when the operation also writes an outbox event.

---

# 50. Outbox Transaction Testing

A critical test is:

```text
Business State Change
+
Outbox Event
```

both commit together.

Also test:

```text
Business State Change
+
Outbox Insert Failure
```

results in:

```text
Transaction Rollback
```

---

# 51. Persistence Observability

Useful database metrics include:

```text
Query Latency
Transaction Latency
Connection Pool Usage
Pool Wait Time
Query Errors
Deadlocks
Timeouts
Rows Returned
```

Redis metrics should include relevant operational store latency/error measures.

---

# 52. Persistence Tracing

Database spans should identify the operation without exposing sensitive payloads.

Useful attributes include:

```text
Repository
Operation
Database System
Query Type
Latency
Result
```

Do not put full SQL with sensitive parameter values into traces by default.

---

# 53. Logging

Persistence logs should focus on:

```text
Connection Failure
Transaction Failure
Deadlock
Timeout
Unexpected Constraint Failure
Migration Failure
```

Do not log every successful query in normal production operation.

Use metrics/tracing for high-volume visibility.

---

# 54. Performance Requirements

Persistence components should optimize for:

```text
Bounded Connections
Efficient Queries
Batch Access
Short Transactions
Minimal Serialization
Explicit Timeouts
Predictable Resource Usage
```

Avoid premature sharding, replicas, CQRS, or additional databases without an actual workload requirement.

---

# 55. Database Failure

When PostgreSQL is unavailable:

```text
Repository
   ↓
Infrastructure Error
```

The application must not pretend that a durable write succeeded.

Likewise, a read failure must not be converted into:

```text
No Record
```

unless the contract explicitly permits a safe fallback.

---

# 56. Redis Failure

When Redis is unavailable, components using Redis should expose the infrastructure failure.

Do not silently convert:

```text
Redis unavailable
```

into:

```text
Driver unavailable
```

unless the higher-level dispatch policy explicitly defines that fail-closed behaviour.

---

# 57. Fail-Closed Ownership Decisions

For safety-critical dispatch ownership operations:

```text
Cannot Confirm Reservation
      ↓
Do Not Assume Ownership
```

The persistence implementation must provide enough information for the application service to make that decision.

# 58. AI Agent Implementation Rules

Before modifying persistence components, an AI coding agent must:

1. Read this document.
2. Read `docs/02-architecture/4.DATA_ARCHITECTURE.md`.
3. Read `docs/02-architecture/10.RESERVATION_ARCHITECTURE.md`.
4. Read `docs/02-architecture/11.OUTBOX_AND_RELIABILITY.md`.
5. Inspect the relevant repository interface.
6. Inspect the current PostgreSQL schema/migrations.
7. Inspect the Redis key contract of the relevant component.
8. Inspect transaction boundaries in the application service.
9. Inspect existing connection-pool configuration.
10. Inspect current error types and mapping.
11. Preserve existing repository abstractions.
12. Preserve batch-read interfaces where present.
13. Add integration tests for SQL/Redis behaviour that changed.
14. Verify transaction rollback behaviour.
15. Verify no new N+1 access pattern was introduced.
16. Run the relevant test suite before completion.

---

# 59. AI Agent Forbidden Patterns

An AI agent must not:

- put business rules inside repositories,
- create hidden transactions that break caller atomicity,
- open a new PostgreSQL connection per request,
- introduce database access inside candidate ranking,
- query PostgreSQL once per candidate,
- treat cache misses as database failures automatically,
- treat infrastructure failures as empty results,
- create Redis keys outside their owning component,
- change TTL semantics without reviewing the owning component,
- store durable business truth only in Redis,
- bypass the outbox for events requiring transactional reliability,
- hold database transactions while waiting for network delivery,
- add speculative indexes without query evidence,
- introduce a second persistence abstraction for the same resource,
- add sharding/read replicas/CQRS merely for architectural appearance,
- weaken database constraints to compensate for application-level bugs.

# 61. Component Responsibility Matrix

| Component | Responsibility | Must Not Own |
|---|---|---|
| Repository | Durable data access | Business policy |
| PostgreSQL Repository | SQL-backed persistence | Dispatch decisions |
| Redis Cache | Operational state access | Durable business truth |
| H3 Index | Spatial operational state | Driver lifecycle |
| Geo Service | Geographic Redis operations | Ranking |
| Driver Locker | Temporary ownership | Assignment |
| Outbox Repository | Durable event records | Broker transport |
| Connection Pool | Resource management | Query policy |
| Transaction Boundary | Atomic persistence operation | External network calls |
| Migration System | Schema evolution | Runtime business logic |

# 64. Final Component Rule

When an AI agent is asked to modify persistence behaviour, determine first:

```text
Is the change about:
    │
    ├── Durable business data?
    │       → PostgreSQL Repository
    │
    ├── Realtime operational state?
    │       → Redis-backed Component
    │
    ├── Spatial membership?
    │       → H3 Driver Index
    │
    ├── Temporary driver ownership?
    │       → Driver Locker
    │
    ├── Reliable event persistence?
    │       → Outbox Repository
    │
    ├── Multiple writes that must be atomic?
    │       → Application Transaction
    │
    └── Asynchronous publication?
            → Outbox Publisher / Messaging
```

The Persistence Components should remain responsible for **efficient and reliable storage access while keeping durable state, operational state, concurrency ownership, and asynchronous event durability clearly separated**.
