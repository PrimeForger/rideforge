# RideForge — Candidate Pipeline Components

> **Document:** `docs/03-components/3.CANDIDATE_PIPELINE_COMPONENTS.md`  
> **Status:** Active  
> **Scope:** Component-level documentation for candidate collection, enrichment, filtering, ranking integration, and final candidate selection preparation

# 1. Purpose

The Candidate Pipeline transforms geographically discovered driver candidates into a validated, ranked, dispatch-ready candidate set.

The pipeline sits between discovery and dispatch selection:

```text
Discovery
    ↓
Candidate Collection
    ↓
Enrichment
    ↓
Filtering
    ↓
Ranking
    ↓
Heap / Ordered Result
    ↓
Dispatch
```

Its responsibility is to ensure that only candidates that satisfy the applicable matching rules reach the final dispatch-selection stage.

---

# 2. Pipeline Boundary

The Candidate Pipeline owns:

```text
Candidate Representation
Candidate Iteration
Candidate Enrichment
Candidate Validation
Deduplication
Availability Filtering
Already-Offered Filtering
Ranking Integration
Final Candidate Ordering
```

It does not own:

```text
Geographic Discovery
Driver Reservation
Offer Creation
Ride Assignment
Retry Policy
Realtime Transport
Durable Driver Lifecycle
```

---

# 3. Current Pipeline

The current pipeline is composed in this order:

```text
DefaultDriverLoader
        ↓
ValidationFilter
        ↓
DuplicateFilter
        ↓
AvailabilityFilter
        ↓
AlreadyOfferedFilter
        ↓
RankingStage
        ↓
HeapBuilder
```

This ordering is intentional and should not be changed casually.

---

# 4. Pipeline Construction

The bootstrap currently builds the candidate pipeline through the builder layer.

Conceptually:

```text
BuildCandidatePipeline(
    driverSource,
    offeredDriverProvider,
    ranker,
)
```

The builder composes the stages and returns the pipeline abstraction.

This keeps `bootstrap/container.go` focused on composition rather than stage construction details.

---

# 5. Pipeline Abstraction

The Dispatch Engine depends on the candidate pipeline abstraction rather than directly invoking individual stages.

Conceptually:

```text
MatchingEngine
      ↓
CandidatePipeline
      ↓
Stage 1
      ↓
Stage 2
      ↓
...
      ↓
Final Result
```

This allows individual stages to evolve without changing dispatch orchestration.

---

# 6. Pipeline Context

The pipeline context carries execution-level information and accumulated results.

It should contain pipeline metadata rather than becoming a second application-wide state store.

Examples of pipeline-level information include:

```text
Loaded Candidates
Filtered Candidates
Ranking Information
Final Result
```

The context should remain bounded to the current pipeline execution.

---

# 7. Candidate

A candidate represents a driver discovered as potentially relevant to the ride.

Conceptually:

```text
Candidate
 ├── Driver ID
 ├── Driver Data
 ├── Candidate State
 ├── Ranking Features
 └── Score
```

The candidate is progressively enriched as it moves through the pipeline.

---

# 8. Candidate Identity

The driver ID is the stable identity of a candidate.

Candidate processing must not create multiple logical candidates for the same driver.

The candidate ID should remain stable throughout the pipeline.

---

# 9. Candidate Collection

The candidate collection is the container used by pipeline stages to process candidates.

It provides operations required by the pipeline, including:

```text
Length
Iteration
Lookup By Driver ID
Mutation / Enrichment
```

The collection should remain lightweight because it operates on the dispatch hot path.

---

# 10. Candidate Iterator

The iterator abstraction allows stages to consume candidates without depending on the collection's internal representation.

Conceptually:

```text
Collection
    ↓
Iterator
    ↓
Candidate
    ↓
Next Candidate
```

This abstraction also leaves room for more memory-efficient traversal without changing every stage contract.

---

# 11. Streaming Direction

The architecture should prefer controlled candidate iteration over unnecessary intermediate copies.

The desired processing model is:

```text
Candidate
   ↓
Stage
   ↓
Next Candidate
```

rather than repeatedly creating full copies of the candidate population between stages.

The implementation should only introduce true streaming infrastructure where it provides measurable value and fits the existing contracts.

---

# 12. Batch Driver Loading

`DefaultDriverLoader` enriches discovered candidate IDs with driver data.

The current contract is:

```go
type BatchDataSource interface {
    LoadDrivers(
        ctx context.Context,
        driverIDs []uuid.UUID,
    ) ([]*driver.Driver, error)
}
```

This establishes the important performance boundary:

```text
Candidate IDs
      ↓
One Batch Load
      ↓
Driver Records
```

instead of:

```text
Candidate A → Database/Cache
Candidate B → Database/Cache
Candidate C → Database/Cache
```

---

# 13. Driver Source

The driver source is injected through the `BatchDataSource` abstraction.

The pipeline does not need to know whether the data comes from:

```text
Redis
PostgreSQL
Another Cache
```

as long as the source satisfies the required contract.

This keeps enrichment decoupled from infrastructure.

---

# 14. Driver Loader Responsibilities

`DefaultDriverLoader` should:

1. Collect candidate IDs.
2. Perform one batch load.
3. Associate returned driver records with candidates.
4. Record the number of successfully loaded candidates.
5. Return an error if the source operation fails.

It should not:

```text
Rank Drivers
Reserve Drivers
Create Offers
Perform Geographic Search
```

---

# 15. Missing Driver Records

A candidate ID may exist in the discovery index while the corresponding driver record is unavailable.

This can happen because realtime and durable state can change concurrently.

The loader should not fabricate a driver object.

Candidates without the required driver data should be removed or rejected by the appropriate downstream validation behaviour.

---

# 16. Batch Loading Performance

Batch loading is one of the key performance characteristics of the pipeline.

The implementation should avoid accidental N+1 behaviour.

Preferred:

```text
N Candidate IDs
      ↓
1 Batch Load
```

not:

```text
N Candidate IDs
      ↓
N Individual Loads
```

---

# 17. Validation Filter

The validation filter verifies that a candidate contains the information required for downstream processing.

Conceptually:

```text
Candidate
   ↓
Valid?
 ├── Yes → Continue
 └── No  → Reject
```

Validation should be cheap and deterministic.

---

# 18. Validation Scope

Validation should focus on structural/data validity required by the pipeline.

Examples may include:

```text
Valid Candidate ID
Required Driver Data Present
Required Candidate State Available
Required Ranking Inputs Available
```

Business eligibility checks should remain in the appropriate dedicated filters.

---

# 19. Duplicate Filter

The duplicate filter ensures that one driver appears only once in the candidate population.

Conceptually:

```text
Candidate A → Driver X
Candidate B → Driver X
Candidate C → Driver Y

        ↓

Driver X
Driver Y
```

This prevents duplicated ranking and reservation opportunities.

---

# 20. Duplicate Filter Responsibility

The duplicate filter owns candidate-level duplicate protection.

It does not replace discovery deduplication.

Both layers are justified because they protect different boundaries:

```text
Discovery
    ↓
Avoid unnecessary duplicate output

Pipeline
    ↓
Guarantee downstream candidate uniqueness
```

---

# 21. Availability Filter

The availability filter removes candidates that cannot currently participate in normal dispatch.

Conceptually:

```text
Candidate
   ↓
Operationally Available?
 ├── Yes → Continue
 └── No  → Reject
```

Availability must be based on current realtime/driver state according to the existing driver lifecycle rules.

---

# 22. Availability Is Not Discovery

A driver may be geographically discovered but unavailable.

Example:

```text
H3 Cell
   ↓
Driver X discovered
   ↓
Availability Filter
   ↓
Driver X rejected
```

This is expected.

Discovery finds spatial candidates; availability determines operational eligibility.

---

# 23. Availability Data Source

The availability filter should consume the existing driver-state/cache abstraction.

It should not implement its own independent driver-state storage.

This avoids conflicting definitions of availability.

---

# 24. Stale Driver State

A stale driver state must not be blindly interpreted as current availability.

Where the existing realtime cache tracks:

```text
Heartbeat
Connection
Location
Availability
```

the availability filter should respect the existing freshness semantics.

---

# 25. Already-Offered Filter

The already-offered filter prevents a driver from receiving a duplicate active offer for the same ride.

Its contract is distinct from batch driver loading.

The relevant provider is:

```go
type OfferedDriverProvider interface {
    GetOfferedDrivers(
        ctx context.Context,
        rideID uuid.UUID,
    ) (map[uuid.UUID]struct{}, error)
}
```

---

# 26. Separate Provider Responsibilities

The candidate pipeline intentionally distinguishes:

```text
BatchDataSource
```

from:

```text
OfferedDriverProvider
```

A single implementation such as the driver cache may satisfy both interfaces, but the pipeline should depend on the smallest interface required by each stage.

This follows interface segregation and keeps stages independently testable.

---

# 27. Already-Offered Lookup

The already-offered stage should retrieve the active offered-driver set for the ride and use it to reject duplicate offers.

Conceptually:

```text
Ride
 ↓
Already Offered Drivers
 ↓
Candidate Set
 ↓
Remove Already Offered
```

The stage should avoid unnecessary per-candidate lookups.

---

# 28. Offer History vs Active Offers

The already-offered filter is concerned with the offer state represented by its provider contract.

It should not independently invent a second offer-history system.

Rules about whether previously rejected or timed-out drivers can be reconsidered belong to dispatch policy.

---

# 29. Ranking Stage

After hard candidate filtering, the ranking stage delegates ranking to the configured `Ranker`.

Conceptually:

```text
Eligible Candidates
      ↓
Ranker
      ↓
Scored Candidates
```

The ranking stage should not duplicate scoring formulas.

---

# 30. Ranking Boundary

The Candidate Pipeline decides:

```text
When ranking occurs
Which candidates reach ranking
```

The Ranking Engine decides:

```text
How features are extracted
How features are normalized
How scores are calculated
How candidates are ordered
```

This separation is mandatory.

---

# 31. Ranking Inputs

Candidates reaching ranking should contain the information required by the configured feature extractor/enrichers.

Potential feature groups include:

```text
Travel
Quality
Fairness
Demand Context
```

Only features actually supported by the current implementation should be introduced into the active pipeline.

---

# 32. Ranking Configuration

Ranking weights and policy values must come from the configured ranking configuration.

The candidate pipeline must not hard-code:

```text
ETA Weight
Quality Weight
Fairness Weight
```

or other ranking policy values.

Those belong to the ranking configuration and ranking components.

---

# 33. Ranking Failure

If ranking fails because required data or calculation is unavailable:

```text
Ranking Failure
```

must remain distinguishable from:

```text
No Eligible Candidates
```

The pipeline should propagate the failure according to its contract rather than silently returning an empty result.

---

# 34. Heap Builder

The heap builder prepares the final candidate structure used by dispatch selection.

Conceptually:

```text
Ranked Candidates
      ↓
Heap Builder
      ↓
Best Candidate(s)
```

A heap is useful when the dispatch path needs efficient access to the best-ranked candidates without repeatedly sorting a larger population.

---

# 35. Heap Boundary

The heap builder should operate on ranking output.

It should not:

```text
Discover Drivers
Filter Availability
Calculate Quality
Reserve Drivers
Create Offers
```

Those responsibilities belong elsewhere.

---

# 36. Heap and Candidate Limit

The final heap should remain bounded by the configured candidate/dispatch limits.

The pipeline should avoid retaining substantially more candidates than downstream dispatch actually needs unless there is a concrete reason.

---

# 37. Pipeline Ordering

The current ordering is:

```text
1. Driver Loader
2. Validation
3. Duplicate
4. Availability
5. Already Offered
6. Ranking
7. Heap
```

The ordering expresses a cost and correctness strategy:

```text
Load required data
      ↓
Reject invalid data
      ↓
Remove duplicates
      ↓
Reject unavailable drivers
      ↓
Reject duplicate offers
      ↓
Perform expensive ranking
      ↓
Build final selection structure
```

---

# 38. Why Filtering Precedes Ranking

Ranking can require more expensive feature extraction.

Therefore hard filters should remove unsuitable candidates first.

Preferred:

```text
Candidate
   ↓
Cheap Hard Filters
   ↓
Expensive Ranking
```

not:

```text
Candidate
   ↓
Ranking
   ↓
Reject Candidate
```

This reduces dispatch cost.

---

# 39. Why Already-Offered Filtering Precedes Ranking

A driver who already has an active offer for the ride should not consume ranking resources for another offer.

Therefore:

```text
Already Offered
      ↓
Reject
```

occurs before ranking.

---

# 40. Pipeline Stage Independence

Each stage should have one clear responsibility.

For example:

```text
ValidationFilter
    → validation

DuplicateFilter
    → uniqueness

AvailabilityFilter
    → availability

AlreadyOfferedFilter
    → offer duplication protection

RankingStage
    → ranking

HeapBuilder
    → final candidate structure
```

A stage should not silently absorb responsibilities belonging to another stage.

---

# 41. Stage Contract

Pipeline stages should conform to the existing pipeline stage abstraction.

Conceptually:

```text
Stage.Execute(
    context,
    pipelineContext,
    candidates,
) error
```

The exact interface should remain the source of truth in code.

---

# 42. Stage Mutation

Stages may enrich or remove candidates according to their responsibility.

For example:

```text
DriverLoader
    → enrich candidate.Driver

AvailabilityFilter
    → remove unavailable candidates

RankingStage
    → add score / ranking information

HeapBuilder
    → construct final result
```

Stages should not mutate unrelated application state unnecessarily.

---

# 43. Pipeline Context Result

Pipeline execution may populate result metadata such as:

```text
LoadedCandidates
```

and other stage-specific result information already defined by the current implementation.

Result fields should represent useful execution information rather than become an arbitrary telemetry store.

---

# 44. Empty Pipeline Result

An empty result after filtering is a valid outcome.

For example:

```text
Discovery
   ↓
20 Candidates
   ↓
Availability
   ↓
0 Candidates
```

This means:

```text
No Eligible Candidates
```

provided no stage failed.

It is not automatically an infrastructure error.

---

# 45. Stage Failure

A stage error should stop normal pipeline execution unless the stage contract explicitly defines another behaviour.

For example:

```text
Batch Load Failure
    ↓
Pipeline Error
```

The system must not silently convert this into:

```text
Zero Candidates
```

---

# 46. Context Cancellation

All stages operating on external data should respect the request context.

Conceptually:

```text
Ride Dispatch Context
       ↓
Candidate Pipeline
       ↓
Every I/O Stage
```

When the dispatch operation is cancelled, unnecessary work should stop.

---

# 47. Pipeline Memory Behaviour

The candidate pipeline operates on the dispatch hot path.

It should therefore avoid:

```text
Unnecessary Candidate Copies
Unbounded Intermediate Collections
Repeated Full-Set Allocations
N+1 Data Fetches
```

At the same time, the implementation should not introduce complicated streaming infrastructure unless the existing workload demonstrates a need for it.

The current collection/iterator model should be reused where it already provides sufficient performance.

---

# 48. Batch Enrichment as the Main I/O Optimization

The current `BatchDataSource` boundary is intentionally important.

The preferred pattern is:

```text
Candidate IDs
      ↓
BatchDataSource.LoadDrivers(...)
      ↓
Driver Records
```

The pipeline should preserve this design.

---

# 49. Provider Reuse

The same infrastructure object may satisfy multiple small interfaces.

For example:

```text
Driver Cache
 ├── BatchDataSource
 └── OfferedDriverProvider
```

This is acceptable and useful when the underlying component already provides both capabilities.

The pipeline should still inject the narrow interfaces separately.

---

# 50. Candidate State

Candidate state should communicate its current processing condition without creating a second business lifecycle.

For example:

```text
Candidate
   ↓
Valid
   ↓
Eligible
   ↓
Ranked
```

The candidate state must not become a replacement for:

```text
Driver Lifecycle
Ride Lifecycle
Offer Lifecycle
```

---

# 51. Candidate Score

The candidate score belongs to the ranking output.

The pipeline should treat the score as a selection signal.

It must not interpret the score as:

```text
Reservation
Availability
Assignment
```

---

# 52. Candidate Metadata

Candidate metadata may carry discovery/pipeline context needed by downstream stages.

Metadata should remain bounded and relevant to the current candidate-processing operation.

Avoid turning candidate metadata into a general-purpose application state container.

---

# 53. Candidate Collection Lookup

`FindByID`-style candidate lookup is useful for associating batch-loaded driver records back to the corresponding candidate.

The lookup should remain efficient for the expected candidate population.

Do not introduce a more complicated indexing structure without a demonstrated need.

---

# 54. Driver Loader Association

The driver loader performs the association:

```text
Loaded Driver
      ↓
Candidate with same ID
      ↓
candidate.Driver = driver
```

If a returned driver is not present in the candidate collection, it should not create a new candidate.

---

# 55. Driver Loader Result Count

The existing implementation records:

```text
LoadedCandidates = len(drivers)
```

This is useful pipeline execution metadata.

If future semantics require distinguishing:

```text
Requested
Loaded
Missing
```

that should be introduced explicitly rather than changing the meaning of an existing field silently.

---

# 56. Filtering Cost

Filters should generally be ordered from:

```text
Cheap / high-value rejection
```

toward:

```text
More expensive processing
```

The current pipeline already reflects this principle.

Changes to stage order should be justified by:

```text
Correctness
Measured performance
New business requirement
```

not aesthetics.

---

# 57. Availability and Reservation Race

Passing the availability filter does not guarantee successful reservation.

The actual flow is:

```text
Availability Filter
      ↓
Candidate
      ↓
Ranking
      ↓
Reservation
      ↓
Possible Race
```

The reservation component remains authoritative for ownership.

---

# 58. Pipeline and Reservation

The candidate pipeline must not reserve drivers.

This preserves the important boundary:

```text
Pipeline
    =
Evaluate Candidates

Reservation
    =
Claim Candidate
```

A candidate should remain unowned until the dispatch engine explicitly attempts reservation.

---

# 59. Pipeline and Offers

The candidate pipeline must not create or send offers.

The final pipeline output is consumed by dispatch orchestration.

```text
Pipeline
   ↓
Ranked / Heap Candidates
   ↓
Dispatch Engine
   ↓
Reservation
   ↓
Offer
```

---

# 60. Pipeline and Retry

The candidate pipeline should not implement retry.

Retry belongs to dispatch policy/orchestration.

A pipeline execution either:

```text
Produces a result
```

or:

```text
Returns an error
```

The Dispatch Engine decides what happens next.

---

# 61. Pipeline and Discovery

The candidate pipeline consumes discovery output.

It should not repeat geographic discovery.

```text
Discovery
   ↓
Candidate IDs
   ↓
Pipeline
```

If a later architecture requires another discovery pass, that should be a new dispatch attempt or explicitly defined orchestration behaviour.

---

# 62. Pipeline and Ranking

The ranking stage provides the boundary between candidate processing and ranking implementation.

```text
Pipeline
   ↓
RankingStage
   ↓
Ranker
```

The ranker remains independently replaceable.

---

# 63. Testing Strategy

Each stage should be unit-testable with its narrow dependency interface.

Examples:

```text
DriverLoader
    → mock BatchDataSource

AlreadyOfferedFilter
    → mock OfferedDriverProvider

RankingStage
    → mock Ranker
```

This avoids requiring Redis/PostgreSQL for simple stage tests.

---

# 64. Pipeline Integration Tests

The pipeline should also have integration-level tests covering stage ordering and combined behaviour.

Important scenarios include:

```text
Valid Candidate
Invalid Candidate
Duplicate Candidate
Unavailable Candidate
Already Offered Candidate
Multiple Filtering Reasons
Ranking Result
Empty Result
Batch Load Failure
Offer Provider Failure
Ranking Failure
```

---

# 65. Performance Testing

Useful measurements include:

```text
Candidate Count
Batch Load Latency
Filter Latency
Ranking Latency
Total Pipeline Latency
Allocations
Heap Construction Cost
```

Tests should focus on realistic candidate populations rather than artificially huge inputs unless the production system requires them.

---

# 66. Observability

The pipeline should support stage-level observability where useful.

Potential metrics:

```text
Candidates Loaded
Candidates Validated
Duplicates Removed
Unavailable Removed
Already Offered Removed
Candidates Ranked
Final Candidates
Pipeline Duration
```

Tracing can capture stage durations without logging every candidate.

---

# 67. High-Cardinality Warning

Do not create metrics with labels such as:

```text
driver_id
ride_id
candidate_id
```

unless the observability architecture explicitly requires sampled tracing rather than metrics.

Candidate counts and aggregate timings are generally preferable.

---

# 68. Failure Classification

The pipeline should preserve the distinction between:

```text
No Candidates After Filtering
```

and:

```text
Pipeline Error
```

For example:

```text
20 candidates
→ 20 unavailable
→ 0 remaining
```

is a valid empty result.

Whereas:

```text
Driver Cache Failure
```

is an operational failure.

# 70. AI Agent Forbidden Patterns

An AI agent must not:

- create a second candidate pipeline,
- bypass the pipeline abstraction from the Dispatch Engine,
- move geographic discovery into pipeline stages,
- move reservation into the pipeline,
- create offers from pipeline stages,
- implement retry inside the pipeline,
- perform per-candidate driver loads when batch loading is available,
- combine unrelated filters into one large stage without a concrete reason,
- hard-code ranking weights inside pipeline stages,
- make H3 membership equivalent to availability,
- silently treat infrastructure errors as empty results,
- introduce unnecessary streaming abstractions when the current iterator is sufficient,
- add a stage solely to mark a roadmap item complete,
- reorder stages without documenting the correctness/performance reason.

The Candidate Pipeline is an established production-oriented component of RideForge.

The current architecture already provides:

```text
Candidate Collection
Iterator
Batch Driver Loading
Validation
Deduplication
Availability Filtering
Already-Offered Filtering

Heap Construction
```

The preferred approach is to strengthen these existing components where required rather than create parallel pipelines or duplicate filtering systems.

# 74. Final Component Rule

When an AI agent is asked to modify candidate processing, determine first:

```text
Is the change about:
    │
    ├── Candidate representation?
    │       → Candidate / Collection
    │
    ├── Driver data loading?
    │       → Driver Loader
    │
    ├── Structural validity?
    │       → Validation
    │
    ├── Duplicate identity?
    │       → Duplicate Filter
    │
    ├── Operational availability?
    │       → Availability Filter
    │
    ├── Existing offer?
    │       → Already-Offered Filter
    │
    ├── Score / ranking?
    │       → Ranking
    │
    └── Final best-candidate structure?
            → Heap Builder
```

The Candidate Pipeline should remain a **bounded, composable processing chain that converts discovered driver IDs into validated and ranked dispatch candidates**.

# 24. Dispatch Strategy and Configuration Clarifications

The Candidate Pipeline must implement the clarified RideForge dispatch model.

## 24.1 Strategy Resolution Happens Before the Pipeline

The Candidate Pipeline must receive the already-resolved effective dispatch strategy.

It must not independently resolve the configuration hierarchy.

```text
Ride Request
    ↓
Hierarchical Dispatch Configuration Resolution
    ↓
Effective Dispatch Strategy
    ↓
Candidate Discovery
    ↓
Candidate Pipeline
```

The hierarchy may contain levels such as:

```text
State
→ District
→ City / Town
→ Rural Area
→ Auto Stand
→ Ride-level
→ Other configured intermediate levels
```

The first explicit configuration found from the most specific applicable level upward takes precedence.

If no explicit configuration exists, the system default is used.

---

## 24.2 Smart Stand Dispatch

The Candidate Pipeline must treat **Smart Stand Dispatch as stand-preferred, not stand-exclusive**.

When the rider is inside a configured auto-stand radius:

```text
Preferred Stand Candidates
        ↓
Eligibility
        ↓
Stand Queue / Ordering Preference
        ↓
Suitable candidate?
```

If suitable stand supply is unavailable, the pipeline may receive and process broader eligible candidates, including:

```text
Drivers outside the preferred stand
Drivers at nearby stands
Drivers from nearby locations
```

The pipeline must not reject a candidate solely because the candidate is not physically at the preferred stand.

---

## 24.3 Smart Stand Dispatch Outside Stand Radius

If the rider is outside the radius of all configured auto stands, Smart Stand Dispatch must not create a stand-only candidate pool.

The candidate flow may include all eligible nearby drivers regardless of stand membership.

```text
No Applicable Stand Radius
        ↓
Eligible Nearby Drivers
        ↓
Normal Candidate Processing
```

---

## 24.4 Smart Dispatch

For Smart Dispatch, stand membership does not create a dispatch preference.

The pipeline may process:

```text
Drivers at stands
Drivers outside stands
Drivers from nearby locations
```

provided they satisfy the applicable eligibility and operational constraints.

---

## 24.5 Cross-Location Candidates

A candidate's location must not automatically become a hard eligibility boundary.

If local supply is insufficient:

```text
Origin Location
    ↓
Local Candidates
    ↓
Insufficient Suitable Supply
    ↓
Nearby Location Candidates
```

Candidates from nearby locations may enter the same pipeline.

The pipeline should preserve relevant source context, such as:

```text
Candidate Location
Candidate Location Strategy
Stand Membership
Relevant Stand
Queue Position
Discovery Source
Expansion Level
Distance
ETA
```

This context is required for downstream strategy-specific prioritization and ranking.

---

## 24.6 Candidate Eligibility vs Preference

The pipeline must distinguish between:

```text
Candidate is ineligible
```

and:

```text
Candidate is eligible but not currently preferred
```

Examples:

```text
Non-stand driver during Smart Stand Dispatch
    = potentially eligible, but not the initial preferred source

Driver from nearby location
    = potentially eligible, if geographic/legal/service constraints permit

Driver at preferred stand
    = preferred source when rider is inside that stand's radius
```

Therefore:

```text
Not Preferred ≠ Ineligible
```

---

## 24.7 Strategy Preservation During Expansion

Expanding candidate discovery must not silently change the resolved dispatch strategy.

For example:

```text
Effective Strategy:
Smart Stand Dispatch

Preferred stand unavailable
        ↓
Expand candidate discovery
        ↓
Consider broader candidates
```

The effective strategy remains:

```text
Smart Stand Dispatch
```

unless an explicit business/configuration rule defines another strategy.

Candidate expansion is not equivalent to switching to Smart Dispatch.

---

## 24.8 Candidate Pipeline Responsibility Boundary

The Candidate Pipeline is responsible for preparing and processing candidates for downstream prioritization/ranking.

It is not responsible for:

```text
Resolving configuration inheritance
Defining the effective dispatch strategy
Changing the resolved strategy
Applying final business assignment
```

The conceptual flow remains:

```text
Configuration Resolution
        ↓
Strategy Resolution
        ↓
Candidate Discovery
        ↓
Candidate Pipeline
        ↓
Strategy-Specific Prioritization
        ↓
Ranking / Selection
        ↓
Reservation
        ↓
Assignment
```

---

## 24.9 AI-Assisted Dispatch

AI-assisted dispatch is not a third primary dispatch strategy.

The pipeline must preserve the resolved strategy and candidate context whether downstream ranking uses:

```text
Deterministic Ranking
AI-Assisted Ranking
Hybrid Ranking
```

AI may optimize ranking or prediction, but it must not silently replace the configured strategy or override hard eligibility, legal, safety, or operational constraints.

---

## 24.10 Implementation Guardrails

Implementations must not:

```text
Treat Smart Stand Dispatch as stand-only.

Reject all non-stand candidates when a ride is inside a stand radius.

Reject candidates from nearby locations solely because their source location has a different dispatch strategy.

Resolve the location configuration hierarchy inside the Candidate Pipeline.

Hard-code a fixed State → District → Town → Stand hierarchy.

Treat candidate preference as candidate eligibility.

Switch Smart Stand Dispatch to Smart Dispatch merely because the preferred stand has no suitable driver.
```

The pipeline should instead preserve enough context for the downstream dispatch/ranking layer to make the final strategy-specific decision.
