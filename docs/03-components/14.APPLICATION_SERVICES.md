# 1. Purpose

Application Services implement RideForge use cases and orchestrate the components required to execute them.

They provide the primary boundary between:

```text
Transport / Events
        ↓
Application Service
        ↓
Domain + Infrastructure Capabilities
```

An application service answers:

```text
What operation is being performed?
```

and coordinates:

```text
Validation
State Loading
Business Operation
Persistence
Concurrency
Event Creation
Result Mapping
```

---

# 2. Application Service Boundary

Application services own:

```text
Use-Case Orchestration
Transaction Boundaries
Application-Level Validation
Dependency Coordination
State Transition Coordination
Event / Outbox Coordination
Result Construction
```

They do not own:

```text
HTTP Transport
Kafka Client Details
Redis Commands
SQL Queries
Provider SDK Details
Low-Level Serialization
```

Those belong to infrastructure or transport components.

---

# 3. Application Service vs Domain

The application layer coordinates a workflow.

The domain layer owns business rules that define the meaning of that workflow.

Conceptually:

```text
Application Service
      ↓
Domain Rule / Domain Object
      ↓
Persistence
```

The application service should not become a replacement for the domain model.

---

# 4. Application Service vs Infrastructure

Application services depend on capabilities.

For example:

```text
MatchingEngine
    ↓
DriverRepository
DriverLocker
CandidateSearcher
CandidatePipeline
OutboxRepository
```

The application service does not need to know:

```text
PostgreSQL SQL
Redis Commands
Kafka Client APIs
```

---

# 5. Use-Case Orientation

An application service should represent a meaningful application operation.

Examples include:

```text
Create Ride
Dispatch Ride
Accept Offer
Reject Offer
Cancel Ride
Update Driver Availability
Process Driver Location
```

The exact current service inventory in the repository is authoritative.

---

# 6. Application Service Lifecycle

A typical use case follows:

```text
Receive Request
      ↓
Validate Input
      ↓
Load Required State
      ↓
Apply Business Rules
      ↓
Persist State
      ↓
Persist Outbox Event if Required
      ↓
Return Result
```

External asynchronous work should occur after durable state has been established.

---

# 7. Input Validation

Application services should reject invalid application input early.

Examples:

```text
Missing Ride ID
Invalid Location
Invalid Driver ID
Unsupported State Transition
Invalid Request Parameters
```

Validation should remain appropriate to the application boundary.

Do not duplicate every domain invariant in every transport handler.

---

# 8. Business Rule Validation

Business rules should be evaluated at the correct ownership boundary.

For example:

```text
RideService
    → Ride lifecycle rules

MatchingEngine
    → Dispatch workflow

Reservation Component
    → Reservation ownership rules

Offer Component
    → Offer lifecycle
```

Do not place unrelated business rules into a generic service.

---

# 9. State Loading

Application services should load only the state required for the operation.

Avoid:

```text
Load Entire System State
```

when the use case needs:

```text
One Ride
One Driver
One Offer
```

This keeps transactions and memory usage bounded.

---

# 10. Transaction Ownership

When multiple durable operations must succeed atomically, the application service owns the transaction boundary.

Conceptually:

```text
Application Service
      ↓
Transaction
   ├── State Change
   ├── Related State Change
   └── Outbox Event
      ↓
Commit
```

Repositories participate in this transaction.

---

# 11. Transaction Scope

Transactions should be:

```text
Short
Explicit
Bounded
Purpose-Specific
```

Do not hold a transaction while waiting for:

```text
Driver Response
External API
Kafka
WebSocket
Long Retry
```

---

# 12. External Work After Commit

If an operation requires external work:

```text
Durable State
      ↓
Commit
      ↓
Outbox / Event
      ↓
Asynchronous Processing
```

This prevents long-running network operations from holding database locks.

---

# 13. Idempotency

Application services must consider duplicate requests and duplicate events.

Examples:

```text
Accept Offer
Accept Offer
```

should not create two assignments.

Likewise:

```text
RideCreated Event
RideCreated Event
```

should not create duplicate durable side effects.

---

# 14. Concurrency

Application services must assume concurrent execution.

Examples:

```text
Two Dispatch Nodes
Two Drivers Accepting
Driver Becomes Offline
Ride Gets Cancelled
Offer Expires
```

Concurrency must be protected by the appropriate combination of:

```text
Database Constraints
Conditional Updates
Transactions
Redis Atomic Operations
Reservations
Idempotency
```

---

# 15. Application Service Errors

Application services should expose meaningful errors.

Examples:

```text
Not Found
Invalid State
Conflict
No Candidate
Reservation Failed
Dependency Unavailable
Operation Timeout
```

Do not expose low-level infrastructure errors directly when they are not meaningful to the caller.

---

# 16. Error Classification

The application layer should distinguish:

```text
Expected Business Outcome
```

from:

```text
Unexpected Infrastructure Failure
```

For example:

```text
No eligible driver
```

is not necessarily an infrastructure error.

Whereas:

```text
Redis unavailable
```

is an infrastructure failure.

---

# 17. Application Service Composition

Services should receive dependencies explicitly.

Conceptually:

```text
NewMatchingEngine(
    driverRepository,
    driverLocker,
    outboxRepository,
    candidateSearcher,
    candidatePipeline,
    config,
    retryPolicy,
    logger,
)
```

The current constructor contract is authoritative.

---

# 18. Dependency Scope

Only inject dependencies actually required by the service.

Avoid:

```text
NewService(
    EntireApplicationContainer
)
```

Prefer explicit dependencies.

This makes:

```text
Responsibilities
Testing
Coupling
```

clear.

---

# 19. Matching Application Service

The Matching Engine is a central application-level dispatch orchestrator.

Conceptually:

```text
Ride
 ↓
Candidate Discovery
 ↓
Candidate Pipeline
 ↓
Ranking
 ↓
Reservation
 ↓
Offer
 ↓
Assignment
```

The Matching Engine coordinates these capabilities.

---

# 20. Matching Engine Responsibilities

The Matching Engine should coordinate:

```text
Candidate Search
Candidate Processing
Candidate Selection
Reservation
Offer Initiation
Retry / Dispatch Attempt
Ride State Coordination
Event Creation
```

It should not implement:

```text
Redis H3 Commands
SQL Queries
Ranking Mathematics
WebSocket Protocol
```

Those belong to their respective components.

---

# 21. Candidate Search Boundary

The Matching Engine asks the candidate search capability for candidates.

It should not know:

```text
H3 Grid Disk Internals
Redis Set Commands
Redis GEO Commands
```

The discovery subsystem owns geographic discovery.

---

# 22. Candidate Pipeline Boundary

The Matching Engine should delegate candidate processing to the candidate pipeline.

The pipeline owns:

```text
Filtering
Enrichment
Ranking Integration
Candidate Iteration
```

The Matching Engine owns the higher-level dispatch workflow.

---

# 23. Ranking Boundary

Ranking should remain isolated behind the Ranker contract.

Conceptually:

```text
MatchingEngine
      ↓
CandidatePipeline
      ↓
Ranker
```

The Matching Engine should not manually calculate ranking weights.

---

# 24. Reservation Boundary

Reservation provides temporary ownership.

Conceptually:

```text
Candidate
   ↓
Reserve
   ↓
Offer
```

The application service must treat reservation success as the prerequisite for initiating the corresponding offer.

---

# 25. Reservation Failure

If reservation fails because another dispatcher already owns the driver:

```text
Candidate
   ↓
Reservation Conflict
   ↓
Try Next Candidate
```

This is different from:

```text
Redis unavailable
```

which should follow infrastructure failure handling.

---

# 26. Offer Boundary

After successful reservation:

```text
Reserved Driver
      ↓
Offer Component
      ↓
Driver
```

The Matching Engine should not implement transport-specific offer delivery.

---

# 27. Offer Acceptance

Offer acceptance is a separate application operation.

Conceptually:

```text
Driver Response
      ↓
Application Service
      ↓
Validate Offer
      ↓
Confirm Assignment
      ↓
Persist Durable State
      ↓
Publish Event
```

The exact current acceptance flow is authoritative.

---

# 28. Offer Rejection

A rejection should:

```text
Validate Offer
      ↓
Record Response
      ↓
Release Ownership where required
      ↓
Continue Dispatch / Retry Policy
```

The application service must preserve the distinction between:

```text
Explicit Rejection
Timeout
Transport Failure
```

---

# 29. Offer Timeout

Offer timeout is an application event with operational scheduling.

Conceptually:

```text
Offer Created
      ↓
Timeout Scheduled
      ↓
No Response
      ↓
Offer Expired
      ↓
Release Reservation
      ↓
Continue Dispatch Policy
```

The timeout scheduler should not independently mutate unrelated business state.

---

# 30. Ride Cancellation

Ride cancellation must coordinate affected state.

Conceptually:

```text
Cancel Ride
   ↓
Validate Ride State
   ↓
Persist Cancellation
   ↓
Release Active Ownership where required
   ↓
Create Outbox Event
   ↓
Commit
```

Any asynchronous cleanup should follow the durable cancellation state.

---

# 31. Driver Availability

Driver availability changes should be coordinated with realtime and operational state.

The application service should distinguish:

```text
Online
Offline
Available
Busy
Reserved
```

according to the current driver-state model.

---

# 32. Driver Location

Driver location processing is a high-frequency application operation.

The service should coordinate:

```text
Validate Update
      ↓
Update Operational Driver State
      ↓
Update Geographic Index
```

The implementation must remain optimized for high update volume.

---

# 33. Location Update Failure

A location-update infrastructure failure should not be represented as:

```text
Invalid Location
```

unless the location itself is invalid.

The application layer must preserve the distinction between:

```text
Invalid Input
```

and:

```text
Infrastructure Failure
```

---

# 34. Event Creation

When a use case produces a durable domain/application event:

```text
Application Service
      ↓
Outbox Repository
```

The event should be persisted in the same transaction as the state change when atomicity is required.

---

# 35. Event Ownership

The application service owns the decision:

```text
Which event should be emitted?
```

The messaging infrastructure owns:

```text
How the event is transported.
```

This distinction is fundamental.

---

# 36. Application Events

Events should represent completed facts.

For example:

```text
RideCreated
OfferCreated
OfferAccepted
RideCancelled
AssignmentCreated
```

Do not publish an event claiming something happened before the durable operation succeeded.

---

# 37. Transactional Event Flow

Correct:

```text
Application Service
      ↓
Transaction
 ├── Business State
 └── Outbox Event
      ↓
Commit
      ↓
Publisher
      ↓
Broker
```

Incorrect:

```text
Kafka Publish
      ↓
Database Commit
```

when the event must represent durable state.

---

# 38. Retry Coordination

Application-level retry is a policy decision.

For dispatch:

```text
Attempt
   ↓
Candidate Availability
   ↓
Reservation / Offer Result
   ↓
Retry Decision
```

Retry policy should not be duplicated across:

```text
MatchingEngine
CandidatePipeline
Reservation
Offer
```

There should be one clear owner for each retry decision.

---

# 39. Configuration-Driven Policy

Operational policies should be configuration-driven where appropriate.

Examples:

```text
Retry Limits
Offer Timeout
Search Limits
Reservation TTL
Ranking Weights
Dispatch Limits
```

Do not hard-code deployable operational policy inside application services.

---

# 40. Application Service Logging

Application services should log meaningful business-operation boundaries.

Examples:

```text
Dispatch Started
Dispatch Failed
Offer Accepted
Ride Cancelled
Assignment Created
```

Avoid logging every internal helper call.

# 41. Application Service Metrics

Use Case Latency

# 43. Application Service Testing

Application services should have unit tests for orchestration behaviour.

Tests should verify:

```text
Correct Dependency Called
Correct Order
Correct Error Handling
Correct State Transition
Correct Event Creation
Correct Retry Behaviour
```

---

# 44. Application Integration Tests

Integration tests should verify cross-component behaviour where orchestration correctness depends on real infrastructure.

Examples:

```text
Dispatch + Redis Reservation
State Change + Outbox
Offer Acceptance + PostgreSQL
Driver Location + H3
Consumer + Application Service
```

---

# 45. Application Service Test Doubles

Use narrow fakes/stubs for external dependencies when testing orchestration.

For example:

```text
Fake CandidateSearcher
Fake Ranker
Fake DriverLocker
Fake Repository
Fake Outbox
Fake Offer Gateway
```

Do not mock internal pure business logic unnecessarily.

---

# 46. Transaction Tests

A service that coordinates multiple durable operations should have rollback tests.

Example:

```text
State Update
+
Outbox Insert
```

If the outbox insert fails:

```text
State Update
→ Rollback
```

---

# 47. Concurrency Tests

Concurrency-sensitive application services should test races such as:

```text
Two Accepts
Two Reservations
Cancel During Offer
Timeout During Accept
Duplicate Event
Duplicate Request
```

The goal is to prove one consistent business outcome.

---

# 48. Application Service Anti-Corruption

Infrastructure-specific concepts should not leak into application contracts.

Avoid application APIs containing:

```text
Redis Pipeline
Kafka Offset
PostgreSQL Connection
Provider SDK Response
```

Instead use application-level concepts:

```text
Candidate
Reservation
Offer
Ride
Driver
Assignment
```

---

# 49. Application Service Size

An application service may coordinate a complex use case, but should not become a "god service."

If a service begins owning:

```text
Discovery
Ranking
Reservation
Realtime
Persistence
Messaging
```

internally, separate those responsibilities behind focused components.

The application service orchestrates them.

---

# 50. Application Service vs Domain Service

Use a domain service when a rule represents domain behaviour that does not naturally belong to one entity/value object.

Use an application service when the requirement is primarily:

```text
Coordinate a Use Case
```

The distinction prevents application services from becoming repositories for arbitrary business logic.

---

# 51. Application Service vs Handler

Transport/event handlers adapt external input to application calls.

Conceptually:

```text
HTTP Handler
    ↓
Application Service

Kafka Consumer
    ↓
Application Service
```

Handlers should remain thin.

---

# 52. HTTP Boundary

HTTP handlers should generally perform:

```text
Decode
Validate Transport Input
Authenticate / Authorize where applicable
Call Application Service
Map Result
```

They should not duplicate use-case logic.

---

# 53. Event Consumer Boundary

Event consumers should perform:

```text
Decode Event
Validate Envelope
Call Application Service
Acknowledge on Success
```

Business processing belongs in the application service.

---

# 54. Realtime Boundary

Realtime handlers should perform:

```text
Decode Driver Message
Validate Message
Call Application Service
Return Transport Response
```

They should not directly mutate PostgreSQL or Redis unless the architecture explicitly defines that handler as the owning application component.

---

# 55. Application Service Return Values

Return application-level results.

Examples:

```text
Ride
Assignment
Offer
Dispatch Result
Reservation Result
```

Do not expose:

```text
sql.Rows
redis.Result
kafka.Message
```

through application APIs.

---

# 56. Application Service Error Mapping

Transport layers may map application errors into protocol-specific responses.

For example:

```text
Application Conflict
      ↓
HTTP 409
```

or:

```text
Application Not Found
      ↓
HTTP 404
```

The application service should not return HTTP-specific errors merely because one caller is HTTP.

---

# 57. Multi-Transport Reuse

The same application service may be called by:

```text
HTTP
Realtime
Kafka Consumer
Background Worker
```

This is a major reason to keep transport-specific logic outside the application layer.

---

# 58. Application Service Security Boundary

Authorization decisions that depend on the use case should be enforced at an appropriate application boundary.

For example:

```text
Driver may accept own offer
```

must not depend solely on the transport handler.

The exact authorization architecture is defined elsewhere.

---

# 59. Application Service Data Ownership

An application service should modify state through the component that owns that state.

For example:

```text
Ride State
    → Ride application/domain component

Reservation
    → Reservation component

Driver operational state
    → Driver/realtime component
```

Avoid direct cross-component writes that bypass ownership.

---

# 60. AI Agent Implementation Rules

Before modifying an application service, an AI coding agent must:

1. Read this document.
2. Read the relevant domain and architecture documentation.
3. Identify the exact use case being changed.
4. Identify the state owner for every state being modified.
5. Identify the transaction boundary.
6. Identify required domain rules.
7. Identify existing application services before creating a new one.
8. Identify existing repository interfaces.
9. Identify existing event/outbox contracts.
10. Identify concurrency protections.
11. Preserve transport independence.
12. Keep infrastructure details outside the service.
13. Keep operational policy configuration-driven.
14. Add unit tests for orchestration.
15. Add integration/concurrency tests when the changed workflow requires them.
16. Run the relevant test suite before completion.

---

# 61. AI Agent Forbidden Patterns

An AI agent must not:

- put SQL inside application services,
- issue raw Redis commands from application services,
- call Kafka clients directly from application services,
- put HTTP response types into application contracts,
- put transport-specific validation into domain rules,
- create a god service,
- duplicate existing use-case orchestration,
- bypass repositories,
- bypass reservation ownership,
- publish durable events before the required transaction commits,
- hold database transactions during external network operations,
- silently swallow infrastructure failures,
- treat duplicate requests as automatically safe,
- hard-code operational retry/timeout policy,
- move ranking mathematics into the Matching Engine,
- move geographic search implementation into the Matching Engine,
- move broker mechanics into event handlers.

# 68. Dispatch Strategy Resolution in Application Orchestration

For ride dispatch, the application layer must resolve the effective dispatch strategy before the dispatch workflow is executed.

The application service is responsible for coordinating the resolution, but the hierarchy/configuration ownership remains in the dedicated configuration capability.

Conceptually:

```text
Create / Dispatch Ride
        ↓
Identify Applicable Configuration Context
        ↓
Resolve Effective Dispatch Strategy
        ↓
Invoke Matching / Dispatch Engine
```

The application layer must not hard-code a fixed hierarchy such as:

```text
State → District → Town → Stand
```

The supported hierarchy may contain:

```text
State
District
City / Town
Rural Area
Auto Stand
Specific Ride Level
Other configured intermediate levels
```

The resolution rule is:

```text
Most Specific Applicable Level
        ↓
Explicit Dispatch Strategy?
   ├── YES → Use It
   └── NO
        ↓
Move to Parent
        ↓
Continue Until Explicit Strategy Is Found
        ↓
System Default if None Exists
```

The nearest explicit configuration always takes precedence.

---

# 69. Dispatch Strategy Context

Once resolved, the effective dispatch strategy should be passed into the dispatch workflow as explicit application context.

For example:

```text
DispatchContext
├── EffectiveStrategy
├── OriginLocation
├── ConfigurationContext
├── ApplicableStandContext
└── DispatchAttemptContext
```

The application service should preserve this context across the dispatch workflow.

It must not silently replace the effective strategy because a particular candidate search or retry attempt produced no result.

---

# 70. Smart Stand Dispatch Application Flow

When the effective strategy is **Smart Stand Dispatch**, the application workflow must preserve the stand-preferred semantics.

```text
Ride
 ↓
Resolve Smart Stand Dispatch
 ↓
Determine Whether Pickup Is Inside a Configured Stand Radius
 ↓
If Yes:
    Prefer Eligible Drivers at the Relevant Stand
    ↓
    Apply Stand Queue / Ordering Rules
 ↓
If No Suitable Stand Driver:
    Expand Candidate Discovery
 ↓
Consider Other Eligible Candidates
```

Broader candidates may include:

```text
Drivers outside the preferred stand
Drivers from nearby stands
Drivers from nearby locations
```

If the rider is outside all configured stand radii, the application workflow must not create a stand-only candidate pool.

The key rule is:

```text
Smart Stand Dispatch
=
Stand Preferred
≠
Stand Exclusive
```

---

# 71. Smart Dispatch Application Flow

When the effective strategy is **Smart Dispatch**, the application service invokes the normal stand-agnostic dispatch workflow.

```text
Ride
 ↓
Resolve Smart Dispatch
 ↓
Discover Eligible Nearby Drivers
 ↓
Candidate Pipeline
 ↓
Ranking
 ↓
Reservation
 ↓
Offer
```

Auto-stand membership does not create an implicit preference under Smart Dispatch.

Any eligible driver may be considered according to the applicable discovery, eligibility, ranking, and operational rules.

---

# 72. Cross-Location Dispatch Orchestration

The application service must support dispatch workflows in which candidate discovery expands beyond the ride's originating location.

For example:

```text
Location A
Smart Dispatch
        ↓
No Suitable Local Candidate
        ↓
Expand Geographic Discovery
        ↓
Location B
Smart Stand Dispatch
        ↓
Evaluate Eligible Drivers from B
```

A candidate from Location B is not automatically rejected because:

```text
Candidate Location ≠ Ride Origin Location
```

The candidate's source context should remain available:

```text
Candidate Location
Candidate Location Strategy
Stand Membership
Relevant Stand
Queue Position
Discovery Source
Distance / ETA
```

The application layer coordinates this context; the final strategy-specific prioritization remains with the appropriate dispatch/ranking components.

---

# 73. Strategy and Candidate Discovery Separation

Application services must preserve the distinction between:

```text
Dispatch Strategy Resolution
```

and:

```text
Candidate Discovery Scope
```

The effective strategy determines how candidates should be prioritized and dispatched.

Candidate discovery determines where eligible candidates may be found.

Therefore:

```text
Dispatch Strategy
≠
Candidate Pool Boundary
```

For example:

```text
Smart Stand Dispatch
        ↓
Preferred Stand
        ↓
No Suitable Supply
        ↓
Broader Candidate Discovery
```

This is still **Smart Stand Dispatch**.

Expanding candidate discovery must not silently change the effective strategy to Smart Dispatch.

---

# 74. Application-Level Retry and Dispatch Expansion

Dispatch retry may expand candidate discovery according to the configured retry/expansion policy.

For example:

```text
Attempt 1
    ↓
Preferred Stand Candidates
    ↓
No Suitable Candidate
    ↓
Attempt 2
    ↓
Broader Eligible Candidates
    ↓
Attempt 3
    ↓
Nearby Location Candidates
```

This represents candidate-pool expansion, not automatic strategy switching.

The application service must preserve:

```text
Effective Dispatch Strategy
```

across retries unless an explicit configuration/business rule defines a strategy change.

Retry ownership must remain centralized according to the existing retry architecture and must not be independently reimplemented by the Candidate Pipeline, Ranking Engine, Reservation component, or Offer component.

---

# 75. Application Service and Stand Queue Ownership

The application service coordinates the dispatch workflow but must not duplicate stand queue implementation.

The separation should remain:

```text
Application Service
    ↓
Dispatch Engine
    ↓
Candidate / Stand Context
    ↓
Strategy-Specific Prioritization
```

The application service should not implement:

```text
Redis queue commands
Stand queue storage
Ranking mathematics
Geospatial search internals
```

It should only coordinate the use case and preserve the required dispatch context.

---

# 76. Application Service and Configuration Ownership

Configuration inheritance must remain owned by the configuration capability.

The application service may request:

```text
ResolveDispatchStrategy(configurationContext)
```

but should not contain logic such as:

```text
if standConfig exists ...
else if townConfig exists ...
else if districtConfig exists ...
```

The configuration capability should return the effective strategy and relevant configuration context.

This keeps configuration inheritance reusable and prevents duplicate resolution logic across application services.

---

# 77. AI-Assisted Dispatch in Application Orchestration

AI-assisted dispatch is not a third primary dispatch strategy.

The application service should first resolve one of the configured primary strategies:

```text
Smart Stand Dispatch
OR
Smart Dispatch
```

AI may then be used by the applicable ranking/optimization components.

Conceptually:

```text
Resolve Strategy
        ↓
Execute Strategy
        ↓
Candidate Discovery / Processing
        ↓
AI-Assisted Ranking where enabled
        ↓
Reservation
        ↓
Offer
```

AI must not override:

```text
Hard Eligibility
Legal / Regional Constraints
Safety Constraints
Authoritative Driver State
Reservation Ownership
```

---

# 78. Application-Level Dispatch Context Contract

The dispatch application workflow should preserve enough context for downstream components to make correct decisions.

At minimum, the context should be capable of representing:

```text
Effective Dispatch Strategy
Origin Location
Applicable Configuration Level
Applicable Stand
Stand Radius Result
Candidate Source Location
Candidate Source Strategy
Stand Membership
Queue Position
Discovery Expansion Level
Dispatch Attempt
```

Not every field needs to be populated for every ride.

For example:

```text
Smart Dispatch
    → Applicable Stand may be absent

Smart Stand Dispatch outside stand radius
    → Stand Radius Result = No Applicable Stand

Cross-Location Candidate
    → Candidate Source Location differs from Origin Location
```

---

# 79. Application Service Guardrails for Dispatch

An AI coding agent modifying application services must not:

- implement Smart Stand Dispatch as a stand-only candidate pool,
- reject non-stand drivers solely because the rider is inside a stand radius,
- reject nearby-location drivers solely because their location uses another dispatch strategy,
- resolve hierarchical configuration through hard-coded geographic conditionals,
- switch Smart Stand Dispatch to Smart Dispatch merely because the preferred stand has no suitable driver,
- move geospatial discovery into the application service,
- move ranking mathematics into the application service,
- duplicate stand queue implementation in the application service,
- bypass the configuration capability,
- bypass the Candidate Pipeline,
- bypass reservation ownership,
- allow AI to override hard eligibility or legal constraints.

The application service should remain an orchestrator:

```text
Resolve Context
    ↓
Invoke Dispatch Capability
    ↓
Coordinate Result
    ↓
Persist Durable State
    ↓
Create Outbox Event when required
```

---

# 80. Canonical Dispatch Application Workflow

The complete application-level dispatch flow is:

```text
Ride Request
    ↓
Application Service
    ↓
Resolve Hierarchical Dispatch Configuration
    ↓
Resolve Effective Dispatch Strategy
    ↓
Create Dispatch Context
    ↓
Dispatch Engine
    ↓
Candidate Discovery
    ↓
Candidate Pipeline
    ↓
Strategy-Specific Prioritization / Ranking
    ↓
Reservation
    ↓
Offer
    ↓
Driver Response
    ↓
Assignment
    ↓
Durable State Change
    ↓
Outbox Event
```

The key architectural rule is:

```text
Configuration Resolution
        ↓
Strategy Resolution
        ↓
Strategy Execution
        ↓
Candidate Discovery
        ↓
Candidate Processing / Ranking
        ↓
Reservation / Offer / Assignment
```

No application service should collapse these responsibilities into one implementation.
