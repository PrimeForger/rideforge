# RideForge — Event and Messaging Components

# 1. Purpose

The Event and Messaging Components provide asynchronous communication between RideForge components and services.

They support:

```text
Domain Events
      ↓
Outbox
      ↓
Event Publisher
      ↓
Kafka / Redpanda
      ↓
Event Consumer
      ↓
Application Handler
```

The messaging layer exists to decouple asynchronous workflows without moving business ownership into the message broker.

---

# 2. Messaging Boundary

The messaging subsystem owns:

```text
Event Publishing
Event Consumption
Topic Configuration
Consumer Groups
Outbox Delivery
Retry Handling
Dead-Letter Handling
Message Serialization
Message Metadata
Consumer Lifecycle
```

It does not own:

```text
Business Decisions
Ride Assignment
Driver Ranking
Reservation Policy
Offer Policy
Database Domain Rules
```

---

# 3. Event-Driven Principle

Events represent facts that have already occurred.

Examples:

```text
Ride Created
Ride Cancelled
Driver Assigned
Offer Created
Offer Accepted
Offer Rejected
```

An event should not be used as an indirect command when a direct application service call is the correct mechanism.

---

# 4. Command vs Event

The architecture distinguishes:

```text
Command
    =
"Please perform this operation."

Event
    =
"This operation already happened."
```

For example:

```text
CreateRide
```

is a command.

After successful creation:

```text
RideCreated
```

is an event.

---

# 5. Event Envelope

Events should use a stable envelope containing the metadata required for reliable asynchronous processing.

Conceptually:

```text
Event Envelope
├── Event ID
├── Event Type
├── Aggregate / Entity ID
├── Occurred At
├── Correlation ID
├── Causation ID where applicable
├── Version
└── Payload
```

The exact current envelope type in code is authoritative.

---

# 6. Event ID

Every published event should have a unique event identifier.

The identifier supports:

```text
Tracing
Deduplication
Debugging
Consumer Idempotency
```

An event ID should remain stable when the same event is retried.

---

# 7. Correlation ID

Correlation IDs connect related operations across asynchronous boundaries.

Conceptually:

```text
Ride Request
    ↓
Correlation ID
    ↓
Ride Event
    ↓
Matching
    ↓
Offer
    ↓
Driver Response
```

This allows an entire dispatch flow to be traced across services.

---

# 8. Causation ID

Where supported, causation identifies the event or command that caused the current event.

Conceptually:

```text
Command
   ↓
Event A
   ↓
Event B
```

`Event B` can retain the identity of `Event A` as its cause.

This is useful for debugging asynchronous workflows.

---

# 9. Event Type

Event types must be explicit and stable.

Examples:

```text
ride.created
ride.cancelled
match.created
offer.created
offer.accepted
offer.rejected
```

The actual topic/event naming convention defined by the current repository is authoritative.

Do not introduce arbitrary naming conventions inside individual consumers.

---

# 10. Event Version

Event schemas may evolve.

A version field allows consumers to distinguish:

```text
Version 1
Version 2
```

without requiring all consumers to upgrade simultaneously.

Schema evolution should remain backward-compatible where practical.

---

# 11. Outbox Pattern

Business state changes that must reliably produce events should use the Outbox Pattern.

Conceptually:

```text
Database Transaction
 ├── Business State Change
 └── Outbox Event
        ↓
   Commit
        ↓
Outbox Publisher
        ↓
Kafka / Redpanda
```

The business change and event record are committed atomically.

---

# 12. Why Outbox Exists

Without an outbox:

```text
Database Commit
      ↓
Kafka Publish
      ↓
Failure
```

can produce:

```text
Business state changed
BUT
Event never published
```

The outbox prevents this gap by persisting the event alongside the business transaction.

---

# 13. Outbox Repository

The Outbox Repository is responsible for durable outbox persistence.

Its responsibilities include:

```text
Insert Event
Fetch Pending Events
Mark Published
Track Attempts
Support Recovery
```

The repository should not contain business decision logic.

---

# 14. Outbox Publisher

The publisher reads pending events and publishes them to the configured message broker.

Conceptually:

```text
Outbox Repository
      ↓
Pending Events
      ↓
Event Publisher
      ↓
Kafka / Redpanda
```

The publisher must tolerate transient broker failures.

---

# 15. Outbox Delivery

An event should remain recoverable until the system has successfully completed the configured publication acknowledgement.

Conceptually:

```text
Pending
   ↓
Publish Attempt
   ├── Success → Published
   └── Failure → Retry
```

The exact delivery-state model in code is authoritative.

---

# 16. At-Least-Once Delivery

The outbox architecture naturally supports at-least-once delivery.

Therefore consumers must assume:

```text
Same Event
   ↓
May Be Delivered More Than Once
```

Consumer handlers must be idempotent.

---

# 17. Consumer Idempotency

A consumer should not produce duplicate business effects when the same event is received more than once.

For example:

```text
OfferAccepted
OfferAccepted
```

must not create two assignments.

The consumer/application service should use an appropriate idempotency mechanism.

---

# 18. Event Consumer

The Event Consumer is responsible for:

```text
Receiving Messages
Deserializing Events
Validating Envelope
Calling Application Handler
Acknowledging Successful Processing
Retrying Failures
```

It should not contain domain business rules directly.

---

# 19. Consumer Group

Consumers should use consumer groups where multiple instances share workload.

Conceptually:

```text
Topic
  ↓
Consumer Group
  ├── Consumer A
  ├── Consumer B
  └── Consumer C
```

The broker distributes partitions among the group.

---

# 20. Partitioning

Partition keys should preserve ordering where the business flow requires it.

Potential keys include:

```text
Ride ID
Driver ID
Aggregate ID
```

The correct key depends on the event stream's ordering requirement.

Do not choose partition keys solely for even distribution if ordering is required.

---

# 21. Ordering

Kafka/Redpanda ordering is guaranteed within a partition, not globally across a topic.

Therefore:

```text
Same Aggregate
   ↓
Same Partition Key
```

should be used when ordered processing is required.

---

# 22. Event Ordering Example

For one ride:

```text
RideCreated
   ↓
MatchStarted
   ↓
OfferCreated
   ↓
OfferAccepted
```

If these events require ordered processing, their partitioning strategy must preserve that ordering.

---

# 23. Cross-Aggregate Ordering

Do not assume global ordering between unrelated aggregates.

For example:

```text
Ride A Event
Ride B Event
```

may be processed in a different order across partitions.

Business logic should not depend on global event ordering unless explicitly designed for it.

---

# 24. Message Serialization

Event payloads should use a stable serialization format.

The current repository's event codec/serialization contract is authoritative.

Serialization should be:

```text
Deterministic
Explicit
Versionable
Compact
```

---

# 25. Deserialization

Consumers must treat incoming messages as untrusted external input.

The consumer should validate:

```text
Envelope
Event Type
Required Fields
Version
Payload
```

before passing the event to an application handler.

---

# 26. Invalid Message

An invalid message should not be acknowledged as successfully processed if doing so would silently discard a required business event.

Depending on failure classification, it should be:

```text
Retried
or
Sent to DLQ
```

according to the messaging failure policy.

---

# 27. Retry

Transient processing failures may be retried.

Examples:

```text
Temporary Database Failure
Temporary Redis Failure
Temporary Downstream Service Failure
```

Retries should be bounded.

Do not retry indefinitely.

---

# 28. Retry Classification

Failures should be classified into:

```text
Transient
Permanent
Unknown
```

Transient failures may be retried.

Permanent failures should generally move toward DLQ handling.

Unknown failures should follow the configured safe failure policy.

---

# 29. Dead Letter Queue

The DLQ stores messages that cannot be successfully processed after the configured retry policy.

Conceptually:

```text
Message
   ↓
Consumer
   ↓
Failure
   ↓
Retry
   ↓
Retry Exhausted
   ↓
DLQ
```

The DLQ prevents a permanently failing message from blocking normal processing indefinitely.

---

# 30. DLQ Event Metadata

A DLQ message should preserve enough information to diagnose the original failure.

Useful metadata includes:

```text
Original Event ID
Event Type
Original Topic
Partition
Offset where available
Failure Reason
Attempt Count
Timestamp
Original Payload
```

The exact current DLQ envelope is authoritative.

---

# 31. DLQ Is Not Data Loss

A message in the DLQ is not automatically discarded.

It represents:

```text
Processing Requires Investigation / Recovery
```

Operational tooling may later support:

```text
Inspect
Repair
Replay
Discard
```

according to policy.

---

# 32. Event Publisher and DLQ

Publishing failures and consumer-processing failures are different failure domains.

```text
Outbox Publish Failure
    → Outbox Retry / Publisher Recovery

Consumer Processing Failure
    → Consumer Retry / DLQ
```

Do not merge these into one generic failure mechanism.

---

# 33. Broker Abstraction

Application components should not depend directly on low-level Kafka/Redpanda client APIs.

The preferred boundary is:

```text
Application
    ↓
Producer / Consumer Abstraction
    ↓
Kafka / Redpanda Client
```

This keeps broker implementation details localized.

---

# 34. Kafka and Redpanda

The architecture is designed to remain compatible with Kafka-compatible brokers.

The current production-oriented deployment uses Kafka-compatible messaging infrastructure.

The application should depend on messaging contracts rather than vendor-specific behaviour wherever practical.

---

# 35. Producer

The producer is responsible for:

```text
Serialize Event
Select Topic
Select Partition Key
Publish Message
Handle Broker Result
```

It should not decide whether a business operation should happen.

---

# 36. Producer Lifecycle

Producer initialization should be controlled by application bootstrap.

Conceptually:

```text
Configuration
   ↓
Producer Construction
   ↓
Connection
   ↓
Application Start
```

Shutdown should flush/close producer resources according to the broker client contract.

---

# 37. Consumer Lifecycle

Consumer lifecycle should support:

```text
Start
Run
Handle Messages
Retry
Shutdown
```

Graceful shutdown should stop accepting new work and allow already-running processing to finish according to configured limits.

---

# 38. Consumer Cancellation

Consumers should respect application context cancellation.

Conceptually:

```text
Application Shutdown
      ↓
Context Cancel
      ↓
Consumer Stops
      ↓
Resources Close
```

No consumer should remain indefinitely blocked during application shutdown.

---

# 39. Message Acknowledgement

A message should be acknowledged only after the required processing succeeds.

Conceptually:

```text
Receive
  ↓
Process
  ↓
Success
  ↓
Acknowledge
```

Acknowledging before processing can create message loss.

---

# 40. Database Transaction and Acknowledgement

Where consumer processing modifies durable state:

```text
Message
   ↓
Database Transaction
   ↓
Commit
   ↓
Acknowledge
```

The consumer should not acknowledge before the durable business change succeeds.

---

# 41. Consumer Crash

If the consumer crashes after committing business state but before acknowledging the message:

```text
Message Re-delivered
```

This is expected under at-least-once processing.

Idempotent application handling prevents duplicate business effects.

---

# 42. Consumer Crash Before Commit

If the consumer crashes before the business transaction commits:

```text
Message Re-delivered
```

The event can be processed again.

This is the desired recovery behaviour.

---

# 43. Event Handler Boundary

The consumer should translate a message into an application-level event/command and delegate processing.

Conceptually:

```text
Broker Consumer
      ↓
Event Decoder
      ↓
Application Handler
      ↓
Domain / Repository
```

Business logic belongs in the application/domain layer.

---

# 44. Event Handlers

Each event handler should have a focused responsibility.

Avoid:

```text
One Giant Event Handler
```

Prefer:

```text
RideCreatedHandler
OfferAcceptedHandler
RideCancelledHandler
```

where the domain actually requires separate behaviours.

---

# 45. Event Handler Idempotency

Idempotency should be implemented at the business-effect boundary.

Do not rely solely on:

```text
Consumer offset
```

because the same business event may be delivered again.

---

# 46. Event Replay

A well-designed event consumer should be able to process a historical event where the business contract allows replay.

Replay should not:

```text
Create Duplicate Assignment
Duplicate Payment
Duplicate Offer
```

Idempotency and state validation are therefore essential.

---

# 47. Event Schema Evolution

When an event changes:

```text
Do Not Break Existing Consumers
```

Prefer additive evolution:

```text
Existing Field
+
Optional New Field
```

Breaking changes require an explicit versioning/migration strategy.

---

# 48. Removing Event Fields

Removing or renaming an event field can break older consumers.

Before removing a field:

```text
Find All Consumers
      ↓
Verify Compatibility
      ↓
Migrate
      ↓
Remove
```

The event contract should be treated as an API.

---

# 49. Topic Ownership

Each topic should have a documented owner and purpose.

Conceptually:

```text
ride.events
    → Ride lifecycle events

match.events
    → Matching/dispatch events

ride.events.dlq
    → Failed ride event processing
```

The exact current topic inventory is authoritative.

---

# 50. Topic Naming

Topic names should remain consistent across environments.

Do not invent environment-specific names inside business code.

Environment prefixes/suffixes, if used, belong to messaging configuration.

---

# 51. Event Producer Placement

Business services should produce events through the event/outbox boundary.

Avoid direct broker access from domain entities.

Correct:

```text
Application Service
   ↓
Outbox Repository
   ↓
Publisher
```

Incorrect:

```text
Domain Entity
   ↓
Kafka Client
```

---

# 52. Outbox and Domain Transaction

If an event is required as a consequence of a database state change:

```text
Application Service
      ↓
Database Transaction
      ├── Domain State
      └── Outbox
```

This ensures that:

```text
State exists
```

and:

```text
Event exists
```

or neither is committed.

---

# 53. Outbox Publisher Retry

If broker publication fails:

```text
Outbox Event
   ↓
Retry Later
```

The publisher should not lose the event.

Retry scheduling/backoff must be configuration-driven.

---

# 54. Duplicate Publication

A publisher retry can result in the same event being published more than once.

Therefore:

```text
Outbox
   ↓
At-Least-Once
```

is expected.

Consumers must remain idempotent.

---

# 55. Message Size

Events should contain only the data required by consumers.

Avoid embedding:

```text
Large Domain Aggregates
Entire Driver Profiles
Large Location Histories
Unrelated Metadata
```

Small messages improve broker throughput and consumer latency.

---

# 56. Sensitive Data

Events should contain only the minimum data required for downstream processing.

Do not publish sensitive data merely because it is available in the source aggregate.

Event schemas should follow the project's privacy and security requirements.

---

# 57. Event Observability

At least one integration test should prove:

```text

   ↓
Processed Twice
   ↓
One Business Effect
```

This is a core correctness requirement of the event-driven architecture.

# 65. Failure Handling Matrix

| Failure | Expected Handling |
|---|---|
| Temporary broker failure | Retry publish |
| Outbox publish failure | Keep event pending/retry |
| Temporary consumer dependency failure | Retry |
| Invalid permanent event | DLQ |
| Duplicate event | Idempotent processing |
| Consumer crash before commit | Redelivery |
| Consumer crash after commit/before ack | Redelivery + idempotent handling |
| Graceful shutdown | Stop/close cleanly |

# 67. AI Agent Forbidden Patterns

An AI agent must not:

- publish directly from domain entities,
- bypass the outbox for required durable events,
- assume exactly-once delivery,
- acknowledge messages before successful processing,
- retry indefinitely,
- silently discard malformed events,
- treat the DLQ as a normal success path,
- create a new topic without documenting its ownership and purpose,
- introduce arbitrary event naming conventions,
- break existing event consumers without a migration plan,
- put large domain aggregates into events,
- expose sensitive data unnecessarily,
- put business rules inside broker consumers,
- introduce a second messaging abstraction for the same broker,
- replace Kafka/Redpanda with another broker without an architectural decision,
- use events to replace simple synchronous calls without a real decoupling requirement.

# 69. Component Responsibility Matrix

| Component | Responsibility | Must Not Own |
|---|---|---|
| Event Envelope | Stable event metadata | Business decisions |
| Outbox Repository | Durable pending events | Broker delivery |
| Outbox Publisher | Publish pending events | Domain rules |
| Producer | Broker publication | Event business semantics |
| Consumer | Receive/decode messages | Domain decisions |
| Event Handler | Application processing | Broker mechanics |
| DLQ Handler | Failed message isolation | Normal business workflow |
| Consumer Group | Parallel consumption | Global ordering |
| Topic | Event transport boundary | Domain state |
| Application Service | Business state transition | Kafka internals |

# 72. Final Component Rule

When an AI agent is asked to modify event/messaging behaviour, determine first:

```text
Is the change about:
    │
    ├── Creating a durable event?
    │       → Application Transaction + Outbox
    │
    ├── Publishing an event?
    │       → Outbox Publisher / Producer
    │
    ├── Consuming an event?
    │       → Consumer
    │
    ├── Applying business effects?
    │       → Application Event Handler
    │
    ├── Retrying failed processing?
    │       → Consumer Retry Policy
    │
    ├── Permanently failed message?
    │       → DLQ
    │
    └── Event contract change?
            → Event Schema / Architecture
```

The Event and Messaging Components should remain responsible for **reliable asynchronous transport and processing while keeping business ownership inside application/domain services and using the outbox as the durable bridge between state changes and events**.
