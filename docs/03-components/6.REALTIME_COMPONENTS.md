# RideForge — Realtime Components

> **Document:** `docs/03-components/6.REALTIME_COMPONENTS.md`  
> **Status:** Active  
> **Scope:** Component-level documentation for driver realtime state, heartbeat, connection state, location freshness, offer delivery, and realtime recovery  
> **Related:** `docs/01-business/2.DRIVER_LIFECYCLE.md`, `docs/01-business/4.MATCHING_RULES.md`, `docs/02-architecture/7.REALTIME_ARCHITECTURE.md`, `docs/02-architecture/8.REALTIME_STATE.md`, `docs/03-components/2.DISCOVERY_COMPONENTS.md`, `docs/03-components/3.CANDIDATE_PIPELINE_COMPONENTS.md`

# 1. Purpose

The Realtime Components maintain the operational state required to make dispatch decisions against rapidly changing driver conditions.

The realtime subsystem answers:

> **What is the driver's current operational state, and can the dispatch system safely use that state right now?**

It covers:

```text
Driver Connection
Driver Heartbeat
Driver Location Freshness
Driver Realtime Availability
Driver Offer State
Realtime Event Delivery
Realtime Recovery
```

It does not replace durable driver state or ride state.

---

# 2. Realtime Boundary

The realtime subsystem owns:

```text
Connection State
Heartbeat State
Location Freshness
Realtime Driver Cache
Offer Delivery
Realtime Driver State Recovery
Realtime Connection Lifecycle
```

It does not own:

```text
Durable Driver Profile
Ride Assignment
Reservation Ownership
Final Ranking
Ride Lifecycle
Payment
Business Accounting
```

---

# 3. Realtime State Model

Realtime state should be understood as operational state:

```text
Driver
   ↓
Realtime State
   ├── Connected
   ├── Heartbeat Fresh
   ├── Location Fresh
   ├── Available
   └── Offer Delivery State
```

This state can change independently of durable database records.

---

# 4. Realtime Is Not the Source of Truth

Redis-backed realtime state is optimized for:

```text
Speed
Low Latency
High Write Frequency
Short-Lived State
Operational Decisions
```

It should not become the authoritative durable source for:

```text
Driver Identity
Driver Legal Status
Ride Ownership
Payment
Historical Trips
```

Durable business state remains in PostgreSQL/domain persistence.

---

# 5. Driver Realtime Cache

The driver cache provides fast access to operational driver state.

Conceptually:

```text
Driver ID
   ↓
Realtime Cache
   ├── Connection
   ├── Heartbeat
   ├── Location
   ├── Availability
   └── Offer-related State
```

The cache should expose narrow interfaces to consumers.

---

# 6. Realtime Cache Responsibilities

The realtime cache is responsible for:

- storing short-lived operational state,
- refreshing state TTLs,
- reading current realtime state,
- removing expired state,
- supporting dispatch-time availability checks,
- supporting offer delivery state.

It should not become a generic database replacement.

---

# 7. Heartbeat

Heartbeat indicates that a driver session is still alive.

Conceptually:

```text
Driver App
    ↓
Heartbeat
    ↓
Realtime Cache
    ↓
Refresh TTL
```

A missing heartbeat eventually causes the driver to be treated as stale/offline according to configured policy.

---

# 8. Heartbeat TTL

Heartbeat freshness is controlled by configuration.

The system should not embed operational heartbeat durations directly inside application logic.

Conceptually:

```text
Heartbeat
   ↓
Configured TTL
   ↓
Fresh / Expired
```

---

# 9. Heartbeat Semantics

A heartbeat means:

```text
The driver session is alive.
```

It does not automatically mean:

```text
The driver is available for a ride.
```

Availability remains a separate operational state.

---

# 10. Connection State

Connection state represents whether the driver currently has a usable realtime communication channel.

Conceptually:

```text
Connected
    ↓
Realtime Connection
```

and:

```text
Disconnected
    ↓
No Active Realtime Channel
```

Connection state is distinct from driver availability.

---

# 11. Connection vs Availability

These states must not be conflated.

Examples:

```text
Connected + Unavailable
```

is valid.

```text
Connected + Available
```

is dispatchable if all other conditions pass.

```text
Disconnected + Available flag
```

should not normally be considered safely dispatchable because realtime delivery cannot be guaranteed.

---

# 12. Location Freshness

A driver can have a location but still have stale location data.

Conceptually:

```text
Location Timestamp
      ↓
Freshness Policy
      ↓
Fresh / Stale
```

A stale location should not be treated as current merely because coordinates exist.

---

# 13. Location TTL

Location freshness is governed by configured realtime/location policy.

The location cache should expire or mark stale data according to that policy.

This prevents drivers from remaining spatially dispatchable after their app stops reporting.

---

# 14. Location and H3

Realtime location updates feed the geographic subsystem.

Conceptually:

```text
Driver GPS
    ↓
Driver Location Service
    ├── Realtime Cache
    └── H3 Driver Index
```

The realtime cache stores the latest operational location.

The H3 index provides spatial discovery.

---

# 15. Location Update Responsibilities

The Driver Location Service coordinates a location update.

It should:

1. Validate the incoming location.
2. Update realtime location state.
3. Determine the H3 cell where applicable.
4. Update the H3 index when the cell changes.
5. Refresh required freshness state.

It should not perform ranking or reservation.

---

# 16. Same-Cell Location Update

If a driver's location remains within the same H3 cell:

```text
Location Changed
       ↓
Cell Unchanged
       ↓
Do Not Move H3 Membership
       ↓
Refresh Realtime Freshness
```

This avoids unnecessary H3 index writes.

---

# 17. Cell Movement

When a driver moves between cells:

```text
Old Cell
   ↓
Atomic Index Movement
   ↓
New Cell
```

The H3 index owns membership consistency.

The realtime service should not manually reproduce H3 index internals.

---

# 18. Driver Availability

Realtime availability represents whether the driver is currently willing/able to receive dispatch offers according to the operational state model.

The exact allowed states come from the driver lifecycle/business rules.

The realtime subsystem should expose the current state needed by candidate filtering.

---

# 19. Availability Changes

An availability change should update realtime state quickly.

Conceptually:

```text
Driver App
   ↓
Availability Command
   ↓
Driver Service / Realtime State
   ↓
Realtime Cache
```

Durable state changes, where required by business rules, remain separate.

---

# 20. Availability Freshness

A driver must not remain operationally dispatchable forever because of an old availability value.

The realtime state should be tied to:

```text
Heartbeat
Connection
Location Freshness
Availability
```

according to the configured operational policy.

---

# 21. Candidate Pipeline Integration

The candidate pipeline consumes realtime state after geographic discovery.

Conceptually:

```text
H3 Discovery
      ↓
Driver IDs
      ↓
Driver Cache
      ↓
Availability Filter
      ↓
Ranking
```

The realtime cache therefore sits directly on the dispatch hot path.

---

# 22. Realtime Cache Read Performance

Realtime reads should be optimized for:

```text
Low Latency
Bounded Network Calls
Batch Access Where Possible
Minimal Serialization
```

The candidate pipeline should avoid performing one independent cache request per candidate when an appropriate batch operation exists.

---

# 23. Batch Driver Reads

The existing `BatchDataSource` abstraction supports batch driver loading.

Conceptually:

```text
Driver IDs
   ↓
BatchDataSource
   ↓
Realtime Driver Records
```

This avoids N+1 cache access patterns.

---

# 24. Narrow Interfaces

Consumers should depend on the smallest realtime interface required.

For example:

```text
BatchDataSource
```

for driver loading and:

```text
OfferedDriverProvider
```

for active offered-driver state.

A single Redis-backed cache implementation may satisfy both interfaces.

This is preferable to exposing a large generic cache interface everywhere.

---

# 25. Offer Delivery

Realtime offer delivery is responsible for sending a dispatch offer to the driver through the configured realtime mechanism.

Conceptually:

```text
Dispatch Engine
      ↓
Driver Offer Gateway
      ↓
Realtime Hub
      ↓
Driver App
```

Push notification can be used as an additional delivery mechanism where configured.

---

# 26. Driver Offer Gateway

The Driver Offer Gateway abstracts offer delivery from dispatch orchestration.

The dispatch layer should not need to know whether delivery uses:

```text
WebSocket
SSE
Push Notification
Another Realtime Transport
```

---

# 27. Realtime Hub

The realtime hub manages active realtime connections.

Conceptually:

```text
Driver ID
   ↓
Connection
```

The hub is responsible for connection-oriented delivery.

It should not own durable ride state.

---

# 28. Connection Registration

When a driver establishes a realtime session:

```text
Connection Established
      ↓
Authenticate / Identify Driver
      ↓
Register Connection
      ↓
Update Connection State
```

The connection registry must avoid accidentally associating one driver's connection with another driver's identity.

---

# 29. Connection Removal

When a connection closes:

```text
Connection Closed
      ↓
Remove Connection
      ↓
Update Realtime State
```

The cleanup operation should be safe if the connection was already removed or replaced.

---

# 30. Multiple Connections

A driver may temporarily have multiple connection attempts due to:

```text
Reconnect
Network Transition
App Restart
Device Change
```

The connection model must avoid treating a stale connection closure as proof that a newer connection is offline.

A connection/session identity should be used where required to distinguish old and current sessions.

---

# 31. Offer Delivery Safety

Offer delivery must not be interpreted as reservation.

The correct sequence is:

```text
Candidate
   ↓
Reservation
   ↓
Offer Delivery
```

The driver receiving an offer does not automatically own the ride.

---

# 32. Offer State

Offer-related realtime state may track information such as:

```text
Offer ID
Ride ID
Driver ID
Delivery State
Expiration
```

The exact durable lifecycle is defined by the offer/dispatch components.

Realtime state should remain focused on operational delivery.

---

# 33. Offer TTL

Short-lived offer state should use configured TTLs.

The system must not leave expired offers permanently in the realtime cache.

Conceptually:

```text
Offer Created
      ↓
Configured TTL
      ↓
Expired
      ↓
Cleanup
```

---

# 34. Offer Delivery Failure

If realtime delivery fails:

```text
Offer Delivery
      ↓
Failure
```

the dispatch system should classify the failure according to the offer/dispatch contract.

The realtime gateway should not independently decide to assign another driver.

---

# 35. Push Notification

The current architecture includes a push notifier abstraction.

Conceptually:

```text
Driver Offer Gateway
      ↓
Push Notifier
      ↓
Push Provider
```

The current development implementation may use a no-op notifier.

The abstraction allows a real provider to be introduced without changing dispatch orchestration.

---

# 36. Push Is Not the Primary State Store

Push delivery is a transport mechanism.

It should not be used as the source of truth for:

```text
Offer Ownership
Ride Assignment
Driver Availability
```

Those remain controlled by application/domain state.

---

# 37. Realtime Recovery Worker

The realtime architecture includes heartbeat recovery.

Conceptually:

```text
Heartbeat State
      ↓
Recovery Worker
      ↓
Detect Stale Drivers
      ↓
Repair / Transition Realtime State
```

The recovery worker prevents stale realtime state from remaining indefinitely.

---

# 38. Recovery Interval

Recovery frequency is configuration-driven.

The system should not hard-code:

```text
Every N seconds
```

inside the worker implementation.

The interval belongs to realtime configuration.

---

# 39. Recovery Scope

The recovery worker should perform bounded operational cleanup.

It should not become a periodic full database reconciliation process.

Examples of realtime recovery:

```text
Expired heartbeat
Stale connection
Expired offer state
Operational cache cleanup
```

Full system reconciliation belongs to the reliability subsystem.

---

# 40. Recovery and Driver Service

The heartbeat recovery worker can coordinate with the Driver Service when a stale driver requires an application-level state transition.

Conceptually:

```text
Recovery Worker
      ↓
Driver Service
      ↓
Driver Operational State
```

The worker should use existing application services rather than directly modifying durable business tables.

---

# 41. Recovery Idempotency

Recovery operations must be safe to run more than once.

For example:

```text
Driver already offline
```

should not cause an invalid second transition.

The worker should tolerate races between:

```text
Driver App
Recovery Worker
Another Dispatch Node
```

---

# 42. Realtime Race Conditions

Realtime state is inherently concurrent.

Potential races include:

```text
Heartbeat vs Disconnect
Location Update vs Cleanup
Availability Change vs Dispatch
Offer Expiry vs Driver Response
Reconnect vs Old Connection Close
```

The implementation should use state/version/session checks where necessary.

---

# 43. Connection Race

A particularly important race is:

```text
Old Connection
      ↓
New Connection Established
      ↓
Old Connection Closes
```

The old connection must not clear the new connection's state.

Connection identity/session ownership should protect this transition.

---

# 44. Driver Availability Race

A driver may become unavailable after candidate filtering:

```text
Candidate Filter
      ↓
Driver Available
      ↓
Driver Goes Offline
      ↓
Reservation Attempt
```

This is expected.

Reservation remains the final ownership boundary.

---

# 45. Realtime and Reservation

Realtime state helps identify candidates but does not guarantee ownership.

The authoritative sequence is:

```text
Realtime Eligibility
      ↓
Ranking
      ↓
Reservation
      ↓
Offer
```

Reservation must protect against concurrent assignment.

---

# 46. Realtime and Ranking

Realtime data may contribute to ranking through:

```text
Location
Idle Time
Availability
Connection State
```

The ranking engine should receive explicit features rather than directly reading the realtime cache from the scorer.

---

# 47. Realtime and Fairness

Idle time can be derived from realtime/dispatch state and exposed as a fairness feature.

Conceptually:

```text
Last Assignment
      ↓
Idle Duration
      ↓
Fairness Feature
      ↓
Ranking
```

The realtime subsystem provides state; ranking decides how to use it.

---

# 48. Realtime and Geo

Realtime location and geographic indexing work together:

```text
GPS Update
    ↓
Realtime Cache
    +
H3 Index
```

The two stores serve different purposes:

```text
Realtime Cache
    → Latest operational driver state

H3 Index
    → Spatial lookup
```

Neither should be treated as a replacement for the other.

---

# 49. Redis Key Ownership

Realtime Redis keys should have clear ownership.

Conceptually:

```text
Driver State Keys
    → Driver Cache

H3 Membership Keys
    → H3 Driver Index

Geo Keys
    → Geo Service

Offer Delivery Keys
    → Offer / Realtime Components
```

Components should not casually manipulate another component's private keys.

---

# 50. TTL Ownership

The component that creates a short-lived realtime key should own its TTL semantics.

Avoid:

```text
Component A
    ↓
Writes Component B's Key
    ↓
Changes TTL
```

This prevents hidden coupling.

---

# 51. Realtime Serialization

Realtime state should use stable, explicit serialization.

The representation should remain compact because these records are read/written frequently.

Avoid storing unnecessary large domain objects in Redis.

---

# 52. Realtime Cache Consistency

Realtime cache state is allowed to be eventually consistent with durable state within the operational tolerance of the system.

However, critical ownership decisions must not rely solely on eventually consistent cache state.

The reservation boundary remains authoritative.

---

# 53. Cache Miss

A cache miss should be treated explicitly.

Possible meanings include:

```text
Driver Offline
State Expired
Driver Not Connected
State Not Yet Initialized
```

The caller must interpret the result according to the relevant contract.

A cache miss should not automatically trigger a database query from every hot-path consumer.

---

# 54. Database Fallback

Database fallback should not be introduced casually into realtime hot-path reads.

The reason is:

```text
Realtime Request
      ↓
Redis Miss
      ↓
PostgreSQL
      ↓
Higher Latency
```

If fallback is required, it should be explicitly designed and bounded.

---

# 55. Realtime Failure Mode

If Redis becomes unavailable, the system must not pretend that realtime state is current.

Possible system-level behaviour should be defined by dispatch/reliability policy.

The realtime component should expose the failure rather than silently returning fabricated state.

---

```text

```

Driver/ride identifiers may be appropriate in traces under the project's privacy/observability policy, but should not be indiscriminately placed in aggregate metrics.

# 58. Logging

Realtime logs should focus on meaningful lifecycle events:

```text
Connection Established
Connection Closed
Heartbeat Expired
Offer Delivery Failed
Recovery Transition
```

Avoid logging every heartbeat or GPS update at normal production log levels.

High-frequency events should use metrics/tracing instead.

# 65. AI Agent Forbidden Patterns

An AI agent must not:

- treat Redis realtime state as durable business truth,
- bypass reservation for realtime decisions,
- directly manipulate another component's private Redis keys,
- hard-code heartbeat/connection/offer TTLs,
- log every heartbeat or GPS update at normal production levels,
- create database fallbacks for every cache miss without an explicit design decision,
- make push notification authoritative,
- create offers directly from heartbeat processing,
- mark a driver assigned because an offer was delivered,
- allow an old connection to clear a newer connection,
- perform full database reconciliation inside heartbeat recovery,
- introduce a second driver realtime cache,
- duplicate H3 movement logic inside the realtime service,
- add distributed locking without first verifying whether existing reservation/ownership guarantees already solve the race.

# 67. Component Responsibility Matrix

| Component | Responsibility | Must Not Own |
|---|---|---|
| Driver Cache | Fast operational driver state | Durable driver history |
| Heartbeat Handling | Driver liveness | Assignment |
| Connection Manager / Hub | Realtime sessions | Ride ownership |
| Driver Location Service | Location update orchestration | Ranking |
| H3 Driver Index | Spatial membership | Realtime connection |
| Driver Offer Gateway | Offer delivery abstraction | Reservation |
| Push Notifier | Push transport | Offer ownership |
| Recovery Worker | Stale realtime recovery | Full reconciliation |
| Availability Filter | Dispatch eligibility | Connection management |
| Reservation | Driver ownership | Realtime transport |

# 68. Current Status

The RideForge realtime architecture already provides the core operational building blocks:

```text
Driver Cache
Heartbeat State
Connection State
Location State
Driver Location Service
Realtime Hub
Driver Offer Gateway
Push Notifier Abstraction
Heartbeat Recovery Worker
TTL-Based Realtime State
H3 Integration
```

The architecture intentionally keeps:

```text
Realtime State
```

separate from:

```text
Durable Business State
```

and:

```text
Reservation Ownership
```

# 70. Final Component Rule

When an AI agent is asked to modify realtime behaviour, determine first:

```text
Is the change about:
    │
    ├── Heartbeat?
    │       → Heartbeat / Driver Cache
    │
    ├── Connection?
    │       → Realtime Hub
    │
    ├── Location?
    │       → Driver Location Service / Geo
    │
    ├── Operational availability?
    │       → Driver Realtime State
    │
    ├── Offer delivery?
    │       → Driver Offer Gateway
    │
    ├── Push transport?
    │       → Push Notifier
    │
    ├── Stale-state cleanup?
    │       → Recovery Worker
    │
    └── Ride ownership?
            → Reservation / Dispatch
```

The Realtime Components should remain responsible for **fast, short-lived operational driver state and reliable realtime communication while preserving durable state and reservation as separate authoritative boundaries**.
