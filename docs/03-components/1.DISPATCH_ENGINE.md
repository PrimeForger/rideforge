# 1. Purpose

The Dispatch Engine is the application-level orchestration component responsible for executing the driver-matching process for a ride.

Its responsibility is to coordinate existing dispatch components rather than implement every dispatch concern itself.

The core responsibility is:

```text
Matchable Ride
      ↓
Resolve Effective Dispatch Strategy
      ↓
Create Matching Attempt
      ↓
Discover Candidates
      ↓
Process Candidate Pipeline
      ↓
Apply Strategy-Specific Prioritization / Ranking
      ↓
Reserve Drivers
      ↓
Create / Trigger Offers
      ↓
Observe Outcome
      ↓
Assign or Retry
```

The strategy is resolved from the applicable hierarchical dispatch configuration before strategy execution begins.

The Dispatch Engine coordinates this flow but does not own the configuration hierarchy, geographic discovery algorithms, candidate filtering algorithms, or ranking mathematics.

The Dispatch Engine is therefore an **orchestrator**, not the owner of every underlying algorithm.

---

# 2. Primary Responsibility

The Dispatch Engine coordinates the dispatch workflow while delegating specialized decisions to dedicated components.

It is responsible for:

- starting a matching attempt,
- validating that the ride can still be matched,
- invoking candidate discovery,
- invoking the candidate pipeline,
- applying dispatch/retry policy,
- coordinating driver reservation,
- initiating offer processing,
- stopping after successful assignment,
- continuing when retry policy permits,
- propagating meaningful failures.

---

# 3. Responsibility Boundary

The Dispatch Engine owns **orchestration**.

It does not own:

```text
H3 indexing
Candidate filtering implementation
Feature extraction
Ranking mathematics
Driver locking implementation
Realtime transport
Database persistence implementation
Kafka transport
Ride lifecycle definition
```

Those responsibilities belong to their respective components.

The relationship is:

```text
Dispatch Engine
     │
     ├── Candidate Searcher
     ├── Candidate Pipeline
     ├── Retry Policy
     ├── Driver Reservation
     └── Offer / Assignment Flow
```

The matching engine should coordinate the workflow rather than reproduce lower-level algorithms.

Conceptually:

```text
MatchingEngine
      │
      ├── search candidates
      │
      ├── execute candidate pipeline
      │
      ├── evaluate candidates
      │
      ├── reserve driver
      │
      ├── initiate offer
      │
      └── continue / stop according to policy
```

# 6. Dispatch Strategy Resolution

Before executing candidate discovery for a ride, the dispatch flow must resolve the **effective dispatch strategy** from the applicable hierarchical configuration.

The hierarchy is not necessarily a fixed list of geographic levels. It may include configured levels such as:

```text
State
 ↓
District
 ↓
City / Town
 ↓
Rural Area
 ↓
Auto Stand
 ↓
Specific Ride Level
```

or other intermediate levels defined by the configuration model.

The resolution rule is:

```text
Most Specific Applicable Level
        ↓
Explicit Dispatch Strategy?
   ├── YES → Use It
   └── NO
        ↓
Parent Level
        ↓
Continue Upward
        ↓
First Explicit Strategy
        ↓
No Strategy Found
        ↓
System Default
```

The **closest / lowest-level explicit configuration wins**.

For example:

```text
District      → Smart Dispatch
Town A        → Smart Stand Dispatch
Town B        → No Explicit Configuration
```

results in:

```text
Town A Ride → Smart Stand Dispatch
Town B Ride → Smart Dispatch
```

The Dispatch Engine may coordinate this resolution through a dedicated configuration/strategy resolver, but it must not hard-code the hierarchy or duplicate configuration inheritance logic.

The resolved strategy becomes part of the dispatch context for the remainder of the attempt.

---

# 7. Dispatch Strategy Execution Boundary

Once the effective dispatch strategy has been resolved, the engine executes that strategy through the existing discovery, candidate pipeline, prioritization, ranking, reservation, and offer components.

```text
Effective Dispatch Strategy
          ↓
Strategy Execution Context
          ↓
Candidate Discovery
          ↓
Candidate Pipeline
          ↓
Strategy-Specific Prioritization / Ranking
          ↓
Reservation / Offer / Assignment
```

The important separation is:

```text
Configuration Resolution
        ≠
Candidate Discovery
        ≠
Candidate Eligibility
        ≠
Strategy-Specific Prioritization
        ≠
Ranking
        ≠
Reservation
```

The dispatch strategy determines **how candidates are prioritized and processed**. It does not automatically define a hard geographic candidate boundary.

---

# 8. Matching Attempt

A dispatch operation is divided into matching attempts.

```text
Ride
 ↓
Attempt 1
 ↓
Outcome
 ↓
Retry Policy
 ↓
Attempt 2
 ↓
Outcome
```

An attempt represents one execution of the dispatch process.

The attempt number must not be confused with the ride lifecycle state.

For example:

```text
Ride State:
MATCHING

Dispatch State:
Attempt 3
```

---

# 9. Attempt Preconditions

Before starting an attempt, the engine must ensure that the ride is still eligible for matching.

Conceptually:

```text
Current Ride State
       ↓
Matchable?
 ├── No  → Stop
 └── Yes → Execute Attempt
```

This protects against:

```text
Cancellation
Concurrent Assignment
Completed Ride
Delayed Retry
Duplicate Event
```

---

# 10. Candidate Discovery

The engine delegates candidate discovery to the configured candidate searcher.

Conceptually:

```text
MatchingEngine
      ↓
CandidateSearcher
      ↓
Discovery Result
```

The engine should not directly perform:

```text
H3 Grid Disk
Redis SMEMBERS
Redis GEO lookup
Haversine calculation
Density classification
Ring expansion
```

Those responsibilities belong to the discovery/geo components.

---

# 11. Discovery Request

The matching engine supplies the discovery component with the information required to search for candidates.

The request may contain values such as:

```text
Pickup Latitude
Pickup Longitude
Search Radius
Candidate Limit
Matching Attempt
Effective Dispatch Strategy
Strategy Configuration Context
Candidate Discovery / Expansion Scope
```

The exact request contract is owned by the discovery component.

The dispatch engine should not depend on the internal implementation of H3 or Redis.

---

# 12. Discovery Result

The discovery layer returns candidate information to the dispatch engine.

Conceptually:

```text
DiscoveryResult
    ↓
Candidate Collection
```

The engine should treat discovery as a bounded candidate-generation step.

The discovery result should preserve relevant context for downstream strategy-specific processing where applicable, such as:

```text
Candidate Location
Candidate Location Strategy
Stand Membership
Relevant Stand
Queue Position
Discovery Source
Distance / ETA
```

No driver should be considered assigned merely because discovery returned its ID.

The presence of stand context does not mean that non-stand candidates are invalid. Likewise, a candidate from another nearby location is not invalid merely because its source location uses a different dispatch strategy.

---

# 13. Candidate Pipeline

After discovery, candidates are processed through the candidate pipeline.

```text
Discovery
    ↓
Candidate Pipeline
    ↓
Eligible / Prepared Candidates
    ↓
Strategy-Specific Prioritization / Ranking
    ↓
Ranked Candidates
```

The pipeline owns candidate processing.

The Dispatch Engine should not duplicate:

```text
Validation
Deduplication
Availability Filtering
Already-Offered Filtering
Feature Extraction
Strategy-Specific Prioritization
Ranking Mathematics
Heap Construction
```

---

# 14. Candidate Pipeline Contract

The engine should depend on the pipeline abstraction rather than individual stage implementations.

Conceptually:

```text
MatchingEngine
      ↓
CandidatePipeline
      ↓
Pipeline Result
```

This keeps the orchestration layer independent from changes to individual pipeline stages.

---

# 15. Empty Candidate Result

An empty candidate result is a valid dispatch outcome.

```text
Discovery / Pipeline
        ↓
No Eligible Candidates
```

This must remain distinguishable from an infrastructure or application failure.

The engine passes the outcome to retry policy.

---

# 16. Ranking Result

The Dispatch Engine consumes the ranked candidate result.

It does not calculate ranking itself.

Ranking is owned by the ranking component.

```text
Candidate Pipeline
      ↓
Eligible / Prepared Candidates
      ↓
Strategy-Specific Prioritization / Ranking
      ↓
Ranked Candidates
      ↓
Dispatch Selection
```

---

# 17. Candidate Selection

The engine uses the pipeline output according to the active dispatch policy.

Selection may involve:

```text
Top-ranked candidate
Offer batch
Configured candidate limit
Adaptive batch policy
```

The exact selection policy should remain explicit and configurable.

---

# 18. Reservation Boundary

Reservation is the concurrency boundary between:

```text
Candidate Preference
```

and:

```text
Driver Ownership
```

The sequence must be:

```text
Ranked Candidate
      ↓
Reserve Driver
      ↓
Reservation Success
      ↓
Offer
```

The engine must not assume that a ranked candidate is still available.

---

# 19. Reservation Race

A driver can become unavailable after ranking.

Example:

```text
Driver A
   ↓
Ranked
   ↓
Another ride reserves Driver A
   ↓
Reservation rejected
```

This is a normal concurrent dispatch outcome.

The engine should continue according to dispatch policy rather than treating every reservation rejection as an infrastructure failure.

---

# 20. Driver Locker

The Dispatch Engine depends on the reservation/locking abstraction.

It should not implement Redis locking details directly.

Conceptually:

```text
MatchingEngine
      ↓
DriverLocker
      ↓
Reservation Result
```

The concrete implementation may use Redis or another mechanism.

---

# 21. Reservation Ownership

A successful reservation means that the current dispatch operation has temporarily claimed the driver according to the reservation contract.

It does not automatically mean:

```text
Ride Assigned
```

The engine must continue through the offer/assignment flow.

---

# 22. Offer Boundary

The Dispatch Engine coordinates with the offer flow after successful reservation.

Conceptually:

```text
Reserve
  ↓
Offer
  ↓
Driver Response
  ↓
Assignment / Retry
```

Offer transport and response handling should remain outside the core candidate-ranking logic.

---

# 23. Successful Assignment

When assignment succeeds:

```text
Matching
    ↓
Driver Assigned
```

the Dispatch Engine must stop normal matching.

It must not:

```text
start another attempt
create unrelated offers
continue candidate search
continue normal retry
```

for the same ride.

---

# 24. Multiple Offers

If the configured dispatch policy allows multiple simultaneous offers:

```text
Ride
 ├── Driver A → Offer
 ├── Driver B → Offer
 └── Driver C → Offer
```

the engine must still preserve the single-assignment invariant.

Only one driver may successfully become the authoritative assignment.

---

# 25. Acceptance Race

Two drivers may accept nearly simultaneously.

The Dispatch Engine must rely on the authoritative assignment/concurrency boundary to resolve the race.

The result must never become:

```text
One Ride
   ↓
Two Assigned Drivers
```

---

# 26. Offer Rejection

When an offered driver rejects:

```text
Reject
  ↓
Release Reservation
  ↓
Continue Dispatch
```

if the ride remains matchable.

The engine should not terminate the ride merely because one driver rejected.

---

# 27. Offer Timeout

When an offer expires:

```text
Timeout
  ↓
Release Reservation
  ↓
Continue Dispatch
```

if retry policy allows another attempt.

Timeout is an unsuccessful offer outcome, not automatically a ride failure.

---

# 28. Retry Policy Boundary

The Dispatch Engine executes retry policy; it should not invent retry rules.

Conceptually:

```text
Attempt Outcome
      ↓
Retry Policy
      ↓
Retry?
 ├── Yes → Next Attempt
 └── No  → Stop
```

The retry policy decides:

```text
Whether another attempt is useful
How the next attempt may differ
When retry must stop
```

---

# 29. Retry Parameters

A later attempt may use different configured parameters such as:

```text
Search Radius
Candidate Limit
Location Expansion Scope
Offer Batch Size
Offer Timeout
```

Retry or expansion parameters must not silently change the resolved dispatch strategy.

For example:

```text
Smart Stand Dispatch
        ↓
Stand supply unavailable
        ↓
Broader candidate discovery
```

is valid when configured, while:

```text
Smart Stand Dispatch
        ↓
Stand supply unavailable
        ↓
Silently switch to Smart Dispatch
```

is not valid unless an explicit business configuration defines that fallback strategy.

The engine passes policy results into the relevant components.

It should not embed these values as unrelated hard-coded constants.

---

# 30. Retry State Validation

Before retrying, the engine must ensure that the ride is still matchable.

```text
Retry Trigger
      ↓
Current Ride State
      ↓
Still Matchable?
 ├── No  → Stop
 └── Yes → Retry
```

This check is important because retry triggers can be delayed.

---

# 31. Retry Exhaustion

When retry policy determines that no further attempt should occur:

```text
Retry Exhausted
      ↓
Stop Matching
      ↓
Apply Ride / Business Outcome
```

The Dispatch Engine must not invent a new ride state merely because matching has stopped.

---

# 32. Cancellation

If a ride is cancelled while matching is active:

```text
Cancellation
      ↓
Stop Dispatch
      ↓
Cleanup Active Dispatch State
```

Delayed matching work must not resurrect the ride.

---

# 33. Concurrent Cancellation

Cancellation may race with:

```text
Candidate Discovery
Reservation
Offer Creation
Driver Acceptance
Retry
```

The Dispatch Engine must respect the authoritative ride state when applying the outcome.

---

# 34. Idempotency

Dispatch execution may encounter duplicate triggers.

Examples:

```text
Duplicate Event
Duplicate Retry
Worker Restart
Repeated Timeout
Repeated Driver Response
```

The engine and its collaborators must prevent duplicate business effects.

---

# 35. Dispatch State vs Ride State

The Dispatch Engine should keep dispatch execution state separate from the ride lifecycle.

Example:

```text
Ride:
MATCHING

Dispatch:
Attempt = 2
Radius = configured value
Candidates = current attempt
```

The dispatch attempt is operational state around the ride.

It must not become an alternative ride state machine.

---

# 36. Error Classification

The engine should preserve meaningful outcome distinctions.

At minimum:

```text
No Candidate
Reservation Rejected
Offer Rejected
Offer Timed Out
Retry Exhausted
Cancellation
Infrastructure Failure
Application Failure
Successful Assignment
```

These outcomes have different operational and retry implications.

---

# 37. No Candidate vs Error

The engine must not convert:

```text
Redis failure
Database failure
Unexpected application error
```

into:

```text
No Candidates
```

unless the relevant component explicitly defines that behaviour.

A genuine failure must remain observable.

---

# 38. Partial Failure

Dispatch may partially succeed.

Example:

```text
Driver A → Reserved + Offered
Driver B → Reservation Failed
Driver C → Reservation Failed
```

The engine must preserve valid successful state while cleaning up failed partial work.

---

# 39. Cleanup Responsibility

The Dispatch Engine coordinates cleanup but should delegate implementation-specific cleanup to the responsible component.

Examples:

```text
Reservation → DriverLocker
Offer State → Offer Component
Persistent State → Application / Repository
Event Intent → Outbox
Realtime Delivery → Realtime Component
```

The engine should not contain duplicated cleanup implementations.

```text

    ↓

# 41. Performance Responsibilities

The Dispatch Engine is on the hot path.

It should therefore:

- avoid unnecessary database round trips,
- avoid duplicate candidate processing,
- avoid duplicate Redis calls,
- avoid unnecessary retries,
- avoid expensive work after assignment,
- avoid loading data that downstream stages do not need,
- preserve bounded candidate processing.

Performance improvements must not bypass lifecycle or concurrency guarantees.

# 52. Dispatch Strategy: Smart Stand Dispatch

RideForge supports two primary dispatch strategies:

```text
Smart Stand Dispatch
Smart Dispatch
```

**Smart Stand Dispatch is stand-preferred, not stand-exclusive.**

When the rider is within the configured radius of an auto stand, the dispatch flow should first prefer eligible drivers associated with that stand and apply the stand's queue/order rules.

```text
Rider inside stand radius
        ↓
Preferred Stand
        ↓
Eligible Stand Drivers
        ↓
Stand Queue / Ordering
```

If the preferred stand cannot provide a suitable or available driver, the dispatch flow may expand to other eligible candidates according to the configured discovery and retry policy.

Broader candidates may include:

```text
Drivers outside the stand
Drivers at nearby stands
Drivers from nearby locations
```

If the rider is outside the radius of all configured stands, Smart Stand Dispatch does not impose a stand preference and eligible nearby drivers may be considered normally.

The Dispatch Engine must therefore not implement:

```text
Smart Stand Dispatch
        =
Stand-only Candidate Pool
```

Instead:

```text
Smart Stand Dispatch
        =
Stand-preferred Candidate Prioritization
        +
Broader Eligible Candidate Fallback
```

Stand queue semantics must not be silently replaced by generic smart ranking. However, once the preferred stand cannot provide a suitable candidate and broader candidates are admitted, those candidates must be evaluated using the applicable matching/ranking rules.

---

# 53. Dispatch Strategy: Smart Dispatch

Smart Dispatch is stand-agnostic.

The dispatch flow considers eligible available drivers near the rider without using auto-stand membership as an inherent preference.

Typical factors may include:

```text
Driver Eligibility
Availability
Distance
ETA
Quality
Fairness
Demand Context
Other Configured Matching Factors
```

A driver may be considered regardless of whether the driver is:

```text
At an auto stand
Outside an auto stand
Associated with another nearby location
```

The Dispatch Engine remains independent of the internal ranking algorithm.

---

# 54. Cross-Location Dispatch

The Dispatch Engine must support dispatch expansion across nearby configured locations when the originating location cannot provide a suitable eligible driver.

Example:

```text
Location A
    ↓
No suitable local driver
    ↓
Expand Candidate Discovery
    ↓
Location B
    ↓
Location B may use Smart Stand Dispatch
    ↓
Evaluate eligible candidates from B
```

A driver's source location is not by itself a hard eligibility boundary.

When a candidate from another location is considered, the candidate's relevant context should remain available to downstream components, including where applicable:

```text
Candidate Location
Candidate Location's Effective Dispatch Strategy
Stand Membership
Relevant Stand
Queue Position
Discovery Source
Distance / ETA
```

The strategy configured for the candidate's source location determines how that candidate's local stand/strategy context is interpreted. It does not automatically prevent the candidate from serving the ride.

For example:

```text
Location B:
    Smart Stand Dispatch

Stand Driver:
    2 km / 5 min ETA

Non-Stand Driver:
    4 km / 9 min ETA
```

If both are eligible and admitted into the candidate flow, the stand driver's candidate context may receive the configured stand preference, and the final selection must follow the established matching/ranking rules.

Cross-location dispatch must still respect:

```text
Regional / Legal Restrictions
Driver Eligibility
Availability
Service Constraints
Distance / ETA
Other Hard Constraints
```

# 58. AI Agent Forbidden Patterns

An AI coding agent must not:

- create a second matching engine,
- create a second retry engine,
- move ranking algorithms into the Dispatch Engine,
- move H3/geo algorithms into the Dispatch Engine,
- directly manipulate Redis locks from the engine,
- directly construct Kafka messages from the engine,
- bypass the existing candidate pipeline,
- bypass driver reservation,
- create offers before reservation,
- assign a ride merely because a candidate was found,
- retry cancelled or assigned rides,
- introduce hidden hard-coded dispatch policy,
- treat Smart Stand Dispatch as a stand-only candidate pool,
- reject non-stand drivers merely because a ride is inside a stand radius,
- reject cross-location candidates merely because they belong to another configured location,
- hard-code the configuration hierarchy inside the Dispatch Engine,
- resolve configuration by requiring every hierarchy level to be explicitly configured,
- silently switch Smart Stand Dispatch to Smart Dispatch when preferred stand supply is unavailable,
- duplicate cleanup logic already owned by another component,
- introduce a new abstraction without checking existing contracts,
- change orchestration solely to mark a roadmap phase complete.

# 60. Component Contract Summary

| Component | Dispatch Engine Responsibility |
|---|---|
| Strategy Configuration / Resolver | Resolve the effective dispatch strategy from hierarchical configuration |
| Candidate Searcher | Discover candidates using the resolved dispatch context |
| Candidate Pipeline | Process and prepare eligible candidates for downstream prioritization |
| Ranking / Prioritization | Apply strategy-specific candidate prioritization and ranking |
| Driver Locker | Attempt driver reservation |
| Offer Component | Initiate and manage offers |
| Retry Policy | Decide whether/how to retry |
| Ride/Application Layer | Authoritative ride lifecycle |
| Outbox/Event Layer | Reliable event publication |
| Realtime Layer | Deliver driver-facing realtime information |
| PostgreSQL | Durable persistence |
| Redis | Realtime/cache/locking infrastructure |

The Dispatch Engine coordinates these components; it does not absorb their responsibilities.

---

# 61. Final Design Principle

The Dispatch Engine should remain intentionally small in terms of responsibility.

Its ideal structure is:

```text
Orchestrate
    ↓
Delegate
    ↓
Validate Outcome
    ↓
Continue / Stop
```

not:

```text
Orchestrate
+
Discover
+
Filter
+
Rank
+
Lock
+
Publish
+
Persist
+
Notify
+
Retry Algorithm
+
Business State Machine
```

A production-grade Dispatch Engine is valuable because it provides a stable orchestration boundary while allowing discovery, candidate processing, ranking, reservation, offers, and retry policy to evolve independently.

# 63. Canonical Rule

When an AI agent is asked to modify dispatch behaviour, it should first determine:

```text
Is this an orchestration problem?
        │
        ├── Yes → Dispatch Engine
        │
        └── No
             ↓
Which component owns the behaviour?
             ↓
Modify that component

        ↓

Candidate Discovery
