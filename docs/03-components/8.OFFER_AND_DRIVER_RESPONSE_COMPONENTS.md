# 1. Purpose

The Offer and Driver Response Components connect dispatch ownership with the driver's realtime response.

They manage the transition:

```text
Reserved Driver
      ↓
Offer
      ↓
Driver Response
      ↓
Accept / Reject / Timeout
```

The components provide the mechanism for delivering and processing a dispatch offer without making realtime delivery itself the source of ride ownership.

---

# 2. Component Boundary

These components own:

```text
Offer Creation
Offer Delivery Coordination
Offer Timeout Scheduling
Driver Offer Response Handling
Offer Validation
Reservation Release Coordination
Driver Acceptance Processing
Driver Rejection Processing
```

They do not own:

```text
Candidate Discovery
Candidate Ranking
Geographic Search
Driver Reservation Primitive
Durable Ride Assignment
Payment
Driver Location
```

---

# 3. Offer Lifecycle

The logical lifecycle is:

```text
Candidate Selected
      ↓
Reservation Acquired
      ↓
Offer Created
      ↓
Offer Delivered
      ↓
Driver Response
   ┌──┼───────────┐
   │  │           │
 Accept Reject  Timeout
   │  │           │
   ▼  ▼           ▼
Confirm Release Release
   │
   ▼
Assignment
```

The exact durable ride-state transitions remain controlled by the ride/dispatch application services.

---

# 4. Reservation Before Offer

An offer must not be sent as though it grants ownership.

The correct order is:

```text
Candidate
   ↓
Reservation
   ↓
Reservation Success
   ↓
Offer
```

If reservation fails:

```text
Reservation Conflict
   ↓
No Offer
```

The Dispatch Engine decides whether another candidate should be attempted.

---

# 5. Driver Offer Gateway

The Driver Offer Gateway is the application-facing abstraction for realtime offer delivery.

Conceptually:

```text
Dispatch / Matching
       ↓
DriverOfferGateway
       ↓
Realtime Hub
       ↓
Driver App
```

The dispatch layer does not need to know the transport implementation.

---

# 6. Offer Gateway Responsibilities

The gateway should:

- accept a prepared offer,
- identify the target driver,
- deliver the offer through the configured realtime transport,
- report delivery success/failure,
- remain independent of candidate ranking.

It should not:

```text
Choose the driver
Acquire reservation
Decide retry count
Persist unrelated ride state
```

---

# 7. Offer Payload

An offer should contain the information required by the driver application to make a response.

The payload should remain intentionally bounded.

It may include information such as:

```text
Offer ID
Ride ID
Pickup Information
Destination Information where permitted
Estimated Trip Information
Expiration
```

The exact payload contract in code is authoritative.

---

# 8. Offer Identity

Every offer should have a stable identity.

Conceptually:

```text
Ride
 +
Driver
 +
Offer ID
```

The offer ID is important for:

```text
Response Validation
Idempotency
Timeout Handling
Tracing
```

A driver response must not be accepted solely because it contains a ride ID.

---

# 9. Driver Identity

An offer is directed to a specific driver.

The system must validate:

```text
Offer Driver ID
==
Response Driver ID
```

A response from another driver must not modify the offer.

---

# 10. Ride Identity

The response must reference the ride associated with the offer.

The application must validate:

```text
Offer Ride ID
==
Response Ride ID
```

This prevents a valid response from being applied to an unrelated ride.

---

# 11. Offer State

Offer state should represent the lifecycle of the offer.

Conceptually:

```text
Created
   ↓
Delivered
   ↓
Pending Response
   ├── Accepted
   ├── Rejected
   └── Expired
```

Terminal states should not be transitioned again by stale responses.

---

# 12. State Transition Protection

The response service must protect against:

```text
Accept after Reject
Reject after Accept
Accept after Timeout
Timeout after Accept
Duplicate Accept
Duplicate Reject
```

Only the valid transition for the current offer state should be applied.

---

# 13. Driver Response Service

The Driver Response Service coordinates the business handling of a driver's response.

Conceptually:

```text
Driver Response
      ↓
DriverResponseService
      ↓
Validate Offer
      ↓
Validate Driver
      ↓
Apply Response
      ↓
Release / Confirm Ownership
```

The exact application service contract remains authoritative.

---

# 14. Command vs Event

The architecture distinguishes the driver response command path from event-driven processing where appropriate.

A command represents:

```text
Driver explicitly responded
```

An event represents:

```text
Something happened and downstream components may react
```

Do not collapse these concepts merely to reduce the number of files.

---

# 15. Driver Response Validation

Before applying a response, validate:

```text
Offer Exists
Offer Belongs to Ride
Offer Belongs to Driver
Offer Is Active
Response Is Allowed
Reservation Ownership Is Valid where required
```

Validation must happen before applying a terminal state transition.

---

# 16. Accepted Response

When a driver accepts:

```text
Offer
   ↓
Validate
   ↓
Accept
   ↓
Confirm / Continue Ownership
   ↓
Assignment Flow
```

The response service should not blindly assume that the reservation is still valid.

Concurrent cancellation, expiry, or another state transition may have occurred.

---

# 17. Acceptance Race

A critical race is:

```text
Offer Timeout
      ↓
Reservation Released

Driver Accepts
      ↓
Response Arrives
```

The system must validate the current offer/reservation state before accepting the response.

A stale acceptance must not resurrect an expired assignment.

---

# 18. Rejected Response

When a driver rejects:

```text
Offer
   ↓
Reject
   ↓
Release Reservation
   ↓
Dispatch May Continue
```

The Dispatch Engine decides whether to:

```text
Try Next Candidate
```

or:

```text
Retry / Expand Search
```

The response component should report the outcome accurately.

---

# 19. Timeout

Offer timeout is an operational lifecycle event.

Conceptually:

```text
Offer Pending
      ↓
Timeout Scheduler
      ↓
Offer Expired
      ↓
Reservation Release
      ↓
Dispatch Continues
```

Timeout processing must be safe against a driver responding at approximately the same time.

---

# 20. Timeout Scheduler

The current architecture includes a Redis-backed timeout scheduler.

Its responsibility is to schedule short-lived offer timeout work.

Conceptually:

```text
Offer Created
      ↓
Timeout Scheduler
      ↓
Delayed Timeout Event
      ↓
Offer Timeout Handler
```

The scheduler should not independently assign drivers.

---

# 21. Timeout Scheduling

Timeout duration must be configuration/policy-driven.

The system must not hard-code offer timeout values inside the scheduler.

The timeout policy may later become dynamic based on:

```text
ETA
Traffic
Driver Response History
```

but that decision belongs to dispatch policy, not the low-level scheduler.

---

# 22. Timeout Idempotency

A timeout handler may execute more than once due to:

```text
Retry
Worker Restart
Duplicate Event
Network Behaviour
```

Therefore timeout processing must be idempotent.

The handler should first verify:

```text
Offer Still Pending?
```

If not:

```text
Do Nothing
```

---

# 23. Timeout vs Acceptance Race

The system must safely handle:

```text
Timeout
```

and:

```text
Accept
```

arriving concurrently.

Exactly one valid terminal transition should win according to the authoritative offer-state mechanism.

The losing operation must not corrupt the resulting state.

---

# 24. Driver Offer Handler

The Driver Offer Handler coordinates delivery and timeout-related behaviour around an offer.

It integrates:

```text
Driver Cache
Timeout Scheduler
Driver Offer Gateway
Configuration
Logging
```

The handler should remain an application coordination component rather than becoming a transport implementation.

---

# 25. Realtime Delivery

The delivery path is:

```text
Offer Handler
      ↓
Driver Offer Gateway
      ↓
Realtime Hub
      ↓
Driver Connection
```

A disconnected driver may require a delivery failure result.

The system must not treat unsuccessful delivery as driver acceptance.

---

# 26. Push Delivery

Where configured, push notification may supplement realtime delivery.

Conceptually:

```text
Driver Offer Gateway
      ├── Realtime Hub
      └── Push Notifier
```

Push is a delivery mechanism, not an ownership mechanism.

---

# 27. Delivery Failure

Delivery failure must remain distinguishable from:

```text
Driver Rejected
```

These mean different things.

```text
Delivery Failure
    =
Offer could not be reliably delivered

Driver Rejected
    =
Driver explicitly declined
```

Dispatch policy may react differently to each.

---

# 28. Offer Expiry

An expired offer should no longer be accepted.

Conceptually:

```text
Pending
   ↓
Expiry
   ↓
Expired
```

A late response must be rejected or ignored according to the response contract.

---

# 29. Duplicate Response

Driver apps may retry requests due to network conditions.

Therefore:

```text
Accept
Accept
```

or:

```text
Reject
Reject
```

must not produce duplicate side effects.

Response handling should be idempotent where the command contract requires it.

---

# 30. Response Idempotency

If a response includes a unique response/request ID, the application may use that identity to prevent duplicate command processing.

Where offer state itself provides sufficient idempotency, do not add a second persistence mechanism unnecessarily.

Use the smallest mechanism that reliably protects the operation.

---

# 31. Accepted Offer and Assignment

An accepted offer moves the process toward ride assignment.

Conceptually:

```text
Accepted
   ↓
Application Assignment Flow
   ↓
Ride / Driver Ownership
```

The Offer/Response Components should not silently bypass the application's assignment service.

---

# 32. Rejected Offer and Retry

A rejection does not itself mean:

```text
Search Wider
```

The response service reports:

```text
Driver Rejected
```

The Dispatch Engine applies the retry policy.

This preserves separation between:

```text
Response Handling
```

and:

```text
Dispatch Policy
```

---

# 33. Timeout and Retry

A timeout similarly reports:

```text
Offer Expired
```

The Dispatch Engine decides whether to:

```text
Try Next Candidate
```

or:

```text
Perform Another Search Attempt
```

---

# 34. Delivery Failure and Retry

A delivery failure may indicate:

```text
Driver Disconnected
Connection Lost
Transport Failure
```

The correct retry behaviour depends on the dispatch/offer policy.

The transport component should not automatically launch a new matching search.

---

# 35. Offer Events

Offer lifecycle events may be emitted for downstream processing.

Potential events include:

```text
Offer Created
Offer Sent
Offer Rejected
Offer Accepted
Offer Expired
Offer Delivery Failed
```

The exact active event contracts are defined by the event architecture.

---

# 36. Event vs Direct Coordination

Use direct application coordination when the caller requires an immediate result:

```text
Reserve
Send Offer
Process Response
```

Use events where:

```text
Multiple Consumers
Asynchronous Processing
Metrics
Audit
Recovery
```

benefit from decoupling.

Do not introduce an event merely to replace a simple synchronous function call.

---

# 37. Outbox Boundary

When an offer/response operation must publish a durable event together with a database state change, the existing transaction/outbox architecture should be used.

Conceptually:

```text
Business State Change
       +
Outbox Event
       ↓
Same Transaction
```

The event publisher then delivers the event asynchronously.

---

# 38. Event Reliability

Offer/response events should not depend on best-effort direct Kafka publishing when the corresponding business state must be durable.

The existing outbox architecture provides the reliability boundary for such events.

---

# 39. Driver Response Command Service

The command service coordinates response-side transactional work where required.

Conceptually:

```text
Driver Response
      ↓
Command Service
      ↓
Transaction
      ├── Business State
      └── Outbox
```

The command service should not become a generic transaction wrapper for unrelated operations.

---

# 40. Transaction Boundary

A transaction should cover only the state changes that must be atomic.

Avoid holding database transactions while performing:

```text
WebSocket Delivery
Push Notification
Long External Calls
Redis Delays
```

External delivery should remain outside long-running database transactions.

---

# 41. Offer and Reservation Release

When an offer reaches a terminal state that requires release:

```text
Offer Rejected
Offer Expired
Offer Cancelled
```

the application must safely release the corresponding reservation.

The release must remain ownership-aware.

---

# 42. Accepted Reservation

On acceptance, the system should not blindly release the reservation before the next ownership transition is safely established.

Conceptually:

```text
Reservation
    ↓
Accept
    ↓
Confirm / Transfer Ownership
    ↓
Assignment
```

The exact transaction/order depends on the current assignment contract.

---

# 43. Stale Offer Protection

A stale offer must not be able to modify current ride state.

Example:

```text
Offer A
   ↓
Expired

New Offer B
   ↓
Active

Late response for A
   ↓
Must NOT affect B
```

Offer identity and current-state validation protect this boundary.

---

# 44. Stale Driver Response

Similarly:

```text
Driver A
   ↓
Offer A
```

must not be able to respond on behalf of:

```text
Driver B
```

Driver identity validation is mandatory.

---

# 45. Offer Security Boundary

Offer responses are externally initiated input.

The response service must validate:

```text
Authenticated Driver
Offer Identity
Ride Identity
Driver Ownership
Offer State
Allowed Transition
```

before applying state changes.

---

# 46. Driver Authentication

The offer response path should rely on the existing authenticated-driver context.

The driver ID should not be trusted solely from request payload data if authenticated identity is already available.

The server-side identity should be authoritative.

---

# 47. Realtime Message Validation

Realtime messages should be validated before being converted into business commands.

Conceptually:

```text
Realtime Message
      ↓
Transport Validation
      ↓
Application Command
      ↓
Business Validation
      ↓
State Transition
```

This prevents transport concerns from leaking into domain logic.

---

# 48. Error Classification

Offer/response processing should distinguish:

```text
Invalid Request
Unauthorized Driver
Unknown Offer
Expired Offer
Invalid State Transition
Reservation Conflict
Infrastructure Failure
```

These are not interchangeable.

---

# 49. Invalid Response

An invalid response should not mutate:

```text
Ride
Offer
Reservation
```

unless the specific validation contract explicitly requires a state transition.

---

```text

   ↓

   ↓
Offer Creation
   ↓

   ↓
Driver Response
   ↓
```

---

# 59. Performance Requirements

Offer/response processing should optimize:

```text
Low Delivery Latency
Short Database Transactions
Small Realtime Payloads
Bounded Timeout Work
Idempotent Response Handling
```

Do not add distributed infrastructure unless actual deployment requirements justify it.

---

# 60. Timeout Scheduler Performance

The timeout scheduler should handle large numbers of short-lived offers without creating one heavyweight goroutine or timer per offer when the implementation cannot safely scale that way.

Use the existing Redis-backed scheduling abstraction.

Do not introduce a second scheduling system without a demonstrated need.

---

# 61. Recovery

If the application restarts while offers are pending:

```text
Persisted / Recoverable Offer State
      ↓
Timeout Scheduler / Recovery
      ↓
Expired or Active State
```

The system must not rely solely on in-memory timers for correctness if the offer lifecycle must survive process restarts.

---

# 62. Realtime Delivery vs Durable State

Realtime delivery is best-effort transport.

Durable business state determines:

```text
Offer State
Ride State
Assignment State
```

The system must not assume:

```text
WebSocket Send Succeeded
```

means:

```text
Driver Accepted
```

# 64. AI Agent Forbidden Patterns

An AI agent must not:

- send an offer before confirmed reservation,
- treat offer delivery as acceptance,
- accept responses without driver/ride/offer validation,
- allow stale offers to mutate current state,
- allow old responses to override terminal offer state,
- release another operation's reservation,
- hard-code offer timeout values,
- create a second timeout scheduler,
- put long external calls inside database transactions,
- make realtime transport the source of truth,
- move retry policy into response handlers,
- create a new reservation implementation,
- bypass the existing Driver Offer Gateway,
- silently swallow delivery failures,
- convert all response failures into generic errors,
- add complex event choreography where synchronous application coordination is sufficient.

# 66. Component Responsibility Matrix

| Component | Responsibility | Must Not Own |
|---|---|---|
| Driver Offer Gateway | Offer delivery abstraction | Candidate ranking |
| Driver Offer Handler | Offer coordination | Driver reservation policy |
| Timeout Scheduler | Delayed timeout execution | Assignment |
| Driver Response Service | Response business coordination | Transport implementation |
| Driver Response Command Service | Transactional response changes | Candidate discovery |
| Realtime Hub | Connection delivery | Ride ownership |
| Push Notifier | Push transport | Offer state authority |
| Reservation | Temporary driver ownership | Driver response |
| Dispatch Engine | Retry/next-candidate orchestration | Realtime transport internals |
| Assignment Service | Durable ride-driver ownership | Temporary offer transport |

# 69. Final Component Rule

When an AI agent is asked to modify offer/response behaviour, determine first:

```text
Is the change about:
    │
    ├── Creating an offer?
    │       → Offer Handler / Application Service
    │
    ├── Delivering an offer?
    │       → Driver Offer Gateway / Realtime
    │
    ├── Waiting for a response?
    │       → Timeout Scheduler
    │
    ├── Driver accepting/rejecting?
    │       → Driver Response Service
    │
    ├── Releasing temporary ownership?
    │       → Reservation
    │
    ├── Trying another candidate?
    │       → Dispatch / Retry Policy
    │
    └── Permanent ride-driver ownership?
            → Assignment / Ride Lifecycle
```

The Offer and Driver Response Components should remain responsible for **reliably coordinating the short-lived offer lifecycle between a successfully reserved driver and the driver's response, without becoming the reservation or assignment authority**.
