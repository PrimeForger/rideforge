# 1. Purpose

Infrastructure Components provide concrete implementations for capabilities required by the application layer.

They connect RideForge business/application components to external systems such as:

```text
PostgreSQL
Redis
Kafka / Redpanda
Realtime Transport
External Routing Providers
Cloud / Platform Services
```

The infrastructure layer exists to isolate technology-specific implementation from application and domain logic.

---

# 2. Infrastructure Boundary

Infrastructure components own:

```text
Database Drivers
Redis Clients
Message Broker Clients
External API Clients
Realtime Transport Adapters
Cache Implementations
Distributed Coordination Implementations
Storage Adapters
Infrastructure Health Adapters
```

They do not own:

```text
Ride Business Rules
Candidate Ranking
Dispatch Policy
Retry Policy
Driver Selection
Reservation Policy
Offer Decisions
Domain State Transitions
```

---

# 3. Core Principle

The application layer should depend on capabilities.

Infrastructure provides implementations.

Conceptually:

```text
Application Interface
        ↑
        │
Concrete Infrastructure
        ↓
External System
```

For example:

```text
DriverLocker
     ↑
RedisDriverLocker
     ↓
Redis
```

---

# 4. Infrastructure vs Application

Application components answer:

```text
What should happen?
```

Infrastructure components answer:

```text
How does the application communicate with the external system?
```

Example:

```text
MatchingEngine
    → decides to reserve a driver

DriverLocker
    → defines reservation capability

Redis Driver Locker
    → implements reservation using Redis
```

---

# 5. Infrastructure Adapters

An infrastructure adapter translates between:

```text
Application Contract
```

and:

```text
External Technology
```

It should hide:

```text
Redis Commands
SQL Driver APIs
Kafka Client APIs
HTTP Client Details
WebSocket Implementation
Provider-Specific Protocols
```

from application components.

---

# 6. PostgreSQL Adapter

PostgreSQL is the primary durable data infrastructure.

The PostgreSQL infrastructure layer provides:

```text
Connection Pool
Transaction Support
Database Driver Integration
Query Execution
Database Health
```

Repository implementations use this infrastructure.

---

# 7. PostgreSQL Connection Pool

The connection pool should be created once at application scope.

Conceptually:

```text
Bootstrap
   ↓
PostgreSQL Pool
   ↓
Repositories
```

Do not create pools inside repositories.

---

# 8. PostgreSQL Pool Configuration

Operational settings should be configuration-driven.

Examples:

```text
Maximum Connections
Minimum Connections
Connection Timeout
Idle Timeout
Health Check
```

The exact current configuration is authoritative.

---

# 9. PostgreSQL Infrastructure Failure

Infrastructure should distinguish:

```text
Connection Failure
Query Failure
Transaction Failure
Timeout
Deadlock
```

from application-level conditions such as:

```text
Record Not Found
Business Conflict
Invalid State
```

Infrastructure must preserve enough error information for the application layer to classify the result correctly.

---

# 10. Redis Adapter

Redis provides low-latency operational infrastructure.

Current usage includes:

```text
Driver Cache
H3 Driver Index
Redis GEO
Driver Reservation
Timeout Scheduling
Operational State
```

Each capability should remain behind its appropriate abstraction.

---

# 11. Redis Client Ownership

The Redis client should be constructed at application scope.

Conceptually:

```text
Bootstrap
   ↓
Redis Client
   ↓
Redis-backed Components
```

Individual components should not independently create Redis connections.

---

# 12. Redis Key Isolation

Infrastructure implementations should centralize key construction for their owned resource.

For example:

```text
Driver Cache
    → owns driver-state keys

H3 Index
    → owns cell/index keys

Driver Locker
    → owns reservation keys

Timeout Scheduler
    → owns timeout keys
```

Avoid shared ad-hoc key construction across unrelated components.

---

# 13. Redis Atomicity

Operations requiring atomicity must use an appropriate Redis mechanism.

Examples:

```text
Lua Script
WATCH / MULTI / EXEC where appropriate
Atomic Redis Command
```

For H3 driver movement and reservation ownership, atomicity is a correctness requirement.

Do not replace an atomic operation with:

```text
GET
SREM
SADD
SET
```

when concurrent updates can create inconsistent state.

---

# 14. Redis TTL

TTL belongs to the component that owns the corresponding key.

Infrastructure implementations should apply the TTL required by the component contract.

Operational TTL values should be configuration-driven where they represent runtime policy.

---

# 15. Redis Failure Behaviour

Redis failures must remain distinguishable from valid empty results.

For example:

```text
Redis unavailable
```

is not equivalent to:

```text
No drivers found
```

The infrastructure adapter must return an explicit infrastructure error.

The application layer decides the safe business response.

---

# 16. Redis Batch Operations

Where the application requires multiple independent Redis reads, infrastructure should use batching/pipelining where appropriate.

Conceptually:

```text
Request
   ↓
Pipeline
   ├── Cell 1
   ├── Cell 2
   └── Cell 3
   ↓
Single Network Round Trip
```

Avoid introducing sequential network calls when the component contract naturally supports a batch.

---

# 17. Redis GEO Adapter

Redis GEO is a secondary geographic index.

The infrastructure adapter exposes geographic operations through the Geo abstraction.

It should not contain:

```text
Dispatch Ranking
ETA Policy
Candidate Selection
```

---

# 18. Redis Driver Locker

The Redis Driver Locker implements distributed driver ownership.

Conceptually:

```text
DriverLocker
     ↑
Redis Implementation
     ↓
Atomic Redis Ownership
```

The implementation must protect against:

```text
Concurrent Reservation
Stale Release
Reservation Expiry
Multiple Dispatch Nodes
```

---

# 19. Reservation Ownership

The infrastructure implementation must not release a reservation belonging to another owner.

Conceptually:

```text
Owner A
   ↓
Reservation A

A expires

Owner B
   ↓
Reservation B

Cleanup A
   ↓
Must NOT delete B
```

Ownership validation is therefore part of the infrastructure correctness contract.

---

# 20. Message Broker Adapter

Kafka/Redpanda infrastructure provides:

```text
Producer
Consumer
Connection
Serialization Transport
Partitioning
Consumer Group
Acknowledgement
```

Application services should not directly depend on the broker client library.

---

# 21. Producer Adapter

The producer adapter should translate:

```text
Application Event
```

into:

```text
Broker Message
```

It owns:

```text
Topic
Partition Key
Message Headers
Serialization
Broker Publication
```

Business event semantics remain outside the broker adapter.

---

# 22. Consumer Adapter

The consumer adapter handles:

```text
Message Polling
Deserialization
Acknowledgement
Consumer Group Lifecycle
Shutdown
```

It delegates business processing to application handlers.

---

# 23. Consumer Error Boundary

Infrastructure consumer errors include:

```text
Broker Connection Failure
Deserialization Failure
Consumer Failure
Commit/Acknowledgement Failure
```

Application handler errors are a separate category.

The infrastructure layer should preserve this distinction.

---

# 24. Broker Retry

Infrastructure may retry transient broker communication failures where the client contract supports it.

Business retry policy must not be silently implemented inside the broker adapter.

For example:

```text
Kafka connection retry
```

is infrastructure behaviour.

But:

```text
Try another driver
```

is dispatch policy.

---

# 25. External Routing Providers

Future routing infrastructure may support:

```text
Google
Mapbox
OSRM
Valhalla
```

through a common application-facing routing abstraction.

Conceptually:

```text
Routing Service
      ↑
Provider Adapter
      ↓
External Routing API
```

---

# 26. Routing Adapter Responsibility

A routing adapter should handle:

```text
Request Mapping
Authentication
HTTP Transport
Response Parsing
Provider Errors
Timeouts
```

It should not decide:

```text
Which Driver to Select
Whether ETA Is Acceptable
How ETA Is Weighted
```

---

# 27. Routing Timeout

External routing calls must have explicit bounded timeouts.

Never allow an external routing provider to block the dispatch hot path indefinitely.

The timeout belongs to configuration/infrastructure policy.

---

# 28. Routing Failure

Routing failures should be classified clearly:

```text
Provider Timeout
Provider Unavailable
Invalid Request
Rate Limited
Malformed Response
```

The application/dispatch policy determines the fallback behaviour.

---

# 29. Routing Provider Selection

If multiple providers are supported:

```text
Configuration
      ↓
Routing Builder
      ↓
Selected Provider Adapter
```

Provider-specific conditionals should not be spread across ranking or discovery code.

---

# 30. Realtime Transport Adapter

Realtime infrastructure provides transport for:

```text
Driver Offers
Driver Responses
Driver Location Updates
Connection Events
```

The application should depend on a realtime capability abstraction.

---

# 31. Realtime Transport Boundary

Conceptually:

```text
Application
     ↓
Realtime Gateway
     ↓
Transport Adapter
     ↓
WebSocket / Realtime Provider
```

Transport implementation should not contain ride business rules.

---

# 32. Driver Connection State

The infrastructure layer may maintain transport-level connection information.

For example:

```text
Connected
Disconnected
Connection ID
Transport Session
```

Business availability remains owned by the appropriate application/realtime component.

---

# 33. Push Notification Adapter

If push notifications are supported:

```text
Application Offer Gateway
      ↓
Push Notification Interface
      ↓
Provider Adapter
      ↓
External Push Service
```

Provider-specific SDK details remain inside the infrastructure adapter.

---

# 34. HTTP Client Infrastructure

External HTTP clients should provide:

```text
Timeout
Connection Reuse
Context Propagation
Request Headers
Authentication
Response Handling
```

Use shared clients where connection reuse is beneficial.

Avoid creating a new HTTP client for every request.

---

# 35. External API Resilience

External infrastructure should use bounded:

```text
Timeouts
Retries
Connection Limits
```

where appropriate.

Retries must respect the operation's idempotency.

Do not automatically retry every HTTP request.

---

# 36. Infrastructure Error Mapping

Infrastructure adapters should return errors that allow application services to distinguish:

```text
Not Found
Conflict
Timeout
Unavailable
Invalid Response
Authentication Failure
Rate Limit
Internal Infrastructure Failure
```

Avoid returning provider-specific errors directly if they unnecessarily couple application code to a vendor.

---

# 37. Infrastructure Error Wrapping

Errors should preserve the underlying cause while adding component context.

Conceptually:

```text
routing provider timeout
    caused by
HTTP timeout
```

The error chain should remain inspectable where the language/runtime supports it.

---

# 38. Infrastructure Health

Infrastructure components may expose health checks for:

```text
PostgreSQL
Redis
Kafka/Redpanda
External Provider
```

Health checks should remain lightweight.

They should not perform expensive business operations.

---

# 39. Health vs Readiness

Infrastructure health information feeds application readiness where appropriate.

For example:

```text
Redis unavailable
```

may make a dispatch service unready if Redis is mandatory for the dispatch path.

The exact readiness policy belongs to runtime configuration, not the infrastructure adapter itself.

---

# 40. Infrastructure Metrics

Infrastructure should expose measurements such as:

```text
Database Query Latency
Redis Command Latency
Redis Errors
Broker Publish Latency
Broker Consumer Latency
External API Latency
External API Errors
Connection Pool Usage
```

Use shared observability conventions.

---

# 41. Infrastructure Tracing

Infrastructure calls should create spans where they provide meaningful diagnostic value.

Examples:

```text
postgres.query
redis.command
kafka.publish
kafka.consume
routing.request
realtime.send
```

Do not create excessive spans for trivial internal operations.

---

# 42. Infrastructure Logging

Log infrastructure failures with:

```text
Component
Operation
Dependency
Error
Correlation / Trace Context
```

Do not log:

```text
Passwords
API Keys
Tokens
Sensitive Payloads
```

---

# 43. Resource Lifecycle

Infrastructure resources should have explicit lifecycle ownership.

Examples:

```text
PostgreSQL Pool
Redis Client
Kafka Producer
Kafka Consumer
HTTP Client
Realtime Transport
```

The component that constructs a shared resource should coordinate its shutdown.

---

# 44. Graceful Shutdown

Infrastructure shutdown should be bounded and coordinated.

Conceptually:

```text
Stop New Work
     ↓
Stop Consumers / Workers
     ↓
Flush Required Output
     ↓
Close Connections
     ↓
Exit
```

Do not close a shared resource while dependent components are still using it.

---

# 45. Infrastructure Configuration

Infrastructure configuration should be typed.

Examples:

```text
PostgresConfig
RedisConfig
KafkaConfig
RoutingConfig
RealtimeConfig
```

Do not pass raw environment variables into infrastructure methods.

---

# 46. Infrastructure Secrets

Infrastructure components may consume credentials but must not expose them.

Secrets must not appear in:

```text
Logs
Errors
Metrics
Traces
Configuration Dumps
```

---

# 47. Infrastructure Isolation

An infrastructure adapter should not import unrelated business packages merely to perform its external operation.

Preferred:

```text
Infrastructure
    → Application Contract
```

Avoid:

```text
Infrastructure
    → MatchingEngine
    → Ranking
    → Dispatch Policy
```

---

# 48. No Business Logic in Adapters

Bad:

```text
Redis Adapter
   ↓
if driver.rating > X
```

Good:

```text
Ranking Service
   ↓
Driver Quality Policy
```

The adapter only retrieves/persists/transports the data required by the caller.

---

# 49. Infrastructure Testing

Infrastructure components require integration tests where correctness depends on external-system semantics.

Examples:

```text
Redis Atomicity
Redis TTL
PostgreSQL Transactions
Kafka Publication
Consumer Acknowledgement
Routing Response Parsing
Realtime Delivery
```

Unit tests alone are insufficient for technology-specific behaviour.

---

```text
Same-Cell Update
Empty Cell Cleanup
Batch Lookup
Reservation Acquisition
Reservation Conflict
Reservation Release
Stale Release Protection
TTL Expiry
```

These verify actual Redis semantics.

---

# 51. PostgreSQL Integration Tests

Important tests include:

```text
Repository Reads
Repository Writes
Transactions
Conditional State Transitions
Constraints
Outbox Persistence
Rollback
Concurrent Updates
```

Use the real PostgreSQL engine for SQL semantics.

---

# 52. Messaging Integration Tests

Important tests include:

```text
Publish
Consume
Partition Key
Consumer Group
Retry
Acknowledgement
Redelivery
DLQ
Shutdown
```

The exact test infrastructure may use local Kafka-compatible infrastructure.

---

# 53. External Provider Tests

Routing/push/realtime providers should have:

```text
Unit Tests for Mapping
Contract Tests
Integration Tests where appropriate
Failure Tests
Timeout Tests
```

External network calls should not be required for every unit test.

---

# 54. Infrastructure Contract Tests

Where multiple implementations satisfy the same application interface, define shared contract expectations.

For example:

```text
DriverLocker Contract
    ↓
Redis Driver Locker
```

Any future implementation should satisfy the same behaviour.

---

# 55. Provider Replacement

Infrastructure abstraction should make provider replacement possible without changing business logic.

For example:

```text
Routing Service
   ├── OSRM Adapter
   ├── Mapbox Adapter
   └── Google Adapter
```

The ranking/dispatch layer should remain unchanged.

---

# 56. Avoid Premature Abstraction

Do not create generic abstractions for technologies that have no realistic replacement or multiple implementation requirement.

Abstraction should exist where it provides:

```text
Application Boundary
Testability
Provider Replacement
Technology Isolation
```

not merely because a component uses an external library.

---

# 57. Infrastructure Performance

Infrastructure should optimize:

```text
Connection Reuse
Batching
Bounded Concurrency
Low Allocation
Short Network Paths
Timeouts
```

Avoid introducing infrastructure complexity without measured benefit.

---

# 58. Infrastructure and Dispatch Latency

Dispatch infrastructure is hot-path infrastructure.

Particularly sensitive operations include:

```text
H3 Lookup
Driver Cache Fetch
Reservation
Realtime Offer
ETA Lookup
```

These should have clear latency measurements.

---

# 59. Infrastructure Backpressure

Messaging and external systems may become slower than the application.

Infrastructure should expose failures/backpressure rather than allowing unlimited in-memory buffering.

Bound:

```text
Queues
Workers
Connections
Retries
Payload Sizes
```

where appropriate.

---

# 60. AI Agent Implementation Rules

Before modifying infrastructure components, an AI coding agent must:

1. Read this document.
2. Read the relevant architecture documentation.
3. Identify the application-facing interface.
4. Inspect the existing infrastructure implementation.
5. Inspect configuration for the dependency.
6. Inspect resource ownership and lifecycle.
7. Inspect existing error types.
8. Search for an existing adapter before creating another.
9. Preserve shared connection/resource ownership.
10. Preserve timeout and retry semantics.
11. Add integration tests for technology-specific behaviour.
12. Verify infrastructure failures remain distinguishable from valid empty results.
13. Verify no business rules moved into the adapter.
14. Run relevant integration tests.
15. Run the full relevant test suite before completion.

---

# 61. AI Agent Forbidden Patterns

An AI agent must not:

- put business rules in infrastructure adapters,
- construct duplicate database/Redis clients,
- bypass application interfaces,
- expose provider-specific APIs unnecessarily,
- swallow infrastructure errors,
- convert dependency failure into an empty result,
- retry indefinitely,
- retry non-idempotent operations blindly,
- hard-code operational timeouts,
- log secrets,
- create unbounded worker pools,
- create one connection per request,
- create one HTTP client per request,
- introduce a new external provider without an architectural need,
- create generic abstractions without a meaningful boundary,
- replace an existing infrastructure implementation without checking all consumers.

```text
PostgreSQL

H3 / Redis GEO
Driver Locker
Kafka-compatible Messaging
```


The primary objective going forward is to keep these boundaries stable while improving reliability and performance based on measured requirements.

# 66. Final Component Rule

When an AI agent is asked to modify infrastructure behaviour, determine first:

```text
Is the change about:
    │
    ├── Durable database access?
    │       → PostgreSQL Infrastructure
    │
    ├── Operational state?
    │       → Redis Infrastructure
    │
    ├── Distributed ownership?
    │       → Driver Locker Infrastructure
    │
    ├── Event transport?
    │       → Kafka/Redpanda Infrastructure
    │
    ├── External routing?
    │       → Routing Adapter
    │
    ├── Realtime transport?
    │       → Realtime Adapter
    │
    ├── External notification?
    │       → Push Adapter
    │
    └── Business decision?
            → Application / Domain Layer
```

Infrastructure Components should remain responsible for **isolating external technologies behind stable application-facing capabilities while preserving correctness, bounded resource usage, explicit failure semantics, and clean lifecycle ownership**.
