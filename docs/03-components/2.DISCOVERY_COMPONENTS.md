# RideForge — Discovery Components

> **Document:** `docs/03-components/2.DISCOVERY_COMPONENTS.md`

# 1. Purpose

The Discovery Components are responsible for finding a bounded set of geographically relevant driver candidates for a matchable ride.

The discovery layer answers:

> **Which driver IDs are geographically relevant enough to enter the candidate-processing pipeline, given the already-resolved dispatch context and search policy?**

It does not decide:

```text
Driver Eligibility
Driver Quality
Final Ranking
Reservation
Offer
Assignment
```

Those decisions belong to later components.

---

# 2. Discovery Boundary

The discovery boundary is:

```text
Ride / Pickup Context
      ↓
Resolved Dispatch Context
      ↓
Geographic Search Policy
      ↓
Spatial Index / Location Search
      ↓
Driver IDs + Discovery Context
      ↓
Candidate Discovery Result
```

The discovery layer receives the **effective dispatch strategy** resolved by the dispatch/configuration layer. It must not independently resolve the configuration hierarchy.

The downstream candidate pipeline then performs enrichment, eligibility processing, strategy-specific prioritization, and ranking.

Important separation:

```text
Configuration Hierarchy
        ↓
Dispatch Strategy Resolution
        ↓
Candidate Discovery
        ↓
Candidate Pipeline
        ↓
Ranking / Reservation
```

Discovery is therefore a geographic candidate-generation boundary, not a dispatch-strategy resolution boundary.

---

# 3. Discovery Is Candidate Generation

Discovery produces a **candidate population**, not a final match.

Therefore:

```text
Discovered
    ≠
Eligible

Eligible
    ≠
Ranked

Ranked
    ≠
Reserved

Reserved
    ≠
Assigned
```

This distinction is fundamental to the architecture.

---

# 4. Current Discovery Architecture

The current discovery system is structured around:

```text
Resolved Dispatch Context
      ↓
CandidateSearcher
      ↓
Spatial Discovery Strategy
      ↓
Expansion / Search Policy
      ↓
Spatial Index / Geo Service
      ↓
Candidate IDs + Discovery Context
```

The **dispatch strategy** and the **spatial discovery strategy** are separate concepts.

Dispatch strategy may be:

```text
Smart Stand Dispatch
Smart Dispatch
```

Spatial discovery strategy may be:

```text
H3-based discovery
Geo-based discovery
```

The discovery implementation must not assume:

```text
Smart Stand Dispatch = stand-only search
```

or:

```text
Smart Dispatch = a particular spatial implementation
```

The discovery layer remains focused on geographic candidate generation while preserving enough context for downstream strategy-specific processing.

# 5. CandidateSearcher

`CandidateSearcher` is the application-facing discovery abstraction.

The Dispatch Engine depends on this abstraction instead of depending directly on H3 or Redis.

Conceptually:

```text
MatchingEngine
      ↓
CandidateSearcher
      ↓
Discovery Strategy
```

This keeps dispatch orchestration independent from geographic implementation details.

---

# 6. Discovery Request

A discovery request contains the information required to locate nearby candidates.

The current matching flow provides values such as:

```text
PickupLat
PickupLng
RadiusKm
CandidateLimit
MatchingAttempt
```

Where required by the dispatch flow, the request may also carry resolved discovery context such as:

```text
EffectiveDispatchStrategy
OriginLocation
PreferredStand
StandRadiusContext
SearchScope
ExpansionPolicy
```

The exact contract should use explicit types rather than leaking configuration storage details into discovery.

The discovery layer may use the attempt number as input to search-policy behaviour.

The discovery request must contain the **already-resolved effective dispatch strategy** when strategy-aware discovery behaviour is required. Discovery must not walk the configuration hierarchy itself.

---

# 7. Discovery Result

The discovery result represents the output of geographic candidate generation.

The result should contain enough information for the candidate pipeline to continue processing without requiring the discovery layer to perform ranking or assignment.

The primary candidate identity is the driver ID.

Where relevant, discovery should preserve contextual metadata such as:

```text
Candidate Location
Candidate Stand
Stand Membership
Queue Position
Discovery Source
Discovery Distance / Approximation
Search Expansion Level
```

This metadata is contextual information, not a final ranking decision.

In particular, a candidate's source location or stand membership must not be converted into automatic ineligibility merely because the ride originated in another location.

---

# 8. H3 Strategy

The H3 strategy is the primary spatial discovery strategy when H3 is enabled.

Conceptually:

```text
Pickup Coordinates
       ↓
H3 Cell
       ↓
Nearby H3 Cells
       ↓
H3 Driver Index
       ↓
Driver IDs
```

The strategy should remain focused on spatial candidate generation.

---

# 9. H3 Service

The H3 service provides the geographic operations required by the discovery strategy.

Responsibilities include operations such as:

```text
Coordinate → H3 Cell
Cell Neighbourhood
Search Ring
Maximum Search Ring
```

The H3 service abstracts the underlying H3 library from the rest of the application.

---

# 10. H3 Driver Index

The H3 driver index maps active driver locations to H3 cells.

Conceptually:

```text
H3 Cell
   ↓
Driver IDs
```

and:

```text
Driver
   ↓
Current H3 Cell
```

The index is an operational spatial index.

It is not the authoritative driver business record.

---

# 11. Driver Movement

When a driver changes H3 cells:

```text
Old Cell
   ↓
Remove Driver
   ↓
New Cell
   ↓
Add Driver
```

The existing H3 index implementation is responsible for maintaining this membership safely.

Discovery only consumes the index.

---

# 12. Same-Cell Movement

When a driver remains in the same H3 cell, discovery infrastructure should avoid unnecessary cell-membership movement.

The driver location/realtime layer may still refresh location freshness independently.

This distinction prevents unnecessary spatial-index writes without losing realtime information.

---

# 13. Atomic H3 Movement

H3 cell membership changes must preserve index consistency under concurrent location updates.

The spatial index implementation is responsible for ensuring:

```text
Old Membership
+
New Membership
+
Driver → Cell Mapping
```

remain consistent.

The discovery components must not implement their own movement mechanism.

---

# 14. H3 Ring Search

The discovery system searches progressively through nearby H3 cells.

Conceptually:

```text
Ring 0
   ↓
Enough candidates?
   ├── Yes → Stop
   └── No
        ↓
      Ring 1
        ↓
      Enough?
        ├── Yes → Stop
        └── No
             ↓
           Ring 2
```

The purpose is to avoid searching a large geographic area unnecessarily.

---

# 15. Ring Expansion

Ring expansion is separated from the low-level H3 implementation.

Conceptually:

```text
H3 Service
      ↓
Ring Expander
      ↓
Expansion Policy
```

The expander performs the search mechanics.

The policy determines how aggressively the search should expand.

For Smart Stand Dispatch, expansion can represent progression from a preferred stand-oriented search toward broader eligible geographic candidate discovery when the preferred stand cannot provide a suitable driver.

Expansion must not be interpreted as changing the resolved dispatch strategy.

For example:

```text
Smart Stand Dispatch
      ↓
Preferred stand search
      ↓
Insufficient suitable supply
      ↓
Broader search
```

remains Smart Stand Dispatch unless an explicit higher-level business rule defines another strategy.

---

# 16. Adaptive Ring Expansion

The current architecture includes adaptive ring expansion.

The expansion decision can consider the local driver-density context.

Conceptually:

```text
Density
   ↓
Expansion Profile
   ↓
Search Ring
```

Dense areas can remain local while sparse areas can expand more quickly.

---

# 17. Density Provider

The density provider supplies the discovery policy with information about driver density.

The current implementation uses the H3/Redis infrastructure to obtain this information.

The provider should answer spatial supply questions without becoming responsible for final candidate eligibility.

---

# 18. Density Classifier

The density classifier converts density information into an operational category.

Conceptually:

```text
Driver Density
      ↓
Density Class
```

The resulting class can influence expansion behaviour.

The classifier must remain policy-oriented rather than implementing Redis or H3 storage details.

---

# 19. Expansion Profile

The expansion profile determines how search behaviour should respond to the detected density.

Conceptually:

```text
Sparse
   ↓
More aggressive expansion

Dense
   ↓
More conservative expansion
```

The profile should be configuration/policy-driven.

---

# 20. Expansion Policy

The expansion policy decides the next useful search boundary.

It should consider:

```text
Current Ring
Available Supply
Candidate Requirement
Density Context
Maximum Search Ring
```

It should not perform Redis lookups directly if the required data is already provided through its dependencies.

---

# 21. Search Budget

Discovery is bounded by a search budget.

The budget limits unnecessary work such as:

```text
Maximum Ring
Candidate Limit
Search Scope
```

The exact budget values belong to configuration/policy.

The discovery engine must never expand indefinitely.

---

# 22. Candidate Limit

The candidate limit bounds the amount of candidate data returned to the matching pipeline.

The purpose is to control:

```text
Redis Work
Memory
Candidate Enrichment
Ranking Work
Dispatch Latency
```

A larger candidate set is not automatically better.

---

# 23. Progressive Search

The discovery engine should prefer progressive search over a single unnecessarily large spatial query.

Preferred:

```text
Ring 0
  ↓
Evaluate
  ↓
Ring 1
  ↓
Evaluate
  ↓
Ring 2
```

instead of:

```text
Always search maximum ring
```

This reduces unnecessary candidate retrieval in dense areas.

---

# 24. Early Stop

Discovery should stop as soon as the search policy determines that sufficient candidates have been found.

Conceptually:

```text
Candidates Found
      ↓
Enough?
 ├── Yes → Stop
 └── No  → Expand
```

This is one of the most important performance properties of the discovery layer.

---

# 25. Sparse Areas

In sparse areas:

```text
Few Drivers
    ↓
Search Wider
```

The adaptive expansion policy may therefore progress through additional rings more aggressively.

The search must still respect the configured maximum boundary.

---

# 26. Dense Areas

In dense areas:

```text
Many Drivers Nearby
    ↓
Stay Local
```

The discovery engine should avoid unnecessary expansion.

This reduces:

```text
Redis Reads
Candidate Count
Ranking Cost
Dispatch Latency
```

---

# 27. Redis H3 Index Lookup

The H3 strategy uses the H3 driver index to retrieve driver IDs from relevant cells.

Where multiple cells must be queried, the underlying index should use an efficient multi-cell retrieval strategy.

The discovery layer should not perform one unnecessary network round trip per cell when the index abstraction can batch the operation.

---

# 28. Multi-Cell Lookup

Conceptually:

```text
Cells:
C1
C2
C3
C4

      ↓

Batch / Pipeline Lookup

      ↓

Driver IDs
```

This reduces network round trips compared with independent sequential lookups.

---

# 29. Driver ID Deduplication

A driver can exist in overlapping search results or multiple cells due to index conditions.

The discovery result must not intentionally produce duplicate candidate identities.

Deduplication should happen at the appropriate candidate/discovery boundary.

The candidate pipeline also maintains its own duplicate protection as a defensive invariant.

---

# 30. Discovery vs Candidate Pipeline Deduplication

Both layers have distinct purposes.

Discovery should avoid unnecessarily returning duplicate IDs.

The candidate pipeline should still protect itself against duplicates because:

```text
Multiple Discovery Paths
Future Strategies
Data Inconsistency
Component Reuse
```

must not break downstream correctness.

---

# 31. Geo Strategy

A Geo strategy provides an alternative spatial discovery path when H3 discovery is disabled or when the configured system requires a geographic implementation based on the geo service.

Conceptually:

```text
CandidateSearcher
      ↓
GeoStrategy
      ↓
Geo Service
      ↓
Nearby Driver IDs
```

This is a **spatial discovery strategy**, not a dispatch strategy.

The Dispatch Engine may have already resolved:

```text
Smart Stand Dispatch
```

or:

```text
Smart Dispatch
```

independently of whether discovery uses H3 or Geo.

The Dispatch Engine does not need to know the low-level spatial implementation.

---

# 32. Spatial Strategy Selection

The application composition layer selects the **spatial discovery strategy**.

Conceptually:

```text
Infrastructure / Application Configuration
     ↓
Spatial Discovery Implementation
 ├── H3 → H3 Strategy
 └── Geo → Geo Strategy
```

This decision belongs in bootstrap/component composition rather than inside the matching engine.

This must not be confused with dispatch strategy resolution:

```text
Dispatch Configuration Hierarchy
        ↓
Effective Dispatch Strategy
        ↓
Smart Stand Dispatch / Smart Dispatch
```

The two resolution processes are independent.

---

# 33. Strategy Contract

Both strategies must satisfy the same candidate-search contract.

This allows:

```text
H3
```

and:

```text
Geo
```

to be exchanged without changing dispatch orchestration.

---

# 34. Discovery Does Not Filter Availability

A driver being returned by H3 or GEO does not mean the driver is available.

For example:

```text
Driver exists in H3 cell
      ↓
Discovered
      ↓
Availability Filter
      ↓
Eligible / Rejected
```

Availability remains a candidate-pipeline responsibility.

---

# 35. Discovery Does Not Filter Quality

The discovery layer should not rank drivers based on:

```text
Rating
Acceptance Rate
Cancellation Rate
Fairness
ETA
```

These belong to later candidate processing/ranking.

---

# 36. Discovery Does Not Reserve Drivers

Discovery must never acquire driver reservations.

The sequence remains:

```text
Discovery
   ↓
Pipeline
   ↓
Ranking
   ↓
Reservation
```

Keeping reservation outside discovery prevents geographic search from becoming coupled to driver ownership.

---

# 37. Discovery Does Not Create Offers

Offers are outside the discovery boundary.

Discovery only produces candidate identities/data required by downstream processing.

---

# 38. Discovery and ETA

Discovery should generally use inexpensive geographic indexing.

Expensive routing/ETA calculations belong later in the candidate-ranking flow where practical.

Preferred:

```text
H3 / Geo
   ↓
Candidate Narrowing
   ↓
Filtering
   ↓
ETA Calculation
   ↓
Ranking
```

This prevents unnecessary routing calls for drivers that will later be rejected.

---

# 39. Discovery and Distance

Geographic discovery determines approximate spatial relevance.

Exact distance refinement may be performed later through the geo/refinement components.

The discovery layer should not turn approximate cell membership into an authoritative exact distance decision.

---

# 40. Refinement Boundary

When secondary geographic refinement is required:

```text
Discovery
   ↓
Candidate IDs
   ↓
Geo Refinement
   ↓
Refined Geographic Information
```

The refinement component owns the refinement calculation.

The discovery strategy should not duplicate it.

---

# 41. Discovery Performance

The discovery path is part of the dispatch hot path.

The implementation should prioritize:

```text
Low Redis Round Trips
Bounded Cell Searches
Early Stop
Bounded Candidate Count
Minimal Data Transfer
Efficient Deduplication
```

---

# 42. Avoiding Over-Expansion

A search must not expand simply because the maximum configured ring exists.

Expansion should have a reason:

```text
Insufficient Candidate Supply
Policy Requirement
Configured Cross-Location Expansion
```

For Smart Stand Dispatch, the existence of a preferred stand does not prevent broader discovery when the stand cannot provide a suitable driver.

For Smart Dispatch, there is no stand-preference restriction.

Expansion should remain bounded by the applicable geographic/search policy and must not be used to silently change the resolved dispatch strategy.

---

# 43. Search Result Stability

Discovery should return a candidate population representing the state observed during that search.

It must not attempt to guarantee that every discovered driver remains available afterward.

Availability and reservation can change concurrently.

---

# 44. Discovery Concurrency

Discovery must assume driver locations can change during a search.

For example:

```text
Search starts
    ↓
Driver moves
    ↓
Candidate returned
```

This is acceptable.

Downstream availability and reservation checks provide the final protection.

---

# 45. Stale Driver Protection

Discovery indexes may contain stale entries temporarily.

The discovery layer should not assume that every indexed driver is currently dispatchable.

Stale/realtime validation belongs to the candidate pipeline and driver-state infrastructure.

---

# 46. Index Consistency

The H3 driver index must remain consistent enough that:

```text
Driver Location
      ↓
Expected H3 Cell
```

maps to:

```text
H3 Cell
      ↓
Driver ID
```

without persistent stale membership.

Index repair/reconciliation belongs to the reliability layer.

---

# 47. Empty Cells

Empty H3 cells should not create unnecessary persistent index state.

Cleanup is an H3 index responsibility, not a discovery responsibility.

---

# 50. Discovery Failure Classification

The system should distinguish:

```text
No Drivers Found
```

from:

```text
Discovery Infrastructure Failure
```

For example:

```text
Redis unavailable
```

is not equivalent to:

```text
Redis available but no drivers in searched cells
```

The distinction matters for retry and operational diagnosis.

---

# 51. Failure Handling

If the spatial index fails:

```text
Discovery
   ↓
Infrastructure Error
```

the error should be propagated through the application flow.

The discovery layer should not silently return an empty result unless the contract explicitly defines that behaviour.

---

# 52. Configuration

Discovery policy should be configuration-driven.

Relevant configuration may include:

```text

```

The exact configuration structure belongs to the application configuration package.

Discovery components may consume configuration through explicit constructor parameters or policy providers.

They should not independently read environment variables throughout the search path.

Configuration should be composed at bootstrap.

# 56. H3 Strategy Responsibilities

The H3 strategy should:

- translate the discovery request into a spatial search,
- use the configured expansion mechanism,
- retrieve driver IDs,
- respect search/candidate budgets,
- return a discovery result.

It should not:

- rank drivers,
- reserve drivers,
- create offers,
- assign rides.

---

# 57. Ring Expander Responsibilities

The ring expander should:

- generate/search progressively relevant rings,
- obtain cells through the H3 service,
- use the expansion policy,
- stop when the policy says enough candidates exist,
- respect the maximum search boundary.

It should not own driver business state.

---

# 58. Expansion Policy Responsibilities

The expansion policy should decide:

```text
Continue?
Next Ring?
Search Scope?
```

based on the available policy inputs.

It should not directly implement:

```text
Redis Commands
H3 Library Calls
Driver Cache Reads
```

unless those are explicitly part of its injected dependencies.

---

# 59. Density Rule Responsibilities

The density rule translates local supply context into an expansion decision/profile.

It should remain focused on:

```text
Density
      ↓
Expansion Behaviour
```

rather than becoming a general matching policy engine.

---

# 60. Density Provider Responsibilities

The density provider supplies density information from the operational spatial state.

It should hide infrastructure details from the policy layer.

Conceptually:

```text
DensityRule
      ↓
DensityProvider
      ↓
Redis / H3 Data
```

---

# 61. Spatial Candidate Search Strategy Selection

The active **spatial discovery strategy** is selected at application composition time.

This allows future spatial strategies to be introduced without changing:

```text
Dispatch Strategy Resolution
CandidatePipeline
RankingEngine
```

The effective dispatch strategy remains an independent input to the discovery/candidate flow.

# 62. Extending Discovery

A future discovery strategy should implement the existing search contract rather than introducing a special dispatch path.

Potential examples:

```text

PostGIS
```

Only introduce a new strategy when the existing abstraction genuinely cannot represent the required behaviour.

# 66. AI Agent Forbidden Patterns

An AI agent must not:

- implement ranking inside discovery,
- implement reservation inside discovery,
- create offers from discovery,
- treat H3 membership as driver availability,
- introduce direct Redis calls into higher-level policies when an existing provider exists,
- create a second H3 index abstraction,
- create a second ring-expansion algorithm,
- bypass the existing `CandidateSearcher` contract,
- perform expensive ETA routing for the entire raw spatial search,
- remove search budgets without a concrete requirement,
- search the maximum ring unconditionally,
- silently convert infrastructure failures into empty candidate results,
- add a new discovery strategy without evaluating the existing strategy contract,
- introduce complexity solely to satisfy a roadmap phase,
- resolve the State → District → Town → Rural Area → Stand → Ride configuration hierarchy inside discovery,
- treat Smart Stand Dispatch as a stand-only geographic search,
- reject a non-stand driver solely because the pickup is within a stand radius,
- reject a driver solely because the driver belongs to another nearby location,
- treat a location's dispatch strategy as a hard cross-location candidate boundary,
- silently change Smart Stand Dispatch into Smart Dispatch when preferred stand supply is insufficient,
- confuse spatial discovery strategy (H3/Geo) with dispatch strategy (Smart Stand/Smart Dispatch).

# 71. Dispatch Strategy Context

The discovery components participate in a dispatch flow where the effective dispatch strategy is resolved before candidate processing.

The discovery layer may receive:

```text
EffectiveDispatchStrategy
OriginLocation
PreferredStand
StandRadiusContext
SearchScope
```

The discovery layer must use these values only where they affect geographic candidate generation.

It must not independently determine which configuration level wins.

The canonical flow is:

```text
Ride
 ↓
Configuration Hierarchy
 ↓
Effective Dispatch Strategy
 ↓
Discovery Context
 ↓
Candidate Discovery
 ↓
Candidate Pipeline
 ↓
Strategy-Specific Prioritization
 ↓
```

# 72. Smart Stand Dispatch Discovery Behaviour

When the effective strategy is:

```text
Smart Stand Dispatch
```

and the rider is inside a configured auto-stand radius, discovery should support a **preferred stand-first search**.

Conceptually:

```text
Pickup
 ↓
Preferred Stand Radius Match
 ↓
Preferred Stand Candidates
 ↓
Suitable Supply?
 ├── YES → continue candidate processing
 └── NO  → broaden geographic discovery
```

Broader discovery may include:

```text
Drivers outside the preferred stand
Drivers at nearby stands
Drivers outside all stands
Drivers from nearby locations
```

The discovery layer must not discard these candidates merely because they are not members of the preferred stand.

The downstream strategy/ranking layer determines how the preferred stand context affects prioritization.

---

# 73. Smart Stand Dispatch Outside Stand Radius

If the rider is outside the radius of all configured auto stands:

```text
Smart Stand Dispatch
        +
No Stand Radius Match
        ↓
Normal Eligible Nearby Driver Discovery
```

There is no stand-specific geographic restriction.

Drivers may be discovered regardless of:

```text
Stand Membership
Stand Location
```

subject to geographic reachability and the normal candidate constraints.

---

# 74. Smart Dispatch Discovery Behaviour

When the effective strategy is:

```text
Smart Dispatch
```

discovery is stand-agnostic.

The geographic candidate search should consider eligible nearby supply without introducing an auto-stand preference.

Conceptually:

```text
Pickup
 ↓
Nearby Geographic Search
 ↓
Eligible Candidate Processing
```

A driver being at an auto stand does not by itself make that driver more preferred under Smart Dispatch.

---

# 75. Cross-Location Discovery

Candidate discovery may expand beyond the ride's originating location.

Example:

```text
Location A
Smart Dispatch
    ↓
No suitable local supply
    ↓
Expand geographically
    ↓
Location B
Smart Stand Dispatch
    ↓
Discover eligible drivers from B
```

The candidate from Location B remains a valid candidate if the driver satisfies the applicable eligibility, geographic, legal, and service constraints.

The fact that Location B uses Smart Stand Dispatch does not automatically mean:

```text
Only Location B stand drivers
```

or:

```text
Reject Location B non-stand drivers
```

The local strategy context should be preserved so downstream dispatch logic can apply the appropriate prioritization rules.

---

# 76. Cross-Location Context Preservation

When a candidate comes from another location, discovery should preserve sufficient context to allow downstream processing to understand the candidate's origin.

Useful context includes:

```text
CandidateLocation
CandidateLocationDispatchStrategy
StandMembership
RelevantStand
QueuePosition
DiscoverySource
SearchExpansionLevel
Distance / Approximate Distance
```

The exact data model belongs to the candidate contract.

The discovery layer should not convert this metadata into final ranking scores.

---

# 77. Strategy Context vs Geographic Scope

These concepts must remain separate:

```text
Dispatch Strategy
    ↓
How candidates are prioritized
```

versus:

```text
Geographic Search Scope
    ↓
Where candidates are discovered
```

Therefore:

```text
Smart Stand Dispatch
≠
Search only inside stand

Smart Dispatch
≠
Search only inside originating location
```

The search scope is controlled by geographic/discovery policy and applicable business constraints.

---

# 78. Stand Radius vs Search Radius

The following are separate concepts:

```text
Stand Radius
    ↓
Determines whether a pickup is associated with a preferred stand context

Driver Search Radius
    ↓
Determines the geographic area searched for driver candidates

Location Expansion Radius
    ↓
Determines how far discovery may expand into nearby locations
```

They must not be represented by one overloaded radius value unless the product configuration explicitly requires that.

In particular:

```text
Pickup inside Stand Radius
        ≠
Search only inside Stand Radius
```

---

# 79. Discovery Must Preserve Strategy Semantics

Discovery expansion must not silently mutate the effective dispatch strategy.

Example:

```text
Resolved Strategy:
Smart Stand Dispatch

Preferred stand has no suitable driver
        ↓
Broader candidate discovery
        ↓
Still Smart Stand Dispatch
```

Broader discovery is a candidate-generation operation.

Changing the effective strategy is a separate business/configuration decision and must be explicit.

---

# 80. Hierarchical Configuration Boundary

The dispatch configuration hierarchy may contain:

```text
State
 ↓
District
 ↓
Town / City
 ↓
Rural Area
 ↓
Auto Stand
 ↓
Ride-level
```

and may contain additional intermediate levels.

The discovery component must not hard-code this hierarchy.

The resolution rule is:

```text
Most Specific Applicable Level
        ↓
Explicit Dispatch Strategy?
 ├── YES → Effective Strategy
 └── NO  → Parent Level
                 ↓
              Continue
                 ↓
          System Default
```

This resolution occurs before strategy-aware discovery.

Therefore discovery consumes:

```text
EffectiveDispatchStrategy
```

rather than implementing:

```text
FindDispatchStrategy()
```

---

# 81. Candidate Discovery and Eligibility

Discovery remains responsible for geographic relevance.

The following are not discovery decisions:

```text
Driver Availability
Driver Eligibility
Legal Eligibility
Vehicle Eligibility
Driver Quality
Acceptance Probability
ETA Ranking
Final Matching
```

However, discovery must not use its geographic context to incorrectly preclude candidates that are valid under the resolved strategy.

For example:

```text
Candidate is outside preferred stand
```

does not necessarily mean:

```text
Candidate is ineligible
```

---

# 82. Discovery Contract for Strategy-Aware Systems

A strategy-aware discovery request should conceptually contain:

```text
RideID
PickupCoordinates
EffectiveDispatchStrategy
OriginLocation
PreferredStandContext (optional)
SearchRadius
CandidateLimit
Attempt
ExpansionPolicy
```

A discovery result may contain:

```text
DriverID
CandidateLocation
StandContext
QueueContext
DiscoverySource
SpatialContext
```

The exact implementation contract may differ, but the semantic distinction should remain.

---

# 83. Final Discovery Responsibility

The Discovery Components are responsible for:

```text
1. Finding geographically relevant drivers.
2. Applying bounded geographic search policies.
3. Supporting preferred-stand-first discovery where required.
4. Expanding discovery when the configured strategy/search policy requires it.
5. Supporting cross-location candidate discovery.
6. Preserving candidate source/context.
7. Avoiding duplicate candidate identities.
8. Returning candidates efficiently.
```

They are not responsible for:

```text
1. Resolving hierarchical dispatch configuration.
2. Performing final eligibility decisions.
3. Performing final ranking.
4. Reserving drivers.
5. Creating offers.
6. Assigning rides.
7. Changing the effective dispatch strategy.
```

# 85. AI Agent Final Guardrail

When modifying discovery for dispatch strategy changes, an AI agent must preserve the following invariants:

```text
1. Smart Stand Dispatch is stand-preferred, not stand-exclusive.

2. Smart Dispatch is stand-agnostic.

3. Being outside a preferred stand does not automatically make a driver ineligible.

4. Being in another nearby location does not automatically make a driver ineligible.

5. Cross-location discovery is allowed when the search/dispatch policy expands geographically.

6. The candidate's source location and strategy context should be preserved where required.

7. Hierarchical configuration resolution happens before discovery.

8. The nearest explicit configuration wins.

9. Discovery must not hard-code configuration hierarchy levels.

10. Discovery strategy (H3/Geo) is independent from dispatch strategy
    (Smart Stand/Smart Dispatch).

11. Broader discovery does not silently change the resolved dispatch strategy.

12. Discovery generates candidates; downstream components determine
    eligibility, prioritization, ranking, reservation, and assignment.
```

# 86. Updated Dispatch Model Status

The Discovery Components are aligned with the current RideForge dispatch model:

```text
Smart Stand Dispatch
    = Stand-preferred, not stand-exclusive

Smart Dispatch
    = Stand-agnostic

Hierarchical Configuration
    = Most-specific explicit configuration wins

Cross-Location Dispatch
    = Nearby locations may contribute candidates

Discovery
    = Geographic candidate generation, not strategy resolution
```

This section supersedes any earlier interpretation that treated a stand as an exclusive candidate boundary.
