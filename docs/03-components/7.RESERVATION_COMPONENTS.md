# RideForge — Reservation Components

> **Document:** `docs/03-components/7.RESERVATION_COMPONENTS.md`  
> **Status:** Active  
> **Scope:** Component-level documentation for driver reservation, ownership, concurrency protection, and reservation lifecycle  
> **Related:** `docs/01-business/4.MATCHING_RULES.md`, `docs/01-business/5.RETRY_POLICY.md`, `docs/02-architecture/10.RESERVATION_ARCHITECTURE.md`, `docs/03-components/1.DISPATCH_ENGINE.md`, `docs/03-components/3.CANDIDATE_PIPELINE_COMPONENTS.md`, `docs/03-components/6.REALTIME_COMPONENTS.md`

# 1. Purpose

The Reservation Components protect the critical transition between:

```text
Candidate
    ↓
Selected
    ↓
Reserved
    ↓
Offer
```

Reservation answers:

> **Can this driver be atomically claimed for this dispatch attempt?**

The reservation layer exists because candidate discovery, realtime state, and ranking are all observations that can become stale between lookup and assignment.

Reservation is the concurrency boundary that protects driver ownership.

---

# 2. Reservation Boundary

The reservation subsystem owns:

```text
Driver Reservation
Reservation Ownership
Reservation TTL
Reservation Release
Reservation Conflict Detection
Reservation Idempotency
Concurrency Protection
```

It does not own:

```text
Candidate Discovery
Ranking
Offer Delivery
Ride Assignment
Driver Profile
Driver Location
Payment
```

---

# 3. Why Reservation Exists

A driver can be selected by multiple concurrent dispatch operations.

Example:

```text
Ride A ──→ Driver X
Ride B ──→ Driver X
```

Both operations may observe:

```text
Driver X = Available
```

at approximately the same time.

Without an atomic ownership mechanism:

```text
Ride A → Driver X
Ride B → Driver X
```

could both proceed.

Reservation prevents this.

---

# 4. Reservation as Final Ownership Gate

The dispatch flow is:

```text
Discovery
   ↓
Filtering
   ↓
Ranking
   ↓
Candidate Selection
   ↓
Reservation
   ↓
Offer
```

Passing every earlier stage does not guarantee reservation success.

Reservation is the final concurrency gate before an offer can safely proceed.

---

# 5. Observation vs Ownership

The architecture intentionally distinguishes:

```text
Realtime State
    = Observation

Candidate Ranking
    = Preference

Reservation
    = Temporary Ownership
```

This distinction is fundamental.

A cache saying:

```text
available = true
```

does not grant ownership.

A high ranking score does not grant ownership.

Only successful reservation grants the dispatch attempt temporary ownership.

---

# 6. Reservation Contract

The reservation abstraction should expose the smallest operation required by dispatch orchestration.

Conceptually:

```text
Reserve(driverID, rideID, ...)
        ↓
Reservation Result
```

and corresponding release/expiration behaviour.

The exact interface in code is authoritative.

---

# 7. Reservation Identity

A reservation should identify at least the ownership relationship:

```text
Driver
   +
Ride / Dispatch Attempt
```

Where the implementation requires it, a reservation identifier/token should distinguish one reservation operation from another.

---

# 8. Reservation Token

If the current implementation exposes a reservation token, that token represents the authority to modify or release the corresponding reservation.

Conceptually:

```text
Reserve
   ↓
Reservation Token
   ↓
Release / Confirm / Validate
```

A stale operation must not be allowed to release or mutate a newer reservation.

---

# 9. Atomic Reservation

Reservation must be atomic from the perspective of competing dispatch operations.

Desired behaviour:

```text
Driver X
   ↓
Reserve
   ↓
Success
```

while a concurrent operation receives:

```text
Reserve Driver X
   ↓
Conflict
```

rather than both operations succeeding.

---

# 10. Redis Driver Locker

The current architecture includes a Redis-backed driver locker.

Conceptually:

```text
MatchingEngine
      ↓
Driver Locker
      ↓
Redis
      ↓
Atomic Driver Ownership
```

The locker provides a fast distributed reservation mechanism suitable for the dispatch hot path.

---

# 11. Locker Abstraction

The Dispatch Engine should depend on the locker abstraction rather than directly using Redis locking commands.

This keeps:

```text
Dispatch Logic
```

separate from:

```text
Redis Lock Implementation
```

---

# 12. Lock TTL

Reservation/lock TTL must be configuration-driven.

The system should not embed values such as:

```text
15 seconds
30 seconds
60 seconds
```

inside the locker implementation unless they are mathematical/algorithmic constants rather than policy.

Operational timing belongs in configuration.

---

# 13. Why Reservation Has a TTL

A reservation can become abandoned because of:

```text
Process Crash
Network Failure
Driver Disconnect
Offer Delivery Failure
Dispatch Timeout
```

A TTL prevents permanent ownership caused by an incomplete operation.

Conceptually:

```text
Reservation
    ↓
TTL
    ↓
Expiration
    ↓
Driver Can Be Considered Again
```

---

# 14. Reservation Expiration

Expiration must be safe under concurrency.

An expired reservation should not accidentally remove a newer reservation created for the same driver.

The implementation must use ownership identity/token checks where required.

---

# 15. Stale Release Protection

A critical race is:

```text
Reservation A
    ↓
Expires

Reservation B
    ↓
Acquires Driver

Reservation A cleanup
    ↓
Must NOT release Reservation B
```

Any release mechanism must verify that the reservation being released still belongs to the caller.

---

# 16. Reservation Success

Successful reservation means:

```text
This dispatch operation currently owns the driver.
```

It does not necessarily mean:

```text
Driver accepted ride
```

Acceptance happens later through the offer/driver-response flow.

---

# 17. Reservation Failure

Reservation failure normally means another operation already owns the driver or the driver is no longer reservable.

Conceptually:

```text
Ranked Candidate
      ↓
Reserve
      ↓
Conflict
      ↓
Try Next Candidate
```

The dispatch engine owns this orchestration decision.

---

# 18. Reservation Conflict Is Not Infrastructure Failure

The system must distinguish:

```text
Reservation Conflict
```

from:

```text
Redis / Lock Infrastructure Failure
```

A conflict is an expected concurrent-dispatch outcome.

An infrastructure failure requires operational error handling.

---

# 19. Reservation and Ranking

Ranking determines preference:

```text
Driver A = Rank 1
Driver B = Rank 2
Driver C = Rank 3
```

Reservation determines ownership:

```text
Reserve A
   ↓
Conflict

Reserve B
   ↓
Success
```

Ranking must not assume that its top candidate is still available.

---

# 20. Reservation and Availability

Availability filtering happens before reservation:

```text
Availability Filter
      ↓
Ranked Candidate
      ↓
Reservation
```

The availability result can become stale.

Reservation is therefore still required.

---

# 21. Reservation and Discovery

Discovery only identifies geographically relevant drivers.

It does not reserve them.

```text
H3
 ↓
Driver IDs
 ↓
Pipeline
 ↓
Ranking
 ↓
Reservation
```

This separation prevents geographic lookup from acquiring driver ownership unnecessarily.

---

# 22. Reservation and Realtime

Realtime state is used to reduce obviously invalid candidates.

For example:

```text
Driver Offline
   ↓
Reject Before Ranking
```

But realtime state is not a concurrency guarantee.

The final ownership decision remains reservation.

---

# 23. Reservation and Offer

The intended ordering is:

```text
Reservation
     ↓
Offer Creation / Delivery
```

An offer should not be sent to a driver that the dispatch operation failed to reserve.

---

# 24. Reservation and Driver Acceptance

Reservation does not equal acceptance.

The complete flow is:

```text
Reserve Driver
      ↓
Send Offer
      ↓
Driver Accepts / Rejects / Times Out
      ↓
Confirm or Release Ownership
```

The response/offer lifecycle determines what happens next.

---

# 25. Reservation Lifecycle

The lifecycle can be represented as:

```text
Candidate
   ↓
Reservation Requested
   ↓
Reserved
   ├── Offer Accepted
   │       ↓
   │    Ownership Confirmed / Assignment
   │
   ├── Offer Rejected
   │       ↓
   │    Release
   │
   ├── Offer Timeout
   │       ↓
   │    Release
   │
   └── Reservation Expired
           ↓
        Available Again
```

The exact terminal state is controlled by the current ride/offer contracts.

---

# 26. Release

Release removes temporary ownership when the reservation is no longer needed.

Typical reasons:

```text
Driver Rejected
Offer Timed Out
Dispatch Cancelled
Ride Cancelled
Reservation Failure Recovery
```

Release must be idempotent.

---

# 27. Idempotent Release

Calling release more than once should not corrupt state.

For example:

```text
Release
Release
```

should result in the same safe final state as:

```text
Release
```

provided the reservation still belongs to the operation.

---

# 28. Reservation Confirmation

If the architecture includes explicit reservation confirmation, confirmation transitions temporary ownership into the next application-level ownership state.

Conceptually:

```text
Temporary Reservation
      ↓
Driver Acceptance
      ↓
Confirm
      ↓
Assignment / Ride Ownership
```

The reservation component should not independently create the durable assignment unless that is explicitly part of its contract.

---

# 29. Reservation Timeout

Reservation timeout and offer timeout are related but distinct concepts.

```text
Reservation TTL
    → protects ownership

Offer Timeout
    → controls driver response window
```

They should not automatically be treated as the same configuration value.

---

# 30. Dispatch Attempt

A dispatch attempt may reserve one candidate at a time or use a configured batch strategy.

The reservation component only handles the ownership operation requested by dispatch orchestration.

It should not independently decide batch size.

---

# 31. Adaptive Batch Reservation

If future dispatch policy offers multiple candidates concurrently:

```text
Candidate A
Candidate B
Candidate C
      ↓
Reservation
```

each reservation must still obey the same ownership guarantees.

The optimizer decides batch size; the reservation layer protects individual driver ownership.

---

# 32. Concurrent Dispatch

Multiple dispatch workers/nodes may compete for the same driver.

The reservation implementation must remain correct across:

```text
Same process
Multiple goroutines
Multiple application instances
Multiple dispatch nodes
```

This is why a local in-memory mutex alone is insufficient for distributed dispatch.

---

# 33. Local vs Distributed Locking

A local mutex protects only:

```text
One process
```

A Redis-backed locker can coordinate:

```text
Multiple processes
Multiple nodes
```

The current architecture uses Redis for the distributed hot-path ownership mechanism.

---

# 34. Lock Scope

The reservation lock should be held only for the ownership operation that requires it.

Avoid holding distributed locks while performing:

```text
Slow External API Calls
Long Database Transactions
Driver Network Communication
Unbounded Processing
```

The lock should remain short-lived.

---

# 35. No Lock Around Entire Dispatch

Do not implement:

```text
Acquire Driver Lock
   ↓
Discovery
   ↓
Ranking
   ↓
Network
   ↓
Offer
   ↓
Release
```

This creates excessive lock duration and contention.

The correct approach is:

```text
Discovery
   ↓
Ranking
   ↓
Acquire / Reserve
   ↓
Short Ownership Transition
   ↓
Offer
```

---

# 36. Reservation Key Ownership

Reservation keys should have clear ownership within the reservation component.

Other components should use the reservation abstraction rather than constructing lock keys themselves.

This prevents key-format coupling.

---

# 37. Reservation Key Design

Reservation keys should uniquely identify the protected driver ownership resource.

Conceptually:

```text
reservation:{driverID}
```

The exact key format is an implementation detail and must remain centralized.

---

# 38. Reservation State

The reservation value should contain enough ownership information to safely validate release/expiration.

Depending on the current implementation, this may include:

```text
Reservation Token
Ride ID
Dispatch Attempt
Expiration
```

Do not store an entire driver or ride object in the lock value.

---

# 39. Reservation Data Size

Reservation state is hot-path operational state.

Keep it compact.

Preferred:

```text
Small Token / Ownership Record
```

rather than:

```text
Serialized Domain Aggregate
```

---

# 40. Reservation Failure Handling

If the lock backend fails:

```text
Reserve
   ↓
Infrastructure Error
```

the dispatch operation should not assume the driver was successfully reserved.

Failing closed is safer than pretending ownership succeeded.

---

# 41. Never Assume Lock Success

An AI agent must never implement:

```go
if err != nil {
    // continue anyway
}
```

for reservation acquisition.

The system must have a confirmed ownership result before proceeding to offer.

---

# 42. Reservation Result

The reservation result should clearly distinguish:

```text
Acquired
Not Acquired / Conflict
Error
```

Do not represent all three cases with a simple boolean if that would lose operational error information.

---

# 43. Reservation Observability

Useful metrics include:

```text
Reservation Attempts
Reservation Successes
Reservation Conflicts
Reservation Errors
Reservation Releases
Reservation Expirations
Reservation Latency
```

These metrics are valuable for understanding dispatch contention.

---

# 44. Reservation Tracing

Useful tracing fields include:

```text
Driver ID
Ride ID
Reservation Attempt
Acquisition Result
Reservation Duration
Release Result
```

Sensitive/high-cardinality data should follow the project's observability policy.

---

# 45. Logging

Reservation logs should focus on exceptional or operationally meaningful events.

Good candidates:

```text
Reservation Conflict
Reservation Infrastructure Error
Unexpected Release Failure
Ownership Mismatch
```

Successful reservation should generally be captured through metrics/tracing rather than noisy logs for every dispatch.

---

# 46. Reservation Metrics Interpretation

A high conflict rate can indicate:

```text
High Dispatch Concurrency
Overlapping Candidate Searches
Insufficient Candidate Diversity
Hot Driver Regions
Stale Availability State
```

It should not automatically be interpreted as a Redis problem.

---

# 47. Testing Atomic Reservation

The reservation implementation must test concurrent acquisition.

Example:

```text
Goroutine A ──┐
              ├── Reserve Driver X
Goroutine B ──┘

Expected:
Exactly one succeeds.
```

This is more important than only testing sequential lock behaviour.

---

# 48. Testing TTL

Tests should verify:

```text
Reservation Created
      ↓
Still Owned Before TTL
      ↓
Expires After TTL
```

and:

```text
Reservation A Expires
Reservation B Acquires
A Cleanup
      ↓
B Remains Owned
```

---

# 49. Testing Release

Test:

```text
Successful Release
Repeated Release
Release After Expiry
Release With Wrong Token
Release After New Owner Acquired
```

A stale release must never remove another owner's reservation.

---

# 50. Testing Infrastructure Failure

Test:

```text
Redis Unavailable
Timeout
Malformed Result
Connection Error
```

The reservation component must return an explicit infrastructure error rather than claiming success.

---

# 51. Integration Testing

A useful integration flow is:

```text
Candidate
   ↓
Reservation
   ↓
Offer
   ↓
Response
   ↓
Release / Confirm
```

The test should verify that ownership remains protected across the complete lifecycle.

---

# 52. Reservation and Retry

The Dispatch Engine decides whether a reservation conflict should cause:

```text
Try Next Ranked Candidate
```

or:

```text
Start Another Dispatch Attempt
```

The reservation component should simply report the conflict accurately.

---

# 53. Reservation and Retry Safety

A failed reservation must not increment unrelated retry state internally.

Retry accounting belongs to the dispatch/retry policy.

This keeps:

```text
Reservation
```

and:

```text
Dispatch Policy
```

independently testable.

---

# 54. Reservation and Ride Cancellation

If the ride becomes cancelled while a reservation is active, the owning dispatch flow must release the reservation according to the ride lifecycle contract.

The reservation component should support safe release but should not independently become the ride lifecycle manager.

---

# 55. Reservation and Driver Disconnect

A driver may disconnect after reservation but before accepting an offer.

The system should handle this through:

```text
Realtime State
+
Offer/Dispatch Timeout
+
Reservation Release
```

The reservation component itself should not continuously monitor connection state.

---

# 56. Reservation and Process Crash

If the process holding a reservation crashes:

```text
Process Crash
   ↓
Reservation Remains Temporarily
   ↓
TTL Expires
   ↓
Driver Becomes Reservable
```

This is one of the primary reasons for the reservation TTL.

---

# 57. Reservation and Network Partition

If the application cannot confirm reservation ownership because the lock backend is unavailable, it must not assume ownership.

The safe behaviour is:

```text
Uncertain Ownership
      ↓
Do Not Send Offer
```

unless a higher-level protocol explicitly provides a stronger guarantee.

---

# 58. Reservation Correctness Priority

Reservation correctness is more important than maximizing dispatch throughput.

Preferred:

```text
False Negative
Driver not reserved
```

over:

```text
False Positive
Two rides believe they own the same driver
```

The latter can cause serious business correctness failures.

---

# 59. Performance Requirements

Reservation is part of the dispatch hot path.

The implementation should optimize:

```text
Single Redis Round Trip Where Possible
Small Lock Payload
Short Lock Duration
No Unnecessary Retries
No Database Calls During Lock Acquisition
```

---

# 60. Avoid Lock Contention

Do not use one global dispatch lock.

Bad:

```text
dispatch:global
```

Preferred:

```text
driver-specific ownership
```

This allows unrelated drivers to be reserved concurrently.

---

# 61. Driver-Scoped Ownership

Reservation should be scoped to the driver resource.

Conceptually:

```text
Driver A → independent reservation
Driver B → independent reservation
Driver C → independent reservation
```

This maximizes concurrency while protecting the actual resource.

---

# 62. Reservation and Multi-Node Dispatch

When multiple dispatch nodes operate simultaneously:

```text
Node A
   ↓
Reserve Driver X

Node B
   ↓
Reserve Driver X
   ↓
Conflict
```

The shared reservation backend provides the cross-node ownership guarantee.

---

# 63. Future Cell Ownership

Future multi-node cell ownership may reduce cross-node candidate contention.

However, cell ownership does not eliminate the need for driver-level reservation.

A driver can still be involved in concurrent operations across:

```text
Cell
Region
Retry
Recovery
```

The final driver ownership gate remains reservation.

# 65. AI Agent Forbidden Patterns

An AI agent must not:

- replace distributed reservation with an in-memory mutex,
- use a global dispatch lock,
- hold a driver lock throughout the complete dispatch flow,
- send an offer before confirmed reservation,
- ignore reservation acquisition errors,
- treat reservation conflict as infrastructure failure,
- release a reservation without ownership validation,
- use hard-coded reservation TTLs,
- store complete domain objects inside reservation keys,
- make the reservation component responsible for retry policy,
- make the reservation component responsible for driver acceptance,
- make reservation dependent on ranking internals,
- bypass the existing `DriverLocker` abstraction without an architectural reason,
- introduce a second locking mechanism for the same driver resource,
- assume a successful cache lookup is equivalent to reservation,
- assume offer delivery equals driver ownership.

```text
                 Candidate Pipeline
                        │
                        ▼
                    Ranking
                        │
                        ▼
                Candidate Selection
                        │
                        ▼
                 Driver Locker
                        │
              ┌─────────┴─────────┐
              │                   │
           Conflict             Success
              │                   │
              ▼                   ▼
        Next Candidate       Reservation
                                  │
                                  ▼
                              Offer
                                  │
                     ┌────────────┼────────────┐
                     │            │            │
                  Accept       Reject       Timeout
                     │            │            │
                     ▼            ▼            ▼
                 Confirm       Release      Release
```

# 67. Component Responsibility Matrix

| Component | Responsibility | Must Not Own |
|---|---|---|
| Driver Locker | Atomic driver ownership | Ranking |
| Reservation Policy | Reservation timing/behaviour where required | Driver state |
| Reservation Token | Ownership identity | Ride aggregate |
| Dispatch Engine | Reservation orchestration | Redis implementation |
| Offer System | Driver offer lifecycle | Lock implementation |
| Realtime System | Driver connection/state | Reservation ownership |
| Retry Policy | Next-attempt decision | Lock acquisition |
| Assignment | Durable ride/driver ownership | Temporary lock mechanics |

# 68. Current Status

RideForge already has the core reservation building block:

```text
DriverLocker
```

with a Redis-backed implementation integrated into the Dispatch/Matching Engine.

The current architecture therefore already establishes the essential ownership boundary:

```text
Candidate
   ↓
Ranking
   ↓
Driver Locker
   ↓
Offer
```

Further work should strengthen correctness, observability, and lifecycle handling rather than introduce another reservation mechanism.

---

# 69. Future Reservation Evolution

Future improvements may include:

```text
Reservation Metrics
Reservation Tokens
Explicit Ownership Confirmation
Stronger Stale-Owner Protection
Reservation Lifecycle Events
Multi-node Dispatch Optimizations
```

These should be introduced only where the current contract requires them.

---

# 70. Final Component Rule

When an AI agent is asked to modify reservation behaviour, determine first:

```text
Is the change about:
    │
    ├── Acquiring driver ownership?
    │       → Driver Locker
    │
    ├── Ownership expiry?
    │       → Reservation TTL
    │
    ├── Safe release?
    │       → Reservation ownership/token
    │
    ├── Choosing another candidate?
    │       → Dispatch / Retry Policy
    │
    ├── Sending an offer?
    │       → Offer / Realtime Components
    │
    └── Permanent ride ownership?
            → Assignment / Ride Lifecycle
```

The Reservation Components should remain responsible for **short-lived, atomic, driver-scoped ownership protection that prevents concurrent dispatch operations from claiming the same driver**.
