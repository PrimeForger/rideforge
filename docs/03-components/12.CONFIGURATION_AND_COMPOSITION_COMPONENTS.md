# RideForge — Configuration and Composition Components

> **Document:** `docs/03-components/12.CONFIGURATION_AND_COMPOSITION_COMPONENTS.md`  
> **Status:** Active  
> **Scope:** Component-level documentation for configuration, dependency construction, application composition, runtime wiring, lifecycle management, and bootstrap boundaries

# 1. Purpose

The Configuration and Composition Components define how RideForge is assembled at runtime.

They answer:

```text
Where does configuration come from?
```

```text
Where are dependencies constructed?
```

```text
Who owns dependency wiring?
```

```text
How does the application start and stop?
```

The objective is to keep runtime construction explicit while preventing business components from becoming responsible for infrastructure creation.

---

# 2. Composition Boundary

Composition components own:

```text
Configuration Loading
Configuration Validation
Dependency Construction
Dependency Injection
Application Wiring
Server Construction
Background Worker Wiring
Lifecycle Coordination
Graceful Shutdown
```

They do not own:

```text
Ride Business Rules
Matching Policy
Ranking Policy
Retry Decisions
Reservation Decisions
Driver Selection
Offer Decisions
```

---

# 3. Composition Root

The application composition root is the place where concrete implementations are assembled.

Conceptually:

```text
Configuration
     ↓
Infrastructure
     ↓
Repositories
     ↓
Services
     ↓
Application Components
     ↓
HTTP / Realtime / Workers
```

The composition root should be the primary location where interfaces are connected to implementations.

---

# 4. Dependency Direction

The intended direction is:

```text
cmd / bootstrap
        ↓
application
        ↓
domain / contracts
        ↑
infrastructure implementations
```

Infrastructure implementations satisfy application-facing interfaces.

Application services should not construct infrastructure dependencies themselves.

---

# 5. Why Explicit Composition

Explicit composition makes the system:

```text
Testable
Replaceable
Understandable
Predictable
```

For example:

```text
MatchingEngine
      ↓
CandidateSearcher Interface
      ↓
Concrete Discovery Implementation
```

The Matching Engine does not need to know how the searcher is constructed.

---

# 6. Configuration as Policy Input

Configuration should contain operational policy and infrastructure settings.

Examples:

```text
Database
Redis
Messaging
HTTP
Realtime
Dispatch
Discovery
Ranking
Reservation
Timeouts
Observability
```

Business algorithms should consume configuration through explicit dependencies.

---

# 7. Configuration Must Not Be Hidden

Avoid:

```go
func NewRanker() *Ranker {
    return &Ranker{
        timeout: 15 * time.Second,
    }
}
```

when the value represents runtime policy.

Prefer:

```text
Configuration
     ↓
Builder / Constructor
     ↓
Component
```

This keeps policy visible and changeable.

---

# 8. No Hard-Coded Operational Policy

Operational values should not be buried inside business components.

Examples include:

```text
Reservation TTL
Offer Timeout
Retry Limits
Search Limits
Ranking Weights
Connection Pool Limits
Consumer Retry Limits
```

These should be configuration-driven where they represent deployable policy.

Mathematical constants and implementation-level invariants may remain in code when they are genuinely not operational policy.

---

# 9. Configuration Ownership

Each configuration section should have a clear owner.

Conceptually:

```text
DatabaseConfig
RedisConfig
KafkaConfig
DispatchConfig
DiscoveryConfig
RankingConfig
ReservationConfig
RealtimeConfig
ObservabilityConfig
```

The exact configuration structure in the repository is authoritative.

Do not create a second configuration model for the same subsystem.

---

# 10. Configuration Loading

The configuration loader should:

```text
Load Environment / Config Sources
        ↓
Parse
        ↓
Apply Defaults where explicitly defined
        ↓
Validate
        ↓
Return Typed Configuration
```

Invalid configuration should fail startup rather than producing partially valid runtime behaviour.

---

# 11. Configuration Validation

Validate configuration before constructing dependent components.

Examples:

```text
Required DSN exists
Redis address valid
Messaging broker configured
Timeouts are positive
Weights are valid
Pool limits are sensible
Required topic names exist
```

The exact validation rules belong to each configuration section.

---

# 12. Fail Fast

If a required dependency cannot be configured:

```text
Application Startup
      ↓
Configuration Validation
      ↓
Failure
      ↓
Process Does Not Start
```

Do not start a partially initialized dispatch system.

---

# 13. Environment Separation

Environment-specific values should be supplied through configuration.

Examples:

```text
Development
Testing
Staging
Production
```

Business code should not contain:

```text
if production
if staging
if development
```

merely to select operational endpoints.

---

# 14. Secrets

Secrets must come from secure configuration mechanisms.

Examples:

```text
Database Password
Redis Credentials
Broker Credentials
API Keys
Authentication Secrets
```

They must not be committed to source code.

They should not appear in:

```text
Logs
Metrics
Traces
Error Messages
```

---

# 15. Configuration Immutability

Once startup construction has completed, configuration should generally be treated as immutable.

Runtime components should receive:

```text
Validated Configuration
```

rather than repeatedly reading environment variables.

---

# 16. Passing Configuration

Pass configuration through explicit constructors.

Preferred:

```text
NewComponent(cfg.Component)
```

Avoid hidden global configuration.

Bad:

```text
globalConfig.Get(...)
```

inside business components.

---

# 17. Configuration Granularity

Do not pass the entire application configuration to every component.

Prefer:

```text
RankingConfig
```

to:

```text
AppConfig
```

when the ranker only needs ranking settings.

This makes dependencies explicit.

---

# 18. Builder Responsibility

Builders should construct components.

For example:

```text
BuildRanker
BuildCandidateSearcher
BuildCandidatePipeline
BuildRealtimeHub
BuildMessaging
```

A builder should not execute business operations during construction.

---

# 19. Builder Simplicity

Builders should primarily perform:

```text
Dependency Construction
Dependency Wiring
Configuration Mapping
```

Avoid putting business algorithms into builders.

---

# 20. Interface Wiring

The composition root should connect:

```text
Interface
     ↓
Implementation
```

Examples:

```text
Ranker Interface
      ↓
Default Ranker

CandidateSearcher Interface
      ↓
Discovery Implementation

DriverLocker Interface
      ↓
Redis Driver Locker
```

---

# 21. Avoid Interface Duplication

Before introducing an interface:

```text
Search Repository
Search Existing Interfaces
```

If an existing contract already represents the required dependency, reuse it.

Do not create:

```text
DriverProvider
DriverReader
DriverLookupProvider
DriverDataProvider
```

for the same responsibility without a real architectural distinction.

---

# 22. Narrow Interfaces

Interfaces should represent the consumer's actual dependency.

For example:

```text
Candidate Pipeline
    → Candidate Data Source Interface
```

rather than:

```text
Candidate Pipeline
    → Entire Driver Cache API
```

This reduces coupling.

---

# 23. Dependency Injection

Dependencies should be injected through constructors.

Conceptually:

```text
NewMatchingEngine(
    repository,
    locker,
    outbox,
    searcher,
    pipeline,
    config,
    retryPolicy,
    logger,
)
```

The current constructor contract is authoritative.

---

# 24. Constructor Responsibility

Constructors should:

```text
Validate Required Dependencies
Store Dependencies
Create Small Internal State
```

They should not:

```text
Start Background Workers
Open Unbounded Loops
Perform Business Operations
```

unless the component contract explicitly requires startup behaviour.

---

# 25. Background Components

Long-lived components should have explicit lifecycle management.

Examples:

```text
Kafka Consumer
Outbox Publisher
Timeout Scheduler
Realtime Hub
Reconciliation Worker
```

Their lifecycle should be visible from the application composition.

---

# 26. Application Lifecycle

The runtime lifecycle is conceptually:

```text
Load Configuration
      ↓
Validate Configuration
      ↓
Construct Infrastructure
      ↓
Construct Repositories
      ↓
Construct Application Services
      ↓
Construct Transport
      ↓
Start Background Workers
      ↓
Start Servers
      ↓
Serve
      ↓
Shutdown
```

---

# 27. Startup Ordering

Dependencies should be initialized before consumers that require them.

For example:

```text
Database
Redis
Messaging
   ↓
Repositories / Infrastructure
   ↓
Application Services
   ↓
Consumers / Workers
   ↓
HTTP / Realtime Servers
```

The exact startup order should follow actual dependency requirements.

---

# 28. Background Worker Startup

Workers should start only after their dependencies are ready.

For example:

```text
Outbox Publisher
   ↓
Requires Database + Broker
```

Therefore both dependencies must be available before the worker begins processing.

---

# 29. Readiness and Startup

Application readiness should not be declared before required startup dependencies are initialized.

Conceptually:

```text
Initialize
   ↓
Validate
   ↓
Start Required Workers
   ↓
Ready
```

The exact readiness semantics are defined by runtime deployment configuration.

---

# 30. Graceful Shutdown

Shutdown should be coordinated.

Conceptually:

```text
Shutdown Signal
      ↓
Stop New Traffic
      ↓
Stop New Background Work
      ↓
Finish Bounded In-Flight Work
      ↓
Close Consumers
      ↓
Close Servers
      ↓
Close Redis / DB / Broker Resources
      ↓
Exit
```

The exact order depends on the runtime component dependencies.

---

# 31. Shutdown Timeout

Graceful shutdown should be bounded by configuration.

A process must not wait indefinitely for:

```text
Consumer
Realtime Connection
Network Operation
Background Worker
```

to terminate.

---

# 32. Context Propagation

Long-lived components should receive application context/cancellation where appropriate.

Conceptually:

```text
Root Context
      ↓
Worker Context
      ↓
Child Operations
```

Cancellation should propagate cleanly.

---

# 33. Resource Ownership

The component that creates a resource should normally be responsible for its lifecycle.

Example:

```text
Bootstrap creates Redis client
      ↓
Bootstrap closes Redis client
```

A repository using the client should not independently close the shared resource.

---

# 34. Shared Resource Rule

Shared resources should be constructed once at the appropriate application scope.

Examples:

```text
PostgreSQL Pool
Redis Client
Kafka Producer
Logger
Tracer
Metrics Registry
```

Avoid constructing one instance per request or per repository.

---

# 35. Database Construction

The composition layer should construct:

```text
PostgreSQL Connection Pool
```

and inject it into repositories.

Repositories should not read:

```text
DATABASE_URL
```

or construct their own pools.

---

# 36. Redis Construction

The composition layer should construct the shared Redis client.

Redis-backed components receive the client through their constructors.

This keeps:

```text
Connection Configuration
```

outside:

```text
Business Components
```

---

# 37. Messaging Construction

The composition layer should construct:

```text
Producer
Consumer
Publisher
```

according to the current event architecture.

Topic configuration should remain external to business logic.

---

# 38. Realtime Construction

The composition root should assemble:

```text
Realtime Hub
Driver Offer Gateway
Push Notifier
Realtime Handlers
```

The exact implementation depends on the current transport architecture.

---

# 39. Dispatch Construction

Dispatch construction should follow dependency order.

Conceptually:

```text
Infrastructure
      ↓
Driver Cache
      ↓
Geo / H3
      ↓
Discovery
      ↓
Ranking
      ↓
Candidate Pipeline
      ↓
Reservation
      ↓
Matching Engine
```

This keeps the dispatch graph explicit.

---

# 40. Ranking Construction

The ranking builder should explicitly construct the ranking pipeline.

Conceptually:

```text
Ranking Config
      ↓
Feature Extractor
      ↓
Scorer
      ↓
Ranker
```

Feature enrichers/providers must be injected explicitly.

A ranker should not create its own data providers internally.

---

# 41. Discovery Construction

Discovery construction should explicitly wire:

```text
H3 Service
H3 Index
Geo Service
Density Provider
Search Policy
Expansion Policy
Refinement
```

The exact current builder contract is authoritative.

---

# 42. Candidate Pipeline Construction

Candidate pipeline construction should explicitly wire:

```text
Candidate Source
Candidate Data Source
Filters
Ranker
Heap / Selection
```

The pipeline should not construct its own Redis client, ranker, or repository.

---

# 43. Reservation Construction

Reservation should receive:

```text
Driver Locker
Reservation Configuration
```

and any required application dependencies.

It should not create a Redis client independently.

---

# 44. Offer Construction

Offer components should receive:

```text
Driver Offer Gateway
Timeout Scheduler
Reservation / Dispatch Dependencies
Offer Configuration
Logger
```

The exact current constructor graph is authoritative.

---

# 45. Messaging Construction

Messaging should be assembled centrally.

Conceptually:

```text
Broker Config
      ↓
Producer
      ↓
Consumers
      ↓
Handlers
      ↓
Application Services
```

Consumer handlers should receive application dependencies rather than constructing repositories themselves.

---

# 46. Persistence Construction

Persistence construction should follow:

```text
Database Config
      ↓
Connection Pool
      ↓
Repositories
      ↓
Application Services
```

The same database pool should be shared by repositories where appropriate.

---

# 47. Observability Construction

Observability infrastructure should be initialized before components that emit telemetry.

Conceptually:

```text
Observability Config
      ↓
Logger
Metrics
Tracer
      ↓
Application Components
```

Telemetry initialization failure should follow the project's explicit startup policy.

---

# 48. Circular Dependencies

The composition graph must remain acyclic.

Bad:

```text
A → B
B → C
C → A
```

Circular dependencies should be resolved by:

```text
Narrower Interface
Application Service Boundary
Event Boundary
Responsibility Extraction
```

Do not solve circular dependencies with global variables.

---

# 49. Composition vs Business Logic

Composition answers:

```text
Which implementation should be used?
```

Business logic answers:

```text
What should happen?
```

These must remain separate.

---

# 50. Runtime Feature Selection

If multiple implementations are intentionally supported:

```text
Configuration
      ↓
Builder
      ↓
Selected Implementation
```

For example:

```text
Redis GEO
OSRM
Mapbox
Google
```

where the architecture supports multiple providers.

Business components should depend on the abstraction.

---

# 51. Avoid Runtime Branch Explosion

Do not scatter:

```text
if provider == X
if provider == Y
```

throughout application code.

Provider selection should happen near composition.

---

# 52. Test Composition

Composition should be testable without starting the entire production system when practical.

Useful tests include:

```text
Configuration Validation
Dependency Wiring
Required Dependency Presence
Provider Selection
Lifecycle Construction
```

---

# 53. Integration Startup Test

A useful integration test should verify:

```text
Configuration
   ↓
Composition Root
   ↓
All Required Components
```

can be constructed successfully with test infrastructure.

This catches broken constructor wiring early.

---

# 54. Configuration Tests

Configuration tests should cover:

```text
Valid Configuration
Missing Required Value
Invalid Duration
Invalid Weight
Invalid Connection Setting
Invalid Provider
```

The exact validation rules belong to each config section.

---

# 55. Shutdown Tests

Where practical, test that:

```text
Shutdown Signal
      ↓
Workers Stop
      ↓
Resources Close
```

without hanging indefinitely.

---

# 56. Dependency Replacement in Tests

Interfaces should allow tests to replace infrastructure with controlled implementations.

Examples:

```text
Fake Repository
Fake Locker
Fake Candidate Searcher
Fake Ranker
Fake Offer Gateway
Fake Event Publisher
```

Do not introduce mocks merely because a constructor exists; use them where isolation provides value.

---

# 57. AI Agent Implementation Rules

Before modifying configuration or composition components, an AI coding agent must:

1. Read this document.
2. Read the relevant architecture documents.
3. Inspect the current `cmd` and bootstrap/composition code.
4. Inspect the current configuration package.
5. Inspect all constructors involved in the requested change.
6. Search for existing interfaces before creating new ones.
7. Search for existing builders before creating new builders.
8. Trace the dependency graph before changing constructor signatures.
9. Keep operational values configuration-driven.
10. Keep infrastructure creation in the composition boundary.
11. Preserve shared-resource ownership.
12. Preserve graceful shutdown.
13. Run composition/integration tests after wiring changes.
14. Run the full relevant test suite before completion.

---

# 58. AI Agent Forbidden Patterns

An AI agent must not:

- create global mutable configuration,
- construct Redis/DB clients inside business services,
- construct repositories inside application methods,
- read environment variables throughout business code,
- hard-code operational policy,
- create duplicate builders for an existing component,
- create duplicate interfaces for the same responsibility,
- start background workers from arbitrary constructors,
- hide lifecycle ownership,
- close shared resources from leaf components,
- introduce circular dependencies,
- solve dependency cycles with globals,
- pass the entire application configuration everywhere,
- add provider-specific branches throughout the application,
- silently change startup/shutdown ordering,
- make configuration validation optional for required dependencies.

# 60. Component Responsibility Matrix

| Component | Responsibility | Must Not Own |
|---|---|---|
| Config Loader | Load configuration | Business decisions |
| Config Validator | Validate startup configuration | Runtime policy decisions |
| Builder | Construct component graph | Business workflows |
| Composition Root | Wire dependencies | Domain rules |
| Resource Manager | Own shared infrastructure lifecycle | Application decisions |
| Bootstrap | Start/stop application | Matching logic |
| Application Service | Execute business use case | Infrastructure construction |
| Repository | Persist/retrieve state | Policy |
| Worker Manager | Lifecycle of background workers | Business strategy |

The current runtime wiring includes components such as:

```text
Configuration

Redis
Messaging
Driver Cache
H3 / Geo
Discovery
Ranking
Candidate Pipeline
Driver Locker
```

The composition architecture therefore already has the essential production-grade boundary:

```text

        ↓
```

Future changes should preserve this explicit dependency graph instead of moving construction into business components.

# 63. Final Component Rule

When an AI agent is asked to modify configuration or composition behaviour, determine first:

```text
Is the change about:
    │
    ├── Loading a runtime value?
    │       → Configuration
    │
    ├── Validating a runtime value?
    │       → Configuration Validation
    │
    ├── Selecting an implementation?
    │       → Builder / Composition Root
    │
    ├── Constructing a dependency?
    │       → Composition Root
    │
    ├── Starting a long-lived component?
    │       → Application Lifecycle
    │
    ├── Closing a shared resource?
    │       → Resource Owner
    │
    └── Executing business behaviour?
            → Application / Domain Component
```

The Configuration and Composition Components should remain responsible for **turning validated runtime configuration into an explicit, correctly wired, testable application while keeping infrastructure construction and lifecycle management outside business logic**.
