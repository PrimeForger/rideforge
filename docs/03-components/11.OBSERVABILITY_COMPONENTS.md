# 1. Purpose

The Observability Components make RideForge's runtime behaviour measurable and diagnosable.

The objective is to answer:

```text
Is the system healthy?
```

```text
Where is latency coming from?
```

```text
Why did dispatch fail?
```

```text
Why was a particular driver selected?
```

```text
Where are candidates being lost?
```

```text
Is the system degrading in a particular region?
```

Observability must provide these answers without changing business behaviour.

---

# 2. Observability Boundary

Observability components own:

```text
Metrics
Tracing
Structured Logging
Request Correlation
Dispatch Instrumentation
Component Health Signals
Runtime Diagnostics
```

They do not own:

```text
Matching Decisions
Ranking Decisions
Retry Policy
Reservation Policy
Ride State
Driver State
Business Rules
```

Observability records what the system does.

It must not decide what the system should do.

---

# 3. Three Pillars

RideForge uses three primary observability signals:

```text
Metrics
   +
Logs
   +
Traces
```

They answer different questions.

```text
Metrics
    → What is happening?

Logs
    → What happened?

Traces
    → Where did it happen and how did the operation flow?
```

---

# 4. Metrics

Metrics provide aggregated runtime measurements.

Important categories include:

```text
Dispatch Metrics
Discovery Metrics
Candidate Metrics
Ranking Metrics
Reservation Metrics
Offer Metrics
Realtime Metrics
Persistence Metrics
Messaging Metrics
System Metrics
```

Metrics should remain low-cardinality.

---

# 5. Dispatch Metrics

The dispatch engine should expose measurements such as:

```text
dispatch_requests_total
dispatch_success_total
dispatch_failure_total
dispatch_duration
dispatch_attempts
dispatch_candidates_examined
dispatch_candidates_offered
```

The exact metric names used by the repository are authoritative.

Do not introduce duplicate metrics for an existing measurement.

---

# 6. Dispatch Latency

Dispatch latency should be decomposed.

Conceptually:

```text
Dispatch
   ├── Discovery
   ├── Filtering
   ├── Ranking
   ├── Reservation
   ├── Offer
   └── Response
```

This allows operators to identify the actual bottleneck rather than observing only total dispatch latency.

---

# 7. Discovery Metrics

Discovery should measure:

```text
Lookup Count
Lookup Latency
Rings Searched
Cells Searched
Drivers Returned
Drivers Examined
Empty Searches
Expansion Count
```

These measurements help identify geographic search inefficiency.

---

# 8. H3 Metrics

The H3 index should expose measurements such as:

```text
Cell Lookup Latency
Cells Queried
Drivers Per Cell
Cell Changes
Same-Cell Updates
Drivers Added
Drivers Removed
```

The exact H3 instrumentation is defined by the H3 component.

---

# 9. Ring Expansion Metrics

The discovery engine should measure:

```text
Average Ring
Maximum Ring
Ring 0 Success Rate
Ring 1 Success Rate
Ring 2 Success Rate
Searches Reaching Maximum Ring
```

This reveals whether search policy is too narrow or too aggressive.

---

# 10. Candidate Pipeline Metrics

The candidate pipeline should measure how candidates move through the pipeline.

Conceptually:

```text
Candidates Discovered
       ↓
Offline Filter
       ↓
Busy Filter
       ↓
Reserved Filter
       ↓
Already Offered Filter
       ↓
Blocked Filter
       ↓
ETA Filter
       ↓
Ranked
       ↓
Reserved
       ↓
Offered
```

Each stage should expose enough aggregate information to identify where candidates are being removed.

---

# 11. Filter Metrics

Useful measurements include:

```text
Candidates Rejected Offline
Candidates Rejected Busy
Candidates Rejected Reserved
Candidates Rejected Already Offered
Candidates Rejected Blocked
Candidates Rejected ETA
Candidates Scored
```

Avoid logging every candidate solely to obtain these counts.

Counters and histograms are preferred.

---

# 12. Ranking Metrics

Ranking should measure:

```text
Ranking Count
Ranking Latency
Candidates Ranked
Top Score
Score Distribution
Feature Extraction Latency
Scoring Latency
```

Where practical, score distributions should use histograms rather than high-cardinality labels.

---

# 13. Ranking Explainability

The system should provide enough tracing/diagnostic information to understand why a candidate received a score.

Conceptually:

```text
Candidate
   ├── ETA Feature
   ├── Quality Feature
   ├── Fairness Feature
   ├── Demand Feature
   └── Final Score
```

Do not put full feature vectors into high-volume logs by default.

Detailed ranking information belongs in traces or controlled debug instrumentation.

---

# 14. Quality Metrics

Driver-quality inputs should be measurable independently from the final ranking score.

Useful measurements include:

```text
Acceptance Rate Distribution
Cancellation Rate Distribution
Timeout Rate Distribution
Rating Distribution
Completed Trip Distribution
```

This helps detect data-quality problems in driver profiles.

---

# 15. Reservation Metrics

Reservation components should expose:

```text
Reservation Attempts
Reservation Successes
Reservation Conflicts
Reservation Errors
Reservation Releases
Reservation Expirations
Reservation Latency
```

A high conflict rate is a concurrency signal.

It should not automatically be treated as a Redis failure.

---

# 16. Offer Metrics

Offer components should measure:

```text
Offers Created
Offers Delivered
Delivery Failures
Offers Accepted
Offers Rejected
Offers Expired
Offer Response Latency
```

These measurements allow dispatch performance to be separated from driver response behaviour.

---

# 17. Driver Response Metrics

Driver response measurements should distinguish:

```text
Accepted
Rejected
Timed Out
Invalid
Duplicate
Late
```

These categories should not be collapsed into a single failure counter.

---

# 18. Acceptance Funnel

A useful operational funnel is:

```text
Candidates
    ↓
Reserved
    ↓
Offered
    ↓
Delivered
    ↓
Accepted
    ↓
Assigned
```

The ratio between each stage provides insight into dispatch effectiveness.

---

# 19. Messaging Metrics

The messaging layer should expose:

```text
Events Published
Publish Failures
Consumer Messages
Consumer Processing Latency
Consumer Failures
Retries
DLQ Messages
Outbox Pending Count
Outbox Publish Latency
```

Consumer lag should be monitored where supported by the messaging infrastructure.

# 20. Persistence Metrics

PostgreSQL instrumentation should expose:

```text
Query Latency
Transaction Latency
Connection Pool Utilization
Connection Wait Time
Query Errors
Transaction Errors
Timeouts
Deadlocks
```

Redis instrumentation should expose appropriate:

```text
Operation Latency
Errors

```

# 21. Realtime Metrics

Realtime components should measure:

```text
Active Connections
Connection Attempts
Connection Failures
Disconnects
Messages Sent
Message Delivery Failures
Message Processing Latency
```

These metrics should distinguish transport failures from business responses.

# 22. Geographic Heat Metrics

Hot-region analysis should measure per-cell aggregates such as:

```text
Drivers
Requests
Supply
Demand
Supply/Demand Ratio
Surge
Dispatch Failures
Average ETA
```

These values may be used by operational dashboards and future dispatch policy.

---

# 23. Cell Cardinality

H3 cell identifiers are potentially high-cardinality.

Do not automatically use:

```text
h3_cell
```

as a metric label for every metric.

Prefer:

```text
Aggregated Regions
Top-K Diagnostics
Logs
Traces
Dedicated Heatmap Data
```

for detailed geographic analysis.

---

# 24. Logs

Logs should be structured.

A production log should provide machine-readable fields rather than relying entirely on free-form messages.

Conceptually:

```json
{
  "level": "warn",
  "event": "reservation_conflict",
  "ride_id": "...",
  "driver_id": "...",
  "correlation_id": "..."
}
```

The actual logging library and field conventions in the repository are authoritative.

---

# 25. Structured Log Fields

Common fields include:

```text
timestamp
level
service
component
operation
event
correlation_id
trace_id
ride_id where appropriate
driver_id where appropriate
error
```

Sensitive data must not be logged merely because it is available.

---

# 26. Logging Levels

Use logging levels intentionally.

Typical meaning:

```text
DEBUG
    Detailed development/diagnostic information

INFO
    Important lifecycle/operational events

WARN
    Recoverable anomaly or degraded condition

ERROR
    Failed operation requiring attention
```

Normal high-frequency success paths should not produce excessive logs.

---

# 27. Error Logging

Errors should include useful context:

```text
Operation
Component
Error
Correlation ID
Relevant Entity ID
```

Avoid logging the same error at every architectural layer.

Prefer logging at the boundary where the error is handled or becomes operationally meaningful.

---

# 28. Tracing

Distributed tracing connects a dispatch operation across components.

Conceptually:

```text
Request
  ↓
MatchingEngine
  ↓
Discovery
  ↓
Candidate Pipeline
  ↓
Ranking
  ↓
Reservation
  ↓
Offer
  ↓
Driver Response
  ↓
Assignment
```

---

# 29. Trace Context

Trace context should propagate across:

```text
HTTP
Realtime
Application Services
Database
Redis
Messaging
```

where the instrumentation supports it.

Asynchronous event processing should preserve correlation/causation information.

---

# 30. Dispatch Trace

A dispatch trace should expose useful spans such as:

```text
dispatch
 ├── discovery
 │    ├── h3_lookup
 │    └── cache_fetch
 ├── filtering
 ├── ranking
 │    ├── feature_extraction
 │    └── scoring
 ├── reservation
 └── offer
```

The exact span hierarchy should follow actual component boundaries.

---

# 31. Discovery Trace Attributes

Useful attributes include:

```text
search_strategy
initial_ring
rings_searched
cells_searched
drivers_returned
drivers_examined
lookup_latency
```

Avoid attaching entire candidate lists to spans.

---

# 32. Ranking Trace Attributes

Useful attributes include:

```text

ranking_latency
top_score
feature_extraction_latency
scoring_latency
```

Detailed candidate features should be sampled or selectively recorded rather than emitted for every production request.

---

# 33. Reservation Trace Attributes

Useful attributes include:

```text
reservation_result
reservation_latency
attempt
```

The trace should make conflicts distinguishable from infrastructure failures.

---

# 34. Offer Trace Attributes

Useful attributes include:

```text
offer_id
driver_id
delivery_result
response_type
response_latency
expiration
```

Avoid recording sensitive trip information unless required.

---

# 35. Messaging Trace Attributes

Useful attributes include:

```text
event_id
event_type
topic
partition
consumer_group
attempt
correlation_id
causation_id
```

Broker metadata should be included where useful for diagnosing processing.

---

# 36. Sampling

Not every trace needs maximum detail.

Production tracing should balance:

```text
Diagnostic Value
+
Storage Cost
+
Runtime Overhead
```

Normal successful requests may be sampled.

Failures and unusual latency should receive stronger visibility where supported.

---

# 37. Error Trace Enrichment

When an operation fails, the active span should capture:

```text
Error Type
Error Message where safe
Failure Stage
Relevant Component
```

Do not duplicate sensitive payloads into tracing metadata.

---

# 38. Health Checks

Health endpoints should distinguish:

```text
Liveness
Readiness
Dependency Health
```

Liveness answers:

```text
Is the process alive?
```

Readiness answers:

```text
Can this instance safely receive traffic?
```

---

# 39. Liveness

Liveness should remain lightweight.

It should not perform expensive checks against every dependency.

A database outage should not necessarily make the process appear dead.

---

# 40. Readiness

Readiness may consider critical dependencies required for serving traffic.

For example:

```text
PostgreSQL
Redis
Messaging
```

depending on the service's actual responsibilities.

A dependency should be included only if the service genuinely cannot operate without it.

---

# 41. Dependency Health

Dependency health should be observable independently.

Conceptually:

```text
Service
 ├── PostgreSQL
 ├── Redis
 ├── Kafka/Redpanda
 └── Realtime Transport
```

This allows operators to distinguish:

```text
Application Failure
```

from:

```text
Dependency Failure
```

---

# 42. Health Check Anti-Patterns

Do not:

- perform expensive business operations in health checks,
- execute full dispatch in a health endpoint,
- make liveness depend on every external dependency,
- create database writes merely to prove health,
- use health checks as monitoring replacements.

---

# 43. Operational Alerts

Alerts should be based on symptoms that require action.

Examples:

```text
High Dispatch Latency
High Dispatch Failure Rate
High Reservation Conflict Rate
High Offer Delivery Failure
Consumer Lag
Growing Outbox Backlog
Growing DLQ
PostgreSQL Connection Exhaustion
Redis Failure Rate
```

Avoid alerting on every individual error.

---

# 44. Alert Threshold Ownership

Thresholds belong to operational configuration/monitoring policy.

They should not be hard-coded inside business components.

For example:

```text
High latency threshold
```

belongs to:

```text
Monitoring / Alerting Configuration
```

not:

```text
MatchingEngine
```

---

# 45. SLO-Oriented Metrics

The most important service-level signals should include:

```text
Dispatch Success Rate
Dispatch Latency

Assignment Success

```

These should eventually support measurable service objectives.

# 46. Dispatch Failure Taxonomy

For example:

```text
NO_CANDIDATES
NO_ELIGIBLE_CANDIDATES
```

# 47. Candidate Funnel Diagnostics

A failed dispatch should be diagnosable through aggregate counters/traces:

```text
100 candidates discovered
    ↓
20 offline
    ↓
15 busy
    ↓
10 reserved
    ↓
5 blocked
    ↓
30 rejected by ETA
    ↓
20 ranked
    ↓
3 reservation conflicts
    ↓
2 offers
    ↓
1 accepted
```

This is significantly more useful than:

```text
dispatch failed
```

alone.

---

# 48. No-Candidate Diagnostics

When no driver is available, observability should help distinguish:

```text
No drivers geographically nearby
```

from:

```text
Drivers nearby but unavailable
```

from:

```text
Drivers available but filtered
```

from:

```text
Reservation conflicts
```

This distinction is essential for improving dispatch policy.

---

# 49. Demand Diagnostics

Hot-region observability should show:

```text
Demand
Supply
Ratio
Average ETA
Search Radius
Dispatch Success
```

This supports future surge and dispatch optimization without coupling dashboards directly to business logic.

---

# 50. Performance Profiling

Application profiling may be used when measurements indicate CPU/memory bottlenecks.

Do not add profiling complexity permanently without evidence.

Prefer:

```text
Metrics
+
Tracing
+
Targeted Profiling
```

when investigating performance problems.

---

# 51. Memory Observability

Useful runtime measurements include:

```text
Heap Usage
GC Activity
Goroutine Count
Process Memory
```

These are especially useful for detecting candidate-pipeline regressions.

The streaming candidate architecture should help keep candidate memory bounded.

---

# 52. Goroutine Observability

Realtime and messaging components can create long-lived goroutines.

Monitor:

```text
Goroutine Count
Consumer Goroutines
Realtime Connection Workers
Background Scheduler Workers
```

Unexpected growth can indicate leaks.

---

# 53. Resource Ownership

Every long-lived background component should have observable lifecycle:

```text
Started
Running
Stopping
Stopped
```

This is particularly important for:

```text
Kafka Consumers
Outbox Publishers
Timeout Schedulers
Realtime Hubs
Reconciliation Workers
```

---

# 54. Shutdown Observability

Graceful shutdown should be traceable/loggable at an operational level.

Conceptually:

```text
Shutdown Signal
   ↓
Stop Accepting Work
   ↓
Stop Consumers
   ↓
Flush / Finish Required Work
   ↓
Close Resources
   ↓
Process Exit
```

The shutdown sequence should not produce false-positive failure alerts.

---

# 55. Observability and Privacy

Observability data can contain identifiers and operational information.

Do not log or trace:

```text
Passwords
Authentication Secrets
Payment Secrets
Private Tokens
Unnecessary Personal Data
```

Only capture identifiers required for diagnosis.

---

# 56. High-Cardinality Rule

Avoid metric labels such as:

```text
ride_id
driver_id
request_id
event_id
trace_id
h3_cell
```

when they create unbounded cardinality.

Use:

```text
Metrics
    → Aggregates

Logs
    → Detailed identities

Traces
    → Per-request relationships
```

This separation keeps telemetry systems scalable.

---

# 57. Metrics Naming

Metric naming should follow the existing repository convention.

Before creating a metric:

```text
Search Existing Metrics
      ↓
Reuse if Equivalent
      ↓
Create Only if Missing
```

Do not create:

```text
dispatch_latency
matching_latency
ride_matching_latency
candidate_dispatch_latency
```

if they all represent the same measurement.

---

# 58. Instrumentation Placement

Instrumentation should be placed at meaningful component boundaries.

Good:

```text
Discovery.Search
Ranking.Rank
Reservation.Reserve
Offer.Send
```

Avoid instrumenting every tiny helper function.

Excessive instrumentation creates noise and overhead.

---

# 59. Observability Must Be Side-Effect Safe

Telemetry failures must not break dispatch.

Conceptually:

```text
Business Operation
       │
       ├── Metrics
       ├── Trace
       └── Logs
```

If a telemetry backend is unavailable:

```text
Business Operation
       ↓
Should Continue
```

unless the observability mechanism is explicitly part of a required compliance workflow.

---

# 60. Telemetry Overhead

Instrumentation should remain lightweight.

Avoid:

```text
Large Object Serialization
Per-Candidate Logging
Full Payload Tracing
Unbounded Metric Labels
```

inside the hot path.

---

# 61. Testing Observability

Observability tests should verify:

```text
Important Metric Recorded
Important Span Created
Correlation Preserved
Error Classified
```

Tests should not become tightly coupled to exact internal instrumentation details unless the telemetry contract itself is important.

---

# 62. Testing Dispatch Instrumentation

A useful integration test verifies:

```text
Dispatch Request
    ↓
Trace
    ├── Discovery
    ├── Ranking
    ├── Reservation
    └── Offer
```

and confirms that the correlation context remains intact.

---

# 63. Testing Failure Telemetry

Test representative failures:

```text
No Candidate
Reservation Conflict
Redis Failure
PostgreSQL Failure
Offer Delivery Failure
Consumer Failure
```

Each should produce an appropriate failure classification.

---

# 64. AI Agent Implementation Rules

Before modifying observability components, an AI coding agent must:

1. Read this document.
2. Read the existing observability architecture documentation.
3. Inspect the current metrics package.
4. Inspect the current logging abstraction.
5. Inspect tracing setup and propagation.
6. Search for existing metric names before adding new ones.
7. Search for existing span names before adding new ones.
8. Inspect health/readiness implementation.
9. Inspect dispatch instrumentation points.
10. Inspect messaging and persistence instrumentation.
11. Preserve low-cardinality metric design.
12. Preserve correlation/trace propagation.
13. Ensure telemetry failures cannot break business operations.
14. Add tests only for meaningful telemetry contracts.
15. Run the relevant test suite after instrumentation changes.

---

# 65. AI Agent Forbidden Patterns

An AI agent must not:

- add a metric for every entity ID,
- use ride ID or driver ID as a high-cardinality metric label,
- log every candidate in production,
- log full request/response payloads by default,
- expose secrets through logs/traces,
- make business logic depend on telemetry success,
- create duplicate metrics for existing measurements,
- create spans for every trivial helper function,
- turn health checks into expensive diagnostic workflows,
- make liveness depend on every external dependency,
- add a new logging framework when an existing abstraction exists,
- add a second tracing implementation,
- hard-code alert thresholds inside business logic,
- introduce dashboards into application code,
- couple ranking decisions to observability output.

# 68. Component Responsibility Matrix

| Component | Responsibility | Must Not Own |
|---|---|---|
| Metrics | Aggregated measurements | Business decisions |
| Logger | Structured operational records | State transitions |
| Tracer | Distributed execution context | Retry policy |
| Health Service | Liveness/readiness | Business workflow |
| Dispatch Instrumentation | Dispatch telemetry | Dispatch decisions |
| Messaging Instrumentation | Broker telemetry | Event semantics |
| Persistence Instrumentation | Storage telemetry | Query policy |
| Alerting | Operational thresholds | Application logic |
| Dashboard | Human-facing visualization | Runtime state mutation |

# 71. Final Component Rule

When an AI agent is asked to modify observability behaviour, determine first:

```text
Is the change about:
    │
    ├── Aggregate measurement?
    │       → Metrics
    │
    ├── Detailed operational event?
    │       → Structured Logging
    │
    ├── Cross-component execution?
    │       → Tracing
    │
    ├── Process availability?
    │       → Health / Readiness
    │
    ├── Operational threshold?
    │       → Monitoring / Alerting
    │
    └── Dispatch diagnosis?
            → Existing component instrumentation
```

Observability Components should remain responsible for **making system behaviour measurable, traceable, and diagnosable without changing business behaviour or introducing operational overhead that is disproportionate to its diagnostic value**.
