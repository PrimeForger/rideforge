# RideForge — Geo Components

> **Document:** `docs/03-components/5.GEO_COMPONENTS.md`  
> **Status:** Active  
> **Scope:** Component-level documentation for geographic indexing, spatial lookup, geo refinement, and distance calculation  
> **Related:** `docs/02-architecture/6.GEO_ENGINE.md`, `docs/02-architecture/3.DISCOVERY_ENGINE.md`, `docs/03-components/2.DISCOVERY_COMPONENTS.md`, `docs/03-components/3.CANDIDATE_PIPELINE_COMPONENTS.md`

---

# 1. Purpose

The Geo Components provide the geographic infrastructure required by RideForge dispatch.

They answer two different questions:

```text
Discovery:
Which drivers are geographically relevant?

Refinement:
How geographically close is a selected candidate?
```

The geo layer provides efficient spatial operations without becoming responsible for:

```text
Driver Eligibility
Ranking Policy
Reservation
Offer Creation
Assignment
Retry
```

---

# 2. Geo Architecture

The current geographic flow is:

```text
Driver Location
      ↓
H3 Cell
      ↓
H3 Driver Index
      ↓
Candidate Discovery
      ↓
Candidate IDs
      ↓
Geo Refinement
      ↓
Distance / Travel Features
      ↓
Ranking
```

H3 is the primary spatial indexing mechanism.

Redis GEO is used as a secondary geographic lookup/refinement mechanism where configured.

---

# 3. Geographic Responsibilities

The geo subsystem is divided into distinct responsibilities:

```text
H3 Service
    → H3 calculations

H3 Driver Index
    → Driver-to-cell spatial index

Geo Service
    → Redis GEO operations

Geo Strategy
    → Geographic candidate discovery

Geo Refiner
    → Candidate geographic refinement

Distance Calculation
    → Exact/approximate geographic distance
```

The responsibilities should remain separated.

---

# 4. H3 Service

The H3 service abstracts the H3 library from application components.

Its responsibilities include operations such as:

```text
Latitude/Longitude → H3 Cell
Cell → Neighbouring Cells
Search Ring
Maximum Search Ring
```

Higher-level discovery components should depend on this abstraction rather than directly calling the H3 library.

---

# 5. H3 Resolution

H3 resolution is configuration-driven.

Conceptually:

```text
Coordinates
    ↓
Configured H3 Resolution
    ↓
H3 Cell
```

The resolution determines the geographic granularity of the spatial index.

It should not be independently selected by every caller.

---

# 6. H3 Cell as Spatial Identity

A driver location is represented in the spatial index through its current H3 cell.

Conceptually:

```text
Driver
  ↓
Current Location
  ↓
H3 Cell
```

The H3 cell is an indexing identity, not an exact driver location.

---

# 7. H3 Driver Index

The H3 driver index maintains the relationship:

```text
H3 Cell
   ↓
Driver IDs
```

and the reverse/current-cell mapping required to move a driver between cells.

It is an operational index.

It is not the authoritative source of the driver's durable business record.

---

# 8. Driver Cell Membership

When a driver enters a cell:

```text
H3 Cell
   ↓
Add Driver ID
```

When a driver leaves:

```text
H3 Cell
   ↓
Remove Driver ID
```

The index implementation is responsible for maintaining correct membership.

---

# 9. Atomic Driver Movement

Driver cell movement must be safe under concurrent location updates.

The desired operation is logically:

```text
Old Cell
   │
   ├── Remove Driver
   │
   └── New Cell
          ↓
       Add Driver
          ↓
     Update Mapping
```

These operations should be performed atomically by the index implementation where required.

Higher-level components must not reconstruct movement logic themselves.

---

# 10. Same-Cell Updates

If:

```text
Old Cell == New Cell
```

the spatial membership should not be unnecessarily removed and re-added.

The realtime/location layer may refresh freshness independently.

This reduces Redis write load while preserving driver liveness.

---

# 11. H3 Cell TTL

Driver cell membership may use a TTL to prevent indefinitely stale spatial entries.

The configured cell TTL represents operational freshness.

TTL handling must remain consistent with the driver heartbeat/location lifecycle.

---

# 12. Empty Cell Cleanup

When the last driver leaves a cell:

```text
SREM
   ↓
Cell Empty
   ↓
Cleanup
```

Empty index structures should not accumulate indefinitely.

Cleanup is an H3 index responsibility.

---

# 13. H3 Lookup

Discovery requests nearby H3 cells.

Conceptually:

```text
Pickup Location
      ↓
Pickup H3 Cell
      ↓
Search Ring
      ↓
Relevant Cells
      ↓
H3 Driver Index
      ↓
Driver IDs
```

The geo layer should keep this lookup efficient and bounded.

---

# 14. Multi-Cell Lookup

When multiple H3 cells are required, the index should batch/pipeline the underlying Redis operations where appropriate.

Preferred:

```text
Cell 1 ─┐
Cell 2 ─┤
Cell 3 ─┼── Batch / Pipeline ──→ Driver IDs
Cell 4 ─┘
```

rather than:

```text
Cell 1 → Redis
Cell 2 → Redis
Cell 3 → Redis
Cell 4 → Redis
```

This reduces network round trips.

---

# 15. H3 Ring Expansion

H3 ring generation belongs to the discovery layer, but it relies on the H3 service for spatial cell generation.

The desired search pattern is progressive:

```text
Ring 0
  ↓
Enough?
  ├── Yes → Stop
  └── No
       ↓
     Ring 1
       ↓
     Enough?
       ├── Yes → Stop
       └── No → Continue
```

The geo components provide the spatial primitives; discovery policy decides how far to search.

---

# 16. Maximum Search Ring

The H3 service exposes the configured maximum search boundary.

The maximum ring is a safety/performance limit.

It prevents discovery from expanding without bounds.

---

# 17. Geo Service

The Geo Service provides geographic operations backed by the configured geo infrastructure.

The current architecture includes Redis GEO as a secondary geographic mechanism.

Conceptually:

```text
Geo Service
    ↓
Redis GEO
```

The service hides Redis GEO implementation details from application-level strategies and refiners.

---

# 18. Redis GEO as Secondary Index

Redis GEO is not the primary H3 membership index.

The intended architecture is:

```text
H3
 ↓
Primary spatial candidate narrowing

Redis GEO
 ↓
Secondary geographic refinement
```

This allows H3 to provide efficient cell-based discovery while GEO can provide more precise geographic distance ordering/refinement.

---

# 19. Why Two Geographic Mechanisms

The two mechanisms solve different problems.

### H3

Optimized for:

```text
Spatial partitioning
Neighbourhood search
Cell-based density
Regional indexing
```

### Redis GEO

Useful for:

```text
Coordinate-based proximity
Distance refinement
Secondary geographic lookup
```

Neither should silently replace the responsibility of the other.

---

# 20. Geo Strategy

The Geo Strategy is an alternative `CandidateSearcher` implementation.

Conceptually:

```text
CandidateSearcher
      ↓
GeoStrategy
      ↓
GeoService
      ↓
Nearby Drivers
```

It provides geographic candidate discovery when the configured system does not use H3 discovery.

---

# 21. H3 Strategy vs Geo Strategy

The application chooses the active strategy through configuration.

Conceptually:

```text
H3 Enabled?
    │
    ├── Yes → H3 Strategy
    │
    └── No  → Geo Strategy
```

The Dispatch Engine remains unaware of the selected strategy.

---

# 22. Geo Strategy Boundary

The Geo Strategy should:

- translate discovery requests,
- invoke geographic lookup,
- return candidate identities,
- respect configured search limits.

It should not:

```text
Rank Drivers
Reserve Drivers
Create Offers
Assign Rides
```

---

# 23. Geo Refinement

Geo refinement operates after broad candidate discovery.

Conceptually:

```text
H3 Discovery
      ↓
Candidate IDs
      ↓
Geo Refinement
      ↓
Distance Information
      ↓
Ranking
```

This prevents expensive geographic calculations from being applied to an unnecessarily large driver population.

---

# 24. Refinement Interface

The refinement layer has a dedicated refiner abstraction.

The current package contains:

```text
Refiner
Request
Result
Source
Redis Geo Refiner
No-op Refiner
```

The interface isolates refinement from the discovery engine.

---

# 25. Refinement Request

A refinement request contains the geographic information required to refine candidate locations.

The exact fields are defined by the current refinement contract.

The refiner should not require unrelated ride or driver business state.

---

# 26. Refinement Result

The refinement result contains the geographic information needed by downstream ranking/travel processing.

The result should remain focused on refinement rather than becoming a general-purpose candidate object.

---

# 27. Redis Geo Refiner

`RedisGeoRefiner` provides the Redis GEO-backed refinement implementation.

Conceptually:

```text
Candidate IDs
      ↓
Redis GEO
      ↓
Geographic Result
```

It should use the existing Geo Service/source abstraction rather than exposing Redis commands to ranking components.

---

# 28. No-Op Refiner

`NoopRefiner` provides a valid refinement implementation when geographic refinement is not required or not configured.

Conceptually:

```text
Refiner
 ├── RedisGeoRefiner
 └── NoopRefiner
```

This avoids forcing every deployment to use Redis GEO.

---

# 29. Refinement Strategy

Refinement should be selective.

The preferred sequence is:

```text
Cheap Spatial Index
       ↓
Candidate Narrowing
       ↓
Refinement
       ↓
Ranking
```

The system should not refine every possible driver before candidate filtering.

---

# 30. Haversine Refinement

Haversine distance can be used when straight-line geographic distance is sufficient.

Conceptually:

```text
Driver Coordinates
+
Pickup Coordinates
      ↓
Haversine
      ↓
Distance
```

Haversine is geographic distance, not travel ETA.

---

# 31. Distance vs ETA

These are distinct concepts:

```text
Distance
    =
Geographic separation

ETA
    =
Estimated travel time
```

The geo subsystem may provide distance.

The travel/ranking subsystem may later use routing providers to obtain ETA.

---

# 32. Routing Provider Boundary

Future ETA providers should be introduced behind a travel/routing abstraction.

Potential providers include:

```text
Google
Mapbox
OSRM
Valhalla
```

The Geo Components should not become tightly coupled to any one routing provider.

---

# 33. Geographic Accuracy

H3 cell membership is approximate.

A driver being in a nearby H3 cell does not mean:

```text
Driver is the closest driver
```

Exact distance or ETA must be calculated later where required.

---

# 34. Candidate Discovery and Geo Refinement

The intended distinction is:

```text
Discovery:
"Is this driver geographically relevant?"

Refinement:
"How close is this driver?"

Ranking:
"How desirable is this driver overall?"
```

Keeping these questions separate prevents the geographic layer from becoming the ranking engine.

---

# 35. Driver Location Updates

The realtime driver-location flow updates geographic indexes.

Conceptually:

```text
Driver GPS
    ↓
Driver Location Service
    ↓
H3 Index
    +
Geo Index where required
```

The Dispatch Engine does not update geographic indexes itself.

---

# 36. Location Service Boundary

The Driver Location Service coordinates location updates.

The geo components provide the underlying spatial operations.

Therefore:

```text
DriverLocationService
      ↓
H3 Service / H3 Index
      ↓
Geo Infrastructure
```

The location service owns application-level location update orchestration.

---

# 37. Geographic State vs Durable State

Spatial indexes are operational state.

They should not be treated as the authoritative durable source for:

```text
Driver Profile
Driver Account
Driver Lifecycle
Ride Assignment
```

Durable business state remains in the appropriate persistence/domain components.

---

# 38. Stale Geographic Entries

A spatial index can temporarily contain stale data.

Examples:

```text
Driver disconnected
Heartbeat expired
Location update delayed
Process restarted
```

The system must therefore combine spatial lookup with current driver-state validation.

---

# 39. Availability Boundary

Geo discovery does not guarantee driver availability.

The actual flow is:

```text
Geo Index
   ↓
Driver ID
   ↓
Driver Cache / State
   ↓
Availability Filter
```

This prevents geographic state from being mistaken for operational state.

---

# 40. Geographic Concurrency

Driver locations can change while a dispatch search is executing.

For example:

```text
Search
  ↓
Driver A discovered
  ↓
Driver A moves
  ↓
Availability / reservation check
```

This is expected.

The system should not attempt to make discovery a global snapshot of driver locations.

---

# 41. Spatial Index Consistency

The H3 index should maintain:

```text
Driver → Current Cell
```

and:

```text
Cell → Driver IDs
```

consistently.

Any reconciliation or recovery mechanism belongs to the reliability architecture.

---

# 42. Redis GEO Consistency

If Redis GEO is used as a secondary index, its state should be updated consistently with the driver location flow.

It should not become a competing source of truth.

---

# 43. Geo Failure Handling

Geographic infrastructure failures must remain distinguishable from an empty geographic result.

For example:

```text
No drivers in cells
```

is different from:

```text
Redis unavailable
```

The former is a valid search result.

The latter is an infrastructure failure.

---

# 44. Error Propagation

Geo components should propagate meaningful infrastructure errors to their callers.

They should not silently transform:

```text
Redis timeout
Redis connection failure
Invalid operation
```

into:

```text
No candidates
```

unless the explicit component contract defines a safe fallback.

---

# 45. No-Op Behaviour

A no-op implementation may intentionally return an empty or unchanged refinement result when refinement is disabled.

This behaviour must be explicit in the refiner contract and must not be confused with a failed Redis refinement.

---

# 46. Geographic Performance

The geo path is part of the dispatch hot path.

The implementation should prioritize:

```text
Low Redis Round Trips
Bounded Cell Searches
Efficient Cell Membership
Early Search Stop
Batch Lookups
Minimal Data Transfer
```

---

# 47. Redis Command Efficiency

The H3 index should avoid unnecessary repeated operations.

Examples:

```text
Same cell
    ↓
Refresh required freshness only

Cell changed
    ↓
Atomic movement
```

This reduces write amplification from high-frequency GPS updates.

---

# 48. Pipeline Multi-Cell Lookup

Multi-cell H3 lookup should prefer Redis pipelining/batching.

This is especially important when the search reaches multiple rings.

The number of network round trips should not grow linearly with cell count where batching is possible.

---

# 49. Geographic Metrics

Useful geo metrics include:

```text
H3 Cell Changes
Same-Cell Updates
Drivers Added
Drivers Removed
Cell Lookup Latency
Drivers Per Cell
Geo Lookup Latency
Refinement Latency
```

Discovery-level metrics such as:

```text
Average Ring
Cells Examined
Drivers Examined
```

belong to discovery/dispatch observability but may use geo data.

---

# 50. Geographic Tracing

Useful geographic tracing attributes include:

```text

Search Ring
Cell Count
Drivers Returned
Lookup Duration
Refinement Duration
```

Tracing should avoid storing unnecessary full location histories.

# 51. Testing H3 Components

Refiner tests should cover:

```text
Valid Request

Source Error
```

The refiner should be independently testable.

# 54. Integration Testing

Geographic integration tests should verify the complete path where practical:

```text

    ↓

    ↓
```

# 56. AI Agent Forbidden Patterns

An AI agent must not:

- create a second H3 index,
- create a second Geo Service,
- bypass the H3 index from discovery without a concrete requirement,
- use Redis GEO as an implicit replacement for H3 without an architectural decision,
- perform Haversine before H3 candidate narrowing without a justified use case,
- perform expensive routing for the entire driver population,
- put ranking weights in geo components,
- reserve drivers during geographic lookup,
- create offers during geographic lookup,
- treat H3 membership as availability,
- treat geographic distance as ETA,
- silently swallow Redis failures,
- introduce direct Redis calls into application components when an existing geo abstraction exists,
- change H3 resolution independently inside a component,
- add spatial complexity solely to mark a roadmap phase complete.

```text

H3 Driver Index
Redis GEO Service
H3 Strategy
Geo Strategy
Refinement Abstraction
Redis GEO Refiner
No-op Refiner
Driver Location Integration
```

The system already follows the intended high-level model:

```text

 ↓
Candidate Narrowing
 ↓
Geo Refinement
 ↓

```

The geographic subsystem can evolve toward:

```text

      ↓
Redis GEO Secondary Index
      ↓
Geographic Refinement
      ↓
```

# 61. Final Component Rule

When an AI agent is asked to modify geographic behaviour, determine first:

```text
Is the change about:
    │
    ├── H3 calculation?
    │       → H3 Service
    │
    ├── Driver-to-cell membership?
    │       → H3 Driver Index
    │
    ├── Redis GEO?
    │       → Geo Service
    │
    ├── Candidate geographic discovery?
    │       → Discovery Strategy
    │
    ├── Geographic refinement?
    │       → Refiner
    │
    ├── Driver location update?
    │       → Driver Location Service
    │
    └── ETA / ranking?
            → Travel / Ranking Components
```

The Geo Components should remain responsible for **efficient, bounded, and reliable geographic indexing and refinement while keeping geographic concerns separate from driver eligibility, ranking, reservation, and assignment**.

# 24. Dispatch Strategy and Configuration Clarifications

The Geo Components must support the clarified RideForge dispatch model without turning dispatch strategy into a hard geographic boundary.

## 24.1 Dispatch Strategy Resolution Is Upstream

Geo components must consume the already-resolved effective dispatch strategy.

They must not independently resolve:

```text
State
→ District
→ City / Town
→ Rural Area
→ Auto Stand
→ Ride-level
→ Other configured levels
```

The resolution process is:

```text
Most Specific Applicable Configuration
        ↓
Explicit Strategy?
   ├── YES → Effective Strategy
   └── NO → Move to Parent
        ↓
Continue Until Strategy Is Found
        ↓
System Default if None Exists
```

The nearest explicit configuration takes precedence.

---

## 24.2 Smart Stand Dispatch and Geo Behavior

Smart Stand Dispatch is **stand-preferred, not stand-exclusive**.

When a pickup is within a configured auto-stand radius, Geo components should identify the relevant stand context and make it available to downstream dispatch processing.

```text
Pickup
  ↓
Inside Stand Radius?
  ├── YES → Identify Preferred Stand
  └── NO  → No Preferred Stand
```

Identifying a preferred stand must not mean:

```text
Search only inside the stand
```

Instead, if suitable supply is unavailable, geographic discovery may expand to:

```text
Non-stand Drivers
Nearby Stands
Nearby Locations
```

---

## 24.3 Smart Dispatch

Smart Dispatch is stand-agnostic.

Geo components should perform normal eligible nearby-driver discovery without creating a stand preference merely because a driver happens to be at an auto stand.

```text
Smart Dispatch
    ↓
Eligible Nearby Drivers
    ↓
Geographic Discovery
```

---

## 24.4 Radius Concepts Must Remain Separate

The following are distinct concepts and must not be conflated:

```text
Stand Radius
Driver Search Radius
Location Expansion Radius
Geo Refinement Radius
```

For example:

```text
Pickup inside Stand Radius
        ≠
Driver must be inside Stand Radius
```

The stand radius identifies stand preference/context. It does not automatically define the complete driver candidate boundary.

---

## 24.5 Cross-Location Geographic Expansion

When local supply is insufficient, geographic discovery may expand to nearby locations.

```text
Origin Location
    ↓
Local Search
    ↓
Insufficient Suitable Supply
    ↓
Nearby Location Search
```

Drivers discovered from another location may be valid candidates when they satisfy the applicable constraints.

The Geo layer should preserve:

```text
Candidate Location
Candidate Location Strategy
Stand Membership
Relevant Stand
Queue Position
Discovery Source
Expansion Level
Distance
ETA where available
```

A driver's source location must not automatically be treated as a hard exclusion boundary.

---

## 24.6 Different Strategies Across Nearby Locations

Nearby locations may use different dispatch strategies.

Example:

```text
Location A → Smart Dispatch
Location B → Smart Stand Dispatch
```

If discovery expands from A into B, Geo components must not exclude B merely because B uses Smart Stand Dispatch.

The candidate's local context should be preserved so downstream dispatch/ranking logic can apply the appropriate strategy-specific prioritization.

---

## 24.7 Strategy Preservation During Geographic Expansion

Geographic expansion does not change the resolved dispatch strategy.

Example:

```text
Effective Strategy:
Smart Stand Dispatch

Preferred Stand
    ↓
No suitable supply
    ↓
Geographic expansion
    ↓
Nearby candidates
```

The system remains under the resolved strategy unless an explicit business/configuration rule defines a strategy change.

Therefore:

```text
Geographic Expansion
≠
Strategy Switching
```

---

## 24.8 Geo Components vs Dispatch Components

Geo components are responsible for geographic operations such as:

```text
Stand-radius evaluation
Nearby-driver discovery
Nearby-location discovery
Distance calculation
Geospatial filtering
Geo refinement
```

They are not responsible for:

```text
Resolving configuration inheritance
Selecting the effective dispatch strategy
Applying stand queue policy
Final candidate ranking
Final driver assignment
```

The conceptual boundary is:

```text
Configuration Resolution
        ↓
Dispatch Strategy Resolution
        ↓
Geo Discovery / Refinement
        ↓
Candidate Pipeline
        ↓
Strategy-Specific Prioritization
        ↓
Ranking / Assignment
```

---

## 24.9 Candidate Eligibility vs Geographic Preference

Geo components must distinguish geographic preference/context from hard eligibility.

For example:

```text
Driver outside preferred stand
    ≠
Driver geographically ineligible
```

and:

```text
Driver from nearby location
    ≠
Driver automatically ineligible
```

Hard eligibility may still be determined by:

```text
Service Area
Legal / Regional Constraints
Driver Availability
Vehicle / Service Compatibility
Freshness of Location
Maximum Reachable Distance
Other Domain Constraints
```

Geo components should expose the information required for those downstream decisions rather than silently applying unrelated business rules.

---

## 24.10 AI-Assisted Dispatch

AI-assisted dispatch may use geographic features such as:

```text
Distance
ETA
Location density
Spatial demand/supply signals
Historical geographic patterns
```

However, Geo components must not treat AI as a third dispatch strategy.

The resolved strategy remains authoritative:

```text
Smart Stand Dispatch
        OR
Smart Dispatch
        ↓
AI-assisted optimization where applicable
```

AI must not override hard geographic, legal, safety, or eligibility constraints.

---

## 24.11 Implementation Guardrails

Geo implementations must not:

```text
Treat a stand radius as a stand-only driver search boundary.

Reject every non-stand driver when a pickup is inside a stand radius.

Reject nearby-location drivers solely because their source location uses another dispatch strategy.

Resolve hierarchical dispatch configuration inside Geo components.

Hard-code the configuration hierarchy into the Geo layer.

Silently switch Smart Stand Dispatch to Smart Dispatch during geographic expansion.

Treat stand membership as universal geographic eligibility.

Conflate stand radius with driver search radius or location expansion radius.
```

The Geo layer should provide accurate geographic context and candidate discovery while leaving strategy-specific prioritization to the appropriate dispatch/ranking components.
