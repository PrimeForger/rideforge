# RideForge Ranking Engine

> **Document:** `docs/02-architecture/RANKING_ENGINE.md`\
> **Status:** Active architecture documentation\
> **Scope:** Candidate feature extraction, travel features, driver
> quality, fairness, scoring, normalization, ranking configuration, and
> ranking-stage integration\
> **Audience:** Backend developers, architects, reviewers, and AI coding
> agents

------------------------------------------------------------------------

# 1. Executive Summary

The RideForge Ranking Engine determines the relative quality of
candidates that have already passed the Candidate Pipeline's required
discovery and filtering stages.

Its responsibility is:

> **Convert an eligible candidate into a comparable dispatch score.**

The Ranking Engine does not discover drivers, filter operational
availability, reserve drivers, or publish offers.

Its position is:

``` text
Discovery
    │
    ▼
Candidate Pipeline
    │
    ├── Enrichment
    ├── Validation
    ├── Filtering
    │
    ▼
Ranking Stage
    │
    ▼
Ranker
    │
    ├── Feature Extraction
    │
    └── Scoring
    │
    ▼
Candidate Score
    │
    ▼
Heap
    │
    ▼
Matching Engine
```

The architecture is intentionally separated into:

``` text
Feature Extraction
        +
Feature Calculation
        +
Scoring
```

This allows ranking behaviour to evolve without turning the Candidate
Pipeline or Matching Engine into a monolithic ranking implementation.

------------------------------------------------------------------------

# 2. Purpose

The Ranking Engine answers:

> **Among the candidates that are currently eligible, which candidates
> should be preferred?**

This is a different question from discovery:

``` text
Discovery:
Who is geographically relevant?
```

and filtering:

``` text
Filtering:
Who is currently eligible?
```

Ranking answers:

``` text
Which eligible candidate is preferable?
```

------------------------------------------------------------------------

# 3. Dispatch Strategy Context

The Ranking Engine operates **after the applicable dispatch strategy has
already been resolved** and after the Candidate Pipeline has produced
eligible candidates.

The Ranking Engine must not resolve the configuration hierarchy itself.

The high-level flow is:

``` text
Ride
   │
   ▼
Dispatch Configuration Resolution
   │
   ▼
Effective Dispatch Strategy
   │
   ▼
Candidate Discovery
   │
   ▼
Candidate Pipeline
   │
   ▼
Eligible Candidates
   │
   ▼
Strategy-Specific Prioritization / Ranking
   │
   ▼
Ordered Candidates
```

The effective strategy may be:

``` text
Smart Stand Dispatch
Smart Dispatch
```

AI-assisted ranking may optionally enhance either strategy, but it does
not become a separate primary dispatch strategy.

## 3.1 Ranking Is Not Strategy Resolution

The Ranking Engine must not:

- walk State → District → Town → Rural Area → Stand → Ride-level
  configuration,
- choose the effective dispatch strategy,
- replace an explicitly configured strategy with another strategy,
- infer strategy from a driver's stand membership.

Configuration resolution belongs to the dispatch/configuration layer.

## 3.2 Ranking Is Not Candidate Discovery

The Ranking Engine also does not determine the geographic candidate
boundary.

For example, a candidate may have been discovered:

``` text
At the preferred stand
Outside the preferred stand
At another nearby stand
Outside any stand
From another nearby location
```

The Ranking Engine receives candidates that have already passed the
required discovery and eligibility stages.

Therefore:

``` text
Dispatch Strategy
        ≠
Candidate Discovery Boundary
```

## 3.3 Smart Stand Dispatch

For Smart Stand Dispatch, stand preference is part of the strategy
context.

When the rider is within a configured stand radius, the relevant stand's
eligible drivers are preferred according to the stand's queue/order
rules.

The Ranking Engine must not turn this into a generic rule that always
selects the globally highest score from every candidate.

The strategy may require:

``` text
Preferred Stand
      ↓
Eligible Stand Candidates
      ↓
Stand Queue / Ordering
      ↓
Strategy-specific selection
```

If the preferred stand cannot provide a suitable driver, the candidate
flow may expand to:

``` text
Nearby stand drivers
Non-stand drivers
Drivers from nearby locations
```

Those broader candidates may then be compared using the applicable
dispatch/ranking factors.

The exact boundary between queue selection and numerical ranking must be
defined by the dispatch business rules and current implementation. The
Ranking Engine must not silently replace queue semantics with a generic
weighted score.

## 3.4 Smart Dispatch

For Smart Dispatch, auto-stand membership does not create a ranking
preference.

Eligible candidates are compared using the normal configured ranking
signals, such as:

``` text
Eligibility
Distance
ETA
Driver Quality
Fairness
Other configured ranking factors
```

A driver at an auto stand and a driver outside an auto stand are
otherwise comparable according to the same Smart Dispatch ranking model.

## 3.5 Cross-Location Candidates

A candidate discovered from a nearby location is not automatically
ineligible because the candidate belongs to a location using a different
dispatch strategy.

For example:

``` text
Ride Origin: Location A
Location A Strategy: Smart Dispatch

Candidate:
Location B
Location B Strategy: Smart Stand Dispatch
```

If the candidate is eligible and discovered by the configured expansion
process, the candidate may enter the final comparison.

The candidate should retain relevant context such as:

``` text
Candidate Location
Candidate Location Strategy
Stand Membership
Relevant Stand
Queue Position
Discovery Source
Distance
ETA
```

This allows downstream dispatch logic to apply the correct strategy
context without treating location boundaries as hard candidate
boundaries.

## 3.6 Strategy Context Must Be Preserved

The ranking stage should receive enough context to distinguish:

``` text
Why was this candidate discovered?
Which location does the candidate belong to?
Is the candidate associated with a preferred stand?
What is the candidate's stand queue position, if applicable?
Which dispatch strategy governs the candidate's originating location?
```

This context is not necessarily converted into a single numeric feature.

It may instead be consumed by the dispatch strategy before or around the
ranking stage.

The important rule is:

> **Do not discard strategy-relevant candidate context before final
> dispatch selection.**

# 4. Ranking Goals

The Ranking Engine is designed around the following goals.

## 3.1 ETA-aware ranking

The long-term production ranking objective is to prefer drivers based on
estimated arrival time rather than raw geographic distance.

Conceptually:

``` text
Pickup
  │
  ▼
Driver
  │
  ▼
Estimated Travel Time
  │
  ▼
ETA Score
```

Distance can remain a useful fallback or intermediate feature, but it
should not become the final dispatch objective when reliable ETA
information is available.

------------------------------------------------------------------------

## 3.2 Driver quality

Driver quality contributes to the overall score.

Relevant signals include:

-   acceptance rate,
-   cancellation rate,
-   timeout rate,
-   rating,
-   completed trips,
-   experience-related signals.

These signals should be normalized before being combined.

------------------------------------------------------------------------

## 3.3 Fairness

The ranking system should avoid repeatedly preferring the same drivers
when other candidates are otherwise comparable.

A driver who has been idle longer can receive a controlled fairness
contribution.

Fairness must remain a ranking signal, not an override that ignores
operational suitability.

------------------------------------------------------------------------

## 3.4 Configuration-driven scoring

Weights and ranking behaviour must come from configuration.

Do not hard-code business weights inside calculators.

For example:

``` text
ETA Weight
Quality Weight
Fairness Weight
```

should be configuration-driven.

------------------------------------------------------------------------

## 3.5 Replaceable scoring implementation

The Candidate Pipeline depends on a `Ranker` contract.

Therefore:

``` text
Candidate Pipeline
       │
       ▼
Ranker
```

rather than:

``` text
Candidate Pipeline
       │
       ▼
Concrete Ranking Formula
```

This allows future ranking strategies without rewriting pipeline
orchestration.

------------------------------------------------------------------------

# 4. Non-Goals

The Ranking Engine does not own:

-   dispatch configuration resolution,
-   hierarchical configuration inheritance,
-   driver discovery,
-   H3 lookup,
-   candidate filtering,
-   stand-radius detection,
-   stand queue ownership,
-   cross-location expansion,
-   driver reservation,
-   offer publication,
-   retry policy,
-   ride state transitions.

It also should not directly mutate driver operational state.

The Ranking Engine may consume strategy-relevant candidate context, but it
must not redefine the resolved dispatch strategy or convert strategy
constraints into arbitrary ranking weights.

------------------------------------------------------------------------

# 6. Core Ranking Contract

The ranking subsystem exposes a ranker boundary.

Conceptually:

``` go
type Ranker interface {
    Rank(
        ctx context.Context,
        pipelineCtx *pipeline.Context,
        candidate *candidate.Candidate,
    ) (candidate.Score, error)
}
```

The Candidate Pipeline only knows about this contract.

It does not know how the score is calculated.

------------------------------------------------------------------------

# 7. Default Ranker

The default ranker coordinates feature extraction and scoring.

Conceptually:

``` text
Candidate
   │
   ▼
FeatureExtractor
   │
   ▼
Features
   │
   ▼
Scorer
   │
   ▼
Score
```

The ranker should remain an orchestration component.

It should not become a second scorer.

------------------------------------------------------------------------

# 8. Feature Extraction

Feature extraction converts candidate/domain data into ranking-specific
features.

Conceptually:

``` go
type FeatureExtractor interface {
    Extract(
        ctx context.Context,
        pipelineCtx *pipeline.Context,
        candidate *candidate.Candidate,
    ) (Features, error)
}
```

The exact method signature may evolve with the current codebase, but the
responsibility remains:

> Convert available candidate information into ranking features.

------------------------------------------------------------------------

# 9. Feature Groups

Ranking features are organized into meaningful groups.

Current conceptual groups include:

``` text
Travel
Quality
Fairness
```

Future ranking work may introduce:

``` text
Demand
Surge
Acceptance Probability
```

but these should only be added when their data source and business rules
actually exist.

------------------------------------------------------------------------

# 10. Features Model

The overall feature set conceptually contains:

``` go
type Features struct {
    Travel   TravelFeatures
    Quality  QualityFeatures
    Fairness FairnessFeatures
}
```

This grouping prevents the scorer from receiving a flat collection of
unrelated values.

------------------------------------------------------------------------

# 11. Travel Features

Travel features represent the candidate's geographic/travel relationship
to the pickup.

Examples:

``` text
DistanceKm
ETASec
```

The architecture should allow the travel calculation to evolve from
simple distance toward routing-aware ETA.

------------------------------------------------------------------------

# 12. Distance

Distance can be represented as:

``` text
DistanceKm
```

It is useful because it is:

-   inexpensive,
-   deterministic,
-   available without a routing provider.

However, geographic distance is not equivalent to arrival time.

Two drivers can have similar straight-line distance but significantly
different road travel times.

------------------------------------------------------------------------

# 13. ETA

ETA represents expected travel time to the pickup.

Conceptually:

``` text
Driver
   │
   ▼
Routing / Travel Calculation
   │
   ▼
ETA
```

ETA is the preferred long-term travel signal.

A future routing provider may supply this through an abstraction rather
than coupling the Ranking Engine to a specific vendor.

------------------------------------------------------------------------

# 14. Travel Calculator

The travel calculator owns travel-related feature calculation.

It should not:

-   calculate driver quality,
-   calculate fairness,
-   determine final ranking weights.

Its responsibility is travel.

------------------------------------------------------------------------

# 15. Quality Features

Quality features represent historical driver performance.

Current conceptual inputs include:

``` text
AcceptanceRate
CancellationRate
TimeoutRate
Rating
CompletedTrips
```

These inputs should be treated as ranking signals rather than direct
business decisions.

------------------------------------------------------------------------

# 16. Quality Calculator

The Quality Calculator transforms raw driver-quality values into a
normalized quality contribution.

The calculation should be configuration-driven.

Conceptually:

``` text
Raw Driver Metrics
       │
       ▼
Quality Calculator
       │
       ▼
Normalized Quality Score
```

------------------------------------------------------------------------

# 17. Acceptance Rate

Acceptance rate is generally positive.

Conceptually:

``` text
Higher acceptance
       │
       ▼
Higher quality contribution
```

The value should be normalized to the expected range before weighted
scoring.

------------------------------------------------------------------------

# 18. Cancellation Rate

Cancellation rate is a negative signal.

Conceptually:

``` text
Higher cancellation
       │
       ▼
Lower quality contribution
```

A typical normalized transformation is:

``` text
1 - cancellation_rate
```

provided the input is already normalized to the expected range.

------------------------------------------------------------------------

# 19. Timeout Rate

Timeout rate is also a negative signal.

Conceptually:

``` text
1 - timeout_rate
```

Again, the input range must be validated or normalized consistently.

------------------------------------------------------------------------

# 20. Rating

Driver rating is typically represented on a bounded scale.

For a five-point rating:

``` text
rating / 5
```

produces a normalized contribution.

The maximum rating should not be buried inside unrelated business logic.

If the rating scale becomes configurable, the calculator should consume
the configured maximum.

------------------------------------------------------------------------

# 21. Experience

Experience can use completed trips as a practical proxy.

A logarithmic transformation is useful because raw trip counts can
otherwise dominate the score.

Conceptually:

``` text
log(completed_trips + 1)
```

The important architectural rule is that the resulting value should be
normalized before it receives a weighted contribution.

------------------------------------------------------------------------

# 22. Quality Configuration

Quality weights belong in ranking configuration.

Conceptually:

``` text
RankingConfig
    │
    ├── AcceptanceWeight
    ├── CancellationWeight
    ├── TimeoutWeight
    ├── RatingWeight
    └── ExperienceWeight
```

Do not write:

``` go
0.25 * acceptance
```

inside the Quality Calculator.

The calculator should consume configured weights.

------------------------------------------------------------------------

# 23. Fairness Features

Fairness represents dispatch fairness signals.

A current example is:

``` text
LastAssignedAt
```

which can be transformed into:

``` text
Idle Duration
```

The goal is to avoid systematically starving otherwise eligible drivers.

------------------------------------------------------------------------

# 24. Fairness Principle

Fairness is a **ranking signal**, not a hard eligibility rule.

Incorrect:

``` text
Driver idle longer
    ↓
Always select driver
```

Correct:

``` text
Driver idle longer
    ↓
Fairness contribution
    ↓
Combine with other signals
```

This prevents fairness from overriding major ETA or quality differences.

------------------------------------------------------------------------

# 25. Fairness Normalization

Raw idle time can grow without a useful upper bound.

Therefore, it should not simply be added directly to the final score.

A bounded transformation should be used.

The exact normalization belongs in the ranking configuration/design
rather than being arbitrarily hard-coded into the scorer.

------------------------------------------------------------------------

# 26. Score Normalization

All major feature groups should produce comparable values.

The intended conceptual range is:

``` text
0.0 ───────────────── 1.0
```

This prevents a feature with a naturally larger numerical range from
dominating the score.

------------------------------------------------------------------------

# 27. Why Normalization Matters

Consider:

``` text
ETA score       = 0.8
Quality score   = 0.9
Experience      = 7.2
```

If experience is added directly, it dominates the other signals.

Instead:

``` text
ETA             = 0.8
Quality         = 0.9
Experience      = 0.6
```

can be safely weighted.

------------------------------------------------------------------------

# 28. Weighted Scoring

For candidates that are being numerically compared by the applicable
strategy, the final score conceptually follows:

``` text
Final Score =
    Travel Contribution
  + Quality Contribution
  + Fairness Contribution
  + Future Contributions
```

Each contribution is weighted using configuration.

Example architecture:

``` text
ETA Weight
Quality Weight
Fairness Weight
```

The exact values belong to configuration, not implementation code.

A strategy-specific preference does not automatically become another
numeric weight.

For example, Smart Stand Dispatch may establish a preferred stand and
queue ordering before broader candidates are compared. The Ranking
Engine must not invent a `StandWeight` merely to force stand semantics
into the generic scorer unless the business rules explicitly define
stand preference as a numerical ranking feature.

------------------------------------------------------------------------

# 29. Scorer Responsibility

The scorer combines already-prepared ranking features.

Conceptually:

``` go
type Scorer interface {
    Score(
        ctx context.Context,
        features Features,
    ) (candidate.Score, error)
}
```

The scorer should not load driver data.

It should not query Redis.

It should not call PostgreSQL.

It should consume features.

------------------------------------------------------------------------

# 30. Separation Between Calculator and Scorer

This distinction is important.

Calculator:

``` text
Raw Data
   │
   ▼
Feature Value
```

Scorer:

``` text
Feature Values
   │
   ▼
Weighted Score
```

This prevents the scorer from becoming a collection of unrelated data
transformations.

------------------------------------------------------------------------

# 31. Default Feature Extractor

The Default Feature Extractor coordinates feature calculation.

Conceptually:

``` text
Candidate
   │
   ├── Travel Calculator
   ├── Quality Calculator
   └── Fairness Calculator
          │
          ▼
       Features
```

The extractor should receive its dependencies through construction.

Do not instantiate calculators inside the extraction method.

------------------------------------------------------------------------

# 32. Enricher Boundary

If a ranking feature requires information not already present on the
candidate, the dependency should be provided through an explicit
enrichment abstraction.

Conceptually:

``` text
Candidate
    │
    ▼
Enricher
    │
    ▼
Ranking Data
```

The extractor should not directly create infrastructure clients.

------------------------------------------------------------------------

# 33. Dependency Injection

The ranking subsystem should be constructed in bootstrap/builders.

Conceptually:

``` text
Ranking Config
     │
     ▼
Feature Calculators
     │
     ▼
Feature Extractor
     │
     ▼
Scorer
     │
     ▼
Ranker
```

This makes dependencies explicit and testable.

------------------------------------------------------------------------

# 34. Builder Responsibility

The builder should assemble the ranking graph.

Conceptually:

``` go
func BuildRanker(
    cfg *config.RankingConfig,
) ranking.Ranker
```

The builder should:

1.  create required calculators,
2.  create required extractors/enrichers,
3.  create scorer,
4.  create ranker.

It should not contain business scoring formulas.

------------------------------------------------------------------------

# 35. Configuration Flow

The expected configuration flow is:

``` text
Application Config
       │
       ▼
RankingConfig
       │
       ├── Travel configuration
       ├── Quality weights
       ├── Fairness configuration
       └── Overall score weights
       │
       ▼
Ranking Components
```

Configuration should be passed explicitly.

------------------------------------------------------------------------

# 36. No Hard-Coded Ranking Weights

This is a strict architectural rule.

Do not write:

``` go
acceptance * 0.25
```

inside the calculator.

Do not write:

``` go
quality * 0.30
```

inside the scorer.

Instead:

``` go
cfg.AcceptanceWeight
cfg.QualityWeight
```

must determine the contribution.

------------------------------------------------------------------------

# 37. Configuration Validation

Ranking configuration should be validated at application startup where
practical.

Invalid configuration examples include:

``` text
Negative weight
Invalid rating maximum
Invalid normalization range
```

The application should fail early rather than silently running an
invalid ranking model.

------------------------------------------------------------------------

# 38. Score Range

If the configured weights and normalized features are designed to
produce a bounded score, the scorer should preserve that invariant.

The exact range should be documented in configuration and tested.

A common target is:

``` text
0.0 <= score <= 1.0
```

If the current implementation intentionally permits another range, that
range must be treated as part of the current contract rather than
assumed.

------------------------------------------------------------------------

# 39. Candidate Score Storage

The resulting score belongs in candidate metadata.

Conceptually:

``` go
candidate.Metadata.Score = &score
```

The driver domain object should not own the dispatch score.

------------------------------------------------------------------------

# 40. Ranking Stage Integration

The Candidate Pipeline invokes ranking after required filtering.

Conceptually:

``` text
Candidate
   │
   ▼
RankingStage
   │
   ▼
Ranker.Rank()
   │
   ▼
Score
   │
   ▼
Candidate.Metadata.Score
```

The Ranking Stage does not need to understand feature internals.

------------------------------------------------------------------------

# 41. Heap Integration

After candidates are ranked:

``` text
Candidates
   │
   ▼
Heap Builder
   │
   ▼
Max Heap
```

The heap uses candidate score for ordering.

Therefore, every candidate entering the heap must have a valid score.

------------------------------------------------------------------------

# 42. Ranking Failure

If ranking fails for a candidate, the default behaviour should be to
return the error and stop the pipeline unless an explicit business rule
defines a safe fallback.

Do not silently assign:

``` text
score = 0
```

to hide ranking failures.

A zero score is a valid ranking result in some models and therefore
should not be confused with an error.

------------------------------------------------------------------------

# 43. Missing Ranking Data

Missing data should be handled explicitly.

Examples:

``` text
Missing rating
Missing last-assigned timestamp
Missing travel information
```

Possible behaviour must be determined by business rules.

The ranking engine should not silently invent values simply because a
field is missing.

If a fallback is required, it should be explicit, deterministic, and
documented.

------------------------------------------------------------------------

# 44. Ranking and Availability

Availability filtering happens before ranking.

``` text
Discovery
   │
   ▼
Enrichment
   │
   ▼
Availability
   │
   ▼
Ranking
```

There is no value in spending ranking work on drivers that cannot
receive an offer.

------------------------------------------------------------------------

# 45. Ranking and Reservation

Ranking is advisory.

It does not guarantee that the driver will ultimately receive an offer.

The actual dispatch sequence is:

``` text
Rank
  │
  ▼
Select
  │
  ▼
Reserve
  │
  ├── Success → Offer
  │
  └── Failure → Try next candidate
```

This is necessary because another concurrent matching flow may reserve
the driver after ranking.

------------------------------------------------------------------------

# 46. Concurrency

Ranking should be treated as a snapshot.

Between:

``` text
Rank
```

and:

``` text
Reserve
```

the world can change.

Therefore:

> **Reservation remains the authoritative concurrency boundary.**

The Ranking Engine must not attempt to solve reservation races.

------------------------------------------------------------------------

# 47. ETA Evolution

The ranking architecture is designed to evolve from:

``` text
Distance
```

toward:

``` text
ETA
```

and eventually:

``` text
Predicted ETA
```

Potential future flow:

``` text
Candidate
   │
   ▼
Travel Provider
   │
   ▼
ETA
   │
   ▼
ETA Normalizer
   │
   ▼
Scorer
```

The existing Ranking Engine should not be tightly coupled to one routing
vendor.

------------------------------------------------------------------------

# 48. Demand-Aware Ranking

The future architecture may include demand-aware signals.

Conceptually:

``` text
Cell Demand
     +
Cell Supply
     │
     ▼
Demand Feature
     │
     ▼
Ranking
```

The current Ranking Engine should not introduce demand infrastructure
until the demand/supply subsystem actually exists.

------------------------------------------------------------------------

# 49. Acceptance Prediction

A future ML model may provide:

``` text
P(driver accepts offer)
```

This can become a ranking feature.

Conceptually:

``` text
Driver
  │
  ▼
Acceptance Model
  │
  ▼
Acceptance Probability
  │
  ▼
Ranking Features
```

This should be introduced behind a feature/model boundary rather than
embedded directly in the scorer.

------------------------------------------------------------------------

# 50. Ranking Pipeline

The intended long-term ranking pipeline is:

``` text
Candidate
    │
    ▼
Feature Extraction
    │
    ├── ETA
    ├── Quality
    ├── Fairness
    ├── Demand
    └── Future Signals
    │
    ▼
Normalization
    │
    ▼
Weighted Scoring
    │
    ▼
Candidate Score
```

Only currently supported signals should be implemented.

------------------------------------------------------------------------

# 51. Performance Requirements

Ranking runs for every candidate reaching the ranking stage.

Therefore:

``` text
N candidates
×
ranking cost
```

can become significant.

The ranking implementation should therefore:

-   avoid unnecessary network calls,
-   reuse already-loaded driver data,
-   perform cheap calculations locally,
-   avoid repeated configuration parsing,
-   avoid repeated object construction.

------------------------------------------------------------------------

# 52. No Per-Candidate Infrastructure Calls Without Need

Avoid:

``` text
for candidate:
    call external service
    calculate score
```

unless the feature genuinely requires an external call and there is no
suitable batch/cached alternative.

For expensive routing/ETA providers, the architecture should eventually
support batching or controlled concurrency.

------------------------------------------------------------------------

# 53. Ranking Metrics

Useful ranking metrics include:

``` text
ranking_duration_seconds

candidates_ranked_total

ranking_errors_total
```

Additional metrics can include:

``` text
average_score

score_distribution

eta_distribution
```

only when they provide operational value.

------------------------------------------------------------------------

# 54. Tracing

Ranking traces should allow an operator to understand ranking latency.

Useful attributes include:

``` text
candidate_count

ranked_candidates

ranking_duration
```

Per-candidate traces should be avoided by default because
high-cardinality tracing can become expensive.

# 56. Ranking Test Invariants

Important invariants include:

## Better ETA should improve ranking

When all other features are equal:

``` text
lower ETA
    ↓
higher score
```

------------------------------------------------------------------------

## Better quality should improve ranking

When all other features are equal:

``` text
higher quality
    ↓
higher score
```

------------------------------------------------------------------------

## Fairness should remain bounded

A very long idle period must not completely dominate other signals
unless explicitly configured to do so.

------------------------------------------------------------------------

## Configuration must affect ranking

Changing configured weights should change the resulting score
accordingly.

# 57. Common Implementation Mistakes

## Mistake 1 --- Hard-coded weights

Incorrect:

``` go
score := eta*0.45 + quality*0.25
```

Correct:

``` go
score := eta*s.cfg.ETAWeight +
         quality*s.cfg.QualityWeight
```

------------------------------------------------------------------------

## Mistake 2 --- Scorer loading data

Incorrect:

``` text
Scorer
   ↓
Redis
```

Correct:

``` text
Feature Extractor
   ↓
Features
   ↓
Scorer
```

------------------------------------------------------------------------

## Mistake 3 --- Ranking unavailable drivers

Filtering should happen before ranking.

------------------------------------------------------------------------

## Mistake 4 --- Distance treated as ETA

Distance and ETA are different signals.

------------------------------------------------------------------------

## Mistake 5 --- Fairness dominating everything

Fairness should be a bounded contribution.

------------------------------------------------------------------------

## Mistake 6 --- Ranking mutating driver state

Ranking should be side-effect free with respect to driver operational
state.

------------------------------------------------------------------------

## Mistake 7 --- Silent fallback on ranking failure

Do not hide real ranking errors behind arbitrary scores.

## Rule 1 --- Configuration First

Do not hard-code ranking weights or business thresholds.

## Rule 11 --- Preserve Dispatch Strategy Context

Do not assume that:

``` text
Smart Stand Dispatch = stand-only candidates
```

The Ranking Engine must preserve the distinction between:

``` text
Preferred Stand
Broader Eligible Candidates
Cross-Location Candidates
```

Do not reject a candidate solely because the candidate is outside a stand
or belongs to another nearby location when the upstream discovery flow
has already determined that the candidate is eligible.

------------------------------------------------------------------------

## Rule 12 --- Do Not Convert Strategy Semantics Into Arbitrary Weights

Do not introduce a generic `StandWeight`, `LocationWeight`, or similar
score component merely to represent Smart Stand Dispatch.

Stand preference and queue semantics are strategy rules. Only represent
them as numerical ranking features when the business rules explicitly
require that behaviour.

------------------------------------------------------------------------

## Rule 10 --- Preserve Feature Separation


Do not move quality calculations into the scorer if they belong in
feature extraction/calculation.

------------------------------------------------------------------------

## Rule 12 --- Preserve Scorer Simplicity

The scorer combines features.

It should not become an infrastructure orchestrator.

------------------------------------------------------------------------

## Rule 10 --- Preserve Ranker Boundary

The Candidate Pipeline should depend on `Ranker`, not a concrete
implementation.

------------------------------------------------------------------------

## Rule 11 --- Preserve Candidate Ownership

Store ranking output in candidate metadata.

Do not mutate the driver domain model for ranking-only data.

------------------------------------------------------------------------

## Rule 12 --- Avoid Premature ML

Do not add ML prediction merely because the architecture supports it.

------------------------------------------------------------------------

## Rule 10 --- Avoid Premature Routing

Do not add a production routing provider without a concrete requirement,
contract, and performance plan.

------------------------------------------------------------------------

## Rule 11 --- Do Not Overengineer Normalization

Introduce normalization components only when they represent a real
reusable boundary.

A small deterministic calculation can remain inside its appropriate
calculator.

------------------------------------------------------------------------

## Rule 12 --- Preserve Testable Determinism

Ranking should be deterministic for the same inputs unless a deliberate
probabilistic model is introduced.

# 67. Relationship With Geo Engine

The Geo Engine supplies geographic/travel information.

Ranking consumes travel features.

``` text
Geo Engine
   │
   ├── Driver proximity
   ├── Stand radius context
   ├── Nearby location discovery
   └── Travel / ETA information
             │

      Feature Extraction
             │
             ▼
```

The Geo Engine does not decide the effective dispatch strategy.

Stand radius detection and nearby-location discovery are discovery
responsibilities; their resulting context may be passed downstream to
dispatch and ranking.

This keeps spatial infrastructure separate from score policy.

# 68. Relationship With Reliability

Ranking should remain stateless with respect to dispatch ownership.

If a ranking request fails:

``` text
No reservation occurred
```

so no ranking-specific rollback is required.

The transactional/concurrency boundary remains in Matching and
reservation.

# 69. Final Summary

The Ranking Engine is the decision-support subsystem that converts
eligible candidates into comparable scores.

Its architecture is:

``` text
Candidate
    │
    ▼
Feature Extraction
    │
    ├── Travel
    ├── Quality
    └── Fairness
    │
    ▼
Scoring
    │
    ▼
Candidate Score
    │
    ▼
Heap
```

The most important architectural rules are:

1.  **Do not hard-code ranking weights.**
2.  **Keep feature calculation separate from score combination.**
3.  **Keep infrastructure access outside the scorer.**
4.  **Keep ranking independent from reservation.**
5.  **Store scores on candidates, not drivers.**
6.  **Normalize features before combining them.**
7.  **Prefer ETA over raw distance as travel data matures.**
8.  **Add future ranking signals only when their supporting data and
    business rules exist.**
9.  **Keep the implementation simple until real requirements justify
    additional complexity.**
10. **Preserve the existing Ranker → Feature Extractor → Scorer
    boundaries.**
11. **Do not resolve hierarchical dispatch configuration inside the
    Ranking Engine.**
12. **Do not treat Smart Stand Dispatch as stand-exclusive.**
13. **Do not treat dispatch strategy as a hard candidate-location
    boundary.**
14. **Preserve strategy-relevant candidate context through the ranking
    flow.**
15. **Do not replace stand queue semantics with arbitrary numerical
    weighting.**
16. **Keep strategy execution, candidate discovery, ranking, and
    reservation as separate responsibilities.**

The result is a ranking subsystem that is production-oriented today
while leaving a clean path toward ETA-aware, demand-aware, and
eventually ML-assisted dispatch without forcing premature complexity
into the current codebase.
