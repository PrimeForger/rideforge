# RideForge Candidate Pipeline Architecture

> **Important:** This document is the detailed candidate-pipeline architecture. `02-architecture/4.CANDIDATE_PIPELINE.md` describes the higher-level pipeline contract; both documents must remain behaviorally consistent.

> **Document:** `docs/02-architecture/9.CANDIDATE_PIPELINE_ARCHITECTURE.md`  
> **Status:** Active architecture documentation  
> **Scope:** Candidate representation, collection, iteration, enrichment, filtering, ranking handoff, pipeline stages, candidate state, batch loading, and composition  
> **Audience:** Backend developers, architects, reviewers, operators, and AI coding agents

---

# 1. Purpose

The Candidate Pipeline transforms candidates produced by discovery into an ordered set of dispatch-ready candidates.

The pipeline operates **after the effective dispatch strategy has been resolved**. It may consume strategy and discovery context, but it must not resolve the configuration hierarchy itself.

Its responsibility is:

```text
Resolved Dispatch Context
        │
        ▼
Discovered Candidate IDs
        │
        ▼
Candidate Objects
        │
        ▼
Enrichment
        │
        ▼
Validation
        │
        ▼
Eligibility / Filtering
        │
        ▼
Strategy-Specific Candidate Context
        │
        ▼
Ranking
        │
        ▼
Ordered Candidate Source
```

The pipeline does not:

```text
Resolve State → District → Town → Stand → Ride-level configuration
Perform geographic discovery
Create geographic expansion policy
Reserve drivers
Create offers
```

The pipeline may preserve and expose discovery/strategy context needed by downstream prioritization and ranking.

---

# 2. Core Principle

The Candidate Pipeline follows:

> **Prepare candidates for dispatch without claiming ownership of them.**

The pipeline may determine:

```text
Is this candidate valid?
Is this candidate eligible?
How should this candidate be ranked?
```

It must not determine:

```text
Can I reserve this driver?
Has this driver been finally acquired by this ride?
```

Those decisions belong to the reservation/dispatch boundary.

---

# 3. Pipeline Boundary

The high-level architecture is:

```text
Candidate Discovery
       │
       ▼
Candidate Pipeline
       │
       ├── Enrichment
       ├── Validation
       ├── Filters
       ├── Ranking
       └── Ordering
       │
       ▼
Matching Engine
       │
       ▼
Reservation
```

---

# 3A. Dispatch Strategy Context

The Candidate Pipeline receives the **effective dispatch strategy** from the dispatch/configuration layer.

The separation is:

```text
Configuration Hierarchy
        │
        ▼
Dispatch Strategy Resolution
        │
        ▼
Effective Dispatch Strategy
        │
        ▼
Candidate Discovery
        │
        ▼
Candidate Pipeline
        │
        ▼
Strategy-Specific Prioritization / Ranking
```

The pipeline must not independently walk the configuration hierarchy.

The effective strategy may be:

```text
SMART_STAND_DISPATCH
SMART_DISPATCH
```

AI-assisted ranking may be applied within the resolved strategy when configured, but AI-assisted dispatch is not a third primary dispatch strategy.

---

# 3B. Smart Stand Dispatch Candidate Semantics

For **Smart Stand Dispatch**, stand membership is a **preference/context**, not an exclusive candidate boundary.

When the rider is inside a configured stand radius:

```text
Preferred Stand
      │
      ▼
Eligible Stand Candidates
      │
      ▼
Stand Queue / Ordering Context
```

If the preferred stand cannot provide a suitable driver, the candidate flow may include:

```text
Drivers outside the preferred stand
Drivers at nearby stands
Non-stand drivers
Drivers from nearby locations
```

provided they are otherwise eligible.

When the rider is outside all configured stand radii, Smart Stand Dispatch does not restrict candidates to auto-stand drivers.

Therefore:

```text
Inside Stand Radius
    ≠
Stand-only Candidate Pool
```

---

# 3C. Smart Dispatch Candidate Semantics

For **Smart Dispatch**, candidate processing is stand-agnostic.

A candidate may be:

```text
At an auto stand
Outside an auto stand
Associated with another nearby location
```

and stand membership does not create a dispatch preference merely because the driver is at a stand.

The normal candidate factors remain applicable:

```text
Eligibility
Availability
Distance
ETA
Matching / Ranking Factors
Operational Constraints
```

---

# 3D. Cross-Location Candidate Semantics

Candidate discovery may expand beyond the ride's originating location when the configured dispatch flow requires it.

A candidate from another nearby location is **not automatically rejected** because:

```text
candidate.location != ride.origin.location
```

Instead, candidate processing must preserve relevant context such as:

```text
Candidate Location
Candidate Location Strategy
Stand Membership
Relevant Stand
Queue Position
Discovery Source
Distance
ETA
```

This allows downstream prioritization to respect the candidate's local dispatch context.

For example:

```text
Ride Origin: Location A
Location A: Smart Dispatch

Candidate:
Location B
Location B: Smart Stand Dispatch
At Stand B1
2 km / 5 min ETA
```

The candidate can still be considered if discovery and hard eligibility rules permit it.

The fact that Location B uses Smart Stand Dispatch does not make the candidate invalid merely because the ride originated in Location A.

---

# 3E. Candidate Pipeline Responsibility Boundary

The Candidate Pipeline owns:

```text
Candidate representation
Candidate enrichment
Candidate validation
Candidate eligibility filters
Candidate context preservation
Strategy-aware preparation
Ranking handoff
Candidate ordering
```

It does not own:

```text
Dispatch strategy resolution
Geographic search
Location expansion policy
Final reservation
Offer creation
```

This boundary prevents the pipeline from becoming a second dispatch engine.

---

# 4. Candidate Discovery vs Candidate Pipeline

Candidate discovery answers:

> **Which drivers are geographically worth considering?**

The candidate pipeline answers:

> **Which discovered drivers are suitable for dispatch and in what order, given the resolved strategy context?**

This distinction is important.

Discovery owns geographic discovery and expansion.

The pipeline owns candidate processing and eligibility.

Strategy resolution happens before the pipeline.

The pipeline must not perform spatial search or independently resolve configuration inheritance.

---

# 5. Candidate Representation

The candidate model contains dispatch-specific information.

Conceptually:

```text
Candidate
├── ID
├── State
├── Driver
├── Dispatch Context
│    ├── Candidate Location
│    ├── Candidate Location Strategy
│    ├── Stand Membership
│    ├── Relevant Stand
│    ├── Queue Position
│    └── Discovery Source
└── Metadata
     └── Score
```

The candidate is not a replacement for the domain `Driver`.

It is a dispatch representation of a driver during matching.

---

# 6. Candidate ID

Every candidate has a driver identifier.

The identifier is the stable link between:

```text
Candidate
     │
     ▼
Driver
```

The pipeline can initially operate using IDs and enrich the candidate with driver data when required.

---

# 7. Candidate State

Candidate state represents pipeline-level processing state.

Conceptually:

```text
DISCOVERED
    │
    ▼
ENRICHED
    │
    ▼
ELIGIBLE / REJECTED
    │
    ▼
RANKED
```

The exact state model must remain aligned with the current candidate package.

State should describe candidate processing, not driver lifecycle.

---

# 8. Driver State vs Candidate State

These are different concepts.

### Driver state

Examples:

```text
ONLINE
OFFLINE
RESERVED
```

### Candidate state

Examples:

```text
DISCOVERED
FILTERED
RANKED
```

Do not introduce driver lifecycle semantics into candidate state.

---

# 9. Candidate Collection

The candidate collection owns the candidate set flowing through the pipeline.

Conceptually:

```text
Collection
├── Candidate
├── Candidate
├── Candidate
└── ...
```

The collection provides controlled operations such as:

```text
Add
Len
Iterator
FindByID
```

The internal storage remains encapsulated.

---

# 10. Encapsulation

Pipeline consumers should not access collection internals directly.

Incorrect:

```go
collection.items
```

Preferred:

```go
collection.Iterator()
collection.Len()
collection.FindByID(...)
```

This allows the collection implementation to evolve without breaking callers.

---

# 11. Candidate Factory

Candidate creation is centralized through candidate constructors.

Conceptually:

```text
Driver ID
   │
   ▼
candidate.New(...)
   │
   ▼
Candidate
```

For multiple IDs:

```text
[]DriverID
     │
     ▼
NewCollectionFromIDs(...)
```

This avoids duplicating initialization logic throughout the application.

---

# 12. Candidate Iterator

Candidate iteration is abstracted.

Conceptually:

```text
Candidate Source
      │
      ▼
Next()
      │
      ├── Candidate
      │
      └── false → exhausted
```

This prevents consumers from depending on the underlying collection representation.

---

# 13. Streaming Direction

The architecture is compatible with streaming candidate processing.

The intended conceptual model is:

```text
Candidate
   ↓
Process
   ↓
Next Candidate
```

rather than requiring every future implementation to materialize every intermediate result.

The current collection/iterator implementation provides the foundation without prematurely introducing a complex streaming framework.

---

# 14. Pipeline Interface

The pipeline exposes one orchestration boundary:

```text
Execute(
    context,
    pipeline context,
    candidates
)
```

The caller does not need to know the internal stage sequence.

# 15. Pipeline Stage

Each stage implements a common execution contract.

Conceptually:

```text
Stage
 └── Execute(...)
```

This allows stages to be:

- added,
- removed,
- reordered,
- tested independently.

# 16. Default Pipeline

The default pipeline composes the currently required stages.

Conceptually:

```text
New(
    Driver Loader,
    Validation Filter,
    Duplicate Filter,
    Availability Filter,
    Already Offered Filter,
    Ranking Stage,
    Heap Builder,
)
```

Composition belongs in bootstrap/builders rather than inside individual stages.

# 18. Stage Ordering

Stage order matters.

The pipeline should perform inexpensive rejection before expensive ranking where possible.

Preferred conceptual order:

```text
Load
  ↓
Validate
  ↓
Remove duplicates
  ↓
Check availability
  ↓
Check already-offered
  ↓
Rank
  ↓
Build ordering structure
```

Do not reorder stages without considering their cost and semantic dependencies.

---

# 19. Driver Batch Loading

Candidate discovery normally produces IDs.

The driver loader converts those IDs into driver objects using a batch data source.

Conceptually:

```text
Candidate IDs
      │
      ▼
BatchDataSource
      │
      ▼
[]Driver
      │
      ▼
Attach to Candidates
```

This avoids one backend request per candidate.

---

# 20. Batch Loading Principle

Avoid:

```text
Candidate 1 → Redis
Candidate 2 → Redis
Candidate 3 → Redis
...
```

Prefer:

```text
Candidate IDs
      │
      ▼
One batch lookup
      │
      ▼
Driver data
```

This is one of the primary performance properties of the pipeline.

---

# 21. Batch Data Source

The pipeline depends on an abstraction similar to:

```text
LoadDrivers(driverIDs)
```

The pipeline does not need to know whether the implementation uses:

```text
Redis
PostgreSQL
another cache
```

The infrastructure adapter owns that detail.

---

# 22. Missing Driver Data

A candidate ID may fail to produce a driver object.

This can happen because:

- cache expiration,
- driver went offline,
- stale discovery result,
- cache inconsistency,
- data removal.

The pipeline must not create a fake driver object.

The candidate should remain ineligible for stages that require driver data.

---

# 23. Validation Filter

Validation verifies that the candidate contains the required data for further processing.

Typical validation checks include:

```text
Candidate ID valid
Driver data present
Required driver attributes available
```

Validation should reject malformed candidates early.

---

# 24. Duplicate Filter

Discovery or upstream components may produce duplicate driver IDs.

The duplicate filter ensures:

```text
Driver A
Driver A
Driver B
```

becomes:

```text
Driver A
Driver B
```

before expensive processing.

---

# 25. Why Duplicate Filtering Is Early

Duplicates create unnecessary work.

Without early filtering:

```text
Duplicate
   ↓
Load
   ↓
Filter
   ↓
Rank
```

The same driver may be processed multiple times.

Removing duplicates early reduces:

- memory,
- ranking work,
- reservation attempts,
- confusing metrics.

---

# 26. Availability Filter

The availability filter removes drivers that are not currently eligible according to the available realtime driver state.

Conceptually:

```text
Candidate
   │
   ▼
Available?
   │
   ├── Yes → Continue
   └── No  → Reject
```

This is a pre-selection filter.

It is not a replacement for final reservation.

---

# 27. Availability Is Not Ownership

A driver can pass:

```text
Availability Filter
```

and still fail:

```text
Reservation
```

because another worker may reserve the driver between filtering and selection.

Therefore:

```text
Filter = eligibility snapshot
Reservation = authoritative concurrency decision
```

---

# 28. Already Offered Filter

The already-offered filter prevents the same ride from repeatedly considering drivers that have already received an offer.

Conceptually:

```text
Candidate
   │
   ▼
Already offered for ride?
   │
   ├── Yes → Reject
   └── No  → Continue
```

This is an important protection against repeated targeting.

---

# 29. Offered Driver Provider

The already-offered stage depends on a provider that can retrieve drivers already associated with the ride's active offer history.

Conceptually:

```text
Ride ID
   │
   ▼
OfferedDriverProvider
   │
   ▼
Set of Driver IDs
```

The filter does not need to know whether the provider is backed by Redis or another implementation.

---

# 30. Ranking Stage

After filtering, eligible candidates are passed to the ranking engine together with the relevant dispatch context.

Conceptually:

```text
Eligible Candidates
      │
      ├── Resolved Dispatch Strategy
      ├── Candidate Location Context
      ├── Stand Context
      ├── Queue Context
      ├── Distance / ETA
      │
      ▼
Feature Extraction
      │
      ▼
Strategy-Aware Score / Ordering
      │
      ▼
Candidate Metadata
```

The ranking stage attaches ranking information to candidates.

It does not reserve them.

For Smart Stand Dispatch, stand preference and queue semantics must remain consistent with the business rules. Do not automatically convert stand preference into a generic numeric weight unless the authoritative ranking/business design explicitly defines that behaviour.

For Smart Dispatch, stand membership must not receive an implicit preference merely because a driver is at a stand.

---

# 31. Ranking Boundary

The pipeline should depend on the ranking interface rather than concrete scoring implementations.

Conceptually:

```text
RankingStage
      │
      ▼
Ranker
      │
      ▼
Score
```

This allows ranking strategies to evolve without changing pipeline orchestration.

---

# 32. Candidate Metadata

Candidate metadata contains dispatch-specific ranking information.

At minimum:

```text
Score
```

Additional metadata may be introduced only when required by downstream pipeline or dispatch behaviour.

Avoid turning metadata into a copy of the entire driver record.

---

# 33. Score Ownership

The ranking engine owns score calculation.

The candidate pipeline owns attaching the result to the candidate.

The dispatch engine consumes the resulting order.

Responsibilities:

```text
Ranking Engine
    → Calculate

Candidate Pipeline
    → Attach

Dispatch Engine
    → Consume
```

---

# 34. Heap Builder

The heap builder converts ranked candidates into an efficient ordered source.

Conceptually:

```text
Ranked Candidates
      │
      ▼
Max Heap
      │
      ▼
Highest Score First
```

The heap is an implementation detail of candidate ordering.

---

# 35. Heap Semantics

The heap should return the candidate with the highest ranking score first.

Conceptually:

```text
Score 0.92
Score 0.81
Score 0.74
Score 0.61
```

consumption becomes:

```text
0.92
 ↓
0.81
 ↓
0.74
 ↓
0.61
```

---

# 36. Candidate Source

The matching engine consumes a candidate source rather than depending directly on heap internals.

Conceptually:

```text
CandidateSource
      │
      ▼
Next()
```

The current heap implementation can provide that source.

Future implementations can provide another ordered source without changing the dispatch orchestration contract.

---

Conceptually:

```text
Pipeline Context
├── Ride ID
├── Pickup Location
├── Matching Attempt
├── Effective Dispatch Strategy
├── Origin Location
└── Result
```

The context should contain information required by multiple stages or for pipeline-level results.

# 38. Pipeline Result

The result records useful pipeline-level information such as:

```text
Loaded Candidates
Filtered Candidates
Ranked Candidates
Candidate Source
```

The exact fields must remain aligned with the current implementation.

---

# 39. Pipeline Metrics

Pipeline result information supports matching observability.

Useful measurements include:

```text
loaded_candidates
filtered_candidates
ranked_candidates
offered_driver_count
```

Do not create a metric for every individual candidate.

# 40. Stage Independence

Each stage should own one clear transformation or validation responsibility.

Good:

```text
AvailabilityFilter
```

Less desirable:

```text
AvailabilityAndRankingAndOfferFilter
```

A stage may perform multiple closely related operations only when separating them would add unnecessary complexity.

---

# 41. Stage Failure

A stage may return an error when its dependency or required operation fails.

Example:

```text
Driver Loader
      │
      ▼
Redis failure
      │
      ▼
Pipeline Error
```

The pipeline should stop rather than silently continue with incomplete candidate data when correctness depends on the failed operation.

---

# 42. Filter Rejection vs Stage Error

These must remain distinct.

### Rejection

```text
Candidate is invalid/ineligible
```

This is normal pipeline behaviour.

### Error

```text
Pipeline cannot determine eligibility correctly
```

This should propagate to the caller.

# 44. Performance Model

The pipeline should optimize for:

```text
Low network round trips
Low repeated work
Early inexpensive rejection
Batch data access
Bounded candidate processing
Efficient ordered selection
```

The pipeline must not perform expensive operations before cheap filters unless there is a semantic reason.

---

# 45. Candidate Count Boundaries

Candidate discovery controls the geographic breadth and candidate expansion policy.

The pipeline should respect the candidate set it receives.

Do not introduce another arbitrary geographic expansion mechanism inside the pipeline.

If discovery has already expanded from the originating location to nearby locations, the pipeline must not discard those candidates merely because their source location differs from the ride origin.

The responsibilities remain:

```text
Discovery
→ Spatial breadth and candidate expansion

Pipeline
→ Candidate enrichment, eligibility, context, and ordering

Ranking
→ Strategy-specific prioritization / scoring

Dispatch
→ Reservation and offer execution
```

---

# 46. Memory Behaviour

The pipeline should avoid unnecessary copies.

Preferred:

```text
Candidate Collection
      │
      ▼
Enrich existing candidates
      │
      ▼
Filter existing candidates
      │
      ▼
Rank existing candidates
```

Avoid repeatedly constructing entire new collections unless required by semantics.

---

# 47. Streaming Compatibility

The current implementation may use a collection because ranking and heap construction need a bounded candidate set.

The architecture remains compatible with future streaming improvements.

Do not introduce a complex streaming abstraction merely to claim streaming support.

The existing iterator/source boundary is sufficient for incremental evolution.

---

# 48. Pipeline Composition

Pipeline composition should occur in a builder/bootstrap layer.

Conceptually:

```text
Bootstrap
    │
    ▼
BuildCandidatePipeline(...)
    │
    ├── Driver Loader
    ├── Validation
    ├── Duplicate
    ├── Availability
    ├── Already Offered
    ├── Ranking
    └── Heap
```

This keeps dependency wiring out of stage implementations.

---

# 49. Multiple Data Providers

Some stages may require different provider interfaces.

For example:

```text
BatchDataSource
    └── LoadDrivers

OfferedDriverProvider
    └── GetOfferedDrivers
```

Even if the same concrete Redis cache implements both, the stage should depend on the smallest interface it actually needs.

This preserves interface segregation.

---

# 50. Why Interfaces Are Separate

Do not combine:

```text
LoadDrivers
GetOfferedDrivers
GetLocation
GetHeartbeat
GetConnection
...
```

into one giant pipeline dependency.

Separate interfaces make stages:

- easier to test,
- easier to reason about,
- less coupled,
- easier to replace.

---

# 51. Concrete Redis Cache

The Redis driver cache may implement multiple stage-facing interfaces.

Conceptually:

```text
RedisDriverCache
      │
      ├── BatchDataSource
      ├── OfferedDriverProvider
      └── other application interfaces
```

This is acceptable.

The stage should still depend on the smallest relevant interface.

---

# 52. Candidate Pipeline and Reservation

Reservation must not be a pipeline stage.

The pipeline answers:

```text
Who should be considered first?
```

The dispatch engine answers:

```text
Who can I reserve now?
```

This separation is essential for concurrency correctness.

---

# 53. Candidate Pipeline and Offers

Offer creation must not be a pipeline stage.

Avoid:

```text
Ranking
  ↓
Reserve
  ↓
Offer
```

inside the pipeline.

Preferred:

```text
Pipeline
  ↓
Ranked candidates
  ↓
Dispatch Engine
  ↓
Reservation
  ↓
Offer
```

---

# 54. Candidate Pipeline and Geo

The pipeline should not perform:

```text
H3 lookup
Redis GEO lookup
Grid expansion
Ring expansion
```

Those belong to candidate discovery/refinement.

---

# 55. Candidate Pipeline and Retry

The pipeline should not decide:

```text
Radius
Retry Count
Batch Size
Timeout
```

Those belong to dispatch/retry policy.

---

# 56. Candidate Pipeline and Ranking Policy

The pipeline invokes the ranker.

It should not embed ranking weights or business scoring formulas.

For example, avoid:

```go
score := distance * 0.5 + rating * 0.5
```

inside a pipeline stage.

The Ranking Engine owns this behaviour.

---

The full lifecycle is:

```text

    │
    ▼
Created
    │
    ▼
Enriched
    │
    ▼
Validated
    │
    ▼
Filtered
    │
    ▼
Ranked
    │
    ▼
Selected
    │
    ▼
Reserved
    │
    ▼

```

The Candidate Pipeline owns only the middle portion:

```text
Discovered
   ↓
Enriched
   ↓
Validated
   ↓
Filtered
   ↓
Ranked
```

Dispatch owns:

```text
Selected
   ↓
Reserved
   ↓
Offered
```

# 66. Common Implementation Mistakes

## Mistake 1 — Accessing Collection Internals

Do not access:

```go
collection.items
```

outside the candidate package.

Use the collection API.

---

## Mistake 2 — One Redis Call Per Candidate

Use batch loading.

---

## Mistake 3 — Reserving in a Filter

Filtering and reservation are different responsibilities.

---

## Mistake 4 — Ranking Inside Availability Filter

Keep ranking separate.

---

## Mistake 5 — Hard-Coding Ranking Weights

Weights belong to ranking configuration/scoring.

---

## Mistake 6 — Performing Geo Search in the Pipeline

Geo discovery belongs upstream.

---

## Mistake 7 — Adding Retry Logic to Stages

Retry belongs to the appropriate application/infrastructure boundary.

---

## Mistake 8 — Creating Huge Generic Stage Frameworks

The current `Stage` interface is sufficient.

---

## Mistake 9 — Rebuilding Candidate Collections Between Every Stage

Prefer modifying/processing the existing collection when safe.

---

## Mistake 10 — Treating Filter Rejection as an Error

A rejected candidate is normal.

---

## Rule 1 — Preserve Stage Boundaries

Do not move geo, reservation, offer, or retry logic into pipeline stages.

---

## Rule 2 — Use Existing Collection APIs

Do not access private collection fields from outside the candidate package.

---

## Rule 3 — Prefer Batch Operations

Do not introduce per-candidate network calls when an existing batch boundary is available.

---

## Rule 4 — Keep Interfaces Narrow

Depend on the smallest provider interface required by a stage.

---

## Rule 5 — Preserve Ordering Semantics

Do not reorder stages without checking:

```text
Correctness
Performance
Dependency requirements
```

---

## Rule 6 — Do Not Duplicate Ranking Logic

Ranking formulas belong to the Ranking Engine.

---

## Rule 7 — Do Not Reserve in the Pipeline

Reservation remains the dispatch concurrency boundary.

---

## Rule 8 — Avoid Speculative Streaming Infrastructure

The current collection and iterator abstraction is sufficient until measured workload requires more.

---

## Rule 9 — Reuse Existing Stages

Before creating a new filter or enrichment stage, inspect the current pipeline and verify that the behaviour does not already exist.

---

## Rule 10 — Update Documentation

Any architectural change to candidate processing must update this document and the relevant component documentation.

# 67A. Dispatch-Specific AI Agent Rules

Any AI coding agent modifying this pipeline must preserve the following rules:

1. **Do not implement Smart Stand Dispatch as stand-only.**
2. **Do not reject non-stand candidates solely because they are outside the preferred stand.**
3. **Do not reject cross-location candidates solely because their location differs from the ride origin.**
4. **Do not resolve hierarchical dispatch configuration inside the Candidate Pipeline.**
5. **Do not treat the candidate's source location as a hard dispatch boundary.**
6. **Do not treat Smart Dispatch and Smart Stand Dispatch as interchangeable strategies.**
7. **Do not introduce AI as a third primary dispatch strategy.**
8. **Do not silently switch the resolved strategy because a preferred stand has no suitable driver.**
9. **Do not move geographic expansion into pipeline stages.**
10. **Preserve stand, queue, location, and discovery context for downstream strategy-specific ranking.**
11. **Do not convert stand preference into a generic ranking score unless explicitly required by the authoritative business/ranking rules.**
12. **Hard eligibility, legal, safety, and availability constraints remain authoritative regardless of strategy.**

# 71. Final Architecture

The Candidate Pipeline is intentionally positioned between discovery and dispatch:

```text
                 Candidate Discovery
                         │
                         ▼
                 Candidate Collection
                         │
                         ▼
                  Batch Enrichment
                         │
                         ▼
                     Validation
                         │
                         ▼
                  Duplicate Filter
                         │
                         ▼
                Availability Filter
                         │
                         ▼
              Already Offered Filter
                         │
                         ▼
                      Ranking
                         │
                         ▼
                        Heap
                         │
                         ▼
                 Candidate Source
                         │
                         ▼
                  Matching Engine
                         │
                         ▼
                    Reservation
                         │
                         ▼
                       Offer
```

The core rules are:

1. **Configuration resolution determines the effective dispatch strategy before pipeline execution.**
2. **Discovery finds geographically relevant candidates and controls geographic expansion.**
3. **The pipeline determines candidate eligibility, preserves dispatch context, and prepares candidate ordering.**
4. **Smart Stand Dispatch is stand-preferred, not stand-exclusive.**
5. **Smart Dispatch is stand-agnostic.**
6. **Cross-location candidates remain eligible for consideration when discovery and hard constraints permit them.**
7. **Batch loading prevents per-candidate backend calls.**
8. **Cheap rejection should happen before expensive ranking where semantics allow it.**
9. **Availability is a snapshot, not ownership.**
10. **Reservation remains the authoritative concurrency boundary.**
11. **Ranking is delegated to the Ranking Engine.**
12. **Geo search and geographic expansion are delegated to Discovery/Geo components.**
13. **Retry and dispatch policy remain outside the pipeline.**
14. **Candidate collection internals remain encapsulated.**
15. **The pipeline must not independently resolve hierarchical configuration or silently change the resolved strategy.**
11. **Stages remain small and independently testable.**
12. **Existing stages and abstractions must be reused before introducing new ones.**
