# RideForge Candidate Pipeline

> **Document:** `docs/02-architecture/4.CANDIDATE_PIPELINE.md`\
> **Status:** Active architecture documentation\
> **Scope:** Candidate lifecycle, collection, iteration, enrichment,
> filtering, ranking, heap ordering, and pipeline composition\
> **Audience:** Backend developers, architects, reviewers, and AI coding
> agents

------------------------------------------------------------------------

# 1. Executive Summary

The Candidate Pipeline is the transformation layer between **candidate
discovery** and **driver offer selection**.

Discovery answers:

> Which driver IDs are geographically relevant?

The Candidate Pipeline answers:

> Which of those candidates are valid, enriched, and ranked well enough
> to be considered for an offer?

The pipeline is deliberately composed of independent stages.

``` text
Candidate IDs
     │
     ▼
Candidate Collection
     │
     ▼
Driver Enrichment
     │
     ▼
Validation
     │
     ▼
Duplicate Filtering
     │
     ▼
Availability Filtering
     │
     ▼
Already-Offered Filtering
     │
     ▼
Feature Extraction
     │
     ▼
Ranking
     │
     ▼
Heap
     │
     ▼
Ordered Candidate Source
     │
     ▼
Matching Engine
```

The pipeline does not reserve drivers and does not publish offers.

Those responsibilities remain in the Matching Engine.

------------------------------------------------------------------------

# 2. Purpose

The Candidate Pipeline exists to convert a raw spatial candidate set
into an ordered candidate source suitable for dispatch.

Its primary responsibilities are:

-   candidate enrichment,
-   candidate validation,
-   candidate filtering,
-   feature extraction,
-   candidate ranking,
-   score ordering.

The pipeline must remain independent of the final driver reservation and
offer workflow.

------------------------------------------------------------------------

# 3. Design Goals

## 3.1 Clear stage ownership

Each stage should have one responsibility.

For example:

``` text
Driver Loader
    =
Load driver information
```

``` text
Availability Filter
    =
Remove unavailable candidates
```

``` text
Ranking Stage
    =
Calculate candidate scores
```

No stage should silently take ownership of another stage's
responsibility.

------------------------------------------------------------------------

## 3.2 Composability

The pipeline should be constructed from independent stages.

Conceptually:

``` go
pipeline.New(
    stage1,
    stage2,
    stage3,
    stage4,
)
```

This allows the composition to evolve without rewriting the pipeline
executor.

------------------------------------------------------------------------

## 3.3 Bounded work

The pipeline should process only the candidate set produced by Discovery
and should avoid unnecessary per-candidate infrastructure calls.

Batch loading is preferred wherever possible.

------------------------------------------------------------------------

## 3.4 Low coupling

The pipeline should depend on contracts rather than concrete
infrastructure.

For example:

``` text
BatchDataSource
OfferedDriverProvider
Ranker
```

rather than direct Redis or PostgreSQL implementations.

------------------------------------------------------------------------

## 3.5 Debuggability

The pipeline context retains useful counters and state so that a
dispatch can be inspected without stepping through every implementation.

------------------------------------------------------------------------

# 4. Non-Goals

The Candidate Pipeline does not own:

-   dispatch strategy configuration resolution,
-   candidate discovery,
-   H3 traversal,
-   search radius decisions,
-   deciding whether a stand is the preferred discovery source,
-   retry policy,
-   driver reservation,
-   offer persistence,
-   offer publication,
-   driver response handling.

It may consume the resolved strategy and discovery context produced by
those upstream components.

These belong to other subsystems.

------------------------------------------------------------------------

# 5. Architectural Position

The Candidate Pipeline sits between Discovery and Matching.

Dispatch strategy resolution and candidate discovery occur before the
pipeline.

``` text
                         Dispatch
                            │
                            ▼
              Strategy Resolution
                            │
                            ▼
                    Discovery Engine
                            │
                            │ Candidates + Context
                            ▼
                 +----------------------+
                 | Candidate Pipeline   |
                 +----------------------+
                            │
                            │ Ranked Candidates
                            ▼
                    Matching Engine
                            │
                            ▼
                       Reservation
                            │
                            ▼
                          Offer
```

The Candidate Pipeline is a shared processing boundary, not a separate
dispatch strategy implementation.

------------------------------------------------------------------------


# 6. Dispatch Context Entering the Candidate Pipeline

The Candidate Pipeline operates **after dispatch strategy resolution and candidate discovery**.

It must receive the resolved dispatch context rather than resolving dispatch configuration itself.

Conceptually:

``` text
Ride Request
     │
     ▼
Dispatch Strategy Resolution
     │
     ▼
Candidate Discovery
     │
     │ candidates + dispatch context
     ▼
Candidate Pipeline
     │
     ▼
Strategy-specific prioritization / ranking
     │
     ▼
Matching Engine
```

The pipeline must not walk the configuration hierarchy such as:

``` text
State → District → Town → Rural Area → Stand → Ride
```

to determine the effective strategy.

That responsibility belongs to **Dispatch Strategy Resolution**.

The pipeline may consume strategy-related candidate metadata required by downstream prioritization.

------------------------------------------------------------------------

# 7. Candidate Context for Strategy-Aware Dispatch

Candidates may carry context produced by Discovery that is relevant to Smart Stand Dispatch and cross-location dispatch.

Examples include:

``` text
Origin Location
Candidate Location
Candidate Location / Configuration Context
Relevant Auto Stand
Stand Membership
Stand Distance
Stand Queue Position
Discovery Source
Discovery Scope / Expansion Stage
```

These values describe **candidate context**. They do not by themselves make a candidate eligible or ineligible.

The Candidate Pipeline should preserve this context rather than discarding it during collection, enrichment, or filtering.

------------------------------------------------------------------------

# 8. Candidate Pipeline and Dispatch Strategies

The Candidate Pipeline is shared by the supported dispatch strategies.

It does not implement two separate pipelines merely because the resolved strategy differs.

## Smart Dispatch

Smart Dispatch is stand-agnostic.

Candidates may be:

``` text
At an auto stand
Outside an auto stand
From the originating location
From a nearby location
```

Stand membership must not automatically increase or decrease eligibility.

## Smart Stand Dispatch

Smart Stand Dispatch is stand-preferred, not stand-exclusive.

When the rider is inside a configured stand radius, Discovery should prefer candidates from the relevant stand.

If suitable stand candidates are unavailable, Discovery may expand to:

``` text
Nearby stands
Non-stand drivers
Nearby locations
```

The Candidate Pipeline must not remove those fallback candidates merely because they are outside the preferred stand.

When the rider is outside all configured stand radii, candidates are processed without a stand-only restriction.

The pipeline processes the candidate set it receives and preserves the metadata required for downstream stand-aware prioritization.

------------------------------------------------------------------------

# 9. Cross-Location Candidate Handling

A candidate's location is not automatically a hard dispatch boundary.

For example:

``` text
Ride Origin
Location A
    │
    ▼
No suitable local candidates
    │
    ▼
Discovery expands
    │
    ▼
Location B candidates
```

Location B may use Smart Stand Dispatch while Location A uses Smart Dispatch.

The Candidate Pipeline must allow candidates from Location B to proceed through normal validation and filtering if they are otherwise eligible.

The pipeline must not apply:

``` text
Candidate Location != Ride Origin
    ↓
Reject
```

unless an explicit business, legal, service, or eligibility rule requires it.

------------------------------------------------------------------------

# 10. Strategy-Aware Prioritization Boundary

The Candidate Pipeline owns the execution point for ranking, but it does not own the business definition of every ranking strategy.

``` text
Candidate Pipeline
       │
       ▼
Strategy-aware Ranking Stage
       │
       ▼
Ranker
       │
       ├── Smart Dispatch ranking
       │
       └── Smart Stand Dispatch prioritization/ranking
```

For Smart Stand Dispatch, strategy-specific ranking may consume:

``` text
Preferred Stand
Stand Queue Position
Stand Membership
Distance
ETA
Eligibility
Other configured factors
```

The exact business ordering comes from the dispatch and matching rules.

The pipeline itself must not hard-code a generic rule such as:

``` text
Stand always wins
```

unless the corresponding business rule explicitly requires it.

------------------------------------------------------------------------

# 11. Candidate Pipeline Must Not Resolve Configuration

The following is outside the Candidate Pipeline:

``` text
Find ride configuration hierarchy
        ↓
Walk parent configuration
        ↓
Resolve Smart Dispatch / Smart Stand Dispatch
```

That process belongs to Dispatch Strategy Resolution.

The Candidate Pipeline receives the already-resolved strategy/context.

This prevents configuration logic from being duplicated in:

``` text
Discovery
Candidate Pipeline
Ranking
Matching
```

------------------------------------------------------------------------

# 12. Candidate Boundary Rules

The Candidate Pipeline must distinguish between:

``` text
Candidate Discovery Boundary
```

``` text
Candidate Eligibility
```

and:

``` text
Strategy-specific Preference
```

These are different concepts.

A driver being:

``` text
outside the preferred stand
```

does not automatically mean:

``` text
ineligible
```

A driver being:

``` text
from a nearby location
```

does not automatically mean:

``` text
ineligible
```

Eligibility must be determined by the applicable business, legal, operational, and driver-state rules.

Preference is applied separately.

------------------------------------------------------------------------

# 13. Core Pipeline Contract

The pipeline is represented by a small execution boundary.

Conceptually:

``` go
type Pipeline interface {
    Execute(
        ctx context.Context,
        pipelineCtx *Context,
        candidates *candidate.Collection,
    ) error
}
```

The pipeline executor is responsible only for running stages in order.

It should not contain stage-specific business logic.

------------------------------------------------------------------------

# 14. Pipeline Stage Contract

Every stage follows the same basic contract.

``` go
type Stage interface {
    Execute(
        ctx context.Context,
        pipelineCtx *Context,
        candidates *candidate.Collection,
    ) error
}
```

This creates a consistent extension point.

A stage may:

-   enrich candidates,
-   remove candidates,
-   modify candidate metadata,
-   calculate scores,
-   build ordering structures.

A stage should not modify unrelated application state unless that is
explicitly part of its responsibility.

------------------------------------------------------------------------

# 15. Default Pipeline

The current composition follows this general order:

``` text
Default Driver Loader
        │
        ▼
Validation Filter
        │
        ▼
Duplicate Filter
        │
        ▼
Availability Filter
        │
        ▼
Already Offered Filter
        │
        ▼
Ranking Stage
        │
        ▼
Heap Builder
```

The exact stage list is composed during bootstrap.

This is intentional.

The pipeline implementation does not decide which business stages exist.

------------------------------------------------------------------------

# 16. Why Stage Order Matters

The order is part of the architecture.

For example:

``` text
Load
  ↓
Validate
  ↓
Filter
  ↓
Rank
```

is preferable to:

``` text
Rank
  ↓
Load
  ↓
Filter
```

because expensive ranking work should not be performed for candidates
that are already invalid.

The pipeline should generally perform inexpensive rejection before
expensive enrichment or ranking.

------------------------------------------------------------------------

# 17. Candidate Model

A candidate represents a driver being considered for a ride.

Conceptually:

``` go
type Candidate struct {
    ID       uuid.UUID
    State    State
    Driver   *driver.Driver
    Metadata Metadata
}
```

The candidate begins primarily as an identity.

As it progresses through the pipeline, it becomes enriched.

`Metadata` may retain discovery/strategy context required downstream,
such as discovery source, candidate location, relevant stand, stand
membership, queue position, distance, or ETA.

------------------------------------------------------------------------

# 18. Candidate Lifecycle

A candidate generally progresses through these states:

``` text
Discovered + Context
    │
    ▼
Loaded
    │
    ▼
Validated
    │
    ▼
Filtered
    │
    ▼
Enriched
    │
    ▼
Strategy-aware Ranked
    │
    ▼
Ordered
```

Not every state needs to be represented as a separate enum value.

Discovery and strategy context should survive this lifecycle when it is
required by downstream prioritization.

The important concept is the lifecycle through the pipeline.

------------------------------------------------------------------------

# 19. Candidate Collection

The collection owns the candidate set being processed.

Conceptually:

``` go
type Collection struct {
    items []Candidate
}
```

It provides operations such as:

-   Add
-   Len
-   Items
-   Iterator
-   ForEach
-   FindByID
-   RemoveIf

The collection owns the candidate storage.

------------------------------------------------------------------------

# 20. Why Candidate Collection Exists

The collection prevents pipeline stages from passing raw slices
everywhere.

Instead of:

``` text
[]Candidate
```

the pipeline works with:

``` text
Candidate Collection
```

This gives the candidate subsystem one place to own candidate-specific
operations.

------------------------------------------------------------------------

# 21. Iterator

The candidate subsystem exposes an iterator contract.

Conceptually:

``` go
type Iterator interface {
    Next() (Candidate, bool)
}
```

The iterator allows stages to consume candidates without depending on
the collection's internal representation.

------------------------------------------------------------------------

# 22. Iterator Design

The current slice iterator is collection-backed.

Conceptually:

``` text
Collection
    │
    ▼
SliceIterator
    │
    ▼
Next()
```

The iterator currently returns candidate values.

This keeps the iteration contract simple.

------------------------------------------------------------------------

# 23. Why the Iterator Exists

The iterator creates a boundary between:

``` text
How candidates are stored
```

and:

``` text
How candidates are consumed
```

This gives the subsystem room to evolve its internal storage without
requiring every consumer to know about it.

However, the iterator should not be expanded into a complicated
streaming framework unless there is a concrete performance requirement.

------------------------------------------------------------------------

# 24. Candidate State

Candidate state represents the candidate's current pipeline status.

The state should remain lightweight.

The pipeline should not create a large state machine merely to represent
normal candidate processing.

------------------------------------------------------------------------

# 25. Candidate Metadata

Metadata contains pipeline-produced information that is not part of the
driver's domain entity.

Examples include:

``` text
Score
```

and other candidate-specific ranking information.

This separation is important.

Driver domain data belongs to:

``` text
driver.Driver
```

Dispatch candidate information belongs to:

``` text
candidate.Metadata
```

------------------------------------------------------------------------

# 26. Batch Driver Loading

The first major enrichment stage loads complete driver information.

The stage uses a batch source.

Conceptually:

``` go
type BatchDataSource interface {
    LoadDrivers(
        ctx context.Context,
        driverIDs []uuid.UUID,
    ) ([]*driver.Driver, error)
}
```

The stage first collects candidate IDs:

``` text
Candidate 1 ┐
Candidate 2 ├──► ID list
Candidate 3 ┘
```

and performs one batch load.

------------------------------------------------------------------------

# 27. Why Batch Loading Matters

Avoid:

``` text
Candidate 1 → Redis
Candidate 2 → Redis
Candidate 3 → Redis
Candidate 4 → Redis
```

Prefer:

``` text
Candidate IDs
      │
      ▼
One batch lookup
      │
      ▼
Driver records
```

This reduces network round trips and improves dispatch latency.

------------------------------------------------------------------------

# 28. Driver Loader Responsibilities

The Driver Loader should:

1.  Read candidate IDs.
2.  Request driver records from its source.
3.  Attach returned driver records to matching candidates.
4.  Update pipeline context counters.

It should not:

-   filter drivers,
-   rank drivers,
-   reserve drivers,
-   publish offers.

------------------------------------------------------------------------

# 29. Missing Driver Records

A discovered driver may no longer exist in the cache by the time the
pipeline executes.

The loader should not invent a driver record.

Candidates without a usable driver record must be removed or rejected by
the appropriate validation stage.

This is a normal consequence of real-time systems.

------------------------------------------------------------------------

# 30. Validation Filter

The validation filter protects later stages from malformed or incomplete
candidates.

Typical validation concerns include:

-   missing driver object,
-   invalid candidate identity,
-   invalid required driver data,
-   invalid coordinates where required.

Validation should remain deterministic and inexpensive.

------------------------------------------------------------------------

# 31. Duplicate Filter

The duplicate filter prevents the same driver from being processed more
than once.

Duplicates can appear because:

-   multiple spatial cells may reference the same driver,
-   discovery sources may overlap,
-   refinement may preserve overlapping identities.

The candidate pipeline should guarantee that ranking and offering do not
unnecessarily process duplicate driver identities.

------------------------------------------------------------------------

# 32. Availability Filter

The availability filter removes candidates that cannot currently
participate in dispatch.

Examples:

``` text
Offline
Busy
Reserved
Disconnected
```

The exact availability rules should remain driven by the current driver
state model and configuration.

The filter should not perform reservation.

------------------------------------------------------------------------

# 33. Already-Offered Filter

A driver that has already received an offer for the same ride should not
normally be offered again during the same matching flow unless an
explicit business rule allows it.

The filter uses an offered-driver provider boundary.

Conceptually:

``` go
type OfferedDriverProvider interface {
    GetOfferedDrivers(
        ctx context.Context,
        rideID uuid.UUID,
    ) (map[uuid.UUID]struct{}, error)
}
```

This keeps Redis/cache details outside the stage.

------------------------------------------------------------------------

# 34. Why Already-Offered Filtering Exists

Without this stage:

``` text
Attempt 1
    Driver A offered

Attempt 2
    Driver A discovered again
        ↓
    Driver A offered again
```

The filter prevents duplicate offers across retries.

------------------------------------------------------------------------

# 35. Filtering Philosophy

Filters should be:

-   deterministic,
-   independently testable,
-   cheap where possible,
-   explicit about what they reject.

A filter should not secretly perform ranking or reservation.

------------------------------------------------------------------------

# 36. Ranking Boundary

After candidates pass required filtering:

``` text
Valid Candidates
      │
      ▼
Ranking Stage
```

The Ranking Stage delegates actual ranking to a `Ranker`.

Conceptually:

``` go
type Ranker interface {
    Rank(
        ctx context.Context,
        pipelineCtx *pipeline.Context,
        candidate *candidate.Candidate,
    ) (candidate.Score, error)
}
```

------------------------------------------------------------------------

# 37. Ranking Stage Responsibilities

The Ranking Stage should:

1.  Iterate over candidates.
2.  Ask the ranker to calculate a score.
3.  Store the score in candidate metadata.
4.  Update ranking counters.

It should not implement ranking formulas itself.

------------------------------------------------------------------------

# 38. Feature Extraction

The ranker separates feature extraction from scoring.

Conceptually:

``` text
Candidate
   │
   ▼
Feature Extractor
   │
   ▼
Features
   │
   ▼
Scorer
   │
   ▼
Score
```

This separation allows ranking features and scoring formulas to evolve
independently.

------------------------------------------------------------------------

# 39. Travel Features

Travel-related information belongs to the ranking feature model.

Examples include:

``` text
DistanceKm
ETASec
```

The long-term architecture should allow distance-based calculation to
evolve into routing-aware ETA without changing the candidate pipeline
contract.

------------------------------------------------------------------------

# 40. Quality Features

Quality-related driver information may include:

``` text
Acceptance Rate
Cancellation Rate
Timeout Rate
Rating
Completed Trips
```

The quality calculation should be configuration-driven.

Weights should not be hard-coded inside calculators.

------------------------------------------------------------------------

# 41. Fairness Features

Fairness-related information includes driver idle time and related
dispatch fairness signals.

A typical input is:

``` text
LastAssignedAt
```

The fairness calculation belongs to ranking, not filtering.

------------------------------------------------------------------------

# 42. Score

The candidate score is represented separately from the driver domain
model.

Conceptually:

``` go
type Score struct {
    Value float64
}
```

The score belongs to the dispatch candidate.

It should not be written into the Driver domain entity.

------------------------------------------------------------------------

# 43. Score Ordering

After ranking, candidates need to be consumed from highest score to
lowest score.

The current design uses a heap.

``` text
Ranked Candidates
      │
      ▼
Heap Builder
      │
      ▼
Max Heap
      │
      ▼
Highest Score First
```

------------------------------------------------------------------------

# 44. Heap Responsibilities

The heap owns ordering.

It should:

-   accept candidate references,
-   order candidates by score,
-   return the highest-ranked candidate,
-   avoid implementing ranking logic.

The heap does not calculate scores.

------------------------------------------------------------------------

# 45. Pointer-Based Heap Candidates

The heap can hold candidate pointers.

Conceptually:

``` go
items []*candidate.Candidate
```

This is useful because the heap operates on the same candidate objects
that have already been enriched and ranked.

It avoids unnecessary copying of larger candidate structures.

The implementation must still maintain clear ownership and avoid
dangling references.

------------------------------------------------------------------------

# 46. Candidate Source

After heap construction, the matching workflow can consume candidates
through a source abstraction.

Conceptually:

``` go
type CandidateSource interface {
    Next() (*candidate.Candidate, bool)
}
```

The heap-backed source returns the next highest-ranked candidate.

------------------------------------------------------------------------

# 47. Why Candidate Source Exists

The Matching Engine should not need to know that candidates are stored
in a heap.

It needs only:

``` text
Next candidate
```

This creates a useful boundary:

``` text
Heap
  │
  ▼
CandidateSource
  │
  ▼
Matching Engine
```

------------------------------------------------------------------------

# 48. Pipeline Context

The pipeline context carries information shared across stages.

Conceptually:

``` text
Ride ID
Pickup Coordinates
Retry Attempt
Started At
Result
```

The context should contain only information needed by multiple stages or
required for pipeline observability.

It should not become a general-purpose application state container.

------------------------------------------------------------------------

# 49. Pipeline Result

The result contains pipeline-level state and candidate source
information.

Useful counters include:

``` text
LoadedCandidates
FilteredCandidates
RankedCandidates
```

These counters are valuable for:

-   debugging,
-   tracing,
-   metrics,
-   diagnosing candidate drop-off.

------------------------------------------------------------------------

# 50. Candidate Drop-Off

A useful diagnostic view is:

``` text
Discovered
    │
    ▼
Loaded
    │
    ▼
Validated
    │
    ▼
Available
    │
    ▼
Not Previously Offered
    │
    ▼
Ranked
```

If 100 drivers are discovered but only 2 reach ranking, pipeline
counters help identify where the candidates disappeared.

------------------------------------------------------------------------

# 51. Pipeline Execution

The default pipeline executor is intentionally simple.

Conceptually:

``` go
for _, stage := range p.stages {
    if err := stage.Execute(
        ctx,
        pipelineCtx,
        candidates,
    ); err != nil {
        return err
    }
}
```

The executor should not contain business logic.

Its only responsibility is ordered stage execution.

------------------------------------------------------------------------

# 52. Error Handling

A stage failure should normally stop pipeline execution.

``` text
Stage
  │
  ├── Success → next stage
  │
  └── Error → pipeline stops
```

This avoids silently ranking or offering partially invalid candidate
data.

------------------------------------------------------------------------

# 53. Reservation Boundary

Reservation occurs after the pipeline.

``` text
Candidate Pipeline
       │
       ▼
CandidateSource
       │
       ▼
Matching Engine
       │
       ▼
Driver Locker
```

The pipeline should never reserve drivers.

This is one of the most important boundaries in the architecture.

------------------------------------------------------------------------

# 54. Offer Boundary

Offers are also outside the pipeline.

``` text
Pipeline
   │
   ▼
Ranked Candidate
   │
   ▼
Reservation
   │
   ▼
Offer Event
```

This keeps the candidate-processing subsystem reusable.

------------------------------------------------------------------------

# 55. Current Composition

The current bootstrap composition is conceptually:

``` text
Candidate Pipeline
│
├── DefaultDriverLoader
├── ValidationFilter
├── DuplicateFilter
├── AvailabilityFilter
├── AlreadyOfferedFilter
├── RankingStage
└── HeapBuilder
```

The actual infrastructure implementations are injected from bootstrap.

------------------------------------------------------------------------

# 56. Dependency Direction

The Candidate Pipeline depends on contracts.

Example:

``` text
Candidate Pipeline
       │
       ├── BatchDataSource
       ├── OfferedDriverProvider
       └── Ranker
```

Infrastructure implements those contracts.

``` text
Redis Driver Cache
       │
       ├── BatchDataSource
       └── OfferedDriverProvider
```

The pipeline must not depend directly on Redis.

------------------------------------------------------------------------

# 57. Performance Considerations

The Candidate Pipeline is on the dispatch critical path.

Important performance rules:

## Batch external reads

Prefer one batch lookup over N individual lookups.

------------------------------------------------------------------------

## Filter early

Reject obviously invalid candidates before expensive ranking.

------------------------------------------------------------------------

## Avoid unnecessary copies

Use references where candidate mutation and ownership are clear.

------------------------------------------------------------------------

## Avoid unnecessary allocations

Pre-size candidate collections when the expected candidate count is
known.

------------------------------------------------------------------------

## Keep ranking deterministic and local

Ranking should not perform unnecessary network calls for each candidate.

------------------------------------------------------------------------

# 58. Streaming Considerations

The original long-term goal includes streaming candidates:

``` text
Candidate
   │
   ▼
Process
   │
   ▼
Next
```

The current candidate subsystem already has an iterator boundary.

However, the pipeline should not be rewritten into a complicated
streaming architecture merely to satisfy a roadmap item.

The current collection + iterator design is sufficient until actual
candidate-volume or latency measurements demonstrate a need for true
streaming.

------------------------------------------------------------------------

# 59. Memory Considerations

The pipeline currently operates on a bounded candidate collection.

Memory usage is primarily proportional to:

``` text
number of discovered candidates
+
driver data
+
heap entries
```

Candidate limits and search budgets provide natural bounds.

A future streaming implementation can be introduced if measurements
justify it.

------------------------------------------------------------------------

# 60. Observability

The pipeline should expose enough information to understand candidate
processing.

Useful measurements include:

``` text
Candidates discovered

Candidates loaded

Candidates filtered

Candidates ranked

Candidates offered

Pipeline duration

Ranking duration
```

Stage-specific metrics may be introduced when operational evidence shows
they are useful.

Do not create dozens of metrics merely for completeness.

------------------------------------------------------------------------

# 61. Tracing

A pipeline span should provide useful attributes such as:

``` text
ride.id

matching.attempt_count

loaded_candidates

filtered_candidates

ranked_candidates
```

Individual stages may create child spans if a stage becomes a meaningful
latency contributor.

------------------------------------------------------------------------

# 62. Testing Strategy

## Candidate Tests

Test:

-   candidate creation,
-   collection operations,
-   iterator behaviour,
-   lookup by ID,
-   removal.

------------------------------------------------------------------------

## Stage Tests

Each stage should be independently testable.

Examples:

``` text
Driver Loader
Validation Filter
Duplicate Filter
Availability Filter
Already Offered Filter
Ranking Stage
Heap Builder
```

------------------------------------------------------------------------

## Pipeline Tests

Test:

-   stage order,
-   successful execution,
-   failure propagation,
-   context propagation,
-   candidate mutation.

------------------------------------------------------------------------

## Integration Tests

Test the pipeline with real infrastructure where appropriate:

``` text
Redis
Driver Cache

```

The unit tests should not require infrastructure.

------------------------------------------------------------------------

# 63. Failure Scenarios

## Driver Cache Failure

If required enrichment fails:

``` text
Pipeline
   │
   ▼
Error
   │
   ▼
Matching fails safely
```

The system should not fabricate driver information.

------------------------------------------------------------------------

## Missing Driver

A missing driver should not reach ranking.

------------------------------------------------------------------------

## Ranking Failure

Ranking failure should stop the pipeline rather than producing an
unscored candidate.

------------------------------------------------------------------------

## Empty Candidate Set

An empty candidate set is a valid operational outcome.

The pipeline should complete without panic.

Matching decides what to do next.

------------------------------------------------------------------------

# 64. Candidate Collection Rules

The collection should remain the owner of candidate storage.

Other packages should not directly mutate its internal slice.

Prefer:

``` go
collection.Add(candidate)
```

over:

``` go
collection.items = append(...)
```

from outside the package.

This preserves encapsulation.

------------------------------------------------------------------------

# 65. Iterator Rules

Consumers should use the iterator contract instead of depending on
internal collection storage.

Do not introduce separate iterator implementations unless there is a
concrete need.

------------------------------------------------------------------------

# 66. Heap Rules

The heap should receive candidates that already have valid scores.

The heap must not:

-   calculate scores,
-   fetch drivers,
-   call Redis,
-   call PostgreSQL,
-   modify retry policy.

Its only responsibility is ordering.

------------------------------------------------------------------------

# 67. Ranking Rules

The Ranking Stage must delegate scoring to the ranker.

Do not duplicate scoring formulas inside the stage.

The architecture is:

``` text
RankingStage
    │
    ▼
Ranker
    │
    ├── FeatureExtractor
    │
    └── Scorer
```

packages.

Changing stage order changes dispatch behaviour.

------------------------------------------------------------------------

## Rule 10 --- Do not add ranking formulas to stages

Ranking belongs in the ranking subsystem.

# 69. Additional AI Agent Rules for Dispatch Strategy Context

## Rule 11 — Do not make Smart Stand Dispatch stand-only

A candidate must not be rejected merely because the driver is outside
the preferred stand when Smart Stand Dispatch has expanded beyond that
stand.

Fallback candidates must be allowed to continue through validation and
ranking when otherwise eligible.

------------------------------------------------------------------------

## Rule 12 — Do not reject cross-location candidates by default

A candidate must not be rejected solely because:

``` text
candidate location != ride origin location
```

Cross-location eligibility is determined by applicable business, legal,
geographic, service, and driver-state rules.

------------------------------------------------------------------------

## Rule 13 — Do not resolve dispatch configuration inside the pipeline

Do not implement configuration hierarchy traversal inside Candidate
Pipeline stages.

The effective dispatch strategy must already be resolved upstream.

------------------------------------------------------------------------

## Rule 14 — Preserve stand and location context

Do not discard metadata needed to distinguish:

``` text
Preferred stand candidate
Fallback non-stand candidate
Nearby-location candidate
```

The ranking/strategy layer may require this context.

------------------------------------------------------------------------

## Rule 15 — Keep strategy preference separate from eligibility

Do not implement:

``` text
Not preferred
    ↓
Ineligible
```

Preference and eligibility are separate decisions.

# 69. Common Implementation Mistakes

## Mistake 1 --- God Stage

Incorrect:

``` text
CandidateProcessingStage

    load
    validate
    filter
    rank
    reserve
    offer
```

Correct:

``` text
Load
 ↓
Validate
 ↓
Filter
 ↓
Rank
 ↓
Heap
```

------------------------------------------------------------------------

## Mistake 2 --- Per-Candidate Redis Requests

Incorrect:

``` text
for candidate:
    redis.Get(...)
```

Prefer the existing batch loading boundary.

------------------------------------------------------------------------

## Mistake 3 --- Ranking Before Filtering

Incorrect:

``` text
Load
 ↓
Rank all
 ↓
Filter
```

Prefer:

``` text
Load
 ↓
Validate
 ↓
Filter
 ↓
Rank remaining
```

------------------------------------------------------------------------

## Mistake 4 --- Reservation Inside Ranking

Ranking determines preference.

Reservation determines concurrency ownership.

They are different responsibilities.

------------------------------------------------------------------------

## Mistake 5 --- Modifying Driver Domain Data for Dispatch Metadata

Do not add:

``` text
Driver.Score
```

just because ranking needs a score.

Use candidate metadata.

# 72. Relationship With Stage 4 --- Ranking Engine

The Candidate Pipeline owns the **execution point** for ranking.

The Ranking Engine owns the **ranking implementation**.

``` text
Candidate Pipeline
       │
       ▼
Ranking Stage
       │
       ▼
Ranker
       │
       ▼
Feature Extraction
       │
       ▼
Scorer
```

This distinction is important.

The pipeline controls **when** ranking occurs.

The Ranking Engine controls **how** ranking works.

------------------------------------------------------------------------

# 73. Relationship With Stage 5 --- Dispatch Optimizer

The Candidate Pipeline produces the ordered candidate source.

The Dispatch Optimizer / Retry Policy determines:

``` text
How many candidates to offer
How long to wait
How to retry
```

Therefore:

``` text
Candidate Pipeline
        │
        ▼
Ordered Candidates
        │
        ▼
Dispatch Policy
        │
        ▼
Offer Selection
```

------------------------------------------------------------------------

# 74. Relationship With Stage 6 --- Geo Engine

Geo discovery and refinement happen before the pipeline.

Travel calculation may later contribute ranking features inside the
pipeline's Ranking Stage.

``` text
Discovery
   │
   ▼
Geo Refinement
   │
   ▼
Candidate Pipeline
   │
   ▼
Ranking
   │
   ▼
Travel / ETA Features
```

The pipeline should not become responsible for geographic indexing.

The following should not be added merely to claim completeness:

These belong to later architectural stages or should only be added when
measurements and requirements justify them.

# 77. Architectural Decisions

The following decisions should be represented in the project's ADR
collection.

## ADR --- Pipeline-Based Candidate Processing

Candidate processing is split into independent stages to avoid a
monolithic matching implementation.

------------------------------------------------------------------------

## ADR --- Batch Driver Enrichment

Driver data is loaded in batches rather than one candidate at a time.

------------------------------------------------------------------------

## ADR --- Ranking Outside Matching

Ranking is isolated from Matching so ranking strategies can evolve
independently.

------------------------------------------------------------------------

## ADR --- Heap-Based Candidate Ordering

A max heap provides efficient highest-score-first consumption.

------------------------------------------------------------------------

## ADR --- Candidate Source Boundary

Matching consumes an ordered candidate source rather than depending
directly on the heap implementation.

------------------------------------------------------------------------

## ADR --- Reservation Outside Pipeline

Reservation remains in Matching because it is a concurrency-sensitive
dispatch decision.

# 79. Final Summary

The Candidate Pipeline is the controlled transformation boundary between
spatial discovery and dispatch selection.

Its responsibility is:

``` text
Discoveries
    │
    ▼
Enrichment
    │
    ▼
Validation
    │
    ▼
Filtering
    │
    ▼
Ranking
    │
    ▼
Ordering
```

It deliberately does not own:

``` text
Discovery
Reservation
Offer publication
Retry policy
```

The pipeline is intentionally simple at its core:

``` text
Pipeline
    │
    ├── Stage
    ├── Stage
    ├── Stage
    └── Stage
```

This simplicity is a feature.

Future functionality should be added as a focused stage or through an
existing subsystem boundary only when there is a real requirement.

The long-term objective is not to build the most elaborate
candidate-processing framework.

The objective is to build a **fast, understandable, testable,
production-grade candidate pipeline that can evolve without unnecessary
refactoring**.
