# RideForge Event-Driven Architecture

> **Document:** `docs/02-architecture/EVENT_DRIVEN_ARCHITECTURE.md`  
> **Status:** Active architecture documentation  
> **Scope:** Domain events, application events, event envelopes, event routing, Kafka/Redpanda transport, transactional outbox, idempotency, consumers, retries, and dead-letter handling  
> **Audience:** Backend developers, architects, reviewers, operators, and AI coding agents

---

# 1. Purpose

RideForge uses event-driven communication to decouple ride lifecycle changes, matching, driver responses, notifications, and asynchronous processing.

The event-driven architecture provides:

- reliable asynchronous communication,
- transactional event publication,
- service decoupling,
- retryable processing,
- idempotent consumption,
- failure isolation,
- future microservice extraction.

The architecture follows:

```text
Domain/Application Action
        │
        ▼
Database Transaction
        │
        ├── State Change
        │
        └── Outbox Event
                │
                ▼
             Commit
                │
                ▼
        Outbox Publisher
                │
                ▼
          Kafka / Redpanda
                │
                ▼
             Consumer
                │
                ▼
        Application Handler
```

---

# 2. Core Principle

The system must not depend on a distributed two-phase transaction between PostgreSQL and Kafka/Redpanda.

Instead:

```text
PostgreSQL
    │
    ├── Business State
    └── Outbox Event
          │
          ▼
       Commit
          │
          ▼
       Publisher
          │
          ▼
        Kafka
```

The database transaction establishes durable intent.

The event publisher asynchronously transports that intent.

---

# 3. Event Categories

RideForge distinguishes between:

```text
Domain Events
Application Events
Transport Messages
```

These concepts should not be conflated.

---

# 4. Domain Events

A domain event represents something meaningful that happened in the business domain.

Examples:

```text
RideCreated
MatchingStarted
DriverAccepted
DriverRejected
DriverTimeout
RideCancelled
RideCompleted
```

Domain events should describe facts rather than commands.

Preferred:

```text
DriverAccepted
```

Not:

```text
AcceptDriver
```

The first describes something that happened.

The second describes an instruction.

---

# 5. Application Events

Application events are the events used by application orchestration and integration boundaries.

They may contain:

- event type,
- aggregate identifier,
- event identifier,
- occurrence timestamp,
- payload.

The current application uses an event envelope to provide a consistent outer structure.

---

# 6. Event Envelope

The event envelope provides metadata around the actual event payload.

Conceptually:

```text
Envelope
├── ID
├── Type
├── Aggregate
├── Data
└── Occurred
```

The payload remains domain/application-specific.

The envelope provides transport-independent event metadata.

---

# 7. Event Identifier

Every event must have a unique event identifier.

Conceptually:

```text
Event
  │
  ▼
Unique Event ID
```

The identifier is important for:

- tracing,
- idempotency,
- debugging,
- event correlation.

Consumers should be able to identify whether an event has already been processed.

---

# 8. Aggregate Identifier

The envelope contains an aggregate identifier.

For ride-related events:

```text
Aggregate = Ride ID
```

This allows consumers and operators to associate an event with its business aggregate.

---

# 9. Event Timestamp

Every event carries the time at which the event occurred.

This should represent event occurrence rather than consumer processing time.

These are different:

```text
Occurred
    ≠
Consumed
```

Both may be useful for observability.

---

# 10. Event Payload

The envelope's `Data` contains the event-specific payload.

For example:

```text
DriverOfferedEvent
├── RideID
├── DriverID
├── OfferTimeout
├── MatchingAttempt
└── SearchRadius
```

The event payload should contain only data required by consumers and event semantics.

---

# 11. Event Naming

Event names should represent completed facts.

Preferred:

```text
DriverOffered
DriverAccepted
DriverRejected
DriverTimedOut
```

Avoid ambiguous names such as:

```text
DriverAction
DriverUpdate
ProcessDriver
```

Event names should remain stable once published.

---

# 12. Transactional Outbox

The transactional outbox is the reliability boundary between PostgreSQL and Kafka/Redpanda.

The required pattern is:

```text
BEGIN
   │
   ├── Business State Change
   │
   └── Insert Outbox Event
   │
COMMIT
```

Only after the transaction commits should the event become eligible for publishing.

---

# 13. Why Outbox Is Required

Without an outbox, this sequence is unsafe:

```text
DB Transaction
     │
     ▼
Commit
     │
     ▼
Kafka Publish
```

If the process crashes between the two operations:

```text
Database = updated
Kafka = no event
```

The system loses the event.

With an outbox:

```text
Database
├── Business state
└── Outbox event
```

both are committed together.

---

# 14. Outbox Lifecycle

The conceptual lifecycle is:

```text
PENDING
   │
   ▼
PUBLISHING
   │
   ▼
PUBLISHED
```

Failure may return the event to a retryable state depending on the current publisher implementation.

The exact state model must remain aligned with the outbox repository and publisher implementation.

---

# 15. Outbox Publisher

The publisher is responsible for:

1. reading pending outbox events,
2. publishing them to Kafka/Redpanda,
3. marking successful events as published,
4. retrying failed publication where appropriate,
5. exposing failures through observability.

The publisher must not mutate domain state unrelated to event publication.

---

# 16. Kafka / Redpanda Boundary

Kafka/Redpanda is the transport layer.

The application should not embed broker-specific behaviour throughout domain services.

Preferred:

```text
Application
    │
    ▼
Event / Outbox
    │
    ▼
Producer Adapter
    │
    ▼
Kafka / Redpanda
```

This preserves the ability to replace or configure transport infrastructure later.

---

# 17. Topics

Current event transport uses separate topics for major event categories.

Examples include:

```text
ride.events
match.events
ride.events.dlq
```

Topic ownership and naming should remain documented as the event system grows.

Do not create a new topic for every small event without a concrete operational reason.

---

# 18. Topic Design Principle

A topic should represent a meaningful stream boundary.

Avoid:

```text
ride.created.topic
ride.cancelled.topic
ride.completed.topic
...
```

unless there is a demonstrated operational requirement.

Prefer meaningful streams such as:

```text
ride.events
match.events
```

with event type represented in the envelope.

---

# 19. Producer Responsibility

A producer is responsible for transporting an already-created event.

It should not:

- modify business state,
- calculate dispatch policy,
- perform domain validation,
- construct unrelated business events.

The producer is infrastructure.

---

# 20. Consumer Responsibility

A consumer receives a transport message and passes it into the application event-processing boundary.

Conceptually:

```text
Kafka
  │
  ▼
Consumer
  │
  ▼
Decode Envelope
  │
  ▼
Event Router
  │
  ▼
Application Handler
```

---

# 21. Event Router

The Event Router maps event types to application handlers.

Conceptually:

```text
Event Type
    │
    ├── RideCreated → Ride Handler
    ├── MatchingStarted → Matching Engine
    ├── DriverOffered → Driver Offer Handler
    ├── DriverAccepted → Driver Response Handler
    └── ...
```

The router should not implement the business logic of the handlers.

It only determines where the event should go.

---

# 22. Event Handler

A handler owns the application behaviour associated with an event.

For example:

```text
MatchingStarted
       │
       ▼
Matching Engine
```

The matching engine then coordinates:

```text
Retry Policy
Candidate Search
Candidate Pipeline
Reservation
Offer
```

This keeps event transport separate from dispatch behaviour.

---

# 23. Event Router and Transaction Boundary

Where event processing modifies durable state, the event processing path should establish an appropriate transaction boundary.

Conceptually:

```text
Consume Event
     │
     ▼
Begin Transaction
     │
     ├── Idempotency Check
     ├── Business Processing
     └── Outbox Events
     │
     ▼
Commit
```

The exact ownership of the transaction is determined by the application event-processing architecture.

---

# 24. Idempotent Consumption

At-least-once delivery means consumers can receive the same event more than once.

Therefore:

```text
Same Event
   │
   ▼
Consumer
   │
   ├── First time → Process
   │
   └── Duplicate → Ignore safely
```

The system must not assume exactly-once delivery from the transport.

---

# 25. Processed Event Repository

The current architecture contains a processed-event persistence boundary.

Conceptually:

```text
Event ID
   │
   ▼
Processed Event Store
```

The consumer can use this to determine whether the event has already been processed.

The repository implementation owns persistence details.

---

# 26. Idempotency Sequence

A safe processing flow is:

```text
Receive Event
     │
     ▼
Check Event ID
     │
     ├── Already Processed
     │       │
     │       ▼
     │      Skip
     │
     └── New
             │
             ▼
       Process Business Logic
             │
             ▼
       Record Processed Event
             │
             ▼
           Commit
```

The processed-event record and business state should be coordinated transactionally when both belong to the same transaction boundary.

---

# 27. Duplicate Delivery

Duplicate delivery can happen because of:

- consumer restart,
- network failure,
- acknowledgement failure,
- broker retry,
- process crash.

Duplicate delivery is expected behaviour, not necessarily a system error.

---

# 28. Event Ordering

Ordering must not be assumed globally.

The architecture should only rely on ordering where the transport partitioning and event design explicitly guarantee it.

Consumers should prefer idempotent state transitions over assumptions such as:

```text
Event A always arrives before Event B
```

unless that ordering is part of the documented contract.

---

# 29. Aggregate Ordering

Where ordering matters for a ride, events should be designed so that related events can be associated with the same aggregate.

Conceptually:

```text
Ride ID
   │
   ▼
Partitioning / Ordering Key
   │
   ▼
Ride Event Stream
```

The exact producer configuration should remain an infrastructure concern.

---

# 30. Event Versioning

Published event contracts should be treated as compatibility boundaries.

When an event changes:

```text
Existing consumers
        │
        ▼
Compatibility
```

must be considered before deployment.

Do not silently change the meaning of an existing field.

---

# 31. Adding Event Fields

Adding an optional field is generally safer than changing or removing an existing field.

Avoid changing:

```text
driver_id
```

from one semantic meaning to another.

Event schema changes should be documented when they affect consumers.

---

# 32. Event Compatibility

Consumers should tolerate fields they do not use.

The goal is:

```text
Producer evolves
      │
      ▼
Existing consumer remains functional
```

This is especially important as RideForge evolves toward more independent services.

---

# 33. Retry Strategy

Transient event-processing failures should be retryable.

Examples:

```text
Temporary database failure
Temporary broker failure
Temporary external dependency failure
```

Retry logic should not retry permanent business errors indefinitely.

---

# 34. Retry Classification

Errors should be conceptually separated into:

```text
Transient
Permanent
Unknown
```

### Transient

Retry may succeed.

### Permanent

Retry is unlikely to help.

### Unknown

Use conservative handling and observability.

The exact classification belongs to the relevant infrastructure/application boundary.

---

# 35. Dead-Letter Queue

Events that cannot be successfully processed after the configured retry policy should be isolated.

Conceptually:

```text
Event
  │
  ▼
Retry
  │
  ├── Success → Complete
  │
  └── Repeated Failure
          │
          ▼
         DLQ
```

The current architecture includes:

```text
ride.events.dlq
```

for failed event handling.

---

# 36. DLQ Purpose

A dead-letter queue is not a garbage bin.

It exists to preserve failed messages for:

- investigation,
- controlled replay,
- operational recovery,
- failure analysis.

DLQ processing must be observable.

---

# 37. DLQ Replay

A future replay mechanism should:

```text
DLQ Event
    │
    ▼
Inspect Failure
    │
    ▼
Correct Cause
    │
    ▼
Replay
```

Replay must respect event idempotency.

A replayed event must not create duplicate business effects.

---

# 38. Event Failure Handling

The system should preserve enough context to understand:

```text
Which event?
Which aggregate?
Which consumer?
Which failure?
Which attempt?
```

Useful metadata includes:

```text
event_id
event_type
aggregate_id
consumer
retry_count
occurred_at
failed_at
error
```

Sensitive data should not be copied into failure metadata unnecessarily.

---

# 39. Event Correlation

The event ID and aggregate ID should support distributed tracing and debugging.

Conceptually:

```text
Ride ID
  │
  ├── Ride Created
  ├── Matching Started
  ├── Driver Offered
  ├── Driver Accepted
  └── Ride Completed
```

This allows the full ride lifecycle to be reconstructed.

---

# 40. Event Processing Observability

Useful metrics include:

```text
events_consumed_total
events_processed_total
events_failed_total
events_retried_total
events_dlq_total
event_processing_duration_seconds
outbox_pending_total
outbox_publish_failures_total
```

Metrics should remain low-cardinality.

Do not use:

```text
ride_id
driver_id
event_id
```

as metric labels.

---

# 41. Event Tracing

Useful span attributes include:

```text
event.id
event.type
event.aggregate
consumer.name
retry.count
```

Avoid putting large payloads into tracing attributes.

---

# 42. Event Logging

Structured logs should provide enough information to correlate event processing.

Preferred fields:

```text
event_id
event_type
aggregate_id
consumer
retry_count
```

Avoid logging complete event payloads unless required for debugging and safe to do so.

---

# 43. Event Security

Events should contain only data required by consumers.

Avoid publishing:

- credentials,
- access tokens,
- secrets,
- unnecessary personal data.

Event payloads can persist in brokers, logs, and DLQs and therefore should be treated as durable operational data.

---

# 44. Event Data Ownership

The producer owns the meaning of its event.

Consumers should not modify an event payload.

Conceptually:

```text
Producer
   │
   ▼
Immutable Event
   │
   ▼
Consumers
```

A consumer creates its own state based on the event.

---

# 45. Commands vs Events

Commands:

```text
Do something
```

Events:

```text
Something happened
```

Examples:

```text
AcceptDriver       = Command
DriverAccepted     = Event
```

The current event architecture primarily transports events.

Commands may be introduced at explicit application boundaries when needed.

---

# 46. Event Bus Independence

Application code should depend on application event contracts and publisher/consumer abstractions.

It should not directly depend on:

```text
kafka-go
```

or broker-specific APIs outside infrastructure.

This keeps the application layer transport-independent.

---

# 48. Event-Driven Matching

Matching is integrated into the event system.

Conceptually:

```text
Ride Lifecycle
      │
      ▼
Matching Started
      │
      ▼
Matching Engine
      │
      ▼
Driver Offered
      │
      ▼
Driver Response
      │
      ├── Accepted
      ├── Rejected
      └── Timeout
```

This allows matching to remain independent from direct synchronous callers.

---

# 49. Driver Offer Event

The driver-offer event represents:

```text
A driver has been reserved and an offer has been created for the ride.
```

The event should not be emitted before the durable offer operation has reached its required consistency boundary.

The current flow is:

```text
Reserve
   │
   ▼
Insert Offer
   │
   ▼
Create Envelope
   │
   ▼
Insert Outbox
```

---

# 50. Driver Response Events

Driver responses may produce events such as:

```text
DriverAccepted
DriverRejected
DriverTimeout
```

These events are consumed by the application response/matching lifecycle.

The exact event names must follow the current event contracts.

---

# 51. Event-Driven vs Synchronous Calls

Not every operation should become an event.

Use synchronous application calls when:

```text
Immediate result is required
```

Use events when:

```text
Asynchronous processing
Decoupling
Durable notification
Cross-component propagation
```

is more appropriate.

---

# 52. Avoid Event Explosion

Do not create events for every internal method call.

Incorrect:

```text
LoadCandidateStarted
FilterCandidateStarted
CalculateScoreStarted
...
```

These are internal implementation details.

Events should represent meaningful business or integration facts.

---

# 53. Event Boundaries and Microservices

The event architecture is designed to support future service extraction.

Potential future boundaries include:

```text
Ride Service
Matching Service
Driver Service
Notification Service
Analytics Service
```

Events can become integration contracts between these services.

However, the current modular monolith should not be split prematurely.

---

# 54. Modular Monolith Principle

The current application can use:

```text
Modules
+
Events
+
Interfaces
```

without requiring every module to become a network service.

This provides architectural separation without unnecessary distributed-system complexity.

---

# 55. Future Service Extraction

A future extraction can follow:

```text
Application Module
       │
       ▼
Stable Contract
       │
       ▼
Event Boundary
       │
       ▼
Independent Service
```

The existing event architecture helps establish these boundaries gradually.

---

# 56. Transactional Event Creation

When an event represents a state transition that must not be lost, the event should be created in the same transaction as that state transition.

Example:

```text
BEGIN
   │
   ├── Mark Driver Accepted
   └── Insert Driver Accepted Event
   │
COMMIT
```

This prevents state/event divergence.

---

# 57. Event Publication Is Asynchronous

After the transaction commits:

```text
Business State = Durable
Outbox Event   = Durable
```

The actual broker publication may happen later.

This is intentional.

The architecture prioritizes reliable event creation over immediate transport publication.

---

# 58. Publisher Failure

If Kafka/Redpanda is unavailable:

```text
PostgreSQL
   │
   └── Outbox remains pending
```

The business transaction does not need to be rolled back merely because the broker is temporarily unavailable after commit.

The publisher retries later.

---

# 59. Consumer Failure

If a consumer fails:

```text
Event remains retryable
```

according to the consumer/retry mechanism.

The producer should not need to know that a downstream consumer failed.

This is one of the benefits of event-driven decoupling.

---

# 60. Backpressure

The event system must tolerate temporary differences between:

```text
Producer Rate
```

and:

```text
Consumer Rate
```

The broker and consumer architecture provide buffering.

Future scaling may increase:

- consumer concurrency,
- partitions,
- regional consumers.

These should be introduced based on measured workload.

---

# 61. Event Processing Performance

Consumer processing should avoid unnecessary work.

Preferred:

```text
Decode
→ Validate
→ Idempotency
→ Business Handler
→ Commit
```

Avoid:

```text
Decode
→ many unrelated database calls
→ repeated lookups
→ synchronous external calls
→ long transaction
```

unless required by the business operation.

---

# 62. Long-Running Handlers

Long-running event handlers should be avoided inside a single synchronous consumer path where possible.

If a handler requires substantial asynchronous work, consider producing a new event or delegating to a dedicated worker.

Do not block broker consumption unnecessarily.

---

# 63. Event Contract Documentation

This documentation becomes part of the integration contract.

# 66. Event Invariants

Important invariants include:

### No lost transactional event

```text
State transition committed
    ⇒
Required outbox event committed
```

---

### Duplicate-safe processing

```text
Same event processed twice
    ⇒
Business effect occurs once
```

---

### Failed publication is recoverable

```text
Broker unavailable
    ⇒
Outbox event remains recoverable
```

---

### DLQ is not silent

```text
Event enters DLQ
    ⇒
Observable operational failure
```

# 67. Common Implementation Mistakes

## Mistake 1 — Publishing directly from business code

Avoid:

```text
Service
  ↓
Kafka.Publish()
```

when the event represents a transactionally coupled state change.

Use:

```text
Service
  ↓
Outbox
```

---

## Mistake 2 — Assuming exactly-once delivery

Consumers must tolerate duplicates.

---

## Mistake 3 — Using event IDs as metric labels

This creates high cardinality.

---

## Mistake 4 — Putting business logic in the Event Router

The router should dispatch.

Handlers should implement business behaviour.

---

## Mistake 5 — Making every internal operation an event

Events represent meaningful facts, not implementation tracing.

---

## Mistake 6 — Treating DLQ as permanent deletion

DLQ messages must remain inspectable and potentially replayable.

---

## Mistake 7 — Ignoring event compatibility

Published events are integration contracts.

# 73. Architectural Decisions

The following decisions should be represented in ADR documentation.

## ADR — Transactional Outbox

Business state changes and required events are committed together in PostgreSQL.

---

## ADR — At-Least-Once Consumer Model

Consumers must be idempotent because duplicate delivery is possible.

---

## ADR — Kafka/Redpanda as Transport

Broker infrastructure is isolated behind producer/consumer boundaries.

---

## ADR — Event Router

Event routing is separated from business handlers.

---

## ADR — DLQ for Unrecoverable Events

Repeatedly failing events are isolated rather than silently discarded.

---

## ADR — Modular Monolith Before Microservices

Event boundaries prepare the application for future extraction without forcing premature distributed deployment.

```text
Consumer
        │
        ▼
Event Router
        │
        ▼
Application Handler
```

The most important rules are:

1. **Transactionally coupled events go through the outbox.**
2. **Consumers must be idempotent.**
3. **Events represent facts, not internal method calls.**
4. **Kafka/Redpanda remains an infrastructure concern.**
5. **The Event Router dispatches; handlers implement business behaviour.**
6. **Failed events must be retryable or observable through the DLQ.**
7. **Published event contracts must evolve compatibly.**
8. **Do not assume global event ordering.**
9. **Do not introduce distributed microservices merely because event boundaries exist.**
10. **Use existing event infrastructure instead of creating parallel event mechanisms.**
