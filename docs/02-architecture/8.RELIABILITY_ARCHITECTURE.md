# RideForge Reliability Architecture

> **Document:** `docs/02-architecture/RELIABILITY_ARCHITECTURE.md`  
> **Status:** Active architecture documentation  
> **Scope:** Failure handling, recovery, idempotency, reconciliation, stale-driver cleanup, reservation recovery, event reliability, Redis recovery, database consistency, and operational resilience  
> **Audience:** Backend developers, architects, reviewers, operators, and AI coding agents

---

# 1. Purpose

RideForge reliability architecture ensures that temporary infrastructure failures, process crashes, duplicate events, stale realtime state, and partial operations do not leave the ride-hailing system in an invalid or permanently inconsistent state.

The reliability model is based on:

```text
Detect
  ↓
Contain
  ↓
Retry / Recover
  ↓
Reconcile
  ↓
Repair
  ↓
Observe
```

Reliability is implemented at the boundaries where failures can actually occur rather than through a generic reliability framework.

---

# 2. Reliability Goals

The system must preserve the following properties:

- no lost transactionally required events,
- no permanent driver reservation caused by an application failure,
- duplicate event processing must be safe,
- stale realtime state must eventually be removed,
- Redis-derived indexes must be rebuildable,
- database state remains authoritative,
- transient failures are retryable,
- permanent failures are isolated,
- inconsistencies are detectable,
- repair operations are observable.

---

# 3. Source of Truth

RideForge uses different systems for different responsibilities.

The authoritative source depends on the data.

Conceptually:

```text
Business / Durable State
        │
        ▼
    PostgreSQL
```

Realtime state:

```text
Driver Presence
Location
Connection
Offer Delivery State
        │
        ▼
       Redis
```

Spatial index:

```text
Driver → H3 Cell
        │
        ▼
       Redis
```

Event transport:

```text
Event Delivery
        │
        ▼
Kafka / Redpanda
```

The system must not treat every cache or index as an independent source of truth.

---

# 4. PostgreSQL as Durable Business State

PostgreSQL is the durable authority for business state such as:

```text
Ride
Driver
Ride Driver Offer
Driver Metrics
Processed Event
Outbox Event
```

Redis-derived state must be recoverable from authoritative state and realtime inputs.

---

# 5. Redis as Realtime Infrastructure

Redis is used for low-latency operational state.

Examples include:

```text
Driver Cache
Driver Location
Heartbeat
Connection State
Offer Delivery State
Driver Lock / Reservation
H3 Driver Index
Redis GEO Index
```

Redis is intentionally optimized for the dispatch critical path.

Because this state is operational and rebuildable, reliability mechanisms must account for Redis loss or expiration.

---

# 6. Cache Failure Principle

A Redis failure must not be treated as permanent loss of business state.

Conceptually:

```text
Redis Failure
    │
    ▼
Dispatch Degraded
    │
    ▼
Recover Redis
    │
    ▼
Rebuild Derived State
```

The application should fail safely rather than inventing driver availability.

---

# 7. Driver Availability Safety

A driver should not be considered available solely because a stale cache entry exists.

Availability is a combination of:

```text
Realtime Presence
+
Driver State
+
Reservation State
+
Candidate Filters
+
Final Reservation
```

The final reservation operation remains authoritative for concurrent ownership.

---

# 8. Reservation Reliability

Driver reservation is a critical concurrency boundary.

The normal flow is:

```text
ONLINE
  │
  ▼
Reserve
  │
  ▼
RESERVED
```

The system must also support:

```text
RESERVED
  │
  ├── Offer Accepted
  ├── Offer Rejected
  ├── Offer Timeout
  ├── Cancellation
  └── Recovery
       │
       ▼
     ONLINE
```

---

# 9. Reservation Failure

If reservation fails before ownership is established:

```text
Reserve
  │
  ▼
false
```

the candidate can be skipped.

This is normal concurrency behaviour.

It should not be interpreted as a system-wide failure.

---

# 10. Post-Reservation Failure

A more dangerous case is:

```text
Reserve
  │
  ▼
Success
  │
  ▼
Offer Persistence
  │
  ▼
Failure
```

The reservation must be released.

The system therefore follows:

```text
Successful Reservation
       │
       ▼
Offer Operation
       │
       ├── Success → Keep Reservation
       │
       └── Failure → Release
```

---

# 11. Force Release

A force-release capability exists for recovery situations where the original ride-specific release path cannot be used.

Conceptually:

```text
Driver RESERVED
      │
      ▼
Recovery
      │
      ▼
ForceRelease(driver)
      │
      ▼
ONLINE
```

Force release must be used carefully because it can affect active dispatch state.

It belongs to recovery/cleanup paths, not normal candidate selection.

---

# 12. Reservation TTL

Reservations should have a bounded lifetime.

The TTL prevents:

```text
Application Crash
      +
No Cleanup
      =
Driver Reserved Forever
```

Conceptually:

```text
Reserve
  │
  ▼
TTL
  │
  ├── Normal release → delete/clear reservation
  │
  └── No release → automatic expiration
```

The exact TTL is configuration-driven.

---

# 13. Event Reliability

The event-driven architecture uses the transactional outbox.

The reliability sequence is:

```text
Business Transaction
       │
       ├── State Change
       └── Outbox Event
       │
       ▼
     Commit
       │
       ▼
Outbox Publisher
       │
       ▼
Kafka / Redpanda
```

This guarantees that a transactionally required event is durable with the associated database state.

---

# 14. Broker Failure

If Kafka/Redpanda becomes temporarily unavailable:

```text
Database
   │
   └── Outbox remains pending
```

The business transaction does not depend on immediate broker availability after commit.

The publisher retries later.

---

# 15. Consumer Failure

If an event consumer fails:

```text
Event
  │
  ▼
Consumer
  │
  ▼
Failure
  │
  ▼
Retry
```

Repeatedly failing events are eventually isolated through the dead-letter mechanism.

The producer does not need to synchronously handle downstream consumer failures.

---

# 16. Idempotent Event Processing

Event delivery is treated as at-least-once.

Therefore:

```text
Event A
  │
  ├── Delivery 1 → Process
  │
  └── Delivery 2 → Detect duplicate → Ignore safely
```

The processed-event boundary prevents duplicate business effects.

---

# 17. Crash During Event Processing

Consider:

```text
Receive Event
     │
     ▼
Process
     │
     ▼
Process crashes
```

The system must not mark the event as successfully processed unless the required business work has reached its durable transaction boundary.

After restart:

```text
Event
  │
  ▼
Retry
  │
  ▼
Idempotent Processing
```

---

# 18. Transactional Idempotency

When business state and processed-event state must change together, they should be committed in the same transaction.

Conceptually:

```text
BEGIN
   │
   ├── Check / record event
   ├── Business state transition
   └── Required outbox events
   │
COMMIT
```

This avoids a state where:

```text
Business change committed
but
event processing status missing
```

or the reverse.

---

# 19. Dead-Letter Handling

The DLQ isolates events that cannot be successfully processed after the configured retry policy.

```text
Event
  │
  ▼
Retry
  │
  ├── Success
  │
  └── Repeated Failure
          │
          ▼
         DLQ
```

A DLQ event must remain inspectable.

---

# 20. DLQ Is Not Data Deletion

Moving an event to the DLQ means:

```text
Processing stopped
```

It does not mean:

```text
Event discarded
```

The event should remain available for investigation and controlled recovery.

---

# 21. Recovery and Replay

A future replay process should follow:

```text
DLQ
 │
 ▼
Investigate
 │
 ▼
Fix Cause
 │
 ▼
Replay
 │
 ▼
Idempotent Consumer
```

Replay must not bypass normal validation and idempotency controls.

---

# 22. Redis Recovery

Redis contains derived/realtime state that may disappear because of:

- Redis restart,
- failover,
- eviction,
- expiration,
- data corruption,
- manual maintenance.

The architecture therefore requires a recovery path.

Conceptually:

```text
Redis Restart
      │
      ▼
Rebuild Driver Cache
      │
      ▼
Rebuild H3 Index
      │
      ▼
Rebuild GEO Index where required
```

---

# 23. Driver Cache Recovery

The driver cache should be reconstructed from valid authoritative/realtime information.

Recovery must not mark every database driver as online.

A driver should only become dispatchable when its realtime availability requirements are satisfied.

---

# 24. H3 Index Recovery

The H3 index is derived from driver location.

Recovery follows:

```text
Valid Driver Location
       │
       ▼
H3 Cell Calculation
       │
       ▼
H3 Driver Index
```

The index must not contain drivers that are no longer valid for dispatch.

---

# 25. GEO Index Recovery

If Redis GEO is used as a secondary spatial refinement index:

```text
Driver Location
      │
      ▼
Redis GEO
```

it must be rebuildable independently from the H3 index.

The GEO index is not the authoritative business record.

---

# 26. Recovery Ordering

Recovery should rebuild the minimum state required to restore safe operation.

Preferred conceptual order:

```text
Redis Available
      │
      ▼
Driver Realtime State
      │
      ▼
H3 Index
      │
      ▼
GEO Refinement Index
      │
      ▼
Dispatch Ready
```

The exact implementation may differ depending on startup and worker architecture.

---

# 27. Background Reconciliation

Periodic reconciliation repairs drift between derived systems.

The target model is:

```text
Driver Cache
     │
     ▼
Geo Index
     │
     ▼
H3 Index
     │
     ▼
PostgreSQL
```

The reconciliation process compares state rather than blindly rewriting everything.

---

# 28. Reconciliation Principle

Reconciliation should be:

```text
Detect
  ↓
Compare
  ↓
Repair only differences
```

Avoid:

```text
Delete everything
  ↓
Rebuild everything
```

during normal operation.

Full rebuilds belong to explicit recovery procedures.

---

# 29. Stale Driver Detection

A driver may remain in Redis after:

```text
Heartbeat expiration
Connection loss
Application crash
Network failure
```

Such a driver must eventually become undispatchable.

Conceptually:

```text
Driver Heartbeat
      │
      ▼
Expired?
      │
      ├── No → Remain eligible
      │
      └── Yes → Remove / mark stale
```

---

# 30. Stale H3 Membership

A stale driver must not remain indefinitely inside an H3 cell.

Otherwise:

```text
H3 Cell
  │
  ├── Real Driver
  ├── Real Driver
  └── Dead Driver
```

would produce false candidate discovery.

The H3 index therefore requires TTL and cleanup/reconciliation mechanisms.

---

# 31. Empty Cell Cleanup

When the final driver leaves an H3 cell:

```text
SREM
  │
  ▼
Cell Empty?
  │
  ▼
DEL Cell
```

This prevents accumulation of orphaned empty keys.

---

# 32. Atomic Geo Updates

Driver cell movement must be atomic.

The intended operation is:

```text
Old Cell
   │
   ▼
Atomic Update
   │
   ├── Remove old membership
   ├── Add new membership
   ├── Update driver mapping
   └── Refresh required TTL
```

This prevents intermediate inconsistent states from being observed by concurrent lookups.

---

# 33. Same-Cell Updates

If:

```text
oldCell == newCell
```

the system should not perform unnecessary membership movement.

Instead:

```text
Same Cell
   │
   ▼
Refresh required TTL/state
```

This reduces Redis writes.

---

# 34. Partial Geo Failure

A multi-step geo update can fail if implemented without atomicity.

Unsafe:

```text
Remove old
   │
   ▼
Network failure
   │
   ▼
Add new never happens
```

Atomic movement avoids this class of partial update.

---

# 35. Candidate Discovery Failure

If candidate discovery fails:

```text
Discovery
   │
   ▼
Error
```

the system should not fabricate an empty success result.

The matching attempt should return a meaningful failure state and allow the surrounding retry/recovery mechanism to decide what happens next.

---

# 36. Candidate Pipeline Failure

Candidate pipeline failures should be separated from discovery failures.

Conceptually:

```text
Discovery Success
      │
      ▼
Pipeline Error
      │
      ▼
Matching Failure
```

This distinction is important for observability and diagnosis.

---

# 37. Ranking Failure

Ranking is part of the candidate pipeline.

If ranking fails:

```text
Candidate Data
      │
      ▼
Ranking Error
      │
      ▼
No Offer
```

The system should not silently fall back to an arbitrary candidate unless such fallback is an explicitly documented dispatch policy.

---

# 38. Reservation Concurrency

Multiple workers may attempt to reserve the same driver.

The expected result is:

```text
Worker A ──┐
           ├── Reserve Driver
Worker B ──┘
              │
              ▼
        One succeeds
        One fails safely
```

The reservation mechanism must provide the atomicity required for this boundary.

---

# 39. Duplicate Matching Trigger

A ride may trigger matching more than once because of:

- event retry,
- worker retry,
- process restart,
- duplicate event delivery.

The system must rely on durable offer state, already-offered filtering, reservation ownership, and idempotent event handling to prevent uncontrolled duplicate dispatch.

---

# 40. Process Crash During Matching

Consider:

```text
Discover
  ↓
Rank
  ↓
Reserve
  ↓
Process crashes
```

Recovery depends on reservation TTL and subsequent reconciliation/cleanup.

The architecture must not require the crashed process to perform cleanup.

---

# 41. Process Crash After Offer Persistence

If the process crashes after:

```text
Offer + Outbox
```

have committed:

```text
Outbox Publisher
      │
      ▼
Publishes event later
```

No manual recovery should be required merely because the matching process died.

This is one of the primary benefits of the outbox architecture.

---

# 42. Process Crash Before Offer Persistence

If the driver was reserved but the offer transaction did not commit:

```text
Reservation
   │
   ▼
Crash
   │
   ▼
No Offer
```

The reservation TTL and cleanup/reconciliation mechanisms must prevent permanent reservation.

---

# 43. Database Failure

Database failures must be treated as infrastructure failures.

The application should:

- return an error,
- avoid partial success assumptions,
- allow retry where safe,
- preserve transactional boundaries.

Do not continue as if durable state was successfully written.

---

# 44. Database Transaction Failure

When a transaction fails:

```text
BEGIN
  │
  ├── partial operations
  │
  ▼
ROLLBACK
```

The application should assume that the transactionally protected state changes did not commit.

Any external side effect already performed outside that transaction must have an explicit compensation path.

---

# 45. External Side Effects

A major reliability boundary is:

```text
PostgreSQL Transaction
        +
Redis / External System
```

These are not automatically atomic.

Therefore:

```text
External side effect
      │
      ▼
Failure after DB success
```

must be handled through cleanup, retry, TTL, or reconciliation.

---

# 46. Recovery Hierarchy

The system uses progressively stronger recovery mechanisms:

```text
1. Atomic operation
       ↓
2. Transaction
       ↓
3. Retry
       ↓
4. TTL / expiration
       ↓
5. Background reconciliation
       ↓
6. Explicit rebuild / replay
```

The cheapest reliable mechanism should be preferred.

---

# 47. Do Not Use Reconciliation as Normal Control Flow

Reconciliation is a safety net.

It must not replace correct primary-path behaviour.

Incorrect:

```text
Write inconsistent state
   ↓
Wait for reconciliation
```

Correct:

```text
Perform atomic / transactional operation
   ↓
Reconciliation repairs exceptional drift
```

---

# 48. Reliability and Performance

Reliability mechanisms must not unnecessarily degrade the dispatch critical path.

Prefer:

```text
Atomic Redis operation
Batch read
Single transaction
Asynchronous publisher
Background reconciliation
```

over:

```text
Repeated synchronous repair
Full scans on every request
Extra database calls for every candidate
```

---

# 49. Background Worker Design

Recovery and reconciliation tasks should run outside the synchronous matching path where possible.

Examples:

```text
Heartbeat Recovery Worker
H3 Reconciliation Worker
Outbox Publisher
Stale Cleanup Worker
```

Workers should be independently observable.

---

# 50. Worker Failure

A background worker can itself crash.

Therefore worker tasks should be restartable and idempotent.

Preferred:

```text
Worker crashes
   │
   ▼
Restart
   │
   ▼
Continue safely
```

Avoid relying on in-memory progress as the only recovery mechanism.

---

# 51. Reconciliation Frequency

Reconciliation frequency should be configuration-driven.

Do not hard-code operational intervals in business logic.

The interval should reflect:

```text
Failure tolerance
Redis workload
Driver volume
Recovery requirements
```

---

# 52. Cleanup Scope

Cleanup operations should be targeted.

For example:

```text
Stale Driver
   │
   ├── Driver Cache
   ├── H3 Membership
   └── GEO Membership
```

Do not globally rebuild unrelated state because one driver became stale.

---

# 59. Failure Injection

Before production scale, selected failure scenarios should be deliberately tested.

Examples:

```text

Stop Redis
```

The goal is to verify that the architecture behaves as designed rather than merely verifying the happy path.

# 60. Reliability Invariants

### Business state remains durable

```text
Committed business state
    ⇒
Persisted in PostgreSQL
```

---

### Required events are durable

```text
Committed state transition requiring event
    ⇒
Corresponding outbox record committed
```

---

### Duplicate events are safe

```text
Duplicate delivery
    ⇒
No duplicate business effect
```

---

### Reservations do not become permanent accidentally

```text
Reservation
    ⇒
Explicit release OR bounded expiry
```

---

### Derived geo state is recoverable

```text
H3 / GEO loss
    ⇒
Rebuild possible
```

---

### Reconciliation is corrective

```text
Drift
    ⇒
Detect
    ⇒
Repair
```

# 61. Common Reliability Mistakes

## Mistake 1 — Treating Redis as the business database

Redis state must remain recoverable.

---

## Mistake 2 — Publishing events outside the transaction

Use the outbox for transactionally required events.

---

## Mistake 3 — Assuming exactly-once delivery

Consumers must be idempotent.

---

## Mistake 4 — Depending on process cleanup

Use TTL/reconciliation for crash recovery.

---

## Mistake 5 — Using reconciliation to hide broken primary logic

Fix the primary operation first.

---

## Mistake 6 — Retrying permanent business errors forever

Classify failures.

---

## Mistake 7 — Performing full rebuilds during every inconsistency

Repair only what is necessary.

---

## Mistake 8 — Adding synchronous recovery to the dispatch critical path

Use background workers where possible.

---

## Mistake 9 — Creating high-cardinality reliability metrics

Use identifiers in logs/traces, not metric labels.

---

## Rule 1 — Preserve Existing Recovery Boundaries

Reuse:

```text
Transactions
Outbox
TTL
Idempotency
Reconciliation
```

before introducing new mechanisms.

---

## Rule 2 — Do Not Add Generic Retry Frameworks

Retry should remain close to the operation that understands whether a failure is transient.

---

## Rule 3 — Prefer Atomic Operations

If a race can be eliminated by one atomic database or Redis operation, prefer that over compensation logic.

---

## Rule 4 — Keep Recovery Idempotent

Running recovery twice must not make the system less correct.

---

## Rule 5 — Do Not Hide Failures

Recovery failures must be observable.

---

## Rule 6 — Preserve Source-of-Truth Boundaries

Do not promote a cache or index into an authoritative business database without an explicit architectural decision.

---

## Rule 7 — Avoid Speculative Recovery Systems

Do not build complex disaster-recovery infrastructure before the actual operational requirement exists.

---

## Rule 8 — Test Failure Paths

Every reliability change should include at least the relevant failure-path tests.

# 66. Final Reliability Model

RideForge reliability follows:

```text
                ┌──────────────────┐
                │  Durable State   │
                │   PostgreSQL     │
                └────────┬─────────┘
                         │
                  Transaction
                         │
                         ▼
                  ┌─────────────┐
                  │   Outbox    │
                  └──────┬──────┘
                         │
                         ▼
                 Kafka / Redpanda
                         │
                         ▼
                    Consumers
                         │
                         ▼
                   Idempotency
                         │
                         ▼
                    Handlers
```

For realtime dispatch:

```text
Driver
  │
  ▼
Realtime State
  │
  ▼
Redis
  │
  ├── Driver Cache
  ├── H3 Index
  ├── GEO Index
  └── Reservation
```

For recovery:

```text
Failure
  │
  ▼
Detect
  │
  ▼
Contain
  │
  ▼
Retry / TTL
  │
  ▼
Reconcile
  │
  ▼
Repair
  │
  ▼
Observe
```

The core reliability rule is:

> **The primary path must establish correctness; retries, TTLs, reconciliation, and rebuilds exist to recover from exceptional failure—not to compensate for an incorrect primary design.**
