# RideForge Dispatch Engine

> **Document:** `docs/02-architecture/DISPATCH_ENGINE.md`  
> **Status:** Active architecture documentation  
> **Scope:** Matching orchestration, dispatch lifecycle, candidate discovery, ranking, reservation, offers, retries, adaptive dispatch policy, transactional boundaries, and concurrency  
> **Audience:** Backend developers, architects, reviewers, operators, and AI coding agents

---

# 1. Executive Summary

The Dispatch Engine is the orchestration layer responsible for turning a ride that requires matching into a driver offer.

Its responsibility is not to implement every dispatch capability itself.

Instead, it coordinates specialized components:

```text
Ride Requires Matching
        │
        ▼
Dispatch Engine
        │
        ├── Attempt Policy
        ├── Candidate Discovery
        ├── Candidate Pipeline
        ├── Ranking
        ├── Candidate Selection
        ├── Driver Reservation
        ├── Offer Persistence
        └── Offer Event
```

The central architectural principle is:

> **The Dispatch Engine orchestrates decisions; specialized components own the implementation of those decisions.**

---

# 2. Purpose

The Dispatch Engine exists to answer:

> **Given a ride that needs a driver, which eligible driver or drivers should receive an offer now?**

The process is intentionally separated into:

```text
Discover
   ↓
Enrich
   ↓
Filter
   ↓
Rank
   ↓
Select
   ↓
Reserve
   ↓
Offer
```

This separation allows individual subsystems to evolve without turning matching into a monolith.

---

# 3. Dispatch Responsibilities

The Dispatch Engine owns orchestration of:

- matching attempts,
- retry-policy decisions,
- candidate discovery invocation,
- candidate pipeline invocation,
- candidate selection,
- driver reservation,
- offer persistence,
- offer event creation,
- dispatch-level observability,
- failure propagation.

---

# 4. Dispatch Non-Responsibilities

The Dispatch Engine does not own the internal implementation of:

- H3 indexing,
- Redis GEO,
- driver cache loading,
- candidate filtering,
- ranking formulas,
- quality calculations,
- routing,
- driver reservation storage implementation,
- Kafka transport,
- push notification delivery.

Those are delegated to explicit boundaries.

# 6. Matching Attempt

A matching attempt represents one dispatch cycle for a ride.

Conceptually:

```text
Attempt 1
   │
   ├── Search
   ├── Rank
   └── Offer

No acceptance
   │
   ▼

Attempt 2
   │
   ├── Wider search
   ├── Rank
   └── Offer
```

Attempt state must remain durable enough to prevent the system from repeatedly treating the same dispatch cycle as a new attempt.

---

# 7. Attempt Counting

The current implementation derives attempt count from persisted ride-driver offer records.

Conceptually:

```text
ride_driver_offers
        │
        ▼
Count attempts
        │
        ▼
Retry Policy
```

This keeps retry state connected to actual persisted dispatch activity.

The exact persistence representation must remain consistent with the repository contract.

---

# 8. Maximum Attempt Boundary

The dispatch engine must stop when the configured maximum attempt count has been reached.

Conceptually:

```text
Attempt Count
      │
      ▼
Max Attempts?
      │
      ├── No → Continue matching
      │
      └── Yes → Stop
```

This is a dispatch policy boundary, not a candidate-search concern.

---

# 9. Retry Policy

The retry policy determines how the next dispatch attempt should behave.

Inputs may include:

```text
Attempt Count
Nearby Driver Count
Eligible Driver Count
```

Outputs may include:

```text
Search Radius
Candidate Limit
Offer Batch Size
Offer Timeout
```

The dispatch engine consumes the decision.

It does not calculate retry policy internally.

---

# 10. Adaptive Dispatch

The intended behaviour is:

```text
Attempt 1
   │
   ▼
Small/local search
   │
   ▼
No suitable result
   │
   ▼
Attempt 2
   │
   ▼
Expand search
   │
   ▼
Retry
```

This is preferable to blindly searching the maximum radius on every attempt.


Adaptive retry expansion and cross-location expansion are related but distinct:

```text
Retry Expansion
    → broadens search across matching attempts

Cross-Location Expansion
    → allows eligible drivers associated with nearby locations
      to enter the candidate flow when local supply is insufficient
```

Neither mechanism should silently change the resolved dispatch strategy.

---

# 10A. Dispatch Strategy Resolution

Before candidate discovery is executed, the Dispatch Engine must operate with an **effective dispatch strategy** resolved from the ride's applicable configuration hierarchy.

```text
Ride / Pickup Context
        │
        ▼
Most Specific Applicable Configuration
        │
        ├── Explicit Strategy? ── YES → Use it
        │
        └── NO
             ↓
        Parent Configuration
             ↓
        Continue upward
             ↓
        System Default
```

The first/nearest explicit configuration wins.

The hierarchy is extensible and may contain levels such as:

```text
State
 ↓
District
 ↓
City / Town
 ↓
Rural Area
 ↓
Auto Stand
 ↓
Ride-level / other configured level
```

The canonical rule is:

> **Specific configuration overrides inherited configuration.**

Example:

```text
District → Smart Dispatch
Town A   → Smart Stand Dispatch
Town B   → no explicit configuration
```

Therefore:

```text
Town A ride → Smart Stand Dispatch
Town B ride → Smart Dispatch (inherited)
```

If no explicit strategy exists anywhere in the applicable hierarchy, the configured system default is used.

---

# 10B. Dispatch Strategy Execution

Once the effective strategy is resolved, the Dispatch Engine executes that strategy. Strategy resolution and candidate discovery are separate concerns.

## Smart Stand Dispatch

Smart Stand Dispatch is **stand-preferred, not stand-exclusive**.

When the pickup is within a configured auto stand's radius:

```text
Pickup inside stand radius
        │
        ▼
Prefer eligible drivers at that stand
        │
        ▼
Apply stand queue / ordering rules
        │
        ▼
Suitable stand driver?
   ├── YES → continue with stand-preferred candidates
   └── NO  → expand to broader eligible candidates
```

If the rider is outside all configured stand radii, Smart Stand Dispatch does not restrict discovery to stand drivers.

Broader candidates may include:

```text
Drivers at other stands
Drivers outside stands
Drivers from nearby locations
```

subject to eligibility, availability, geographic reachability, legal/regional rules, service constraints, and applicable matching rules.

The stand is a **preferred dispatch source**, not an exclusive candidate boundary.

## Smart Dispatch

Smart Dispatch is **stand-agnostic**.

It searches for eligible nearby drivers without using auto-stand membership as a dispatch preference.

Typical factors include:

```text
Driver Eligibility
Availability
Distance
ETA
Matching / Ranking Factors
Operational Constraints
```

Any eligible driver may be considered regardless of stand membership.

# 11. Candidate Discovery Boundary

The Dispatch Engine calls the candidate search abstraction.

Conceptually:

```go
CandidateSearcher.FindCandidates(...)
```

The dispatch engine provides:

```text
Pickup Location
Search Radius / Expansion Policy
Candidate Limit
Matching Attempt
Effective Dispatch Strategy
Applicable Location / Configuration Context
```

The discovery implementation returns a candidate collection plus discovery metadata.

The effective dispatch strategy must not be treated as a hard geographic candidate boundary. Discovery may expand to nearby locations when the configured dispatch flow requires it.

---

# 12. Discovery Result

Discovery may provide:

```text
Candidates
Backend
Radius Used
Rings Visited
Cells Visited
```

These values are useful for:

- observability,
- adaptive policy,
- debugging,
- operational analysis.

The Dispatch Engine should not need to know how H3 or Redis performs the lookup.

---

# 13. Candidate Pipeline Boundary

After discovery:

```text
Discovery Result
       │
       ▼
Candidate Pipeline
```

The pipeline owns candidate preparation.

Its current conceptual sequence is:

```text
Load Drivers
      ↓
Validation
      ↓
Duplicate Filter
      ↓
Availability
      ↓
Already Offered
      ↓
Ranking
      ↓
Heap
```

The Dispatch Engine only consumes the resulting ranked candidate source.

---

# 14. Candidate Collection

Candidates are represented independently from the driver domain object.

Conceptually:

```text
Candidate
 ├── ID
 ├── State
 ├── Driver
 └── Metadata
       └── Score
```

This separation allows dispatch-specific state to exist without contaminating the driver domain model.

---

# 15. Candidate Iterator

After pipeline processing, candidates are consumed through an iterator/source boundary.

Conceptually:

```text
Ranked Candidates
       │
       ▼
Candidate Source
       │
       ▼
Next Candidate
```

The Dispatch Engine does not need to know whether the source is backed by:

- heap,
- slice,
- future streaming implementation.

---

# 16. Ranking Boundary

Ranking determines candidate preference.

The Dispatch Engine does not calculate ranking scores.

The flow is:

```text
Eligible Candidates
       │
       ▼
Ranker
       │
       ▼
Candidate Score
       │
       ▼
Heap
       │
       ▼
Best Candidate
```

See:

```text
docs/02-architecture/RANKING_ENGINE.md
```

---

# 17. Geo Boundary

Geographic discovery and refinement are delegated to the Geo/Discovery subsystems.

The dispatch engine only supplies the required search parameters.

See:

```text
docs/02-architecture/GEO_ENGINE.md
```

# 18. Candidate Selection

The Dispatch Engine consumes candidates in ranking order.

Conceptually:

```text
Best Candidate
      │
      ▼
Reserve
      │
      ├── Success → Offer
      │
      └── Failed → Next Candidate
```

This is important because ranking does not provide ownership.

---

# 19. Reservation Is the Concurrency Boundary

The reservation operation is authoritative.

Between:

```text
Rank
```

and:

```text
Reserve
```

another matching worker may select the same driver.

Therefore:

```text
Ranking = preference
Reservation = ownership
```

The dispatch engine must always respect the result of reservation.

---

# 20. Driver Reservation

The reservation abstraction provides:

```text
Reserve(driverID, rideID)
```

The expected semantics are:

```text
ONLINE
   │
   ▼
Reserve
   │
   ▼
RESERVED
```

If the driver is no longer available:

```text
Reserve
   │
   ▼
false
```

The engine should skip that candidate and continue.

---

# 21. Why Reservation Happens After Ranking

Reservation before ranking would:

- lock unnecessary drivers,
- increase contention,
- create unnecessary cleanup,
- reduce fairness,
- waste resources.

Preferred sequence:

```text
Discover
   ↓
Filter
   ↓
Rank
   ↓
Reserve only selected candidates
```

---

# 22. Reservation Failure

Reservation can fail without being an infrastructure error.

Example:

```text
Candidate ranked
      │
      ▼
Another worker reserves driver
      │
      ▼
Reserve returns false
      │
      ▼
Try next candidate
```

This is expected concurrency behaviour.

It should not automatically fail the entire matching attempt.

---

# 23. Reservation Error

A reservation infrastructure error is different from a reservation conflict.

### Conflict

```text
reserved == false
error == nil
```

Meaning:

```text
Driver unavailable
```

### Infrastructure failure

```text
error != nil
```

Meaning:

```text
Reservation mechanism failed
```

The latter should normally fail the dispatch operation rather than silently skipping all candidates.

---

# 24. Offer Persistence

Once a driver has been successfully reserved, the offer attempt must be persisted.

Conceptually:

```text
Reserve Driver
      │
      ▼
Insert Ride Driver Offer
      │
      ▼
Offer Event
```

The persisted offer record prevents the same ride from repeatedly targeting the same driver.

---

# 25. Offer Attempt Record

An offer record contains information such as:

```text
Ride ID
Driver ID
Offer Status
Attempt
```

The repository owns persistence details.

The dispatch engine supplies the required identifiers and attempt number.

---

# 26. Offer Event

After the offer has been persisted, an event is created.

Conceptually:

```text
Driver Reserved
      │
      ▼
Offer Persisted
      │
      ▼
Driver Offered Event
      │
      ▼
Outbox
      │
      ▼
Event Bus
```

The event may contain:

```text
Ride ID
Driver ID
Offer Timeout
Matching Attempt
Search Radius
```

---

# 27. Transactional Boundary

The current architecture uses a transaction for matching orchestration where durable ride/offer state is involved.

Conceptually:

```text
Transaction
   │
   ├── Read dispatch state
   ├── Insert offer
   └── Insert outbox event
```

The exact transaction lifecycle is owned by the caller/transaction manager.

---

# 28. Outbox Pattern

Offer events should use the transactional outbox pattern.

Preferred sequence:

```text
Database Transaction
       │
       ├── Offer Record
       │
       └── Outbox Record
               │
               ▼
          Commit
               │
               ▼
       Outbox Publisher
               │
               ▼
           Event Bus
```

This avoids the unsafe pattern:

```text
DB commit
   +
Kafka publish
```

where one can succeed while the other fails.

---

# 29. Reservation and Transaction Consistency

Reservation and database persistence are different systems.

For example:

```text
Redis Reservation
       +
PostgreSQL Offer
```

cannot be assumed to participate in one atomic transaction.

Therefore the dispatch engine must explicitly handle failure after reservation.

---

# 30. Failure After Reservation

Example:

```text
Reserve
  │
  ▼
Success
  │
  ▼
Insert Offer
  │
  ▼
Failure
```

The driver must not remain indefinitely reserved.

A release path is required.

Conceptually:

```text
Insert Offer Failed
      │
      ▼
Release Reservation
      │
      ▼
Return Error
```

---

# 31. Release Helper

Reservation cleanup should be isolated in a small helper rather than duplicated around every failure branch.

Conceptually:

```text
offerCandidate()
   │
   ├── reserve
   ├── persist
   ├── event
   │
   └── failure
         │
         ▼
    release helper
```

The helper should provide consistent logging and cleanup.

---

# 32. Partial Batch Offers

The dispatch engine can offer multiple drivers in one matching attempt when configured.

Conceptually:

```text
Ranked Candidates
      │
      ▼
Batch Size = N
      │
      ▼
Reserve candidate 1
Reserve candidate 2
Reserve candidate 3
...
```

Only successfully reserved candidates should become active offers.

---

# 33. Batch Size

Batch size is controlled by dispatch policy.

It should not be hard-coded in the matching engine.

Conceptually:

```text
Retry Policy
    │
    ▼
OfferBatchSize
    │
    ▼
Dispatch Engine
```

---

# 34. Adaptive Batch Size

The dispatch optimizer may eventually use:

```text
Acceptance History
+
Driver Behaviour
+
Current Supply
+
Demand
```

to determine batch size.

The current engine should consume the policy result without embedding prediction logic.

---

# 35. Dynamic Offer Timeout

Offer timeout is also policy-driven.

Conceptually:

```text
Dispatch Policy
      │
      ▼
Offer Timeout
      │
      ▼
Driver Offered Event
```

The Dispatch Engine should not independently calculate timeout from ETA or driver behaviour.

That belongs to dispatch policy.

---

# 36. Offer Lifecycle

Once an offer is created:

```text
OFFERED
   │
   ├── ACCEPTED
   │
   ├── REJECTED
   │
   └── TIMEOUT
```

The response subsystem owns the subsequent driver response lifecycle.

The Dispatch Engine's responsibility is to create the offer correctly.

---

# 37. Accepted Offer

When a driver accepts:

```text
Driver Response
      │
      ▼
Response Service
      │
      ▼
Ride Assignment
```

The exact acceptance lifecycle is outside the candidate-ranking portion of dispatch.

---

# 38. Rejected Offer

When an offer is rejected:

```text
Offer
  │
  ▼
Rejected
  │
  ▼
Reservation Release
  │
  ▼
Retry / Next Candidate
```

The response subsystem and matching retry flow coordinate the next action.

---

# 39. Timeout

A timeout is similar:

```text
Offer
  │
  ▼
Timeout
  │
  ▼
Release
  │
  ▼
Retry
```

Timeout scheduling is delegated to the timeout subsystem.

---

# 40. Already Offered Protection

A ride should not repeatedly offer the same driver unnecessarily.

The Candidate Pipeline already supports an already-offered filter.

Conceptually:

```text
Discovered Driver
      │
      ▼
Already Offered?
      │
      ├── Yes → Reject Candidate
      │
      └── No → Continue
```

This is preferable to putting duplicate-offer logic directly inside candidate selection.

---

# 41. Candidate Filter Responsibility

The Dispatch Engine should not duplicate filters.

For example, avoid:

```text
Pipeline filters unavailable drivers
        +
Matching engine checks availability again
```

unless the second check is the authoritative reservation operation.

The pipeline prepares candidates.

Reservation verifies final availability.

---

# 42. Matching Attempt Flow

A complete attempt is:

```text
Matching Started
      │
      ▼
Resolve Effective Dispatch Strategy
      │
      ▼
Count Attempts
      │
      ▼
Check Max Attempts
      │
      ▼
Retry Policy / Search Policy
      │
      ▼
Candidate Discovery
      │
      ├── Preferred stand/local candidates where applicable
      └── Broader / cross-location candidates when required
      │
      ▼
Candidate Pipeline
      │
      ▼
Strategy-Specific Prioritization / Ranking
      │
      ▼
Candidate Selection
      │
      ▼
Reservation
      │
      ▼
Offer Persistence
      │
      ▼
Outbox Event
      │
      ▼
Matching Attempt Complete
```

The resolved strategy remains authoritative throughout the attempt. Candidate expansion must not accidentally convert Smart Stand Dispatch into Smart Dispatch or otherwise discard the configured strategy semantics.

# 43. No Candidates

If discovery returns no candidates:

```text
Discovery
   │
   ▼
Empty
   │
   ▼
Retry / Expansion Policy
   │
   ├── Broaden local search
   ├── Expand to nearby locations when allowed
   └── Next Attempt
```

The system should not invent a driver.

For Smart Stand Dispatch, failure to find a suitable driver at the preferred stand does not by itself terminate matching. The configured broader candidate discovery flow may consider other eligible drivers.

# 44. No Eligible Candidates

Candidates may exist geographically but all may be removed by filtering.

Example:

```text
10 discovered
   │
   ▼
Availability / duplicate filters
   │
   ▼
0 eligible
```

This is different from geographic discovery failure.

Observability should preserve that distinction.

---

# 45. No Successful Reservations

Candidates may be ranked but all reservations can fail.

Example:

```text
5 ranked
   │
   ├── reserve false
   ├── reserve false
   ├── reserve false
   ├── reserve false
   └── reserve false
```

The attempt ends with:

```text
No Drivers Reserved
```

rather than pretending an offer was created.

---

Useful metrics include:

# 50. Performance Requirements

The dispatch critical path should minimize:

- network round trips,
- repeated Redis reads,
- repeated database reads,
- expensive ranking calls,
- unnecessary candidate processing.

The architecture already addresses this through:

```text
H3 candidate discovery
        ↓
Batch driver loading
        ↓
Candidate filters
        ↓
Ranking
        ↓
Heap
        ↓
Small reservation batch
```

---

# 51. Why Batch Loading Happens Before Ranking

Ranking may require several driver attributes.

Instead of:

```text
candidate 1 → Redis
candidate 2 → Redis
candidate 3 → Redis
```

the pipeline performs:

```text
candidate IDs
      │
      ▼
batch driver load
      │
      ▼
candidate enrichment
```

This reduces network overhead and makes ranking cheaper.

---

# 52. Why Ranking Happens Before Reservation

Reservation is an exclusive operation.

Therefore the system should avoid reserving every discovered candidate.

Preferred:

```text
100 discovered
      │
      ▼
filter
      │
      ▼
30 eligible
      │
      ▼
rank
      │
      ▼
top 3
      │
      ▼
reserve
```

---

# 53. Why Reservation Happens Near the End

Reservation should be performed only after:

- discovery,
- enrichment,
- filtering,
- ranking.

This minimizes:

- lock contention,
- cleanup,
- wasted reservations,
- concurrent conflicts.

---

# 54. Dispatch Optimizer Boundary

Adaptive dispatch policy belongs behind a policy boundary.

The optimizer may eventually decide:

```text
Batch Size
Timeout
Retry Behaviour
Radius
Candidate Limit
```

The Dispatch Engine should consume those decisions.

It should not become the optimizer.

```text
    │
```

# 56. Future Acceptance Probability

A future optimizer may use:

```text
P(driver accepts)
```

to decide:

```text

How many candidates?
How long to wait?
When to retry?
```

This should remain outside the current orchestration layer.

# 57. Future Dynamic Timeout

A future policy may combine:

```text
ETA
+
Traffic
+
Driver Response History
```

to determine timeout.

The resulting value is passed into the offer event.

The Dispatch Engine remains responsible only for applying it.

---

# 58. Future Retry Optimization

The retry system may eventually evolve from:

```text
Attempt++
Radius++
```

toward:

```text
Acceptance Probability
+
Supply
+
Demand
+
ETA
```

Again, this is a policy evolution, not a reason to complicate the current orchestration layer.

---

# 59. Reliability Model

The dispatch engine is designed around recoverable operations.

Examples:

```text
Discovery failure
    → no offer created

Reservation conflict
    → try next candidate

Persistence failure after reservation
    → release reservation

Outbox failure
    → transaction fails / reservation cleanup path
```

The implementation must ensure that failure paths do not leave drivers permanently reserved.

---

# 60. Idempotency

Matching can be triggered more than once because of:

- event delivery retries,
- worker retries,
- process crashes,
- timeout handling,
- infrastructure recovery.

Therefore the dispatch lifecycle should be designed so repeated processing does not create uncontrolled duplicate offers.

Existing persistence constraints and already-offered checks are part of this protection.

---

# 61. Event-Driven Dispatch

The surrounding system uses event-driven orchestration.

Conceptually:

```text
Ride Event
   │
   ▼
Event Router
   │
   ▼
Matching Engine
   │
   ▼
Offer Outbox Event
   │
   ▼

```

This keeps dispatch processing decoupled from external consumers.

---

# 62. Transaction Ownership

The Dispatch Engine should not arbitrarily create nested transactions if the caller already owns the transaction boundary.

The current architecture passes the transaction into matching orchestration where required.

This preserves consistency with the surrounding event-processing workflow.

---

# 63. Repository Boundaries

The dispatch engine consumes repository interfaces rather than concrete database implementations.

Examples:

```text

CandidateSearcher
```

This makes the orchestration layer independently testable.

# 67. Offer Candidate Helper

Offer creation should be isolated from the main matching orchestration.

Conceptually:

```text

      │
      ▼

      │
      ├── Reserve
      ├── Persist offer
      ├── Build event
      ├── Marshal event
      ├── Insert outbox
      └── Cleanup on failure
```

This keeps `HandleMatchingStarted` focused on orchestration.

# 68. Main Matching Method

The main method should read approximately like a workflow:

```text
count attempt
check retry boundary
get retry decision
discover candidates
run candidate pipeline
get dispatch decision
offer candidates
return result
```

It should not contain every low-level persistence and event-building detail inline.

# 69. Avoiding Overengineering

The Dispatch Engine should remain intentionally small.

- a generic state machine framework,
- a generic transaction orchestration framework,
- multiple layers of factories for simple helpers,
- speculative distributed locking abstractions.

The current interfaces are sufficient until real complexity justifies additional boundaries.

```text
Candidate excluded
```

### No permanent reservation on offer failure

```text
Offer creation failure
    ⇒
Reservation cleanup attempted
```

```text
High score
    ≠

```

### Retry policy controls adaptive parameters

```text
Dispatch Engine
    consumes

```

It does not duplicate the policy.

# 75. Common Implementation Mistakes

## Mistake 1 — Reserving before ranking

This creates unnecessary contention.

---

## Mistake 2 — Treating reservation conflict as infrastructure failure

A false reservation result is normal concurrency behaviour.

---

## Mistake 3 — Persisting offer before reservation

This can create an offer for a driver that was never secured.

---

## Mistake 4 — Publishing Kafka event directly after DB work

Use the outbox pattern.

---

## Mistake 5 — Leaving a driver reserved after failure

Every post-reservation failure path must consider cleanup.

---

## Mistake 6 — Reimplementing candidate filters in MatchingEngine

Filters belong to the Candidate Pipeline.

---

## Mistake 7 — Reimplementing ranking in MatchingEngine

Ranking belongs to the Ranking Engine.

---

## Mistake 8 — Reimplementing geo lookup

Discovery owns spatial search.

---

## Mistake 9 — Hard-coding batch size or timeout

These are dispatch policy outputs.

---

## Mistake 10 — Making the main matching method enormous

Low-level offer creation belongs in a focused helper.

---

## Rule 1 — Preserve Orchestration

Keep MatchingEngine focused on coordinating existing components.

---

## Rule 2 — Do Not Duplicate Subsystems

Do not move ranking, filtering, discovery, or geo logic into MatchingEngine.

---

## Rule 3 — Reservation Is Authoritative

Never assume that a ranked candidate remains available.

---

## Rule 4 — Cleanup Matters

Any successful reservation followed by a failure must have an explicit cleanup path.

---

## Rule 5 — Outbox for Offer Events

Do not bypass the outbox for durable dispatch events.

---

## Rule 6 — Policy Over Constants

Do not hard-code:

- batch size,
- timeout,
- radius,
- retry thresholds.

---

## Rule 7 — Keep the Main Workflow Readable

Prefer:

```text
discover
→ pipeline
→ select
→ offer
```

over deeply nested implementation details.

---

## Rule 8 — Resolve Configuration Before Strategy Execution

Do not hard-code a dispatch strategy at a geographic level.

Always resolve the effective strategy by walking the applicable configuration hierarchy from the most specific level upward.

---

## Rule 9 — Smart Stand Dispatch Is Not Stand-Only

Never implement Smart Stand Dispatch as:

```text
stand drivers only
```

The correct interpretation is:

```text
stand-preferred
→ broader eligible candidates when required
```

A driver outside the preferred stand can be considered when the stand cannot provide a suitable driver.

---

## Rule 10 — Do Not Treat Strategy as a Hard Geographic Boundary

The resolved strategy determines how candidates are prioritized, not necessarily which geographic location's drivers are eligible to be discovered.

Cross-location expansion may consider nearby-location drivers when local supply is insufficient.

---

## Rule 11 — Preserve Candidate Location Strategy Context

When cross-location candidates are considered, do not assume that every candidate belongs to the origin location's configuration.

The applicable location/configuration context must be respected when applying strategy-specific prioritization.

---

## Rule 12 — Keep AI as an Optimization Layer

AI-assisted dispatch is not a third primary dispatch strategy.

AI may influence ranking, prediction, or optimization while the resolved dispatch strategy and hard eligibility constraints remain authoritative.

---

## Rule 8 — Avoid Speculative Abstractions

Introduce a new abstraction only when it represents a real boundary or removes meaningful complexity.

# 81. Final Summary

The RideForge Dispatch Engine is the orchestration layer connecting discovery, candidate processing, ranking, reservation, and offer creation.

Its core flow is:

```text
Matching Started
      │
      ▼
Attempt / Retry Policy
      │
      ▼
Candidate Discovery
      │
      ▼
Candidate Pipeline
      │
      ▼
Ranking
      │
      ▼
Candidate Selection
      │
      ▼
Reservation
      │
      ▼
Offer Persistence
      │
      ▼
Outbox Event
```

The most important architectural rules are:

1. **MatchingEngine orchestrates; specialized components implement.**
2. **Candidate discovery happens before ranking.**
3. **Ranking happens before reservation.**
4. **Reservation is the authoritative concurrency boundary.**
5. **No successful reservation means no active offer.**
6. **Post-reservation failures must trigger cleanup.**
7. **Offer events use the transactional outbox.**
8. **Retry, batch size, timeout, and radius are policy-driven.**
9. **Do not duplicate discovery, filtering, ranking, or geo logic.**
10. **Keep the main matching workflow readable and small.**
11. **Prefer existing abstractions over speculative new layers.**
12. **Before implementing roadmap items, inspect the current code and mark already-completed capabilities as complete.**

Additional dispatch-strategy invariants are:

13. **Resolve the most-specific explicit dispatch configuration before strategy execution.**
14. **Smart Stand Dispatch is stand-preferred, not stand-exclusive.**
15. **Smart Dispatch is stand-agnostic.**
16. **Dispatch strategy does not automatically define a hard candidate-location boundary.**
17. **Cross-location candidates remain subject to eligibility, legal, geographic, and strategy-specific rules.**
18. **AI-assisted dispatch enhances an existing strategy; it is not a third primary strategy.**

The result is a dispatch orchestration layer that is production-oriented, concurrency-aware, observable, configuration-driven, capable of cross-location candidate expansion, and able to evolve toward adaptive and ML-assisted dispatch without forcing speculative complexity into the current system.
