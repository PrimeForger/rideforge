# RideForge Discovery Engine

> **Document:** `docs/02-architecture/DISCOVERY_ENGINE.md`\
> **Status:** Active architecture documentation\
> **Scope:** Candidate discovery, H3-based search, adaptive expansion,
> candidate lookup, and geo refinement\
> **Audience:** Backend developers, architects, reviewers, and AI coding
> agents

------------------------------------------------------------------------

# 1. Executive Summary

The RideForge Discovery Engine is responsible for finding a bounded set
of driver candidates that are geographically relevant to a ride request.

Its responsibility ends at **candidate discovery and refinement**. It
supports the dispatch engine after the effective dispatch strategy has
already been resolved from the hierarchical configuration.

The Discovery Engine does not resolve business configuration and does
not perform final driver ranking. It receives the resolved dispatch
context and discovers candidates according to the applicable search
scope and expansion rules.

It does not:

- resolve the hierarchical dispatch configuration,
- decide the effective dispatch strategy,
- rank drivers,
- decide which driver receives an offer,
- reserve drivers,
- publish offers,
- calculate business-level dispatch policy.

The Discovery Engine is intentionally separated from the Candidate
Pipeline, Ranking Engine, and Matching Engine.

The high-level flow is:

```text
Ride Request
    │
    ▼
Resolved Dispatch Context
    │
    ├── Smart Stand Dispatch
    │       ├── Stand-aware preferred search
    │       └── Broader search when required
    │
    └── Smart Dispatch
            └── Normal nearby-driver search
    │
    ▼
Candidate Discovery
    │
    ├── Local location search
    ├── Stand-aware search when applicable
    └── Nearby-location expansion when required
    │
    ▼
Candidate IDs + Discovery Context
    │
    ▼
Geo Refinement
    │
    ├── No-op refinement
    └── Redis GEO refinement
    │
    ▼
Candidate Collection
    │
    ▼
Candidate Pipeline / Strategy-specific Prioritization
```

The engine is designed around the principle:

> **Use inexpensive spatial indexing to find a bounded set of eligible
> geographic candidates, preserve the context required for
> strategy-specific prioritization, and progressively refine the set
> before expensive enrichment and ranking.**

# 2. Purpose

The Discovery Engine answers:

> **Which drivers are geographically relevant enough to enter the
> dispatch candidate pipeline?**

This is intentionally different from:

> Which driver is best?

The first question belongs to Discovery.

The second belongs to Ranking.

------------------------------------------------------------------------

# 3. Goals

The Discovery Engine has the following goals.

## 3.1 Low-latency discovery

Candidate discovery must be fast enough to participate in the ride
dispatch critical path.

------------------------------------------------------------------------

## 3.2 Bounded work

Discovery should not scan an unbounded geographic area or unbounded
number of drivers.

Search is controlled by:

-   radius,
-   candidate limit,
-   search rings,
-   expansion profile,
-   search budget.

------------------------------------------------------------------------

## 3.3 Progressive search

The engine should search the nearest useful area first.

Conceptually:

``` text
Ring 0
  │
  ├── enough candidates? ──► stop
  │
  ▼
Ring 1
  │
  ├── enough candidates? ──► stop
  │
  ▼
Ring 2
  │
  └── continue until budget / requirement is satisfied
```

This avoids doing unnecessary work in dense regions.

------------------------------------------------------------------------

## 3.4 Density awareness

Driver density affects how aggressively the search should expand.

Dense region:

``` text
Small search area
    │
    ▼
Enough candidates
    │
    ▼
Stop
```

Sparse region:

``` text
Small search area
    │
    ▼
Not enough candidates
    │
    ▼
Expand faster
```

------------------------------------------------------------------------

## 3.5 Replaceable search implementations

The application should not depend directly on H3 implementation details.

The search boundary is represented through a strategy abstraction.

This allows alternative discovery implementations without changing the
Matching Engine.

------------------------------------------------------------------------

## 3.6 Refinement after coarse discovery

H3 is a spatial index.

It should not be treated as the final travel-distance calculation.

The architecture therefore supports a refinement stage after coarse
candidate discovery.

``` text
H3
 │
 ▼
Candidate IDs
 │
 ▼
Geo Refinement
 │
 ▼
Candidate IDs
```

------------------------------------------------------------------------

# 4. Non-Goals

The Discovery Engine does not own:

-   candidate scoring,
-   driver quality calculation,
-   ETA ranking,
-   offer batch selection,
-   offer timeout calculation,
-   driver reservation,
-   ride-driver offer persistence,
-   driver acceptance handling.

Those responsibilities belong elsewhere.

------------------------------------------------------------------------

# 5. Architectural Boundaries

The Discovery Engine sits inside the dispatch flow after dispatch
strategy resolution and before candidate enrichment, prioritization,
ranking, and assignment.

```text
Ride Request
      │
      ▼
Dispatch Strategy Resolution
      │
      ▼
Resolved Dispatch Context
      │
      ▼
Candidate Searcher
      │
      ├──────────────────────┐
      ▼                      ▼
Smart Stand Context     Smart Dispatch Context
      │                      │
      ▼                      ▼
Stand-preferred          Normal nearby
search                   search
      │                      │
      └──────────┬───────────┘
                 ▼
        Nearby Location Expansion
                 │
                 ▼
          Geo Refinement
                 │
                 ▼
        Candidate Collection
                 │
                 ▼
       Candidate Pipeline / Ranking
```

The important boundary is:

```text
Configuration Resolution
        ≠
Candidate Discovery
        ≠
Candidate Ranking
```

The Dispatch Engine resolves the effective strategy. Discovery uses
that resolved context to determine the appropriate candidate search and
expansion behavior. Ranking and strategy-specific prioritization remain
outside Discovery.

The Discovery Engine must not interpret a dispatch strategy as a hard
candidate boundary.

For example, Smart Stand Dispatch does not mean that only drivers at an
auto stand may be discovered. When stand supply is unavailable or
unsuitable, discovery may expand to other eligible drivers according to
the dispatch flow.

Likewise, a location using one strategy is not automatically isolated
from nearby locations using another strategy. Cross-location discovery
may include eligible drivers from nearby locations when local supply
cannot satisfy the ride.

The Matching Engine does not need to know whether discovery used H3,
Redis GEO, another spatial index, stand-aware search, nearby-location
expansion, or a fallback strategy. It consumes the search contract and
discovery metadata.

# 6. Core Search Contract

The discovery boundary is represented by a candidate searcher.

Conceptually:

``` go
type CandidateSearcher interface {
    FindCandidates(
        ctx context.Context,
        req search.Request,
    ) (search.Result, error)
}
```

The exact implementation may change, but the responsibility remains
stable.

------------------------------------------------------------------------

# 7. Search Request

A discovery request contains the information necessary to perform
spatial candidate discovery together with the already-resolved dispatch
context needed to choose the appropriate discovery path.

Conceptually:

```go
type Request struct {
    PickupLat float64
    PickupLng float64

    RadiusKm float64

    CandidateLimit int

    MatchingAttempt int

    EffectiveStrategy Strategy
    OriginLocationID LocationID

    StandContext *StandContext
    ExpansionContext ExpansionContext
}
```

The exact types may evolve. The important principle is that Discovery
receives **resolved dispatch context**, not responsibility for resolving
business configuration itself.

Discovery may need to know:

- the effective dispatch strategy,
- the origin location,
- the applicable stand context when Smart Stand Dispatch applies,
- whether broader/cross-location expansion is allowed,
- configured search and expansion limits.

It must not independently walk the configuration hierarchy and choose a
strategy. That responsibility belongs to Dispatch Strategy Resolution.

# 8. Search Result

The result represents discovered candidates plus useful discovery and
source-context metadata.

Conceptually:

```go
type Result struct {
    Candidates *candidate.Collection

    Backend string

    RadiusKm float64

    RingsVisited int

    CellsVisited int

    LocationsVisited int
    StandsVisited int
}
```

Candidate/source metadata may also preserve information such as:

```text
Origin Location
Candidate Location
Stand ID (when applicable)
Stand Queue Position (when applicable)
Discovery Source
```

The Discovery Engine should preserve this information when it is needed
by downstream strategy-specific prioritization. It should not turn that
metadata into final ranking decisions itself.

The metadata is useful for observability, debugging, performance
analysis, strategy-specific prioritization, cross-location analysis,
and future dispatch optimization.

# 9. Candidate Representation

Discovery produces candidate identities together with lightweight
context required by downstream dispatch processing.

```text
Candidate
├── ID
├── State
├── Driver
└── Metadata
```

At discovery time, the important field is primarily:

```text
ID
```

When relevant, metadata may identify:

```text
Candidate Location
Source Stand
Stand Queue Position
Discovery Scope / Source
```

This is especially important for Smart Stand Dispatch and
cross-location dispatch. Discovery should preserve the facts needed to
apply stand preference and compare candidates later, without performing
final ranking itself.

Driver enrichment happens later in the Candidate Pipeline.

This keeps spatial discovery from becoming a driver-data loading
subsystem.

# 10. H3 Discovery Architecture

The primary production-oriented discovery path uses H3.

The conceptual flow is:

``` text
Pickup Coordinates
       │
       ▼
H3 Service
       │
       ▼
Initial Cell
       │
       ▼
Adaptive Ring Expansion
       │
       ▼
H3 Driver Index
       │
       ▼
Driver IDs
```

------------------------------------------------------------------------

# 11. H3 Service

The H3 service owns geographic cell operations.

Responsibilities include:

-   converting coordinates to H3 cells,
-   determining neighboring cells,
-   calculating search rings,
-   providing H3-related geographic operations.

Discovery components should not duplicate H3 calculations.

------------------------------------------------------------------------

# 12. H3 Driver Index

The H3 driver index maps active drivers to H3 cells.

Conceptually:

``` text
Driver
  │
  ▼
Current H3 Cell
  │
  ▼
Redis Set
```

Candidate discovery then performs:

``` text
Pickup
  │
  ▼
H3 Cell
  │
  ▼
Nearby Cells
  │
  ▼
Driver IDs
```

The driver index is a spatial lookup structure, not the source of truth
for driver state.

------------------------------------------------------------------------

# 13. Driver Cache

The driver cache contains real-time driver information.

The architecture separates:

``` text
H3 Index
    =
Where might the driver be?

Driver Cache
    =
What is the driver's current operational state?
```

This separation is important.

The H3 index should remain optimized for spatial lookup.

The cache should remain optimized for real-time driver information.

------------------------------------------------------------------------

# 14. Adaptive Ring Expansion

The search should not blindly search a fixed maximum ring.

Instead:

``` text
Ring 0
  │
  ▼
Enough candidates?
  │
  ├── Yes ──► Stop
  │
  └── No
        │
        ▼
      Ring 1
        │
        ▼
      Enough?
        │
        └── Continue
```

The expansion policy determines how far the search should progress.

------------------------------------------------------------------------

# 15. Expansion Profile

The discovery architecture contains an expansion profile layer.

The profile describes how search should behave for the current
geographic conditions.

Conceptually:

``` text
Driver Density
      │
      ▼
Density Classifier
      │
      ▼
Expansion Profile
      │
      ▼
Adaptive Ring Expansion Policy
```

This allows sparse and dense areas to behave differently without
embedding density logic directly into the H3 search implementation.

------------------------------------------------------------------------

# 16. Density Classification

The current architecture supports density-aware classification.

Conceptually:

``` text
Driver Count
     │
     ▼
Density Classifier
     │
     ├── Sparse
     ├── Normal
     └── Dense
```

The thresholds are configuration-driven.

They should not be hard-coded inside discovery algorithms.

------------------------------------------------------------------------

# 17. Profile Selection

The profile pipeline evaluates the discovery context and selects the
appropriate expansion profile.

The architecture currently uses a profile pipeline and selector.

Conceptually:

``` text
Density Information
        │
        ▼
Density Rule
        │
        ▼
Profile Pipeline
        │
        ▼
Profile Selector
        │
        ▼
Expansion Profile
```

This keeps policy separate from the ring traversal mechanism.

------------------------------------------------------------------------

# 18. Ring Expansion Policy

The ring expansion policy decides how the search progresses.

It should answer questions such as:

-   Which ring should be searched next?
-   How aggressively should the search expand?
-   When should expansion stop?
-   What limits apply?

It should not:

-   load driver objects,
-   rank drivers,
-   reserve drivers,
-   publish offers.

------------------------------------------------------------------------

# 19. Search Budget

Search budget exists to prevent discovery from doing unbounded work.

A budget may constrain:

-   maximum ring,
-   candidate count,
-   cells visited,
-   other bounded search work.

Conceptually:

``` text
Search Request
      │
      ▼
Budget Factory
      │
      ▼
Search Budget
      │
      ▼
Ring Expansion
```

The budget is an operational guardrail.

It should remain independent from candidate ranking.

------------------------------------------------------------------------

# 20. H3 Strategy

The H3 strategy coordinates:

- H3 service,
- ring expansion,
- expansion policy,
- search budget,
- driver index,
- refinement.

It is an orchestration component for H3 discovery.

It is a **spatial discovery mechanism, not a business dispatch
strategy**. The same H3 implementation may support both Smart Dispatch
and Smart Stand Dispatch.

For Smart Stand Dispatch, H3 discovery may first target the preferred
stand context when the rider is inside a configured stand radius. If
that preferred source cannot provide suitable supply, the discovery
flow may expand to broader eligible drivers and nearby locations.

H3 must not become a general-purpose Matching Engine or encode final
driver ranking.

# 21. Alternate Geo Strategy

The architecture also supports a Geo Strategy.

Conceptually:

```text
CandidateSearcher
       │
       ├── H3 Strategy
       │
       └── Geo Strategy
```

The selected spatial strategy can be controlled through infrastructure
or search configuration.

The alternate strategy must preserve the same dispatch semantics and
search contract as H3. It must not reinterpret Smart Stand Dispatch as
stand-only or Smart Dispatch as a different candidate boundary.

The Matching Engine remains unaware of the concrete implementation.

# 22. Strategy Selection

There are two different kinds of strategy selection in the dispatch
architecture and they must not be conflated.

## 22.1 Dispatch Strategy Resolution

The Dispatch Engine resolves the business dispatch strategy from the
hierarchical configuration:

```text
Most Specific Configuration
        ↓
First Explicit Strategy
        ↓
Effective Dispatch Strategy
```

The result is one of the primary dispatch strategies:

```text
Smart Stand Dispatch
Smart Dispatch
```

Discovery does **not** walk the configuration hierarchy to make this
decision.

## 22.2 Spatial Discovery Strategy Selection

Discovery then selects the spatial mechanism used to execute the
resolved dispatch context:

```text
Resolved Dispatch Context
        ↓
Spatial Search Strategy
        ├── H3
        └── Alternate Geo Strategy
```

Therefore:

```text
Dispatch Strategy
    ≠
Spatial Search Strategy
```

Smart Stand Dispatch and Smart Dispatch may use the same underlying H3
search implementation while applying different discovery scopes and
candidate-source contexts.

## 22.3 Strategy-Aware Discovery

### Smart Stand Dispatch

When the rider is inside a configured stand radius, discovery first
identifies candidates associated with the preferred stand.

```text
Rider Pickup
     │
     ▼
Inside Stand Radius?
     │
     ├── YES → Preferred Stand Candidates
     │              │
     │              ├── Suitable supply → continue
     │              └── Insufficient / unsuitable
     │                         ↓
     │                   Broader Candidate Search
     │
     └── NO  → Normal Eligible Nearby Search
```

The preferred stand is a **preferred discovery source, not an exclusive
candidate pool**.

If suitable stand supply is unavailable, discovery may consider nearby
stands, drivers outside stands, and drivers from nearby locations,
subject to configured expansion and hard eligibility constraints.

Discovery preserves stand/source context for downstream prioritization.

### Smart Dispatch

Smart Dispatch is stand-agnostic. Discovery searches for eligible
nearby drivers without using auto-stand membership as a preference.

```text
Ride Pickup
     ↓
Eligible Nearby Drivers
     ↓
Candidate Pipeline
```

### Cross-Location Dispatch

If the originating location cannot provide a suitable driver, discovery
may expand into nearby locations.

```text
Location A
    ↓
No suitable local candidate
    ↓
Expand search
    ↓
Location B / C / ...
    ↓
Eligible candidates
```

The strategy configured for a nearby candidate's location does not make
that candidate automatically ineligible. Its location/stand context is
preserved so downstream dispatch prioritization can apply the applicable
strategy rules.

For example, if Location B uses Smart Stand Dispatch, both an eligible
stand driver and an eligible non-stand driver from B may enter the
candidate flow. Discovery does not make the final comparison; it
preserves the context needed for the downstream decision.

The critical rule is:

```text
Dispatch Strategy
        ≠
Candidate Discovery Boundary
```

Cross-location discovery must still respect legal/regional rules,
driver eligibility, availability, service constraints, geographic
limits, and configured expansion limits.

# 23. Geo Refinement

H3 provides coarse geographic candidate discovery.

The architecture now provides a refinement boundary.

``` text
H3
 │
 ▼
Candidate IDs
 │
 ▼
Refiner
 │
 ├── NoopRefiner
 │
 └── RedisGeoRefiner
 │
 ▼
Refined Candidate IDs
```

The refiner is intentionally separate from H3.

------------------------------------------------------------------------

# 24. Why Refinement Exists

H3 cells are excellent for fast spatial indexing.

They are not intended to replace precise geographic distance or routing
calculations.

The architecture therefore separates:

``` text
Coarse Discovery
```

from:

``` text
Precise Refinement
```

This enables future implementations such as:

-   Redis GEO,
-   precise distance calculation,
-   routing-aware refinement.

------------------------------------------------------------------------

# 25. Refiner Contract

The refinement boundary should remain small.

Conceptually:

``` go
type Refiner interface {
    Refine(
        ctx context.Context,
        result search.Result,
        req search.Request,
    ) (search.Result, error)
}
```

The refiner should preserve discovery metadata when transforming
candidates.

------------------------------------------------------------------------

# 26. No-op Refinement

A no-op implementation is useful when refinement is disabled or not
required.

Its behaviour is:

``` text
Input Candidates
      │
      ▼
Noop Refiner
      │
      ▼
Same Candidates
```

It should not add unrelated behaviour.

------------------------------------------------------------------------

# 27. Redis GEO Refinement

Redis GEO can act as a secondary spatial refinement mechanism.

Conceptually:

``` text
H3
 │
 ▼
Coarse Candidate IDs
 │
 ▼
Redis GEO
 │
 ▼
Refined Candidate IDs
```

Redis GEO should not replace H3 in the current architecture.

H3 remains the primary spatial partition/index.

------------------------------------------------------------------------

# 28. Why H3 and Redis GEO are Complementary

The two structures serve different purposes.

  Technology     Primary Responsibility
  -------------- ----------------------------------------------
  H3             Spatial partitioning and candidate discovery
  Redis GEO      Geographic refinement
  Driver Cache   Real-time driver state
  PostgreSQL     Durable source of truth

This separation prevents one data structure from becoming responsible
for everything.

------------------------------------------------------------------------

The complete discovery flow is:

```text
Ride Request
    │
    ▼
Resolve Effective Dispatch Strategy
    │
    ▼
Resolved Dispatch Context
    │
    ▼
Candidate Discovery Scope
    │
    ├── Smart Stand: preferred stand when applicable
    ├── Smart Stand: broader search when required
    └── Smart Dispatch: normal nearby search
    │
    ▼
Spatial Strategy
    │
    ├── Density Classification
    ├── Profile Selection
    ├── Ring Expansion
    ├── Budget
    └── H3 / Alternate Geo Index
    │
    ▼
Candidate IDs + Source Context
    │
    ▼
Cross-Location Expansion when required
    │
    ▼
Geo Refinement
    │
    ▼
Candidate Collection
    │
    ▼
Candidate Pipeline
    │
    ▼
Strategy-specific Prioritization / Ranking
```

The flow intentionally avoids expensive operations until the candidate
set has been bounded.

The discovery layer does not resolve hierarchical configuration and
does not perform final candidate ranking.

# 30. Discovery Does Not Rank

This is a critical architectural boundary.

Discovery should never do:

``` text
Driver A = score 0.92
Driver B = score 0.87
```

Discovery only determines:

``` text
Driver A
Driver B
Driver C
```

Ranking happens later.

------------------------------------------------------------------------

# 31. Discovery Does Not Reserve

Discovery must never call:

``` text
Reserve(driver)
```

Reservation belongs to Matching / offer orchestration.

This prevents spatial lookup from becoming coupled to dispatch state
transitions.

------------------------------------------------------------------------

# 32. Discovery Does Not Publish Offers

Discovery must never publish:

``` text
DriverOfferedEvent
```

Discovery ends before offer selection.

------------------------------------------------------------------------

# 33. Discovery and Candidate Pipeline Boundary

The boundary is:

``` text
Discovery
    │
    │ Candidate IDs
    ▼
Candidate Pipeline
```

Discovery answers:

> Who is geographically relevant?

Pipeline answers:

> Which discovered candidates are valid and how should they be
> enriched/ranked?

------------------------------------------------------------------------

# 34. Performance Model

The Discovery Engine is on the critical path.

Performance should therefore be considered at every level.

## Primary costs

``` text
H3 lookup
+
Redis cell lookup
+
Candidate set processing
+
Optional geo refinement
```

The architecture should avoid:

``` text
N candidates
×
N Redis requests
```

where a batch operation can be used.

------------------------------------------------------------------------

# 35. Bounded Candidate Discovery

Candidate limits should be respected.

If the caller requests:

``` text
CandidateLimit = 50
```

the discovery engine should not intentionally scan thousands of
candidates unless required by the search algorithm and its configured
budget.

The purpose of the limit is to bound downstream work.

------------------------------------------------------------------------

# 36. Progressive Search Performance

Progressive rings reduce unnecessary work.

Dense area:

``` text
Ring 0
  │
  ▼
Enough
  │
  ▼
Stop
```

Sparse area:

``` text
Ring 0
  │
  ▼
Ring 1
  │
  ▼
Ring 2
```

This allows the same engine to behave appropriately across different
geographic environments.

------------------------------------------------------------------------

# 37. Redis Round Trips

Discovery should prefer batched or pipelined Redis operations where
practical.

Avoid:

``` text
cell 1 → Redis
cell 2 → Redis
cell 3 → Redis
```

Prefer:

``` text
cell 1 ─┐
cell 2 ─┼─► Redis Pipeline
cell 3 ─┘
```

The exact implementation belongs to the infrastructure layer.

------------------------------------------------------------------------

# 38. Driver Cache Loading

Discovery should not individually load complete driver records.

Avoid:

``` text
Candidate 1 → Redis
Candidate 2 → Redis
Candidate 3 → Redis
```

The Candidate Pipeline owns batch driver loading.

The discovery boundary remains lightweight.

------------------------------------------------------------------------

# 41. Failure Handling

## H3 failure

If H3 lookup fails:

``` text
Discovery
   │
   ▼
Error
   │
   ▼
Matching fails / retry mechanism handles it
```

The engine should not silently fabricate candidates.

------------------------------------------------------------------------

## Refinement failure

If refinement is part of the required dispatch path, its failure should
be surfaced rather than silently producing an invalid result.

If a no-op refiner is configured, there is naturally no refinement
failure.

The fallback policy should be explicit rather than hidden.

------------------------------------------------------------------------

# 42. Consistency Considerations

The H3 index and driver cache are real-time operational structures.

They can temporarily diverge.

Therefore:

``` text
H3 membership
```

does not imply:

``` text
Driver is currently eligible
```

The Candidate Pipeline performs subsequent validation and availability
filtering.

This is intentional.

Discovery is allowed to return a candidate that later becomes
ineligible.

------------------------------------------------------------------------

# 43. Race Conditions

Driver movement can happen while a ride is being dispatched.

The system therefore must not assume:

``` text
Discovered = Reserved
```

The reservation operation remains authoritative for the final
concurrency decision.

Conceptually:

``` text
Discover

↓

Filter

↓

Rank

↓

Reserve

↓

Offer
```

A driver can disappear or become reserved between these stages.

The system must handle that normally.

# 47. Relationship with Ranking

Discovery and Ranking intentionally remain separate.

``` text
Discovery
    │
    ▼
Candidate Set
    │
    ▼
Ranking
```

Discovery may provide geographic information that ranking consumes, but
Discovery does not calculate the final dispatch score.

# 48. Relationship with Retry Policy

Retry Policy determines when Discovery should attempt another search.

For example:

```text
Attempt 1
   │
   ▼
Local / preferred search
   │
   ▼
No suitable candidates
   │
   ▼
Attempt 2
   │
   ▼
Broader search / nearby-location expansion
```

Retry policy should not duplicate the expansion logic inside Discovery.

Retry and expansion must preserve the **effective dispatch strategy**.
A retry must not silently convert Smart Stand Dispatch into Smart
Dispatch or vice versa unless such a strategy transition is explicitly
configured as a business fallback.

Cross-location expansion is distinct from strategy resolution:

```text
Strategy Resolution
    = Which dispatch strategy applies?

Expansion / Retry
    = How far should candidate discovery extend?
```

# 54. What Should Not Be Added Prematurely

Do not introduce the following merely to make Discovery appear more
sophisticated:

-   Multiple redundant spatial indexes
-   Distributed cell ownership
-   Regional routing
-   ML-based candidate selection
-   Complex caching layers
-   Speculative provider abstractions
-   Per-candidate network calls
-   Ranking logic inside Discovery

These belong to later stages only when there is a concrete requirement.

# 55. AI Agent Implementation Rules

AI coding agents working on Discovery must read:

```text
PROJECT_VISION.md

MATCHING_RULES.md
```

and, when changing dispatch configuration or AI-assisted behavior, the

project context-loading instructions before modifying this subsystem.

## Rule 1 — Preserve boundaries

Do not move ranking logic into Discovery.

## Rule 2 — Preserve strategy abstraction

Do not make Matching Engine depend directly on H3.

## Rule 3 — Preserve refinement abstraction

Do not embed Redis GEO directly into H3 traversal logic.

## Rule 4 — Do not bypass the Candidate Pipeline

Discovery should return candidates to the pipeline.

## Rule 5 — Do not load full driver objects unnecessarily

Discovery should remain identity-oriented, while preserving the small
amount of source context required downstream.

## Rule 6 — Prefer bounded work

Respect candidate limits, search budgets, configured expansion limits,
and cross-location limits.

## Rule 7 — Avoid speculative abstractions

Do not introduce an abstraction unless it represents a real
architectural boundary or a concrete requirement.

## Rule 8 — Preserve metadata

When transforming search results, preserve useful discovery metadata
such as backend, radius, rings visited, cells visited, candidate
location, source stand, and relevant queue/source context.

## Rule 9 — Do not make Smart Stand Dispatch stand-only

Smart Stand Dispatch is **stand-preferred, not stand-exclusive**.
When the preferred stand cannot provide suitable supply, broader
eligible candidates may be discovered according to configured expansion
rules.

## Rule 10 — Do not make dispatch strategy a geographic boundary

A driver's association with another nearby location does not by itself
make the driver ineligible. Cross-location discovery is allowed when
configured expansion requires it and hard constraints permit it.

## Rule 11 — Do not resolve configuration inside Discovery

Discovery must not independently walk the configuration hierarchy to
determine Smart Stand Dispatch versus Smart Dispatch. The effective
strategy must already have been resolved by the Dispatch Engine using
hierarchical configuration inheritance.

## Rule 12 — Preserve candidate source context

When a candidate originates from a stand or another location, preserve
the source context required by downstream prioritization and ranking.

# 56. Common Implementation Mistakes

## Mistake 1

Putting ranking inside H3.

Incorrect:

```text
H3 → Rank → Return
```

Correct:

```text
H3 → Candidates → Pipeline → Rank
```

## Mistake 2

Loading drivers individually during discovery.

Incorrect:

```text
H3
 ↓
Redis driver lookup × N
```

Correct:

```text
H3
 ↓
Candidate IDs
 ↓
Batch Driver Loader
```

## Mistake 3

Treating H3 as precise routing.

Incorrect:

```text
H3 distance = ETA
```

H3 is a spatial index.

## Mistake 4

Making Redis GEO the primary discovery mechanism.

Current architecture:

```text
H3 = primary discovery
Redis GEO = refinement
```

## Mistake 5

Allowing discovery to reserve drivers.

Reservation belongs to dispatch orchestration.

## Mistake 6

Treating Smart Stand Dispatch as stand-only discovery.

Incorrect:

```text
Rider inside stand radius
 ↓
Only stand drivers are ever considered
```

Correct:

```text
Prefer stand candidates
 ↓
If insufficient, expand to other eligible candidates
```

## Mistake 7

Treating the origin location as a hard candidate boundary.

Incorrect:

```text
Ride in Location A
 ↓
Never consider Location B drivers
```

Correct:

```text
Search Location A
 ↓
If insufficient, expand to nearby eligible locations
```

## Mistake 8

Letting Discovery resolve dispatch configuration.

Incorrect:

```text
Discovery
 ↓
Walk configuration hierarchy
 ↓
Choose Smart Stand / Smart Dispatch
```

Correct:

```text
Dispatch Engine
 ↓
Resolve effective strategy
 ↓
Discovery uses resolved context
```

## Mistake 9

Using Discovery to decide the final best driver.

Discovery may preserve queue, stand, location, distance, and other
source context, but final prioritization and ranking belong downstream.

# 57. Architectural Decisions

The following decisions are important enough to be recorded as ADRs.

### ADR --- H3 as Primary Spatial Index

H3 provides efficient spatial partitioning and supports bounded
ring-based discovery.

------------------------------------------------------------------------

### ADR --- Separate Discovery from Ranking

Discovery determines geographic relevance.

Ranking determines candidate preference.

------------------------------------------------------------------------

### ADR --- Separate Refinement from H3

Refinement allows more precise geographic filtering without coupling H3
traversal to a specific implementation.

------------------------------------------------------------------------

### ADR --- Candidate IDs Before Enrichment

Discovery returns identities first and lets the Candidate Pipeline
perform batch enrichment.

------------------------------------------------------------------------

### ADR --- Bootstrap Composition

Infrastructure and strategy composition belongs in bootstrap/builders
rather than inside business components.

------------------------------------------------------------------------

# 60. Final Summary

The RideForge Discovery Engine is a bounded, strategy-aware spatial
candidate discovery subsystem.

Its responsibility is deliberately narrow:

```text
Find geographically relevant candidates and preserve the context
required for downstream dispatch prioritization.
```

It uses:

```text
H3
+
Adaptive Expansion
+
Density Awareness
+
Search Budgets
+
Geo Refinement
+
Cross-Location Expansion when required
```

and produces:

```text
Candidate IDs
+
Discovery / Source Context
```

for the Candidate Pipeline.

The most important architectural boundaries are:

```text
Configuration Hierarchy
        │
        ▼
Effective Dispatch Strategy
        │
        ▼
Candidate Discovery Scope
        │
        ▼
Candidate IDs + Source Context
        │
        ▼
Candidate Pipeline
        │
        ▼
Strategy-specific Prioritization / Ranking
        │
        ▼
Assignment
```

The key business rule is:

```text
Smart Stand Dispatch
    = stand-preferred, not stand-exclusive

Smart Dispatch
    = stand-agnostic nearby-driver dispatch

Cross-Location Dispatch
    = nearby locations may contribute eligible candidates
      when local supply is insufficient
```

This separation allows discovery mechanisms to evolve independently
from dispatch policy and ranking while ensuring the clarified RideForge
dispatch model is preserved.

The system is therefore prepared to introduce more precise geographic
refinement, routing-aware travel estimates, demand-aware discovery, and
eventually distributed regional dispatch without requiring the Matching
Engine to be rewritten.
